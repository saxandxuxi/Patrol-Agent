# 问答库自动转模板（templatizer）代码评审与整改方案（给 codex）

评审对象：`backend/app/services/templatizer.py`（挖掘 mine_sql / 聚类 _merge_cluster / 回环 _verify / 运行期 match·bind）、触发入口（main.py:77、chat.py:263 approve 后台、generic_api.py:207 手动重建）、产物 `backend/app/data/auto_templates.json`（当前 5 条 mature）。

结论先行：链路骨架（sqlglot AST 挖槽 → 指纹聚类 → 跨样本/domain 确认 → 回填回环 → 结构匹配）是对的，绑定也做了白名单校验。但有 3 个 P0 正确性问题会让它"挖错"或"主力引擎答对的题挖不下来"，以及若干质量、增量、可观测问题。按下面顺序修。

---

## P0-1 路线"名称列"被当成 route_id 槽，绑定值与列对不上（已在库里坐实）

证据：`auto_6e7126a7ae1590ce`（西乡段7月巡检几次）的 SQL 是
`... WHERE r.short_name = '{route_id}' AND p.collection_time >= '{time_start}' ...`
- 槽名固定叫 `route_id`（`_name_for` 630-631 只要 role==route 就命名 route_id），options 的 value 是 32 位 id，但被过滤的物理列是 `r.short_name`（名称列）；该槽 `form=label`，而 samples.values.route_id 存的又是中文"宝安大道西乡段"，三处自相矛盾。
- 对比其他模板 `r.id = '{route_id}'`、form=value、绑 id，是对的。

影响：换路线时可能把 32 位 id 填进 short_name、或把全名填进只存简称的列，直接 0 条或错口径；这类错不报错，最难发现。

修法：
1. 挖槽时区分"被过滤的是路线 id 列还是名称列"。`_fk_display_targets`（172 行）已经掌握外键显示列信息，要把它用到槽生成上：
   - lhs 是 `r.id`/`p.routes_id` → 槽 `route_id`，绑 id（现状）；
   - lhs 是 `short_name/full_name` → 生成 `route_name` 槽、绑规范中文名，**或更稳妥**：在挖槽时把名称谓词归一化成 id 谓词（`p.routes_id = '{route_id}'`），统一只保留 id 槽，避免 name/id 两套。
2. `_name_for` 不能只按 role 命名，要结合物理列；`form`（value/label）必须与最终被替换的列真实存储一致，不能靠样本碰巧对上。
3. 对现有 auto_templates.json 里这条 short_name 模板，重建时归一化成 id 列，别留着错模板。

## P0-2 Wren 编译产物被"表不在白名单：disease"大面积误拒（主力引擎的题沉淀不下来）

证据：auto_templates.json 的 rejects 里，最标准的三条——"西乡段泛油病害有多少处""最大宽度和最大高度""把 luge_name 字段全部调出来"——拒绝原因都是 `表不在白名单：disease`。

根因：`_precheck`（659-666）遍历 `tree.find_all(exp.Table)`，要求每个表名都在 field_catalog 物理表白名单里。但 Wren 编译出的物理 SQL 带 CTE/派生表：
`... FROM (SELECT ... FROM (SELECT ai_problem.* ...) AS __source) AS disease) AS wren_src_disease`
sqlglot 会把派生表别名 `disease`/`route`/`__source` 也当成 Table 节点，它们不在物理表白名单 → 误拒；`wren_src_` 前缀更是 663-664 直接拒（注释写"第一期不做模板化"）。

影响：现在 Wren 是主力引擎，形态越复杂（CTE、窗口、多 JOIN）越依赖 Wren，而这些成功 SQL 恰好全部挖不成模板；能沉淀的只剩内置模板风格的扁平 SQL，自动模板库只会在"内置模板本来就会"的形态里打转，复用价值被自我截断。

修法：
1. 白名单只校验**真实基表**：用 sqlglot 区分 CTE 名/派生表别名（`exp.Subquery` 的 alias、`WITH` 定义名）与物理表，CTE 名和 `__source/disease/route` 这类别名跳过；递归进 CTE/子查询内部校验其真正引用的物理表。
2. `wren_src_` 外壳不要一刀切拒绝：剥掉/下钻到内层，校验内层基表是否全在白名单，在内层基表达标时允许模板化（模板里保留可执行的物理 SQL 即可，不必保留 wren_src 包装）。
3. 校验逻辑抽成"收集 SQL 里的物理基表集合"，`_ctx_for`/白名单/回环共用同一套表解析，避免各认各的。

## P0-3 BETWEEN 区间、排名窗口（rnk=1）被一刀切拒绝（高频问法沉淀不了）

证据：rejects 中
- "k1+802 附近还有哪些病害" → `有不可泛化的条件：p.pile_distance BETWEEN 1802 AND 2801`
- "置信度最高的病害是哪个？类型？桩号？" → `有不可泛化的条件：t.rnk = 1`

影响："某桩号附近/某区间"（BETWEEN 两边界都可参数化）和"最高/前 N + 附带字段"（窗口排名）是高频问法，现在整条放弃。

修法：
1. BETWEEN：识别成同一数值列的下界/上界两个槽（`col >= '{lo}' AND col <= '{hi}'`，或保留 BETWEEN 两个占位符），桩号区间、时间区间都走这个；只有边界不是字面量/不是同一列才放弃。
2. 排名窗口：`rn = 1`（ROW_NUMBER 排名）与 ORDER BY 一起识别为"TopN 固定结构"，rn 比较值当固定结构（=1），ORDER BY 的列/方向、外层 SELECT 的附带字段保留，N 可复用现有 top_n 槽；不要把 `rnk=1` 当普通不可泛化谓词判死。
3. OR / 子查询 / LIKE 自由文本维持拒绝（这些参数位置确实不稳定），但要在 rejects 里区分"暂不支持形态"与"脏 SQL"，便于后续按高频度排期。

## P1-1 单条样本即 mature，回环只验"填回原值"，挡不住错误口径和过泛化

现状：`_merge_cluster` 1114-1122 对 entity/time/numeric/int/op 类型槽，单条样本也按 domain 直接 confirmed → mature 进对话推荐；`_verify`（1178-1196）只把每条样本**自己的值**填回去，比对结构和结果一致。

两个漏洞：
1. 不验证"换一个值是否仍正确"。SQL 里若埋了与原路线强绑定、却没被挖成槽的条件（sections_id、device_code、具体桩号、patrol 编号、上下行），它们作为写死结构保留，换路线就带着错误限定，回环发现不了。当前 5 条 fixed 恰好为空，但机制上没拦。
2. 不验证口径对错。`auto_6e7126` 用 `ai_problem INNER JOIN ai_maintain_patrol` 后 `COUNT(DISTINCT t.id)` 算"巡检次数"——**没有病害的巡检任务会被 INNER JOIN 漏掉**，口径本身错误，但填回原值结果稳定，照样 mature 并会被反复复用。

修法：
1. 换值回环：对 entity 槽用 options 里**另一个**实体（另一条路线）、time 槽用相邻时间各绑定实跑一次，要求能执行、结构签名一致、结果非异常（行数为 0 要能区分"真没数据"还是"条件写错"）；换值后再校验"未挖槽的固定条件里没有引用当前实体的 id/名称"。
2. 固定条件相关性检查：被写死的字面量若出现在路线/路段/设备/巡检编号等实体列上，而本模板又含可变路线槽，则一律不允许 mature（要么挖成槽，要么降级 candidate）。
3. 口径风险类（COUNT(DISTINCT)、多表 JOIN 后计数、EXISTS/子查询计数）默认标 `needs_review`，首条只到 candidate，人工转正或出现第二条同构样本再 mature；巡检/任务次数这类应直接从巡检表计数，不能从病害表 JOIN 推。

## P1-2 病害类型 options 重复、含脏值，且每个模板内联整份字典

证据：auto_1c07…/auto_1dfe…/auto_69bd… 每个模板的 damage_type.options 都内联了 80+ 项字典；同一中文名对应两个 code（泛油→01585e…/9f1873…，大量"一类两码"），并混入明显测试值 `adsad213223`、`eqweqw2313`、`848626`、`45625`、`adsad293826` 等。JSON 文件因此 1600+ 行且三份重复。

影响：卡片下拉出现重复项和假项；multi IN 按 label 取值时容易漏 code 或选错；文件膨胀、维护困难。

修法：
1. options 生成处（`_entity_options` 196）按 label 归并：同中文名的多个 code 合并为一个可选项（multi IN 时展开该 label 下全部有效 code，或按租户/启用状态选定权威 code）。
2. 过滤未启用/逻辑删除字典项和明显假值（非标准 id 形态、测试占位串），以 ai_problem_base 实际启用集为准。
3. 字典类 options 抽成**共享字典**（按 table.column 存一份，带 generated_at），模板 params 里只放引用键，不整份内联；卡片渲染时按引用取。

## P1-3 mine_all 全量覆盖写，会丢模板、重置人工状态

现状：`mine_all` 1248 `_write(templates)` 全量覆盖，而 templates 只来自本次 trusted（`list_recorded_example_pairs(limit=500)`，1208）聚类的结果；`_merge_cluster` 虽接收 existing，但只对本次命中的 fp 生效。

影响：某模板对应的问答对一旦这次没进 trusted（取消收藏、超过 500 截断被分页滚走、样本被删、当次挖掘异常），它就不在 templates 里，被直接抹掉——人工 promote、enabled、usage、created_at 全部丢失。

修法：
1. 改成按 fingerprint 的 **upsert 合并**：本次挖到的更新，没触及的现有模板原样保留。
2. usage/enabled/status/promoted_at/title 以现库为准，重建不重置；只有模板 SQL 指纹失效（基表/列被删）才标记 disabled，不静默删除。
3. trusted 拉取分页拉全（或按更新时间增量），不要 500 截断。

## P2-1 每次 approve 都全量重挖 + 每条样本双查询回环，重复连库

现状：chat.py:263 每次点"答对了"都起线程跑 `mine_all()`；mine_all 对最多 500 条 trusted 全量 parse，`_verify` 对每条样本把"回填 SQL"和"原始 SQL"各跑一次（`_rows_of` 805-808）。高频 approve 时线程虽被 `_LOCK` 串行但会排队，反复全量扫库。

修法：
1. 增量挖掘：approve 只挖当前这一条（按 sql 文本哈希缓存挖掘/回环结果），后台定时（或手动 rebuild）才全量。
2. 回环查询加结果缓存与限流（同指纹、同值不重复跑）；P1-1 的换值回环也走缓存。
3. mine_all 加"正在运行"标志，避免一次 approve 排队起多个全量任务。

## P2-2 match 静默不匹配，命中率/usage 不可观测

现状：5 条模板 3 条 usage=0。match（1352-1458）的硬门槛是 `required.issubset(conditions|fixed|structural)`（1376），plan 的条件命名与模板 declares（route/damage_type/time_range/列名）稍有出入就静默淘汰，不记录原因；comparison/multi_route 直接排除（1356）。

修法：
1. 每个 mature 模板未命中时记录"第一淘汰原因"（缺哪个 condition、shape/subject/group_by/metrics 哪项不符、哪个必填槽取不到值），落日志并在维护页可见，形成"近失清单"，据此补 declares/槽映射，而不是猜为什么没推荐。
2. 收紧过宽画像：list 模板 subjects 同时含 disease、route（auto_1c07 的 match.subjects）容易误命中，subject 以主表为准。
3. 维护页展示每个自动模板的 usage、最近命中/近失原因，形成闭环。

## P2-3 同列多谓词槽名冲突、PG 不覆盖、自由文本绑定

1. 槽名固定：数值槽 `num_{column}`（532）、时间槽 `time_start/time_end`（591）。同一列出现两个阈值、或两条不同时间列时会生成同名槽互相覆盖。修：槽名追加序号或表达式哈希（如 `num_area_1`），declares 仍归一到同一条件域。
2. mine_sql 672-673 只收 mysql，gpsdb（PG）成功 SQL 不沉淀。当前 PG 表空可接受，但应在 PG 出现 trusted pair 后放开（kind 透传、方言用 postgres 解析），避免以后补数据还要改。
3. 绑定安全：op/enum/fragments/int/numeric 已有白名单，注入面可控；但 form=label 时中文 label 经 1501 字符集正则直接拼入，多选按英文逗号 split（1504）对本身含逗号/特殊符号的名称不安全。建议 entity/enum 一律走"label→受控 value/options"映射后再拼，不直接拼自由文本；含分隔符的 label 用 options 精确匹配而非 split。

## 建议修复顺序与验收

顺序：P0-2（打通 Wren 成功 SQL 的沉淀源头）→ P0-1（路线 name/id 槽）→ P1-3（upsert 防丢）→ P0-3（BETWEEN/窗口）→ P1-1（换值回环+口径风控）→ P1-2（options 去重去脏/共享字典）→ P2。

验收：
1. 取一条 Wren 产出的带 CTE/派生表的成功 SQL（如 rejects 里"西乡段泛油有多少处"），mine_sql 能挖成路线槽模板，不再报"表不在白名单：disease"；剥壳后校验的是 ai_problem 等真实基表。
2. short_name 谓词不再生成 route_id 槽；换绑"恒明珠"到任意路线模板，实跑返回的路线与所选一致、非 0。
3. "k1+802 附近"能挖成桩号区间槽；"置信度最高+类型+桩号"能挖成 TopN 结构槽。
4. 取消某条问答对的收藏 / trusted 超过 500 条后重建，其余自动模板（含人工 promote、usage）不丢失。
5. 新建模板用第二条路线、相邻月份各绑定实跑通过；含"写死的与路线相关 id"的模板无法 mature；COUNT(DISTINCT) 口径类默认 candidate。
6. damage_type 下拉无重名、无 adsad/eqweqw 类脏值；auto_templates.json 不再每条内联整份字典。
7. 连续 approve 5 次不触发 5 次全量回环扫库；维护页能看到每个模板的 usage 与未命中第一原因。

## 实施记录：可换的数字都要能挖（2026-09-23，用户反馈）

### 现象

「宝安大道西乡段面积大于 5 平方米的病害占总病害的百分比是多少？」——示例库里有几乎同题的一条，
但挖出来的模板把阈值**写死成 10**，`面积` 也不是可传参的槽；而且这条模板的 `conditions` 里连
面积条件都没有，所以它还会去接**不含阈值**的题（"各病害类型分别多少处"）。

### 根因：挖槽只看 WHERE，不看投影里的 CASE WHEN

`mine_sql` 只把 **WHERE 的顶层 AND 谓词**送进 `_mine_predicate`。而"面积大于 10 的占比"这类题的
阈值住在投影里：

```sql
SELECT COUNT(*) AS 总病害数,
       SUM(CASE WHEN d.area > 10 THEN 1 ELSE 0 END) AS 面积大于10平方米病害数,
       ROUND(SUM(CASE WHEN d.area > 10 THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) AS 占比
```

于是那个 10 原样留在 SQL 里（换阈值复用不了），`declares` 里也没有 `num_area`（条件白丢）。

### 这一轮一起修掉的 5 个相关缺陷

| # | 缺陷 | 修法 |
|---|---|---|
| 1 | 投影里 `CASE WHEN <数值比较>` 的阈值不挖（本次主诉） | 新增 CASE 分支挖掘：**只挖数值阈值**（编码列的"码→中文"映射、分类型列名挖成槽反而错），挖不动就原样保留 |
| 2 | 同一列出现两个阈值时**槽名撞车**：`area > 10 AND area < 100` 挖出的两条占位符同名，绑定时被同一个值覆盖 → **SQL 静默变错**（P2-3.1 早就点过这个风险） | 槽名去重（`num_area` → `num_area_2`）；**同一个** (列,比较符,值) 重复出现时共用一个槽（占比题里 CASE 写了两遍） |
| 3 | 数字写在左边（`10 < p.area`）被判"不可泛化" → 整条 SQL 丢掉 | 识别后翻转成 `p.area > 10` 再走同一套 |
| 4 | 引号数字（`p.area > '10'`，LLM 常这么写）被当成固定值 | 数值列的引号数字照样挖；顺带放开负数 |
| 5 | 占比 SQL 的画像里没有 `ratio` → 挖出来也匹配不上"占比"问题（语义层给的是 `ratio`） | `_ast_profile`：聚合相除（含 `*100/COUNT(*)`）登记 `ratio` |

另外把**别名里写死的阈值**也参数化了：`AS 面积大于10平方米病害数` → ``AS 面积大于{num_area}平方米病害数``，
绑定时整条 SQL 一起替换，卡片表头不会写着"大于 10"却按 5 查。

### 实测（用户原场景）

```
宝安大道西乡段面积大于10平方米的病害有多少处？占总病害的百分比是多少？
   → 命中 auto_116c1bf2553e1f32，槽位 num_area=10、num_area_op='>'
宝安大道西乡段面积大于5平方米的病害占总病害的百分比是多少？
   → **同一条模板**，槽位 num_area=5（默认值来自本轮问题，不用手填）
宝安大道西乡段面积大于 5 平方米的病害有多少处？
   → 同上，num_area=5
```

回归集新增用例 `numeric-threshold-slot`（断言"换阈值要复用同一模板 + 槽位默认值跟着问题走"），
全量 **PASS 20 / FAIL 0**。挖槽侧的写法覆盖度也补了断言以外的抽查：
`CASE WHEN 阈值` / `WHERE 同列两个阈值` / 引号数字 / 整型列(pile_distance) / BETWEEN 五种现在都能挖成槽。

### 事故与恢复（如实记录）

重挖那一条模板时，我误把模板库的键当成 `queries`（真实键是 `templates`），`_write` 收到空列表 →
**模板库被写空**（38 条 → 0）。恢复方式与代价：

- 三个历史备份都只有 5~10 条（都是"某次挖掘前后的片段"），恢复不了 37 条；
- 按示例库**全量重挖**（`mine_all(force=True)`）重建：**38 条 = 37 mature + 1 candidate**，
  与事故前一致；**旧台账里 37 个模板 id 全部未变**（指纹一样说明内容等价），只有那条占比题是新增；
- 代价：`promoted_at`（人工转正标记）、`enabled=false`（用户手工停用）、`usage` 计数这几个
  **运行时标记丢了**（备份里人工转正数为 0，所以主要是 usage）。这正是 P1-3 说的"全量覆盖会丢人工状态"。
- 事故现场留在 `backend/app/data/auto_templates.before_remine.json`（只有台账、没模板），
  重建前的三份历史备份也都在。

教训（建议后面做）：`mine_all` 的写盘入口加一道守卫——**新模板数为 0 而旧模板数 > 0 时拒绝写**
（除非显式 `--allow-empty`），别让一次调用把整库清空。

## 实施记录 2：长对话补全的问题要预处理（2026-09-23，用户反馈）

### 现象（用户原话）

「宝安大道西乡段的 **377 处**"未识别"病害，按桩号分段…」——这句是**长对话接着补全**出来的
（377 是上一轮答案里的数字），被当成模板问法存了下来。查证结果：

- 377 **没有**进 SQL/槽位（SQL 里没有 377，params 只有 route_id）——不是"把 377 定死"，是
  **问法里带着上一轮的痕迹**：模板清单/卡片上写着 377，看着像是"只能查那 377 处"；
  而且这条模板只认那一句话，同类问题复用不了；
- 更麻烦的是这条模板当时**压根匹配不上任何问题**（profile 记成 count/无分组，而 SQL 是按桩号段
  分组的 distribution）——它是 18 条"spec 漂移"里的一个；
- 顺带查出一个**口径漏洞**：SQL 里的 `COALESCE(problem_type_name,'未识别')='未识别'`
  属于"挖不动就原样保留"的谓词，但保留时**没在 match.fixed 里声明** → 一旦 profile 修好，
  这条模板会去接**不含"未识别"**的题，等于偷偷加过滤条件（"按桩号分段统计"只会统计未识别病害）。

### 修法

| # | 改动 | 说明 |
|---|---|---|
| 1 | 新增 `clean_template_question(question, sql)` | 删掉**没在 SQL 里用到的数量短语**（`377 处`/`这 377 处`）；真条件（"面积大于 5 平方米""每 100 米一段"）的数字在 SQL 里找得到，一个不动 |
| 2 | 模板记录的 `question` / `variants` / `samples[].question` / `title` 全部走它 | 增量挖掘时 `base` 可能来自上一版样本（脏问法），`_merge_cluster` 入口再清一遍 |
| 3 | `_fixed_condition_of(predicate_sql)` + `fixed_extra` | "挖不动但原样留在 SQL 里"的条件必须声明进 `match.fixed`/`conditions`（目前识别 `未识别/未知类型/damage_type IS NULL` → `unknown_type`）；模型兜底那条路也带上 |
| 4 | `_ast_profile` 认桩号分段 | `GROUP BY CONCAT('K', FLOOR(p.pile_distance/1000) …)` 记成 `group_by=['pile_bucket']`（语义层对这个维度的取值），否则记成"无分组的计数" |

### 实测

```
问法（新）＝ 宝安大道西乡段的“未识别”病害，按桩号分段（每 100 米一段）统计各段的病害数量，看是不是集中在某一段？
match    ＝ shapes=['distribution'], group_by=['pile_bucket'], conditions=['route','unknown_type'],
            fixed={'unknown_type': 'true'}

宝安大道西乡段的“未识别”病害，按桩号分段统计            → 命中 auto_83d0377e8a6a5a93 ✓
宝安大道西乡段的病害，按桩号分段统计各段的病害数量       → **不命中**（builtin pile_bucket 接）✓
```

回归集新增用例 `context-completed-question`（断言：模板问法里不许再有 `377`、`fixed` 必须声明
`unknown_type`、该模板对"含未识别/不含未识别"两句的命中范围分别正确），全量 **PASS 21 / FAIL 0**。

顺带：这轮挖槽修复后按示例库重挖，模板从 38 条涨到 **43 条**（42 mature）——之前挖不动的
几个问法（CASE 阈值、占比、桩号分段…）现在都能沉淀了。

### 补做：源头侧也清了（用户点头后）

**做法**：区分"留档"和"对外"两种问法——

- 本地 `example_pairs.question` 仍是**用户原话**（含 377）——这是"当时确实这么问过"的证据，
  而且 `doc_name`（示例身份、看板卡片 id）就是按原话+SQL 算的，改了身份就变了；
- 另外记一个 **`spec.display_question`（对外问法）**，原始原句同时进 `spec.variants` 留档。

哪里用对外问法（都已改）：

```
RAGFlow 示例集文档正文 `# 问题`（_example_document）
问题索引集文档正文（question_index_document → 同义召回的向量本体）
看板卡片 question/title（routers/dashboard.py）
同义召回卡片标题「相似已验证问法：…」（capabilities._example_candidates）
模板问法（挖槽时本来就清，见上）
```

入口在 `nl2sql.outward_question(question, sql, spec)`：`spec.display_question` 优先，否则现算。
`save_successful_pair` 入库那一刻就判定一次，脏问法会写 `context_question_cleaned` 日志。

**存量修复**（已跑）：本地 spec 补 `display_question` + 原句进 variants（1 条）；
`renormalize_examples()` 重写 RAGFlow 示例集正文 **73 条（0 失败）**；
`backfill_question_index(force=True)` 重传问题索引 **73 条**。
实测四处显示都干净了：

```
本地 question           = 宝安大道西乡段的 377 处“未识别”病害，按桩号分段…（留档）
spec.display_question   = 宝安大道西乡段的“未识别”病害，按桩号分段…（对外）
看板卡片 question        = 同上（干净）
问题索引集正文           = 同上（干净）
```

### 清洗规则的一个自查（这条差点造成新 bug）

第一版规则是"数字不出现在 SQL 文本里就删"，实测把**真条件**也删了：
`面积等于 7.52 平方米` → `面积等于的`、`置信度大于 0.5 的` → 被顺手吃掉"的"。
原因有两个：① 挖出来的 SQL 里数字已经换成占位符（得看 `values`）；② 我加了一条多余的
"的+标点"清理。

现在的判据（两条任一成立就保留）：**前面是阈值/分段词**（大于/小于/超过/低于/等于/每/前/后/至/到/比较符），
或**这个数字出现在 SQL 文本或参数值里**。全库复扫：73 条示例里只有那 1 条（377）会被清，
43 条模板问法一条都不会变。
