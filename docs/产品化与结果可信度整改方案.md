# 产品化与结果可信度整改方案

> 目标有两个：
> 1. 不再死磕"NL2SQL 100%答对"，用产品手段把高频问题分流、把错误在执行前拦住。
> 2. 让不懂 SQL、不懂数据库的业务用户，也敢相信助手给出的数字。
>
> 本方案大部分是呈现层和交互层的改动，不涉及复杂算法，工作量不大但对实际体验提升明显。

---

## 一、定位先想清楚

NL2SQL 是"辅助查询入口"，不是"唯一入口"。

业界头部产品在业务库上的准确率也就 70~85%，追求"不管怎么问都全自动答对"不现实。正确的思路是：

- 高频固定问题 → 用看板/收藏/筛选器解决，不经过自然语言
- 长尾临时问题 → 走自然语言，执行前复述确认、执行后给可信证据
- 答错的 → 一键反馈攒成 bad case，规律性问题批量修

这样自然语言的压力小了，用户实际感受到的错误率也低了。

---

## 二、查询前：大白话复述确认

### 现在的问题
SQL 生成后直接执行，理解错了用户也不知道，等看到离谱答案才发现。

### 改成
SQL 生成后、执行前，先用一句人话把统计口径复述出来，让用户确认：

> 我将查询：**宝安大道西乡段**、**2026年7月**、**泛油病害**，按**病害类型**分组，统计**数量和面积**。
> [确认查询] [不对]

规则：
1. 简单问题（"西乡段泛油有多少处"）不确认，直接查，别把交互搞重。
2. 复杂问题（多条件、多维度、对比、分析类）才确认。
3. 用户点"不对"，让他用大白话说哪里不对，把纠正拼回问题重走一遍（复用现在的问题优化链路）。
4. 复述的内容来自语义槽位（路线/时间/类型/分组/指标），不是把 SQL 翻译一遍。

这一步等于把"校验 SQL 对不对"的压力，从 LLM 转移给看得懂业务的用户——用户判断口径对不对，比让模型猜 SQL 对不对准得多。

---

## 三、查询后：怎么让外行相信数字是对的（重点）

用户看不懂 SQL，他判断"对不对"靠的是：口径清不清、数字能不能对上、能不能抽查、异常有没有交代。下面八件事，每一件都不复杂。

### 1. 给"人话口径卡片"，不要给 SQL

每个回答下面附一段统计说明，说清五件事：统计范围、时间范围、统计对象、排除了什么、数据来源。

示例，用户问"西乡段泛油有多少处"，不要只回"534处"，要回：

> 宝安大道西乡段共有泛油病害 **534 处**。
>
> 统计口径：
> - 范围：宝安大道西乡段（K0+000~K0+887，全长 5.10 公里）
> - 时间：该路段数据实际覆盖 2026-07-15 ~ 2026-07-30
> - 对象：AI 识别为"泛油"的病害，已排除已删除、已忽略记录
> - 来源：车辆巡检 AI 识别数据，截至 2026-07-30 17:26

口径卡片的内容直接从语义槽位和实际 SQL 条件生成，不需要额外查库。

### 2. 让数字自己证明自己：分项加总要等于总数

外行最朴素的验证方式就是"加起来对不对"。回答里把算式摆出来：

> 西乡段全部病害 911 处 = 泛油 534 处 + 未识别 377 处
> 泛油占比 = 534 ÷ 911 = 58.6%

密度类问题把公式摆出来：

> 病害密度 = 911 处 ÷ 5.10 公里 = 178.6 处/公里
> 平均间距 = 5100 米 ÷ 911 处 = 5.6 米/处

用户看到分项加起来等于总数、公式摆得明明白白，自然就信了。这要求结果总结环节必须做一次"数字自洽核对"：各分项之和与总数不一致时，要么重算，要么明确说明差异（比如有未归类项）。

### 3. 每个汇总数字都能点开看明细（抽查机制）

给用户审计的能力，比把 SQL 贴给他更让他放心：

> [查看这 534 条泛油病害明细]（桩号、类型、面积、采集时间、现场图）

用户不会全看，但他抽查两三页，发现桩号、时间、图片都对得上，就敢信了。明细本来就是现成的查询结果，前端加个下钻入口即可。

### 4. 直接带两三条真实记录当"样例"

光有数字是空的，回答里直接带 2~3 条真实数据：

> 其中包括：k0+020（7月30日采集，面积 1.2㎡，有现场图）、k0+202（7月29日，0.8㎡）……

有具体桩号、有时间、有图，可信度立刻上来。

### 5. 主动暴露边界和异常（主动说丑话最加分）

藏着掖着才让人怀疑，主动交代反而极大增加信任：

- "数据只覆盖 7月15日~30日，不是完整的7月"
- "另有 42 条病害没有归属路线，未计入本路段统计"
- "其中有 1 条面积 5000㎡，明显异常（疑似录入问题），已在平均值中标注"
- "有 73 条病害 AI 未识别出类型，归为'未识别'"

把这些异常从数据里检测出来（空归属、异常大值、未识别类型、时间覆盖不全），固定在口径卡片里展示。

### 6. 给对比基准，孤立的数字没有意义

单独一个 534 处，用户没感觉。给对比：

> 泛油是西乡段数量最多的病害类型，占全部病害的 58.6%；
> 对比宝安中心--恒明珠段，泛油 402 处、占该段 53.7%。

有了基准，用户才能判断"这个数正不正常"。

### 7. 确定性分级，别一本正经地胡说

回答要区分三种语气：

- 库里直接查到的 → 直接给数字
- 推算出来的（密度、占比、分档）→ 写明"按 XX 口径推算"
- 库里没有的 → 明说"系统中没有这个数据"，绝不硬编

用户最不能接受的是"很自信地给了个错答案"。诚实标注不确定性，信任度反而高。分档类问题（新病害/老病害、密集/稀疏）必须把分界线写出来（"按采集时间中位数7月29日17:27划分"），不能黑盒给两个数。

### 8. 标数据新鲜度

每个回答标"数据截至 XXXX-XX-XX"。业务用户第一个疑问往往是"这数据是不是最新的"，直接回答掉。

### 可信回答的完整样例（对照）

现在的回答：

> 共 534 处。

改完之后：

> 宝安大道西乡段共有泛油病害 **534 处**，是该路段数量最多的病害类型。
>
> 构成核对：泛油 534 处 + 未识别 377 处 = 全部 911 处，泛油占 58.6%
> 典型记录：k0+020（7月30日，1.2㎡，有图）、k0+202（7月29日，0.8㎡）
> 统计范围：西乡段 K0+000~K0+887（5.10公里），数据覆盖 7月15日~30日，已排除删除/忽略记录
> 数据截至 2026-07-30 17:26
> 另有 42 条病害无路线归属，未计入
>
> [查看534条明细] [查看现场图]

## 四、答错反馈闭环

每个回答下方加"答对了 / 答错了"两个按钮。

- 点"答错了"，让用户用一句话说哪里不对，自动把：原始问题、补全后的问题、SQL、结果、用户反馈 一起存下来。
- 不追求自动修复。每周或每攒够一批，翻一遍 bad case，规律性的问题批量改提示词/MDL。
- 系统变好靠的是真实 bad case 的积累，不是靠拍脑袋想测试题。

## 五、把高频问题从自然语言分流出去

### 1. 验证过的问题一键查询（预置 SQL，最直接、最省钱）

把已经测成功、答案核对过的题目和对应 SQL 固化下来，放到前端做成问题卡片，用户点一下直接出答案，**不经过 LLM、不花一分钱、毫秒级返回、结果 100% 确定**。

这不是新发明，就是把测试集里验证过的 SQL 从"测试材料"变成"产品功能"。

后端怎么做：
1. 新增一张预置查询表（或一个配置文件 preset_queries.json），每条记录包含：
   - id、分类（病害统计/巡检任务/路线对比/养护分析）
   - 问题文案（用户看到的）
   - SQL 模板（参数化，路线、月份用变量占位）
   - 参数定义（哪个变量是路线、哪个是月份，对应下拉选项来源）
   - 口径说明（直接喂给第三章的口径卡片）
2. 新增接口 /api/preset-query：只接收"预置查询 id + 参数值"，后端从白名单取出 SQL 模板、绑定参数后执行。
3. 安全红线：前端只能传 id 和参数值，不能传 SQL 本身；参数只能作为绑定值，不能拼接进 SQL 结构，从根上杜绝注入和乱查。
4. SQL 模板尽量参数化，一条覆盖一类问题。比如"XX路段泛油有多少处"只写一条模板，路线用变量，西乡段、恒明珠都能点。

前端怎么做：
1. 对话页和悬浮球首页按分类摆问题卡片，例如：
   - 西乡段泛油有多少处
   - 各路线病害密度排名
   - 7月份巡检了几次、每次发现多少
   - 待转工单的病害有多少
2. 不带参数的，点击直接出答案；带参数的（路线/月份/类型），弹一个小选择器让用户选，选完直接查。
3. 返回结果照样走第三章的可信呈现（口径卡片、分项加总、明细下钻）。

数据从哪来：从已经跑通的问答数据集里挑，SQL 都是核对过真实答案的。以后每修好一类 bad case、验证通过，就沉淀成一条预置查询——越用越多、越用越准，这是比改提示词更稳的积累方式。

自然语言和预置查询的关系：用户自由提问还走原来的 NL2SQL；当自然语言没把握、或者命中了高频问法时，前端可以主动推荐"要不要直接看【XX】的固定统计"，把用户往确定的结果上引导。

### 2. 固定看板
把最常见的固定问题做成看板，点一下就出，不走自然语言：
- 各路线病害总数/密度/类型分布
- 月度病害趋势
- 巡检任务次数与发现量
- 待转工单病害数量

自然语言只处理剩下的长尾临时问题。

### 3. 查询收藏
查过一次的问题可以收藏，下次直接点。业务人员常问的就那几十个，收藏夹等于用户自己维护的模板，不用开发写代码。

### 4. 半自动筛选器
给一个点选界面：路线（下拉）+ 时间（日历）+ 病害类型（下拉）+ 指标（下拉），点选出数。点选覆盖不了的再打字问。

### 5. 输入框推荐问法
输入框上方按场景放示例（病害统计、巡检任务、路线对比、养护分析），用户会照着系统能理解的句式问，命中率自然上去。看起来笨，但所有 To B 问答产品都在这么做。

## 六、其他小改动

1. 0 结果给相近数据：查的时间没数据，直接说"数据实际覆盖 X~Y，要不要看这个范围"（calibrate 已在做，继续强化）。
2. 异常值主动提醒：5000㎡ 的病害、多次巡检数量完全相同，主动标注疑似数据问题（这类判断可固化成确定性规则）。
3. 列表/明细类回答不要硬套极值结论：104 行明细后面不要再加"k0+193最多"这种没意义的总结。

## 七、悬浮球内嵌方案（嵌入巡检业务平台）

### 目标
助手以悬浮球形式内嵌到现有巡检平台页面右下角：
- 平时是一个小气泡，不占地方
- 点开是精简聊天窗，完成日常提问、看预置查询结果、看口径和明细
- 需要知识库管理、数据库浏览、模型配置这些重功能时，点"打开完整工作台"，新窗口跳到现在的完整平台页

### 现状（已确认可行）
- 前端是 Vue3 + Vite，App.vue 是"顶部导航 + 四个 tab（对话/知识库/数据库/模型设置）"的完整平台。
- 后端是 FastAPI，已经开了 CORS，接口都是标准 HTTP（/api/...），并且打包后的前端由后端静态托管，本来就有独立访问 URL。
- 所以"嵌入别的平台"在技术上没有障碍，差的只是一个精简形态的入口。

### 两种落地方式

方式一：iframe + 模式参数（最快，建议先做）
1. 前端支持 URL 参数 ?mode=widget：widget 模式下隐藏顶部导航和知识库/数据库/模型设置三个 tab，只渲染 ChatPanel，并去掉外层页面边距，背景透明。
2. 巡检平台页面自己画一个悬浮球，点击展开一个小窗，里面用 iframe 指向 `http://智能体地址/?mode=widget`。
3. ChatPanel 里加一个"打开完整工作台"按钮，用 window.open 打开不带 widget 参数的完整页面。
4. 优点：现有代码几乎不动，一两天能上；缺点：iframe 有边框、和宿主页面通信受限。

方式二：打包成 JS SDK / Web Component（体验最好，二期）
1. Vue3 原生支持 defineCustomElement，把聊天窗打包成一个自定义元素（如 <road-copilot>），再带一小段悬浮球样式和展开逻辑，产出一个独立 js。
2. 巡检平台只需引入这个 js、加一行标签，页面右下角就出现悬浮球，没有 iframe 边框，样式天然隔离。
3. 完整工作台仍然用现在的独立页面，按钮新窗口打开。
4. 优点：原生嵌入、体验一体；缺点：Vite 打包配置要调一次。

不建议把 ChatPanel 源码直接拷进巡检平台仓库，后续两边更新会互相拖累。

### 悬浮球里放什么、不放什么
放（轻、高频）：
- 对话输入和自然语言问答
- 预置问题卡片（第五章第 1 节），一键出答案
- 结果的精简呈现：结论数字 + 口径卡片 + 明细下钻入口 + 图片
- "打开完整工作台"入口

不放（重、低频，留给完整页面）：
- 知识库管理、数据库/Schema 浏览、模型设置
- 大批量明细表格的复杂操作、导出

### 内嵌要处理的三件事
1. 跨域：后端 CORS 已支持，把巡检平台的域名加进 cors_allow_origins 配置即可。
2. 登录态：目前系统没有登录。如果巡检平台有登录，需要约定 token 透传方式（URL 参数或 postMessage 传入，后端校验），这个等对方平台的鉴权方案明确后再接；内网环境也可以先按可信来源放开。
3. 网络可达：宿主页面和智能体后端网络要通；如果两边不在一个域，统一走网关反代，避免浏览器混合内容和跨域问题。

## 八、优先级

第一批（工作量小、体感最强）：
1. 人话口径卡片 + 分项加总核对 + 数据新鲜度（可信度的核心）
2. 明细下钻入口（本来就有明细数据，前端加入口）
3. 答错反馈按钮 + bad case 收集
4. 预置验证 SQL 一键查询：先把测试集里已核对过的高频题固化成卡片，零成本秒出

第二批：
5. 复杂问题查询前大白话复述确认
6. 输入框推荐问法
7. 异常/边界主动提示固化成规则
8. 悬浮球 widget 模式（方式一：?mode=widget + iframe），先嵌进巡检平台试用

第三批：
9. 固定看板分流高频问题
10. 查询收藏、半自动筛选器
11. 悬浮球升级为 JS SDK / Web Component（方式二）
12. 预置查询后台维护界面（不发版就能增删问题卡片）

做完第一批，即使 SQL 正确率一个数字没变，业务用户感受到的"靠谱程度"也会明显提升——因为他看得懂口径、对得上数字、抽查得了明细、异常有人交代。
