# 推荐卡硬推荐：指标空匹配（给 codex）

## 一、现象
问"西乡段的纬度范围"，推荐卡第一名是"西乡段和恒明珠分别是几车道"，第二三名是"西乡段泛油桩号""7月29日泛油明细"——全和纬度无关。真正对的同义问法"西乡段的经度范围"排在后面。

## 二、复现（已跑）
build_query_plan("西乡段的纬度范围")：
- shape=list, subject=route, group_by=None
- **metrics=[]、output_fields=[]**（语义层没认出 lat 是指标、"范围"是 min/max）
- required_conditions=['route']

templatizer.match 结果：
- [4.62] 西乡段和恒明珠分别是几车道（missing=[]，全槽填齐）
- [4.17] 西乡段泛油桩号（missing=['damage_type']）
- [3.72] 7月29日泛油明细
- [3.35] 泛油面积>1

## 三、根因
1. **语义层把"纬度范围"解析成了空 metrics**：只认出"关于一条路线的查询"，没把 lat/min-max 抽成指标。
2. **card_for_template 的指标检查对空集恒真**（templatizer.py:2019 `metrics.issubset(模板metrics)`）：问题 metrics=空集，空集是任何集合子集 → 任何带具体指标的模板都过指标检查。
3. 于是只要 subject=route、条件只要 route 的模板都套得上；全槽填齐的"几车道"score 最高排第一——路线对得上而已，指标完全对不上。
4. 同义问法"经度范围"是真同义，却被 auto(tier 0) 压在 example(tier 1) 后面。

## 四、整改
1. **问题指标为空时，不收"带具体指标"的 auto 模板**：card_for_template 加一条——若 plan 的 metrics/output_fields 都空，而模板声明了具体 metrics（车道数/面积/泛油/置信度这类），直接不匹配。你不知道用户要哪个指标，就别把一个"有明确指标"的模板硬塞给他。
2. **这种"指标未解析"的题，优先交给同义召回 + 通用算子**：纬度范围→经度范围同义、里程桩点纬度通用算子，才是对路的；auto 结构指纹对它没区分度。
3. **同义度高的 example 压过指标对不上的 auto**：tier 不再 auto 恒 0；"经度范围"这种高同义 example 应排在"几车道"前面。
4. （提示词侧）planning 要把"纬度/经度范围""海拔范围"这类解析成 metrics=[对应经纬度列的 min/max]，不要 metrics=[]。

## 六、上游根因：字段触达跑在 LLM 规划之后（更关键）
实测 field_grounding.ground("mysql","西乡段的纬度范围") 其实**找对了**：
- 落点表 = basic_facilities_sections_pile_detail（里程桩点表）
- 触达列 = lat，label=纬度，score=4.0，"列名命中：纬度"

但 nl2sql.py:1274 是在 **LLM 规划完之后**才跑 ground：
```
LLM 先规划（看不到任何列，metrics=[]、subject=route）→ 规划完才 ground → ground 找到 lat
```
ground 结果只塞进 plan["grounded"] 供后续拼 SQL，**不会回头改 LLM 已定的 metrics/output_fields**。于是 LLM 在规划阶段是"瞎猜"——不知道库里有"纬度"这列。

修法（顺序前置）：
1. 把 ground 提到 LLM 规划**之前**；
2. 把 ground 挑出的候选表/列（如"lat=纬度，里程桩点表"）写进规划 prompt；
3. LLM 再规划 → metrics=[lat]、output_fields=[纬度]、"范围"→min/max。
这样"纬度范围"metrics 不再空，后续 auto 模板也能靠 metrics 把"几车道/泛油"卡掉。

## 五、验收
1. "西乡段的纬度范围" → 不再推荐"几车道/泛油桩号/7月29日泛油"；推荐里应优先"经度范围"同义问法或"里程桩点纬度"通用算子；
2. "西乡段的经度范围"同理不被 route 类模板硬套；
3. 现有 38 条模板自匹配不回归（有明确指标的题照常命中对应模板）；
4. 提醒：codex 刚改 example_reuse.py 中途出现过 IndentationError，现已编译通过，需重启后端生效。

## 七、本轮实施与实测记录（codex，2026-09-23）

### 7.1 实际改了什么（对 §四）

§四.1「指标为空时不收带指标的模板」按方案落地；但**光堵这一条不够**——纬度题被硬推荐的上游原因是"指标压根解析不出来"。所以本轮的主修在 §四.4（提示词侧）与"冷门列白名单"上：

| 文件 | 改动 | 为什么 |
| --- | --- | --- |
| `backend/app/services/field_catalog.py` | 新增 `metric_names()` / `output_field_names()` / `field_vocabulary()` | 原来的指标/字段白名单是写死的 13 + 10 个短名单，字段目录里别的列即使存在也被过滤掉，`metrics=[]` 就是这么来的 |
| `backend/app/services/nl2sql.py` | `parse_semantics` 改用 `_semantic_metric_names()` / `_semantic_output_field_names()`；新增 `sql_covers_fields()` | 白名单扩到「短名单 ∪ 字段目录」，语义层给出的 `min_lat`/`max_lat` 不再被丢掉 |
| `prompts/query_semantic.md` | metrics 说明补「任意数值列的 `<聚合>_<列名>`」+ 举例；output_fields 说明补「字段目录里的任意列名」；user 段注入 `<<fields>>` | 让 LLM 知道库里有一列叫"纬度" |
| `backend/app/services/templatizer.py` | `card_for_template` 两道过滤：①问题 metrics/output_fields 都空而模板声明了指标 → 不匹配；②问题点名列、bind 出的 SQL 不含这些列 → 不匹配 | 直接治"几车道"被硬推荐 |
| `backend/app/services/capabilities.py` | `_code_template_candidates` 同款「SQL 必须体现点名列」检查；`expressible` 白名单补 `short_name` / `full_name` | 语义层有时直接给物理列名，原来只认 `route_name`，"基本情况"的 route_info 会被丢 |
| `backend/app/config.py` / `.env` / `.env.example` | 23 个可调项（`CAPABILITY_LIMIT`、`RAG_DIRECT_*`、各 TTL、`GENERIC_DETAIL_LIMIT`、`ANALYSIS_NUMERIC_RATIO`、`NUMBER_COMPARE_EPSILON` 等），全部带中文注释 | 用户要求：阈值不许写死在代码里 |

白名单扩充后的实测规模：字段目录 **17 张表 / 592 列**；`metric_names` **213** 个、`output_field_names` **320** 个。

注意一个隐含事实：`field_catalog._field_rows()` 只有 **324** 行，它是**按列名去重**的（同名列表记进 `alts`），所以"600 多个字段全部可达"这件事不能只看 `_field_rows()` 的长度——本轮把可达性判据改成了"列名级并集"，这才是 592 列里冷门列也能被语义层看到的实际条件。

### 7.2 §六（把 ground 前置到 LLM 规划之前）——**试了，回退了，不采纳**

按 §六 实现过一版：`field_grounding.ground()` 提到 `parse_semantics` 之前跑，结果压成 `_grounding_hint()` 写进 prompt 的 `<<grounding>>`。实测**有害**：

```
宝安大道西乡段的基本情况是什么样的？
  前置后：subject 从 route 变成 asset（"基本情况"命中了 basic_facilities_bridges 的列注释）
          → route_info 模板不再命中
  回退后：subject=route，内置模板 route_info 命中 ✓
```

原因是字段注释存在跨表歧义（"基本情况"在桥梁表里也是列），把 raw ground 结果前置等于用**弱信号**（列名匹配）抢占**强信号**（整句语义）的决策位，正好违反"不许弱信号优先"的总原则。

**替代放法**（已落地、已实测有效）：把"列清单"前置（`<<fields>>`，即 `field_vocabulary()` 输出的候选表列名+类型），而把 `ground()` 留在原位不动。这样 LLM 规划阶段**看得到列**（能给出 `metrics=['min_lat','max_lat']`），但不被某一列的匹配结果**强行指定主体**。`_grounding_hint()` 保留在代码里但**当前未被调用**（没有调用点，不产生副作用）。

## 八、§四.3 那道闸原来漏了"缺槽的弱候选"（2026-09-23 补）

§四.3 的规则是"问题点名了列、模板 SQL 里没有那一列 → 不匹配"。它写在
`card_for_template` 里"槽位齐全、SQL 拼出来了"的分支里，**缺槽的弱候选（卡上还要用户补参数的）
会绕过它**。实测「西乡段的纬度范围」每次都用新进程跑（语义层重新判）共 5 次：

```
3 次 → 前三名是 auto_1dfe118d / auto_2920a2fc / auto_04a40f38（"…有多少处泛油"，缺 damage_type 的弱卡）
2 次 → 第一名 generic_geo:basic_facilities_sections_pile_detail ✓
```

差别只在语义层把主体判成 route 还是 asset（判成 route 时那几个模板的 `subjects` 正好命中）。
已把这道闸提到槽位判定**之前**、直接判模板自带的 SQL（`sql_covers_fields`）；修完再跑 4 次全部第一
是 generic_geo。37 条 auto 模板的自匹配命中数不受影响（19→20，仍在抖动区间内）。

顺带说明：上一轮 §7.4 那 3 条注册表不一致也已改完（`builtin_registry_issues()` 现在返回 0，
`route_density` 接上 `_build_density_template`、新增 `pg_point_query` 对接 `_build_pg_template`），
详见 `docs/代码走查与目录结构重构方案.md`。
