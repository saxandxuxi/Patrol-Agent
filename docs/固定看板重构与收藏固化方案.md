# 固定看板重构与"收藏即固化"方案

这份方案解决三件事：让看板和快捷查询有明确分工；把对话框里"问对了"的问题一键固化成看板卡片，下次点一下直接出最新数据、不再为生成 SQL 付费；预置查询维护时能看到已有 SQL 模板作为仿写样例；并清理掉定位重复的半自动筛选。

## 一、先理清三个板块的定位（解决"杂"）

现在的问题是三种角色、两种引擎混在一屏。重新划分后：

- 对话（含悬浮球）：唯一的自由提问入口。问对了，点"⭐ 固化到看板"。
- 固定看板（Workbench 主页）：用户自己的常用问题仪表盘。卡片来自"对话里收藏固化"，每张卡片背后是已经生成好、用户确认过对的查询，点"刷新"直接取最新数据。面向所有使用者，不需要会写 SQL。
- 快捷查询（PresetQueries 页）：系统级、管理员预先做好的参数化模板（现在的 22 条），特点是带"路线/月份/类型"等可换的参数槽，零大模型、毫秒级。
- 管理区（高级，默认收起或单独入口）：预置查询维护、知识库、数据库、模型设置。"预置查询维护"从看板页移到这里，它是管理员功能，不该和看数卡片同屏。

一句话区分快捷查询和固定看板：快捷查询是"管理员提前做好、可以换参数"的标准模板；固定看板是"我自己问过、确认对、想天天看最新值"的一键刷新卡片。

## 二、核心：把"收藏"升级成"固化查询"

> 修订（以第七章为准）：不再新建独立的 saved_queries 表、也不保留单独的 ⭐ 收藏按钮。固化能力直接复用现有的示例库（本地 example_pairs 表 + RAGFlow"SQL问答示例"数据集）——用户点"答对了/approve"即自动入池，等于默认收藏。下面 2-6 小节描述的"固化时存什么、怎么重放、时间口径、卡片交互"在概念上仍然成立，但落地载体从 saved_queries 改为在 example_pairs / RAGFlow 示例记录上扩展字段（shape、produces、intent、归一化 SQL、问法变体、可信分级、pin 标记），看板卡片直接读示例库和模板库。详见第七章。

### 1. 现状与缺口

- 收藏接口 save_favorite 现在只存问题文本（store.py 的 favorites，user_memory 里，最多 50 条）。
- 前端 favorite()（ChatPanel.vue 360-376 行）手里其实有 msg.result_id，但只把问题文本传给了后端。
- 点收藏夹走 sendMessage()，等于重新做一遍意图分类、选表、SQL 生成、校验，token 一分不少。
- 而每次问答的完整产物（intent、单条 sql 或多段 sections、rows、images、references）已经在 result_cache 里，query_history 也长期存了 intent/sql_text/result_id/summary。缺的只是收藏时把这份"可重放计划"落库。

### 2. 固化时存什么：按五类意图分别保存

收藏时前端把 result_id 一起传上来，后端从 result_cache 取完整 payload，抽取成一份 replay_spec 落库（result_cache 有 TTL 会清理，所以 SQL 文本必须在收藏时复制进固化表，不能只存 result_id）。五类意图的存法：

- data（明细/计数）：存最终 SQL、数据库类型（mysql/postgresql）、标题、口径。重放零大模型。
- image（看图）：存取图片的 SQL（查 problem_url/preview_url 等）和图片后处理方式。重放零大模型，跑完 SQL 直接渲染图片。
- analysis（统计/分布/趋势/对比）：存取数 SQL，外加这一步的分析任务描述（用当时 section 的 title/question 作为分析口径）。重放时跑 SQL 取最新数，只调一次大模型做"结果到结论"的分析，跳过意图分类、选表、SQL 生成、校验这些最贵的步骤。
- knowledge（规范/工艺/处置，不查库）：没有 SQL，存问题和检索到的数据集名称（datasets）。重放时重新检索知识库并回答一次（规范文件可能更新，不能把答案焊死），但跳过意图判断和规划。
- composite（数据+知识的综合题）：按 sections 逐段存，每个 section 存 type 和对应的 sql/数据集/分析口径。重放时按下文第四节的顺序逐段重放。

### 3. 固化表结构（新增，建议 SQLite 建表，风格对齐 store.py 现有表）

```
CREATE TABLE IF NOT EXISTS saved_queries (
  id TEXT PRIMARY KEY,              -- uuid
  title TEXT NOT NULL,              -- 卡片标题，默认=问题，可改
  question TEXT NOT NULL,           -- 原始完整问题
  intent TEXT,                      -- knowledge/data/analysis/image/composite
  db_kind TEXT DEFAULT 'mysql',     -- mysql/postgresql；knowledge 为空
  replay_spec TEXT NOT NULL,        -- JSON，见下
  scope TEXT DEFAULT '',            -- 口径说明（展示给用户，建立信任）
  group_name TEXT DEFAULT '默认',   -- 看板分组
  pinned INTEGER DEFAULT 0,
  created_at TEXT, last_run_at TEXT,
  last_summary TEXT DEFAULT ''      -- 最近一次结果摘要，卡片上直接显示
);
```

replay_spec 是 JSON：
- 单查询（data/image/analysis/knowledge）：{"kind": "...", "sql": "...", "datasets": [...], "analysis_brief": "...", "image_mode": "..."}。
- composite：{"sections": [{"type":"data","sql":"..."},{"type":"image","sql":"...","image_mode":"..."},{"type":"knowledge","datasets":[...]},{"type":"analysis","analysis_brief":"..."},{"type":"post_calc","rule":"..."}], "order":[...]}。
- 安全标记 source 必须是系统生成（wren/template/preset/post_calc），不接受用户手填 SQL 进入这张表；手填 SQL 仍只走管理员预置模板那条白名单链路。

### 4. 重放接口

新增 POST /api/saved-queries/{id}/run，逻辑：

1. 取出 replay_spec，按类型执行。
2. data/image：直接用 sql_engine 执行存好的 SQL；image 类型跑完后复用现有 _image_result 的图片组装逻辑（取 URL、SeaweedFS 展示）。
3. analysis：先执行取数 SQL，再调用现有的分析服务（agent._analysis_payload / analysis_service.analyze）把"最新 rows + analysis_brief"喂给大模型出结论，只此一次大模型调用。
4. knowledge：复用 _answer_knowledge(question, datasets) 重新检索回答。
5. composite：按 sections 顺序重放——data/image 段执行 SQL，knowledge 段重新检索，analysis 段用前面刚查出的最新结果做分析，post_calc 段用现有 _post_calc_payload 重算；最后沿用现在 composite 的结论组装方式输出。也就是把 agent 里"规划、拆子问题、逐段生成 SQL"整段跳过，只保留"执行 + 末段分析"。
6. 返回结构和 /api/chat 对齐（reply、columns、rows、sections、images、chart_data、intent），前端 ResultPanel 直接能渲染，不用为看板单独写结果展示。

安全约束：执行前校验 SQL 只能是 SELECT/WITH 开头、不含写操作和多语句；强制包一层 LIMIT 上限（明细类）；只读账号；固化 SQL 来源必须是系统生成。

### 5. 时间口径：固化的是"怎么查"，不是"旧数字"

卡片点刷新要的是最新数据，但有些 SQL 带绝对时间（如 2026 年 7 月）。两档处理，一期做简单的：

- 默认原样重跑，卡片上明确展示口径里的时间范围（例如"2026 年 7 月"），用户知道自己在看哪一期。
- 对带 collection_time 绝对月份的查询，保存时识别出月份字面量并替换成 {month} 占位，重放默认取"最新有数据的月份"（复用 preset.py 里 months 动态选项的取法）；卡片上标注"跟随最新数据周期"。路线 id、病害类型这类稳定主键不替换。
- 一期不做更复杂的自动参数化（路线换值等），那是快捷查询模板的职责；固化卡片先保证"一键刷新同一问题"。

### 6. 前端交互

- 对话每条带 result_id 的回答，操作区现在是"⭐ 收藏 / 查看这次结果"。把"⭐ 收藏"改成"⭐ 固化到看板"，点击时把 question + result_id 一起提交。
- 弹一个轻量确认框：标题（默认问题，可改）、分组（默认"默认"，可新建）、时间口径提示；确认后落成卡片。
- 固定看板页改成卡片网格：每张卡片显示标题、意图类型标签（数据/分析/看图/规范/综合，用不同颜色但克制）、最近结果摘要（last_summary，如"共 911 处"）、最近刷新时间；卡片上有"刷新"和"展开"和"移除"。
- 点"刷新"调重放接口，按钮 loading，回来就地更新摘要；点"展开"用 ResultPanel 展示完整表格/图片/分析（和对话里"查看这次结果"同一个组件）。
- 支持分组和置顶；空状态引导"去对话里提问，点⭐就能加到这里"。

## 三、预置查询维护：能看到 SQL 模板、能仿写、能让 AI 帮写

现在编辑弹窗 SQL 框是空的，根因是 GET /api/preset-queries 返回列表时刻意不带 sql（preset.py 158-168 行，安全红线是"前端不能提交自定义 SQL 执行"）。展示已有模板 SQL 给管理员看并不破坏这条红线，照下面改：

1. 列表接口增加管理态参数：GET /api/preset-queries?with_sql=1（仍走 require_token 鉴权），管理页用它拿到含 sql 的完整内容；普通运行端（快捷查询页、看板）继续拿不到 SQL。编辑某条时用 with_sql 的数据把 SQL 回填到文本框，解决"打开是空白"。
2. 新增/编辑弹窗里增加"仿写示例"区：按分类列出其他模板的标题和完整 SQL（只读、可折叠、可复制），让不会写的人照着改。占位规则在示例里能直接看到（{route_id}、{month}、{damage_type}、{up_or_down}、{bucket_m}、{top_n}），并在旁边写清每个参数的取值来源（路线/月份/病害类型连库现查，其余静态白名单）。
3. 增加"让 AI 帮写草稿"按钮：把用户填的标题/问法/所选参数，加上现有模板示例和相关表结构说明，发给大模型，产出一版草稿（id、category、title、question、params、sql、scope），填回表单供人工核对。保存仍走现有 POST /api/preset-queries，后端照旧校验参数必须在 params 段定义、SQL 落库、运行时只做白名单值绑定。AI 只生成草稿、人确认后才存，不直接生效。
4. 不会用的人可以直接截这个弹窗（含示例和表结构）的图给外部 AI，让它照着写好再粘回来——所以示例区要让一屏内能同时看到"字段 + 一条完整样例 SQL"。

## 四、下线半自动筛选

Workbench 里的"半自动筛选"建议直接移除，理由：

- 它的"要什么"是前端写死的 4 个句式（Workbench.vue metricOptions），和预置查询维护里的 22 条问法没有任何绑定，维护里加得再多它也不会多。
- 它拼出的话走的是 /api/chat（大模型），不是确定性模板，名字叫"半自动筛选"却既不确定性、也不省成本，和固定看板、快捷查询的定位都重叠。
- 它想满足的两类需求已有更好的归属：标准高频统计走快捷查询的参数模板；任意新组合去对话问，问对了固化成看板卡片，之后零成本刷新。

如果短期不想删，至少把它从看板页移走并明确标注"AI 理解、结果需核对"，不要和确定性卡片放在一起误导使用者。本方案建议直接删，相关的 askFiltered/metricOptions 一并清理。

## 五、落地步骤

1. 后端（以第七章两层库为准，不建 saved_queries）：扩展 example_pairs 表与 RAGFlow 示例记录，补齐 shape、subject、produces、intent、归一化 SQL、问法变体、可信分级（trusted/待确认）、pin/分组字段；approve 即入池作为默认收藏，下线只存问题文本的 favorites 和对话里的 ⭐ 收藏按钮（可做一次数据迁移）。
2. 后端：实现示例/模板卡片的"运行"接口（列表、pin/移除、分组、运行）；运行按意图分流，data/image 直接填参执行，analysis/composite 先取数再用 _analysis_payload 结合结果和规范做一次分析，knowledge 重新检索；复用 agent 现有 _image_result、_analysis_payload、_answer_knowledge、_post_calc_payload，不重写规划逻辑。
3. 后端：preset 列表支持 with_sql，弹窗示例数据接口（可直接复用 with_sql 列表）。
4. 前端：对话结果区保留"答对了/approve"（即加入看板/示例库），去掉 ⭐ 收藏；Workbench 主页改为卡片网格，卡片来自示例库 trusted 题（含 pin/分组）和模板库，支持刷新/展开；预置查询维护移到管理区，编辑弹窗回填 SQL、加示例区和 AI 草稿按钮；删除半自动筛选区块。
5. 前端：导航文案对齐（对话 / 固定看板 / 快捷查询 / 管理），悬浮球模式保持只露对话，"打开完整工作台"进入看板。
6. 能力融合（第七章）：模板库走 plan 结构匹配（不进 RAGFlow、不走向量），示例库走 RAGFlow 向量召回 + 结构同型/槽位对齐/条件覆盖精判；在 _handle_composite 循环和 _build_query_result 单问题入口前加能力路由三道闸（模板结构匹配 → 示例向量复用直接填参执行 → Wren），高置信直接执行、中置信降级为 few-shot；模板/示例/AI 结果统一并入 task_results/produces，打通内部参数绑定的白名单通道；扩展 choose_capability 选择式澄清；chat_settings 增加 auto/ask/off 复用开关；接入校验失败降级与误命中记录；完善 RAGFlow 示例文档分段（问法变体/结构头/spec/归一化 SQL/解读）。
7. 自动同步（第八章）：模板加载收口到带 mtime/hash 版本号的统一 loader，前端保存即时刷新索引、后端手改文件靠轮询热重载；示例以本地 example_pairs 为事实源、RAGFlow 为向量投影，写入顺序改为本地先落 pending_sync 再后台补偿上传，实现 reconcile_examples 增量对账（复用 knowledge_sync 的 hash/删旧传新/孤儿清理范式）和解析状态管理，启动加定时对账兜底；管理端加两库同步状态面板与手动重建按钮。

## 六、验收用例

- 对话问"西乡段泛油有多少处"，答 534，点固化到看板；看板出现卡片"共 534 处"。以后数据变了点刷新，数字更新，过程无大模型生成 SQL（data 类型重放零 LLM，可看日志确认没有走 nl2sql/wren 生成）。
- 问"给我看西乡段面积最大的病害图片"，看图题固化后刷新，直接出最新图片，不重新生成 SQL。
- 问"西乡段和恒明珠哪条路养护压力大"（analysis/composite），固化后刷新：取数走存好的 SQL，只在最后结论处调一次大模型，卡片结论随最新数据变化；对比全链路，大模型调用次数明显减少。
- 问"路面泛油一般怎么处置"（knowledge），固化后刷新会重新检索规范并回答，规范库更新后能拿到新内容。
- 预置查询维护编辑任意一条，SQL 文本框能看到这条已有 SQL；新增时能看到同分类示例；AI 草稿生成的 SQL 必须人工点保存才生效，且参数不在 params 定义里时后端拒绝。
- 看板页不再有半自动筛选；普通使用者看不到模板维护、知识库、模型设置这些管理入口。

## 七、能力融合：模板/示例库与问答在子问题级打通

前面几节解决"手动点卡片重放"。这一节解决更重要的问题：用户在对话里随便问、规划器拆成多个子问题时，每一步都应该先看看能不能用已有的确定性模板或已验证的示例问答来算，而不是每个子问题都重新生成 SQL。

本章是最终架构，对第二、三章做一处修订：取消独立的收藏功能和单独的 saved_queries 表。用户"答对了"（approve）的问答自动入示例库，这就是默认收藏，不再需要 ⭐ 收藏按钮和只存问题文本的 favorites；固定看板的卡片直接来自示例库（用户/管理员 pin 置顶的题）和模板库。原因是 approve 入示例库这件事现在已经在做（chat.py 的 /feedback/approve → save_successful_pair / save_composite_pair，同时写本地 example_pairs 和 RAGFlow"SQL问答示例"数据集），没必要再维护一套平行的收藏存储。

### 1. 现状的断点

- 规划器 orchestrator.decompose 已经把复杂问题拆成子任务，每个子任务带 type、question、produces、needs、depends_on；执行器 agent._handle_composite 也已经实现前序结果按 {{key}} 回填后序步骤的链式机制。
- 已验证问答入池时，_normalize_sql_for_example 已经把具体值挖成占位符（{route_id}/{route_name}/{damage_type}/{pile_start}/{time_start}/{device_code}），spec_json 已经存了查询结构（shape、subject、route、damage_type、time_range 等槽位），_same_structure 已经能按 shape+主体判同型。
- 但这些示例现在只在 _local_example_text 里作为 few-shot 文本喂给写 SQL 的模型（让它"照着写"），从不在高置信时直接填参执行；22 条 preset 模板也只能手动点，不进入子问题执行链路。结果是明明某一步和已验证的题一模一样，系统还是重新选表、生成 SQL、校验，既花钱又可能错。

### 2. 分两个库，不要混存

模板和示例是两种不同的东西，匹配方式也不同，必须分两个库存、两条路匹配，混在一起用向量匹配会出现"抽象句和具体句对不上"的问题。

库一：模板库（抽象、结构化）

- 内容：现在 preset_queries.json 里的参数化模板，问法是抽象的，如"某条路的病害总数""这条路某类病害有多少处、面积多大"，SQL 带 {route_id} 这类占位，params 段声明槽位和取值来源。
- 为什么不能用文本/向量匹配：模板问法是"某条路……"这种抽象骨架，用户问的是"西乡段泛油有多少处"这种具体句子，两者字面和向量都不相近，向量召回会失灵。
- 正确匹配方式：纯结构匹配，不走向量。子问题经过语义理解得到 plan/spec（shape 形态、subject 主体、槽位），当某个模板的 shape 与子问题一致、模板声明的槽位能覆盖子问题全部条件时命中。模板库不需要进 RAGFlow。

库二：示例库（具体、已验证问答对）

- 内容：RAGFlow"SQL问答示例"数据集 + 本地 example_pairs 表，每条是一个具体问法 + 归一化 SQL（带占位）+ spec_json（槽位结构）+ shape + 当时的结果解读。来源有三类：用户 approve 的问答（默认收藏，自动入池）、RAGFlow 里已有的问答数据集、管理员整理的标准题。
- 正确匹配方式：先用语义向量按具体问法召回（问法再随机，"多少处/几处/数量"这类在向量空间是相近的），再用结构同型 + 槽位对齐做精判。
- 可信分级：只有 trusted（人工 approve 或管理员确认）的示例才能参与"直接填参执行"；刚自动采集、未确认的进"待确认池"，只能做 few-shot 或在管理端等人确认，避免错误 SQL 被反复复用。

### 3. 能力路由：每个子问题按顺序过三道闸

在执行每个 data/image/analysis 子任务之前（_handle_composite 循环内、_build_query_result 单问题入口同样加），插一个能力路由，顺序如下，命中即停：

第 0 步，语义理解：子问题先走和现在一样的语义理解，拿到 plan/spec（意图、主体、指标、条件集合、分组、时间、shape、各槽位当前值）。复用现有产物，不新增大模型调用。

第 1 道闸，模板库结构匹配（精确、零大模型）：用 plan 的 shape+subject+槽位去对模板库。模板能完整表达子问题的全部条件（槽位一一对应、没有模板覆盖不了的额外条件）才命中，走参数绑定直接执行，等价于现在 preset 的确定性通道。

第 2 道闸，示例库语义复用：用子问题文本对示例库做向量召回取 topK，然后逐条做三层判定：

- 结构同型：shape 和 subject 相同（复用 _same_structure）。
- 槽位可对齐：示例归一化 SQL 里的占位，都能用当前 plan 的槽位值填上。
- 条件覆盖（最关键）：子问题里的每个过滤条件，示例 SQL 都有对应槽或本就固定覆盖；子问题多出示例表达不了的条件维度（如收藏 collect、经纬度范围、工单状态等冷门字段），这一条就不能直接执行。宁可不匹配也不能少过滤，避免"西乡段收藏的病害"被套用"西乡段病害总数"而答成全部 911 处。

三层全过且置信高 → 直接填参执行（见下），零 SQL 生成大模型；结构同型但个别槽位要确认或置信在中段 → 不直接执行，把该示例作为强 few-shot 喂给 Wren（现状做法）；不满足 → 放弃示例。

第 3 道闸，Wren 全流程：前两道都没命中，走现在的 Wren/LLM 生成、校验链路，完全不变。

示例直接执行的值迁移：示例库存的是带占位的归一化 SQL，命中后把当前 plan 的槽位值填进占位（路线名换成当前路线、病害类型换成当前类型、时间换成当前区间），得到可执行 SQL。填值必须经过和 preset 一样的校验：路线 id 为 32 位 hex 且来自路线表实查、病害类型来自字典表、时间符合格式、数值类转义；不接受自由文本直接拼。执行前同样限定 SELECT/WITH、只读、明细强制 LIMIT。这样复用的是"验证过的查询结构"，跑的是"本次的最新条件"。

第 1、2 道闸命中后仍要过现有结果校验器；校验不通过自动降级到下一道闸（模板错→示例/Wren，示例错→Wren），并记一次误命中、下调该条目的自动置信度。

### 4. RAGFlow 问题库要存成什么样

要让向量召回和直接执行都可靠，示例数据集每条文档建议固定分段：问题原文（可附 2-3 个问法变体，提升随机问法召回）、结构头（query_type、shape、subject）、spec_json 槽位、归一化 SQL（带占位，不给具体值）、输出形状说明、# 解读（当时结果怎么总结的，供分析阶段复用）。向量只负责按问题召回候选；真正的结构判定、槽位对齐和填参执行用本地 example_pairs 表里的结构化字段（spec_json + 归一化 SQL），RAGFlow 召回 doc_name 后回本地表取，不让模型从召回文本里手抄 SQL。模板库不进这个数据集。

### 5. 命中 0/1/多个分别怎么办

- 命中 0 个：走 Wren，链路不变。
- 唯一高置信命中（模板或示例）：自动执行，回复轻标注"这一步用了已验证口径：模板名/示例题"，并给"不对？用 AI 重新查"，点了就降级并记录误命中。
- 多个且分差明显：按"槽位覆盖最全 > 形状最吻合 > 语义最近 > 历史成功率高"自动取最优。
- 多个且分差接近、或槽位需要用户定、或落在灰区：不静默硬套，走选择式澄清让用户点（见第 7 点）。

chat_settings 增加复用策略开关（与 engine_mode 并列）：auto（默认，高置信自动、灰区询问）、ask（每次命中都让我选）、off（不做复用，全走 AI）。

### 6. 链式效应：模板/示例结果和 AI 结果同池、可互相喂

这是"融合"的核心。无论一步是模板执行、示例填参执行还是 Wren 生成，结果都一视同仁：

- 写进同一个 task_results，并按该能力声明的 produces，用现有 _extract_produced 抽值填入 produced，后续步骤的 {{key}} 照常回填，不管后序是模板、示例还是 Wren。
- 反向也成立：前序 AI 步骤查出的值（如病害最多那次的 patrol_id），可以作为参数喂给后序模板/示例的槽位。来自前序结果的内部传值同样要过白名单/类型校验和"值到列"探测（复用 _resolve_entity_condition），不能直接字符串拼接。
- 于是一条复杂问题可以是混合链路：一段模板、一段示例、一段 Wren、最后 analysis 综合，用户看到的是一条完整答案。

链式示例：步骤一"7 月西乡段巡检几次、每次多少"命中模板，produces 最多那次 patrol_id；步骤二"把那次明细调出来"命中示例库里"某巡检病害明细"，patrol_id 槽从前序结果取，确定性执行；步骤三"这些病害置信度普遍怎样"无匹配转 Wren，patrol_id 作为上下文继承。

### 7. 选择式澄清的交互协议

扩展现在只回一段文字的 clarify：新增 kind=choose_capability，payload 带 2-4 个候选（来源类型=模板/示例、标题、口径、还缺哪个槽及可选项）。/api/chat 请求体支持带回 choices（某子问题选哪个能力、补的参数值），选定后该步直接走对应能力，其余步骤照常。前端把这类澄清渲染成候选按钮加参数下拉，并保留"都不是，让 AI 自己查"。单轮问题命中灰区时用同样卡片，避免静默猜错。

### 8. 固定看板就是示例库/模板库的卡片化

- 看板卡片来源：示例库里 trusted 的题（用户 approve 即出现，相当于默认收藏）和模板库的系统模板，分两个区展示；用户可 pin 常用的到顶部、可移除（从看板移除不等于删示例）。
- 点卡片运行：data/image 类按当前默认条件（或卡片上选参数）走第 1/2 道闸的确定性执行，直接出最新数/最新图片，不生成 SQL。
- analysis/composite 类：先确定性跑出各步数据，再结合"运行结果 + 知识库规范文件 + 大模型"做一次分析综合（复用 _analysis_payload：数据结果 + 检索到的规范片段交给模型出结论），省掉意图、选表、SQL 生成，只保留这一次分析。
- knowledge 类：重新检索知识库回答（规范会更新）。
- 卡片上显示口径说明和最近结果摘要、刷新时间，让使用者知道数字怎么来的。

### 9. 防错闭环与库治理

- 只有 trusted 示例能直接执行；自动采集的先进待确认池，管理端可批量确认。
- 固化去重：approve 入库时若与已有示例结构同型、槽位相同，视为同一题的新问法变体，合并到该题的问法变体列表，而不是无限新增，控制召回噪声。
- 半自动沉淀：定期统计"高频走 Wren 且校验通过"的结构，在管理端提示可沉淀为模板或标准示例，只提示不自动写。
- 误命中治理：连续被判错的模板/示例转成"仅询问时可用"，不再自动命中。

### 10. 能力精判提示词要点

示例/模板的最终选择尽量用规则（结构同型、槽位对齐、条件覆盖都是确定性计算）；确需小模型在多个候选间确认时，输入是"子问题语义结构 + 每个候选的 shape/槽位/固定条件/口径"，让它只输出：每个候选是否满足条件覆盖（不满足要指出缺哪个条件）、形状是否一致、置信度与一句话理由；明确"子问题有而候选没有对应槽位的条件，一律判不满足，宁可漏匹配不可错匹配"。匹配阶段禁止模型生成或改写 SQL。

### 11. 验收用例（补充）

- 复合问题"7 月西乡段巡检几次、每次多少，把最多那次明细调出来"：步骤一走模板、步骤二命中示例库并正确继承 patrol_id，步骤二不重新生成 SQL、不把编号当时间。
- 用不同问法问同一题（"西乡段泛油多少处""西乡段有几处泛油"）：向量能召回同一条示例，结构同型且槽位对齐时直接填参执行，结果一致。
- "西乡段收藏的病害有多少处"：即使召回"西乡段病害总数"示例，因多出 collect 条件、条件覆盖不过而不直接执行，转 Wren 正确过滤。
- approve 一道复合题后，看板出现该卡片；点刷新时数据步确定性重跑、分析步结合最新结果和规范重新综合，SQL 生成环节零大模型调用。
- 一个子问题近似命中两条示例且分差接近时弹候选卡片；auto/ask/off 三个开关行为分别符合预期；选择"都不是"后正常走 Wren。
- 前序 Wren 查出的路线名能作为后序模板/示例的槽位值正确执行，内部传值经过白名单校验。

## 八、两个库的自动同步与一致性

要求是：无论从前端界面还是后端（直接改文件、直接灌库）新增或修改了模板、示例，能力路由用来匹配的索引都必须自动更新，不能靠重启、不能出现"加了但匹配不到"或"删了还在召回"。

总原则：每个库只有一个事实源，匹配用的索引是事实源的投影，投影随时可以由事实源幂等重建；所有增删改收口到同一组服务函数，再用三种触发方式保证不漏。

### 1. 模板库：json 是事实源，内存结构索引是投影

- 事实源：backend/app/data/preset_queries.json。前端新增/编辑/删除统一走 POST/DELETE /api/preset-queries，落盘后立即触发模板索引增量刷新（现在只清了 lru_cache，需要同时通知能力路由重建结构索引）。
- 后端直接改文件也要生效：给模板加载加文件版本号（mtime + 内容 hash）。能力路由每次取模板前（或后台一个轻量定时任务，几十秒一次）比对 json 的 mtime/hash，发现被后端直接改过就热重载并重建索引，无需重启。多 worker 部署时各进程靠文件版本号自检，不依赖进程间消息。
- 模板库不进 RAGFlow、不建向量，结构索引重建成本极低（几十条），直接全量重建即可。

### 2. 示例库：本地 example_pairs 表是事实源，RAGFlow 向量是投影

- 统一方向：以本地 example_pairs 表为结构化事实源（spec_json、归一化 SQL、trusted/pending、pin、updated_at），RAGFlow"SQL问答示例"数据集只是它的向量投影。前端 approve、管理端确认、后端批量灌库，都只写这一个事实源，再由同一个同步函数把变更投影到 RAGFlow，不在多处各自维护。
- 增量同步复用 knowledge_sync.py 的成熟范式：按内容 hash 去重（hash 没变不传）、变更就删旧文档传新文档并重新 parse、本地删除则远端删除、远端多出的孤儿文档定期清理。把现有 renormalize_examples 扩展成一个 reconcile_examples() 对账函数，统一处理"新增/变更/删除/孤儿"，并返回计数。
- 写入顺序要改：现在 save_successful_pair 是 RAGFlow 传成功才写本地表，RAGFlow 一抖，用户这次 approve 就整条丢了。改成"本地先落（标记 pending_sync）→ 后台/立即同步上传 → 成功标记 synced"，同步失败不阻塞查询、不丢记录，由定时对账补偿重试。
- 后端直接灌 example_pairs 表（SQL 导入）或直接放文件：启动时和定时对账会扫描本地表，把未同步的记录投影到 RAGFlow，无需人工干预。不建议绕过本地表直接手工往 RAGFlow 传文档；如确有外部文档，对账时按孤儿处理，进"待确认"列表，不直接参与执行。
- 向量解析有延迟：upload 后 parse 是异步的，不能立刻被向量召回。同步记录里维护状态（已上传/解析中/可检索/失败，knowledge_sync 已有 parsed_docs 状态可复用）。在向量就绪前，新示例先走本地匹配兜底（_local_example_text 本就是纯本地的字符相似度 + _same_structure 结构判定），解析完成后自动纳入向量召回；管理端能看到每条示例的同步状态。
- 能力路由若缓存了示例的 spec/embedding，在同步完成后按 updated_at 增量失效或重建，避免用到旧版本。

### 3. 三种触发，保证"前端后端加了都自动同步"

- 即时触发：前端任何增删改（保存模板、approve、确认待确认示例、删除、pin）走接口，落事实源后立即触发对应投影刷新。
- 文件热监听：模板 json 用 mtime/hash 轮询热重载，覆盖"后端直接改文件"这一路。
- 启动 + 定时对账兜底：服务启动和后台定时任务各跑一次模板版本校验和示例 reconcile，覆盖直接灌库、漏同步、RAGFlow 临时不可用、远端孤儿等所有非正常路径。对账是幂等的，重复执行不产生重复文档（沿用 doc_name/内容 hash 判重）。

### 4. 管理端可见、可手动重建

管理区提供两个库的同步状态面板：模板库显示条目数和文件版本；示例库显示本地条数、已同步、解析中、待重试、孤儿文档数，以及"立即同步/重建向量索引"按钮和失败明细。这样同步是否真的生效一目了然，出问题能一键重建投影而不影响事实源。

### 5. 验收补充

- 前端新增一条模板，不重启，立刻能在快捷查询和能力路由里命中；后端直接编辑 preset_queries.json 保存，最多一个轮询周期后自动生效。
- 前端 approve 一道题，本地示例表立即有记录；RAGFlow 正常时随后可被向量召回，RAGFlow 临时停服时这条也不丢、恢复后自动补传。
- 删除一条示例后，本地表和 RAGFlow 文档都消失，能力路由不再召回；直接往本地表批量导入若干示例，定时对账后自动出现在 RAGFlow 和看板上。
- 同一条示例重复 approve 不产生重复文档；同步状态面板的计数与实际一致。

## 九、成本对比

一次完整链路通常包含意图分类、问题补全/拆分、语义选表、SQL 生成、执行、校验重试、结果分析等多次大模型调用。固化重放后：data、image 为零大模型；analysis、knowledge 各保留一次"基于结果/检索的生成"；composite 只保留末段分析和知识检索，省掉每个子问题的选表与 SQL 生成。越是高频天天看的问题，节省越明显，同时结果口径保持用户当初确认过的那一版，稳定性反而更高。
