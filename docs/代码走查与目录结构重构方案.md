# 代码走查：逻辑 bug 与目录结构重构（给 codex）

## 一、现状规模（实测行数）
- `services/nl2sql.py` **7240 行、约 224 个函数**：路线解析、字段字典、SQL 形状校验、约 30 个 `_build_*_template`、分档桶、示例召回与回填全堆在一个文件。
- `agent.py` 3372、`templatizer.py` 1976、`capabilities.py` 1250，也偏大。

## 二、逻辑 bug / 坏味道（按严重度）

### 1.【中】异常被静默吞成"查不到/无数据"
多处 `except Exception: pass` 或直接 `return [] / return None`，把内部异常和"真的没数据"混为一谈：
- `clarify.py:74` `except Exception: pass`、`clarify.py:83` `return {}`；
- `analysis.py:99`、`analysis.py:125` 都是 `except Exception: return None`。
后果：SQL 报错/字段拼错/LLM 超时，用户看到的是"没有数据""无法回答"，和真空表分不出来，排错全靠翻日志。
改法：这些兜底分支统一 `log_error(...)` 留痕；返回时区分"真空结果"和"内部异常"——至少在 reply 里带一句"查询出错已自动重试"，别让它伪装成"没数据"。

### 2.【中】用字符串正则判 SQL 形状，脆
`infer_example_spec`（nl2sql.py:5746-5782）靠 `"group by" in lower`、`"order by" in lower and "limit" in lower` 判 shape。CTE/子查询里只要出现 group by 就误判成 distribution。项目已经依赖 sqlglot 做模板化，这里应统一用 AST 解析，别再 substring。

### 3.【结构，反复踩坑的根因】nl2sql.py 上帝文件
30 个 `_build_*_template`、路线解析、字段字典、SQL lint、示例复用、分档全挤一起。之前"模板构造器改了共享 plan 对象导致同一问题两次推荐不一样"就是这个结构埋的雷。继续在这个文件上加逻辑，迟早再踩。

### 4.【结构】模板字段白名单/取值映射硬编码散在代码里
`_TEMPLATE_SAFE_FIELDS`、`_CONDITION_VALUE_HINTS`、`_FIELD 中文名映射` 等都写死在 nl2sql.py。和之前"冷门字段覆盖"是同一类问题：加一个字段要改代码、还要记得同步多处。建议抽到数据驱动的配置（和 schema 字典同源），代码只读配置。

### 5.【需确认，先别改】plan 进程缓存的 key
`_build_query_plan_uncached` 外面套了缓存，确认缓存 key 是否只含 `message+kind`。长对话里同一句"恒明珠呢"在不同上文下 plan 应不同，如果缓存 key 不含会话上下文，会把上一轮的 plan 错配到这一轮。请先打印确认，确实有串味再改成按 message+session_id。

## 三、目录结构建议（渐进，先纯移动不改逻辑）

把 nl2sql.py 按职责拆，对外入口保持 `build_query_plan` / `build_template_sql` 不变：

- `services/route_resolver.py`：`_resolve_route` / `_resolve_damage_type` / `_route_matches*` / `_route_pieces` / `_unmatched_route_token` 等路线与类型解析。
- `services/field_catalog.py`：`_field_rows` / `_catalog` / `_column_label` / `_column_value_hint` / `_LazyFieldTable` / `value_samples`。
- `services/sql_lint.py`：`sql_shape_issue` / `field_misuse_issue` / `unknown_columns` / `dictionary_join_issue` / `route_length_issue` / `fix_mdl_sql`。
- `services/templates/*.py`：30 个 `_build_*_template` 按主题分（route/patrol/bucket/metric…），配一个注册中心（取代现在散落的 if-else 链）。
- `services/example_reuse.py`：`_reuse_candidates` / `find_reusable_examples` / `fill_example_slots` / `infer_example_spec` / `_skeleton_*` / `_example_spec_usable`。
- `nl2sql.py` 只保留对外入口和共享小工具。

其他：
- `prompts/*.md` 已经外移，方向对；代码里残留的内联提示词/字典字符串继续外移到这里或配置文件。
- `docs/` 下方案越堆越多，按主题建子目录（召回与模板 / 拆分与规划 / 交互与前端 / 数据与口径），别全平铺。

## 四、落地顺序
1. 先做 1、2（小改动、收益直接）：异常吞错留痕 + SQL 形状改 sqlglot；
2. 再做 5（先确认缓存 key，别盲改）；

4. 模板注册中心化、字段配置化，最后做，避免一次性大改。

原则：每一步都能独立回滚，不一次性重写。

### LLM 优先原则的落地（2026-09-23，用户明确要求）

原则：**主判据必须是 LLM；关键词只能兜底，不许抢先**（关键词兜底本身保留）。

已经 LLM 优先（复核过，不用改）：

- `intent.classify_intent`：先问 LLM，规则只给 `rule_hint`、LLM 失败才兜底；
- `build_query_plan`：LLM 的 shape/主体覆盖规则结果，规则只留 `rule_shape` 兜底；
- `cross_db.db_scope`：多候选时由 LLM 定夺（`_llm_classify_dbs`）。

本轮改掉的是构造器里的**关键词否决门**（语义在就听语义，语义缺失才看措辞）：

新增 `_semantic_decided(plan)`（semantic 里有 shape/指标/派生/分组/输出字段任一 = LLM 已判断），
然后把 6 处 `if not any(word in message for word in …): return None` 改成
`if not _semantic_decided(plan) and not any(…)`：`_build_route_info_template`（台账词表）、

| 位置 | 现状 | 改成 LLM 优先的代价 |
|---|---|---|

### 用户裁定（2026-09-23）与据此的改动

第 5 条的落地（`nl2sql.py` + `resources/sql_templates/_index.yaml`）：

1. 新增 `_semantic_table_subjects(plan)`：由 LLM 语义（`subject` ± `group_by`）直接决定"数哪张表"——
   `subject` → `_SUBJECT_TABLE_BY_NAME`（route/section/pile_point/asset/work_order/patrol），
   `(subject, group_by)` → `_DICTIONARY_TABLE_BY_SUBJECT`（病害/资产问"分类"时落到字典表）；
   **词表只在语义缺失（LLM 没跑/失败）时兜底**。表不在 `_TABLE_SUBJECTS` 里的（路线/巡查这类）
   用 `_table_subject_entry()` 按 `schema_catalog.table_label` 现造一条。

PG 那条为什么值得接上：`is_simple_single_query` 对 PG 计划一直直接放行（注释写"PG 只有两张空表，


两条都直接跑通了物理库（`gps_points` / `inclination_points` 各 0 行，不是报错）。
