## 二、用户误解澄清：44 个 png 不是病害图片

用户说"image_cache 里有很多不同的病害图"，但实际上：

### 2.1 病害图片（problem_url）都是 jpeg 格式
- ai_problem.problem_url 里的 65 个图片全部是 `.jpeg` 扩展名
- 缓存里只有 3 个 jpeg，对应 SeaweedFS 上存在的 3 个文件

### 2.2 44 个 png 来自其他表的图片字段

数据库里有大量表包含图片字段（共 100+ 个图片/URL 字段），例如：

| 表 | 字段 | 说明 | 缓存命中 |
|---|---|---|---|
| `basic_facilities_sections` | `picture_cover` | 路段封面 | ✅ 2个png |
| `ai_problem_base` | `problem_sample_image` | 病害样图 | 待确认 |
| `ai_problem_base` | `init_image` | 内置图片 | 待确认 |
| `ai_asset_base` | `asset_sample_image` | 资产样图 | 待确认 |
| `basic_facilities_routes` | `picture_cover` | 路线封面 | 待确认 |
| `basic_facilities_bridges` | `picture` / `picture_cover` | 桥梁图片/封面 | 待确认 |
| `basic_facilities_tunnels` | `picture` / `picture_cover` | 隧道图片/封面 | 待确认 |
| `basic_facilities_slope` | `picture` / `picture_cover` | 边坡图片/封面 | 待确认 |

**已验证的 2 个 png 对应关系：**
- `4bc867fe9a27fea302c181526ec395dfdc3c4977.png` ← `/base/sys-file/airoad-bj-1321614036/09f14a2c1635414b834c4a0b`（路段封面）
- `7a85fd06b77a1c3fcdd5b71de98bb82e47775363.png` ← `/base/sys-file/airoad-bj-1321614036/12ba0601aa7b4d44947e9077`（路段封面）

### 2.3 结论
- image_cache 里的 44 个 png **不是病害图片**，是路段封面、病害样图、资产样图、桥梁/隧道/边坡图片等其他类型的图片
- 用户看到的"不同的病害图"可能是病害样图（`ai_problem_base.problem_sample_image`），不是病害记录的现场图片（`ai_problem.problem_url`）

## 四、Bug 描述

### Bug 标题
**病害图片查询：数据库记录 65 个不同图片路径，但 SeaweedFS 上只有 3 个可访问，导致前端只能显示 3 张图，且不同病害类型显示相同图片**

### Bug 分类
数据一致性问题（非代码 bug）

### 严重程度
P1（影响用户体验，但不影响数据查询功能）

### 问题描述
1. **数据不一致**：ai_problem 表 1703 条记录全部有 problem_url，指向 65 个不同图片路径，但其中 62 个路径（1420324265166 前缀，对应 1292 条记录）的文件在 SeaweedFS 上不存在
2. **前端显示异常**：查询病害图片时，由于大部分文件不存在，只能显示 3 张图；这 3 张图被 9 种病害类型共用，导致不同病害类型显示相同的图片
3. **codex 结论表述有误导性**：codex 说"存储里只有 3 个病害图片文件"，但没有说明数据库里记录了 65 个不同图片路径，其中 62 个路径的文件已不在存储上
4. **用户误解**：用户认为 image_cache 里的 44 个 png 是病害图片，实际上这些是路段封面、病害样图、资产样图等其他类型的图片

### 根因分析
- 1420324265166 前缀的 62 个图片文件可能是历史数据，在 SeaweedFS 迁移或清理时被删除，但数据库里的 problem_url 没有同步更新
- 这是数据迁移/清理导致的历史数据不一致问题，不是代码 bug

### 影响范围
- 1292 条病害记录（占总数 75.9%）的图片无法显示
- 14 种病害类型中，5 种完全无法显示图片，9 种只能显示同样的 3 张图
- 用户查询病害图片时，会看到大量重复图片，影响体验

## 五、修复建议

### 方案 A：恢复图片文件（推荐，如果有备份）
- 从备份恢复 1420324265166 前缀的 62 个图片文件到 SeaweedFS
- 恢复后，1292 条记录的图片就能正常显示
- 工作量：需要找到历史备份，操作 SeaweedFS

### 方案 B：清理无效记录（如果无法恢复）
- 清理数据库里指向不存在文件的 problem_url（1292 条记录）
- 或者将这些记录的 problem_url 置空
- 工作量：简单，但会丢失图片关联信息

### 方案 C：前端优化（短期缓解）
- 查询图片时，先批量探测文件是否存在（HEAD 请求）
- 对于不存在的图片，显示占位图或"图片已丢失"提示
- 不要把不存在的图片和存在的图片混在一起显示
- 对于 404 的图片，缓存一个"不存在"标记，避免每次都去 SeaweedFS 探测
- 工作量：中等，需要修改前端和后端图片查询逻辑

### 方案 D：区分病害现场图和病害样图（产品优化）
- 病害现场图（ai_problem.problem_url）：实际巡检时拍摄的图片
- 病害样图（ai_problem_base.problem_sample_image）：字典表里的标准样图
- 当前端查询病害图片时，如果现场图不存在，可以自动 fallback 到病害样图
- 这样即使用户外业图片丢失，也能看到该病害类型的标准样图
- 工作量：中等，需要修改图片查询逻辑
