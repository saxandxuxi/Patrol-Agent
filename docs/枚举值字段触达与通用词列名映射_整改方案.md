# 枚举值字段触达与通用词列名映射 系统性整改方案

> 覆盖两类相关问题：①枚举值字段（route_level/tech_level/route_type 等）的取值命中不影响表级选择，导致落点被带偏；②"名称/编号/类型/状态"等通用词被 LLM 映射成不存在的物理列名（route_name/route_number），实际是 full_name/code。

---

## 一、问题 A：枚举值命中不影响表级选择

### 复现
问"记录的国道总共有多少条"——"国道"是 routes.level 的枚举值（code_map: 0=国道），列级能命中 routes.level（+1.5 分），但系统回答对象是"巡查资产记录"（ai_asset_main），不是 routes。

### 根因
`field_grounding.ground()` 表级选择（225-239 行）**只看表名/表注释的词元重合**，完全不看列级证据（包括枚举值命中）：
```python
for name, haystack in _table_texts(kind):
    overlap = query_terms & wren_engine._terms(haystack)
    score = sum(len(token)**2 for token in overlap) / 4.0
    # 只比表名/表注释的词重合，不比列级枚举值命中
```
结果：用户说"国道"（枚举值），没说"路线"（表主体词），routes 表的表级词重合分=0，top_table 被其他表（如 ai_asset_main，因为"记录"命中）抢走。

### 修复：枚举值命中给所属表加表级证据分
在表级打分循环之后、定 top_table 之前，加一步"列级枚举值命中反哺表级"：
```python
# 枚举值命中反哺表级：用户说了某列的枚举中文值（"国道"/"特大桥"/"上行"），
# 说明这句话很可能在问这张表——给该表加表级证据分，不让表级只看表名/表注释。
enum_table_evidence: dict[str, float] = {}
for column in _columns(kind):
    code_hits = _code_value_hits(column["code_map"], message)
    if code_hits:
        table = column["table"]
        # 每个枚举命中 +1.0 表级分（和列级 +1.5 区分开，表级权重稍低）
        enum_table_evidence[table] = enum_table_evidence.get(table, 0) + 1.0 * len(code_hits)

# 合并到 table_evidence，再选 top_table
for table, bonus in enum_table_evidence.items():
    table_evidence[table] = table_evidence.get(table, 0) + bonus
```
**注意**：单字枚举值（"是/否"）已经在 `_code_value_hits` 里过滤了（长度≥2 才算），不会误加分。

### 验收
1. "记录的国道总共有多少条" → 落点表是 routes（不是 ai_asset_main）；
2. "特大桥有多少座" → 落点表是 bridges（span_category 枚举值命中）；
3. "上行的病害有多少" → 落点表是 ai_problem（up_or_down 枚举值命中）；
4. 回归：之前通过的题不退化（单字"是/否"不会误加分）。

## 二、问题 B：通用词列名映射错误（名称/编号/类型/状态）

### 复现
问"这5条国道的具体名称和编号分别是哪些"→ 系统报"查不到 route_name/route_number 字段"。但 routes 表实际有 full_name（路线全称）、short_name（路线简称）、code（路线代码）。

### 根因
LLM 语义规划（build_query_plan）把"名称"映射成 metric=route_name、"编号"映射成 metric=route_number——这两个是 LLM 脑补的物理列名，实际不存在。字段触达的列级匹配能找到 full_name/code（列名/注释命中），但**没有用字段触达的结果纠正 plan 里的 metric 名**，后续 SQL 生成按 plan 的 route_name/route_number 去找列，找不到就报错。

### 修复：plan 生成后用字段触达纠正 metric 名
在 `build_query_plan` 返回 plan 之前，加一步"metric 名物理化"：
```python
# 用字段触达的结果纠正 plan 里的 metric 名：
# LLM 可能生成 route_name（不存在），字段触达能找到 full_name（存在）→ 替换。
def _physicalize_metrics(plan: dict, kind: str, message: str) -> dict:
    grounded = field_grounding.ground(kind, message, plan=plan)
    physical_columns = {item["column"] for item in grounded.get("columns") or []}
    semantic = plan.get("semantic") or {}
    metrics = semantic.get("metrics") or []
    for i, metric in enumerate(metrics):
        name = str(metric.get("name") or metric.get("column") or "")
        # LLM 生成的 metric 名不在物理列里 → 用字段触达找到的最相关列替换
        if name and name not in physical_columns:
            # 找同表的、列名/注释最相关的物理列
            best = _find_best_physical_column(name, grounded.get("columns") or [])
            if best:
                metrics[i]["name"] = best["column"]
                metrics[i]["physical_column"] = best["column"]
                metrics[i]["original_semantic_name"] = name  # 保留原名用于展示
    return plan
```

**通用词映射表（辅助）**：对于高频通用词，加一个确定性映射（不依赖字段触达也能纠正）：
```python
_GENERIC_COLUMN_ALIASES = {
    # 通用词 → 各表的常见物理列名（按优先级）
    "名称": ["full_name", "short_name", "name", "problem_name", "bridge_name"],
    "编号": ["code", "problem_number", "patrol_number", "task_number", "bridge_code"],
    "类型": ["problem_type", "damage_type", "type", "categories_type", "route_type"],
    "状态": ["problem_status", "status", "operate_type"],
    "描述": ["problem_describe", "description", "memo", "remark"],
}
```
这个映射是辅助的，主判据还是字段触达的列级匹配结果。映射只在字段触达找不到时兜底。

### 验收
1. "国道的名称和编号" → 用 full_name/code，不报 route_name/route_number；
2. "病害的类型和状态" → 用 problem_type/problem_status；
3. "桥梁的名称和跨径分类" → 用 bridge_name/span_category；
4. 回归：之前通过的题不退化（LLM 生成的正确 metric 名不被误替换）。

## 三、统一原则

1. **枚举值是强信号**：用户说了某个枚举中文值（国道/特大桥/上行），说明这句话很可能在问这张表——必须影响表级选择，不能只给列级加分。
2. **plan 的 metric 名必须物理化**：LLM 生成的语义名（route_name）不一定是物理列名（full_name），必须用字段触达的结果纠正，不能直接拿 plan 的 metric 名去生成 SQL。
3. **不手写穷举**：通用词映射表只是辅助兜底，主判据是字段触达的列级匹配（从 schema 自动派生，不随问法增长）。

## 四、实施顺序
1. **第一步**：问题 A——枚举值命中反哺表级（field_grounding.py，约 10 行）；
2. **第二步**：问题 B——plan metric 名物理化（nl2sql.py build_query_plan 末尾，加 _physicalize_metrics）；
