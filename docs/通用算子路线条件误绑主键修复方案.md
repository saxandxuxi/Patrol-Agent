# 通用算子把路线条件误绑到主键，导致里程桩点查 0（给 codex）

## 一、现象（实测，2026-09-22）

问"宝安大道西乡段一共有多少条里程桩点明细记录"，走通用算子（engine=chosen_generic），返回 0 行、"未查询到符合条件的数据"。实际西乡段有 **52 个有效里程桩点**。

实际执行的 SQL（数据血缘）：

```sql
SELECT m.sections_id AS '路段id', m.pile_map_position AS '桩号坐标点', m.lng AS '经度',
       m.lat AS '纬度', m.sort AS '排序', m.pile_map_position_name AS '桩号名称',
       m.meter AS '米', m.create_time AS '创建时间', m.update_time AS '更新',
       j0.full_name AS '路段全称'
FROM basic_facilities_sections_pile_detail m
LEFT JOIN basic_facilities_sections j0 ON m.sections_id = j0.id
WHERE m.del_flag = 0
  AND m.id = '1b0b4a9f700477b1d96119caac87c168'   -- 错：路线 id 被绑到了桩点表主键
LIMIT 500
```

连库核验：
- `WHERE m.id = '路线id'` → **0 行**（复现 bug）；
- 正确写法经路段表中转 → **52 行**：

```sql
SELECT COUNT(*)
FROM basic_facilities_sections_pile_detail m
JOIN basic_facilities_sections s ON m.sections_id = s.id AND s.del_flag = 0
WHERE m.del_flag = 0 AND s.route_id = '1b0b4a9f700477b1d96119caac87c168';
-- = 52
```

补充数据事实：西乡段 pile_detail 物理 416 行 = 52 个桩点各约 8 条版本记录，其中 364 条 del_flag=1、52 条 del_flag=0；按经纬度去重也是 52，与评测用例 MT1 标准答案一致。`full_name` 在 sections 表为"宝安大道西乡段"，JOIN 正常。

## 二、根因链（两处缺陷叠加）

1. **路线过滤被写死成主表 `routes_id`**：`capabilities.py` 的 `_generic_filters`（约 307-308 行）只要 plan 里有 route_match，就无条件追加
   `{"column": "routes_id", "op": "=", "value": route.id}`。
   这假设主表都有 routes_id（病害表 ai_problem 确实有），但里程桩点表 `basic_facilities_sections_pile_detail` **没有 routes_id**，它到路线的关系是 `sections_id → basic_facilities_sections.route_id`，必须经路段表中转。

2. **字段解析的"包含匹配"把 routes_id 兜成了主键 id**：generic_detail 在 `generic.py:123-128` 对每个过滤列调 `catalog.resolve_column(kind, table, "routes_id")`。pile_detail 没有该列，精确匹配失败后，`schema_catalog.resolve_column`（约 352-356 行）做双向包含匹配：`label in wanted or wanted in label`。主键列名/标签是 `id`，而 `'id'` 是 `'routes_id'` 的子串 → 命中主键，于是生成 `m.id = '路线id'`，必然 0 行。
   函数注释写的是"找不到返回 None（交给 Wren，不猜）"，但包含匹配实际上猜了，而且猜得很危险。

3. **JOIN 不会因过滤条件而补**：`generic._joins_for`（70-89 行）只为"SELECT 里要展示的列（如路段全称 full_name）"补 JOIN（所以有 j0），不会因为"路线条件需要经 sections 中转"而补 JOIN。结果就是：展示用的 sections JOIN 在了，过滤用的路线关系却没接，条件错落到主键。

4. **计数形态也没走对**：用户问"多少条"，应返回 COUNT(*) 单值（52），实际 generic_detail 出的是明细列 SELECT ... LIMIT 500。说明 shape 被判成了 list/detail；即便如此，主 bug 仍是路线列错绑，COUNT 也会是 0。

注：专门的桩点计数路径其实是对的——`nl2sql._SUBJECT_SOURCES`（2366-2372 行）已登记 pile_point 的 JOIN 链（pile_detail→sections→routes），通用指标模板（3122-3147 行）据此能算出 52。这次是通用算子 generic 另起炉灶、没用这套关系，才出错。

## 三、修复要求

### P0-1 路线条件按"表到路线的真实关联"生成，不许写死 routes_id
- `_generic_filters` 不要对所有表统一塞 `routes_id`。应按字段目录/表关系判断该表的路线过滤落点：
  - 主表直接有路线列：ai_problem.routes_id、ai_asset_main.route_id、ai_distance_capture.routes_id、桥梁 belong_route_id 等 → 解析到该物理列；
  - 主表需经中间表：basic_facilities_sections_pile_detail（sections_id→basic_facilities_sections.route_id）、以及其他通过 sections/route 外键挂路线的表 → 自动补 JOIN，条件落在中转表的 route_id 上；
  - 建议直接复用/对齐 `nl2sql._SUBJECT_SOURCES` 已登记的"主体→主表→JOIN 链"，或在字段目录里为每张表登记 `route_join_path`（经哪张表、哪两列、落到哪个 route_id），generic 与 nl2sql 共用一份关系，不要各写一套。

### P0-2 generic_detail 支持"过滤条件驱动的 JOIN"
- 当某个过滤列不在主表、而在关联表时（如路线要经 sections），应像展示列一样自动把对应 JOIN 加进 FROM，并把条件拼到关联表别名上（`s.route_id = ...`），而不是只在主表别名 m 上拼条件。

### P0-3 收紧 resolve_column 的包含匹配，禁止兜成主键/通用列
- 物理名（如 routes_id）只允许精确匹配物理名，不参与中文 label 的包含匹配；
- 主键 `id` 以及 name/code/sort 这类通用短名，不参与"子串包含"兜底（`id` 会是几乎所有 xxx_id 的子串）；包含匹配要求标签达到最小长度/最小中文词数，且不得跨到带 primary 角色的列；
- 找不到就按注释承诺的返回 None；generic_detail 对解析不出的过滤列应**整体弃权**（交专门模板/Wren），绝不允许静默换成主键硬查一个 0。

### P0-4 计数 vs 明细形态分开
- "多少个/几条/几处"（shape=count）应生成 `COUNT(*)`（带正确 JOIN 和 del_flag、租户条件）返回单值；"列出/明细/有哪些"才走 generic_detail 的行式 SELECT。
- 这次即便走明细，也应在正确的 s.route_id 条件下返回 52 行，而不是 0。

### P0-5 构建期护栏
- 通用算子在生成 SQL 后自检：若 WHERE 出现"主键 id = 一个 32 位路线/其他实体 id"这种跨实体等值，直接判无效、弃权并记日志，不允许执行；
- 结果为 0 行且条件含路线时，在 scope/日志中标注"疑似路线条件未正确关联"，便于发现同类问题。

## 四、影响面
凡是"主表没有直接路线列、要经 sections/其他表中转"的对象，通用算子都会踩同一个坑（目前至少里程桩点 pile_detail；未来路段子表、桩号附属设施等同理）。P0-1/P0-2 用统一的 route_join_path 解决一类问题，而不是只给 pile_detail 打补丁。

## 五、验收（连库断言）
1. "西乡段一共有多少条里程桩点" → COUNT = **52**（del_flag=0，经 sections.route_id）；
2. "列出西乡段里程桩点明细" → 返回 **52 行**，含 K0+000…K5+100，路段全称=宝安大道西乡段；不再出现 `m.id = '路线id'`；
3. 病害/资产/定距等主表自带路线列的查询回归正常（ai_problem.routes_id 等不受影响）；
4. 人为构造一张"无路线列、无中转关系"的表加路线条件时，通用算子明确弃权交 Wren，不返回误导性 0；
5. resolve_column("…pile_detail", "routes_id") 返回 None 而不是主键 id；
6. 计数题返回单值 COUNT，不返回 500 行明细。

- `backend/app/services/generic.py`：generic_detail 支持过滤条件驱动 JOIN（70-89、123-151）；count 形态；主键等值护栏。
- `backend/app/services/schema_catalog.py`：resolve_column 包含匹配收紧（352-356）。
