# 病害图片查询优化方案（只读库权限下可行）

> 前提：只能读库，不能改库，不能操作 SeaweedFS
> 核心思路：全部通过改代码（前端+后端）来解决，不碰数据库和存储
> 生成时间：2026-10-11

---

## 一、问题现状（已验证）

| 指标 | 数值 |
|---|---|
| ai_problem 总记录 | 1703 条，全部有 problem_url |
| 不同图片路径 | 65 个 |
| SeaweedFS 可访问 | 3 个（102367594567 前缀，411 条记录） |
| SeaweedFS 不存在 | 62 个（1420324265166 前缀，1292 条记录，404） |
| 本地缓存 image_cache | 47 个文件（3 jpeg 病害图 + 44 png 其他图） |

**影响：**
- 14 种病害类型中，9 种能显示图片但都是同样的 3 张（共用）
- 5 种完全无法显示图片（条状修补、坑洞、减速带损坏、护栏缺损、路面摊晒）
- 前端查询病害图片时，大量 404 混在结果里，体验差

## 二、可行方案（全部改代码，不碰库/存储）

### 方案 1：图片存在性批量预探测 + 404 缓存（P0）

**问题：** 当前代码每次查询图片都去 SeaweedFS 试错，404 的图片每次都会重新探测，浪费时间。

**改法：**

#### 1.1 后端：批量探测 + 404 缓存

在 `db.py` 的 `fetch_seaweedfs_many` 里增加：

```python
# 新增：404 缓存（进程内，带 TTL）
self._image_404_cache: dict[str, float] = {}  # path -> 探测时间
self._404_ttl = 3600 * 24  # 24 小时，因为文件不会突然恢复

def _is_404_cached(self, path: str) -> bool:
    ts = self._image_404_cache.get(path)
    if ts and time.time() - ts < self._404_ttl:
        return True
    return False

def _mark_404(self, path: str) -> None:
    self._image_404_cache[path] = time.time()
```

在 `fetch_seaweedfs` 和 `fetch_seaweedfs_many` 里：
- 下载前先查 404 缓存，如果命中直接返回 404，不去 SeaweedFS
- 下载失败（404）时，调用 `_mark_404(path)` 记入缓存

**收益：** 第二次查询同一批图片时，62 个 404 图片直接跳过，节省大量 SSH 隧道往返时间。

#### 1.2 后端：返回结果里区分"存在"和"不存在"

修改图片查询接口的返回格式：

```json
{
  "images": [
    {"path": "102367594567/xxx.jpeg", "status": "ok", "url": "/api/image/xxx"},
    {"path": "1420324265166/xxx.jpeg", "status": "missing", "url": null}
  ],
  "total": 10,
  "available": 3,
  "missing": 7
}
```

**关键：** 不要把 404 的图片和存在的图片混在一起返回，前端可以根据 status 分别处理。

#### 1.3 前端：404 图片显示占位图

在 `ResultPanel.vue` 的图片渲染部分：
- status=ok 的图片：正常显示
- status=missing 的图片：显示灰色占位图，标注"现场图片已丢失"
- 占位图可以用 SVG 或 base64 小图，不需要额外请求

**示例：**
```vue
<div v-if="img.status === 'missing'" class="image-placeholder">
  <svg>...</svg>
  <span>现场图片已丢失</span>
</div>
<img v-else :src="img.url" />
```

### 方案 2：病害样图 Fallback 机制（P0，最有价值）

**问题：** 现场图丢失了，但字典表 `ai_problem_base` 里有病害样图（`problem_sample_image`）和内置图片（`init_image`），可以用来兜底。

**关键：** 这些字段在可读的字典表里，不需要改库，只需要改查询逻辑。

#### 2.1 后端：查询病害图片时，自动关联字典表的样图

修改图片查询逻辑：

```python
# 查询病害记录时，同时查字典表的样图
sql = """
SELECT 
  p.problem_number,
  p.problem_url,
  p.damage_type,
  p.pic_position,
  b.problem_sample_image,  -- 病害样图
  b.init_image,             -- 内置图片
  b.problem_type            -- 病害类型名称
FROM ai_problem p
LEFT JOIN ai_problem_base b ON p.damage_type = b.problem_code
WHERE ...
"""
```

#### 2.2 后端：图片返回时带 fallback 选项

```json
{
  "images": [
    {
      "path": "1420324265166/xxx.jpeg",
      "status": "missing",
      "damage_type": "坑洞",
      "fallback": {
        "type": "sample_image",
        "path": "base/sys-file/xxx.png",
        "label": "坑洞标准样图"
      }
    }
  ]
}
```

#### 2.3 前端：现场图丢失时，自动显示样图，并标注来源

在 `ResultPanel.vue` 里：
- 现场图存在：显示现场图
- 现场图丢失但有样图：显示样图，右上角标注"标准样图（非现场）"
- 现场图和样图都没有：显示占位图"暂无图片"

**示例 UI：**
```
┌─────────────────┐
│  [图片]         │
│  ┌───────────┐  │
│  │标准样图    │  │  ← 右上角角标
│  └───────────┘  │
│  坑洞           │
└─────────────────┘
```

#### 2.4 样图的缓存

样图的 path 也会走 `fetch_seaweedfs`，同样有本地缓存和 404 缓存。
如果样图也 404，就显示占位图。

**收益：**
- 14 种病害类型都能显示图片（现场图或样图）
- 用户能看到该病害类型的标准样图，即使现场图丢失
- 不需要改库，只需要改查询 SQL 和前端渲染

### 方案 3：图片查询结果按"可显示性"排序（P1）

**问题：** 当前图片查询结果里，3 张可显示的图和大量 404 的图混在一起，用户需要翻很久才能看到可显示的图。

**改法：**

#### 3.1 后端：排序规则

```python
# 排序优先级：
# 1. 现场图存在（status=ok）
# 2. 现场图丢失但有样图（status=missing + fallback）
# 3. 都没有（status=missing + 无 fallback）
images.sort(key=lambda x: (
    0 if x['status'] == 'ok' else 1 if x.get('fallback') else 2,
    x.get('collection_time', '')  # 同优先级按时间倒序
))
```

#### 3.2 前端：分组显示

在 `ResultPanel.vue` 里，把图片分成三组：
1. **现场图片**（可显示）
2. **标准样图**（现场图丢失，用样图替代）
3. **暂无图片**（现场图和样图都没有）

每组前面加一个小标题，用户可以快速定位。

**示例 UI：**
```
现场图片（3张）
┌────┐ ┌────┐ ┌────┐
│图1 │ │图2 │ │图3 │
└────┘ └────┘ └────┘

标准样图（8张，现场图已丢失）
┌────┐ ┌────┐ ...
│样图│ │样图│
└────┘ └────┘

暂无图片（2张）
[占位图] [占位图]
```

### 方案 4：图片查询时的"去重"优化（P1）

**问题：** 3 张可显示的图被 9 种病害类型共用，查询"全部病害图片"时会返回大量重复的图片。

**改法：**

#### 4.1 后端：按图片路径去重

```python
# 按 problem_url 去重，保留第一条记录的元数据
seen = set()
unique_images = []
for img in images:
    if img['path'] not in seen:
        seen.add(img['path'])
        unique_images.append(img)
```

#### 4.2 后端：去重后标注"共用条数"

```json
{
  "path": "102367594567/xxx.jpeg",
  "status": "ok",
  "shared_by": 534,  // 被 534 条记录共用
  "damage_types": ["泛油", "纵向裂缝", "块状修补"]  // 涉及的病害类型
}
```

#### 4.3 前端：显示"共用 N 条"角标

在图片右下角显示"共用 534 条"，用户就知道这张图被很多记录共用，不是每条记录都有独立的图。

### 方案 5：图片查询接口的"只看可显示"开关（P2）

**问题：** 用户查询病害图片时，可能只关心能显示的图片，不想看大量 404。

**改法：**

#### 5.1 后端：增加 `available_only` 参数

```python
# GET /api/images?problem_type=泛油&available_only=true
if available_only:
    images = [img for img in images if img['status'] == 'ok' or img.get('fallback')]
```

#### 5.2 前端：增加"只看有图"复选框

在图片查询结果上方加一个复选框：
- ☑ 只看可显示图片（默认勾选）
- ☐ 显示全部（包括已丢失）

勾选时只显示可显示的图片，取消勾选时显示全部（包括占位图）。

---

### 方案 6：利用本地缓存的 44 个 png（P2）

**问题：** image_cache 里有 44 个 png，是路段封面、病害样图、资产样图等。这些缓存可以优先使用。

**改法：**

#### 6.1 后端：查询病害样图时，先查本地缓存

样图的 path（如 `/base/sys-file/airoad-bj-1321614036/xxx.png`）也会走 `fetch_seaweedfs`，而 `fetch_seaweedfs` 已经有本地缓存逻辑。

所以只要样图的 path 之前被查询过，就会命中本地缓存，不需要去 SeaweedFS。

#### 6.2 后端：预热缓存

启动时或定时任务里，把 `ai_problem_base` 表里所有病害样图的 path 预取一遍，缓存到本地。

```python
# 启动时预热病害样图缓存
sql = "SELECT DISTINCT problem_sample_image FROM ai_problem_base WHERE problem_sample_image IS NOT NULL"
paths = [r['problem_sample_image'] for r in db_manager.query('mysql', sql)['rows']]
db_manager.fetch_seaweedfs_many(paths)  # 批量下载并缓存
```

**收益：** 病害样图查询全部命中本地缓存，不需要去 SeaweedFS，速度快。

## 三、实施优先级

| 优先级 | 方案 | 工作量 | 收益 |
|---|---|---|---|
| **P0** | 方案 1：404 缓存 + 占位图 | 小 | 查询速度提升，前端不显示裂图 |
| **P0** | 方案 2：病害样图 Fallback | 中 | 14 种病害都能显示图片，最有价值 |
| P1 | 方案 3：按可显示性排序+分组 | 中 | 用户体验提升 |
| P1 | 方案 4：图片去重+共用标注 | 小 | 避免大量重复图片 |
| P2 | 方案 5："只看可显示"开关 | 小 | 用户可选 |
| P2 | 方案 6：样图缓存预热 | 小 | 样图查询速度提升 |

**建议实施顺序：** 方案 1 → 方案 2 → 方案 4 → 方案 3 → 方案 6 → 方案 5

## 五、验收标准

1. **404 缓存**：第二次查询同一批图片时，62 个 404 图片直接跳过，查询时间明显缩短
2. **样图 Fallback**：14 种病害类型都能显示图片（现场图或样图），样图右上角有"标准样图"标注
3. **排序分组**：可显示的图片排在前面，分组显示
4. **去重**：3 张可显示的图只显示 3 张，不重复显示 534 次
5. **占位图**：404 图片显示灰色占位图，不显示裂图
6. **不改库**：所有修改只涉及代码，不修改数据库和 SeaweedFS

## 六、为什么这些方案在只读库权限下可行

1. **404 缓存**：纯进程内缓存，不需要改库
2. **样图 Fallback**：只需要改查询 SQL（LEFT JOIN 字典表），字典表是可读的；不需要改库
3. **排序去重**：纯代码逻辑，在内存里处理
4. **前端渲染**：纯前端修改
5. **缓存预热**：启动时批量下载，只需要读库取 path，不需要改库

**所有方案都不涉及：**
- ❌ 修改数据库记录
- ❌ 删除/上传 SeaweedFS 文件
- ❌ 修改表结构
- ❌ 操作存储系统

**只涉及：**
- ✅ 读库（查询 SQL）
- ✅ 改后端代码（Python）
- ✅ 改前端代码（Vue）
- ✅ 本地文件缓存（image_cache）
