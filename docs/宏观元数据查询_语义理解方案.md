# 宏观元数据查询（表级/库级）语义理解方案

> 针对的问题类型：用户问的是**数据库本身的结构信息**，不是业务数据。如"每个数据库有哪些表""哪些表不为空""每张表多少行""库里有多少张表"。
> 核心原则：**不靠关键词穷举，一切以语义理解为主**。LLM 判断是不是元数据查询、解析要查什么，执行层才查 information_schema（确定性）。

---

## 一、为什么关键词方案不行

用户问法千变万化，不可能穷举：
- "库里都有啥表" / "数据库里装了哪些东西" / "这个库的表结构概览"
- "哪些表还没用上" / "有数据的表是哪几张" / "空着的表列一下"
- "表的行数排名" / "哪张表记录最多" / "数据量最大的表"
- "这个库多大规模" / "表的数量级" / "库的完整度"

关键词触发（is_metadata_question + 触发词列表）必然漏。**必须用语义理解判断"用户在问数据库本身，还是在问业务数据"。**

---

## 二、系统性解决方案（三层，前两层语义，第三层确定性）

### 层 1：LLM 语义分类——判断是不是元数据查询

**文件**：`intent_service.py`（意图分类）或新增 `metadata_service.py`

**改法**：在意图分类里增加 `metadata` 意图，用 LLM 判断：
> "这个问题是在问数据库/表/字段本身的结构信息（有哪些表、哪些表空、表行数、字段列表等），还是在问表里的业务数据（某条路的病害、某座桥的等级等）？"

**提示词要点**：
- 元数据查询的特征：问题的**主语是数据库/表/字段/列/记录本身**，不是业务实体（路线/桥梁/病害/巡检）；
- 业务数据查询的特征：问题的主语是业务实体（西乡段/特大桥/泛油病害/7月巡检）；
- 边界："西乡段的病害表有哪些字段"——主语是"字段"，是元数据查询（查 ai_problem 表结构），不是业务数据查询（不需要过滤西乡段）；
- 边界："国道有多少条"——主语是"国道"（业务实体），是业务数据查询，不是元数据。

**不新增 LLM 调用**：复用现有的意图分类调用（intent_service.classify_intent），在分类提示词里加 metadata 类别即可，不额外花一次模型往返。

### 层 2：LLM 语义解析——解析元数据查询的具体诉求

**文件**：新增 `metadata_service.py` `parse_metadata_request(message, kind)`

**改法**：判断为 metadata 意图后，用 LLM 解析具体诉求，输出结构化 JSON：
```json
{
  "object": "table",          // table / column / database
  "action": "list",            // list / count / rank / filter_empty / filter_nonempty
  "target_table": null,        // 如果是字段列表，指定表名；否则 null
  "sort_by": "row_count",      // 排序依据：row_count / table_name / null
  "order": "desc",             // asc / desc
  "cross_db": false,           // 是否跨库对比
  "filters": {}                 // 其他过滤条件
}
```

**提示词要点**：
- 给 LLM 看当前库的表清单（表名+中文注释，从 schema_catalog 拿，不调 LLM），让它知道"库里有什么"；
- 让 LLM 判断用户要的是：表列表 / 表数量 / 空表 / 非空表 / 行数排名 / 某表字段列表 / 跨库对比；
- 不限制用户问法，LLM 自由理解；
- 输出 JSON，执行层按 JSON 拼 SQL。

**这一步可以复用层 1 的 LLM 调用**：在意图分类的同时输出 metadata 解析结果（如果分类为 metadata），不额外花一次模型往返。或者用一次轻量 LLM 调用专门解析（成本低，因为输入短）。

### 层 3：确定性执行——按解析结果查 information_schema/pg_catalog

**文件**：`metadata_service.py` `execute_metadata(parsed, kind)`

**改法**：按层 2 输出的 JSON，拼对应的 information_schema 查询（MySQL）/ pg_catalog 查询（PostgreSQL），执行并返回结果。这一层是**确定性的**，不调 LLM：

| object | action | SQL（MySQL 示例） |
|---|---|---|
| table | list | `SELECT table_name, table_comment FROM information_schema.tables WHERE table_schema=DATABASE() ORDER BY table_name` |
| table | count | `SELECT COUNT(*) FROM information_schema.tables WHERE table_schema=DATABASE()` |
| table | filter_empty | `... WHERE table_rows = 0` |
| table | filter_nonempty | `... WHERE table_rows > 0 ORDER BY table_rows DESC` |
| table | rank | `... ORDER BY table_rows DESC` |
| column | list | `SELECT column_name, column_type, column_comment FROM information_schema.columns WHERE table_schema=DATABASE() AND table_name=?` |
| database | cross_db | 两个库分别查再合并对比 |

**注意**：
- information_schema.table_rows 是估算值（InnoDB），如果用户问"准确行数"，对 Top N 表跑 `SELECT COUNT(*)` 精确统计；
- PostgreSQL 用 pg_catalog.pg_tables / pg_catalog.pg_class，语法不同，按 kind 分支；
- 执行结果用自然语言总结（LLM 或模板），返回给用户。

## 三、判断逻辑流程图

```
用户问题
  │
  ▼
意图分类（LLM，复用现有调用）
  │
  ├─ metadata 意图？
  │    ├─ 否 → 走原有业务链路（不变）
  │    └─ 是 ▼
  │         元数据语义解析（LLM，可复用层1调用或轻量调用）
  │           → 输出 JSON：object/action/target_table/sort_by/cross_db...
  │           │
  │           ▼
  │         确定性执行（不调 LLM）
  │           → 按 JSON 拼 information_schema/pg_catalog 查询
  │           → 跨库则循环两个库再合并
  │           │
  │           ▼
  │         自然语言总结 → 返回用户
  │
  └─ 其他意图（data/knowledge/image/composite）→ 原有链路
```

## 四、和关键词方案的本质区别

| 维度 | 关键词方案（废弃） | 语义方案（本方案） |
|---|---|---|
| 识别 | 触发词列表穷举 | LLM 语义分类 |
| 子类型判断 | 关键词匹配（"不为空"→非空表） | LLM 解析输出 JSON |
| 新问法覆盖 | 必须加触发词，否则漏 | LLM 自由理解，自动覆盖 |
| LLM 调用 | 0（纯规则） | 1（复用意图分类，不额外增加） |
| 执行 | information_schema | information_schema（不变） |

**关键**：层 1 和层 2 是语义理解（LLM），层 3 是确定性执行（information_schema）。LLM 只负责"理解用户要什么"，不负责"拼 SQL"——拼 SQL 是确定性的，不会 hallucinate。

## 五、验收（覆盖各种问法，包括关键词方案覆盖不了的）

1. "每个数据库的不为空的表格名称" → 列出 MySQL 和 PostgreSQL 各自的非空表；
2. "库里都有啥表" → 列出所有表（口语化问法，关键词方案覆盖不了）；
3. "哪些表还没用上" → 列出空表（语义理解"没用上"=空表）；
4. "哪张表记录最多" → 行数排名第一的表；
5. "这个库多大规模" → 表数量 + 总记录数估算；
6. "ai_problem 表有哪些字段" → 列出该表字段；
7. "MySQL 和 PostgreSQL 各有几张表" → 跨库对比；
8. 回归："国道有多少条" → 业务数据查询，不走元数据链路（不退化）；
9. 回归："西乡段的病害表有哪些字段" → 元数据查询（查 ai_problem 表结构），不过滤西乡段。

---

## 六、不做的（明确边界）
- 不做表结构变更（ALTER TABLE 等）；
- 不做索引/约束/外键的元数据查询（后续可扩展）；
- 不让 LLM 直接拼 SQL（LLM 只输出 JSON，SQL 由确定性代码拼，防 hallucinate）；
- 不改 Wren/MDL 链路（元数据查询完全绕过 Wren）。

---

## 七、实施顺序
1. **第一步**：意图分类加 metadata 类别（层 1，复用现有 LLM 调用，提示词加一类）；
2. **第二步**：新增 metadata_service，实现语义解析（层 2）+ 确定性执行（层 3）；
3. **第三步**：agent.py 接入 metadata 意图分支，绕过业务 plan/cross_db；
4. 每步做完跑验收例子，确认不回归。
