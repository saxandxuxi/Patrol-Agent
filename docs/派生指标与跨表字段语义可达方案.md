# 派生指标与跨表字段语义可达方案

## 一、问题复现

用户问："路段名称以及对应的桩号以及对应的路段长度调出来看看"

系统回答："路段台账里没有「长度」这列，按现有数据答不了。"

换说法问"路段米数"，同样回答"没有「距离路段起点米数」这列"。

## 二、数据真相

这个答案是错的，数据里能算出路段长度，存在三个位置。

| 位置 | 字段 | 含义 | 字段触达能否看到 |
|---|---|---|---|
| 路段表 `basic_facilities_sections` | `distance` | 公路实际里程（km），台账手填值，实测不准 | 能看到列，但注释没有"长度"二字 |
| 路段表 | `abslute_distance` | 起点终点直接坐标距离，单位米 | 能看到列，注释没有"长度" |
| 路段表 | `start_meter_total` / `end_meter_total` | 起点总米数、终点总米数 | 能看到列 |
| Wren 路段模型 `section` | `section_length_km` | 起止桩号相减算出的路段实际长度，公里 | **看不到** |
| 桩点表 `basic_facilities_sections_pile_detail` | `meter` | 桩点米数，注释只有一个字"米" | 能看到列，单字注释无法匹配 |

`section_length_km` 是 Wren 模型用 `ref_sql` 在物理表基础上算出来的计算列，语义最准确，提示词里也写明了算密度和间距要用它。但它只存在于 MDL，物理表 `basic_facilities_sections` 里没有这一列。

## 三、根因（读代码后确认）

### 根因1：字段目录只读物理列，看不到 MDL 计算列

`schema_catalog.py` 的 `_shape_catalog` 只从 `information_schema.COLUMNS` 整理字段。`field_grounding.py` 的 `_columns()` 只额外合并了 `pic_position` 的 JSON 字段。

Wren 模型里用 `ref_sql` 或 `is_calculated` 声明的计算列，例如 `section_length_km`、`route_length_km`，字段目录完全不可见。用户说"路段长度"时，本地字段触达在物理列注释里找不到任何带"长度"的列，判定该字段不可达。

### 根因2：字段触达是纯字面匹配，极简注释列被规则排除

`field_grounding.py` 列级打分靠三条证据：列注释词元与问题词元重合、列注释短名整段出现在问题中、枚举值命中。

`meter` 列的注释只有一个字"米"。`_phrase_hit` 函数第128行要求列名长度不小于2，单字列直接返回 False。词元重合也要求问题里出现"米"这个词元，而用户说的是"长度"。于是桩点表的米数列永远拿不到分。

### 根因3：跨表字段只认单表，已有 JOIN 关系没有被利用

"路段名称、桩号在路段表，米数在桩点表"是一个跨表查询。Wren 的 `relationships.yml` 已经定义了 `pile_point.sections_id = section.id`，Wren 能正确 JOIN。

但确定性引擎按单表字段目录拼 SQL，拼不出这种跨表查询，过去的 `multi_field_join` 引擎还会把路段错误 JOIN 到边坡表。这类问题的正确出路是 Wren，而系统在字段触达阶段就判定"没有这列"，根本没走到 Wren。

### 根因4：本地匹配不到就直接判死，没有语义层兜底

`field_grounding.py` 把物理列里找不到的字段直接写进 `unavailable_fields` 和 `missing_fields`，下游据此回答"库里没有这列"。语义层虽然能看到 MDL 全文，但本地字段触达先下了结论，语义层没有机会对"路段长度"和"section_length_km"做语义对齐。

## 四、这是一类问题，不是单点

这类问题的本质是业务概念到物理字段之间的语义鸿沟，共三种形态，覆盖路线、路段、桥梁、隧道、边坡、工单、巡检全部资产对象。

### 形态A：派生指标

用户说的是算出来的概念，物理表没有现成列，MDL 里有计算列。

典型：路段长度（section_length_km）、路线长度（route_length_km）、密度、平均间距、总米数差、隧道长度、桥梁跨径合计。

### 形态B：极简或缺失注释列

列注释只有一个单位字，或注释与业务口语完全不同。

典型：桩点表的 meter 注释为"米"、各类 *_distance 列只写"距离"不写"谁的距离"。

### 形态C：跨表字段

用户一句话要的字段分布在多张表，表之间有明确外键关系。

典型：路段名称和桩号在路段表，桩点米数在桩点表；桥梁名称在桥梁表，所属路段桩号在路段表；工单编号在工单表，病害描述在病害表。

## 五、方案设计

总原则：不新增关键词表、不逐个问题打补丁、不重新连库。字段触达继续保持本地确定性计算保证速度，但喂给它的字段视图必须包含 MDL 计算列和完整语义描述；真正的语义判断交给已经能看到 MDL 的规划模型；需要跨表的查询交给 Wren。

### 层1：字段目录合并 MDL 模型列，让派生指标可达

在 `schema_catalog.py` 构建字段目录时，除了读取 information_schema 物理列，再读取 Wren 项目的模型定义。

做法：

1. 遍历每个模型的 `columns` 声明，拿到模型名、列名、类型、description。
2. 通过模型的 `table_reference` 或 `ref_sql` 里的 FROM 物理表名，把模型映射到物理表。
3. 用模型列名集合减去物理表列名集合，差集就是模型级计算列。
4. 计算列追加进该物理表的列清单，标注 `source: "mdl_calculated"`，带上 description 和所属模型名。

`section_length_km` 在路段模型的 columns 里声明，物理表没有，差集识别后写入路段表，描述为"路段实际长度（公里），由起止桩号相减算出"。用户说"路段长度"时，词元"长度"命中描述，字段触达即可达。

这是一次性机制，以后 MDL 新增任何计算列，重建目录后自动可达，不需要改代码。

字段目录缓存策略复用现有 TTL，重建字段目录时同步重新读取 MDL 模型目录，不额外增加数据库查询，只读取本地项目文件。

### 层2：极简注释列做确定性语义补全

在 `schema_catalog.py` 整理列信息时，对描述过短或只有单位字的列做标签补全。

补全规则：

1. 列描述去掉空格和标点后长度为 1，或只由单位词组成，单位词表为 米、千米、吨、个、次、处、条、座、根、%、天、小时。
2. 补全标签 = 所属表的业务名 + 列名语义。
3. 桩点表的 meter 补全为"桩点米数"，pile_distance 补全为"桩号解析米数"，pile_meter 补全为"距路段起点米数"。

列名到中文的映射从列名本身做确定性转换，例如 meter 转米数、distance 转距离、pile 转桩号，再加表业务名前缀。补全结果同时写入 MDL 模型的 description，保持语义层单一事实来源一致。

`field_grounding.py` 第128行的单字过滤保留，防止"是、否、米"这类字在句子里误匹配，但补全后的标签长度已经超过 2，可以正常参与短语命中。

### 层3：跨表字段走 Wren，读 MDL 关联关系，不复活多表引擎

`field_grounding.py` 已经把每张表命中的列保存在 `table_fields` 里。利用这个现成结果做跨表判定。

判定逻辑：

1. 语义层点名的字段经过层1和层2后，分别归属到不同的表。
2. 当字段归属表数量大于等于2时，读取 `relationships.yml`，判断这些表之间是否存在连通的 JOIN 路径。
3. 存在连通路径时，不要求确定性引擎单表硬拼，也不回答"没有这列"，而是把这道题标记为跨表查询，路由到 Wren。
4. 传给 Wren 的提示词包含三张信息：每个字段归属哪张表的哪个物理列、表之间的 JOIN 条件、字段的中文描述。

"路段名称、桩号、米数"这道题，字段落在路段表和桩点表，relationships 里有 `pile_point.sections_id = section.id`，路由到 Wren 后由 Wren 生成 JOIN SQL。

表间关联关系全部从 MDL relationships 读取，不手写 JOIN 条件。桥隧边坡与路段的关联已经在 relationships 里定义，天然覆盖。

### 层4：本地未命中字段交语义层兜底，不提前判死

调整 `field_grounding.py` 中不可达字段的判定时机。

1. 物理列和 MDL 计算列的并集都匹配不到的字段，先标记为"待语义确认"，不直接写进 `unavailable_fields`。
2. 规划模型看到候选表的完整列清单后，对这类字段做一次语义映射。规划模型本来就会收到字段清单和 MDL，不增加模型调用次数。
3. 模型把"路段长度"映射到 section_length_km 或 end_meter_total 减 start_meter_total，字段转为可达。
4. 模型也确认所有候选表都没有这个字段时，才写入 `unavailable_fields`，由下游如实回答"没有这列"并提示库里有哪些相近字段。

## 六、代码改动点

### 6.1 `backend/app/services/schema_catalog.py`

新增函数 `_mdl_calculated_columns(kind)`：

1. 读取 Wren 项目目录下每个模型的 `metadata.yml`。
2. 解析模型到物理表的映射，`table_reference.table` 直接取表名，`ref_sql` 用正则提取 FROM 后的表名。
3. 模型列与物理列做差集，返回计算列列表，字段含 name、type、description、model、source 标记。

在 `_shape_catalog` 组装每张表的 columns 时，把对应物理表的计算列追加到末尾，结构与物理列保持一致，额外带 `source` 字段。

新增函数 `_enrich_tiny_label(table_label, column_name, comment)`：实现层2的极简注释补全规则。

### 6.2 `backend/app/services/field_grounding.py`

`_columns()` 函数读取字段目录时，让 `source=mdl_calculated` 的列正常进入列清单，计算列的 label 用 MDL description，不加入停用列。

`_expresses()` 判定一张表能否表达某字段时，候选列集合改为物理列加 MDL 计算列。

新增跨表判定逻辑：对 wanted 字段的归属表集合，调用 Wren 关系图判断连通性，结果写入返回结构的 `cross_table` 字段，包含 join 路径和字段归属。

`unavailable_fields` 的写入增加门槛：物理列和计算列都未命中且没有跨表路径时，先标 pending，由语义层确认后再决定是否不可达。

### 6.3 `backend/app/services/wren_engine.py`

新增函数 `join_path(kind, tables)`：

1. 读取 relationships.yml，构建模型之间的无向关系图。
2. 给定多个表，返回连接它们的最短关系路径和每条关系的 condition。
3. 找不到路径返回空。

### 6.4 `backend/app/services/nl2sql.py`

读取字段触达结果时，若 `cross_table` 非空，跳过单表确定性引擎，把跨表字段证据和 JOIN 条件加入 Wren 提示词，走 Wren 编译。

规划提示词中增加说明：跨表字段按 JOIN 路径取数，不要在单表内编造不存在的列；派生指标优先用 MDL 计算列，不要用台账手填的 distance 字段。

### 6.5 MDL 描述补全

补全 `wren_projects` 下相关模型的极简字段 description，重点是桩点表 meter 以及各资产表语义不清的 distance 列。描述写明业务含义和单位，例如"桩点距路段起点的米数"。

## 七、数据流（改动后）

1. 用户提问，进入字段触达。
2. 字段目录读取 information_schema 物理列，并合并 MDL 计算列、补全极简注释。
3. 字段触达按物理列和计算列的并集做本地匹配，得到字段归属。
4. 字段分布在多张表且 MDL 有连通路径，标记跨表，路由 Wren。
5. 本地未命中的字段交规划模型在完整列清单和 MDL 中做语义映射。
6. 模型确认不存在的字段才如实回答。
7. 全程只读本地字段目录和 MDL 项目文件，不新增数据库连接。

## 八、给 Codex 的执行清单

1. `schema_catalog.py` 新增 MDL 模型目录读取和计算列差集识别，计算列并入字段目录。
2. `schema_catalog.py` 新增极简注释列的确定性标签补全。
3. `wren_engine.py` 新增基于 relationships.yml 的多表 JOIN 路径查询。
4. `field_grounding.py` 让计算列参与匹配和可达性判断，新增跨表判定和 pending 字段状态。
5. `nl2sql.py` 跨表查询路由 Wren，传入字段归属和 JOIN 条件。
6. 补全 MDL 中 meter 等极简字段的描述。
7. 字段目录重建后验证计算列已写入、极简列标签已补全。

## 九、回归测试

### 派生指标
1. "路段名称、桩号、路段长度" → 命中 section_length_km，不再回答没有长度列。
2. "每条路线的长度是多少" → 命中 route_length_km。
3. "西乡段的路段长度是多少" → 单表取计算列。
4. "各路段的病害密度" → 用 section_length_km 算密度，不用 distance。

### 极简注释列
5. "列出桩点的米数" → 命中桩点表 meter。
6. "每个桩点距离路段起点多少米" → 命中 pile_meter 或 meter。

### 跨表字段
7. "路段名称、桩号、路段米数" → 路段表 JOIN 桩点表，走 Wren，不再 JOIN 边坡表。
8. "每座桥梁的名称和所属路段桩号" → 桥梁表 JOIN 路段表。
9. "每个隧道的名称和所在路段长度" → 隧道表 JOIN 路段表。
10. "每个边坡的名称和所属路线" → 边坡表 JOIN 路段表再 JOIN 路线表。
11. "工单编号和对应的病害描述" → 工单表 JOIN 病害表。

### 语义兜底
12. "路段有多长" → 语义映射到 section_length_km。
13. "这段路一共多少米" → 语义映射到长度计算列或总米数差。
14. "桥梁在哪个省" → 全库确实没有，如实回答没有该列，并列出相近字段。

### 不回归
15. 原有单表字段查询结果不变。
16. 字段触达耗时不增加明显，MDL 目录读取走本地文件并随目录缓存。
17. 已经删除的 multi_field_join 引擎不被恢复。
18. 路线、桥梁、隧道、边坡、工单各类对象的明细查询不受影响。

## 十、核心原则

1. 派生指标通过 MDL 计算列差集自动并入字段目录，一次机制长期生效。
2. 极简注释列按表业务名和列名确定性补全，不维护业务关键词表。
3. 跨表查询读 MDL relationships 走 Wren，不复活确定性多表引擎。
4. 本地匹配不到的字段先交语义层确认，不提前判死。
5. 覆盖全部资产对象，不针对路线打补丁。
6. 只读本地 MDL 和字段目录，不新增数据库连接。
