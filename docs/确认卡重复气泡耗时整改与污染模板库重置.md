# 确认卡点选后提速、重复气泡修复 + 污染自动模板库重置（给 codex）

本篇处理三件实测问题：
1. 点完确认卡，对话里又冒出一条一模一样的用户问题（截图实证两条相同蓝色气泡）；
2. 命中确认卡后，点「用这口径查询」到出结果仍偏慢（目标：和快捷查询/看板刷新同量级）；
3. 现有自动模板库已被污染，需要清空重来，但不能误删快速通道内置模板和用户收藏。

**边界（用户明确要求）**：第一次"发送问题 → 弹出确认卡"这一段**保留完整规划模型**，每个问题仍先过一道 parse_semantics，保证口径识别准；本次**不做**零 LLM 快匹配前移、不扩大轻量探测（can_light_probe）、不跳过规划。要优化的只有"用户在卡上选定模板 → 出结果"这一段。

---

## 一、前端 P0：确认动作重发同一句，导致重复用户气泡 + 可能重复提交

实测链路（`frontend/src/components/ChatPanel.vue`）：
- 第一次提问走 `sendMessage(text)`，第 862 行 `messages.value.push({ role: 'user', content: text })`，用户气泡①上屏；后端返回候选，第 877 行把原问题存进 `pendingQuestion`，弹出确认卡。
- 点「用这口径查询」走 `confirmCapability()`（606-637），第 632 行**再次调用 `sendMessage(text, …)`**，而 sendMessage 第 862 行无条件再 push 一次 → 用户气泡②，内容和①完全相同。
- `chooseSteps()`（696-703）、`confirmSteps()`（706-723）同理，都会重发同一句并再 push 一条气泡。

这就是截图里同一句"置信度最高的病害是哪个？类型是什么？桩号？"出现两条、体感"弹完卡又出现一个对话"的根因。确认是对**已上屏那条问题**选择口径，不是用户又问了一遍。

改法：
1. sendMessage 增加一个参数，例如 `reissue = false`（放进现有 extra 即可）。当它是确认/步骤重发（带 `choose_token`/`capability_id`，即 confirmCapability、chooseSteps、confirmSteps 三处）时 `reissue=true`，**跳过第 862 行的用户气泡 push**；只把原气泡①就地置为"已确认口径，查询中"状态。
2. 普通打字发送、「让 AI 自己查」如果是新问题，仍正常 push。
3. 确认按钮（287 行「用这口径查询」、步骤确认按钮）点击后立刻 `disabled + loading`，本次请求返回（出结果 / 重新摆卡 / 报错）前不可再点，防止连点发两次。截图底部停在"正在查看这次结果"，说明缺少提交期锁。
4. 重新摆卡（token 失效、绑定失败）时不要再新增用户气泡，复用同一张卡/同一气泡更新提示文案。

验收：任意命中确认卡的问题，点确认后对话流里只有一条用户气泡；快速连点按钮只发出一次确认请求。

## 二、只优化"点确认之后"：第一次弹卡的规划保留，砍掉确认后的多余动作

### 现状核对（这部分 codex 已经做对，不要回退）
确认请求（execute_choice，agent.py 3076-3077、3147-3218、3396-3465）已经：不做长对话补全、不做意图分类、不重新规划（复用暂存的 chosen_plan）、不选表、不进 Wren、不检索 RAGFlow；结果总结对非归因题走 `_summarize_rows_core` 纯本地确定性文案（`_summarize_rows` 869-896，只有"为什么/原因"等归因词才调 `_llm_result_summary`）；外层 chosen_* 已在 `_DETERMINISTIC_ENGINES` 短路集合（2461-2498），不再校验/反思/追问。

也就是说，点确认后**理论上已经没有大模型调用**。还剩三处会拖慢或埋雷，按下面改。

### P0-1 用户已确认的 SQL，仍被范围校准 calibrate 拦一道
`_build_query_result` 现在对每条结果都先跑 `calibrate.check(plan)`（1327-1332），coverage=none 会在 1332-1358 提前返回、**根本不执行用户认的那条 SQL**；calibrate 内部还会为桩号/时间条件额外发范围探测 SQL（多一次甚至多次连库往返）。

确认卡场景下，SQL 和口径用户已经看过并点了确认，范围校准没有意义，反而多跑探测、还可能把确认过的查询提前截胡。
改法：`forced_sql`/`forced_engine` 非空时跳过 `calibrate.check`，直接执行绑定 SQL；零结果的 `calibrate.explain_zero/explain_numeric_zero`（1626-1639）在确认路径也不要再发范围探测，按真实 0 行确定性返回即可。

### P0-2 用户已确认的 SQL，仍进"生成 SQL 校验重试环"，可能被规则误判后偷偷调 LLM 重写
forced_sql 非空时 `candidate = forced_sql`，但仍进入 1467-1538 的重试环，依次过 `validate_semantics`、`unknown_columns`、`field_misuse_issue`、`sql_shape_issue`、`route_length_issue` 五道校验。任何一道误判都会 `sql=None`、置 last_error，随后在 1473-1475 调 `generate_with_context` **让大模型重写**——这会带来一次大模型往返（变慢），还可能把用户确认的模板 SQL 换成 Wren/LLM 结果（这正是偶发"明明点了模板、结果台却显示 Wren 语义层/突然变慢"的隐患之一）。

这五道校验是给"LLM/Wren 新生成的 SQL"挑错用的，不该作用于用户已经确认过的模板 SQL。
改法：forced_sql 路径**不进生成/校验/重试环**，绑定成功后直接 `sql_engine.execute_sql(kind, forced_sql)` 执行一次；执行报错就如实把数据库错误返回（SQL 来自已确认模板，不触发自由重写、不静默换引擎）。仅当不是 forced_sql（AI/Wren 新生成）时才走现在的五道校验 + 重试。

### P0-3 前端重复气泡 / 无提交锁
见第一节。一次确认若在界面上产生两条相同问题、或连点发出两个请求，体感就是"点完又冒一条、还慢"。

### P1（可选，确认后仍偏慢再查，不引入新 LLM）
- `_empty_condition_note`（1621）若会对每个条件连库探测"整列是否为空"，确认路径应复用缓存或在 forced_sql 时跳过，不新增连库往返。
- 确认后只允许保留：一次必要的模板 SQL 执行 + 本地确定性文案/图表数据计算。SeaweedFS 逐张拉图只在 photo/list 且用户明确要看图时进行，不阻塞文字结果先返回。
- 不允许为了"确认后提速"去动第一次弹卡前的规划，也不要给确认请求加任何新的大模型环节。

### 验收（用"置信度最高的病害是哪个？类型是什么？桩号？"以及任意模板题实测）
- 发送→弹卡这一段不变：仍先过规划模型（不追求这段变快）。
- 点「用这口径查询」到出结果：该次请求后端日志中大模型调用次数为 0、无 calibrate 探测 SQL、不进 generate_with_context、无 verify/reflect/followup，只有一次模板 SQL 执行。
- 结果台引擎稳定显示 chosen_* 对应中文名与"零大模型直出"标记，不出现 Wren 语义层。
- 对话流只有一条用户气泡，连点按钮只发一次请求。
- 确认后耗时降到与快捷查询/看板刷新同量级（亚秒~1 秒级，仅剩 SQL 执行与前端渲染）。

## 三、清空被污染的自动模板库，并在修复合入前暂停自动重挖

### 3.1 要删的（自动挖掘产物，已被污染）
重置 `backend/app/data/auto_templates.json` 为空骨架：
```json
{ "version": 1, "generated_at": null, "templates": [], "rejects": [] }
```
现有 5 条 mature 全部作废，原因见《自动模板挖掘代码评审与整改方案.md》：
- auto_6e7126…（巡检次数）：`r.short_name = '{route_id}'` 名称列绑 route_id，且用病害表 INNER JOIN 巡检表 COUNT(DISTINCT) 算巡检次数，会漏掉没病害的巡检任务，口径错误；
- 其余 4 条：damage_type 选项一类多码、混入 adsad213223/eqweqw2313/848626 等测试脏值，且每条内联整份字典。

可以直接用已有的 `templatizer.delete(id)` / generic_api 删除接口逐条删，或直接把文件重置成上面的空骨架。

### 3.2 绝不能删的
- `backend/app/data/preset_queries.json`：快速通道/预置内置模板（参数从库里动态查 routes_with_data/months/damage_types），是人工维护的确定性模板，**保留不动**。
- store 里的原始问答对/固定看板收藏（`store.list_recorded_example_pairs` 取的 trusted 记录，templatizer.py 1208-1213）：那是用户"答对了/固化"沉淀的原始资产，也是修好后重新挖槽的原料，**一条都不要删**。这次只清"从问答对挖出来的自动模板 JSON"，不清原始问答对。

### 3.3 关键：光删文件会被立刻写回来，必须同时关掉自动挖掘
现状 `auto_template_enabled` 开关（chat_settings.py:52，默认 True）只在运行期推荐处被读取（capabilities.py:113 的 templatizer.match），**管不住挖掘**：
- 后端启动 `main.py:75-77` 会跑一次 `templatizer.mine_all()`；
- 每次点「答对了」`chat.py:267-272` 后台又跑一次 `mine_all()`。

所以重置文件后，一旦重启或再点"答对了"，同样的污染模板（short_name 错配、脏 options、错误口径）会被重新写回。请改成：
1. 让挖掘也受开关控制：新增或复用一个开关（例如 `auto_template_mine_enabled`，修复合入前默认 false；也可直接让现有 auto_template_enabled=false 同时拦住 mine_all）。main.py:77、chat.py:272 两处调用前先判断，关闭时启动不挖、approve 只记录 trusted 不触发挖掘。
2. 在《自动模板挖掘代码评审与整改方案.md》的 P0-1（name/id 槽）、P0-2（Wren/CTE 白名单）、P1-1（换值回环+计数口径风控）、P1-2（选项去重去脏/共享字典）、P1-3（指纹 upsert 不全量覆盖）合入并验证前，保持挖掘关闭。
3. 修复后第一次重建：先全部落 candidate（不自动 mature），人工核对口径无误再 promote；确认无误后再把挖掘/推荐开关打开。
4. 顺手修 P1-3：mine_all 改指纹 upsert，未被本次触及的现有模板原样保留，避免以后开关重开、trusted 超过 500 截断时又把模板静默删掉。

验收：
- 重置后 auto_templates.json 为空；preset_queries.json 与 trusted 问答对数量不变；
- 关闭挖掘开关后重启后端、连点几次"答对了"，auto_templates.json 仍为空、不出现 auto_* 记录，对话里也不再推荐自动模板（预置内置模板的卡照常）；
- 修复合入、重新打开开关后，新挖出来的模板：路线槽统一 id 列、类型选项无重名无脏值、计数口径类默认 candidate、Wren 成功 SQL 能被挖成模板。
