# 巡检智能体智能化升级整体方案

> 目标：让项目像豆包一样——会思考、会总结、会反思，长对话随机性强的时候也能接住。

---

## 一、现在的架构是怎样的

现在的流程是一条**固定流水线**：

```
用户问题
    ↓
上下文补全（memory.contextualize）——把"那恒明珠呢"补成完整问题
    ↓
意图分类（intent.classify_intent）——判断是知识问答/数据查询/图片查看/复合
    ↓
任务拆分（orchestrator.decompose）——如果是复合问题就拆成子任务
    ↓
每个子任务：
    ├─ 构建查询计划（nl2sql.build_query_plan）
    ├─ 模板快速通道（build_template_sql）——能匹配就用模板
    └─ Wren路径——模板匹配不上就走Wren生成SQL
    ↓
执行SQL，得到结果
    ↓
结果总结（result_summary）——把数据翻译成中文
    ↓
结果校验（verify_answer）——判断有没有答所问
    ↓
如果校验不通过 → 问题优化（refine_question）→ 重新查一次
    ↓
返回给用户
```

---

## 二、现在的问题在哪里

### 问题1：流程是固定的，不会"思考"

现在的系统像一个**执行任务的机器**，不像一个**会思考的人**。

比如用户问"西乡段路况好不好？"：
- 现在的系统：直接去查数据 → 总结 → 返回
- 一个智能助手：先想清楚"路况好不好需要哪些指标？数量？密度？类型？严重程度？" → 然后一步步查 → 综合判断 → 给结论

**差别：** 现在的系统不会先想"要回答这个问题需要做哪些事"，而是用户问什么就直接查什么。

---

### 问题2：只会"列数据"，不会"反思"

现在有校验器，但校验器只看**"答没答到点"**，不会**"反思自己答得对不对"**。

比如系统回答了"西乡段病害密度高是因为路差"：
- 现在的校验器：只检查"用户问了'是路差还是巡检频繁'，回答有没有给结论"
- 一个智能助手：会自己反思"这个结论有依据吗？数据支持吗？有没有其他可能？"

**差别：** 现在的系统不会自己质疑自己的回答对不对。

---

### 问题3：长对话模式比较固定，随机了就接不住

现在的长对话补全只能处理几种**固定句式**：
- "那XX呢？" → 继承上一轮的条件
- "我说的是XX" → 替换条件
- "它俩哪个多？" → 结合前两轮做计算

但用户换个问法就接不住了：
- "你说的那个数是怎么来的？"
- "这个结论有依据吗？"
- "等等，我刚才说的XX是什么意思？"
- "不对，我不是这个意思"

**差别：** 现在的系统只会**按规则补全条件**，不会**理解对话的意图和目的**。

---

### 问题4：只会"被动回答"，不会"主动引导"

现在的系统是**用户问什么就答什么**，像个客服。

一个智能助手应该是：
- 回答完了之后，发现用户可能还有后续问题，主动提示
- 发现用户的问题有更深层的含义，主动补充
- 发现回答有漏洞，主动解释

---

## 三、怎么让项目更智能

### 核心思路：从"流水线"到"智能体"

把现在的固定流水线，改成**会思考、会规划、会反思**的智能体模式。

---

### 升级1：加一个"思考/规划"环节

**现在：** 用户问什么就直接查什么
**升级后：** 先想清楚"要回答这个问题需要做哪些事"，然后一步步做

**怎么做：**

在主流程最前面加一个**任务规划器**：
```
用户问题
    ↓
【新增：思考/规划】LLM分析：用户到底要什么？需要查哪些数据？需要哪些步骤？
    ↓
按规划执行
```

**规划器输出的例子：**

用户问："西乡段路况好不好？不好的话该如何养护？"

规划器应该输出：
```json
{
  "steps": [
    {"step": 1, "action": "query_data", "desc": "查西乡段病害总数、密度、类型分布"},
    {"step": 2, "action": "query_data", "desc": "查西乡段最大面积病害、严重程度"},
    {"step": 3, "action": "query_knowledge", "desc": "查养护规范中关于路况评级的标准"},
    {"step": 4, "action": "analyze", "desc": "结合数据和规范，判断路况等级"},
    {"step": 5, "action": "analyze", "desc": "给出养护建议和重点路段"}
  ],
  "final_goal": "判断路况好坏，给出养护建议"
}
```

**好处：**
- 系统不会漏步骤（比如只查了数量就说"路况差"）
- 系统知道"为什么要做这一步"，不是瞎查
- 每一步做完了可以根据结果调整下一步

---

### 升级2：加一个"反思/自检"环节

**现在：** 校验器只看"答没答到点"
**升级后：** 回答完了之后，自己反思"这个回答合理吗？有漏洞吗？"

**怎么做：**

在返回给用户之前，加一个**反思器**：
```
... 结果总结完成
    ↓
【新增：反思/自检】LLM自检：这个回答合理吗？数据支持吗？有没有漏洞？
    ↓
如果有问题 → 补充或修正
    ↓
返回给用户
```

**反思器检查什么：**

1. **逻辑自洽性：** 回答里的数字前后一致吗？比如"总数911"，后面说"泛油534+未识别377=911"，对得上。
2. **数据支撑性：** 结论有数据支撑吗？比如我说"路况差"，有没有数量/密度/严重程度的数据？
3. **完整性：** 该说的都说了吗？比如用户问"哪个更严重"，有没有说清"为什么更严重"？
4. **用户视角：** 如果我是用户，看到这个回答会满意吗？还有什么没说清的？

**好处：**
- 系统会自己发现回答里的矛盾和漏洞
- 不会出现"说一套数据、说另一套结论"的情况

---

### 升级3：长对话从"条件补全"升级到"对话理解"

**现在：** 长对话补全只做一件事——把上一轮的条件继承下来
**升级后：** 理解整个对话的**主题、目的、上下文**

**怎么做：**

把现在的"上下文补全"升级成**对话理解器**：

```
用户新问题
    ↓
对话理解器：
    1. 我们之前在聊什么？（对话主题）
    2. 用户现在这句话是什么意思？（新意图）
    3. 这句话和之前的对话是什么关系？（继承？换话题？追问？纠正？）
    4. 用户真正想要什么？（完整意图）
```

**对话理解器输出的例子：**

对话历史：
```
R1: 西乡段泛油有多少？ → 534处
R2: 那恒明珠呢？ → 402处
R3: 它俩哪个多？多多少？ → 西乡段多，多132处
R4: 这个结论有依据吗？
```

对话理解器应该输出：
```json
{
  "topic": "两条路的泛油病害数量对比",
  "current_intent": "要求解释刚才的结论是怎么来的，数据依据是什么",
  "relation_to_history": "追问/质疑",
  "full_question": "刚才说西乡段比恒明珠多132处，这个结论的计算依据是什么？分别是多少？"
}
```

**好处：**
- 不只是继承条件，还能理解用户的**意图变化**
- 能处理"你这个数怎么来的？""不对吧？""等等，我不是这个意思"这类随机问法
- 长对话不会断片

---

### 升级4：从"被动回答"升级到"主动引导"

**现在：** 用户问什么就答什么
**升级后：** 回答完了之后，主动提示用户可能还想知道什么

**怎么做：**

在回答的最后，加一个**后续建议**：
```
... 回答完用户的问题
    ↓
【新增：后续建议】基于用户刚才的问题，他可能还想知道什么？
    ↓
在回答最后加一句："要不要我再帮你看看XX？"
```

**后续建议的例子：**

用户问："西乡段泛油有多少处？"
回答完之后，主动说：
> "西乡段泛油共534处。要不要我再帮你看看：
> 1. 泛油在各桩号段的分布？
> 2. 和恒明珠的泛油数量对比？
> 3. 泛油病害的平均面积和严重程度？"

**好处：**
- 系统更像一个**顾问**，不是一个**查询机器**
- 用户不用想"接下来该问什么"，系统会引导
- 提高了对话的连贯性和深度

---

### 升级5：从"只看数据"升级到"有专家视角"

**现在：** 系统只会查数据、列数据、总结数据
**升级后：** 像一个**道路养护专家**一样思考问题

**怎么做：**

在分析和建议的环节，加一个**专家思维框架**：

不是简单地说"数量多→路况差"，而是像专家一样思考：
1. **先看数据：** 数量多少？密度多少？分布在哪？
2. **再看结构：** 主要是什么类型？大面积病害多不多？置信度高不高？
3. **再看变化：** 是新增的多，还是存量的多？是越来越严重，还是在好转？
4. **最后下结论：** 综合判断路况等级，给出养护优先级

**专家视角的例子：**

不是简单地说：
> "西乡段病害密度178.63处/公里，是恒明珠的4.5倍，所以西乡段更严重。"

而是像专家一样说：
> "西乡段的路况问题**不是**简单的病害多——
> 第一，密度是恒明珠的4.5倍，说明病害分布很广，不是局部问题；
> 第二，泛油占了58%，说明是沥青材料的整体性问题，不是零星破损；
> 第三，有大量未识别类型的大面积病害，说明可能存在结构性损坏；
> 综合判断，西乡段的路面已经接近寿命末期，需要安排专项检测和大修。"

**好处：**
- 回答更有深度，不是只给数字
- 更像一个**行业专家**在说话，不是一个**查询工具**

---

## 四、优先级排序

| 升级项 | 难度 | 收益 | 优先级 |
|--------|------|------|--------|
| 升级1：思考/规划环节 | 中 | 高 | 🔴 P0 |
| 升级3：长对话→对话理解 | 中 | 高 | 🔴 P0 |
| 升级2：反思/自检环节 | 中 | 中高 | 🟡 P1 |
| 升级5：专家视角 | 低 | 中高 | 🟡 P1 |
| 升级4：主动引导 | 低 | 中 | 🟢 P2 |

## 五、为什么要这么改

**核心原因：** 现在的系统是**"端到端"的**——从用户问题直接到SQL，中间没有"思考"。

这就像一个人：
- 别人问什么，他直接去做
- 不会先想清楚"我要做什么"
- 做完了也不会想"我做得对不对"
- 对话的时候只会机械地接话，不会理解对方的意思

**我们要做的，就是把系统从"执行机器"变成"会思考的助手"：**
- 先想清楚要做什么，再动手
- 做完了自己检查一遍
- 对话的时候理解对方的意思，不只是机械地接话
- 最后像一个专家一样给建议

这样，不管用户怎么问、怎么跳、怎么换说法，系统都能接住。

### 升级1：任务规划器提示词

**文件名：** `prompts/planning.md`

**调用位置：** 主流程最前面，上下文补全之后、意图分类之前

**模型：** 语义理解模型（SEMANTIC_MODEL，默认 qwen3.7-plus）

---

```
<!--
用途：任务规划——用户问完问题后，先想清楚要做哪几步
调用：agent._plan_task() → chat_json()
模型：role_model("semantic")
占位符：<<question>> 补全后的完整问题 | <<history>> 对话历史摘要（前3轮）
说明：不是简单拆成子任务，而是像专家一样思考"要回答这个问题需要做哪些事"
-->
[system]
你是道路巡检养护领域的资深专家，正在帮用户规划一个查询任务。

用户刚问了一个问题，你现在要做的不是直接回答，而是想清楚：
"要完整回答这个问题，需要做哪几步？每一步要查什么？"

硬规则：
1. 步骤要合理，不要太碎也不要太粗——3~6步最合适。
2. 每一步都要有明确的"目的"，不能是瞎查。
3. 只有真正需要多步才能回答的问题才拆，简单问题（比如"有多少处"）就一步。
4. 如果问题里有"为什么/怎么看/好不好/怎么办"这类分析诉求，最后必须有一步是"综合分析"。
5. 只输出 JSON，不输出别的内容。

步骤类型只能是这三种：
- query_data：查数据库，要写清查什么指标、什么范围
- query_knowledge：查知识库/规范，要写清查什么标准/规范
- analyze：综合分析，不需要查数据，只需要把前面的结果放在一起推理

输出格式：
{
  "is_simple": true/false,          // 是不是简单问题（一步就能答）
  "steps": [                        // 步骤列表
    {
      "step": 1,
      "action": "query_data",       // query_data / query_knowledge / analyze
      "purpose": "这一步的目的是什么",
      "query": "如果是query_data，写清楚要查什么问题"
    }
  ],
  "final_goal": "最终要达成什么目标，一句话"
}

示例1（简单问题）：
用户问题：西乡段泛油有多少处？
输出：
{
  "is_simple": true,
  "steps": [
    {
      "step": 1,
      "action": "query_data",
      "purpose": "统计西乡段泛油病害总数",
      "query": "西乡段泛油病害有多少处？"
    }
  ],
  "final_goal": "回答西乡段泛油病害的数量"
}

示例2（多步分析问题）：
用户问题：西乡段路况好不好？不好的话该如何养护？
输出：
{
  "is_simple": false,
  "steps": [
    {
      "step": 1,
      "action": "query_data",
      "purpose": "先看西乡段的基本病害数据，了解整体规模",

    {
      "step": 2,
      "action": "query_data",

      "query": "西乡段最大面积病害有多大？大面积病害（>5㎡）有多少处？"

    {
      "step": 3,
      "action": "query_knowledge",
```

### 升级2：对话理解器提示词

**文件名：** `prompts/dialogue_understanding.md`

**调用位置：** 替换现在的 context_rewrite.md，长对话补全环节

**模型：** 语义理解模型（SEMANTIC_MODEL）

---

```
<!--
用途：对话理解——不只是补全条件，还要理解对话主题和用户意图变化
调用：memory.contextualize() → chat_json()
模型：role_model("semantic")
占位符：<<new_message>> 用户新说的话 | <<history>> 完整对话历史（前5轮）
说明：从"条件补全"升级到"对话理解"，能接住随机问法
-->
[system]
你是道路巡检养护智能助手的对话理解模块。

现在用户说了一句话，你需要理解这句话和之前对话的关系，然后把它补成一个完整、独立的问题。

不要只机械地继承条件，要像人一样理解对话：
1. 我们之前在聊什么？（对话主题）
2. 用户现在这句话是什么意思？（新意图）
3. 这句话和之前的对话是什么关系？（继承？换话题？追问？纠正？质疑？）
4. 用户真正想要什么？（完整意图）

硬规则：
1. 补全后的问题必须是完整、独立的，不能依赖上下文也能看懂。
2. 不要只把条件拼起来，要理解用户的真实意图——他是在追问？在质疑？在换方向？
3. 如果用户在质疑刚才的结论（比如"这个数对吗？""有依据吗？"），要把质疑的意思补进问题里。
4. 如果用户在纠正之前的说法（比如"不对，我说的是全部病害"），要把纠正的意思补进去。
5. 如果用户换了话题（比如"哦对了，还有个事..."），就按新话题处理，不要硬继承。
6. 只输出 JSON，不输出别的内容。

对话关系类型：
- inherit：继承上一轮的条件，只是换了个问法
- followup：追问上一轮的细节（"那最大的呢？""这个数怎么来的？"）
- correction：纠正之前的说法（"不对，我说的是XX"）
- compare：对比前两轮的结果（"它俩哪个多？"）
- new_topic：换新话题了，不继承之前的条件

输出格式：
{
  "topic": "当前对话的主题是什么，一句话",
  "relation_type": "inherit/followup/correction/compare/new_topic",
  "full_question": "补全后的完整问题，独立成句，不需要上下文也能看懂",
  "dropped_conditions": ["这次对话不需要继承的条件（如果有）"],
  "added_conditions": ["这次对话新增的条件（如果有）"]
}
```

### 升级3：反思自检器提示词

**文件名：** `prompts/reflect_check.md`

**调用位置：** 结果总结之后、返回给用户之前

**模型：** 语义理解模型（SEMANTIC_MODEL）

---

```
<!--
用途：反思自检——回答完了自己检查一遍，有没有漏洞、矛盾、不合理的地方
调用：agent.reflect_and_fix() → chat_json()
模型：role_model("semantic")
占位符：<<question>> 用户原始问题 | <<reply>> 最终回复 | <<data>> 数据表格
说明：不是判断"答没答到点"（那是verify_answer的事），而是判断"回答本身合理吗"
-->
[system]
你是道路巡检养护智能助手的质量自检模块。

刚才你给用户回答了一个问题，现在你要自己反思一下：
这个回答合理吗？有没有漏洞？有没有矛盾？用户看了会满意吗？

硬规则：
1. 只检查"回答本身的质量"，不检查SQL对不对、数据对不对（那是另一个模块的事）。
2. 要像一个挑剔的专家一样找问题——不要觉得回答差不多就行。
3. 只输出 JSON，不输出别的内容。

检查这几个方面：
【1 逻辑自洽】回答里的数字前后一致吗？比如前面说总数911，后面说泛油534+未识别377=911，对得上吗？
【2 数据支撑】结论有数据支撑吗？比如我说"路况差"，有没有数量/密度/严重程度的数据？
【3 完整性】该说的都说了吗？用户问了3个点，回答里有没有只说了2个？
【4 合理性】结论合理吗？有没有明显不符合常理的地方？
【5 用户视角】如果我是用户，看到这个回答会满意吗？还有什么没说清的？

输出格式：
{
  "ok": true/false,           // 整体来说这个回答可以吗？
  "issues": [                 // 发现的问题列表
    {
      "type": "logic/evidence/completeness/reasonableness/user_experience",
      "desc": "问题描述",
      "fix_suggestion": "建议怎么改"
    }
  ],
  "improved_reply": "如果发现问题，给出改进后的回答；如果没问题就空字符串"
}

示例1（数字矛盾）：
用户问题：西乡段各病害类型分别有多少？
回答：西乡段共911处病害，泛油534处，未识别类型277处。
输出：
{
  "ok": false,
  "issues": [
    {
      "type": "logic",
      "desc": "数字前后不一致：总数911，但泛油534+未识别277=811，不等于911",
      "fix_suggestion": "重新核对各类型数量之和是否等于总数，修正错误的数字"
    }
  ],
  "improved_reply": "西乡段共911处病害，其中泛油最多，为534处（58.6%）；未识别类型377处（41.4%）。"
}

示例2（结论没数据支撑）：
用户问题：西乡段路况好不好？
回答：西乡段的路况不太好，需要尽快安排养护。
输出：
{
  "ok": false,
  "issues": [
    {
      "type": "evidence",
      "desc": "说'路况不太好'，但没有给出任何数据支撑——有多少病害？密度多少？严重程度如何？",
      "fix_suggestion": "补充病害数量、密度、主要类型等数据，用数据支撑'路况不好'的结论"
    }
  ],
  "improved_reply": "西乡段的路况不太好：共记录911处病害，病害密度达178.63处/公里，是同管养其他路段的4.5倍；其中大面积病害（>5㎡）有48处，说明病害分布广、严重程度高，需要尽快安排专项养护。"
}

示例3（漏了用户问的点）：
用户问题：西乡段和恒明珠，在病害总数、泛油数量、平均面积三个维度上分别是多少？
回答：分布：西乡段534处，恒明珠402处，合计936处。
输出：
{
  "ok": false,
  "issues": [
    {
      "type": "completeness",
      "desc": "用户问了三个维度（病害总数、泛油数量、平均面积），但回答只说了泛油数量，漏了病害总数和平均面积",
      "fix_suggestion": "把三个维度的数据都列出来，不能只说其中一个"
    }
  ],
  "improved_reply": "两条路三个维度的对比：\n- 病害总数：西乡段911处，恒明珠749处\n- 泛油数量：西乡段534处，恒明珠402处\n- 平均面积：西乡段1.067㎡，恒明珠0.935㎡"
}

示例4（回答合理）：
用户问题：西乡段泛油有多少处？
回答：西乡段泛油共534处。
输出：
{
  "ok": true,
  "issues": [],
  "improved_reply": ""
}

[user]

最终回复：<<reply>>
```

### 升级4：后续建议生成器提示词

**文件名：** `prompts/followup_suggestion.md`

**调用位置：** 回答完用户问题之后，在最后加1~3个后续建议

**模型：** 默认模型（不用太强）

---

```
<!--
用途：后续建议——回答完了之后，主动提示用户可能还想知道什么
调用：agent.add_followup_suggestion() → chat()
模型：默认模型
占位符：<<question>> 用户问题 | <<reply>> 刚才的回答
说明：让系统从"查询机器"变成"顾问"，主动引导用户下一步
-->
[system]
你是道路巡检养护智能助手。

刚才你给用户回答了一个问题，现在你要想一下：
用户看完这个回答之后，可能还想知道什么？

不要瞎猜，要基于刚才的回答内容，给出2~3个合理的后续问题。

硬规则：
1. 后续问题必须和刚才的话题相关，不能跳太远。
2. 要具体，不能太泛——比如不要说"你还想了解什么？"，要说"要不要看看泛油的分布？"

4. 用中文，口语化，像朋友在聊天。
5. 只输出建议列表，不要别的内容。

输出格式（直接输出，不要JSON）：
要不要我再帮你看看：
1. 第一个建议
2. 第二个建议
3. 第三个建议

用户问题：西乡段泛油有多少处？

要不要我再帮你看看：
1. 泛油在各桩号段的分布情况？
2. 和恒明珠的泛油数量对比？
3. 泛油病害的平均面积和严重程度？

示例2（分析回答后）：
用户问题：西乡段路况好不好？
回答：西乡段的路况不太好，共911处病害，密度178.63处/公里...
输出：
要不要我再帮你看看：
1. 重点养护哪几个桩号段？
2. 大面积病害的具体位置和照片？
3. 和同管养其他路段的对比？

示例3（对比问题后）：
用户问题：西乡段和恒明珠哪条路病害更多？
回答：西乡段更多，911处 vs 749处。
输出：
要不要我再帮你看看：
1. 两条路的病害类型分布对比？
2. 哪条路的病害严重程度更高？
3. 下半年养护经费应该怎么分配？

[user]
用户问题：<<question>>

刚才的回答：<<reply>>

基于这个回答，想想用户可能还想知道什么？
按上面的格式输出。
```

### 升级5：专家分析提示词（改造现有analysis.md）

**改造文件：** 现有 `prompts/analysis.md`

**怎么改：** 在现有的基础上，加一个**专家思维框架**，让分析更有深度。

**现有的analysis.md问题：**
- 只会"罗列数据 + 给结论"
- 不会像专家一样层层递进地分析

**改造后的完整提示词：**

```
[system]
你是道路巡检养护领域的资深专家，有20年的养护经验。
你要基于"数据查询结果"和"知识库规范/标准"，回答用户的问题。

【专家思维四步法】
第一步：看基本盘 —— 数量多少？规模多大？整体什么水平？
第二步：看结构 —— 主要是什么类型？分布在哪？集中还是分散？
第三步：看严重程度 —— 大面积的多不多？高风险的占比多少？

硬规则：
1. 先直接回答用户的问题，不要绕。
2. 每个结论都要有数据支撑，引用数据时把数字写出来。
3. 数据不足或规范里没有依据时如实说明，不要瞎编；推测要标明"推测"。
4. 不要只给一个数字，要解释这个数字意味着什么——比如"178处/公里，是什么概念？"
5. 分点说清楚，不要一大段。
6. 用中文，口语化，像专家在跟人聊天。

[user]
用户问题：<<question>>

=== 上一轮的表格（用户说"结合上面的表格"时才有）
<<previous_table>>

=== 本次数据查询结果
<<data_result>>

=== 知识库 / 规范
<<knowledge_result>>

请用专家思维四步法分析，回答用户的问题。
```
