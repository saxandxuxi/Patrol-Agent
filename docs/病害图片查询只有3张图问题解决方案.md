# 病害图片查询"永远只有3张图"问题解决方案

> 前提：只读库权限，不能改库，不能操作 SeaweedFS
> 核心问题：不管问什么病害类型的图片，前端都只显示同样的 3 张图
> 生成时间：2026-10-11

---

## 一、问题根因（连库验证）

### 1.1 数据层面：只有 3 张现场图在 SeaweedFS 上可访问

| 指标 | 数值 |
|---|---|
| ai_problem 总记录 | 1703 条，全部有 problem_url |
| 不同图片路径 | 65 个 |
| SeaweedFS 可访问 | **3 个**（102367594567 前缀，411 条记录） |
| SeaweedFS 不存在 | 62 个（1420324265166 前缀，1292 条记录，404） |

### 1.2 这 3 张图被严重共用

| 图片 | 对应记录数 | damage_type | pic_position 类型（AI识别） |
|---|---|---|---|
| 图1 | 139 条 | 10（泛油） | 划痕、块状修补、标牌绿化遮挡、标线缺损、横向裂缝... |
| 图2 | 138 条 | 10（泛油） | 划痕、块状修补、抛洒物、标牌绿化遮挡、标线缺损... |
| 图3 | 134 条 | 10（泛油） | 划痕、块状修补、抛洒物、标牌绿化遮挡、标线缺损... |

**关键发现：**
- 这 3 张图的 `damage_type` 都是 '10'（泛油）
- 但 `pic_position.$.type`（AI 识别类型）有 9 种不同的值
- 这是数据本身的问题：`damage_type` 和 `pic_position.$.type` 不一致

### 1.3 各病害类型的现场图可访问率

| 病害类型（AI识别） | 总记录 | 可访问图 | 丢失图 | 可访问率 |

| 横向裂缝 | 61 | 17 | 44 | 27.9% |

| 边角剥落 | 38 | 5 | 33 | 13.2% |

### 1.4 病害样图情况

| 指标 | 数值 |
|---|---|
| 字典表病害类型数 | 44 种 |
| 有样图的病害类型 | **44 种（全部有）** |
| 样图总数 | 84 个（每种类型 2 条记录） |
| 本地缓存可访问 | 42 个 |
| SeaweedFS 404 | 42 个 |

### 1.5 为什么"不管怎么问都是 3 张图"

**用户问"泛油的病害图片"：**
- SQL 用 `damage_type='10'` 过滤 → 返回 936 条记录
- 这 936 条记录对应 36 个不同图片路径
- 但只有 3 个路径在 SeaweedFS 上可访问 → 前端只显示 3 张图

**用户问"裂缝的病害图片"：**
- SQL 用 `pic_position.$.type LIKE '%裂缝%'` 过滤 → 返回纵向裂缝+横向裂缝+网状裂缝
- 这些记录中可访问的图也是这 3 张（因为被共用）→ 前端只显示 3 张图

**用户问"坑洞的病害图片"：**
- SQL 过滤后返回 12 条记录
- 这 12 条记录的图片全部 404 → 前端可能显示 0 张图，或者 SQL 过滤有问题时也显示这 3 张

**结论：可访问的现场图永远只有这 3 张，这是数据存储丢失导致的，不是代码 bug。但前端体验很差，需要优化。**

## 二、解决方案（全部改代码，不碰库/存储）

### 方案 1：图片查询结果去重 + 共用标注（P0）

**问题：** 3 张图被 411 条记录共用，前端可能重复显示 411 次，或者去重后只显示 3 张但不告诉用户为什么。

**改法：**

#### 1.1 后端：按图片路径去重

```python
# 图片查询结果按 problem_url 去重，保留第一条记录的元数据
seen = set()
unique_images = []
for img in images:
    if img['path'] not in seen:
        seen.add(img['path'])
        unique_images.append(img)
```

#### 1.2 后端：每张图标注共用信息

```python
# 统计每张图被多少条记录共用、涉及哪些病害类型
for img in unique_images:
    path = img['path']
    shared_records = sum(1 for r in all_records if r['problem_url'] == path)
    shared_types = list(set(
        r.get('pic_type') or r.get('damage_type_name')
        for r in all_records if r['problem_url'] == path
    ))
    img['shared_by'] = shared_records
    img['shared_types'] = shared_types[:5]  # 最多显示5种
```

#### 1.3 前端：图片右下角显示"共用 N 条"角标

在 `ResultPanel.vue` 的图片渲染部分：
- 每张图右下角显示"共用 139 条"
- 鼠标悬停显示 tooltip："被 139 条记录共用，涉及：划痕、块状修补、标牌绿化遮挡..."

**示例 UI：**
```
┌─────────────────┐
│  [图片]         │
│          ┌────┐ │
│          │共用│ │  ← 右下角角标
│          │139条│ │
│          └────┘ │
└─────────────────┘
```

### 方案 2：病害样图 Fallback 机制（P0，最有价值）

**问题：** 5 种病害类型（条状修补、坑洞、减速带损坏、护栏缺损、路面摊晒）的现场图可访问率为 0%，用户问这些类型的图片时什么都看不到。

**关键前提：** 字典表 `ai_problem_base` 里 44 种病害类型全部有样图（`problem_sample_image` 字段），其中 42 个样图在本地缓存里可访问。

**改法：**

#### 2.1 后端：图片查询时，自动关联字典表的样图

修改图片查询逻辑：

```python
# 查询病害记录时，同时查字典表的样图
sql = """
SELECT 
  p.problem_number,
  p.problem_url,
  p.damage_type,
  p.pic_position,
  b.problem_sample_image,  -- 病害样图
  b.problem_type            -- 病害类型名称
FROM ai_problem p
LEFT JOIN ai_problem_base b ON p.damage_type = b.problem_code
WHERE ...
"""
```

#### 2.2 后端：现场图丢失时，自动用样图替代

```python
for img in images:
    if img['status'] == 'missing' and img.get('sample_image_path'):
        # 尝试访问样图
        sample_status, sample_ct, sample_body = db_manager.fetch_seaweedfs(img['sample_image_path'])
        if sample_status == 200 and sample_body:
            img['fallback'] = {
                'type': 'sample_image',
                'path': img['sample_image_path'],
                'label': f"{img['damage_type_name']}标准样图",
                'url': f"/api/image?path={img['sample_image_path']}"
            }
```

#### 2.3 前端：现场图丢失时，显示样图并标注来源

在 `ResultPanel.vue` 里：
- 现场图存在：正常显示
- 现场图丢失但有样图：显示样图，**右上角标注"标准样图（非现场）"**
- 现场图和样图都没有：显示占位图"暂无图片"

**示例 UI：**
```
┌─────────────────┐
│  [样图]         │
│  ┌───────────┐  │
│  │标准样图    │  │  ← 右上角角标，区别于现场图
│  └───────────┘  │
│  坑洞           │
└─────────────────┘
```

#### 2.4 样图缓存预热（防止 7 天 TTL 过期）

当前缓存 TTL 是 7 天，过期后样图也会被删除。需要：
- 启动时批量下载字典表里所有病害样图（84 个），缓存到本地
- 定时任务（每天）重新下载，防止过期
- 对于 404 的样图，缓存 404 标记，避免重复探测

### 方案 3：图片查询结果"现场图 + 样图"混合显示（P1）

**问题：** 对于有部分现场图的病害类型（比如纵向裂缝有 148 条可访问，但只有 3 张不同的图），用户可能想看到更多图片。

**改法：**

#### 3.1 后端：现场图不足时，自动补充样图

```python
# 阈值：现场图可访问数量 < 5 张时，自动补充样图
if len(accessible现场图) < 5:
    # 查询该病害类型的样图
    sample_images = query_sample_images(damage_type)
    # 去重（样图和现场图不重复）
    补充样图到结果里
```

#### 3.2 前端：分组显示

在 `ResultPanel.vue` 里，把图片分成两组：
1. **现场图片**（实际巡检拍摄，可访问的）
2. **标准样图**（字典表样图，现场图不足时补充）

每组前面加小标题，用户可以清楚区分。

**示例 UI：**
```
现场图片（3张，被411条记录共用）
┌────┐ ┌────┐ ┌────┐
│图1 │ │图2 │ │图3 │
└────┘ └────┘ └────┘

标准样图（2张，现场图不足时补充）
┌────┐ ┌────┐
│样图│ │样图│
└────┘ └────┘
```

### 方案 4：查询结果顶部明确告知图片丢失情况（P1）

**问题：** 用户不知道为什么只有 3 张图，以为系统有 bug。

**改法：**

#### 4.1 后端：返回图片统计信息

```python
result = {
    'images': [...],
    'stats': {
        'total_records': 936,           # 该病害类型总记录数
        'total_images': 36,             # 不同图片路径数
        'accessible_images': 3,         # 可访问的现场图数
        'missing_images': 33,           # 丢失的现场图数
        'sample_images': 2,             # 可用的样图数
        'accessible_rate': 8.3,         # 可访问率
    }
}
```

#### 4.2 前端：结果顶部显示统计信息

在图片查询结果顶部显示一个提示条：

```
┌─────────────────────────────────────────────────┐
│ 📊 图片统计：该病害类型共 936 条记录，36 张不同图片  │
│    其中 3 张现场图可显示，33 张现场图已丢失（存储迁移） │
│    已补充 2 张标准样图                              │
└─────────────────────────────────────────────────┘
```

这样用户就知道不是系统 bug，而是数据存储丢失导致的。

### 方案 5：图片查询 SQL 严格性检查（P1）

**问题：** 需要确认用户问不同病害类型的图片时，SQL 是否正确过滤了病害类型。如果 SQL 没过滤（返回全部图片），那不管问什么都是这 3 张图。

**需要 codex 检查：**

1. 问"泛油的病害图片"时，SQL 是否用 `damage_type='10'` 或 `pic_position.$.type='泛油'` 过滤？
2. 问"裂缝的病害图片"时，SQL 是否用 `pic_position.$.type LIKE '%裂缝%'` 过滤？
3. 问"坑洞的病害图片"时，SQL 是否正确过滤？
4. 图片查询的专用模板（`_build_photo_template`）是否支持按病害类型过滤？
5. 如果用户问的病害类型在 `pic_position.$.type` 里没有（比如"泛油"），是否会 fallback 到 `damage_type` 过滤？

**如果 SQL 过滤有问题，需要修复。**

### 方案 6：图片查询支持字典表样图独立查询（P2）

**问题：** 用户可能直接问"坑洞的病害样图"，但当前图片查询逻辑可能只查 `ai_problem.problem_url`，不查 `ai_problem_base.problem_sample_image`。

**改法：**

#### 6.1 后端：增加样图查询模板

在图片查询的专用模板里，增加对 `ai_problem_base.problem_sample_image` 的支持：
- 用户问"XX 的病害样图"或"XX 的标准样图"时，查询字典表的 `problem_sample_image`
- 用户问"XX 的现场图片"或"XX 的病害图片"时，查询 `ai_problem.problem_url`
- 用户只问"XX 的图片"时，先查现场图，现场图不足时补充样图

#### 6.2 意图分类：区分"现场图"和"样图"

在意图分类/语义规划里，增加图片类型的识别：
- "现场图片"、"实拍图"、"巡检图片" → 现场图
- "样图"、"标准样图"、"示例图"、"字典图" → 样图
- 只说"图片" → 默认现场图 + 样图混合

| 优先级 | 方案 | 工作量 | 收益 |
|---|---|---|---|
| **P0** | 方案 1：去重 + 共用标注 | 小 | 前端不重复显示 411 次，用户知道为什么只有 3 张 |

**建议实施顺序：** 方案 5（先确认 SQL 有没有问题）→ 方案 1 → 方案 2 → 方案 4 → 方案 3 → 方案 6

## 五、验收标准

1. **去重**：查询"泛油的病害图片"，前端只显示 3 张不同的图，不重复显示 411 次
2. **共用标注**：每张图右下角显示"共用 139 条"，鼠标悬停显示涉及的病害类型
3. **样图 Fallback**：查询"坑洞的病害图片"，现场图全部丢失时，自动显示坑洞的标准样图，并标注"标准样图（非现场）"
4. **统计信息**：结果顶部显示"该病害类型共 N 条记录，X 张现场图可显示，Y 张已丢失"
5. **SQL 过滤正确**：问不同病害类型的图片，SQL 正确过滤，不返回全部图片
6. **不改库**：所有修改只涉及代码，不修改数据库和 SeaweedFS

## 六、为什么这些方案在只读库权限下可行

| 操作 | 是否需要改库 |
|---|---|
| 图片去重 + 共用标注 | ❌ 纯内存逻辑 |

**所有方案都不涉及：**
- ❌ 修改数据库记录
- ❌ 删除/上传 SeaweedFS 文件
- ❌ 修改表结构
- ❌ 操作存储系统

**只涉及：**
- ✅ 读库（查询 SQL）
- ✅ 改后端代码（Python）
- ✅ 改前端代码（Vue）
- ✅ 本地文件缓存（image_cache）
