# 字段目录可更新配置 + 问题字段触达前置方案（给 codex）

本文两件事：

1. 核验并记录当前"复合问题"的真实流转链路（含哪些地方还靠关键词）。
2. 新增需求落地：把所有白名单表的表名、字段、注释（含枚举 code）落成**可更新配置**，问题进来先做**字段触达**，强命中某张表/某列时确定性地判成查库并锁定落点，避免"隧道表通风方式明细"这种问题被误判成知识问答。

所有行号为 2026-09-22 快照，以函数名为准。

## 一、当前复合问题流转链路（已逐行核验）

入口在 `agent.handle_message`，拆分在 `orchestrator.decompose` / `cross_db.decompose_cross_db`，候选在 `capabilities`。

1. 意图分类 `intent.classify_intent`（intent.py:96）：**LLM 优先**（semantic 模型），把 `wren_engine.search_models` 检索到的 top3 候选表当证据喂给模型（intent.py:113-125）；关键词规则 `fallback_intent` 只在 LLM 失败时兜底。唯一在主路径生效的规则防呆是"把图片当过滤条件"（intent.py:135）。
2. `mixed_request`：除 knowledge/image 外先一律标成"可能多任务"（agent.py:3098）。
3. 确定性总闸（agent.py:3105-3117）：纯数据（`not asks_knowledge`）时先 `build_query_plan` + `build_template_sql`，内置模板能一次答对就把 mixed_request 置 False，不拆。
4. 进 `_handle_composite`（agent.py:1894）：
   - `decompose_cross_db → orchestrator.decompose`：**LLM 规划优先**（`_llm_tasks` 用 planning 提示词，orchestrator.py:206、297-304），LLM 返回 1 条=不拆；LLM 不可用才退回关键词门 `should_decompose`（orchestrator.py:85）+ 规则切句 `_rule_tasks`。
   - 整题确定性闸（agent.py:1912-1932）：`tasks>1`、非 force_ai/prefer_steps、reuse_mode=ask、且 **`not orchestrator.asks_knowledge`** 时，`collect_capabilities(deterministic_only=True)` 收整题候选；有候选就抛 `ChooseCapability` 出整题确认卡，用户确认后直接执行，跳过拆分。
   - 没整题候选 → `collect_steps`（capabilities.py）给每个查库子步骤各收一套候选，抛逐步骤卡（agent.py:1933-1942）。
   - 用户在卡里逐步骤选了口径（step_choices）→ 选中的子步骤直接用 chosen SQL，其余子步骤走 Wren（agent.py:2040-2089）；链式依赖用 produces/needs 回填关键值。
   - 「按步骤逐条查」→ `prefer_steps=True` 只收各步候选，不摆整题口径（agent.py:3160-3171）。
5. 数据+规范混合（H2/H3/H10 那类）靠 `asks_knowledge`（orchestrator.py:78，关键词 `KNOWLEDGE_TERMS`）硬排除整题模板，强制走逐步骤。

### 还在主路径靠关键词的地方（不是 LLM 兜底，是每次生效）

- `orchestrator.asks_knowledge`：`KNOWLEDGE_TERMS`（规范/标准/处置/养护方法/措施/依据/条款…，orchestrator.py:38-52、78-82）决定"数据+规范混合不被模板截胡"。
- 确定性总闸 `build_template_sql`：内置模板本身是规则/关键词驱动（agent.py:3114）。
- 其余关键词（`should_decompose`、`_rule_tasks`、`_task_type`、`fallback_intent` 的 DATA/ KNOWLEDGE_HINTS）**只在 LLM 不可用时兜底**，正常链路不走。

结论：复合"拆不拆、拆几步"已经是 LLM 说了算；关键词只剩两个硬规则（知识词排模板、内置模板总闸）和 LLM 失败兜底。codex 描述的复合链路属实，`_result_words` 把"键→多档取值"列表压成字符串导致方向档逐字符乱码的 bug，修复也属实（agent.py:2662-2673 对 dict 里的 list 值保留 tuple，2699-2702 重建 `_KNOWN_GROUP_DOMAINS`）。

## 二、字段触达要解决的具体问题

用户问"隧道表的通风方式明细"，本质是查 `basic_facilities_tunnels.ventilate_mode` 这一列。连库核验（2026-09-22）：

- 白名单 17 张 MySQL 表（config.py:152）含 `basic_facilities_tunnels`（隧道）、`basic_facilities_bridges`（桥梁）、`basic_facilities_slope`（边坡）等台账表；PG 2 张（gps_points/inclination_points）。
- 隧道表 80 列，`ventilate_mode varchar(100)` 注释就是"通风方式（0局部排风 1局部送风 2全面通风）"，另有 tunnel_clear_width/height（净宽净高）、is_lighting（照明）、is_fire_device（消防）、technical_assessment_grade（技术评定等级）等；**该表当前 0 行（空表）**。
- `wren_engine.search_models`（wren_engine.py:202）对"隧道的通风方式明细/隧道表通风方式/通风方式"**已能把 basic_facilities_tunnels 召回排第一**，单词"通风方式"精确命中 ventilate_mode；MDL 对白名单表 **17/17、2/2 全覆盖**（无缺模型）。
- 意图提示词 prompts/intent.md 第 49-56、63-68 行也写了"字段/属性取值→data""台账表某列（含图片/URL）→data"。

**那为什么还会误判 knowledge？缺口有三个：**

1. 召回只是**软证据**。intent.md:63 明写"只是证据，不是结论"，最终全凭模型；便宜模型遇到"通风方式"这种像工艺/规范的词、或表是空表时，仍可能判 knowledge，没有任何确定性规则把它拉回 data。
2. 命中的**具体字段没有结构化下沉**。search_models 只返回表名/分数/hits 文本，`ventilate_mode` 这个落点列、它的 code_map 没传进 plan 和选表，后续还可能选错列或反问用户要字段。
3. 缺一份**稳定、可更新、各环节统一引用**的字段目录。现有 data/schema_catalog.json 是全量快照、数据库字段字典.md 是给人看的，MDL 是 Wren 产物；没有一份同时带"枚举 code_map、字段角色、词项倒排"且可被意图/选表/模板共同消费的配置。

## 三、目标设计

总原则：**不手写业务关键词、不按问法穷举**。所有触达词项从白名单表的表名/表注释/列名/列注释/枚举中文自动派生，库结构变了重建配置即可（和 codex"封闭枚举来自 schema 就安全"的思路一致）。

### 3.1 可更新字段目录（单一事实源）

扩展 `schema_catalog.py`，在现有 information_schema 抓取基础上新增一份机器配置 `resources/schema/field_catalog.json`（随仓库走、可被覆盖更新），每张白名单表：

```json
{
  "kind": "mysql",
  "table": "basic_facilities_tunnels",
  "table_comment": "基本设施_隧道表",
  "subject": "tunnel",
  "row_count": 0,
  "columns": [
    {"name": "ventilate_mode", "type": "varchar(100)", "nullable": "YES",
     "comment": "通风方式（0局部排风 1局部送风 2全面通风）",
     "role": "enum",
     "code_map": {"0": "局部排风", "1": "局部送风", "2": "全面通风"}},
    {"name": "tunnel_clear_width", "type": "decimal(16,4)", "role": "measure", "comment": "隧道净宽（米）"},
    {"name": "is_lighting", "type": "varchar(100)", "role": "bool_enum",
     "comment": "是否有隧道照明（0否 1是）", "code_map": {"0": "否", "1": "是"}},
    {"name": "picture", "type": "varchar(500)", "role": "image", "comment": "资产图片"}
  ]
}
```

- code_map 复用现成的 `_code_map_from_comment`（schema_catalog.py:209）；字段角色复用 `_FOREIGN_KEYS/_IMAGE_COLUMNS/_GEO_COLUMNS/_TIME_HINTS`（schema_catalog.py:178-206）并补 enum/bool_enum/measure/dimension。
- 更新机制（必须可更新，不允许一次生成后固化）：
  - 后端启动时按 information_schema 算表/列指纹，与 field_catalog.json 不一致就自动重建并记一条日志（表新增/列变更/注释变更）。
  - 管理页"预置查询维护/数据配置"加"重建字段目录"按钮 + 接口（和"重新挖掘模板"同级），手动强制刷新。
  - 沿用 `_CATALOG_TTL_SECONDS` 缓存思路，运行期读目录带 TTL。
  - `check_mdl_drift.py` 增加三方一致性校验：白名单（config）↔ field_catalog ↔ MDL 模型，缺表/缺列/注释漂移报警（实测当前 MDL 全覆盖，作为基线）。

### 3.2 字段触达倒排索引（纯本地、零 LLM）

在 field_catalog 上派生倒排索引 `term → [{table, column, kind, weight}]`，建议放新文件 `services/field_grounding.py`：

- 词项来源（全部自动派生）：表注释、表物理名拆词、列注释、列名拆词、code_map 的中文值。分词直接复用 `wren_engine._terms`（中文 2~3 字滑窗 + 英文/数字词，wren_engine.py:168）与 `_rare_chars`（罕见单字，:185）。
- 权重：字段级罕见词命中列注释最高（"通风方式""净宽""抗震设防等级"）；表级词（隧道/桥梁/边坡）次高；枚举中文值中等；通用列（create_time/remark/memo/del_flag/tenant_id/id）列入停用低权，不单独作为触达证据。
- 输出结构化触达结果（不只是文本 hits）：
  - `matched_tables`: [{table, score, hits}]
  - `matched_columns`: [{table, column, comment, role, code_map, score, hits}]
- 可在 wren_engine 现有 search_models（表级，:202）/suggest_fields（列级反查，:258）基础上统一出一个 `ground(kind, text)`，避免两套打分。

### 3.3 意图前置：字段触达硬兜底（不新增 LLM 调用）

classify_intent 本来就调了 search_models（intent.py:113-120），把它换成/升级为 ground()，加一段**确定性判定**（与现有 image 防呆同级，intent.py:135）：

- 强字段触达（满足任一）：
  1. 命中具体列注释的罕见词（如"通风方式"→tunnels.ventilate_mode）；
  2. 表级强命中（表注释/表名词命中，分数过阈值）且句子含数据诉求（明细/列出/有哪些/多少/几个/是什么/取值/分别）。
- 判定规则：
  - 强触达 且 没有明确规范诉求（`not asks_knowledge`，或规范词与字段词指的是同一列，如"通风方式是什么"是取值不是规范）→ intent 直接定 **data**（要明细/列表/单值）或 **analysis**（同时带统计/分布/对比/占比词）。模型即使返回 knowledge 也以触达为准。
  - 强触达 且同句另有"怎么处置/规范/标准/工艺"等真规范诉求 → **composite**（先查这列，再给规范）。
  - 弱触达（只命中通用列、或分数低于阈值）→ 不覆盖，仍以 LLM 判断为准。
- 空表照常判 data：落点表 row_count=0 不改变意图，查库返回 0 行，回复"该台账当前没有数据"，**不得因为空表或 MDL 查空就转 knowledge**。
- 台账表（隧道/桥梁/边坡/资产）问题在内置模板拼不出 SQL 时，明确走 Wren（MDL 已全覆盖），不许落 knowledge、也不许反问"用哪个字段"。

### 3.4 触达结果下沉到 plan / 选表 / 澄清

- ground() 产出的 table、matched_columns（含 code_map）挂到 query_plan（如 `plan["grounded_tables"] / plan["grounded_columns"]`），供：
  - Wren/物理 SQL 选模型、选列、枚举中文转 code（通风方式"全面通风"→ventilate_mode='2'）；
  - 多表候选消歧（表级分数 + 字段级分数共同决定主表）；
  - clarify 反问：已经能从字段目录确定落点时，不再让用户"告诉我用哪个字段"。

### 3.5 提示词补丁（prompts/intent.md，可直接落盘）

把第 60-68 行 user 段中"只是证据，不是结论"的措辞，替换为下面这段（保留候选注入）：

```
按**表结构语义**检索，这句话最可能落在下面这些表/字段（命中证据见括号）：
<<candidates>>

字段触达规则（优先级高于你的直觉）：
- 证据里命中了**具体字段/列注释**（例如命中"通风方式"→隧道表 ventilate_mode、"净宽/净高"、
  "技术评定等级""养护等级""是否有照明/消防"），说明用户要的是**这张台账表这一列的值**，
  一律判 data（要明细/列表/单值）或 analysis（还要统计/分布/对比），**不许判 knowledge**。
- 哪怕这张表现在是空表、你"觉得"像专业术语，只要答案是"某张表某列的取值/清单"，就是 data；
  空表由查询返回 0 行，不由意图分类改判。
- 只有用户明确问**规定/标准/工艺/怎么处置/分类依据**（"通风方式按规范应该怎么设""泛油怎么处置"）
  才判 knowledge；既问这列的值、又问该怎么处理 → composite。
- 台账/字典表里的图片、样图、URL、图标列 → data（查记录和链接），只有"把照片调出来看"才是 image。
判不准时先问自己：这句话的答案是不是某张表某一列的值？是 → data/analysis。

<<message>>
```

并在 system 段判断边界补两条 few-shot：

```
- "隧道表的通风方式明细""列出所有隧道以及通风方式""隧道净宽净高分别是多少"
  → data（命中隧道表 ventilate_mode / tunnel_clear_width / tunnel_clear_height 列）
- "隧道有照明和消防设施吗，各有多少座" → analysis（命中 is_lighting / is_fire_device，按列分组计数；空表就回 0）
- "通风方式按规范应该怎么选" → knowledge（问的是规定，不是这一列的值）
```

### 3.6 与复合/模板链路衔接

- 字段触达在意图阶段一次完成，单题、复合题、子步骤都复用同一份 ground()，不新增模型调用。
- 复合题里 data 子步骤带上 grounded table/columns；asks_knowledge 与字段触达并存时按 3.3 走 composite。
- 自动模板（L1）以病害表为主，台账表问题不强行套模板；field_catalog 同时作为后续"通用明细模板覆盖全字段"的字段来源（与《通用模板扩充与全字段明细方案》对接，不在本文展开）。

### 3.7 复合题整题未命中模板 → 直接走 Wren，取消默认"逐步骤卡"（改默认分支）

**现状（第一节步骤 4 的默认分支，要改）**：复合题整题闸没确定性候选时，会调 `collect_steps` 给**每一个查库子步骤**各收一套确定性候选、弹"逐步骤卡"让用户逐步挑口径。问题是：一道复合题有几个数据子问题，就要多跑几轮候选收集 + 多一轮人工确认，是当前复合题耗时最长、交互最重的一段；而 Wren 实测已覆盖全部白名单表（17/17、PG 2/2），子步骤模板相对 Wren 的边际收益很小。

**改成下面的默认链路：**

1. 复合题先过整题闸（保持现状）：`tasks>1`、非 force_ai/prefer_steps、reuse_mode=ask、且 `not asks_knowledge` 时，`collect_capabilities(deterministic_only=True)` 收整题候选。
2. **整题闸命中确定性模板/示例 → 只出一次整题确认卡**，用户确认后直接执行（保留，模板用不用仍由人拍板）。
3. **整题闸没命中 → 不再 `collect_steps`、不弹逐步骤卡，直接执行**：
   - 数据子问题一律走 Wren（带上 3.4 的 grounded table/columns 与 code_map）；
   - 知识子问题走 RAGFlow；
   - 后置计算（差值/占比/密度/同环比）照常；
   - 链式依赖的 produces/needs 关键值回填照常，不能因为不弹卡就断链；
   - 最后统一综合成一个回答。
4. **数据+规范混合题（asks_knowledge）维持硬约束**：整题模板不许接，直接走"数据子问题 Wren + 知识子问题 RAGFlow + 综合"，两半答案都不能缺。
5. "逐步骤挑模板"**降级为手动入口，不再默认触发**：在整题确认卡上保留一个次级按钮（或放进设置开关，复用现有 prefer_steps），只有用户主动想逐步抠口径/抠成本时才走旧的 collect_steps 链路。
6. **单题（tasks=1）的确认卡不动**：简单题命中模板仍是主要省钱入口，本改动只针对"复合题整题闸未命中"这一个分支。

一句话：把"是否用确定性模板"的人工确认**集中到整题一次**；整题没把握就别再一步步追问，直接让 Wren 把数据查完。

## 五、验收（连库，空表返回空算正确）
