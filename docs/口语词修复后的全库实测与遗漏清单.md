# 口语词修复后的全库实测与遗漏清单

实测时间 2026-11-05，数据库为当前生产库，全部数字为同一批次快照，统计口径统一 `del_flag = 0`。

## 一、先说结论

裂缝原题仍然没有修好。改后的类型展开逻辑本身能用，但模板生成 SQL 时把病害类型挂在 `damage_type` 上，这个字段存的是损坏程度，不是类型编码。原题实测返回 0 处，按主键口径应为 49 处 105.86 米。

同一个字段错位还污染了按类型分布的全部分支。11 月 2 日实测分布只有两类，未知类型 894 条、泛油 539 条，而真实分布是条状修补 1190 条、横向裂缝 38 条、路肩垃圾 35 条等十余类，泛油只有 3 条。

路线长度存在系统性错误。3899 条路线里 3622 条的 MDL 计算列会算成 0 公里，只有 80 条正常。尚尚线实际 2.772 公里、计算列 0，蒋青线实际 0.970 公里、计算列 0。

长度类问题还会被表计数模板抢走。问蒋青线的路段长度，系统回答路段台账 7057 条；问 S50 长芷高速的路线长度，系统回答 1 条。

## 二、会让答案直接出错的五个问题

### 1. 病害类型过滤挂错字段，是原题仍然失败的根因

位置在 `backend/app/services/nl2sql.py` 第 2854 行到第 2862 行，函数 `_metric_filters`。

生成的条件是：

```
JOIN (SELECT DISTINCT problem_code, problem_type FROM ai_problem_base
      WHERE problem_type IS NOT NULL) b
  ON p.damage_type = b.problem_code
WHERE b.problem_type IN ('横向裂缝', '纵向裂缝', '网状裂缝', '裂缝')
```

`ai_problem.damage_type` 的实际取值只有 0、5、10、空四档，分别有 2882、15626、10643、5738 条，它是损坏程度字段。字典的 `problem_code` 是 02、03、04、10、47 这样的类型编码。两者不是同一套编码，除了 10 号泛油能偶然连上，其余 46 个类型全部连不上。

实测原题生成的 SQL 执行结果为 `count = 0`。同一句话按 `b.id = p.problem_base_id` 的正确口径执行，11 月 2 日裂缝共 50 处，加上长度大于 0.5 米的条件是 49 处，合计 105.86 米。

即使碰上能连上的类型，结果也会被放大。字典里每个 `problem_code` 有 4 到 5 行重复，10 号有 5 行，`damage_type = '10'` 的 10643 条病害 JOIN 之后变成 53215 行，正好五倍。

修法：模板里的类型条件改成 `JOIN ai_problem_base b ON b.id = p.problem_base_id AND b.del_flag = 0`，条件落在 `b.problem_type`。Wren 的关系文件里 `disease_damage_dict` 本来就是 `disease.problem_base_id = damage_dict.id`，模板应当向它对齐，而不是另起一套。

### 2. 尺寸阈值题被降级成计数，长度答案出不来

同一道原题的计划里，指标是 `sum_effective_disease_length`，但命中的模板是 `_build_threshold_count_template`，它固定输出 `SELECT COUNT(*) AS count`。

也就是说，即使第一个问题修好 JOIN，这道题也只能回答 49 处，回答不了 105.86 米。用户问的是长度，系统给的是处数。

修法：阈值模板按计划的 `metrics` 选择聚合方式。计数用 COUNT，长度用 SUM 包住同一段 `CASE WHEN disease_length IS NOT NULL AND disease_length > 0 THEN disease_length ELSE GREATEST(...) END` 表达式，并把别名和单位一并写进结果标签。

### 3. 字典查询不过滤删除标记，废弃类型混进有效集合

位置有两处，`backend/app/services/route_resolver.py` 第 46 行到第 49 行，`backend/app/services/nl2sql.py` 第 3499 行到第 3503 行，两处都只写了 `problem_type IS NOT NULL`。

字典表共 237 行，其中 13 行 `del_flag = 1`，是旧版桥梁病害留下的废弃条目，包括编码 47 的裂缝、编码 54 的边坡、编码 43 到 55 的支座开裂、滑移、腐蚀、蜂窝、麻面等。

编码 47 存在撞号。有效行是交安设施设置不达标，共 4 行，废弃行是裂缝，共 1 行。同一个编码指向两个完全不同的类型。

这个漏洞直接放大了口语展开的副作用。问裂缝，展开结果里带着废弃的裸裂缝，最终类型集合是横向裂缝、纵向裂缝、网状裂缝、裂缝四项，前三项有数据，结果仍然对。问裂缝长度，双向包含只命中废弃的裸裂缝一项，落到库里 0 条，必查空。问边坡，同样会把废弃的裸边坡带进集合。

实测三句计划的 `damage_matches` 都带着这两个废弃条目，说明缓存里已经是污染状态。

修法：两处 SQL 都补 `AND (del_flag = 0 OR del_flag IS NULL)`。`_resolve_damage_type` 的候选集合与 `known_problem_types` 的字典部分同源，改一处要同步改另一处，避免只修一半。

### 4. 路线长度计算列对九成以上路线失效

位置在 `wren_projects/road_mysql/models/route/metadata.yml` 第 4 行到第 7 行的 `route_length_km`。

它的算法是先取所属路段的 `SUM(end_meter_total - start_meter_total)`，取不到再用路线自己的起止桩号相减。问题在于 COALESCE 只认 NULL，不认 0。

7057 条路段里，`start_meter_total` 非零的只有 1175 条，`end_meter_total` 非零的只有 1216 条。按路线汇总后，有路段但汇总值为 0 的路线共 3622 条，没有路段的 197 条，汇总值为正的只有 80 条。

实测三条路线。S50 长芷高速计算列 382.517 公里，桩号真值 382.588 公里，基本正确。尚尚线计算列 0，桩号真值 2.772 公里。蒋青线计算列 0，桩号真值 0.970 公里。

路线表的 `distance` 也兜不住底，3899 条里 3895 条为 NULL，只有 2 条有值。

MDL 的描述明确要求算长度、密度、每公里一律用 `route_length_km`，不要用 `distance`。按这个要求执行，3622 条路线的长度、病害密度、每公里指标全部会变成 0 或者除零。

修法：把第一段改成 `NULLIF(SUM(...), 0)`，或者写成 `CASE WHEN SUM(...) > 0 THEN SUM(...) ELSE 桩号差 END`。同一份文件里 `distance` 的描述也要跟着改，说明只有 2 条有值。

### 5. 长度类问题被表计数模板劫持

`_build_table_count_template` 只要判定形状是计数、主体落在某张表，就直接输出该表的 `COUNT(*)`，不看路线、路段这些实体槽位。

实测问蒋青线的路段长度，计划里 `section_match` 已经正确落到蒋青线那一条，模板仍然输出 `SELECT '路段台账' AS type, COUNT(*) FROM basic_facilities_sections WHERE del_flag = 0`，回答 7057。问 S50 长芷高速的路线长度，回答 1。两个答案都不是用户问的东西。

伤害面不止长度。任何带具体实体、但形状被判成计数的表级问题，都可能被这个模板答成整表条数。

修法：表计数模板加前置判断，句子里出现长度、里程、多长、几公里、多少公里这类词，且主体是路线或路段时直接返回空，交给长度模板或 Wren。或者在存在 `route_match`、`section_match` 时不允许走整表计数。

## 三、会答偏或误导的十一个问题

### 6. 语义模型会编造库里不存在的类型名

问边坡的病害数量，语义模型输出的条件是十个类型，边坡溜塌、边坡坍塌、边坡滑坡、边坡裂缝、边坡渗水、边坡冲刷、边坡风化、边坡落石、边坡沉降、边坡变形。

库里与边坡相关的只有边坡落石 11 条和一条废弃的裸边坡。前九个类型一条数据都没有。类型展开只做包含关系过滤，不会识别库里没有这些名字，也不会回落到如实回答无此类型。

修法：语义层输出的类型名必须过一遍字典值域核对，命中为零的单独收集，回答时明确说明库里没有这些类型，而不是静默返回 0。

### 7. 设备短号没有解析器

问 7072 这台设备 11 月巡检了多少处病害，语义层给的条件是 `device_code = '7072'`。

库里设备编码是 1420324267072，直接等于 7072 查不到任何记录。设备台账实际有七条有效记录，名称分别是无人车巡检、APP 设备、567test、平整度测试设备、QY5671、5195、7072，其中 7072、5195 这类名称本身就是编码尾号。

现有实体解析只覆盖路线、路段、桥梁、隧道、边坡，没有设备。三张资产台账都是 0 行，设备台账有 7 行却没有对应解析器。

修法：新增设备解析，按 `device_name` 与 `device_code` 双向匹配，短号按后缀匹配，命中唯一才落 `device_code`。七条数据量很小，可以全量进缓存。

### 8. 空表静默返回 0，用户无法区分没有数据和没有这张表

实测工单数量返回 AI 巡检工单 0 条。工单表确实 0 行，但用户拿到 0 会理解为业务上没有工单，而不是系统里没有工单台账。

同类空表还有巡检员、车辆、桥梁、隧道、边坡、涵洞、渠道、服务区、标志、其他设施、资产文档、资产主表，以及 `maintenance_*`、`road_officer_*`、`road_administration_*`、`uav_*`、`sm_*`、`su_*` 全系列。有数据的只有 `maintenance_road_damage_condition` 13 行与 `basic_construction_maintenance_information` 16 行。

修法：表计数结果为零时，附带一句该台账当前没有入库数据，并说明是数据未接入而不是业务为零。这句要由代码根据表行数生成，不能交给模型自由发挥。

### 9. 任务编号在任务表里大量重复

`ai_maintain_patrol_task` 299 行，同一个 `task_number` 最多出现 13 次，`XJJL202606180008` 13 次，`XJJL202606250001` 12 次。原因是任务表按路段或子任务拆了多行。

`ai_maintain_patrol` 209 行，编号与任务一一对应。按任务编号统计病害、里程、完成情况时，用任务表会把结果放大数倍。

修法：所有按任务编号聚合的模板统一以 `ai_maintain_patrol` 为主表，任务表只用于设备、路段、桩号计算状态这类明细字段。这条要写进字段目录的表述里。

### 10. 两个时间字段差一倍，月度口径必须钉死

11 月 2 日按 `create_time` 过滤是 761 条，按 `collection_time` 过滤是 1433 条，差 672 条。原因是次日导入的数据 `collection_time` 仍记采集当天，`create_time` 记入库时刻。

病害的时间语义应当用采集时间。但现有月度、趋势类模板里两种写法都出现过，同一句话换个月份可能得到不同数。

修法：字段目录里把 `collection_time` 标为唯一时间口径，`create_time` 标为入库时间只用于审计。所有模板统一改 `collection_time`，并在口径卡片上写明。

### 11. 字典别名机制形同虚设

`ai_problem_base` 有效行 224 行，`problem_alias` 等于 `problem_type` 的有 224 行，不同的 0 行。

也就是说别名这一列填的就是本名，`_resolve_damage_type` 里按别名做匹配的分支等于重复匹配，没有带来任何口语映射能力。

修法：要么补真实别名，裂缝类补上裂、龟裂、网裂，坑槽类补上坑洞、槽，要么在代码里明确别名分支不参与打分，避免误以为已有别名能力。

### 12. 路段解析不唯一时仍然硬取第一条

`backend/app/services/section_resolver.py` 的 `resolve` 在匹配到多条时，仍然执行 `matches[0]` 取第一条，`unique` 字段只放在返回值里，没有阻断赋值。

实测尚尚线匹配到 10 个候选，函数照样给出第一条的 id。这与转述的同名多版本返回候选、不硬选不一致。

修法：`unique` 为假时返回候选列表并把 `id` 置空，由上层弹选择或反问。

### 13. 路段同名多版本极多，按名字查询天然歧义

同名路段最多的是邱沙线 25 条，杨万线 21 条，安均线 19 条，三三线、天封线、淮谢线各 18 条。这些是不同年份或不同版本的同一路段。

任何按路段名称统计的题目都会面临多版本选择，选错版本长度和病害都会不同。

修法：解析层按 `section_version` 取最新版本作为默认，同时在口径卡片上写明选了哪个版本。或者要求用户补充版本，不默认。

### 14. 方向字段只有病害表能用

病害表 `up_or_down` 分布是上行 21413 条、下行 13434 条、空 42 条，可用。

任务表 `up_or_down` 206 条全是 0，路段表 7057 条全是 NULL。这两张表的方向字段没有实际数据。

按路段或任务区分上下行的问题，只能通过病害表的方向字段回答，任务与路段侧无法提供分母。

修法：方向类问题的字段目录只指向 `ai_problem.up_or_down`，不要把任务表和路段表的同名字段作为候选，避免模型误选后得到 0 或把 0 当成上行。

### 15. 桩号米数跨路线累计，过滤必须带路线

`ai_problem.pile_distance` 最小值 2，最大值 2204012，均值 522931。这个值是全线累计桩号，不是单条路线内归一的米数。

只按桩号区间过滤而不限定路线，会把其他路线同桩号区间的病害一起算进来。

修法：桩号区间条件一律与路线或路段条件成对出现，模板里做成强绑定，缺一项就不生成桩号条件。

### 16. 路段轨迹里程字段注释是乱码

`basic_facilities_sections.track_mileage` 的库注释是 `杞ㄨ抗閲岀▼`，GBK 与 UTF-8 错位。字段目录里的中文标签会带这串乱码，模型看到后可能误判字段含义。

修法：修库注释，或者在字段目录里覆盖成正确中文，说明它是轨迹实测里程。

## 四、已经验证正常的部分

Wren 关系文件里病害到字典的关系是正确的，`disease.problem_base_id = damage_dict.id`，多对一，用主键连接不会放大。

病害表的关键外键都完整，34889 条里 `routes_id`、`sections_id`、`patrol_id` 空值为 0，`problem_base_id` 空值也为 0，`pic_position` 空值为 0。

病害类型的两条来源当前完全一致。按字典外键统计与按图片 JSON 的 `$.type` 统计，全库前十二类逐项相同，11 月 2 日纵向裂缝都是 12 条。暂时不存在两套口径打架。

裂缝按三个子类展开的结果正确，11 月 2 日 49 处 105.86 米，不加长度条件 50 处 106.36 米。

路段解析对唯一名称有效，蒋青线正确落到 `002bf265`，群十线也唯一。

## 五、建议的修复顺序

第一步改类型过滤的主键连接，这是原题和分布题共同的前提。

第二步补字典的删除标记过滤，清掉废弃类型污染。

第三步让阈值模板按指标输出求和，长度题才能给出长度。

第四步修路线长度计算列的零值回退。

第五步阻止表计数模板接管长度类问题。

以上五步完成后再处理设备解析、空表提示、任务编号口径、别名补录。前五步都属于改一处、影响一片的底层修正，越早改越省事。

## 六、需要定口径的两个点

病害类型的唯一口径，是以字典外键 `problem_base_id` 为准，还是以图片 JSON 标注为准。当前两者一致，但这是数据现状，不是机制保证。建议以字典外键为准，JSON 标注只作图片检索用。

路线长度的唯一口径，是以路线自身起止桩号相减为准，还是以所属路段汇总为准。路段存在大量同名多版本，按路段汇总会把同一条路重复累加，尚尚线 12 个路段版本累加出 6.02 公里，实际 2.772 公里。建议以路线起止桩号为准，路段汇总只在单版本路段上使用。
