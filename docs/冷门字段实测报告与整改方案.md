测试时间：2026-09-20。方式：连真实 MySQL（new_four_road_base_ai，经 SSH 隧道），为每个有数据的冷门字段出一道最简单的问题，走完整 agent.handle_message 链路（模板→Wren→物理 LLM→校验），再用直接查库的真实结果核对。脚本：backend/test_cold_fields.py、test_cold_fields_retry.py；错题 SQL：docs/冷门字段错题SQL.json。

## 二、问题分类与修复

### P0-1 病害大类 category_name 映射错误（沿路设施、交安事件永远查成 0）

现象：问"沿路设施类病害多少条"答 0（实际 505），"交安事件类多少条"答 0（实际 168）。

根因：disease 模型的 ref_sql（wren_projects/road_mysql/overrides.yml 第 26-31 行，构建后落到 models/disease/metadata.yml）里，category_name 是这样算的：

```
(SELECT CASE b.disease_categories_type WHEN '0' THEN '路面病害' ... WHEN '10' THEN '沿路设施' WHEN '15' THEN '交安事件' ...
 FROM ai_problem_base b WHERE b.problem_code = ai_problem.damage_type LIMIT 1) AS category_name
```

它用 damage_type 去关联字典 problem_code，但 damage_type 只有 10（936 条，泛油，大类路面）和 5（16 条）两个值，另外 750 条为 NULL 关联不上。于是 505 条沿路设施、168 条交安事件的 category_name 全部是 NULL，WHERE category_name='沿路设施' 必然是 0。实测这套关联算出来的大类分布只有"路面 936、NULL 766"，而真实分布是路面 1029、沿路设施 505、交安事件 168。

而 ai_problem 表本身就有 categories_type 字段，直接翻译它即可，不需要关联字典。

修复（改 overrides.yml 的 disease ref_sql，problem_type_name 保留不动，它用 damage_type 关联 problem_code 翻译具体类型是对的，泛油 936 已验证）：

```
CASE ai_problem.categories_type
  WHEN '0' THEN '路面病害' WHEN '5' THEN '路基病害'
  WHEN '10' THEN '沿路设施' WHEN '15' THEN '交安事件'
  ELSE ai_problem.categories_type END AS category_name
```

改完重新跑 backend/sync_wren_mdl.py 重建 MDL。同时把 categories_type 列的说明改成"病害大类编码：0 路面病害、5 路基病害、10 沿路设施、15 交安事件"，让模型优先用 category_name / categories_type，而不是自己去关联字典。

### P0-2 damage_type 与 history_damage_interval 字段语义混淆

现象：问"损坏程度编码为 10 的病害多少条"，系统去查了 history_damage_interval（历史损坏程度区间，全空），答 0；实际 damage_type='10' 有 936 条。

根因：damage_type 列注释写的是"损坏程度"，但实测存的是病害类型编码（problem_code，10=泛油）；真正带"损坏程度"字样的 history_damage_interval 反而全空。模型看到"损坏程度"就选了后者。

修复：在 overrides.yml / 字段说明里如实标注——damage_type 是"病害类型编码，关联 ai_problem_base.problem_code，10=泛油等"；history_damage_interval 是"历史损坏程度区间，当前库无数据"。不要让"损坏程度"这个词把模型引到空字段。

### P1-1 有效任务等条件字段没有翻译成过滤条件

现象：问"标记为有效的巡查任务多少次"，SQL 只 COUNT 了全部任务答 147，没加 valid_task 过滤；实际 valid_task='1' 是 30 条。patrol 模型 MDL 里其实有 valid_task 字段，是 SQL 生成时没选它。

修复：sql_mdl.md / 语义提示词补一条业务规则——巡查任务里"有效/无效"对应 valid_task（1 有效），"巡查方式"对应 patrol_method_type、"巡查里程"对应 patrol_mileage、"超时"对应 over_time；问"有效的 XX"必须带 valid_task 过滤。同类的 code 字段（patrol_method_type 6/5、surface_type 11/12、tech_grade 等）要给 code→中文映射，实测 F23 只回了"方式 6 有 143 次、方式 5 有 4 次"，没说方式名。

### P1-2 技术等级/路面类型/路面宽度在 section 模型，模型去 route 上找导致报错

现象：问"西乡段技术等级、路面类型、路面宽度"，Wren 报 "No field named route.tech_grade"，因为这些列在 section 模型，route 模型没有，模型不知道要 join section。实测西乡段 section：tech_grade=1、surface_type=11、surface_width=10.00。

修复：sql_mdl.md 明确字段归属——路线级属性（车道数 lane_count、限速、起终点地名/经纬度、通车日期、行政等级）在 route；路段级属性（技术等级 tech_grade、路面类型 surface_type、路面宽度 surface_width、路基宽度、涵洞数 culvert_count、管养单位）在 section，查一条路线的这些属性要 JOIN section ON section.route_id=route.id（当前深圳两条路各只有 1 个 section）。并在 MDL 的 route、section 模型描述里互相点明。

### P1-3 一条 SQL 里混"去重总数"和"Top1 分组"，总数恒为 1

现象：问"西乡段病害分布在多少个不同路格、最多的是哪个"，SQL 写成：

```
SELECT COUNT(DISTINCT d.luge_name) AS 不同路格数, d.luge_name AS 路格, COUNT(*) AS 病害数量
... GROUP BY d.luge_name ORDER BY COUNT(*) DESC LIMIT 1
```

GROUP BY 路格后每组内 COUNT(DISTINCT 路格) 恒等于 1，又 LIMIT 1，于是"不同路格数"答 1，实际是 9；Top1（k0+800-k0+899，136 处）倒是对的。

修复：这类"既要去重总数、又要排名第一"的问题，拆成两条 SQL（一条 COUNT(DISTINCT) 不带分组，一条 GROUP BY 排序取 Top），或总数用子查询/窗口函数。校验器加一条形状检查：SELECT 里的 COUNT(DISTINCT x) 与 GROUP BY x 是同一列时，该计数在每组内恒为 1，不可能是用户要的"不同 X 总数"，判错重写。

### P1-4 结果总结把多列/多行属性念错（SQL 和表格是对的）

两个实测案例：

- 最大宽度 100、最大高度 50，SQL 正确返回一行两列，回复却念成"共 100.00 处（各口径：最大高度=50）"，把第一列极值当成了"处数"。
- 两条路车道数（恒明珠 2、西乡 6），SQL 正确返回两行，回复只说"共 2 条明细记录"，没念 6 和 2。

修复：结果总结不能对所有结果套"共 X 处"。要按列语义和行结构念：单行多列且是极值/属性（最大/最小/宽度/高度/车道数/里程/日期/经纬度）时，逐列念"指标=值（单位）"，不出现"处"；多行属性（每个对象一行）时，逐行念"对象：属性1=值、属性2=值"。只有 COUNT 计数结果才用"共 X 处"。这是结果总结提示词的通用语义规则，不是针对宽高或车道数写死。

### P1-5 能直接查的台账问题被误判成"要澄清"

- 问"病害点位经纬度范围（最小/最大经纬度分别是多少）"，被"分别是多少"触发分组口径追问，没有查（即《语义兜底机制与误判整改方案》里的"分别"问题，这次再次复现）。
- 问"台账上的起点和终点地名叫什么""起点经纬度和终点经纬度"，被"起点/终点"误判成"前/后 N 米两种桩号口径"澄清。实际上 start_name/end_name、start_lnt/end_lnt 是路线台账的起终点字段，和桩号前后 N 米无关。

修复："分别"后接的是多个指标（最小经度、最大经度…）时不追问、不分组，一条 SQL 多个聚合列；"起点/终点"后接"地名/经纬度/坐标"时走 route 的 start_name/end_name/start_lnt/start_lat/end_lnt/end_lat，只有"起点往前/终点往后 N 米"这类才是桩号距离口径。

### P2-1 数据库字段查询被误路由到知识库

现象：问"西乡段什么时候通车"（routes.open_date）、"泛油的别名和病害描述"（ai_problem_base.problem_alias/problem_description），都走到知识库回"资料中没有相关内容"。

修复：数据源判断要识别"某对象的某属性是什么/什么时候/别名/描述/公式/单位"这类是数据库查询（属性取值），只有问规范、标准、养护办法、判定依据时才走知识库。damage_dict 模型已有 problem_alias、problem_description、formula、length_unit、confidence 字段，直接可查。

### P2-2 字段登记表只覆盖 ai_problem 一张表

nl2sql._field_rows 从 catalog 自动登记字段时写死了只取 ai_problem（if table != "ai_problem": continue），routes/sections/patrol/字典表的冷门字段在物理 LLM 兜底路径里没有登记，全靠少量手写 _SPECIAL_FIELDS。Wren 路径靠 MDL 不受影响，但一旦降级到物理 LLM 路径，这些表的冷门字段就容易丢。

修复：字段登记表对全部白名单表自动生成（表名前缀区分，如 r.lane_count、s.tech_grade、p.valid_task），手写特殊字段只保留 MDL 预抽的语义字段（confidence、route_name、problem_type_name、category_name 这类物理表不存在的）。

## 三、空表、空字段以后怎么自动支持（不需要以后再补代码）

当前一半表是空的，但不能因为空就不支持。原则：

1. MDL 和字段登记按全部白名单表的 schema 自动生成（sync_wren_mdl.py 已经是自动从库结构生成，ref_sql 只做少量人工覆盖）。表是空的不影响模型定义，等数据写入后自然可查，不需要改代码。
2. 字段有没有数据、code 取哪些值，应该在构建 MDL / 数据字典时自动采样写进字段说明（例如 valid_task: 1 有效/0 无效；patrol_method_type: 6/5），而不是靠人工记。空字段如实标注"当前无数据"，模型查到 0 就如实答 0 并说明该字段未录入（F01 收藏字段现在就是这样，表现正确）。
3. code→中文的枚举翻译集中维护（categories_type、problem_source、problem_status、patrol_method_type、surface_type、tech_grade、up_or_down 等），最好直接从字段注释和字典表自动生成，避免模型拿 code 当中文或猜含义。
4. 新增表后只要跑一次 MDL 同步 + 数据字典构建就能被检索到，不需要为每张表写专门的模板或函数。

## 五、修复优先级

先改 P0-1（category_name 重建 MDL，影响所有大类统计）和 P0-2（两个程度字段说明），这两个一改，沿路设施/交安事件/路基相关的一大批问题立即恢复。再做 P1（valid_task 等条件翻译、section 字段归属、SQL 形状校验、结果总结念法、误判澄清），最后做 P2（数据源路由、字段登记表全表覆盖、枚举自动采样）。P1-4 结果总结和 P1-5 误判追问与《语义兜底机制与误判整改方案》是同一批改动，可一并处理。
