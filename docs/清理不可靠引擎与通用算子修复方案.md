# 清理不可靠引擎与通用算子修复方案

> 背景：项目里有多个自动执行的引擎（multi_field_join、multi_field_parallel）会错误选择表/字段，且跳过用户确认直接执行，导致查询结果错误。通用算子（generic）保留，但存在月份错误、生成重复列、效果差等问题，需要修复。同时，"拱起是怎么计算的"这类表格与知识混合问题（查询 ai_problem_base.formula 字段）没有得到很好的支持。
> 核心思路：删除 multi_field_join / multi_field_parallel 不可靠引擎；保留通用算子但修复其 Bug；所有业务查询要么走模板（用户确认后执行），要么走 Wren 语义层；新增表格与知识混合问题的处理逻辑。
> 生成时间：2026-10-12

---

### 1.2 需要删除的引擎

#### 引擎 1：multi_field_join

**问题：**
- 错误选择 JOIN 表（如把里程桩点表选成边坡表）
- 字段解析靠字段名匹配，"长度"在多张表里都有，没有语义理解能力
- 跳过用户确认直接执行

**案例：** "路段名称以及对应的桩号以及对应的路段长度" → JOIN 了边坡表而不是里程桩点表，结果完全错误。

生成的 SQL：
```sql
SELECT s.full_name AS '路段全称', s.start_num AS '起点桩号', s.end_num AS '终点桩号', 
       s.section_num AS '路段序号', ..., j1.length AS '长度' 
FROM basic_facilities_sections s 
LEFT JOIN basic_facilities_slope j1 ON j1.sections_id = s.id AND j1.del_flag = 0 
WHERE s.del_flag = 0 LIMIT 500
```

**根因：**
- `multi_field.py` 的字段解析逻辑靠字段名匹配，"长度"这个词在多张表里都有（边坡长度、桥梁长度、路段长度等）
- 它没有足够的语义理解能力来判断用户到底要哪张表的"长度"
- 选错表后直接执行，没有用户确认环节

#### 引擎 2：multi_field_parallel

**问题：**
- 与 multi_field_join 共用同一套字段解析逻辑（`multi_field.py`）
- 同样存在选错表、选错字段的问题
- 跳过用户确认直接执行

## 二、通用算子修复方案（保留但修复）

### 2.1 通用算子的定位

通用算子作为**兜底引擎**保留：
- 当没有任何模板匹配、且 Wren 语义层也失败时，通用算子可以作为最后一道防线
- 通用算子基于字段目录（schema_catalog）确定性拼接 SQL，不依赖 LLM，速度快
- 但通用算子的根本问题是靠字段名匹配，没有语义理解能力，所以需要修复已知 Bug

### 2.2 Bug 1：月份错误

**现象：**
- "2026年6月全库有多少处病害？" → 返回 1702 处
- "2026年7月全库有多少处病害？" → 也返回 1702 处
- 明显是时间条件没有正确生效

**根因分析：**
- 通用算子的 `_filter_sql` 函数处理时间条件时，可能没有正确解析时间范围
- 或者是调用方传入的 filters 里时间值不正确
- 需要检查 `generic_count` / `generic_detail` 接收的 filters 参数

**修复方案：**

1. **在 `_filter_sql` 中增加时间条件的专门处理**：
   - 识别时间类型的列（通过字段目录的 `roles` 或 `type`）
   - 确保 `between` 操作符的两个值都是合法的时间格式
   - 时间值统一格式化为 `YYYY-MM-DD HH:MM:SS`

2. **增加时间条件的单元测试**：
   - 测试"2026年6月" → 生成 `collection_time >= '2026-06-01 00:00:00' AND collection_time < '2026-07-01 00:00:00'`
   - 测试"2026年7月" → 生成 `collection_time >= '2026-07-01 00:00:00' AND collection_time < '2026-08-01 00:00:00'`
   - 验证两个查询返回的结果不同

3. **在调用方增加日志**：
   - 记录通用算子接收到的 filters 参数
   - 记录生成的 SQL
   - 方便排查时间条件是否正确传递

### 2.3 Bug 2：生成重复列

**现象：**
- "分别列出路段桩号和相关的修改人" → 生成了 6 个重复的 `m.update_by AS '修改人'`

生成的 SQL：
```sql
SELECT m.update_by AS '修改人', m.update_by AS '修改人', m.update_by AS '修改人', 
       m.update_by AS '修改人', m.update_by AS '修改人', m.update_by AS '修改人' 
FROM basic_facilities_sections_pile_detail m  
WHERE m.del_flag = 0 LIMIT 500
```

**根因分析：**
- `generic_detail` 函数的列解析逻辑有问题
- 当用户点名的字段在字段目录里解析不到时，可能会重复添加同一列
- 或者是 `_select_expr` 函数的别名生成有问题，导致同一列被多次添加

**修复方案：**

1. **在 `generic_detail` 中增加列去重逻辑**：
   - 按列名去重，同一列只添加一次
   - 如果用户点名的字段解析不到，返回错误而不是重复添加
   - 代码示例：
     ```python
     seen_columns = set()
     for name in columns or []:
         column = catalog.resolve_column(kind, table, name)
         if not column:
             return None, f"字段「{name}」在 {table} 里找不到"
         col_name = str(column.get("name"))
         if col_name in seen_columns:
             continue  # 去重，同一列只添加一次
         seen_columns.add(col_name)
         resolved.append(column)
     ```

2. **修复默认列的选择逻辑**：
   - 当用户没有点名具体字段时，默认列也需要去重
   - 确保不会因为 JOIN 导致同一列被多次添加

3. **增加重复列的单元测试**：
   - 测试"分别列出路段桩号和相关的修改人" → 生成的 SQL 中每列只出现一次
   - 测试多列查询 → 验证列数正确

### 2.4 Bug 3：效果差，经常答错

**现象：**
- 用户反馈"通用算子效果太差了，全部都是错的"
- 通用算子经常选错表、选错字段

**根因分析：**
- 通用算子靠字段名匹配，没有语义理解能力
- 当多张表有同名字段时，容易选错表
- 当字段名和用户问法不完全匹配时，容易解析不到

**修复方案：**

1. **增加字段匹配的语义辅助**：
   - 在字段匹配时，不仅看列名，还看列注释（label/comment）
   - 利用字段目录的 `roles` 信息（如 `geo`、`code`、`fk`）辅助判断
   - 当有歧义时，返回错误交 Wren，而不是硬选一个

2. **增加弃权机制**：
   - 当字段解析有歧义时，通用算子应该弃权，交回 Wren 语义层
   - 而不是硬选一个可能错误的表/字段
   - 代码示例：
     ```python
     # 当字段在多张表里都有匹配时，弃权交 Wren
     candidate_tables = find_candidate_tables(kind, column_name)
     if len(candidate_tables) > 1:
         return None, f"字段「{column_name}」在多张表中都有，交 Wren 处理"
     ```

3. **增加通用算子的置信度评估**：
   - 在生成 SQL 后，评估查询的置信度
   - 置信度低时，弹卡让用户确认，而不是直接执行
   - 置信度高时，可以直接执行（但仍然需要用户确认）

### 2.5 Bug 4：优先级问题

**用户反馈：**
- "通用算子模版推荐太烦人了，一直优先级比较靠前"
- 用户说"它的优先级好像不参与排名，我记得改过"

**修复方案：**

1. **确认通用算子的推荐排序逻辑**：
   - 检查推荐卡的排序代码，确认通用算子是否参与排名
   - 如果通用算子不参与排名，确保它排在最后（作为兜底）
   - 如果通用算子参与排名，降低它的权重

2. **通用算子作为兜底**：
   - 通用算子应该只在"没有任何模板匹配、且 Wren 也失败"时才出现
   - 在推荐卡中，通用算子应该排在最后
   - 卡片上明确标注"兜底口径"，让用户知道这是最后一道防线

### 2.6 通用算子修复的验收标准

1. ✅ "2026年6月全库有多少处病害？" 和 "2026年7月全库有多少处病害？" → 返回不同的结果
2. ✅ "分别列出路段桩号和相关的修改人" → 生成的 SQL 中每列只出现一次，没有重复列
3. ✅ 通用算子在推荐卡中排在最后（作为兜底）
4. ✅ 当字段解析有歧义时，通用算子弃权交 Wren，而不是硬选
5. ✅ 通用算子生成的 SQL 经过用户确认后才执行（不再直接执行）

## 三、删除不可靠引擎方案

### 3.1 核心思路

**删除 multi_field_join / multi_field_parallel，所有业务查询只走三条路径：**

1. **模板路径**：匹配到模板 → 弹卡用户确认 → 执行
2. **Wren 路径**：没有匹配到模板 → Wren 语义层生成 SQL → 执行
3. **通用算子兜底**：模板和 Wren 都失败 → 通用算子生成 SQL → 弹卡用户确认 → 执行

## 四、表格与知识混合查询方案

### 4.1 问题分类

#### 类型 A：查询字典表的知识字段

**例子：**
- "拱起是怎么计算的？" → 查询 `ai_problem_base.formula`
- "泛油的单位是什么？" → 查询 `ai_problem_base.length_unit`
- "边坡落石属于哪一类病害？" → 查询 `ai_problem_base.disease_categories_type`
- "横向裂缝的病害代码是什么？" → 查询 `ai_problem_base.problem_code`

**特点：**
- 查询对象是字典表（`*_base`）
- 返回的是知识/描述性信息，不是业务数据统计
- 需要解释字段含义（特别是 formula 这种 JSON 格式）

#### 类型 B：查询业务数据 + 字典知识

**例子：**
- "西乡段泛油病害的计算公式是什么？" → 先查西乡段有多少泛油病害，再查泛油的计算公式
- "每种病害类型的计算公式分别是什么？" → 按病害类型分组，查每种的计算公式

### 4.2 解决方案

#### 方案 A：新增字典知识查询意图分类

**文件：** `prompts/intent.md`

**改动：**
- 新增 `dict_knowledge` 意图类别
- 边界例子：
  - "XX是怎么计算的" → dict_knowledge
  - "XX的单位是什么" → dict_knowledge
  - "XX属于哪一类" → dict_knowledge
  - "XX的病害代码是什么" → dict_knowledge
  - "XX有多少处" → data（业务查询）

#### 方案 B：新增字典知识查询执行器

**文件：** `backend/app/services/dict_knowledge.py`（新建）

**功能：**
1. 识别用户问的是哪个字典表、哪个字段、哪条记录
2. 执行查询，返回原始数据
3. 特殊字段解析：
   - `formula`：解析 JSON 数组，转换成人类可读的公式描述
   - `code_map` 字段：把编码翻译成中文
   - `problem_sample_image`：返回图片 URL
4. 生成自然语言解释

**formula 解析逻辑：**
```python
def parse_formula(formula_json: str) -> str:
    """把 formula 的 JSON 数组转换成人类可读的公式描述。
    
    输入：[{"label":"长","value":1},{"label":"*","value":6},{"label":"宽","value":2}]
    输出："计算公式：长 × 6 × 宽（其中 6 是系数）"
    """
    items = json.loads(formula_json)
    parts = []
    for item in items:
        label = item.get("label", "")
        value = item.get("value", "")
        if label in ("*", "×", "x"):
            parts.append("×")
        elif label == "+":
            parts.append("+")
        elif label == "-":
            parts.append("-")
        elif label == "/":
            parts.append("÷")
        elif label == "输入框":
            num = item.get("num", "")
            parts.append(f"[输入值，默认 {num}]")
        else:
            parts.append(label)
    return " ".join(parts)
```

#### 方案 C：在 agent.py 中接入字典知识查询

## 五、确保所有查询都经过用户确认

### 5.1 可以不弹卡的查询类型

1. 元数据查询（`metadata`）：查询库/表/字段结构，不涉及业务数据
2. 字典知识查询（`dict_knowledge`）：查询字典表的知识字段，不涉及业务数据统计

### 5.2 必须弹卡的查询类型

1. 所有业务数据查询（统计、明细、分组等）
2. 通用算子生成的查询（作为兜底，更需要用户确认）
3. Wren 生成的查询（除非匹配到高置信度模板）

### 5.3 弹卡内容标准化

所有弹卡必须包含以下信息：
1. **查询口径**：用户问的是什么，系统理解的是什么
2. **涉及的表**：查询会用到哪些表
3. **过滤条件**：有哪些 WHERE 条件，特别是用户没提到的默认条件
4. **SQL 预览**：可以展开查看完整 SQL
5. **确认按钮**：用户点确认后才执行
6. **"让 AI 重新查"按钮**：用户觉得不对，可以让 AI 用 Wren 重新生成

## 八、风险与应对

| 风险 | 应对 |
|---|---|
| 删除 multi_field_join 后，某些跨表多字段题 Wren 处理不好 | 优化 MDL 里的表关系定义；Wren 是基于语义模型的，只要 MDL 正确就能处理 |
| 通用算子修复后仍然有答错的情况 | 通用算子作为兜底，答错了用户可以点"让 AI 重新查"走 Wren；持续收集 bad case 优化 |
| 所有查询都弹卡会降低效率 | 高置信度模板匹配可以直接弹卡（减少一次 LLM 调用）；用户确认后下次相似问题可以更快 |
| 字典知识查询意图分类不准确 | 收集 bad case，持续优化意图分类提示词；可以先用关键词规则兜底 |
| formula 字段格式多样，解析不完整 | 先支持常见格式，遇到不支持的格式返回原始 JSON + 提示"格式待解析" |
