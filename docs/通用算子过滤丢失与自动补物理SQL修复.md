# 通用算子 count/分组丢弃用户过滤条件 + 自动补物理 SQL（给 codex）

## 一、通用算子把时间条件丢了，两个月都答成全表（实测，连库已核对）

用户问：
- 「2026 年 6 月全库有多少处病害？」→ 系统答 **1702**；
- 「2026 年 7 月全库有多少处病害？」→ 系统也答 **1702**。

系统自报的统计口径写的是对的（分别标了"时间 2026-06-01~07-01"和"2026-07-01~08-01"），但数字都是全表总数。连库实测（mysql `new_four_road_base_ai`，ai_problem del_flag=0）：

| 口径 | 真实行数 |
|---|---|
| 全库 del_flag=0 | 1702 |
| 2026-06（collection_time 6/1~7/1） | **323** |
| 2026-07（collection_time 7/1~8/1） | **1379** |
| 数据时间范围 | 2026-06-18 19:58 ~ 2026-07-30 17:26 |

即 6 月应答 **323**、7 月应答 **1379**，系统两个都答成 1702——时间条件根本没进 WHERE，COUNT(*) 退化成了全表计数。**口径文案和数字对不上**：语义层把时间槽抽对了（所以文案写对了），但执行 SQL 没带这个条件。这就是用户说"通用算子效果太差、全是错的"的直接原因。

### 根因（已读代码定位）
- 行式明细 `generic_detail`（generic.py:123-151）是接收 filters 并逐列拼 WHERE 的；
- 但聚合/分组那几个函数（`group_count` 约 217 行、`time_bucket`/按时间分桶 约 239-255 行，以及 generic.py 里其它 group/agg 封装）的 where 是**硬编码 `[del_flag=0]`，根本没有把 `_generic_filters` 算出的 filters（时间 between、路线、病害类型 in、面积阈值）传进来拼**。
- 于是凡是走通用算子的 count、按时间/维度分组、按指标聚合，用户的所有业务过滤条件全部丢失，只剩 del_flag。

### 修复要求
1. **所有 generic 聚合/分组算子统一接收 filters 并拼进 WHERE**：和 generic_detail 同一套过滤构建（时间 between、路线、类型 in、面积/置信度阈值、设备等），不得在聚合函数里把 where 写死成只有 del_flag。抽一个共用的 `_build_where(kind, table, filters, alias)`，detail 与 group/count/time-bucket 都调它。
2. **时间条件必须落到 collection_time（或对应物理列）的 between**：抽到 time_range 就生成 `collection_time >= ? AND collection_time < ?`，而不是只在口径文案里写时间。
3. **结果自洽校验（重要，这类错最隐蔽）**：执行后若"统计口径声称带了时间/路线过滤，但返回计数 == 全表 del_flag=0 总数"，说明过滤没生效，必须判为结果不一致、交给 LLM 重写或放弃直出，不许把全表数当带条件的结果报给用户。
4. 路线/类型过滤同样适用：之前里程桩点误绑主键是另一处错（见《通用算子路线条件误绑主键修复方案》），与本项是同一类"过滤没正确落到表/列"问题，一并按 route_join_path 修。
5. 回归断言：
   - 「2026 年 6 月全库病害」= 323；
   - 「2026 年 7 月全库病害」= 1379；
   - 全库（不限时间）= 1702；
   - 「西乡段 7 月」「恒明珠 7 月」等带路线+时间的组合，计数等于"带 del_flag+路线+时间 WHERE"的真结果，不得再退化成全表。

## 二、不用手动按钮：后端自动给 MDL 补物理 SQL

用户反馈：管理页「示例库同步」卡片**确实没有**"给 Wren 示例补物理 SQL"按钮（已截图，线上构建产物里只有"立即同步"和三行统计，没有该按钮；源码 AdminPanel.vue:139-146 有，但部署的前端是旧构建）。

用户明确：**不需要这个按钮，只要把物理 SQL 自动补掉即可**。

### 要求
1. 不要依赖前端手动按钮，改为**后端自动补**：
   - 启动时、以及 `import_ragflow_examples`（立即同步）跑完后，遍历示例库里"有 MDL-SQL / 标了待补物理 SQL"的条目，自动调 Wren 编译成物理 SQL，写进文档的 `# 物理SQL` 段（沿用 nl2sql.py:6008-6010、6310 现有约定）；
   - 重放、挖模板、看板刷新一律优先用已补好的物理 SQL；
   - Wren 不可用/编译失败时**静默跳过、记日志、下次再试**，不要报错、不要阻塞启动、不要删原始 MDL。
2. 这样那 4 条 MDL（里程桩点、luge_name、最大宽高、西乡泛油计数）在 Wren 正常的环境里会被自动补成物理 SQL，无需人工点按钮。
3. 前端那个按钮可保留也可删（用户无所谓），但**不要把"补物理 SQL"做成必须人工触发**——以自动补为准。
4. 配合上一份《人工示例池全量参与模板挖掘方案》：对账把 RAGFlow 人工题全部置 trusted=1 后，重跑 mine_all，已补物理 SQL 的 MDL 题即可参与挖掘。

## 三、验收汇总
- 6 月=323、7 月=1379、全库=1702，三条都对；
- 任何"带过滤条件的通用算子 count/分组"，返回数 = 带完整 WHERE 的真实结果，且不等于被过滤掉的全表总数；
- 统计口径文案与实际 SQL 的 WHERE 一致，不一致时直出被拦；
- 启动/同步后，Wren 可用时 MDL 示例自动出现 `# 物理SQL` 段，无需手动点按钮；Wren 不可用时不报错、不丢数据。

- `backend/app/services/generic.py`：抽 `_build_where`，detail/group_count/time_bucket 等统一拼 filters（当前 group/time 的 where 约 217-255 写死 del_flag）。
- `backend/app/services/nl2sql.py`：补物理 SQL 改为启动/同步自动跑（复用 backfill_physical_sql）；结果自洽校验（口径时间 vs 计数=全表）。
- `backend/app/routers/dashboard.py` / `chat.py`：启动或同步后触发自动补物理 SQL。
- 前端按钮：按用户意愿可不做强制依赖；若保留需重新构建才能见到。
