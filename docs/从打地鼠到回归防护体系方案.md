# 从"打地鼠"到回归防护体系（给 codex）

## 一、为什么现在是发现一个改一个
1. 端到端没有"对不对得上问题"的自动判定：SQL 跑通、行数对就当对；但 SELECT 列/WHERE 条件/指标是不是用户问的，全靠人眼发现。
2. eval 脚本虽多（eval_cases/test_all_592_fields/test_cross_db...），但是"跑一次看结果"，不是"改代码就拦"；用户新遇到的 bug 没沉淀成用例。
3. bug 模式重复：通用算子多列/张冠李戴、auto 空条件乱套、ground 顺序、推荐 tier——都是规则只覆盖写它时想到的场景。

## 二、系统性解法

### ① 用户真实问法回归集（最重要）
把这几轮实际踩过的 bug 沉淀成固定用例，每条记：问法 + 期望（落点表 / SELECT 列 / 必带条件 / 必不出现的错）。改代码后自动跑，红了不让上。
已踩过、必须进回归集的用例：
- "西乡段的纬度范围" → 落 sections_pile_detail、SELECT 含 lat，metrics 不空；
- "分别列出路段桩号和相关的修改人" → SELECT 同时有桩号列 + update_by，update_by 不重复；
- "每种病害类型对应的病害代码" → 看板同义题排第一，不被空槽 auto 顶；
- "西乡段的病害图片" → 需要确认口径时弹卡，不说"暂不可用"；
- "宝安大道西乡段的泛油面积>10" → 路线名精确命中，不报"没找到路线"；
- "泛油病害里面积>10的有多少" → 上下行统计不能只剩上行；
后续每发现一个 bug，先加用例再修。

### ② 统一"结果对不对得上问题"校验器
SQL 出来后自动核对三件事，对不上就降级/重查：
- SELECT 列 ⊇ 用户点的列（"桩号+修改人"两列都在）；
- WHERE 条件 ⊇ 用户提的条件（路线/时间/类型一个不丢）；
- 指标/分组 = 用户要的（"纬度范围"必须有 lat 的 min/max）。
现在这些校验散在 validate_semantics/_drop_condition_losing/_result_words，收成一个统一 gate。

### ③ 字段目录唯一事实源
加表加列只改 schema_catalog；named_columns 按列名去重、认 model；_SUBJECT_TABLES 这类硬编码映射逐步退掉。

## 三、落地
1. 新建 regression_cases.json：上述用例 + 以后每踩一个加一个；
2. run_regression.py：跑用例、对期望、红了退出；
3. 统一结果校验 gate 接到出答案前；
4. 以后报 bug 的流程：先加用例 → 复现红 → 改 → 绿。这样每个 bug 只修一次。

### 6.1 夹具库怎么用

```bash
cd backend
python run_regression.py --fixtures            # 体检：预置 72 + 自动 44 条都在夹具上跑一遍
python run_regression.py --only static-check   # 只想验结构（表/列/编码值/矩阵），秒级
python run_regression.py --data-check          # 想验"真数据到了之后模板还对不对"
```

`--fixtures` 输出长这样：

```
夹具库 logs\test\fixture_lab.sqlite：18 张表 × 12 行；跑出行 55、0 行 60、报错 1
（夹具限制，不判红）auto_5e6b…：执行失败：circular reference: basic_facilities_bridges
```

**验自己写的一条 SQL**（不用等空表有数据）：

```python
from app.services import fixture_lab
fixture_lab.build()                                   # 建/重建夹具（本地 SQLite，只读业务库）
print(fixture_lab.run_sql("SELECT b.name FROM basic_facilities_bridges b "
                          "JOIN basic_facilities_routes r ON b.routes_id = r.id"))
# (True, 12, '')      ← 能跑、12 行
print(fixture_lab.run_sql("SELECT b.name FROM basic_facilities_bridges b "
                          "JOIN basic_facilities_routes r ON b.sections_id = r.id"))
# (True, 0, '')       ← join 键写错：本该有行却 0 行，这就是口径错的信号
print(fixture_lab.run_sql("SELECT b.tunnel_length FROM basic_facilities_bridges b"))
# (False, 0, '执行失败：no such column: b.tunnel_length')
```

用法要点：

1. **看行数**：明细类 SQL 的"行数"就是命中条数；**聚合类（COUNT/SUM）永远 1 行**，
   要看值（`run_sql` 只回行数，聚合题请用 `sqlite3` 直连 `logs/test/fixture_lab.sqlite` 看结果）；
2. **0 行要分辨**：join 键写错、编码值写错、条件筛太死都会 0 行——这正是空表上永远看不见的信号，
   但夹具数据本身也有取舍（每表 12 行、取值按 code_map 轮转），0 行是"值得核"而不是"一定错"；
3. **它只读**：对 MySQL/PG 只有 SELECT，夹具落在本地 SQLite；重建夹具只删自己那份 sqlite 文件；
4. **方言差异不算 bug**：`no such function`/自名 CTE 这类是 SQLite 限制
   （`--fixtures` 已把它们标成"不判红"），真 MySQL 跑得通就不算问题。
