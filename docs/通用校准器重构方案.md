# 通用校准器重构方案

## 一、背景与问题

### 1.1 现有校准器的问题

| 问题 | 表现 | 根因 |
|---|---|---|
| **只关注路线** | 桥梁/隧道/边坡/工单等资产对象没有校准 | `route_facts()` 只查路线 |
| **规则死板** | 多时间段只认"6月""7月"，不认"第31周""Q3" | `_MONTH_TOKENS` 只匹配月份 |
| **拦截激进** | 只要时间完全超出就拦截，不考虑用户意图 | 没有置信度/场景区分 |
| **回复矛盾** | 说"没有数据"又给全量统计 | `calibrated_reply()` 逻辑错误 |
| **枚举值不校准** | 用户说"桥梁病害"（不存在的大类），SQL查0行，用户不知道错哪 | 没有枚举值校准 |
| **实体不校准** | 用户说"宝安大道"（不存在的路线），SQL查0行 | 没有实体校准 |
| **重复连库** | 每次问同一条路都重新查库 | 缓存时间短（5分钟） |

### 1.2 核心痛点

> "600个字段我也校准不过来，但是关键字段（时间、桩号、枚举值、实体）必须校准，否则SQL错了用户还不知道错在哪。"

---

## 二、核心思路

### 2.1 只校准4类关键字段

| 字段类型 | 例子 | 校准内容 |
|---|---|---|
| **时间** | collection_time | 时间范围是否越界 |
| **数值范围** | pile_distance（桩号）、area（面积） | 数值是否在合理范围内 |
| **枚举值** | categories_type（所属大类）、problem_status（工单状态） | 用户说的枚举值是否存在，是否需要映射 |
| **实体** | route_id（路线）、bridge_id（桥梁） | 用户说的实体是否存在 |

**其他字段不校准**：SQL查0行用户也能理解。

### 2.2 覆盖所有资产对象

| 资产对象 | 实体表 | 数据范围表 | 关键字段 |
|---|---|---|---|
| **路线** | basic_facilities_routes | ai_problem | 时间、桩号、枚举值 |
| **路段** | basic_facilities_sections | ai_problem | 时间、桩号、枚举值 |
| **桥梁** | basic_facilities_bridges | ai_problem（通过sections关联） | 时间、桩号、枚举值 |
| **隧道** | basic_facilities_tunnels | ai_problem（通过sections关联） | 时间、桩号、枚举值 |
| **边坡** | basic_facilities_slope | ai_problem（通过sections关联） | 时间、桩号、枚举值 |
| **工单** | maintenance_work_order / ai_work_order | 工单表自身 | 时间、状态枚举值 |
| **巡查任务** | ai_maintain_patrol | 巡查任务表自身 | 时间、状态枚举值 |
| **病害** | ai_problem | ai_problem | 时间、桩号、枚举值 |

### 2.3 复用现有数据流，不重新连库

| 现有模块 | 已有数据 | 校准器怎么用 |
|---|---|---|
| **field_catalog（字段目录）** | 所有表的字段信息，包括字段注释 | 从字段注释里提取枚举值 |
| **field_grounding（字段触达）** | 用户问题里的字段匹配结果 | 知道用户问的是哪个字段 |
| **entity_facts（资产对象事实）** | 对象的台账信息 + 实际数据范围（时间、桩号） | 时间/桩号校准直接用，带缓存 |
| **global_data_range（全库数据范围）** | 全库的时间/桩号范围 | 没有具体对象时用这个 |
| **语义规划（plan）** | 用户问题的结构化描述（条件、字段、分组） | 校准的输入就是 plan |
| **实体解析（entity resolution）** | 路线/桥梁/隧道等实体的解析结果 | 实体校准直接用 |

**结论：校准器不需要重新连库，所有需要的数据都已经在现有数据流里了！**

### 2.4 基于字段元数据自动校准，不是每个字段写死规则

- 枚举值从字段注释里自动提取（如"所属大类（0路面病害，5路基病害...）"）
- 实体从关联表里自动查询（如路线→basic_facilities_routes）
- 时间/数值范围从数据表里自动统计
- 通过配置驱动，新增资产对象只需要加一行配置

## 三、枚举值校准（核心）

### 3.1 校准逻辑

1. 从字段注释里提取枚举值列表（纯文本解析，不需要连库）
2. 判断用户说的值是否在枚举值列表里
3. 如果不在，尝试模糊匹配（同义词、包含关系，纯字符串相似度）
4. 分级处理：
   - 高置信度匹配（相似度≥0.9）：自动映射
   - 低置信度或多个匹配：提示用户选择
   - 没有匹配：拦截，告诉用户正确的值

### 3.2 例子1：所属大类

**字段注释：** `categories_type varchar(100) YES 所属大类（0路面病害，5路基病害，10沿路设施，15交安事件）`

**用户问：** "桥梁病害有多少？"

**校准过程：**
1. 从字段注释里提取枚举值：`{0: "路面病害", 5: "路基病害", 10: "沿路设施", 15: "交安事件"}`
2. 用户说的"桥梁病害"不在枚举值里
3. 模糊匹配："桥梁" → 沿路设施？（相似度0.3，不确定）
4. **校准结果：** 拦截，告诉用户
   > "没有'桥梁病害'这个大类，可选的大类是：路面病害、路基病害、沿路设施、交安事件。您是想问'沿路设施'吗？"

### 3.3 例子2：作业类型

**字段注释：** `work_type varchar(100) YES 作业类型(清扫路面0、绿化保洁5、路灯维护10)`

**用户问：** "需要打扫路面的道路作业有哪些？"

**校准过程：**
1. 从字段注释里提取枚举值：`{0: "清扫路面", 5: "绿化保洁", 10: "路灯维护"}`
2. 用户说的"打扫路面"不在枚举值里
3. 模糊匹配："打扫路面" → "清扫路面"（同义词，相似度0.9）
4. **校准结果：** 自动映射到"清扫路面"（code=0），不需要问用户，直接生成正确的SQL

### 3.4 例子3：用户列出一个没有的类

**用户问：** "桥梁病害和隧道病害各有多少？"

**校准过程：**
1. "桥梁病害"不在枚举值里，"隧道病害"也不在
2. 模糊匹配：都没有高置信度匹配
3. **校准结果：** 拦截，告诉用户
   > "没有'桥梁病害'和'隧道病害'这两个大类，可选的大类是：路面病害、路基病害、沿路设施、交安事件。"

### 3.5 从字段注释里提取枚举值的函数

```python
def extract_enum_from_comment(comment: str) -> dict[str, str]:
    """从字段注释里提取枚举值映射。
    
    例子：
    "所属大类（0路面病害，5路基病害，10沿路设施，15交安事件）"
    → {"0": "路面病害", "5": "路基病害", "10": "沿路设施", "15": "交安事件"}
    
    "作业类型(清扫路面0、绿化保洁5、路灯维护10)"
    → {"0": "清扫路面", "5": "绿化保洁", "10": "路灯维护"}
    """
    match = re.search(r"[（(](.+?)[）)]", comment)
    if not match:
        return {}
    
    content = match.group(1)
    enum_map = {}
    
    # 模式1："0路面病害，5路基病害"（数字在前，中文在后）
    for code, name in re.findall(r"(\d+)\s*([^，、,0-9]+)", content):
        enum_map[code] = name.strip()
    
    # 模式2："清扫路面0、绿化保洁5"（中文在前，数字在后）
    for name, code in re.findall(r"([^，、,0-9]+?)\s*(\d+)", content):
        enum_map[code] = name.strip()
    
    return enum_map
```

## 四、时间/数值范围校准

### 4.1 时间校准

**用户问：** "西乡段2026年8月的病害有多少？"

**校准过程：**
1. 从 entity_facts 里获取数据范围：`MIN(collection_time)=2026-07-15, MAX(collection_time)=2026-07-30`
2. 用户问的8月（2026-08-01 ~ 2026-09-01）完全超出数据范围
3. 越界幅度：2天（8月1日 - 7月30日 = 2天）
4. **校准结果：** 小幅越界（<3天），放行，让SQL自己查0行

**用户问：** "西乡段2026年9月的病害有多少？"

**校准过程：**
1. 数据范围：2026-07-15 ~ 2026-07-30
2. 用户问的9月完全超出，越界幅度：32天
3. **校准结果：** 明显越界（>3天），拦截，告诉用户
   > "西乡段的病害数据实际覆盖 2026-07-15 ~ 2026-07-30，您问的9月没有数据。"

### 4.2 桩号校准

**用户问：** "西乡段K10+000 ~ K11+000的病害有多少？"

**校准过程：**
1. 从 entity_facts 里获取桩号范围：`MIN(pile_distance)=11, MAX(pile_distance)=887`
2. 用户问的10000~11000米完全超出数据范围
3. 越界幅度：9113米
4. **校准结果：** 明显越界（>100米），拦截，告诉用户
   > "西乡段的病害数据实际覆盖 K0+011 ~ K0+887，您问的 K10+000 ~ K11+000 没有数据。"

### 4.3 越界幅度判断

| 字段类型 | 小幅越界（放行） | 明显越界（拦截） |
|---|---|---|
| 时间 | <3天 | ≥3天 |
| 桩号 | <100米 | ≥100米 |
| 面积 | <10平方米 | ≥10平方米 |

## 五、实体校准

### 5.1 校准逻辑

1. 复用现有的实体解析结果（路线解析、桥梁解析等）
2. 如果实体解析结果是空的，看有没有相似的实体（实体解析时已经算过了）
3. 如果有相似的，提示用户选择
4. 如果没有相似的，拦截，告诉用户实体不存在

### 5.2 例子：路线

**用户问：** "宝安大道的病害有多少？"

**校准过程：**
1. 从路线解析结果里看：匹配到2条相似的路线
2. 结果：`["宝安大道西乡段", "宝安中心--恒明珠"]`
3. "宝安大道"不在结果里，但匹配到2个相似的
4. **校准结果：** 不拦截，提示用户
   > "找到2条名字相近的路线：宝安大道西乡段、宝安中心--恒明珠。您是想问哪一条？"

## 六、校准结果的分级处理

| 校准结果 | 处理方式 | 例子 |
|---|---|---|
| **明显错误** | 拦截，告诉用户正确的值 | 枚举值不存在、实体不存在、时间/桩号明显越界 |
| **可能错误（模糊匹配到多个）** | 不拦截，提示用户选择 | 路线名匹配到多个 |
| **可能错误（模糊匹配到1个，高置信度）** | 自动映射，不提示用户 | "打扫路面"→"清扫路面" |
| **小幅越界** | 不拦截，让SQL自己查0行 | 时间越界<3天、桩号越界<100米 |
| **正确** | 不拦截 | 所有值都正确 |

## 八、通用资产对象事实缓存（扩展 route_facts）

```python
def entity_facts(entity_type: str, entity_id: str) -> dict[str, Any]:
    """通用资产对象事实缓存（扩展 route_facts，支持所有资产对象）。
    
    返回：
    - entity_name: 对象名称
    - data_min_time: 数据最早时间
    - data_max_time: 数据最晚时间
    - data_min_pile: 数据最小桩号（如果有）
    - data_max_pile: 数据最大桩号（如果有）
    - data_count: 数据条数
    """
    config = ENTITY_CONFIG.get(entity_type)
    if not config:
        return {}
    
    key = f"{entity_type}:{entity_id}"
    cached = _facts_cache.get(key)
    if cached and time.time() - cached[0] < _FACTS_TTL_SECONDS:
        return cached[1]
    
    # 1. 查实体表（对象名称、台账信息）
    entity = (_query(
        f"SELECT {config['entity_name_field']} AS name "
        f"FROM {config['entity_table']} "
        f"WHERE id = '{entity_id}' LIMIT 1"
    ) or [{}])[0]
    
    # 2. 查数据表（数据范围：时间、桩号、数量）
    if config["data_table"] == config["entity_table"]:
        data = (_query(
            f"SELECT MIN({config['time_field']}) AS min_time, "
            f"MAX({config['time_field']}) AS max_time, "
            f"COUNT(*) AS cnt "
            f"FROM {config['data_table']} "
            f"WHERE id = '{entity_id}'"
        ) or [{}])[0]
    else:
        pile_sql = f", MIN({config['pile_field']}) AS min_pile, MAX({config['pile_field']}) AS max_pile" if config['pile_field'] else ""
        data = (_query(
            f"SELECT MIN({config['time_field']}) AS min_time, "
            f"MAX({config['time_field']}) AS max_time, "
            f"COUNT(*) AS cnt "
            f"{pile_sql} "
            f"FROM {config['data_table']} "
            f"WHERE {config['data_join_field']} = '{entity_id}' AND del_flag = 0"
        ) or [{}])[0]
    
    facts = {
        "entity_type": entity_type,
        "entity_id": entity_id,
        "entity_name": entity.get("name"),
        "data_min_time": data.get("min_time"),
        "data_max_time": data.get("max_time"),
        "data_min_pile": data.get("min_pile"),
        "data_max_pile": data.get("max_pile"),
        "data_count": data.get("cnt"),
    }
    _facts_cache[key] = (time.time(), facts)
    return facts
```

**缓存时间延长到30分钟**（对象的台账和数据范围不会频繁变）。

## 九、校准器在数据流中的位置

**现有数据流：**
```
用户输入 → 意图分类 → 语义规划(plan) → 字段触达 → 选表选字段 → 生成SQL → 执行 → 结果总结
```

**校准器的位置（插入在语义规划之后，生成SQL之前）：**
```
用户输入 → 意图分类 → 语义规划(plan) → 【校准器】 → 字段触达 → 选表选字段 → 生成SQL → 执行 → 结果总结
```

**校准器的输入（全部来自现有数据流，不需要重新连库）：**
- `plan`：语义规划的结果（已有）
- `field_catalog`：字段目录（已加载，全局缓存）
- `entity_facts`：资产对象事实（已有，30分钟缓存）
- `field_grounding`：字段触达结果（已有）

**校准器的输出：**
- `issues`：校准问题列表（如果有明显错误，拦截并告诉用户）
- `updated_plan`：更新后的 plan（如果有自动映射，更新条件值）

## 十一、校准器主逻辑

```python
def calibrate_plan(plan: dict) -> list[dict]:
    """通用校准：支持所有资产对象（路线/桥梁/隧道/边坡/路段/工单/巡查任务）。"""
    issues = []
    
    # 1. 判断当前是哪个资产对象
    entity_type = get_entity_type_from_grounded(plan) or get_entity_type_from_plan(plan)
    if not entity_type:
        return issues  # 多表查询或未知对象，不校准
    
    # 2. 获取实体ID（从 plan 的 slots 里）
    entity_id = get_entity_id_from_plan(plan, entity_type)
    if not entity_id:
        return issues  # 没有实体ID，不校准
    
    # 3. 获取资产对象事实（复用缓存，不需要重新连库）
    facts = entity_facts(entity_type, entity_id)
    if not facts:
        return issues  # 没有事实数据，不校准
    
    # 4. 时间范围校准（所有资产对象都有时间）
    time_issue = calibrate_time(plan, facts)
    if time_issue:
        issues.append(time_issue)
    
    # 5. 桩号范围校准（只有路线/路段/桥梁/隧道/边坡有桩号）
    if facts.get("data_min_pile") is not None:
        pile_issue = calibrate_pile(plan, facts)
        if pile_issue:
            issues.append(pile_issue)
    
    # 6. 枚举值校准（所有资产对象的字段都需要，复用 field_catalog）
    enum_issues = calibrate_enums(plan, entity_type)
    issues.extend(enum_issues)
    
    return issues
```

## 十二、拦截后的回复优化

**时间越界的回复：**
- 只说明数据覆盖范围
- 建议换时间段
- **不要给全量统计**（那是误导）

```python
def calibrated_reply(plan, info):
    facts = info["facts"]
    lines = [info["message"] + "。"]
    
    if info["kind"] == "time":
        # 时间越界：只说明覆盖范围，不给全量统计
        lines.append(
            f"（数据覆盖范围：{str(facts.get('data_min_time'))[:10]} ~ "
            f"{str(facts.get('data_max_time'))[:10]}，共 {facts.get('data_count')} 条）"
        )
        lines.append("建议换一个在数据覆盖范围内的时间段，或者问「全部时间」的统计。")
    else:
        # 桩号越界：可以给实际范围内的统计
        scope = f"{fmt_pile(facts.get('data_min_pile'))}~{fmt_pile(facts.get('data_max_pile'))}"
        lines.append(f"（台账：{facts.get('ledger_start')}~{facts.get('ledger_end')}，"
                     f"病害数据实际范围：{scope}，共 {facts.get('data_count')} 处）")
        stats = _range_stats(plan, facts)
        if stats:
            lines.append(f"实际范围内的统计：{stats}。")
    
    return "\n".join(lines)
```

## 十四、核心原则

1. **只校准关键字段**：时间、数值范围、枚举值、实体，其他字段不校准
2. **覆盖所有资产对象**：路线、桥梁、隧道、边坡、路段、工单、巡查任务，都要校准
3. **复用现有数据流**：field_catalog、entity_facts、实体解析结果，全部复用，**不重新连库**
4. **基于字段元数据自动校准**：从字段注释里提取枚举值，不是每个字段写死规则
5. **配置驱动**：通过 `ENTITY_CONFIG` 配置表名、字段名、关联关系，新增资产对象只需要加一行配置
6. **校准结果分级处理**：明显错误拦截，可能错误提示，高置信度自动映射，小幅越界放行
7. **纯内存操作**：模糊匹配用简单的字符串相似度，不用LLM，不增加回答时间
8. **缓存优化**：每个资产对象的事实数据只查一次，之后用30分钟缓存，不重复连库
9. **校准要明确**：告诉用户哪个字段错了，正确的值是什么，不要含糊
10. **拦截后不误导**：说"没有数据"就不要给全量统计

## 十五、不做的边界

- 不校准600个字段，只校准4类关键字段
- 不加LLM，全是确定性规则
- 不重新连库，复用现有数据流
- 不做自动修复SQL，只做校准和提示
- 不做用户意图推断（除了枚举值同义词的自动映射）
- 不做复杂的语义理解，只做简单的字符串相似度匹配
