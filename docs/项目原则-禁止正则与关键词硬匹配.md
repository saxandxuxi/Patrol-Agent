# 项目原则：禁止正则与关键词硬匹配

> 本文件是巡检智能体业务语义链路的强制约束。每次修改 QuerySpec、规划器、模板推荐、工具路由、字段解析、结果验收或回答生成前，都必须先阅读本文件。

> QuerySpec 规划、TopN、结果验收、用户裁决或评测代码变更，还必须同时阅读
> [项目原则-AI晋级考试与用户裁决.md](./项目原则-AI晋级考试与用户裁决.md)。
> 修改提示词、事实源、MDL 投影或能力配置时，还必须阅读
> [项目原则-提示词与事实源一致性.md](./项目原则-提示词与事实源一致性.md)。

## 一、最高原则

巡检智能体必须依靠语义模型理解用户问题，依靠结构化契约约束执行，不允许用正则表达式、关键词列表、中文短语包含关系或问题 ID 映射来猜测业务语义。

正则、关键词和代码规则最多只能生成“候选证据 JSON”供 LLM 参考，不能直接把候选证据当成业务结论、QuerySpec、过滤条件、SQL、工具选择或最终答案。

以下行为一律禁止：

1. 用 `if "关键词" in question` 判断意图、主体、指标、时间、路线、病害类型、比较关系或输出形状。
2. 用 `re.search()`、`re.findall()`、`re.match()` 从自然语言中抽取业务条件或选择查询路径。
3. 维护“同义说法词表”，通过不断补词让某道题通过。
4. 根据用户原话中的固定短语直接决定 SQL、字段、工具、模板或确认卡。
5. 用题目 ID、完整问句或问句片段映射到特定 SQL、特定步骤或特定答案。
6. 模型输出不符合要求时，用字符串规则静默改写用户问题、查询范围或业务条件。
7. 把代码扫描出的候选实体直接写入 QuerySpec。即使扫描出了工单号、病害名称或路线名，也必须交给规划 LLM 结合用户原话确认。

如果换一种说法就失败，正确修复方向是补充字段字典、业务规则、结构化契约、模型上下文或受控反馈，不是继续增加关键词和正则。

允许的代码辅助方式只有一种：代码产生候选证据，LLM 做语义判断。例如：

```json
{
  "source": "code_candidate",
  "raw_span": "XJJL202611040003",
  "candidate_type": "business_identifier",
  "candidate_field": "patrol.task_number",
  "reason": "符合已登记的业务编号格式",
  "trusted": false
}
```

规划 LLM 收到这类证据后，仍需结合问题原意输出 QuerySpec，并由字段目录、值来源和规划契约验证。禁止代码看到这个编号就直接把 `task_number` 塞进 SQL。

## MDL、业务配置与口语证据并行

生成和审计 MDL-SQL 时，以下三类输入必须同时可用：

1. Wren MDL：模型名、真实列、计算字段、cube 指标和关系拓扑。
2. `resources/capabilities/`：巡检业务字段标签、枚举、实体层级、指标口径、谓词和业务断言。
3. `resources/capabilities/assist_rules.yaml` 产生的口语候选证据：只作为
   `trusted=false` 的参考线索。

三者是并行互补的事实视图，不存在“MDL 优先、本地业务配置兜底”，也不存在“本地配置优先、MDL 只做校验”。MDL 已经完整表达的通用结构事实直接使用 MDL；本地配置只补充巡检业务特有、MDL 无法表达的口径。两类事实同时进入 Planner、合同构建和受控 MDL-SQL 生成上下文，QuerySpec 与冻结合同始终是本次查询范围和权限的权威。

同一事实在两套来源中冲突时，返回结构化失败证据，不静默选边。口语候选证据可以帮助模型理解用户说法，但不得直接覆盖主体、字段、过滤、指标、JOIN 或 SQL。

## 单一事实源与文件职责

所有人工维护的语义与能力映射必须统一放在 `resources/capabilities/`。逐文件职责只维护一份权威清单：
  [resources/README.md](../resources/README.md) 的“文件职责”表。本原则文件只规定归属和验收规则，
不再复制逐文件职责表，避免规则文件自身出现双写。

1. **一个原子事实只能有一个人工 owner。** 字段含义、枚举编码与展示值、表中文名、实体成员、
   指标公式、关系、SQL 形状和业务谓词都必须能指认唯一 owner 文件。
2. **别名不是第二份事实。** 同义说法只能登记为别名、候选证据或引用键，不能复制编码映射、
   公式、JOIN 或查询范围。展示值和存储值仍按数据流不变量显式区分。
3. **派生结果不是人工来源。** `metadata.yml`、`target/mdl.json`、缓存和运行期模板可以由 owner
   生成或投影，但禁止手工维护后反向冒充来源；生成器必须从唯一 owner 读取并生成。
4. **一个文件只承担一个清晰职责。** 新配置必须先在 `resources/README.md` 登记职责；禁止把
   互不相关的规则塞进“其他”“杂项”或已有大文件。
5. **冲突必须显式失败。** 同一事实在多个运行时来源中出现不同公式、单位、标签、关系或枚举时，
   加载或编译阶段必须返回结构化失败证据，不能按文件顺序或模型偏好静默选边。
6. **迁移必须同步删除旧定义。** 某条规则换文件后，原位置的旧定义和旧读取分支必须在同一次
   修改中删除，禁止双写、兼容期暗读或保留未登记副本。

禁止继续把业务枚举、实体别名、病害层级、指标名或字段到 SQL 的映射写在 `.py` 文件中。
运行数据（自动模板、预设查询、日志、缓存和数据库实时读取结果）不属于能力配置，不迁入该目录。

统一能力注册表和 QuerySpec 数据断点的正式设计见
  [2026-11-06-unified-capability-registry-design.md](./superpowers/specs/2026-11-06-unified-capability-registry-design.md)。

## 代码组织与业务规则归集约束

新增或迁移代码前，必须先按业务职责确定归属，不允许继续把功能堆进 `agent.py`、`nl2sql.py` 等大文件。

1. 通用算术、列计算、序列计算、比例、对比、趋势、密度和表格证据分别放入独立模块。
2. 具体病害或养护公式放入独立业务公式模块，不写进 `post_calc` 调度器。
3. 人工维护的计算能力、参数约束和公式登记统一放在 `resources/capabilities/calculators.yaml`。
4. 工具注册文件一个工具或一组紧密相关工具一个文件，不在注册表入口堆实现。
5. 迁移某个函数后，必须删除原文件中的旧实现和旧触发分支，禁止双写。
6. 单个业务文件职责过多时，应先拆分再增加功能；不允许继续向已有上帝文件追加新逻辑。
7. 查询结果的单位解析、数值去尾零和分组摘要统一放在
   `backend/app/query/presentation/`；查询为空时的可回答性判定统一放在
   `backend/app/query/empty_results.py`。不得再向 `service.py` 重复添加同类规则。

计算子系统的正式设计见
  [2026-11-06-calculation-tool-registry-design.md](./superpowers/specs/2026-11-06-calculation-tool-registry-design.md)。

## 二、六个必须牢记的数据流不变量

1. **同一个数据结构在不同阶段可能需要不同视图。** 字段触达列视图、完整物理列目录、展示字段集合不能互相替代。
2. **字符串相等不等于语义相等。** `"下行"` 可能是值，也可能只是 `"上下行"` 的一部分。
3. **显示值和存储值必须显式区分。** code 只用于执行和比较，中文标签用于展示；输入和输出方向都要测试。
4. **语义预测不能代替执行事实。** 用户“想要分布”不代表 SQL 真的返回了分组统计。
5. **中间对象必须带来源。** 一个字段或条件来自用户原话、规则推断、字段目录还是模型猜测，必须可追溯。
6. **边界要有契约测试。** 只测完整聊天回答，定位成本高，且会被模型随机性掩盖。

修改这类数据流前，必须先写清四个问题：

1. 这个对象的输入是什么？
2. 谁生产它？
3. 谁消费它？
4. 消费方依赖的最小不变量是什么？

如果这四个问题回答不清楚，说明边界还没有定义，不能开始改代码。

## 三、唯一允许的输入

业务语义只能来自以下受控来源：

1. **用户原话**：`user_explicit`，必须保留原始约束。
2. **字段字典**：真实存在的表、物理列、逻辑字段、类型、单位、枚举 code 和显示标签。
3. **业务规则**：明确登记、可追溯、可测试的规则，例如“本月”换算为半开时间区间。
4. **模型语义结论**：模型输出结构化字段，但必须经过闭集、字段存在性、来源和值解析校验。

每个过滤条件、指标、维度、依赖和派生计算都必须携带来源。没有来源的模型推断不能直接进入 SQL。

## 四、标准流程

```text
用户问题
  → LLM 生成 QuerySpec
  → 代码校验 JSON 结构和闭集字段
  → 字段目录校验表/列是否存在
  → 字典解析枚举值和显示标签
  → 规划契约校验主体、视图、指标、维度、依赖和输入绑定
  → 编译器生成 SQL
  → 只读与安全校验
  → 执行 SQL
  → 按结构化事实验收结果
  → 失败时反馈结构化 FailureEvidence
  → LLM 只修 QuerySpec 或 SQL 的可修部分
  → 仍有界失败则明确返回原因
```

正则和关键词不参与上述任一“业务语义判断”环节。

## 五、代码可以确定性地做什么

禁止的是用文本匹配推断业务语义，不是禁止确定性代码。以下能力仍应由代码完成：

1. 校验字段是否存在、类型是否兼容、枚举 code 是否合法。
2. 将模型给出的中文枚举标签通过字段字典解析成存储 code。
3. 将“本月”等已登记业务规则换算成明确时间边界。
4. 检查依赖图、输入绑定、视图结构和输出投影是否满足契约。
5. 检查 SQL 是否只读、是否越权、是否缺少 `del_flag` 或必要的 `LIMIT`。
6. 对执行结果做空结果、分组结构、字段缺失、截断和数值边界检查。
7. 执行单位换算、算术、并列排序和确定性聚合。
8. 对用户明确给出的业务编号做字典精确查找；这是台账解析，不是按关键词猜语义。

## 六、失败后的正确处理

验收失败必须返回结构化证据，例如：

```json
{
  "failure_code": "wrong_grouping",
  "node_id": "q2",
  "question": "按巡检批次统计坑槽数量",
  "sql": "...",
  "result_sample": [],
  "reason": "SQL 未按巡检批次分组",
  "allowed_repairs": ["rewrite_query_spec", "rewrite_sql"],
  "preserve": ["user_scope", "business_id", "time_range"]
}
```

控制器只能在允许范围内修复。不得用关键词判断“这次像是时间题/分布题/完成情况题”，然后偷偷替换用户范围。

## 七、修改检查表

每次提交前必须确认：

1. 本次改动是否新增了任何业务关键词列表或业务正则？
2. 是否通过 LLM 输出的 QuerySpec 或结构化工具参数进入业务链路？
3. 字段、枚举和值是否来自字段字典或已登记业务规则？
4. 是否保留用户原话中的范围、编号、时间和对象？
5. 失败是否返回结构化原因，而不是静默换路径或拼接兜底答案？
6. 是否增加至少一个同义改写测试，证明换说法不依赖新关键词？
7. 改动涉及的文件是否都能在 `resources/README.md` 的职责表中找到唯一职责，且没有向
   不相关文件追加功能？
8. 是否完成“功能杂糅、内容重复、内容矛盾”一致性审计，并在交付说明中列出扫描范围、
   扫描结果和仍然存在的债务？

只要第 1 项为“是”，本次修改不合格。

## 八、强制验收：功能杂糅、重复与矛盾审计

任何涉及 QuerySpec、规划器、SQL 编译、能力注册表、业务配置、结果验收或回答生成的修改，
验收时都必须逐项审计。只跑通测试不能代替本审计。

1. **功能杂糅**：改动是否让一个文件同时承担多个无关职责？若是，先按
   `resources/README.md` 拆分，再继续验收。
2. **内容重复**：同一原子事实是否仍在两个人工文件、代码常量或可编辑生成物中维护？
   若是，保留唯一 owner，删除其余定义和旧读取分支。
3. **内容矛盾**：相同字段、枚举、表名、指标或关系在不同阶段是否出现不同标签、单位、
   公式或取值？若是，按唯一 owner 归一；无法确定归属时返回结构化冲突，不得静默选边。
4. **来源与生成物**：确认生成物、缓存和运行期数据没有被当成人工事实源；生成物必须能由
   owner 配置重新生成。
5. **证据留痕**：交付时必须说明检查了哪些目录和文件、用了哪些扫描或测试，以及没有关闭的
   同类问题。不能只写“已检查”或“应该没有问题”。

## 九、当前已删除的错误做法

为避免再次把临时补丁当成架构，以下做法已经明确删除：

1. 根据“完成情况”“巡检”“本月”等词直接生成巡检状态计划。
2. 根据“路”“健康状况”“最严重”“优先养护”等词直接生成路线健康计划。
3. 根据“哪个道路……最严重”正则自动给查询补指标和 `post_calc`。

这些能力必须由 `prompts/query_spec.md` 的语义规则、QuerySpec 校验器和规划审计共同保证。

## 十、迁移说明

项目历史上仍有其他关键词/正则分支。它们属于待迁移债务，不代表允许继续使用。后续修改业务语义链路时，应删除所触碰到的硬匹配分支，并迁移为 QuerySpec、字段字典、业务规则或结构化审计，不得在旧分支旁继续叠加新的特例。
