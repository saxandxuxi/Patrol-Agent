# ReAct 编排大脑落地方案

> 适用对象：道路巡检养护 NL2SQL 智能体后端，根目录 
>
> `backend/`
>
> 。
> 本文回答一个问题：现在有十几个提示词、多个分工 LLM 和几十个确定性函数，但它们靠一条写死的流程串起来，缺一个统一指挥的大脑。本方案给出这个大脑长什么样、落在哪、怎么和现有代码无缝接起来，以及分几步落地、每步怎么验收。
> 写作前提：所有结论均基于对当前代码的只读走查，涉及函数均标注文件与行号，落地时以行号附近的真实代码为准。



***

## 一、先把现状讲清楚：现在的智能体是怎么跑的

### 1.1 它是一条写死的流水线，不是一个会边做边想的智能体

对外入口是 `backend/app/services/agent.py` 的 `handle_message`（第 3791 行）。它先调 `_handle_message`（第 4500 行）拿到结果，成功之后再按固定顺序挂三道后置处理：`_verify_and_refine`（第 4080 行，答非所问校验加优化重查）、`_reflect_check_step`（数字自洽反思）、`_followup_step`（后续建议）。

`_handle_message` 是一个上千行的巨型分支函数，里面用一长串 `if/elif` 把一次请求往下推。主干顺序是：



1. 问题归一化 `query_rewrite.normalize`；

2. 多轮上下文补全 `memory.contextualize`；

3. 并行做两件事，意图分类 `intent.classify_intent` 和语义规划 `nl2sql.build_query_plan`；

4. 跨库判定 `cross_db.db_scope`；

5. 模板总闸、确定性引擎判定；

6. 按意图硬路由到五个分支：知识库走 `_answer_knowledge`，图片走 `_image_result`，元数据走 `metadata_service.profile_answer`，复合题走 `_handle_composite`，普通数据题走 `_build_query_result`。

复合题的执行在 `_handle_composite`（第 2540 行）。它先让 `orchestrator.decompose`（`orchestrator.py` 第 129 行）**一次性**把整个问题拆成一串步骤，然后用一个 `for task in tasks` 循环按顺序执行，按 `task.type` 再分派到 `post_calc`、`analysis`、`knowledge`、`image`、`data` 五种处理器。它支持 `produces` 产出值和 `needs` 回填占位符，比如第一步算出最多的那一周，第二步把这个周名填进自己的问题里。但这一步填值是**静态**的，循环开始时所有步骤已经写死，执行中途不会因为某一步的结果不符合预期而改变后面的路线。

单条数据查询的主执行器是 `_build_query_result`（第 1636 行）。它内部完整走一遍：语义规划、派生字段强制 Wren、缺失字段拦截、能力确认卡、预置模板或 Wren 或 LLM 生成 SQL、校验、执行、结果摘要。这是项目里沉淀最厚、最值得复用的一条链路。

### 1.2 大脑该有的零件其实已经有了，只是散着、焊死了

走查下来，ReAct 所需的大部分组件都已存在：



* **规划能力**：`prompts/planning.md` 加 `orchestrator.decompose`，能产出带 `is_simple`、`final_goal`、`steps`、`produces`、`needs` 的 JSON 计划。问题是它只规划一次，不看执行结果。

* **链式依赖**：`planning.md` 已定义 `{{key}}` 占位符、`from_column` 取值、`peak_week` 这类峰值键命名，`_handle_composite` 也实现了回填。问题是它只能按写死的顺序填，不能动态增删步骤。

* **事后纠错循环**：`_reflect_loop`（第 4239 行）已经是一个 "校验失败就改 SQL 重查、最多三次" 的循环，是最接近 ReAct 的雏形。但它只在拿到结果之后做 "同一条 SQL 的修正"，不会在任务执行中途换策略，比如不会从 "拉明细" 改成 "GROUP BY 聚合"。

* **候选能力**：`capabilities.collect_capabilities`（第 1469 行）能收集确定性口径卡，`execute`（第 1829 行）能把选中的口径绑成 SQL。

* **一批确定性原子能力**：`calibrate` 做时间和桩号覆盖校准，`asset_resolver` 解析桥梁隧道边坡，`route_resolver` 解析路线和病害类型，`field_grounding` 做字段触达，`clarify` 做信息不足追问，`sql_engine` 做只读校验和执行。

这些零件的共同问题是：它们没有统一的入口和统一的调用契约，彼此之间靠 `agent.py` 里的 `if/elif` 硬接。加一种新能力，就要去主流程里再加一个分支；某一步查空了，后续步骤也不会自己调整。

### 1.3 已经踩过的坑，根因都是 "规划写死、不会看结果"

本项目过去几轮反复出现的故障，本质都指向同一个缺口。

**周数错位。** 问 "哪个星期西乡段泛油最多，把那周明细列出来"，第一步按周分组算出峰值周，第二步本应按算出来的那一周查明细。实际执行时第二步的时间区间被填成了错误的日期，比如用户说的是第 31 周，落库却用了 10 月 12 日到 19 日。静态回填只认字符串，不会拿第一步结果和库里真实覆盖范围对一遍。

**零结果却拼出矛盾回复。** 时间范围越界查空时，`calibrate.calibrated_reply` 先说 "您问的时间段没有数据"，随后无条件又拼上一段 `_range_stats` 输出 "实际范围内泛油 534 处"。两句话前后矛盾，因为流程是 "先回零结果，再拼统计"，没有一个环节看着最终回复判断它是否自洽。

**拿截断明细做全局排名。** 问 "西乡段哪半个月病害最多"，系统拉回前 500 条明细就停，再让模型基于这 500 条判断，模型只能答 "数据不全，无法判断"。正确做法是第一步就该用 `GROUP BY 半月` 聚合，但静态规划把它拆成了拉明细，执行时没有任何人发现 "这个动作根本拿不到答案"。

**复合题第二步时间整体错位。** 第 31 周和第 32 周对比，第一步给出的范围是 7 月 27 日到 8 月 3 日，和 ISO 周历真实区间对不上，第二步顺着错区间继续查，错上加错。

这四类问题的共同根因是：系统在开始执行前就决定了全部动作，执行过程中拿到的观察结果不会反过来影响下一步。这正是 ReAct 要补的能力。

## 二、改造目标与边界

### 2.1 目标

把现在散落在各 service 的原子能力封装成一批**签名统一、可被统一调度的工具**，再增加一个**只在执行出现偏差时才启动的编排大脑**。计划由前置的对话理解、意图、规划环节一次性产出并冻结，执行器按计划逐步调用工具、读取观察结果，门控判定异常时才交给大脑选择纠偏动作，如此循环，直到拿到最终答案或判断必须向用户追问。

### 2.2 必须守住的边界



1. **不重写取数链路，不重复连库。** 大脑的查数工具内部直接调用现有 `_build_query_result`，复用它内部的模板、Wren、LLM 生成、校验、执行全部能力。数据库仍只通过 `db_manager` 一条只读通道访问，大脑不新增任何直连。

2. **不拖慢简单题。** 确定性模板和已确认示例必须保留零次大脑 LLM 的直出捷径。大脑只在真正需要边做边看的复杂题上启动，这是硬约束。

3. **不推倒重来。** 现有 `_handle_message` 的前置归一化、意图分类、跨库判定、能力确认卡全部保留，大脑是其中复合分支的一个新执行器，不是替换整个入口。

4. **大脑提示词严格输出 JSON。** 遵循既有工程约定，大脑只产出纯 JSON 文本，不输出 Markdown 和解释性散文，由代码解析。

5. **覆盖全部资产对象。** 工具层的实体解析不只认路线，桥梁、隧道、边坡沿用 `asset_resolver` 已有的三类映射，不新建只服务路线的窄通道。

6. **只读。** 大脑能调用的工具全部是只读查询和纯计算，不开放任何写入、修改、建表动作。

## 三、总体架构：三层路由、一个大脑、一组工具

### 3.1 三层路由

一次请求在做完前置归一化和意图分类后，按复杂度进入三层之一。



| 层级          | 触发条件                                            | 执行方式                                                | 大脑 LLM 次数                          |
| ----------- | ----------------------------------------------- | --------------------------------------------------- | ---------------------------------- |
| L0 确定性直出    | 命中预置模板、已确认示例、元数据画像、单对象台账属性                      | 现有能力卡或模板直接出 SQL                                     | 0 次                                |
| L1 单轮规划     | 单步数据查询、单步知识库、单图查询，无需依赖前一步结果                     | 现有 `_build_query_result` 或 `_answer_knowledge`，一次执行 | 0 次（语义规划仍用现有 `semantic` 模型，不额外加大脑） |
| L2 ReAct 循环 | 链式依赖、TopN 后查明细、多步对比、零结果需要调整、聚合维度需要修正、数据加规范的综合分析 | 代码按冻结计划确定性推进，观察门控判定异常才调大脑选纠偏动作 | 计划顺利为 0 次，仅异常分叉时调用，上限五步 |

L0 和 L1 完全走现有代码，行为和耗时与今天一致。只有 L2 是新增的执行路径。

### 3.2 L2 的判定信号

进入 L2 不新增一个独立的分类 LLM，而是复用已有信号，避免多一次往返。满足以下任一条件即进 L2：



1. `orchestrator.decompose` 返回 `is_simple=false` 且 `steps` 数量大于等于 2；

2. 计划里存在 `needs` 或 `produces`，即步骤之间有值依赖；

3. 计划里出现 `query_knowledge` 加 `analyze` 组合，即需要规范加数据的综合判断；

4. 现有 L1 执行后出现需要改策略的观察结果，比如查空、结果被 LIMIT 截断、字段不可达，这些信号在 L1 执行器内部抛出，由大脑接管而非直接回复用户。

前三条在规划阶段就能确定，属于 "规划即入 L2"。第四条是 "执行中升级到 L2"，保证本来以为简单、实际碰壁的题也能进入循环。


## 四、工具层：大小两层、全量盘点、统一落到 tools 目录

### 4.1 工具分两层：大工具优先，小工具纠偏

项目代码量很大，`agent.py` 约 248KB、`nl2sql.py` 约 405KB、`templatizer.py` 约 210KB，能复用的函数成百上千，不可能在方案里靠人工列全。工具层因此分两层设计。

**大工具是能力级工具**，一个工具对应一个完整子任务，输入一句自然语言子问题，内部编排多个函数，直接给出结果。查一次数据、查一次规范、取一批图、做一次综合分析，都属于大工具。大工具是大脑的默认选择，一条链式问题通常调几个大工具就够了。

**小工具是原子级工具**，一个工具只做一件确定性的换算或取值，不连库或只查极小的确定性数据。把 “2026 年第 31 周” 换算成起止日期、把桩号换算成米、把病害类型中文名翻译成代码、从第一步结果里取出峰值周标签、把峰值标签回填进第二步问题，都属于小工具。这些函数现在散落在 `parsers.py`、`nl2sql.py`、`agent.py`、`calibrate.py`、`sql_engine.py` 里，大工具内部已经在用，但大脑调不到。

**调用纪律是大工具优先、小工具纠偏。** 常规路径执行器只调大工具，让大工具内部完成全部换算，不产生大脑往返。只有当门控判定大工具观察异常，比如空结果、结果被截断、回填的时间区间和第一步峰值对不上、病害类型没解析出来，才调大脑，由它指定对应的小工具把关键中间量算准，再带着正确中间值重新调大工具。

以 “哪周泛油最多、列出那周明细” 为例，正常路径下第二步 `query_data` 大工具内部会用 `parsers._iso_week_range` 把峰值周换算成区间。一旦换算错，比如把第 31 周填成了当前周，门控不会接受错误结果，而是调大脑选 `retry_atomic`，由执行器先调小工具 `iso_week_range` 传入 “2026 年第 31 周” 拿到准确起止日期，再调小工具 `fill_placeholder` 把区间填进第二步冻结子问题，最后用确定的子问题重调 `query_data`。大工具解决绝大多数题，小工具提供出错时逐层定位和精确重算的抓手。

### 4.2 工具统一契约

所有工具无论大小都通过注册表登记，注册表按名称查找和调用。大工具和小工具的登记字段相同，`run` 的返回结构不同。

登记字段统一为：



```
{

&#x20; "name": "工具名，英文蛇形，全局唯一",

&#x20; "layer": "big 或 atomic",

&#x20; "domain": "能力域，如 data、knowledge、time、pile、enum、entity、field、coverage、sql、compose",

&#x20; "description": "说明工具能做什么、什么时候用、什么时候不该用，供大脑选择",

&#x20; "input\_schema": { "type": "object", "properties": { }, "required": \[ ] },

&#x20; "wraps": "底层复用的现有函数定位，形如 模块.函数名:行号"

}
```

大工具的 `run` 返回观察结构，保证大脑每一步拿到的信息口径一致。



```
{

&#x20; "ok": true,

&#x20; "tool": "工具名",

&#x20; "summary": "给大脑看的一句话结论，不超过两百字",

&#x20; "data": {

&#x20;   "row\_count": 0,

&#x20;   "columns": \["列名"],

&#x20;   "preview\_rows": \[ { } ],

&#x20;   "produced": { "peak\_week": "2026年第31周" },

&#x20;   "truncated": false

&#x20; },

&#x20; "coverage": {

&#x20;   "asked\_range": { "start": "", "end": "" },

&#x20;   "actual\_range": { "start": "", "end": "" },

&#x20;   "empty": false

&#x20; },

&#x20; "error": null,

&#x20; "next\_hint": "当 ok 为 false 时，确定性地给出可尝试的下一步，供大脑参考"

}
```

`produced` 是大工具替大脑提取好的键值，对应现有 `produces` 机制。`truncated` 标明结果是否达到取数上限，是半月趋势那类题必须暴露的信号。`coverage` 把校准器的时间和桩号覆盖结论结构化带出，避免零结果矛盾回复。

小工具的 `run` 返回精简的原子结果，不包观察外壳。



```
{

&#x20; "ok": true,

&#x20; "tool": "工具名",

&#x20; "value": "换算或取值的直接结果，类型随工具而定，如区间对象、代码值、字符串、布尔值",

&#x20; "error": null

}
```

小工具必须是确定性的，同样输入永远同样输出，不在内部发起 LLM 调用。需要 LLM 推理的环节一律归到大工具，这样大脑每次调小工具都不产生额外的生成延迟。

### 4.3 大工具骨架

下表九类是大工具的初始骨架，给出每一类的底层复用点。它是起点不是全量，Codex 盘点时如果发现还有同一量级的完整子任务能力，例如元数据画像、跨库分解，按同样契约补充登记。



| 大工具名               | 职责                            | 底层复用                                                                     | 是否连库      |
| ------------------ | ----------------------------- | ------------------------------------------------------------------------ | --------- |
| `query_data`       | 按自然语言子问题查数据库，返回聚合结果或受控明细      | `agent._build_query_result`（第 1636 行），内部已含模板、Wren、LLM、校验、执行              | 是，走现有只读通道 |
| `query_knowledge`  | 查养护规范、定额、评定标准                 | `agent._answer_knowledge`（第 169 行）                                       | 否，走 RAG   |
| `fetch_images`     | 取某批病害的现场图片                    | `agent._image_result`（第 3472 行），底层经 `db_manager.fetch_seaweedfs`         | 是，只读图片    |
| `post_calc`        | 对前面已取回的小结果做求和、求差、占比、取最大、条件计数  | `agent._post_calc_payload`（第 2411 行），纯计算                                 | 否         |
| `analyze`          | 把数据和规范合在一起做综合判断与建议            | `agent._analysis_payload`（第 2328 行）                                      | 否         |
| `profile_metadata` | 表级、库级元数据画像和字段说明               | `generic.profiling_reply`、`metadata_service`                             | 是，只读      |

### 4.7 三类资产对象走同一个实体工具

病害表 `ai_problem` 只有 `routes_id` 和 `sections_id`，没有任何桥梁、隧道、边坡的资产 id 列，已经用 `SHOW COLUMNS` 实测确认。因此绝不能生成 `ai_problem.sections_id = 资产id` 这样的条件，资产表主键和路段 id 不是一回事，必然查空。正确关联链按资产类型分别取路段：桥梁表 `basic_facilities_bridges.sections_id`、边坡表 `basic_facilities_slope.sections_id` 直接存所属路段 id，隧道表 `basic_facilities_tunnels` 用 `belong_section_id`。工具先拿资产 id 查资产表得到所属路段 id，一座资产跨多个路段或带桩号区间时，再用路段 id 加桩号范围过滤病害表。

## 五、ReAct 大脑

### 5.1 大脑的定位：只做调度，不重复前置 LLM 的工作

在进入 ReAct 之前，现有流水线已经用四个专门的大模型把问题处理了一遍，而且每个都比通用大脑做得更专。大脑如果再做一遍意图理解、对话补全、任务拆解和问题改写，只会更慢更差。Codex 阶段二实测的三个故障都源于此：链式第二步漏掉"泛油"、把"泛油明细"改写成"所有病害"导致 500 条与 401 条对不上、最后渲染时编造不存在的桩号和图片名。这些工作本不该由大脑做。

进入 L2 时，下面四份产物已经产出并冻结，大脑只读不写。

| 前置环节 | 提示词与调用点 | 冻结产物 | 大脑如何使用 |
| --- | --- | --- | --- |
| 长对话理解 | `dialogue_understanding.md`，`memory._llm_complete_followup` | 独立成句的 `full_question`、关系类型、继承或丢弃的条件 | 作为本次唯一的完整问题，不再补全、不再继承上轮条件 |
| 意图分类 | `intent.md`，`intent.classify_intent` | 意图大类 | 决定走哪类工具，不重新判断意图 |
| 任务规划 | `planning.md`，`orchestrator.decompose` | `final_goal` 和 `steps`，每步含 `action`、`purpose`、`query`、`produces`、`needs`、`wants_images` | 作为执行剧本，每步调哪个工具、子问题怎么写、产出什么键全部照此执行 |
| 语义规划 | `nl2sql.build_query_plan` | 字段、过滤条件、时间槽、分组度量的结构化 spec | 透传给 `query_data`，不重新选表选列 |

问题优化器 `optimize_question.md` 性质不同，它是在结果被校验判为答非所问后才带着失败原因补口径的事后纠错器，不是每次都跑。大脑不承担这个职责，需要重规划时把它作为一个纠偏动作调用。

据此明确大脑的边界。大脑不做意图分类、不做长对话补全、不重新拆步骤、不改写任何一步的子问题、不写 SQL、不自己换算时间范围、不造句明细。大脑只做四件事：按计划顺序推进、用前序产出值填充依赖、读取观察判定当前步骤是否成功、在观察异常时从一组有限的纠偏动作里选一个。最终答复由真实观察拼接，明细行只来自工具返回。

### 5.2 执行节奏：计划确定性推进，观察门控，异常才调大脑

大脑不再每一轮都被调用。典型链式题如果计划顺利，整个执行过程零次大脑大模型调用，由代码按计划确定性跑完，这与现有静态循环的速度一致。只有某一步的观察被判定为异常时，才调用一次大脑，让它在有限动作里做选择。

正常路径对每一步按固定顺序确定性处理。

1. 检查这一步 `needs` 引用的键是否都已在黑板中。依赖未就绪时不执行，进入门控。
2. 工具由这一步的 `action` 直接映射，`query_data`、`query_knowledge`、`query_images`、`post_calc`、`analyze` 各自对应一个大工具，工具选择不交给模型。
3. 子问题文本直接取这一步冻结的 `query`，用黑板里的值做 `{{key}}` 回填。路线、病害类型、时间、桩号、设备条件天然保留，模型没有改写子问题的入口。
4. 执行大工具，取得观察。
5. 按这一步的 `produces` 和 `from_column` 从结果列确定性提取产出值，写入黑板，供下一步回填。

每一步执行后经过一个确定性的观察门控，门控不调用模型，只按观察字段判定。

| 观察状态 | 判定条件 | 门控动作 |
| --- | --- | --- |
| 成功 | `ok` 为真、有行、该产出的键都取到 | 直接推进下一步，不调大脑 |
| 缺依赖 | 回填时报 `missing_values`，或 `produces` 没取到值 | 调大脑处理取值与依赖 |
| 范围越界或空结果 | `coverage.empty` 为真，问的时间、桩号或枚举落在真实覆盖外 | 调大脑在相邻范围重查与追问之间选择 |
| 结果截断 | `truncated` 为真，命中取数上限 | 优先确定性改聚合重查，必要时调大脑确认维度 |
| 字段不可达 | 字段触达判定字段或对象不存在 | 调大脑决定换字段、换对象或追问 |
| 工具异常 | 大工具返回异常或澄清 | 调大脑决定换小工具、追问或回退 |

只有门控判定为异常时才调用大脑。大脑拿到的是冻结计划、当前步骤、观察到的具体异常和一组允许的纠偏动作，输出只能是其中一个动作加结构化参数，不允许输出新的子问题文本。允许的纠偏动作固定如下。

| 纠偏动作 | 含义 | 子问题文本来源 |
| --- | --- | --- |
| `retry_atomic` | 调时间、桩号、枚举、取值类小工具把中间量算准，修正黑板的值后重跑当前步 | 仍是当前步冻结的 `query`，只改回填值 |
| `retry_adjacent_range` | 用 `check_coverage` 给出的真实相邻范围重查一次 | 当前步 `query` 加确定性范围槽，不造句 |
| `rerun_aggregate` | 截断时把明细改成 `GROUP BY` 或 `COUNT` 聚合 | 由代码基于语义 spec 改写，不造句 |
| `skip_step` | 该步查空且后续步骤不依赖它，常见于分析题缺少某类数据 | 不产生子问题 |
| `replan` | 计划本身缺步或维度错，调用问题优化器或规划器重规划一次 | 由 `optimize_question`、`orchestrator` 专门生成 |
| `ask_user` | 对象、时段或枚举确实不存在，带真实覆盖说明终止 | 不产生子问题 |
| `abort` | 无法自洽，放弃 ReAct 回退静态执行器 | 不产生子问题 |

关键约束是所有重查的子问题都来自冻结计划或代码的确定性变换，大脑只能选择动作，不能重写问题。需要重新规划时调用的是专门的规划器和优化器，大脑不自己改步骤。Codex 阶段二已经写的 `_apply_current_plan_step` 强制采用计划步骤问法、`_grounded_answer` 用观察摘要拼接答案，正是这个方向，方案把它们从临时补丁升级为默认且唯一的执行路径。

### 5.3 工作记忆黑板

新增一个 `ReactBlackboard` 对象，在单次请求内存活，分冻结输入和运行状态两部分。

冻结输入在进入循环时写入，运行中不可变，包含 `full_question`、`intent`、`final_goal`、完整 `steps`、语义 `spec`。运行状态随执行更新，包含 `values` 跨步骤传递的键值，对应 `produces` 和 `needs`，如 `peak_week`；`observations` 已执行步骤的工具名、入参摘要、观察摘要；`used_plan_steps` 已完成的计划步骤；`facts_cache` 校准事实和实体解析结果。

黑板直接复用现有 `_handle_composite` 里的 `task_results` 和 `produced` 思路，只是从局部变量提升为门控和大脑都能读的显式状态。缓存纪律是同一个语义规划不重复调用 `build_query_plan`，同一条路线的覆盖事实不重复调用 `calibrate.route_facts`，这两个函数本身都带缓存，工具层确保跨步骤复用同一个上下文即可。黑板写入和第十节的过程事件共用一个出口，前端看到的步骤与后端状态完全一致。

### 5.4 大脑提示词：偏差处理决策器

`prompts/react_controller.md` 重写为偏差处理决策器。它不再每步被调用，只在门控报异常时调用一次。它的任务不是规划下一步，而是判断当前异常属于哪一类、应该用哪个纠偏动作，因此不需要看到完整计划让它自由发挥，只需要看到当前步骤、观察异常和允许动作。它严格输出 JSON，不输出 Markdown，不输出任何新的查询句子。提示词主体如下，可直接作为文件内容落地。

```
[system]
你是道路巡检养护问答系统的执行调度器。任务计划、每一步的子问题、依赖键都已经在你之前确定并冻结，你不负责规划，也不负责改写问题。

正常情况下系统按计划逐步执行，不会调用你。只有某一步的观察出现异常时，才会把当前步骤和异常交给你。你要做的是判断异常类型，从允许的纠偏动作里选一个，让系统把这一步纠正后继续。

你不能做的事：
1. 不能改写任何一步的子问题，不能增删路线、病害类型、时间、桩号、设备条件。
2. 不能自己拆步骤或调整步骤顺序，计划有问题只能选择 replan，由专门的规划器重规划。
3. 不能写 SQL，不能自己换算周、月、桩号区间，这些由确定性小工具完成。
4. 不能编造数字、桩号、图片名，最终明细只来自工具返回的真实行。

允许的纠偏动作只能取以下之一：
- retry_atomic：中间值算错或没取到。用指定小工具重算后重跑当前步，子问题不变，只修正回填值。
  小工具限于 time_convert 周月季度转区间、pile_convert 桩号转米、enum_map 类型名转码、chain_value 从结果列取值或回填。
- retry_adjacent_range：时间或桩号问在真实覆盖外。用 check_coverage 的真实相邻范围重查一次。
- rerun_aggregate：结果被取数上限截断，不能做全局排名。改为聚合查询重查。
- skip_step：该步查空且后续步骤不依赖它，跳过。
- replan：计划缺步或度量维度错误。交给规划器重规划，你不自己改。
- ask_user：对象、时段或枚举确实不存在，带真实覆盖范围向用户说明并终止。
- abort：无法自洽，回退原有静态执行器。

判定原则：
1. 周名、月名、桩号、枚举代码对不上，或前一步该产出的键为空，选 retry_atomic。
2. 空结果且 coverage 显示真实范围与提问范围不重叠，先看能否用相邻范围重查，能则 retry_adjacent_range，
   用户确实问了库里没有的对象或时段则 ask_user。
3. truncated 为真选 rerun_aggregate，不允许直接回答数据不全。
4. 一步只允许纠偏重试一次，同一类异常第二次仍失败时，在 ask_user 和 abort 之间选择，不反复重试。
5. 桥梁、隧道、边坡的查询若关联链错误，选 retry_atomic 调实体解析小工具取所属路段，不拿资产 id 直接比病害表 sections_id。

只输出一个 JSON 对象，不要输出解释文字：
{
  "thought": "当前异常属于哪一类，一句话",
  "action": "retry_atomic / retry_adjacent_range / rerun_aggregate / skip_step / replan / ask_user / abort",
  "atomic_tool": "action 为 retry_atomic 时填 time_convert / pile_convert / enum_map / chain_value，否则留空",
  "fix_values": {"要修正的回填键": "修正方式或来源列"},
  "message": "action 为 ask_user 或 abort 时填写给用户的说明，其余情况留空"
}

[user]
最终目标：{goal}
当前步骤：{current_step}
当前步骤冻结子问题：{frozen_query}
观察异常：{observation_error}
真实覆盖与已取键值：{coverage_and_values}
可用纠偏动作：retry_atomic、retry_adjacent_range、rerun_aggregate、skip_step、replan、ask_user、abort
```

### 5.5 输入输出契约与最终答案

进入 L2 时由代码组装冻结输入，包含补全后的完整问题、意图、最终目标、步骤序列和语义 spec，步骤里每一步的工具映射、子问题、依赖键、产出列都已确定。工具目录由注册表导出，进程启动时生成一次并缓存。

正常推进不调用大脑，门控异常才调用，调用时只传当前步骤、冻结子问题、观察异常、覆盖范围和已取键值，以及固定的纠偏动作清单，不传让模型自由重写计划所需的冗余空间。大脑返回的 JSON 只做动作枚举校验，动作非法或参数无法执行时，直接按 `abort` 回退静态执行器，不再把错误喂回让模型反复试。

最终答案分三类确定性生成。纯数据查询由各步骤已经生成的观察摘要拼接，结果卡片和明细只用工具返回的真实行与真实图片，这部分沿用现有 `result_summary` 和结果工作台。需要数据结合规范下结论的分析题，由 `analyze` 工具基于黑板上的真实数值生成，模型能使用的数字全部来自观察。确实缺信息时由 `ask_user` 给出真实覆盖说明。任何路径下大脑都不自由渲染明细，从而杜绝编造桩号和图片名。

### 6.3 规划器角色的变化

`orchestrator.decompose` 产出的 `steps` 在 L2 是冻结剧本，每一步的工具映射、子问题、依赖键、产出列都由它确定，执行器照此推进，大脑不增删、不重排、不改条件。规划器在 `planning.md` 里沉淀的峰值键命名、中文可读标签、`COUNT DISTINCT` 拆两步、同维度 `GROUP BY`、阈值直接 COUNT 等实测规则因此原样生效，不会在执行环节被大脑改写丢掉。

这不是回到规划即定死的老路。静态执行器的缺陷是查空、截断、越界后仍按原顺序硬走，新执行器在每步后加了观察门控。区别在于门控发现计划本身走不通时，不允许大脑在执行中临时改句子，而是用 `replan` 动作把失败原因交回 `optimize_question` 或 `orchestrator` 重新规划一次，规划仍归规划器，大脑只负责判定当前计划走不通并触发重规划。

### 6.4 确定性执行优先，大脑只处理偏差

正常路径不调用大脑。时间换算、桩号解析、枚举值校验、占位符回填、峰值键提取这些已有确定性函数的环节，由执行器和工具在内部完成，比如周数到日期区间的换算由 `query_data` 内部的语义规划和槽位处理完成，代码只看到结论。大脑只在门控判定观察异常、需要换一个方向时才介入，这是把大模型调用次数压到最低的关键。

## 七、关键场景的执行轨迹

### 7.1 链式题：哪个星期泛油最多，把那周明细列出来

执行器按计划推进第一步，工具映射为 `query_data`，子问题直接取计划里的“西乡段泛油按周分组统计数量，从多到少排序”，不经过大脑改写。工具返回观察，`produces` 按 `from_column` 取出 `peak_week` 的真实值，周名到起止日期的换算由工具内部按 ISO 周历完成，门控判定成功，这一步零次大脑调用。

第二步的依赖键已就绪，执行器用 `peak_week` 回填计划里第二步的冻结子问题“西乡段泛油在这一周的明细”，路线和泛油条件随计划原文保留，不会被改成所有病害。门控再次判定成功，进入确定性答案拼接，全过程不调用大脑。

只有当第二步观察出现空结果或区间对不上时，门控才调大脑，在 `retry_atomic` 和 `retry_adjacent_range` 之间选一个。第二步区间来自第一步真实结果，周数错位在工具层就被拦住，明细数与聚合数对得上。

### 7.2 零结果：问了库里没有的时段

`query_data` 返回 `coverage.empty` 为真，观察里同时给出真实覆盖范围，门控据此判定范围越界并调用大脑。大脑在 `retry_adjacent_range` 和 `ask_user` 之间选择，能用相邻有效周重查就重查一次，若用户确实问了库里没有的时段则选 `ask_user`，回复里只说清楚该时段无记录、数据实际覆盖到某日，不再拼接互相矛盾的全量统计。

### 7.3 半月趋势：避免拿截断明细排名

计划若把这一步拆成了查明细，工具观察返回 `truncated=true` 且行数等于上限，门控直接触发 `rerun_aggregate`，由代码基于语义 spec 把这一步改成按半月分组的聚合，不需要大脑造句。拿到每个半月的计数后再排序，最终答案基于聚合表而非前五百条明细。

### 7.4 桥梁资产：先解析再查

问“某座桥梁有多少处病害”。计划里的实体解析步骤由执行器确定性调 `resolve_entity`，或由 `query_data` 内部的实体解析直接完成，拿到桥梁 id、所属路段 id 关联链。随后查询的条件用所属路段 id 加桩号区间，而不是用桥梁 id 直接比 `sections_id`。关联链缺失或解析为空时门控才调大脑，选 `retry_atomic` 重取关联链或追问。这避免了旧配置里对有数据的桥说没有数据的假报警。

### 7.5 数据加规范：路况好不好、怎么养护

执行器按计划里“基本盘统计、严重程度统计、规范查询、综合分析”的顺序确定性推进，前三步分别由 `query_data` 和 `query_knowledge` 完成，最后 `analyze` 拿到黑板上全部真实数值和规范条款下结论。这条拆步经验由规划器在示例 2 里沉淀并冻结。某一步查空且后续不依赖时，门控调大脑选 `skip_step` 跳过，需要补维度时选 `replan`，执行器不自行增删步骤。

## 八、延迟控制

延迟是本项目反复强调的约束，大脑设计上做四层控制。



1. **分层路由把大脑挡在简单题之外。** L0 和 L1 不增加任何大脑 LLM 调用，现网多数高频问法是单对象单度量，走的仍是零次大脑的直出路径。

2. **大脑只在观察异常时调用。** 计划顺利时执行器按步骤确定性推进，零次大脑大模型调用；只有门控报空、截断、越界、缺依赖时才调一次。时间换算、字段触达、SQL 生成、纠错这些已有大模型调用维持现状，大脑不额外叠加。

3. **观察结果裁剪。** 喂给大脑的观察只含列名、前若干行、聚合值和覆盖摘要，明细行数受上限控制，控制输入 token。

4. **规划和事实只算一次。** 语义规划、实体解析、路线覆盖事实通过黑板跨步骤复用，`query_data` 每步不重复规划、不重复连库取同一条事实。

L2 典型链式题相比现状的额外开销，在计划顺利时为零，执行器只是把现有静态循环换成带门控的确定性推进，增加的是本地字段判断，不产生模型往返。以“先找峰值周再查明细”为例，现状是规划一次加两次数据查询，改造后顺利时仍是规划一次加两次数据查询，第二步区间正确和零结果自洽由确定性门控与工具保证；只有区间算错或查空时才多一次大脑纠偏调用，这一次调用换来的是自动改路线而非直接报错，属于必要成本。

## 九、护栏与失败处理



1. **步数上限。** 执行器按计划步数推进，单次请求计划步骤和纠偏重试合计不超过五步，由 `react_agent.run` 强制计数。每一步因门控触发的纠偏重试不超过一次，同一异常第二次仍失败就在追问和回退之间选择，不无限循环。超限用 `ask_user` 给出已查到的部分和卡点。

2. **只读白名单。** 所有工具最终都经过 `sql_engine.validate_sql`（第 175 行），只允许 SELECT 和 WITH，危险词拦截、表白名单、强制 `del_flag=0`、自动 LIMIT 全部保留，大脑无法绕过。

3. **JSON 解析容错。** 复用 `llm.chat_json` 的坏 JSON 重试和宽松解析；连续两次解析失败则降级到现有静态执行路径，不把解析错误抛给用户。

4. **工具不存在或入参非法。** 计划里的动作在注册表找不到，或入参不符合模式，属于计划错误而非模型可纠偏，执行器直接按 `abort` 回退静态执行器，不把错误喂回大脑反复试。

5. **工具执行异常。** 数据库异常、Wren 编译异常被捕获成 `ok=false` 的观察，附 `next_hint`，大脑据此换路径或追问，不让单次异常中断整个请求。

6. **数字自洽。** 最终答案由观察摘要确定性拼接，明细和数字只来自工具返回的真实行，大脑没有自由渲染入口；事后仍走现有 `_reflect_check_step` 做数字自洽校验，双层兜底。

7. **降级路径常驻。** 大脑不可用、超限、反复出错时，回落到现有 `_handle_composite` 静态执行或现有单查询路径，保证可用性不低于现状。

## 十、工作流过程实时可视化：让前端看到大脑在做什么

### 10.1 现状是过程数据已经有了，只缺实时通道

前端的 `api.chat`（`frontend/src/api.js` 第 22 行）是一次同步 POST，后端 `/api/chat`（`chat.py` 第 93 行）把完整 payload 一次性返回。等待期间前端只有一个三点跳动的 loading 动画（`ChatPanel.vue` 第 216 至 224 行），用户看不到系统正在做什么。

过程数据其实已经存在。后端在返回 payload 里带了 `process.steps`，复合题在 `agent.py` 第 2907 行组装，单查询在第 3860 行补一份单步记录，每一步含序号、类型、引擎、行数、图片数、子问题，复合题还带 `chain_values` 回填键值。前端在助手气泡下方渲染一个默认折叠的执行链路面板（`ChatPanel.vue` 第 137 至 165 行），另外还有一个查看思考过程的折叠框（第 166 至 170 行）。

所以可视化要补的不是数据采集，而是两件事：让过程在执行的同时推到前端，而不是等全部结束；把折叠面板升级成一条边执行边生长的实时时间线。已有的 `process` 结构、管线样式和字段命名全部复用。

### 10.2 目标：最终答案出现前，工作流一步步可见

用户点发送后，在最终答案出现之前，能看到系统正在理解问题、正在解析路线和周数、正在匹配模板或生成 SQL、正在执行、正在校验，链式题还能看到第一步算出峰值周、第二步用这个周换算区间再查明细。执行器每一步的动作和观察、大脑纠偏时的思考都即时上屏。回答结束后，时间线自动折叠成现在的执行链路面板，样式和历史回看保持一致。

### 10.3 传输方式：SSE 单向流，不引新依赖

新增 `POST /api/chat/stream`，用 FastAPI 自带的 `starlette.responses.StreamingResponse` 返回 `text/event-stream`，每一条事件是一行 `data: {json}`，以空行分隔。现有链路是同步函数，同步生成器在 Starlette 的线程池里迭代，业务函数无需改成 async。

过程是单向的服务端推送、一问一答，SSE 比 WebSocket 更轻，不需要握手和连接管理，也走标准 HTTP 和现有鉴权。轮询需要把任务状态和任务 id 落库，前端和后端状态会分裂，明显更重。

原有的同步端点 `POST /api/chat` 原样保留。L0 和 L1 简单题一两秒返回，可以继续走同步，SSE 被网关拦截或读取失败时前端自动回退同步，灰度和降级都有退路，不影响现有嵌入宿主。

### 10.4 后端：一个事件总线，上下文变量贯穿，业务逻辑零改动

新增 `app/services/event_bus.py`，提供 `emit_event(event)` 和一个请求级上下文变量。当前请求设置了回调时，事件被推给回调，没有设置时 emit 是空操作。这样同步通道和单测、脚本里直接调用 `handle_message` 的行为完全不变。

`handle_message` 增加一个可选的 `on_event` 参数，默认 None。流式端点先创建一个队列，把向队列写事件的回调放进上下文变量，然后在同一线程里照常调用 `handle_message`，最后用一个同步生成器把队列里的事件逐条读出来写成 SSE。

埋点放在现有节点上，不新增任何查询，不重复连库。归一化、意图分类、语义规划、模板命中、Wren 编译、SQL 执行、校验、结果汇总各发一条阶段事件，每个大工具和小工具开始与结束各发一条。`react_agent` 是主要事件源，确定性执行器每一步的动作和观察都发事件，门控触发大脑时再发思考和纠偏动作事件。

事件类型固定为七类，字段保持稳定：



| 类型          | 含义                                      | 关键字段                                          |
| ----------- | --------------------------------------- | --------------------------------------------- |
| phase       | 进入某个阶段，如理解、规划、选引擎、执行、校验、汇总              | title                                         |
| thought     | 大脑这一轮的推理，来自 react\_controller 的 thought | text                                          |
| action      | 决定调用的工具和入参摘要                            | layer、tool、sub\_question、values 引用            |
| observation | 工具返回的观察摘要，不推全量明细                        | ok、rows、produced、truncated、empty、duration\_ms |
| clarify     | 等待用户确认或选择口径                             | choose\_token、capability 概要                   |
| final       | 最终 payload 就绪                           | result\_id                                    |
| error、done  | 异常或正常结束                                 | message                                       |

每条事件带单调递增的 seq 和时间戳，前端按 seq 渲染，入参只推摘要，不推完整参数和明细。黑板和事件是状态与投影的关系，ReactBlackboard 每次写入只走一个出口，这个出口同时更新黑板并发出对应事件，前端收到的事件序列与后端黑板完全一致，不会出现两套口径。

### 10.5 前端：复用管线样式，新增实时时间线组件

`api.js` 增加 `chatStream(payload, onEvent)`，用 fetch 读取 `response.body` 的文本流并按 SSE 协议解析。EventSource 只支持 GET，而聊天接口要带 POST body，所以用 fetch 的 ReadableStream 读流，与现有 `request` 封装风格一致。

`ChatPanel.vue` 发送后，把原来的三点 loading 换成一个工作流时间线容器，监听事件逐条追加：phase 显示阶段标题，action 显示工具名、子问题和引用的回填键，observation 显示是否成功、行数、产出键值、是否截断或空结果，thought 折叠成次级灰色文字，正在进行的步骤显示加载图标。

大工具和小工具在视觉上分层。大工具是主步骤行，小工具纠偏是挂在主步骤下的子行，比如主步骤查明细时，下面挂一行 “周名转区间，2026 年第 31 周换算为 7 月 27 日到 8 月 2 日”，让用户清楚看到是哪一步把区间纠正了。收到 final 事件后，前端把累积事件直接映射成现有 `process.steps` 结构，时间线自动折叠成现在的执行链路面板，最终气泡和结果工作台照常渲染。实时态和历史态是同一个组件、同一份数据。

### 10.6 噪声、延迟与信息边界

事件只推过程骨架，不推 SQL 全文和明细数据，SQL 仍在结果工作台查看，需要排查时由后端调试开关决定是否推送完整 SQL。L0 和 L1 简单题的事件可能在几十毫秒内连续到达，前端把同一阶段的开始和结束合并成一条完成态，避免闪烁。思考内容默认折叠，沿用现在查看思考过程的处理方式，不把完整推理直接铺开。事件里只出现实体标准名、时间区间、行数、回填键值，不出现连接串、密钥等敏感信息。

### 10.7 兼容与降级

同步端点和流式端点并存，前端优先尝试流式，读取失败或宿主不支持时回退同步，用户无感。历史会话从本地存储读取，没有事件流，仍用已经保存的 `process` 字段渲染，回看体验不回退。事件总线在没有回调时全部为空操作，所有既有测试和脚本直接调用 `handle_message` 的行为不变。

### 10.8 落地顺序与验收

后端先做事件总线和 SSE 端点，用命令行对一条链式题确认能按序收到完整事件，再做前端时间线组件。验收标准：链式题能实时看到第一步查峰值周、小工具换算区间、第二步查明细逐条出现；简单题时间线快速完成且不闪烁；断流自动回退同步，最终答案、执行链路、历史回看与改造前一致。

## 十一、分阶段落地

### 阶段一：Codex 盘点工具并落地 tools 目录，不接入执行路径

按 4.6 的任务让 Codex 建立 `tools/` 目录，全量盘点大工具和小工具并登记，导出 `catalog.json`。每个工具单独写一个只读验证脚本，确认 `query_data` 能调通 `_build_query_result` 并返回标准观察结构，时间、桩号、枚举、回填、取值五类小工具和直接调用原函数结果一致，`resolve_entity` 对路线、桥梁、隧道、边坡各返回正确关联链，`check_coverage` 能复现时间和桩号覆盖结论。此阶段不改主流程，被包装函数零改动，风险为零。

验收标准：在 backend 目录用临时脚本直接调每个工具，入参出参与原函数一致，`catalog.json` 覆盖 4.3 和 4.4 全部种子函数并补齐同域函数，脚本用完即删。

### 阶段二：计划确定性执行器和偏差大脑跑通复合题

新建 `react_agent.py` 和偏差决策版 `react_controller.md`，在 `_handle_composite` 增加分支，让多步链式题走带门控的计划执行器，工具和子问题照冻结计划推进，只有观察异常才调大脑，静态循环作为降级。先用“哪周泛油最多并列出明细”一条题打通两步确定性推进和值引用，再人为构造一次区间错位，验证门控触发 `retry_atomic` 后能回到正确结果。

验收标准：链式题顺利时零次大脑调用，第二步区间与第一步峰值周一致，周数正确，明细数和聚合数对得上，子问题不丢失泛油和路线条件；人为制造异常时门控能调大脑并在有限动作内纠偏。

### 阶段三：工作流过程实时可视化

新建 `event_bus.py`，在 `handle_message` 加 `on_event` 可选参数并在现有节点埋点，新增 `POST /api/chat/stream` 用 StreamingResponse 推 SSE；`react_agent` 每一步的动作和观察、每次大脑纠偏的思考都走黑板唯一出口同时发事件。前端新增 `chatStream` 和工作流时间线组件，替换等待时的三点动画，结束后把累积事件折叠成现有执行链路面板。同步端点和历史消息渲染保持不变。

验收标准：命令行对链式题能按序收到 phase、action、observation、final 事件；前端实时看到第一步查峰值周、小工具换算区间、第二步查明细逐条出现；简单题事件合并不闪烁；断流自动回退同步，最终答案和执行链路与改造前一致。

### 阶段四：观察信号驱动改策略

在 `query_data` 观察里补 `truncated` 和 `coverage` 两个信号，接入半月趋势聚合修正和零结果重查，修复 `calibrated_reply` 矛盾回复。

验收标准：半月趋势题用聚合而非明细排名；零结果回复不再自相矛盾；问错时段能给出真实覆盖范围。

### 阶段五：全资产与综合分析

打通桥梁隧道边坡的实体解析关联链，覆盖数据加规范的分析题。用 `docs/` 已有的九套测试题回归，重点是高发桩号、固定长度区间、时间趋势三类含动态决策的题。

验收标准：九套题中涉及链式、聚合、零结果、跨资产的题目全部走对路径，简单题耗时和结果与改造前一致。

### 阶段六：观测与调优

在日志里记录每次大脑的思考、动作、观察摘要和步数，与前端实时事件共用同一出口，沉淀失败案例用于收紧提示词，按实际分布调整步数上限和观察裁剪行数。

## 十二、测试验收

### 12.1 功能验收



1. L0 和 L1 题目结果与改造前逐字节一致，不产生额外大脑调用。

2. L2 链式题第二步时间或对象条件来自第一步真实产出，无写死日期。

3. 零结果题目回复自洽，不出现 "无数据" 与 "实际有 N 处" 并存。

4. 全局排名题使用聚合，观察 `truncated` 为真时门控确定性触发聚合重查，不依赖模型自觉。

5. 桥梁隧道边坡查询走所属路段关联链，不出现假零结果。

6. 超过五步或信息不足时走 `ask_user`，不硬答、不编造。

7. L2 题目在答案出现前能实时看到阶段、工具、观察逐条出现，大小工具分层展示，结束后折叠成执行链路；SSE 不可用时自动回退同步，历史消息仍能从已保存的 `process` 渲染出链路。

## 十三、与既有方案的关系

本方案不替代 `多步推理链式依赖整改方案.md`、`链式复合问题修复方案.md`、`周数计算模式不一致与链式复合问题执行修复方案.md` 中已经落地的规则，那些规则沉淀进了 `planning.md` 和 `orchestrator.py`，改造后作为冻结计划和工具内确定性逻辑继续生效。通用校准器也不取消，而是从独立拦截器变成大脑可调用的 `check_coverage` 工具，只对最终计划给出的具体时间、桩号、枚举范围做确定性核对，不再按场景关键词命中。字段触达和跨表派生字段的既有改造保持不变，对应能力收进 `ground_fields` 和 `query_data` 工具内部。

一句话总结：前置的对话理解、意图、规划、问题优化由专门的大模型一次性完成并冻结，执行器负责按计划把每一步做对，观察门控负责判断这一步是否成功，大脑只在出现偏差时从有限纠偏动作里选一个。计划顺利时零次额外大脑调用，规划归规划器、执行归工具、偏差归大脑，现有厚链路全部复用，这是在不推倒重来、不拖慢简单题的前提下，让智能体真正具备边做边想能力的最小改造路径。
