# 多步推理问题的智能处理方案

> 场景："西乡段的路况好不好？不好的话该如何养护，重点养护哪些路段？"
> 特点：有依赖关系，不是拆成几个子任务并行跑，而是一步一步来，每一步根据结果决定下一步。

---

## 一、这个问题难在哪？

```
西乡段的路况，好不好？不好的话该如何养护，重点养护哪些路段？
```

**这句话里有三层：**
1. **判断：** 路况好不好？（先查数据）
2. **条件分支：** 如果不好，该怎么养护？（查规范）
3. **具体落地：** 重点养护哪些路段？（结合数据+规范）

**关键是：这三步是有依赖的！**
- 必须先知道"好不好"，才知道要不要查规范
- 必须先知道"哪些路段病害多"，再结合规范判断"哪些要重点养护"

不是拆成几个子任务并行跑就行的。

---

## 二、智能的处理流程

### 第一步：理解用户问题的结构

用户要的是：
1. 先判断路况好不好
2. 如果不好，给养护建议
3. 还要指出具体哪些路段要重点养护

**不是一个简单的SQL查询，是一个完整的分析过程。**

---

### 第二步：先查数据，判断路况好不好

**查什么？**
- 总病害数量
- 病害密度（处/公里）
- 病害类型分布
- 平均面积
- 各路段的病害分布

**判断逻辑（给LLM看）：**
> 基于以下数据，判断西乡段的路况好不好：
> - 病害总数：911处
> - 病害密度：178.6处/km
> - 平均面积：61.7㎡
> - ...

**输出：**
> 西乡段路况**比较严重**：
> - 病害密度高达178.6处/km，远高于一般水平
> - 单处平均面积61.7㎡，说明病害规模不小
> - 未识别类型占41.4%，说明AI识别也不准

---

### 第三步：如果不好，再查养护规范

**判断：** 路况不好 → 需要查养护规范

**查什么？**
- 路面病害养护标准
- 什么情况下需要重点养护
- 不同类型病害的处理优先级

**给LLM看：**
> 根据养护规范：
> - 病害密度超过100处/km 属于"严重"等级，需要优先处理
> - 大面积病害（>50㎡）优先级高于小面积
> - 未识别病害需要先人工复核，再处理

---

### 第四步：综合分析提示词（通用版，直接抄到 prompts/analysis.md）

**这不是只分析"路况好不好"，是通用的专家分析提示词，覆盖所有业务场景：**

```markdown
[system]
你是道路巡检养护领域的资深专家。
你要基于"数据查询结果"和"知识库规范/标准"，回答用户的问题。
你不是简单罗列数据，要做专业的分析和判断。

你能分析的角度（根据用户问题选对应的角度）：

【数据统计类】
- 数量/规模：有多少？占比多少？
- 分布情况：集中在哪里？哪条路多？哪段路多？
- 排名对比：哪个最多？哪个最少？排个序
- 变化趋势：越来越多？越来越少？涨得快还是慢？

【判断评估类】
- 好坏判断：路况好不好？严不严重？靠谱吗？
- 优先级判断：先做什么？后做什么？重点在哪？
- 原因分析：为什么会这样？是什么导致的？

【建议方案类】
- 养护建议：应该怎么处理？
- 资源建议：钱/人力应该投在哪里？
- 后续建议：下一步应该做什么？

硬规则：
1. 先直接回答用户的问题，不要绕
2. 每个结论都要有数据或规范支撑，不要空泛
3. 如果数据不足或信息不够，就如实说，不要瞎编
4. 分点说清楚，不要一大段
5. 用中文，口语化，像专家在跟人解释

[user]
用户问题：<<question>>

数据查询结果：
<<data_result>>

知识库/规范：
<<knowledge_result>>

请基于以上信息，回答用户的问题，做专业分析。
```

**为什么这么写？**
- 不写死"必须分析路况好不好"
- 列了所有可能的分析角度，LLM根据用户问题自己选
- 不管用户问什么，都能套用：
  - "哪个路段病害多？" → 分布情况
  - "路况好不好？" → 好坏判断
  - "应该怎么养护？" → 建议方案
  - "病害是不是越来越多？" → 变化趋势

**这才是专家教授的思路：不背答案，懂方法，什么问题都能分析。**

**LLM输出：**
> **总体判断：** 西乡段路况较差，病害密度178.6处/km，远超"严重"标准（100处/km）。
>
> **养护建议：**
> 1. 优先处理大面积病害（>50㎡的有XX处）
> 2. 先人工复核未识别的377处病害，确认类型
> 3. 泛油属于轻微病害，可以延后处理
>
> **重点养护路段：**
> - K0+000~K0+500：病害最密集，有200处，优先处理
> - K2+000~K2+500：大面积病害集中，需要优先处置

---

## 三、现在的系统为什么处理不了？

**现在的做法：**
```
用户问题 → 拆分器拆成几个子任务 → 并行执行 → 拼结果
```

**问题：**
1. **没有"判断"这一步：** 不知道路况好不好，不知道要不要查规范
2. **没有依赖关系：** 所有子任务并行跑，不知道哪个要先做
3. **没有"综合分析"：** 只是把子任务结果拼起来，不会根据数据做推理

---

## 四、怎么改？

### 1. 拆分器提示词要加"多步推理"的识别（直接抄到 prompts/decompose.md）

```markdown
[system]
你是道路巡检智能体的查询任务拆解器。
你要把用户的问题拆成可独立执行的子任务，并明确子任务之间的依赖关系。

判断规则：
1. 如果问题是"先判断A好不好，不好的话再B" → 拆成两步：
   - task1：查数据判断A好不好
   - task2：如果不好，再查B
   - task3：综合分析（依赖task1和task2）

2. 如果问题是"数据 + 知识建议"混合 → 拆成两步：
   - task1：查数据
   - task2：查知识规范
   - task3：综合分析（依赖task1和task2）

3. 如果问题只是"列几个数据" → 不用拆，一个子任务就行

输出格式：
{
  "tasks": [
    {
      "id": 1,
      "type": "data",
      "question": "第一步要做什么"
    },
    {
      "id": 2,
      "type": "knowledge",
      "question": "第二步要做什么"
    },
    {
      "id": 3,
      "type": "analysis",
      "question": "综合分析",
      "depends_on": [1, 2]
    }
  ]
}

示例：
输入：西乡段的路况好不好？不好的话该如何养护？
输出：
{
  "tasks": [
    {"id": 1, "type": "data", "question": "西乡段的病害数量、密度、类型分布是多少？"},
    {"id": 2, "type": "knowledge", "question": "路面病害养护规范是什么？"},
    {"id": 3, "type": "analysis", "question": "结合数据和规范，分析西乡段路况好不好、该如何养护", "depends_on": [1, 2]}
  ]
}
```

### 2. 执行顺序是动态的

不是固定先跑哪个子任务，而是：
1. 先跑第一步（查数据判断好不好）
2. 根据结果决定：要不要查规范？
3. 再跑第三步（综合分析）

### 3. 最后一步是"综合分析"

把前面所有步骤的结果，都给最后一步的LLM，让它综合推理。

---

## 五、这就是智能体和流水线的区别

| 流水线（现在） | 智能体（改完） |
|-------------|-------------|
| 先拆好所有子任务 | 一步一步来，根据结果决定下一步 |
| 所有子任务并行跑 | 有依赖的串行执行 |
| 最后拼结果 | 最后综合分析，给出结论 |
| 机械执行 | 有判断、有推理 |

**核心区别：**
- 流水线：你说什么我做什么，一步一步按流程走
- 智能体：我理解你要什么，自己想办法分步完成

---

## 六、优先级

| 优先级 | 改动 | 效果 |
|--------|------|------|
| P0 | 加"先查数据再判断"的模式 | 能回答"好不好/严不严重" |
| P1 | 加"根据结果决定下一步" | 条件分支（不好才查规范） |
| P1 | 加最后一步综合分析 | 结合数据+规范给出结论 |
| P2 | 识别"重点养护哪些路段" | 能指出具体路段 |
