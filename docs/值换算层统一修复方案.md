# 值换算层统一修复方案（周数/枚举/实体/空间/单位等所有需要换算的场景）

> 背景：周数 bug 的根因是"用户说的第31周"和"SQL 里的 YEARWEEK(date, 1)"计算模式不一致，导致换算错误。类似的"需要换算"的场景还有很多：枚举值（国道→'0'）、实体（路线名称→路线ID）、空间（桩号 K1+200→1200米）、单位（平方米→平方分米）等。如果换算逻辑有问题，就会导致查询错误。
> 核心思路：建立统一的"值换算层"，把所有需要换算的场景集中管理，每个换算逻辑都要有明确的输入输出、测试用例和可追溯的换算过程显示。
> 生成时间：2026-10-12

---

## 一、问题诊断

### 1.1 什么是"值换算"

**定义：** 用户用自然语言描述一个值，系统需要把这个值转换成 SQL 能理解的条件。

**例子：**
- 用户说"第31周" → SQL 条件 `YEARWEEK(date, 3) = 202631`
- 用户说"国道" → SQL 条件 `level = '0'`
- 用户说"泛油" → SQL 条件 `damage_type = '10'`
- 用户说"宝安大道西乡段" → SQL 条件 `routes_id = '1b0b4a9f...'`
- 用户说"K1+200" → SQL 条件 `pile_distance = 1200`

**如果换算逻辑有问题，就会导致查询错误：**
- 周数模式用错（mode=1 vs mode=3）→ 查不到数据
- 枚举值映射错（国道→'1' 而不是 '0'）→ 查错数据
- 实体名称匹配错（西乡段→恒明珠的ID）→ 查错数据
- 桩号换算错（K1+200→1000米而不是1200米）→ 查错数据

### 1.2 严重问题：时间解析失败后用当前日期作为默认值

**案例：**
- 用户问："2026 年第 31 周是西乡段泛油数量最多的星期，时间范围是2026 年 07 月 20 日（周一）～2026 年 07 月 26 日（周日），把这周相关的数据全部列出来"
- 用户已经**明确说了时间范围是 7月20日～7月26日**
- 但是系统自动填充成了 **10月12日～10月19日**（当前日期所在的周）
- 通用算子的条件里写了：`collection_time between ['2026-10-12 00:00:00', '2026-10-19 00:00:00']`

**根因分析：**

1. **时间解析函数没有处理"第N周"的逻辑**：
   - `parsers.py` 里的时间解析函数只处理了"本周"、"上周"、"上个月"、"本月"等相对时间
   - 没有处理"第31周"这种绝对周数
   - 也没有处理"时间范围是X～Y"这种明确的时间范围说明

2. **时间解析失败后，用了默认值（当前日期所在的周）**：
   - 通用算子在生成时间条件时，没有从用户的问题里解析出时间范围
   - 解析失败后，错误地用了当前日期所在的周作为默认值
   - 这是一个非常严重的 bug，因为用户已经明确说了时间范围

3. **用户已经明确说了时间范围，系统应该优先用用户说的**：
   - 用户说"时间范围是2026 年 07 月 20 日（周一）～2026 年 07 月 26 日（周日）"
   - 系统应该直接用这个时间范围，不需要再解析"第31周"
   - 但是系统忽略了用户明确说的时间范围，还是用了默认值

**修复方案：**

1. **时间解析函数增加"第N周"的解析**：
   - 识别"第31周"、"2026年第31周"、"第31个星期"等说法
   - 用 ISO 8601 标准把周数转换成日期范围
   - 例子："2026年第31周" → 2026-07-27 ~ 2026-08-02

2. **时间解析函数增加"时间范围是X～Y"的解析**：
   - 识别"时间范围是..."、"时间是..."、"从X到Y"等说法
   - 直接用用户说的时间范围，不需要再解析
   - 例子："时间范围是2026年07月20日～2026年07月26日" → 直接用这个范围

3. **时间解析失败时必须报错，不能用默认值**：
   - 如果时间解析失败，应该返回 None 或报错
   - 不应该用当前日期作为默认值
   - 通用算子在生成时间条件时，如果没有 time_start 和 time_end，就不应该生成时间条件

4. **用户明确说了时间范围时，优先用用户说的**：
   - 如果用户的问题里有明确的时间范围（如"时间范围是X～Y"），直接用这个范围
   - 不需要再解析"第31周"或其他时间说法
   - 这是最可靠的时间来源

### 1.3 严重问题：校准（calibrate）回答前后矛盾

**案例：**
- 用户问："2026 年第 31 周...时间范围是2026 年 07 月 20 日～2026 年 07 月 26 日，把这周相关的数据全部列出来"
- 系统回答：
  - 前面说："您问的时间段没有数据"
  - 后面又说："实际范围内的统计：泛油 534 处；未识别类型 377 处，合计 911 处"
- **前后矛盾**：如果"没有数据"，那后面的统计是哪里来的？

**根因分析：**

1. **时间条件还是错的**（用了10月12日～10月19日）：
   - 校准（calibrate）从 `plan["slots"]["time_start"]` 读取时间条件
   - 但是时间条件解析失败，用了当前日期所在的周（10月12日～10月19日）
   - 数据覆盖范围是 7月15日～7月30日
   - 所以 `start (10月12日) > data_time_max (7月30日)` → 误判"您问的时间段没有数据"

2. **"实际范围内的统计"表述不准确**：
   - `_range_stats()` 函数查询的是**该路线所有时间的病害统计**（没有时间条件）
   - 不是"实际范围内"（数据覆盖范围内）的统计
   - 表述不准确，误导用户

3. **"全库病害"表述不准确**：
   - `calibrated_reply()` 里写的是"全库病害 911 条"
   - 但实际上是该路线（西乡段）的病害总数，不是全库的
   - 表述不准确

4. **校准逻辑应该在时间条件正确的前提下运行**：
   - 如果时间条件解析失败（用了默认值），不应该运行校准
   - 应该直接报错，告诉用户时间条件解析失败
   - 否则会用错误的时间条件运行校准，给出错误的结论

**修复方案：**

1. **修复时间条件解析**（见阶段 0）：
   - 时间解析失败时必须报错，不能用默认值
   - 用户明确说了时间范围时，优先用用户说的

2. **校准逻辑增加时间条件校验**：
   - 如果 `time_start` 或 `time_end` 是默认值（当前日期），不运行校准
   - 直接报错，告诉用户时间条件解析失败
   - 避免用错误的时间条件运行校准

3. **修正"实际范围内的统计"的表述**：
   - 如果是该路线所有时间的统计，应该说"该路线病害统计"
   - 如果是数据覆盖范围内的统计，应该加上时间条件
   - 表述要准确，不能误导用户

4. **修正"全库病害"的表述**：
   - 如果是该路线的统计，应该说"该路线病害"
   - 如果是全库的统计，才说"全库病害"
   - 表述要准确

5. **校准回答不应该前后矛盾**：
   - 如果说"您问的时间段没有数据"，就不应该再给出统计
   - 或者给出统计时，要明确说明是"该路线所有时间的统计"，不是用户问的时间段的统计
   - 避免前后矛盾

### 1.4 所有需要换算的场景分类

#### 分类 1：时间类

| 场景 | 用户输入 | SQL 条件 | 换算逻辑 | 已知问题 |

| 周数 | 第31周 | `YEARWEEK(date, 3) = 202631` | ISO 8601 周数计算 | **mode=1 vs mode=3 不一致** |
| 月份 | 2026年7月 | `date >= '2026-07-01' AND date < '2026-08-01'` | 月份第一天和下个月第一天 | 可能有边界问题（含不含当月最后一天） |
| 季度 | 2026年Q3 | `date >= '2026-07-01' AND date < '2026-10-01'` | 季度第一天和下季度第一天 | 季度定义可能不一致（自然季度 vs 财年季度） |
| 星期几 | 周一 | `WEEKDAY(date) = 0` 或 `DAYOFWEEK(date) = 2` | 星期几到数字的映射 | **WEEKDAY 和 DAYOFWEEK 不一致**（周一=0 vs 周一=2） |

| 相对时间 | 上周 | `date >= 上周一 AND date < 本周一` | 相对时间到绝对日期范围 | 相对时间的基准可能不一致（"上周"是上周一到上周日，还是最近7天） |
| 日期 | 2026年7月30日 | `DATE(date) = '2026-07-30'` | 日期字符串到 DATE 类型 | 时区问题（UTC vs 本地时间） |

## 二、解决方案

### 2.1 核心思路：建立统一的"值换算层"

**把所有需要换算的场景集中管理，每个换算逻辑都要有：**
1. **明确的输入输出定义**：输入是什么（用户说的自然语言），输出是什么（SQL 条件或值）
2. **标准的换算逻辑**：用统一的函数或方法进行换算，不要各处散落
3. **完整的测试用例**：每个换算逻辑都要有单元测试，覆盖常见情况和边界情况
4. **可追溯的换算过程**：在回答里显示换算过程（如"第31周（2026-07-27 ~ 2026-08-02）"），让用户确认
5. **统一的错误处理**：换算失败时要有明确的错误提示，不要静默答错

### 2.3 每个换算逻辑的标准实现

**以周数换算为例：**

```python
def week_to_date_range(self, year: int, week: int) -> tuple[date, date]:
    """把 ISO 8601 周数转换成日期范围。
    
    输入：year=2026, week=31
    输出：(date(2026, 7, 27), date(2026, 8, 2))
    
    标准：ISO 8601（mode=3），星期从周一开始，一年的第一周包含该年的第一个星期四
    """
    # 找到该年第一个星期四的日期
    jan4 = date(year, 1, 4)
    first_thursday = jan4 - timedelta(days=jan4.weekday() - 3)  # weekday(): 周一=0, 周四=3
    # 第一周的周一是第一个星期四往前推3天
    first_monday = first_thursday - timedelta(days=3)
    # 第 week 周的周一
    monday = first_monday + timedelta(weeks=week - 1)
    sunday = monday + timedelta(days=6)
    return monday, sunday

def week_to_condition(self, year: int, week: int, column: str = "collection_time") -> str:
    """周数 → SQL 条件。
    
    输入：year=2026, week=31, column="collection_time"
    输出："YEARWEEK(collection_time, 3) = 202631"
    
    注意：统一用 mode=3（ISO 8601），不要用 mode=1
    """
    yearweek = int(f"{year}{week:02d}")
    return f"YEARWEEK({column}, 3) = {yearweek}"
```

    # 2026年第31周：2026-07-27 ~ 2026-08-02

    assert monday == date(2026, 7, 27)

### 2.5 统一的错误处理

**换算失败时的处理：**

1. **枚举值找不到**：
   - 错误提示："没有找到枚举值'xxx'，可选值有：国道、省道、县道、乡道、村道"

2. **实体名称匹配不到**：
   - 错误提示："没有找到路线'xxx'，名字相近的路线有：宝安大道西乡段、宝安中心--恒明珠"
   - 不要静默答错（如随便选一个 ID）

3. **桩号格式错误**：
   - 错误提示："桩号格式'xxx'不正确，正确格式如：K1+200"
   - 不要静默答错（如返回0或None）

4. **单位不支持**：
   - 错误提示："不支持的单位'xxx'，支持的单位有：平方米、平方分米、平方厘米"
   - 不要静默答错（如直接用用户给的数值）

5. **换算结果超出合理范围**：
   - 警告提示："换算结果'xxx'超出合理范围，请确认是否正确"
   - 不要静默答错

## 五、风险与应对

| 风险 | 应对 |
|---|---|
| 值换算层的替换影响现有功能 | 先建立值换算层，然后逐步替换，每替换一个场景就运行回归测试 |
| 换算逻辑有 bug | 每个换算方法都要有完整的单元测试，覆盖常见情况和边界情况 |
| 枚举值映射不全 | 从字段目录的 code_map 读取映射，code_map 是从列注释自动生成的，应该是全的 |
| 实体名称模糊匹配错误 | 模糊匹配时返回最匹配的结果，并在回答里显示匹配过程，让用户确认 |
| 单位换算错误 | 先确认数据库的单位是什么，然后实现对应的换算逻辑；如果不确定，在回答里显示单位 |
| 换算过程显示太啰嗦 | 只在关键换算场景显示（周数、枚举、实体、桩号），简单换算（如比较符）可以不显示 |
| 回归测试失败 | 先检查是测试用例的预期值需要更新（因为换算标准变了），还是代码有 bug |

## 六、扩展：值换算层的其他应用

除了 SQL 条件生成，值换算层还可以用于：

1. **结果展示**：把数据库里的编码转换成中文（如 `level='0'` → "国道"）
2. **数据导出**：把数据库里的编码转换成中文，方便用户阅读
3. **数据校验**：校验用户输入的值是否在合理范围内
4. **提示词构建**：把用户输入的值转换成 SQL 条件，构建给 LLM 的提示词
5. **相似问法匹配**：把不同问法的值统一换算成标准格式，方便匹配

**核心原则：所有需要换算的场景都应该走统一的值换算层，不要各处散落，避免换算逻辑不一致导致的 bug。**
