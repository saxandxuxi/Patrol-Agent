## P0-补（评测发现，按优先级）

### 2e. "最值 + 定位"聚合查询（shape=top）【2026-09-14 评测 Q8 失败 / 2026-09-15 N10 复现】
- 现状：问"面积最大的是哪个桩号？面积多少？"被拆成 2 个子任务，返回 k0+647（错）+ total_area 569.78（错）。正确：最大 7.52㎡，并列 k0+886 / k0+865 / k0+302。
- 原因：MAX 聚合+定位桩号本质是单条 TOP 查询（`ORDER BY area DESC LIMIT 1~5`），但 parse_query_shape 无 top 形状 → 被 orchestrator 误判 composite → vanna/LLM 乱生成。
- 要求：`parse_query_shape` 识别"最大/最小/最多/最严重/之首/最密集"→ shape=top；builtin 模板生成 `SELECT ... ORDER BY <agg字段> DESC/ASC LIMIT N`；N 默认 1（并列时提示"存在并列，共 N 条"）。
- 验收：Q8 返回"最大 7.52㎡，桩号 k0+886（并列 k0+865/k0+302）"。

### 2h. NL2SQL 主体化改造（subject-aware）【2026-09-15 实测 MT1 失败】
- 现状：`build_template_sql` 硬编码 `FROM ai_problem p`（nl2sql.py:289），count/distribution/list/photo 模板**全部锚定病害表**；`parse_query_shape` 只识别"形状"，`parse_slots` 无"主体/对象"槽位 → 问非病害实体时模板答错或掉进 Vanna 乱生成。
- 实测：MT1"宝安大道西乡段这条路上，一共标了多少个里程桩点？" → 回答"共 911 处"（病害数），标准答案 **52 个桩点**。SQL=`COUNT(*) FROM ai_problem JOIN routes WHERE 西乡段`——SQL 正确生成但语义完全错位。
- 要求：
  1. `parsers` 新增 `parse_subject(message)`：主体词表 → {subject, main_table, join_chain}：
     - 病害/问题/坑槽/泛油等病害词 → disease（ai_problem → routes，**默认主体**）
     - 里程桩/桩点/桩号点位/标桩 → pile_point（sections_pile_detail → sections.route_id → routes）
     - 路段/几段/划分 → section（sections → routes）
     - 巡检/巡查/任务 → patrol（ai_maintain_patrol，经 disease.patrol_id 或 sections 关联路线）
     - 工单 → work_order（ai_work_order → ai_problem.problem_id）
     - 优先级：明确主体词 > 默认 disease；歧义时返回候选主体提示确认
  2. `build_template_sql` 重构为主体配置驱动：`shape(count/distribution/list) × subject(disease/pile_point/section/...)`；route 条件按主体 JOIN 链路生成（pile_point 走 sections.route_id，非 ai_problem.routes_id）
  3. Vanna/LLM 兜底 context 注入"候选主体表 + 关联链路"；`_schema_hint` 补"里程桩点/桩点→basic_facilities_sections_pile_detail"等业务词映射
  4. 新主体模板 SQL 校验（validate_semantics 按主体校验表名与条件）
- 验收：MT1 返回 **52 个**；新增"西乡段分几个路段"(1)、"一共几次巡检"(37) 等主体题可答。
- 注意：pile_point 桩号明细与病害所在路段同源（西乡 52/恒明珠 37），但桩号明细表是**全路网导入数据**（新唐线等路线），仅当路线名能 JOIN 到 sections 时才可信，无法 JOIN 时如实说明。 

### 2i. 图片查询链路缺口（2026-09-15 实测 P1/P4/P5/P7）【SeaweedFS 已有真实图片，可完整验证】
- 背景：SeaweedFS 已有图片（`102367594567/2026/07/30/*.jpeg` 200），图片链路具备验收条件。
- 实测失败：
  1. **P1 中文列别名导致取图失败**：Vanna 生成 `p.problem_url AS 病害原始照片`，`_image_result` 按 `row.get("problem_url")` 取不到列 → 911 条带 URL 的记录报"没有找到相关病害图片"（missing=0）。要求：`_image_result` 取列时兼容别名（遍历 row 键做去后缀匹配），或 image 意图强制 builtin 模板输出原始列名。
  2. **P4 白名单误杀**：Vanna 复杂 SQL 被校验判"ai_problem 不在白名单"（自相矛盾，ai_problem 是主表）→ 回复吞异常为"图片查询暂不可用"。要求：白名单校验对 ai_problem 常驻放行；异常必须走日志 + 返回可读信息。
  3. **P5 意图误判**："有图片的病害有多少条"是 count 统计，意图被 image 词命中误判为 image → 答"没有找到图片"。要求：意图分类中"数量/统计"优先级高于"图片"；或 image 意图内对 count 型问题转 data。
  4. **P7 跨意图吞并**："恒明珠的病害照片，以及GPS轨迹" intent=image 吞掉 GPS 子任务，SQL 变聚合非明细。要求：image 分支同样过 composite 拆解（图片+GPS 两路）。
- 验收：P1 返回图片列表；P4 返回最近图片且有日志；P5 返回数量；P7 返回图片+GPS 两段。

### 2j. 回复层数字丢失与形状降级（2026-09-15 实测 N2/N5/N10/N12/N13）
1. **否定/多指标只取第一列**：N2"不是泛油的病害有多少"SQL 已算出 `non_bleeding_count`（766），reply 却答总数 1702；N5"西乡段和恒明珠段各多少"SQL 双子查询，reply 只取 911。要求：回复摘要对多列/多行聚合结果逐项输出，不得只取第一。
2. **top 误写阈值**：N10"面积最大的桩号是哪个"Vanna 生成 `area > 5000`（把"最大"当成阈值，命中 5000 异常数据）→ 答"未查询到"。与 2e（shape=top）同源，2e 实现后复测。
3. **list 形状降级为 count**：N12"7月29日西乡段的泛油明细"shape=list 却生成 `COUNT(*)` 聚合（答"共1条明细"）。要求：list 形状强制明细 SELECT（builtin 模板接管，不交 Vanna）。
4. **分布类型标签丢失**：N13"各类型占比"SQL 按 pb.problem_type 分组，reply 全显示"未知类型 处"且数量空白。要求：distribution 结果在回复层按行重组"类型=数量（占比）"；类型为空时显示"未识别"。
- 验收：N2→766；N5→西乡911/恒明珠749；N10→7.52㎡/k0+886；N12→明细表格；N13→泛油等类型分布。

### 2g. 高难查询缺口（P1）【2026-09-14 评测第二轮 C1/D1/D2/M4】
四条缺口，按数据字段优先级排序：

1. **数值阈值条件（"面积>10㎡"）**：`parsers` 不识别"超过/大于/小于 X 平方米"数值范围槽位 → 条件静默丢弃（D2 实测答 534 而非 0）。
   - 要求：parse_slots 增加数值阈值槽位 `numeric_cond: {field, op, value}`（field∈{area, area_width, area_height, disease_length, pile_distance}，op∈{>,>=,<,<=}）；builtin 模板支持。
   - 验收：D2"面积超过10平方米的泛油"→ 0 处。
2. **JSON 字段查询（置信度）**：`pic_position` 内嵌 `{"confidence": 0.8, ...}`，parse 不识别"置信度"词，SQL 丢弃条件答全库（D1 实测 1702 而非 893/304）。
   - 要求：识别"置信度/可信度"→ `JSON_UNQUOTE(JSON_EXTRACT(pic_position,'$.confidence'))` 条件模板；`_vector_weight` 关键词表补"置信度"。
   - 验收：D1 返回 893 / 304。
3. **字段映射修正（device_code）**：Vanna 把"设备 102367594567"映射到 `vehicle_id`（错），实际字段是 `ai_problem.device_code`（M4 实测 0 而非 323/443）。
   - 要求：`_vector_weight`/schema RAG 字段字典中强化 `device_code` 与"设备号/设备/采集设备"的关联，排除 `vehicle_id` 误映射；builtin 模板支持按 device_code 分组。
   - 验收：M4 返回 6月323 / 7月443。
4. **聚合结果结论化（P2）**：C1 的 SQL 与数字正确（143/259），但回复只罗列数值，未给出"7月多，多116处"结论。
   - 要求：聚合类（对比/趋势/TOP）结果统一过 LLM 一句话结论模板。
   - 验收：C1 回复含"7月更多（259 vs 143），多 116 处"。

## P2（增强优化）

### 9. SQL 生成失败 → 追问澄清，禁止硬生成错误 SQL【2026-09-15 用户明确要求】

- 背景：`clarify.py` 已有 `ClarifyNeeded`（空间/对比/字段三类口径追问）且已接入条件缺失场景；但 **SQL 生成失败/校验失败/执行失败时仍吞异常硬答**：
  - P4 实测"图片查询暂不可用：没能生成满足条件的 SQL：ai_problem 不在白名单"——异常吞进 reply；
  - N10 实测"未查询到符合条件的数据"——SQL 错误（area>5000）但执行"成功"，静默给错结果；
  - D1/D2 实测"条件被丢弃仍答 1702/534"——`validate_semantics` 缺条件未触发追问。
- 要求（复用 `clarify.py`，新增 SQL 生成失败追问分支）：
  1. **全部引擎生成失败**（builtin=None 且 Vanna=None 且 LLM 失败）→ 抛 `ClarifyNeeded(kind="sql_failed", reason="没能在数据库里找到与您描述匹配的查询方式", keywords=..., lead=...)`，向用户说明"没查出来 + 可能是哪些条件没识别 + 请换个说法"，**绝不返回 0 行或假 SQL**；
  2. **`validate_semantics` 缺条件**（required_conditions 未覆盖）→ 同样追问缺失条件（如"您说的'置信度'我没法按字段过滤，请确认是 AI 识别置信度吗"），而不是丢弃条件硬答；
  3. **SQL 执行异常**（白名单误杀/语法错/表不存在）→ 日志记录 + 追问 + 可读错误信息，不把异常当 reply；
  4. **结果可疑但合法**（如 count=1702 且问题含强条件词）→ 由 LLM 判断是否向用户确认口径；
  5. 追问回复带 `answer_format="clarify"`，前端展示追问卡片与可选项按钮。
- 验收：
  - P4 → 追问"请确认查询范围"而非"暂不可用"；
  - N10 → 追问"您是要找面积最大的病害吗（我理解为 TOP 查询）"而非"未查询到"；
  - D1/D2 → 追问缺失条件而非丢条件硬答；
