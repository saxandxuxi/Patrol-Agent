# 结果校验与问题优化方案（完整版）

> 核心思路：不再追问用户，而是让 LLM 自己校验生成的结果是否答非所问，如果不对就自动优化问题、重新生成 SQL。

---

## 一、为什么要做这个

### 现在的问题

1. **追问体验差**：用户问"各月分别多少"，系统反问"按什么分"——用户得自己想怎么回答，体验很差
2. **追问了也不一定对**：用户回答了字段名，系统还是可能返回明细而不是分组统计
3. **规则识别能力有限**："各月"、"各类型"、"分别"这些词，规则识别不出来按什么分
4. **回复总结漏维度**：用户问了3个指标，表格里也都有，但回复只说了1个
5. **指标口径不对**：数是对的，但范围不对（比如把泛油的平均面积当成全部病害的平均面积）

---

## 二、新的流程

```
用户问题
   ↓
生成 SQL → 执行 → 拿到结果
   ↓
结果解读 → 生成回复
   ↓
【LLM 结果校验器】
   ├─ 对（答所问）→ 正常返回用户
   └─ 错（答非所问）→ 【LLM 问题优化器】
         └─ 优化问题 → 重新生成 SQL → 再执行
              ├─ 对 → 返回
              └─ 还错 → 返回当前结果 + 说明
```

**关键原则：**
- 最多重试 1 次，不能死循环
- 校验器只判断"答所问 vs 答非所问"，不判断 SQL 语法对不对
- 优化器只补全口径，不改变用户原始意图
- 优先单问题输出，最多拆成 2 个直观子问题

## 三、结果校验提示词（verify_answer.md）

```markdown
<role>
你是一名数据查询结果校验员，负责判断 SQL 查询返回的结果是否准确回答了用户的原始问题。
你不负责写 SQL，也不判断 SQL 语法对不对，只判断"问题和结果是否匹配"。
</role>

<instructions>
1. 阅读用户原始问题，理解用户到底要查什么。
2. 阅读生成的 SQL，看它查的是什么。
3. 阅读返回的结果（字段名 + 前10行数据），看它返回的是什么。
4. 阅读最终回复总结，看它说了什么、漏了什么。
5. 判断：结果是不是用户要的？
6. 如果不是，指出问题出在哪一步。
</instructions>

<constraints>
1. 只判断"答所问"还是"答非所问"，不判断 SQL 语法对错。
2. 空结果（0行）不算错，可能确实没数据。
3. 行数多不算错，用户要明细就是多行。
4. 必须输出 JSON 格式，不要输出其他内容。
5. 你的判断会决定要不要重新生成 SQL，所以要准确。
</constraints>

<check_rules>
按以下规则逐条检查：

【检查1：聚合 vs 明细】
- 用户问"有多少 / 数量 / 总数 / 多少处 / 多少条" → 结果应该是聚合值（一个数或一行）
- 用户问"有哪些 / 列出 / 明细 / 都有什么" → 结果可以是明细（多行）
- 如果用户问聚合，结果返回了几百行明细 → 错，是"没聚合"问题

【检查2：分组识别】
- 用户说"分别 / 各 / 按...分 / 各...的" → 应该有 GROUP BY，结果应该是分组后的聚合值
- 如果用户说"分别"，但结果是一个总数 → 错，是"没分组"问题
- 如果用户说"按类型分"，但 SQL 里没有 GROUP BY → 错，是"分组维度识别错"问题

【检查3：字段匹配】
- 用户问题里提到的关键词，对应的字段有没有出现在 SQL 里？
- 比如用户说"面积大于5"，SQL 里有没有 area > 5？
- 用户说"7月"，SQL 里有没有时间过滤？
- 如果用户提到的关键条件 SQL 里没有 → 错，是"漏条件"问题

【检查4：主体匹配】
- 用户问的是"病害数量" → 查的应该是 disease 模型
- 用户问的是"资产数量" → 查的应该是 asset 模型
- 用户问的是"巡查任务" → 查的应该是 patrol 模型
- 如果用户问 A，查的是 B → 错，是"主体错"问题

【检查5：单位匹配】
- 用户问"多少公里 / 长度" → 结果应该是长度单位（km/米）
- 用户问"多少处 / 数量" → 结果应该是个数
- 用户问"多少平方米 / 面积" → 结果应该是面积单位
- 如果单位不对 → 错，是"度量错"问题

【检查6：维度完整性】
- 用户问了几个维度/指标？（比如"总数、泛油数、平均面积"三个维度）
- 结果表格里有几列？
- 最终回复总结里说了几个？
- 如果用户问了3个维度，回复只说了1个 → 错，是"漏维度"问题
- 注意：SQL是对的，数据也都查出来了，就是总结的时候漏说了

【检查7：指标口径一致性】
- 用户问的"平均面积"是全部病害的平均，还是某种病害的平均？
- 用户问的"数量"是全部病害数，还是某种病害的数量？
- SQL 里算的指标，和用户要的指标，口径范围对不对？
- 如果数是对的，但范围不对（比如把泛油的平均面积当成全部病害的平均面积） → 错，是"指标口径错"问题

【检查8：推理/结论是否到位】
- 用户问的不是单纯查数据，而是要"分析/判断/结论"的问题
- 这种问题不能只列数据，要给出推理和结论
- 比如：
  - "是A还是B？" → 要对比A和B，给结论：是A/是B/两者都有
  - "为什么会这样？" → 要列可能原因，说明哪个是主要的
  - "好不好？" → 要给个判断：好/一般/较差/严重
  - "应该怎么做？" → 要给具体建议：先做什么，后做什么
- 如果用户问的是需要"推理/结论"的问题，但回答只列了数据，没给结论 → 错，是"推理不到位"问题
</check_rules>
```

## 五、回复总结改造：_ensure_all_values_reported 支持多行多列

### 现在的问题

现在的 `_ensure_all_values_reported` 兜底，只处理**单行多列**：
- 只有一行（单行）
- 有多个数值列
- 检查每个数值有没有在回复里出现

但遇到**多行多列**（两条路线 × 三个维度）就跳过了：

| 路线 | 病害总数 | 泛油数量 | 平均面积 |
|------|---------|---------|---------|
| 西乡段 | 911 | 534 | 61.7357 |
| 恒明珠 | 749 | 402 | 54.6556 |

行数=2 → 直接跳过，没做兜底 → 回复总结容易漏数。

---

### 改造方案

**改成支持两种情况：**

#### 情况1：单行多列
- 检查每个数值列有没有报
- 比如：总数=911，泛油=534，平均=61.7 → 三个数都要说出来

#### 情况2：多行多列
- 检查每个"行×列"的组合有没有报
- 比如：
  - 西乡段的病害总数 → 报了没？
  - 西乡段的泛油数量 → 报了没？
  - 西乡段的平均面积 → 报了没？
  - 恒明珠的病害总数 → 报了没？
  - 恒明珠的泛油数量 → 报了没？
  - 恒明珠的平均面积 → 报了没？
- 缺哪个补哪个

---

### 改造后的兜底逻辑

```python
def _ensure_all_values_reported(reply: str, result: dict[str, Any]) -> str:
    rows = result.get("rows") or []
    if not rows:
        return reply
    
    labels = result.get("metric_labels") or {}
    missing: list[str] = []
    
    # 多行多列：每个"行×列"组合都检查
    for row_index, row in enumerate(rows):
        # 行的标签（比如路线名）
        row_label = _get_row_label(row, rows)  # 西乡段 / 恒明珠
        
        for key, value in row.items():
            if value in (None, "", "NULL"):
                continue
            text = str(value)
            if not _NUMBER_RE.match(text):
                continue
            
            col_label = labels.get(key) or key  # 病害总数 / 泛油数量 / 平均面积
            full_label = f"{row_label}的{col_label}"  # 西乡段的病害总数
            
            # 检查这个数值在回复里出现过没
            if not _value_in_reply(text, reply):
                missing.append(f"{full_label} = {text}")
    
    if missing:
        return reply + "（各口径：" + "、".join(missing) + "）"
    return reply
```

## 六、集成到现有流程

### 6.1 在 agent.py 里的位置

现在的 `_build_query_result` 流程：

```python
# 现在的流程
result = sql_engine.execute_sql(kind, physical)
if result:
    result["engine"] = "wren"
    # ... 直接返回
```

加校验器之后：

```python
# 新的流程
result = sql_engine.execute_sql(kind, physical)
if result:
    result["engine"] = "wren"
    
    # 结果解读（先做总结）
    reply = _summarize_result(message, result)
    
    # 【新增】结果校验
    verify = verify_answer(message, physical, result, reply)
    if not verify["correct"] and retry_count < 1:  # 最多重试1次
        # 【新增】优化问题
        optimized_question = optimize_question(message, verify, plan, physical, result)
        # 重新走一遍
        return _build_query_result(optimized_question, intent, kind)
    
    # 没问题 → 正常返回
    payload["reply"] = reply
```

### 6.2 放在哪个层级

**不要放在最底层**（每次 SQL 执行都校验），**放在最外层**（整个查询流程走完再校验）。

因为：
- 底层校验会重复调用 LLM，成本高
- 外层校验一次就够了，看最终结果对不对

### 6.3 成本控制

| 项目 | 说明 |
|------|------|
| 调用次数 | 最多 1 次校验 + 1 次优化 = 2 次 LLM 调用 |
| 模型选择 | 校验器用小模型（便宜的），优化器用小模型就行 |
| 缓存 | 同一问题不重复校验 |
| 跳过条件 | 模板路径的结果不用校验（写死的SQL，不会错） |

## 八、注意事项

### 8.1 不要过度优化

- 只优化"答非所问"的情况
- 不要因为"结果不够完美"就重新生成
- 用户要明细就是明细，不要硬改成聚合

### 8.2 最多重试一次

- 第一次校验不对 → 优化问题 → 重新生成
- 第二次还不对 → 返回当前结果，不要死循环
- 记录失败原因，方便后续分析

### 8.3 模板路径不用校验

- 模板路径是写死的 SQL，不会"答非所问"
- 只有 Wren 路径和内置 LLM 路径需要校验
- 这样能省很多 LLM 调用成本

### 8.4 记录日志

每次校验和优化都要记录：
- 原始问题
- 校验结果（对/错，问题类型）
- 优化后的问题
- 第二次结果对不对

这些日志可以用来：
- 分析常见的错误类型
- 优化提示词
- 改进 MDL
- 补充测试题
