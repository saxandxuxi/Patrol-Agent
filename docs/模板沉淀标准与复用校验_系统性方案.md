# 模板沉淀标准与复用校验 系统性方案

> 目标：从源头防止模板复用时出现"参数填反、多余条件没清理、只回答部分问题、标签与数据对不上"等问题。
> 核心原则：**模板不是"存一条 SQL 就完事"，而是存"可复用的查询口径"——必须带参数语义角色、条件清单、完整性校验，复用时按规则对齐和清理。**

---

## 一、问题回顾（为什么需要标准）

近期模板复用出现的问题：

| 问题 | 现象 | 根因 |
|---|---|---|
| 参数填反 | 西乡段平均面积 vs 恒明珠大于平均值，两个路线 id 位置互换 | 参数槽位按位置顺序填，没绑定语义角色 |
| 多余条件 | 用户没问时间，模板带了7月份过滤，结果查成7月份数据 | 复用时没按新问题条件清理模板里的多余条件 |
| 只答一半 | 复合问题4步，模板只匹配了1步，其余3步没答 | 模板只存了单步查询，没标记"这是部分答案" |
| 标签对不上 | SQL 算的是恒明珠数据，列别名写"西乡段" | 中文列别名硬编码，复用时没动态替换 |
| 单位错误 | 数量132显示成"132㎡" | 单位硬编码，没按指标类型动态显示 |
| 口径不一致 | 同一问题两次回答数字不同（443 vs 732） | 一次带时间过滤一次没带，模板条件没对齐 |

**本质**：模板沉淀时只存了 SQL，没存"这条 SQL 的口径是什么、参数代表什么、哪些条件是必须的哪些是可选的"——复用时只能靠位置顺序猜，必然出错。

## 二、模板沉淀的准入标准（什么样的问答可以沉淀为模板）

### 2.1 必须满足的条件（全部满足才能沉淀）

1. **回答完整**：用户问题的每个子问题都有对应答案，不能"只答了一半"。
   - 反例：用户问"上下行各多少 + 各方向最多的类型"，模板只答了上下行数量 → 不能沉淀。
   - 正例：两个子问题都答了 → 可以沉淀。

2. **SQL 可执行且结果正确**：SQL 必须在当前库能跑通，结果与用户确认的答案一致。
   - 沉淀前必须跑一次 EXPLAIN + 实际执行，确认无语法错误、无空结果（除非用户问的就是"有没有"）。

3. **参数可识别**：SQL 里的字面值（路线名/时间/病害类型/阈值）必须能被识别为参数，不能和 SQL 逻辑混在一起。
   - 反例：SQL 里写死了 `r.id = '1b0b4a9f...'` 但没标记这是"路线参数" → 不能直接沉淀，要先参数化。

4. **口径清晰**：模板的查询口径（查什么表、什么条件、什么分组）必须能从 SQL 和用户问题里明确读出来。
   - 反例：SQL 里有时间过滤但用户问题没问时间 → 必须确认时间是"用户指定的"还是"模板自带的"，说不清就不能沉淀。

### 2.2 不允许沉淀的情况（满足任一就拒绝）

1. **复合问题只答了部分**：用户问了 N 个子问题，模板只覆盖了 M < N 个 → 不能沉淀为"整题模板"，只能沉淀为"子问题模板"并标记 `partial=true`。
2. **SQL 里有硬编码的中文别名且与参数绑定**：如 `AS 宝安大道西乡段泛油平均面积` → 必须先改成占位符才能沉淀。
3. **结果为空且用户问的是"有多少"**：空结果可能是条件错了，不能沉淀（用户问"有没有"时的空结果除外）。
4. **SQL 引用了不存在的列/表**：显然不能沉淀。
5. **用户没有明确确认"答对了"**：必须用户点了"答对了"或等效确认才能沉淀，不能自动沉淀。
6. **多对象对比类问题（2 个及以上对象）**：用户问了 2 条及以上路线/桥梁/边坡/隧道/工单等资产的对比（如"A、B、C 各有多少"、"西乡段和恒明珠段分别是多少"），**不允许沉淀为自动模板，不做别名动态替换**。
   - 原因：这类问题的 SQL 通常有多个 CTE/子查询/UNION，别名动态替换在多对象场景下极易出错（A→B、B→C、C→A 循环替换）；
   - 覆盖范围：路线（routes）、桥梁（bridges）、边坡（slopes）、隧道（tunnels）、工单（work_order）、巡检任务（patrol）、病害类型（damage_type）等所有可多对象并列的资产；
   - **但可以走相似问法（RAGFlow 同义召回）**：多对象问题不沉淀为自动模板，但如果 RAGFlow 里有相似的已验证问法（如用户之前问过"西乡段和恒明珠段各有多少"并确认答对了），可以召回并弹卡让用户确认；
   - 相似问法复用时的额外校验：
     - 参数按语义角色对齐（不按位置），防止 A/B/C 填反；
     - 条件清理（示例带了时间但用户没问 → 不摆卡，交 Wren）；
     - 不做别名字符串替换（多对象场景下别名替换风险高，直接用示例的原始 SQL + 参数回填，标签如果对不上就如实显示）；
   - 例外：单对象的问题（如"西乡段有多少"）可以正常沉淀为自动模板。

## 三、模板沉淀时必须记录的元数据

每条模板沉淀时，除了 SQL，必须记录以下元数据：

```yaml
template_id: auto_generated_id
source: example_direct | preset | auto_mined
question: "宝安中心--恒明珠中，上行和下行各有多少处病害？上下行数量最多的病害类型分别是什么？"

# 1. 参数槽位（带语义角色，不是按位置）
slots:
  - name: route_id
    role: target_route          # 语义角色：被查询的路线
    label: 目标路线
    type: route_id
    required: true
    example_value: "d74bf5e5fd333c060410d41aced41f7f"
    example_label: "宝安中心--恒明珠"
  - name: start_time
    role: time_range_start      # 语义角色：时间范围起点
    label: 开始时间
    type: datetime
    required: false             # 可选：用户没问时间时不填
    example_value: null
  - name: damage_type
    role: damage_type_filter    # 语义角色：病害类型过滤
    label: 病害类型
    type: damage_type
    required: false
    example_value: null

# 2. 条件清单（哪些条件是模板自带的，哪些是参数化的）
conditions:
  - field: del_flag
    op: "="
    value: "0"
    source: fixed               # fixed=模板固定条件，永远保留
  - field: routes_id
    op: "="
    value: "{{route_id}}"
    source: slot                # slot=来自参数槽位
  - field: collection_time
    op: between
    value: ["{{start_time}}", "{{end_time}}"]
    source: slot
    optional: true              # optional=true：用户没问时间时，整个条件要去掉

# 3. 输出列（带中文标签占位符和单位）
output_columns:
  - name: direction
    label: 方向
    type: string
    unit: null
  - name: cnt
    label: 病害数量
    type: integer
    unit: 处
  - name: top_damage_type
    label: 数量最多的病害类型
    type: string
    unit: null

# 4. 完整性标记
completeness:
  is_partial: false             # false=完整回答了用户问题，true=只答了部分
  covers_subquestions: [1, 2]   # 覆盖了用户问题的哪几个子问题（从1开始）
  total_subquestions: 2

# 5. SQL（参数化后的，用 {{slot_name}} 占位）
sql: |
  SELECT CASE d.up_or_down WHEN '1' THEN '上行' WHEN '2' THEN '下行' ELSE '未填' END AS 方向,
         COUNT(*) AS 病害数量,
         (SELECT ... WHERE d2.routes_id = {{route_id}} AND d2.up_or_down = d.up_or_down ...) AS 数量最多的病害类型
  FROM ai_problem d
  WHERE d.del_flag = 0 AND d.routes_id = {{route_id}}
  {% if start_time %}AND d.collection_time >= {{start_time}} AND d.collection_time < {{end_time}}{% endif %}
  GROUP BY d.up_or_down

# 6. 适用范围（什么样的问题能复用这个模板）
applicability:
  intent: data | analysis
  subject: disease
  must_have_conditions: [route_id]   # 必须有的条件（没有就不能复用）
  optional_conditions: [start_time, damage_type]  # 可选条件
  shape: distribution
```

### 关键设计点

1. **参数槽位带语义角色**：`role: target_route` / `time_range_start` / `damage_type_filter`——复用时按角色填，不是按位置填，防止填反。
2. **条件标记 `source` 和 `optional`**：
   - `fixed`：模板固定条件（如 del_flag=0），永远保留；
   - `slot`：来自参数槽位，按用户问题填；
   - `optional=true`：用户没问这个条件时，整个 WHERE 子句要去掉（防止多余条件）。
3. **输出列带单位**：`unit: 处` / `㎡` / `公里`——复用时动态显示，防止单位错误。
4. **完整性标记 `is_partial`**：标记这条模板是不是只答了部分问题，复用时如果 `is_partial=true`，必须提示用户"这只回答了部分问题"。
5. **SQL 用条件渲染**：`{% if start_time %}...{% endif %}`——可选条件不存在时，整个条件块不渲染，防止多余条件。

## 四、模板复用时的校验规则（必须全部通过才能执行）

复用时，按以下顺序校验，任何一步不通过就不能直接执行，要么降级到 Wren，要么提示用户：

### 4.1 参数对齐校验（防止填反）

```
对模板的每个 slot：
  1. 从用户问题的 plan 里找对应语义角色的参数值
  2. 找到了 → 填入
  3. 没找到但 required=true → 不能复用，降级到 Wren
  4. 没找到但 required=false → 留空（可选条件不渲染）
```

**关键**：按 `role`（语义角色）对齐，不是按槽位在列表里的位置对齐。

### 4.2 条件清理校验（防止多余条件）

```
对模板的每个 condition：
  - source=fixed → 保留
  - source=slot → 看用户问题有没有这个条件
      · 有 → 填值保留
      · 没有且 optional=true → 整个条件去掉（包括 WHERE 里的对应子句）
      · 没有且 optional=false → 不能复用（缺少必要条件）
```

**关键**：用户没问时间，模板里的时间过滤必须整个去掉，不能留着。

### 4.3 完整性校验（防止只答一半）

```
如果模板 is_partial=true：
  - 在弹卡上明确标注"此模板只回答了问题的第 X 部分"
  - 执行后，提示用户"其余部分可以继续追问或让 AI 用 Wren 查"
  - 不能假装回答完整了
```

### 4.4 列别名动态替换（防止标签对不上）

```
SQL 里的中文列别名如果包含参数值（如"宝安大道西乡段泛油平均面积"）：
  - 必须用占位符 {{route_label}} 表示
  - 复用时根据填入的参数动态替换
  - 不能硬编码中文别名

⚠️ 多对象限制：如果问题涉及 2 个及以上对象（路线/桥/边坡/隧道/工单等），
   不做别名动态替换——多对象场景下字符串替换极易出错（循环替换、重叠替换）。
   但可以走相似问法（RAGFlow 召回），用户确认后用示例原始 SQL + 参数回填，
   标签如果对不上就如实显示，不做字符串替换。
```

**为什么多对象不做别名替换**：
- 两条路：A→B、B→A，需要重叠保护（容易出 bug，codex 第一版就踩了"自己抵消"的坑）；
- 三条路：A→B、B→C、C→A，循环替换几乎不可能保证正确；
- 四条路及以上：更复杂，字符串替换不可靠；
- 结论：多对象对比不做别名字符串替换，走相似问法时用原始 SQL + 参数回填，标签如实显示。

### 4.5 单位动态显示

```
每个输出列按 unit 字段显示单位：
  - 数量类 → 处/条/次
  - 面积类 → ㎡
  - 长度类 → 公里/米
  - 密度类 → 处/公里
  - 百分比 → %
不能把数量显示成"㎡"。
```

### 4.6 口径一致性校验（防止同一问题两次答案不同）

```
复用前，对比模板的 conditions 和用户问题的 plan.conditions：
  - 模板有但用户没问的条件 → 必须是 optional=true，否则不能复用
  - 用户有但模板没有的条件 → 模板不支持，降级到 Wren
  - 两者一致 → 可以复用
```

## 五、模板的生命周期管理

### 5.1 LLM 自动审核 + 人工抽检（不靠人眼看复杂 SQL）

**问题**：自动沉淀的模板 SQL 可能很长很复杂（多层 CTE、子查询、CASE WHEN），人眼看不出来有没有条件写死、参数有没有识别对——人审也得靠 AI 看才知道对不对。

**改法**：用 LLM（qwen3-coder-plus，不参与对话功能，只做后台审核）自动审核模板，人工只做抽检。

**LLM 审核的检查项**（输出 JSON，不通过的标原因）：

```json
{
  "pass": true,
  "issues": [
    {
      "type": "hardcoded_condition",
      "severity": "high",
      "description": "WHERE 里有 collection_time >= '2026-07-01' 但用户问题没问时间，应标记为 optional 或去掉",
      "location": "第 15 行"
    },
    {
      "type": "hardcoded_alias",
      "severity": "medium",
      "description": "列别名 '宝安大道西乡段泛油平均面积' 包含参数值，应改为占位符 {{route_label}}",
      "location": "SELECT 第 3 列"
    },
    {
      "type": "wrong_unit",
      "severity": "low",
      "description": "输出列 '病害数量' 的单位应为 '处'，当前标记为 '㎡'",
      "location": "output_columns[1]"
    },
    {
      "type": "partial_answer",
      "severity": "high",
      "description": "用户问了上下行数量 + 各方向最多类型，SQL 只查了上下行数量，is_partial 应设为 true",
      "location": "completeness"
    },
    {
      "type": "parameter_misaligned",
      "severity": "high",
      "description": "avg_area CTE 里的路线 id 是恒明珠，但列别名写'西乡段'，参数与标签不对应",
      "location": "CTE avg_area 第 2 行"
    }
  ],
  "suggested_fixes": [
    "将 collection_time 条件标记为 optional",
    "将列别名改为 {{route_label}}泛油平均面积"
  ]
}
```

**审核流程**：
1. 用户点"答对了" → 自动沉淀模板，状态 `candidate`；
2. 后台异步调 LLM 审核（qwen3-coder-plus，不占对话资源）；
3. LLM 审核通过（无 high 级 issue）→ 自动变为 `active`，进推荐；
4. LLM 审核不通过（有 high 级 issue）→ 保持 `candidate`，记录 issues，通知维护者；
5. 人工抽检：每周随机抽 10% 的 active 模板复审，发现问题降级回 `candidate`。

**为什么用 LLM 不用规则**：
- 规则只能查"有没有硬编码的时间字符串"，但判断"这个时间条件用户有没有问"需要语义理解；
- 规则只能查"列别名里有没有中文路线名"，但判断"这个别名和参数对不对得上"需要理解 SQL 逻辑；
- LLM 能看懂复杂 SQL（多层 CTE、子查询），规则看不懂。

**成本控制**：
- 只在用户点"答对了"时触发一次审核，不是每条问题都审；
- 用 qwen3-coder-plus（便宜、代码能力强），不用贵模型；
- 审核结果缓存，同一模板不重复审。

### 5.2 一键答错（不要求用户写原因）

**问题**：用户点"答错了"时，如果要求填写原因，用户可能懒得写就不点了——导致模板的错误反馈收集不到，坏模板一直在推荐里。

**改法**："答错了"按钮是**一键操作**，不需要填原因。系统自动记录上下文：

```json
{
  "template_id": "xxx",
  "question": "恒明珠段上下行各多少",
  "sql_executed": "...",
  "result_summary": "上行 443，下行 0",
  "user_clicked": "wrong",
  "timestamp": "2026-10-09 10:43:00",
  "auto_collected_context": {
    "plan_subject": "disease",
    "plan_conditions": ["route=恒明珠"],
    "template_conditions": ["route=恒明珠", "time=2026-07"],
    "mismatch": "模板带了时间条件但用户没问"
  }
}
```

**自动收集的上下文**（不需要用户输入）：
- 用户的原始问题；
- 模板的 SQL 和执行结果；
- 用户问题的 plan（主体、条件）；
- 模板的条件清单；
- 自动对比：模板有但用户没问的条件（多余条件）、用户有但模板没有的条件（缺失条件）。

**后续分析**：
- 后台定期分析"答错了"的模板，自动对比 plan 和模板条件，找出常见错误模式（如"模板带了时间条件但用户没问"）；
- 同一模板连续 3 次被点"答错了" → 自动降级回 `candidate`，重新 LLM 审核；
- 不需要用户写一个字，系统自己能分析出大部分原因。

### 5.3 过期与清理

- 模板每次被复用后，记录复用结果（用户点了"答对了"还是"答错了"，一键操作）；
- 连续 3 次复用被用户点"答错了" → 自动降级为 `candidate`，重新 LLM 审核；
- 连续 10 次没被复用 → 标记为 `cold`，不进推荐但保留（防止误删）；
- 模板对应的表结构变了（列被删/改名）→ 自动标记为 `broken`，不进推荐，通知维护者更新。

### 5.4 版本管理

- 模板修改后保留历史版本（至少 3 个版本）；
- 修改时必须说明"改了什么"（参数槽位/条件/SQL）；
- 可以回滚到历史版本。

## 六、沉淀流程（用户点"答对了"之后）

```
用户点"答对了"
  │
  ▼
1. 提取 SQL 里的字面值，识别为参数（路线/时间/病害类型/阈值）
  │
  ▼
2. 分析 SQL 的 WHERE 条件，标记每个条件是 fixed/slot/optional
  │
  ▼
3. 分析 SQL 的输出列，提取中文标签和单位
  │
  ▼
4. 判断完整性：用户问题有几个子问题，SQL 回答了几个
  │   ├─ 全部回答 → is_partial=false
  │   └─ 只答部分 → is_partial=true，标记 covers_subquestions
  │
  ▼
5. 参数化 SQL：字面值替换为 {{slot_name}}，可选条件包 {% if %}
  │
  ▼
6. 生成元数据（slots/conditions/output_columns/completeness/applicability）
  │
  ▼
7. 状态设为 candidate，触发 LLM 自动审核（后台异步，不占对话资源）
  │
  ▼
8. LLM 审核通过（无 high 级 issue）→ active，进对话推荐
   LLM 审核不通过 → 保持 candidate，记录 issues，通知维护者
   人工每周抽检 10% 的 active 模板，发现问题降级回 candidate
```

---

## 七、验收标准

### 7.1 沉淀质量

1. 所有 active 模板的参数槽位都带语义角色（role 字段非空）；
2. 所有 active 模板的条件都标记了 source（fixed/slot）和 optional；
3. 所有 active 模板的输出列都带 unit；
4. 没有 is_partial=true 但没标注的模板；
5. SQL 里没有硬编码的中文参数别名（都用占位符）。

### 7.2 复用质量

1. 同一问题复用模板，两次答案一致（不会一次443一次732）；
2. 参数不会填反（西乡段的平均面积不会算成恒明珠的）；
3. 用户没问时间时，结果不带时间过滤；
4. 复合问题只答部分时，明确提示"只回答了部分"；
5. 数量显示"处"，面积显示"㎡"，不会单位错乱。

### 7.3 回归测试

用以下问题做回归测试，确认模板复用不出错：

| 问题 | 预期 |
|---|---|
| 恒明珠段上下行各多少（复用西乡段的模板） | 参数按角色填，结果是恒明珠的数据，不是西乡段的 |
| 恒明珠段上下行各多少（不指定时间，复用带7月条件的模板） | 时间条件被清理，结果是全量数据，不是7月份的 |
| 西乡段泛油平均面积 + 恒明珠大于该值的数量（复合） | 两个路线参数不填反，标签和数据对应 |
| 上下行各多少 + 各方向最多类型（复合，模板只答了第一问） | 明确提示"只回答了上下行数量，类型部分需追问" |
| 西乡段和恒明珠段各有多少病害（多对象对比） | **不沉淀为自动模板，不做别名替换；可以走相似问法，用户确认后用原始 SQL + 参数回填** |
| A桥、B桥、C桥的技术评定等级分别是多少（三对象对比） | **不沉淀为自动模板，不做别名替换；可以走相似问法** |
| 7月工单和8月工单各有多少（多对象对比） | **不沉淀为自动模板，不做别名替换；可以走相似问法** |

## 八、不做的（明确边界）

1. 不做模板的自动修复（broken 模板通知人工，不自动改 SQL；LLM 只审核不修改）；
2. 不做三维及以上复合问题的模板（太复杂，直接走 Wren）；
3. 不改变现有 preset 模板的格式（preset 是手写的，质量有保障，只对 auto_mined 模板强制执行新标准）；
4. 不要求用户点"答错了"时填写原因（一键操作，系统自动收集上下文）。

---

## 九、实施顺序

1. **第一步**：模板数据结构扩展，加 slots/conditions/output_columns/completeness 字段（数据库 + 代码）；
2. **第二步**：沉淀流程改造，用户点"答对了"后自动提取参数/条件/输出列，生成元数据；
3. **第三步**：复用校验改造，按语义角色填参数、按 optional 清理条件、按完整性提示；
4. **第四步**：LLM 自动审核（后台异步，qwen3-coder-plus），通过则 active，不通过则 candidate 等维护；
5. **第五步**：一键答错反馈（用户不填原因，系统自动收集上下文）；
6. **第六步**：生命周期管理（过期清理/broken 检测/版本回滚）；
7. 每步做完跑回归测试，确认不出错。
