# 周数计算模式不一致与链式复合问题执行修复方案

> 背景：用户问"哪个星期西乡段泛油数量是最多的？把相关的数据全部列出来"，系统只回答了"第31周最多"，没有列出第31周的明细。用户第二次明确问"2026年第31周是西乡段泛油数量最多的星期，把这周相关的数据全部列出来"，系统回答"您问的时间段没有数据"。根因是：①代码用的周数计算模式（YEARWEEK mode=1）和用户理解的（ISO 8601，mode=3）不一致；②链式复合问题没有正确执行第二步（明细查询）；③周数到日期范围的转换错误。
> 核心思路：统一周数计算模式为 ISO 8601（mode=3），修复链式复合问题的两步执行，修复周数到日期范围的转换逻辑。
> 生成时间：2026-10-12

---

## 一、问题诊断

### 1.1 案例分析

**用户第一次问：** "哪个星期西乡段泛油数量是最多的？把相关的数据全部列出来"

**系统回答：**
- 只回答了第一个子问题："2026年第31周（周次代码：202631）是西乡段泛油数量最多的星期"
- 没有执行第二个子问题：没有列出第31周的泛油病害明细
- 回答里还说"无法与其他周次进行横向对比"（偏离用户意图）

**用户第二次问（明确说了第31周）：** "2026 年第 31 周是西乡段泛油数量最多的星期，把这周相关的数据全部列出来"

**系统回答：** "宝安大道西乡段 的病害数据实际覆盖 2026-07-15 ~ 2026-07-30，您问的时间段没有数据"

**为什么会说"没有数据"？**
- 代码里用的是 `YEARWEEK(collection_time, 1)`（mode=1）
- mode=1 的 2026 年第 31 周是 **2026-08-03 ~ 2026-08-09**
- 数据只覆盖到 2026-07-30，所以 8 月 3 日-8 月 9 日这个范围内没有数据
- 系统就回答"您问的时间段没有数据"

### 1.2 周数计算模式不一致（核心问题）

**代码里混用了多种周数计算方式：**

| 位置 | 代码 | 周数计算模式 |
|---|---|---|
| `nl2sql.py:2374` | `YEARWEEK(p.collection_time, 1)` | mode=1（星期从周一开始，第一周是第一个周一所在的周） |
| `nl2sql.py:7610` | `YEARWEEK({alias}.collection_time, 1)` | mode=1 |
| `generic.py:28` | `DATE_FORMAT(..., '%Y-%W')` | %W（星期从周一开始，第一周是第一个周一所在的周） |
| `templatizer.py:558` | `DATE_FORMAT(..., '%Y-%u')` | %u（星期从周一开始，第一周是第一个周一所在的周） |

**用户理解的是 ISO 8601 标准（mode=3）：**
- ISO 8601：星期从周一开始，一年的第一周包含该年的第一个星期四
- 这是国际标准，大部分用户理解的"第几周"都是这个

**两种模式的 2026 年周数对比：**

| 周数 | ISO 8601（mode=3） | mode=1（代码当前用的） |
|---|---|---|
| 第1周 | 2025-12-29 ~ 2026-01-04 | 2026-01-05 ~ 2026-01-11 |
| 第30周 | 2026-07-20 ~ 2026-07-26 | 2026-07-27 ~ 2026-08-02 |
| 第31周 | 2026-07-27 ~ 2026-08-02 | 2026-08-03 ~ 2026-08-09 |

**用户说的"第31周是 7月20日～7月26日"**：这是 ISO 8601 的第30周，用户可能也搞混了，但核心问题是代码用的模式和用户理解的不一致。

### 1.3 链式复合问题没有正确执行

**用户的真实意图（链式复合问题）：**
1. **第一个子问题**："哪个星期西乡段泛油数量是最多的？" → 按周分组统计，找出最多的那一周 → 答案：第31周（401处）
2. **第二个子问题**：用第一个子问题的答案作为条件 → "2026年第31周西乡段泛油相关的数据全部列出来" → 列出第31周的泛油病害明细（每一条记录）

**系统的问题：**
- 只执行了第一个子问题（TopN）
- 没有执行第二个子问题（明细）
- 用户第二次明确说了第31周，系统还是没有列出明细，反而说"没有数据"

### 1.4 周数到日期范围的转换错误

**当用户问"第31周的数据"时，系统需要把周数转换成日期范围：**
- 正确的转换（ISO 8601）：第31周 → 2026-07-27 ~ 2026-08-02
- 错误的转换（mode=1）：第31周 → 2026-08-03 ~ 2026-08-09
- 系统用了错误的转换，导致说"没有数据"

## 二、解决方案

### 2.1 核心思路

**三个问题同时修复：**

1. **统一周数计算模式为 ISO 8601（mode=3）**：所有涉及周数的地方都用 mode=3，和用户理解的一致
2. **修复链式复合问题的两步执行**：先算 TopN，再用 TopN 结果查明细
3. **修复周数到日期范围的转换**：用 ISO 8601 标准把周数转换成日期范围

### 2.2 修复 1：统一周数计算模式为 ISO 8601（mode=3）

**文件：** `backend/app/services/nl2sql.py`、`backend/app/services/generic.py`、`backend/app/services/templatizer.py`

**改动：**

1. **把所有 `YEARWEEK(date, 1)` 改成 `YEARWEEK(date, 3)`**：
   - `nl2sql.py:2374`：`YEARWEEK(p.collection_time, 1)` → `YEARWEEK(p.collection_time, 3)`
   - `nl2sql.py:7610`：`YEARWEEK({alias}.collection_time, 1)` → `YEARWEEK({alias}.collection_time, 3)`

2. **把所有 `DATE_FORMAT(date, '%Y-%W')` 改成 `DATE_FORMAT(date, '%x-%v')`**：
   - `generic.py:28`：`"week": "%Y-%W"` → `"week": "%x-%v"`
   - 注意：%x 是 ISO 8601 的年份（可能和日历年不同），%v 是 ISO 8601 的周数

3. **把所有 `DATE_FORMAT(date, '%Y-%u')` 改成 `DATE_FORMAT(date, '%x-%v')`**：
   - `templatizer.py:558`：`"week": "%Y-%u"` → `"week": "%x-%v"`

4. **全局搜索确认没有其他地方用了不一致的周数计算方式**：
   - 搜索 `YEARWEEK`、`%W`、`%u`、`%U`、`%V`、`%v`
   - 确保所有周数计算都用 ISO 8601 标准

5. **在代码注释里说明为什么用 mode=3**：
   ```python
   # 周数统一用 ISO 8601 标准（mode=3）：星期从周一开始，一年的第一周包含该年的第一个星期四
   # 这是国际标准，和用户理解的"第几周"一致
   # 不要用 mode=1（第一周是第一个周一所在的周），会导致周数和用户理解的不一致
   ```

### 2.3 修复 2：链式复合问题的两步执行

**文件：** `backend/app/services/agent.py`、`backend/app/services/nl2sql.py`

**改动：**

1. **在语义规划中识别链式复合问题**：
   - 当用户问法同时包含"哪个/什么 最/最多/最少"和"把它/相关的数据列出来/列出明细"时，标记为链式复合问题
   - 在 plan 里增加 `chain=True`、`chain_first_subject`、`chain_second_type` 等字段

2. **当 `chain=True` 时，分两步执行**：

   **第一步：执行第一个子问题（TopN）**
   - 按第一个子问题的主体分组统计（如按周分组统计泛油数量）
   - 找出极值（最多的那一周）
   - 得到答案：`{ "week": "202631", "count": 401, "date_range": "2026-07-27 ~ 2026-08-02" }`

   **第二步：用第一步的答案作为条件，执行第二个子问题（明细）**
   - 把第一步的答案转换成 SQL 条件（如 `YEARWEEK(collection_time, 3) = 202631`）
   - 执行明细查询（列出第31周的泛油病害明细）
   - 得到明细数据：`[{ "pile_number": "K1+200", "area": 2.5, "collection_time": "..." }, ...]`

3. **第一步答案到第二步条件的转换逻辑**：
   - 按周 TopN → `YEARWEEK(collection_time, 3) = {week}`
   - 按月 TopN → `DATE_FORMAT(collection_time, '%Y-%m') = '{month}'`
   - 按天 TopN → `DATE(collection_time) = '{date}'`
   - 按路线 TopN → `routes_id = '{route_id}'`
   - 按病害类型 TopN → `damage_type = '{damage_type}'`

4. **第二步明细查询的字段选择**：
   - 默认列出该表的主要字段（如病害表：桩号、面积、采集时间、病害类型、置信度等）
   - 如果用户点名了具体字段，按用户点名的字段列出
   - 明细数量超过 500 条时，只返回前 500 条，提示"完整数据请在结果工作台查看"

### 2.4 修复 3：周数到日期范围的转换

**文件：** `backend/app/services/parsers.py`、`backend/app/services/agent.py`

**改动：**

1. **新增 `week_to_date_range(year, week)` 函数**：
   - 输入：年份、周数（ISO 8601 标准）
   - 输出：该周的周一和周日日期
   - 实现：用 Python 的 `datetime` 模块计算
   ```python
   def week_to_date_range(year: int, week: int) -> tuple[date, date]:
       """把 ISO 8601 周数转换成日期范围。
       
       输入：year=2026, week=31
       输出：(date(2026, 7, 27), date(2026, 8, 2))
       """
       # ISO 8601：一年的第一周包含该年的第一个星期四
       # 找到该年第一个星期四的日期
       jan4 = date(year, 1, 4)
       first_thursday = jan4 - timedelta(days=jan4.weekday() - 3)  # weekday(): 周一=0, 周四=3
       # 第一周的周一是第一个星期四往前推3天
       first_monday = first_thursday - timedelta(days=3)
       # 第 week 周的周一
       monday = first_monday + timedelta(weeks=week - 1)
       sunday = monday + timedelta(days=6)
       return monday, sunday
   ```

2. **当用户问"第N周的数据"时，用这个函数转换成日期范围**：
   - 然后用日期范围作为 SQL 条件（`collection_time >= '2026-07-27' AND collection_time < '2026-08-03'`）
   - 或者直接用 `YEARWEEK(collection_time, 3) = 202631`（更简单）

3. **在回答里显示正确的日期范围**：
   - 当回答"第31周最多"时，同时显示"第31周（2026-07-27 ~ 2026-08-02）"
   - 让用户确认周数和日期范围的对应关系

### 2.5 修复 4：回答生成标准化

**文件：** `backend/app/services/agent.py`、回答生成提示词

**改动：**

1. **链式复合问题的回答模板**：
   ```
   {极值说明}：{第一个子问题的答案}（{日期范围}，{指标值}）
   
   {极值对应的明细}：
   {明细数据，前10条}
   （完整{总数}条请在结果工作台查看表格）
   ```

2. **例子**：
   ```
   2026年第31周（2026-07-27 ~ 2026-08-02）是西乡段泛油数量最多的星期，共401处。
   
   第31周西乡段泛油病害明细如下（共401条，前10条）：
   1. 桩号 K1+200，面积 2.5㎡，采集时间 2026-07-28 10:30
   2. 桩号 K1+350，面积 1.8㎡，采集时间 2026-07-28 11:15
   ...
   （完整401条请在结果工作台查看表格）
   ```

3. **回答生成提示词中增加规范**：
   - 必须先说明极值（第一个子问题的答案），并显示正确的日期范围
   - 然后列出极值对应的明细数据（第二个子问题的结果）
   - 不允许说"无法对比"或"没有数据"（除非真的没有数据）
   - 明细超过 10 条时，列出前 10 条，提示"完整数据请在结果工作台查看"

## 五、风险与应对

| 风险 | 应对 |
|---|---|
| 周数计算模式从 mode=1 改成 mode=3 后，历史数据的周数会变 | 这是预期的，因为 mode=3 才是用户理解的标准；如果有模板或示例存了 mode=1 的周数，需要重新生成或迁移 |
| 回归测试失败 | 先检查是测试用例的预期值需要更新（因为周数计算模式变了），还是代码有 bug；更新测试用例的预期值 |
| 链式复合问题识别不准 | 收集 bad case，持续优化提示词；可以先用关键词规则兜底（"把它/相关的数据列出来"等词） |
| 第一步答案到第二步条件的转换逻辑覆盖不全 | 先支持常见类型（按周/月/天/路线/病害类型），遇到不支持的类型退回 Wren 或提示用户 |
| 链式复合问题执行时间较长（两步查询） | 串行执行是必要的（第二步依赖第一步的答案）；可以优化查询性能（如加索引） |
| 用户搞混了周数（如把第30周说成第31周） | 在回答里显示日期范围，让用户确认；如果用户说的周数和日期范围对不上，可以提示用户确认 |

## 六、扩展：其他时间粒度的统一

除了周数，其他时间粒度也需要确认是否一致：

| 时间粒度 | 当前代码 | 标准 | 是否需要修改 |
|---|---|---|---|
| 年 | `YEAR(date)` | `YEAR(date)` | 一致，不需要修改 |
| 季度 | `QUARTER(date)` | `QUARTER(date)` | 一致，不需要修改 |
| 月 | `DATE_FORMAT(date, '%Y-%m')` | `DATE_FORMAT(date, '%Y-%m')` | 一致，不需要修改 |
| 周 | `YEARWEEK(date, 1)` / `%Y-%W` / `%Y-%u` | `YEARWEEK(date, 3)` / `%x-%v` | **不一致，需要修改** |
| 天 | `DATE(date)` | `DATE(date)` | 一致，不需要修改 |
| 小时 | `DATE_FORMAT(date, '%Y-%m-%d %H')` | `DATE_FORMAT(date, '%Y-%m-%d %H')` | 一致，不需要修改 |
| 星期几 | `DAYOFWEEK(date)` / `WEEKDAY(date)` | 需要确认 | 可能不一致，需要检查 |

**核心原则：所有时间粒度的计算方式都要和用户理解的一致，特别是周数这种容易混淆的。**
