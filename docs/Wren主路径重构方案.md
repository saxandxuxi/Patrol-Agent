# NL2SQL 路径优先级重构方案：Wren 做主，模板做快速通道

## 一、现状问题：为什么"模板做主"走不通

### 1.1 现在的路径优先级

```
用户问题 → 模板匹配 → 匹配到就走模板 → 匹配不到才走 Wren
```

模板是端到端的：一个模板从自然语言直接生成完整 SQL。
这意味着每个模板都要处理所有主体、所有度量、所有分组的组合。

### 1.2 实测暴露的问题

用综合问答数据集测试，10 道题错了 9 道，错误类型集中在三类：

**错误类型1：模板截胡（占 60%）**

问题明明需要 GROUP BY 聚合，但模板匹配到关键词就走了明细模板：

| 问题 | 正确 SQL 形状 | 实际走了 | 结果 |
|------|-------------|---------|------|
| 数量最多的病害类型是哪种？ | GROUP BY 病害类型 + ORDER BY COUNT(*) DESC LIMIT 1 | top 明细模板 | 返回 11 条最大病害明细 |
| 泛油占全部病害的百分之多少？ | COUNT(泛油) / COUNT(*) | 病害明细模板 | 返回 500 条明细 |
| 多少种资产类型？每种多少个？ | GROUP BY 资产类型 | 资产总数模板 | 只返回总数 88 |

**根因：模板匹配只看关键词，不判断 SQL 形状。** 句子里有"最多"就走 top，有"泛油"就走病害明细。它不理解"数量最多的病害类型"是要按类型分组，不是要单条明细。

**错误类型2：拆分器拆了，子问题又走模板（占 20%）**

"平均每隔多少米一处"拆成了 3 个子问题：
- 子问题1：病害总数 → 走对了
- 子问题2：路线长度 → 模板不知道"路线长度"是什么，走了病害明细
- 后置计算：拿不到路线长度，算不出来

**根因：拆分器和模板路径是割裂的。** 拆分器拆出了正确的子问题，但每个子问题还是走"先模板后 Wren"的老路径，模板一截胡就错。

**错误类型3：多指标/多维度漏数（占 20%）**

- 两条路三个维度对比 → 只答了两个维度
- 多少次巡查 + 发现多少 + 平均每次 → 没算平均
- 按每公里分段 → 只算了整体密度，没分段

**根因：模板是为单一查询形状设计的，多指标组合它处理不了。**

### 1.3 数学上为什么收敛不了

查询可以拆成四个正交维度：

```
主体筛选：路线 + 路段 + 病害类型 + 时间 + ...   （10 种）
度量：    count / sum / avg / ratio / ...       （5 种）
分组：    无 / 按类型 / 按图片有无 / 按方向 / ... （8 种）
关系：    单一 / 对比 / 差值 / 后置计算 / ...     （4 种）
```

组合空间 = 10 × 5 × 8 × 4 = **1600 种**。

现在模板覆盖了多少？假设 50 个，覆盖率 3%。每加一个模板，覆盖率涨 0.06%。

**用模板枚举组合空间，数学上永远收敛不了。** 这就是"拆东墙补西墙"的来源。

### 1.4 为什么做了正交分解还是不行

正交分解的思路是对的：把 SQL 拆成主体/度量/分组/关系四个独立维度，每个维度独立处理。但实际落地的时候，**四个维度的识别全靠关键词规则，不是 LLM 语义理解**。

| 维度 | 现在怎么识别 | 问题 |
|------|------------|------|
| shape（查询形状） | `parse_query_shape()`："最多"→top，"分布"→distribution，"多少处"→count | 关键词匹配 |
| group_by（分组维度） | 硬编码："分布"→按类型，"各路线"→按路线 | 只能认这几种说法 |
| metric（度量） | `_detect_metric_specs()`："平均"→avg，"总和"→sum | 关键词匹配 |
| SQL 拼装 | Python 函数写死 SQL 形状 | 每个函数一种固定形状 |

**举个例子：**

问题："数量最多的病害类型是哪种？"

规则的判断流程：
1. 看到"最多" → `shape = "top"`
2. group_by 里没有"分布/各路线" → `group_by = None`
3. 走 top 模板 → 返回最大的 11 条病害明细

但正确的理解应该是：
1. 主体：西乡段所有病害
2. 度量：COUNT(*)
3. 分组：按病害类型
4. 排序：按 COUNT(*) DESC
5. 取第一个

规则为什么识别错了？因为它只看到"最多"这个词，没理解"最多的是什么"——是最多的单条病害？还是最多的病害类型？

**这和端到端模板是同一个问题：** 把端到端模板拆成了槽位，但每个槽位还是靠关键词规则猜。本质还是规则驱动，组合空间还是被规则的关键词覆盖范围限制住了。补一个"数量最多的病害类型"的规则，下次用户问"数量最少的病害类型"又不认了。还是补一个漏一个。

**真正的正交分解应该让 LLM 做维度识别，不是规则。**

## 二、新架构：Wren 做主，模板做快速通道

### 2.1 核心思路

```
用户问题 → 拆分器拆成子问题 → LLM 理解语义生成 MDL-SQL
         → Wren 编译执行 → 编译失败才走模板兜底
```

**Wren 是主力路径，模板只做快速通道。**

为什么 Wren 能解决问题：
- Wren 的 MDL-SQL 是结构化语义层，LLM 只需要说"按什么分组、取什么度量"，不用写物理表名和 JOIN
- Wren 编译器负责把 MDL-SQL 编译成物理 SQL，不会漏 JOIN、不会写错字段
- 组合爆炸由 LLM 理解语义来处理，不是靠枚举模板

**关键点：维度识别由 LLM 做，不是规则。**

之前正交分解失败，是因为四个维度（主体/度量/分组/关系）的识别全靠关键词规则。现在改成 Wren 路径后，这四个维度全部由 LLM 理解语义后直接写进 MDL-SQL：

```
用户问题："数量最多的病害类型是哪种？"

LLM 理解：
  - 主体：disease，过滤 route = 西乡段
  - 度量：COUNT(*)
  - 分组：GROUP BY problem_type
  - 排序：ORDER BY COUNT(*) DESC
  - 取第一行

直接写成 MDL-SQL：
  SELECT dd.problem_type, COUNT(*) AS cnt
  FROM disease d JOIN route r ON ... JOIN damage_dict dd ON ...
  WHERE r.short_name = '西乡段'
  GROUP BY dd.problem_type
  ORDER BY cnt DESC LIMIT 1
```

**不需要规则去猜 shape，不需要规则去猜 group_by，LLM 直接理解语义写 SQL。** 这才是真正的正交分解——零件（维度识别）由 LLM 提供，不是规则。

### 2.2 规则版正交分解怎么过渡到 LLM 版

不用完全推翻现有代码，而是**零件级替换**——哪些零件保留规则，哪些换成 LLM，列清楚：

| 零件 | 现在怎么做 | 改完怎么做 | 为什么 |
|------|-----------|-----------|--------|
| **实体抽取**（路线、桩号、时间、病害类型） | 规则匹配 `parse_route()` / `parse_pile_range()` / `parse_time_range()` | **保留规则** | 这些是精确实体匹配，规则已经很准了，不需要 LLM 再猜一遍 |
| **shape 识别**（count/distribution/list/top） | 关键词规则 `parse_query_shape()` | **换成 LLM** | "最多"可能是 top 明细，也可能是 GROUP BY 类型，规则分不清 |
| **group_by 识别**（按什么分组） | 硬编码几个维度 | **换成 LLM** | 规则只能认"分布/各路线"，"有图片和没图片分别"就认不出来 |
| **metric 识别**（count/sum/avg/ratio） | 关键词规则 `_detect_metric_specs()` | **换成 LLM** | 单指标规则还行，多指标组合就不行了 |
| **SQL 拼装** | Python 函数写死 SQL 形状 | **换成 LLM 写 MDL-SQL** | 每个函数只能拼一种形状，组合爆炸 |
| **校验**（缺条件、格式检查） | `validate_semantics()` | **保留规则** | 这是确定性检查，规则比 LLM 靠谱 |

**一句话：实体抽取和校验保留规则，维度识别和 SQL 生成换成 LLM。**

### 2.3 模板退居二线

模板不再是"默认路径"，而是"快速通道"——只处理最简单、最高频的单条件查询：

**模板保留（快速通道）：**
- 单条件计数："西乡段泛油有多少处？"
- 单条件明细："西乡段 K1+K3 有哪些病害？"
- 单指标最大："西乡段最大的病害是哪条？"

**模板放弃（交给 Wren）：**
- 任何 GROUP BY / 分组统计
- 任何占比 / 比例 / 密度计算
- 任何多指标组合
- 任何多路线对比
- 任何后置计算（post_calc）
- 任何需要 JOIN 多张表的查询

### 2.4 拆分器和 Wren 打通

拆分器拆出的子问题，**一律走 Wren，不走模板**。

```
用户问题 → 拆分器拆成子问题
  → 子问题1（data）→ Wren 生成 MDL-SQL → 编译执行
  → 子问题2（data）→ Wren 生成 MDL-SQL → 编译执行
  → 子问题3（post_calc）→ 用前两个结果计算
```

不再让子问题走模板匹配——模板匹配不到就 Wren，匹配到了也是模板。子问题直接走 Wren，省掉模板匹配这一步。

## 三、具体改法

### 3.1 改路径优先级

**现在的逻辑（nl2sql.py / agent.py）：**
```python
if 模板匹配命中:
    走模板生成 SQL
elif Wren 可用:
    走 Wren 生成 MDL-SQL
else:
    走内置 LLM
```

**改成：**
```python
# 判断是否是"简单单条件查询"，是就走模板快速通道
if is_simple_single_query(plan):
    走模板生成 SQL
else:
    # 其他所有情况一律走 Wren
    if Wren 可用:
        走 Wren 生成 MDL-SQL
    else:
        走内置 LLM 兜底
```

### 3.2 什么算"简单单条件查询"（模板保留区）

满足**全部**条件才走模板：
1. 只有一个主体（一条路线，没有多路线对比）
2. 只有一个度量（要么 count，要么 sum，要么 avg，不组合）
3. 没有分组（没有"按类型/按方向/各/分别"）
4. 没有后置计算（没有"密度/占比/平均间距/差值"）
5. 没有多指标（没有"数量和面积"、"总数和平均"）

**不满足以上任意一条 → 走 Wren。**

### 3.3 拆分器子问题直接走 Wren

orchestrator.py 里，拆出的每个子任务：
- 不再走 `match_template()`
- 直接走 `generate_mdl_sql()`
- Wren 编译失败再走模板兜底

### 3.4 Wren 提示词要补强

既然 Wren 是主力，提示词就要写好：

1. **明确告诉 LLM 可以用哪些聚合函数**：COUNT / SUM / AVG / MAX / MIN
2. **明确分组怎么写**：GROUP BY 什么字段，ORDER BY 什么
3. **明确占比怎么写**：SUM(CASE WHEN ...) / COUNT(*)
4. **明确路线长度用 route_length_km，不要用 distance**
5. **给几个完整示例**：分组统计、占比、多指标

## 四、预期效果

| 场景 | 现在 | 改完后 |
|------|------|--------|
| 数量最多的病害类型 | 返回明细 ❌ | GROUP BY 类型 + ORDER BY COUNT ✅ |
| 泛油占百分之多少 | 返回明细 ❌ | COUNT(泛油)/COUNT(*) ✅ |
| 平均每隔多少米 | 子问题走明细 ❌ | 病害总数 ÷ 路线长度 ✅ |
| 各类型数量和面积占比 | 走对了（因为模板匹配不到）✅ | 继续走 Wren ✅ |
| 多少种资产类型 | 只返回总数 ❌ | GROUP BY 资产类型 ✅ |
| 两条路三维度对比 | 漏指标 ❌ | 一次 GROUP BY 路线 ✅ |

**覆盖率从 3% 提升到多少？** 模板只做快速通道，Wren 覆盖剩余 97% 的组合空间。不用再一个个补模板了。

---

## 五、迁移步骤

1. **第一步**：改路径优先级判断逻辑（3.1），让 Wren 成为默认路径
2. **第二步**：定义"简单单条件查询"的判断规则（3.2），模板只保留这些
3. **第三步**：拆分器子问题直接走 Wren（3.3）
4. **第四步**：补强 Wren SQL 生成提示词（3.4）
5. **第五步**：跑综合问答数据集验证，对比改前改后准确率

**先改第一步和第三步，这两步改动最小、效果最明显。** 第二步和第四步可以后面慢慢调。
