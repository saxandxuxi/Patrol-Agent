## 二、风险点

### 2.1 P0 风险（阻断级，必须测）

#### RM-01：参数对齐错误导致数据与标签不匹配

**风险描述**：模板复用时，多个同类参数（如两个路线 id）按位置顺序填充，导致 avg_area CTE 里的路线和列别名写的路线不一致，用户看到的数字和标签对不上。

**真实案例**：用户问"西乡段泛油平均面积？恒明珠段面积大于该平均值的数量？"，SQL 里 avg_area CTE 用了恒明珠 id，主查询用了西乡 id，但列别名写的是"西乡段平均面积"和"恒明珠数量"——数据和标签完全反了。

**影响模块**：example_reuse.py（_fill_values）、templatizer.py（bind）

**测试要点**：
- 多对象问题的参数填充顺序
- 参数语义角色（avg_route_id vs count_route_id）
- SQL 列别名与参数的对应关系

#### RM-02：多余条件未清理导致查询范围错误

**风险描述**：模板沉淀时带了时间条件（如7月），用户复用时没问时间，系统没有去掉时间条件，导致查出来的是7月的数据而不是全量数据。

**真实案例**：用户问"恒明珠上下行各有多少病害"，第一次弹卡回答上行443/下行0（带了7月过滤），第二次Wren回答上行732/下行17（全量），两个答案矛盾。

**影响模块**：templatizer.py（bind/drop_conditions）、example_reuse.py

**测试要点**：
- 可选条件（时间/类型/阈值）未提供时是否被正确删除
- 必填条件（路线/主体）未提供时是否正确报错
- 删除条件后 SQL 是否有残留占位符
- 删除条件后查询范围是否正确

#### RM-03：结果总结丢失关键维度

**风险描述**：SQL 查询结果是二维分组（路线×巡检方式），但总结函数只支持一维分组，导致只说了总数，没说各分组的数值。

**真实案例**：用户问"西乡段和恒明珠段里，人工巡检和车辆巡检各有多少？"，控制台表格正确（路线×{人工,车辆,总数}），但AI总结只说了749/911，完全没提人工巡检和车辆巡检的数值（人工巡检均为0）。

**影响模块**：agent.py（_grouped_summary/_primary_metric/_label_column）

**测试要点**：
- 一维分组总结是否正确
- 二维分组总结是否列出所有数值列
- 多指标单行结果是否列出所有指标
- 某维度全为0时是否正确说明

#### RM-04：复合问题只答一半

**风险描述**：用户问了多个子问题（如"上下行各多少？上下行最多的类型分别是什么？"），模板只答了第一个子问题，第二个子问题被忽略。

**真实案例**：用户问"恒明珠上下行各多少？上下行最多的类型分别是什么？"，第一次弹卡只答了上下行数量（443/0），没答最多的类型。

**影响模块**：agent.py（复合题闸门）、capabilities.py（deterministic_only）、templatizer.py（partial_answer 检测）

**测试要点**：
- 复合问题的子问题拆分是否完整
- 整题模板闸是否只接完整回答的模板
- partial_answer 标记是否准确
- 部分覆盖时是否如实说明

#### RM-05：选表错误导致查不到数据

**风险描述**：用户问的字段在A表，但系统选了B表（B表没有这个字段），导致查不到数据或查错数据。

**真实案例**：用户问"路段的起止桩号"，系统选了桩点表（sections_pile_detail），但桩点表没有起止桩号字段，正确应该是路段表（basic_facilities_sections）的 start_num/end_num。

**影响模块**：nl2sql.py（select_tables）、field_grounding.py（表级证据）

**测试要点**：
- 字段触达的表级证据是否准确
- 同名字段在多张表时的选择逻辑
- 落点表是否真的"答得出来"用户点名的列
- 并列表的处理是否正确

### 2.2 P1 风险（重要，应该测）

#### RM-06：枚举字段未参数化

**风险描述**：模板挖掘时，WHERE 条件里的枚举值（如 level='0' 表示国道）没有被参数化，导致模板只能查国道，不能查省道/县道。

**真实案例**：用户问"列出行政等级为国道的所有路线"，SQL 里 level='0' 是写死的，没有变成 {{admin_level}}。

**影响模块**：templatizer.py（mine_sql/_classify_column）

**测试要点**：
- 有 code_map 的列在 WHERE 条件里出现时是否被参数化
- 枚举值是 code（'0'）还是 label（'国道'）时都能识别
- 枚举槽位的 options 是否从 code_map 动态生成
- 复用时中文→code 的映射是否正确

#### RM-07：JSON 字段（pic_position）未全量支持

**风险描述**：ai_problem.pic_position 是 JSON 字段，存了 confidence/type/width/height/lat/lng/x0/x1/y0/y1，但代码只注册了 confidence，其他字段查询时调不出来。

**真实案例**：用户问"调出横向裂缝的图片"，系统不知道 type 字段在 JSON 里，调不出来。

**影响模块**：field_catalog.py（_SPECIAL_FIELDS）、nl2sql.py（逻辑字段映射）

**测试要点**：
- pic_type/pic_width/pic_height/pic_lng/pic_lat 是否能被查询
- JSON 字段查询时是否自动加 pic_position IS NOT NULL
- JSON 数值字段是否正确 CAST AS DECIMAL
- pic_type 和 damage_type 的区分是否正确

#### RM-08：LLM 审核误报导致好模板被降级

**风险描述**：LLM 审核把"参数正常用法"（如参数用于 WHERE 过滤、参数名与问法里的实体名不一致）误判为 parameter_misaligned，导致好模板被降级，不能进推荐。

**真实案例**：40条模板中8条被降级，其中4条是误报（误报率55%）。

**影响模块**：templatizer.py（review_template）、prompts/template_review.md

**测试要点**：
- 单花括号参数格式是否被正确识别（真问题）
- 参数用于 WHERE 过滤是否被误判（应该是正常用法）
- 参数名与问法实体名不一致是否被误判（应该是正常的）
- del_flag=0 固定条件是否被误判为硬编码（应该不是）
- 被误降的模板是否能一键恢复

#### RM-09：模板参数 options 静态化导致新增路线不可用

**风险描述**：模板沉淀时，route_id 的 options 是当时连库查的快照（只有3条路线），以后新增路线后，模板的 options 不会自动更新，导致新路线不能复用这个模板。

**影响模块**：templatizer.py（_entity_options/_options/coerce）

**测试要点**：
- 模板里存的 options 是静态快照还是动态查询
- 新增路线后，旧模板是否能识别新路线
- coerce 映射失败时是否有 fallback 机制
- options 缓存 TTL 是否合理

#### RM-10：Wren MDL 与物理 SQL 不一致

**风险描述**：语义检索读的是 YAML 源文件（models/cubes/overrides/relationships），SQL 编译读的是 target/mdl.json（编译产物），改了 YAML 后只清了一个缓存，导致"语义检索说有这个列，但编译说找不到"。

**影响模块**：wren_engine.py、mdl_sync.py、nl2sql.py（_load_mdl）

**测试要点**：
- 改了 YAML 后是否同时清了 _load_mdl 缓存和重新编译 mdl.json
- 语义检索和 SQL 编译用的是否是同一份 MDL
- 跨库（MySQL/PostgreSQL）的 MDL 是否分开
- MDL 编译失败时的降级处理

### 2.3 P2 风险（一般，可以测）

#### RM-11：元数据查询误判为业务查询

**风险描述**：用户问"库里都有啥表""哪些表是空的"这类元数据问题，系统当成业务查询去业务表里找 table_name 字段，报错。

**影响模块**：intent.py（metadata 分类）、metadata_service.py、agent.py

**测试要点**：
- 元数据问题的语义分类是否准确
- 元数据查询是否走 information_schema 而不是 Wren
- 跨库元数据查询是否合并两个库的结果
- 元数据问题是否不做跨库拆分

#### RM-12：多库查询路由错误

**风险描述**：用户问的字段在 PostgreSQL 库，但系统路由到了 MySQL 库，导致查不到数据。

**影响模块**：cross_db.py、db.py、nl2sql.py（选库逻辑）

**测试要点**：
- 选库逻辑是否基于字段触达的表级证据
- 偏向 MySQL 的问题是否存在（另一个库表少但也有数据）
- 跨库 JOIN 是否正确处理
- 两个库都有同名字段时的选择逻辑

#### RM-13：上下文补全错误

**风险描述**：长对话中，上下文补全把上一轮的条件错误地带到这一轮，或者该带的没带。

**影响模块**：nl2sql.py（contextualize）、memory.py

**测试要点**：
- 上一轮的路线/时间/类型条件是否正确延续
- 用户明确换了主题时是否清除旧条件
- 长对话（10轮以上）的上下文是否准确
- 上下文补全是否调用 LLM（长对话时的性能和准确性）

## 四、已知未覆盖

### 4.1 技术限制导致的未覆盖

| 未覆盖项 | 原因 | 建议 |
|---|---|---|
| LLM 输出的随机性 | 同一个问题问两次，LLM 可能给出不同的 plan/SQL | 每次测试跑 3 次，记录一致性 |
| 数据库隧道不稳定 | SSH 隧道断了会导致连库失败 | 测试前确认隧道正常，失败时记录为环境问题 |
| Wren 编译环境 | Wren 项目名/路径配置不对会导致编译失败 | 测试前确认 Wren 环境正常 |
| 长对话上下文 | 需要构造 10+ 轮对话，耗时 | 单独做长对话专项测试 |

### 4.2 方案层面的未覆盖（后续迭代）

| 未覆盖项 | 说明 |
|---|---|
| 性能测试 | 响应时间、并发量、资源占用，需要单独做压测方案 |
| 安全测试 | SQL 注入、越权访问、敏感数据泄露 |
| 兼容性测试 | 不同浏览器、不同分辨率、不同操作系统 |
| 异常恢复测试 | 数据库断连、LLM 超时、Wren 崩溃后的恢复能力 |
| 数据一致性测试 | 同一问题走不同链路（模板/Wren/通用算子）的结果是否一致 |

## 五、测试执行建议

### 5.1 执行顺序

1. **先跑 F4 结果总结**（8题）——不依赖 LLM，纯代码逻辑，最快验证
2. **再跑 F1 NL2SQL 主链路**（15题）——核心功能，重点验证
3. **然后 F2 模板复用**（12题）——当前问题最多的链路
4. **接着 F5 字段触达**（8题）——冷门字段覆盖
5. **最后 F3/F6/F7/F8/F9/F10**——辅助功能

### 5.2 每题执行步骤

1. 发送问题到后端 API（POST /api/chat）
2. 记录返回的 plan、SQL、执行引擎、结果
3. 连库独立执行 SQL，验证结果是否正确
4. 检查总结是否完整（多指标/多维度是否都列出来）
5. 记录实际行为和预期的差异

### 5.3 缺陷分级

- **P0**：数据错误（查错表/查错列/参数填反/条件没删）——阻断发布
- **P1**：总结缺失（多指标少说了/分组没列全）——影响用户信任
- **P2**：性能问题（响应慢/弹卡慢）——体验问题
- **P3**：界面/文案问题——美观问题
