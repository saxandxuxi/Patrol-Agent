# 人工存入 RAGFlow 的问答对全部参与模板挖掘（给 codex）

## 一、结论先行

RAGFlow「SQL问答示例」数据集里的题，按产品定义**全部是人工确认过的**（前端 KnowledgeManager.vue:87 明确写着"只有你在对话里点过『结果正确，存入示例库』的案例才会进这里，任何引擎的 SQL 都不会自动入池"）。用户要求：**凡是人工同意存入 RAGFlow 的问答对，都应能被挖成模板**，不能只挖本地 trusted=1 的十几条。

现状是同步链路有个缺口，把这批人工题挡在了挖掘之外。本方案把"人工池"的事实源统一好，让它们全部可挖；但**模板成熟度的安全验证一条不放松**。

## 二、事实与根因（均已核对代码 / 本地库）

1. 人工确认的写入链路是对的：对话里点「结果正确，存入示例库 / ⭐固化到看板」走 `chat.py:214 approve_result` → `save_successful_pair(template=True)`（chat.py:242）→ 本地 `trusted=1` 并写入 RAGFlow，随后异步 `templatizer.mine_all()`（chat.py:256、265-278）。

2. 挖掘只认本地 trusted：`templatizer.mine_all()`（templatizer.py:1343-1364）取数条件是 `row.get("trusted")` 且有 sql_text（1355-1359）。trusted=0 的行根本不进挖掘。

3. 本地 `agent.db` 的 example_pairs 表实测 60 条、全部 board=1、全部有 SQL，但 **trusted=1 只有 13 条（9 物理 + 4 MDL），其余 47 条 trusted=0**。管理页"示例库同步"显示"本地 60 · 已确认 13 · 带 SQL 60 · RAGFlow 文档 60"。

4. 47 条为什么 trusted=0：`nl2sql.import_ragflow_examples()`（nl2sql.py:6114-6180）从 RAGFlow 反向同步时——
   - 新增的文档走 `add_example_pair(question, sql, name, True, spec)`（6170-6176），第 4 个参数 True 确实写 trusted=1；
   - 但对**本地已存在**的 doc，在 6151 行命中 `if name in known ... continue`，6161-6165 只补 spec_json，**从不回填 trusted**。
   - 于是历史上以 trusted=0 落库的人工题（早期版本同步、清库重建、或先被自动采集占位后又在 RAGFlow 确认），即使 RAGFlow 里早就有人工确认身份，本地永远是 0，挖掘器永远看不到。这是"60 多条人工题只挖出 5 条"的直接原因。

5. 注意区分：board（是否上固定看板）建表默认就是 1，**不能**当作人工凭据；人工凭据只有两个来源——① 本地 approve 的 trusted 标记，② 存在于 RAGFlow「SQL问答示例」数据集。纯自动采集、没进 RAGFlow 的 few-shot 必须保持 trusted=0、不挖。

## 三、改造要求

### P0-1 统一"人工池"事实源
- 定义：trusted=1 等价于"人工确认样本"=（本地 approve 的）∪（RAGFlow 示例集里有的）。
- 挖掘器 `mine_all` 继续只认 trusted 这一个标记，**不要**让挖掘器直接去耦合/实时请求 RAGFlow；做法是用同步对账把 trusted 补对，保持单一事实源。

### P0-2 同步时对账回填 trusted（修核心缺口）
- `import_ragflow_examples` 里，对 RAGFlow 中存在的每个 doc：
  - 新增：维持 `add_example_pair(..., trusted=True, ...)`；
  - 已存在：除补 spec 外，必须把该行 trusted 置 1（在 store.py 新增按 doc_name 批量置 trusted 的方法，如 `mark_examples_trusted(doc_names)`，或在已存在分支 update）。
- 不允许再出现"RAGFlow 里有人工确认、本地却 trusted=0"。

### P0-3 一次性回填（让存量立即生效）
- 在"立即同步"（dashboard.sync-examples → import_ragflow_examples(force=True)）里做一次全量对账：拉取 RAGFlow 示例集全部 doc_name，把本地对应行统一 trusted=1。
- 回填后管理页"已确认"应从 13 升到与人工池一致（当前数据应为 60/60，以 RAGFlow 实际文档数为准），并在返回里给出 `trusted_backfilled` 计数，方便核对。

### P0-4 守住反向边界（防止把自动采集的也挖了）
- 只有"approve 标记"或"在 RAGFlow 示例集内"才能置 trusted=1；
- 仅本地自动采集、未推 RAGFlow、未 approve 的 few-shot 保持 trusted=0，不参与挖掘、不进直放；
- board/pinned 不得作为 trusted 的依据。

### P0-5 准入放宽，验证不放宽
- 对账后重跑 mine_all，候选池从 13 扩到整个人工池；
- 但模板成熟度仍按现有规则判定，不得因为"是人工存的"就跳过：只读单 SELECT、表白名单、仅 AND、谓词可挖、必须有可变槽且带业务过滤、槽位上限、结构指纹聚类、回填回环结果一致；
- 取值域天然可变的槽（路线/病害类型/时间/阈值）单样本可 mature；编码枚举类槽（上下行/收藏/工单状态/有无图片）只见过一个值时仍落 **candidate**，人工转正后才进对话推荐；
- 不可泛化的（如纯空间窗口 `pile_distance BETWEEN ...` 且无其他业务过滤）按现有规则落 candidate 或拒，不硬挖；
- MDL 在本机编译不出物理 SQL 的（审计里的里程桩点、luge_name、最大宽高、西乡泛油计数等），标为"待补物理 SQL"，配合下面的 backfill 在 Wren 正常环境补齐，**不静默丢弃、也不伪造物理 SQL**。

### P0-6 多路线 / 多值槽保持一致
- "几车道（rid IN ('id1','id2')）"审计原因是"rid IN 不可泛化"。现在多值槽已支持（templatizer.py:528-545 挖成单个 multi 槽、bind 时 1651-1653 用 `','` 拼多值；nl2sql.py:6049-6081 另有 `{route_id}/{route_id_2}` 编号回填）。
- 统一这两处的占位与回填口径（要么都用单占位 multi，要么都用编号，不要两套并存），确保 spec.routes/route_ids 能按序填回；对账重挖后，"两条路分别是几车道"应能成模板而不是进 rejects。

### P0-7 管理页与按钮可见性
- "给 Wren 示例补物理 SQL"按钮源码已在 `AdminPanel.vue:139-146`，位置在页面底部「**示例库同步**」卡片内、"立即同步"按钮的下方（不在对话页/看板页）。用户截图只滚到该卡片标题，没看到下面的按钮——请确认部署的前端 dist 是最新构建（必要时重新 `npm run build`），并提示强刷（Ctrl+F5）。
- 可顺手把"补物理 SQL"按钮与"立即同步"并排放在卡片头部，避免再被当成没有。
- 同步状态里的"已确认 N"在对账后要即时刷新。

## 四、验收（连库 / 界面断言）
1. 点一次"立即同步"后：example_pairs 中 trusted=1 的条数 == RAGFlow「SQL问答示例」文档数（当前应为 60）；返回含 trusted_backfilled 数量（约 47）。
2. 重跑 mine_all：日志 `pairs` 从 13 升到人工池规模；mature 条数增加；candidate 单独计数、不进对话推荐。
3. 自动采集但未入 RAGFlow/未 approve 的样本仍 trusted=0、不进挖掘（构造一条验证）。
4. "两条路分别是几车道"在重挖后成为可复用模板（多路线槽正确）；点确认卡能换路线直接出结果。
5. 4 条 MDL 在 Wren 可用时点"给 Wren 示例补物理 SQL"补上物理版后可被挖；Wren 不可用时明确标"待补"，不产生废模板。
6. 任何模板命中后仍必须由用户在确认卡点选才执行，不自动直放（本条不变）。
