# 第一部分：长对话Bug总结与整改方案

> 基于用户实测的长对话，总结4个核心bug。
> 这些bug都是"长对话补全不够智能"导致的。

---

## Bug 1：图片查询找不到图

### 现象
```
R1：西乡段7月30日有多少处泛油？ → 185处
R2：能看看这些病害的照片吗？ → 没有找到相关病害图片
```

### 问题
- 继承了条件（西乡段、7月30日、泛油）✅
- 但为什么找不到图片？是真的没有，还是SQL写错了？
- 应该继承所有过滤条件，去查这些病害的problem_url

---

## Bug 2：拆分器乱拆，不该拆的拆了

### 现象
```
R3：GPS轨迹也一起看？ → 拆成了2个子问题：
  子问题1：185条病害明细
  子问题2：GPS轨迹（未查到）
```

### 问题
- 用户就是要GPS轨迹，不需要拆成两个子问题
- 应该：继承所有过滤条件（西乡段、7月30日、泛油），只换查询对象（从病害明细→GPS轨迹）
- 拆成两个子问题是多余的，而且第一个子问题是重复查询

---

## Bug 3：过滤条件丢失

### 现象
```
R1：全库泛油里面积正好7.52㎡的有几处？ → 17处
R2：其中西乡段的有多少？ → 12处
R3：把西乡段所有满足面积正好7.52㎡的病害的明细全部调出来 → 返回了500条各种面积的
```

### 问题
- R3用户明确说"面积正好7.52㎡"，但结果里各种面积都有
- **过滤条件丢了！** 上下文补全的时候把"面积=7.52"这个条件丢了
- 而且R3用户说"所有...病害"，应该去掉"泛油"的过滤，但系统还是带着泛油

---

## Bug 4：纠正条件不生效

### 现象
```
R3：把西乡段所有满足面积正好7.52㎡的病害的明细全部调出来 → 返回了500条各种面积的
R4：我的意思是面积为7.52平方米的西乡段的病害明细，不是所有的 → 还是返回了500条
```

### 问题
- 用户明确纠正了："我的意思是面积为7.52㎡，不是所有的"
- 但系统还是返回了500条，纠正条件根本没生效
- 说明上下文补全的时候，没理解用户在纠正什么

---

## Bug 5：时间范围理解反了（新发现）

### 现象
```
R1：西乡段7月份的病害类型有哪些？ → 0处，数据从7月15才开始
R2：那西乡段7月15开始采集的病害里，类型有哪些？ → 还是0处，还是说数据从7月15才开始
```

### 问题
- 用户R2的意思是：**"好，那我把起点改成7月15开始"**
  - 正确的时间范围应该是 [7月15, 7月30] → 有911处
- 但系统理解成了：**"7月份里面，到7月15为止"**
  - 错误的时间范围是 [7月1, 7月15] → 确实是0处

### 根因
1. 上下文补全不知道"那我从X开始算"是**修改起点**，不是加一个终点
2. 时间解析可能也有问题："X开始"应该解析成 `time_start`，不是 `time_end`

### 整改
- 上下文补全要识别这种"修改时间起点/终点"的操作
- 时间解析要搞清楚："从X开始" → time_start = X；"到X为止" → time_end = X

---

## Bug 6："那次/那个"的具体ID没继承（新发现）

### 现象
```
R1：7月份西乡段一共巡检了几次？每次发现多少？ → 10次巡检，各有多少
R2：哪次巡检发现的病害最多？ → 找到了：巡检ID=xxx，104处
R3：把那次巡检的病害明细调出来 → 返回了0处，说时间范围不对
```

### 问题
- R3说的"那次巡检"，指的是R2找到的"最多的那次"
- 但SQL里没有按巡检ID过滤，反而把巡检ID当成了时间条件
- 所以时间范围算错了，返回0处

### 对比：为什么R1回答得很好，后面就不行了？
- R1：不需要上下文补全，直接查数据+综合分析 → 有数据、有判断、有建议 ✅
- R2/R3：需要长对话补全 → 补全错了，后面全垮了 ❌

**结论：长对话补全是短板，补全错了，后面的分析再智能也没用。**

### 根因
1. 长对话补全只继承了"粗条件"（路线、时间），没继承"细条件"（具体哪次巡检）
2. R2系统自己算出了"最多的巡检ID=xxx"，但没把这个ID存到上下文里
3. R3的时候，"那次巡检"这个指代，没有对应到具体的巡检ID

### 整改
- 上一轮的查询结果里，如果有"唯一一条"（比如"最多的那次"），要把它的ID存到上下文
- 下一轮说"那次/那个"的时候，要能对应到上一轮找到的具体ID
- 比如："那次巡检" → 上一轮找到的巡检ID = xxx

---

## Bug 7：拆分器过度拆分，把简单问题拆成4步（新发现）

### 现象
```
用户问：病害密度最高的那条路，病害类型主要是什么？

系统拆成了4个子问题：
  子问题1：所有路线的病害总数
  子问题2：所有路线的长度
  子问题3：算密度，还说数据对不上
  子问题4：直接给出结果：西乡段密度最高，泛油为主
```

### 问题
- 前3个全是多余的！第4个才是答案
- 一个简单的问题，被拆成了4步，浪费时间和LLM调用
- 而且前3步还出错了（算密度说数据对不上）

### 根因
1. **拆分器过度拆分**：把一个可以合并成一个SQL的问题，拆成了"算密度→找最高→查类型"三步
2. **没利用上一轮的上下文**：上一轮已经说了"西乡段密度最高"，这一轮用户说"密度最高的那条路"就是指西乡段，不需要再重新算

### 整改
1. **拆分器不要过度拆分**：一个问题能一个SQL搞定的，就不要拆成多个子问题
2. **要利用上一轮的上下文**：上一轮已经找到的结果（比如"最高的那条路"），下一轮直接用，不要重新算
3. **判断标准**：用户问的问题，如果上一轮已经回答过前半部分，就直接继承，不要再重新查一遍

---

## 根因分析

### 根因1：上下文补全不知道"什么时候该继承、什么时候该替换、什么时候该加新条件"

现在的补全是：
- 规则判断：是不是追问？是不是纠正？
- 是追问 → 继承所有旧条件
- 是纠正 → 替换条件
- 否则 → 新话题

**问题：判断太粗了，不知道：**
- 用户说"把明细调出来" → 应该继承所有旧条件（路线、时间、面积、病害类型），只换输出形式（从计数→明细）
- 用户说"所有...病害" → 应该去掉"泛油"的过滤，加"面积=7.52"的过滤
- 用户说"GPS轨迹也一起看" → 应该继承所有过滤条件，只换查询对象

### 根因2：纠正条件不生效

用户说"我的意思是...不是..."，这是在纠正之前的理解。
但系统不知道用户在纠正什么，只是机械地把新句子拼上去。

### 根因3：拆分器乱拆

"GPS轨迹也一起看？" → 不该拆成两个子问题。
应该是：继承所有过滤条件，只换查询对象。

---

## 整改方案

### 1. 上下文补全要更细地判断"操作类型"

现在的操作类型太少了，加几种：

| 操作类型 | 特征词 | 做法 |
|---------|--------|------|
| 换输出形式 | 把明细调出来、列出来、看看 | 继承所有过滤条件，只换输出形式（计数→明细） |
| 换查询对象 | GPS轨迹也一起看、照片呢 | 继承所有过滤条件，只换查询对象 |
| 加过滤条件 | 其中XX的、里面XX的 | 继承所有旧条件，加新过滤 |
| 替换过滤条件 | 不是所有的、我的意思是 | 把对应的旧条件换成新的 |
| 去掉过滤条件 | 所有病害、不限类型 | 去掉对应的过滤条件 |

**关键：要判断用户这句话是在"继承、替换、加新、去掉"哪种操作。**

### 2. 纠正条件要真正生效

用户说"我的意思是...不是..."，要：
1. 识别出用户在纠正哪个条件
2. 把那个旧条件换成新的
3. 其他条件继承

### 3. 拆分器不要乱拆

"GPS轨迹也一起看？"这种短追问，不该拆成两个子问题。
应该是：继承所有过滤条件，只换查询对象。

---

## 为什么现在长对话这么蠢？

**因为现在的补全是"机械拼接"：**
- 是追问就把旧条件全加上
- 是纠正就把新句子拼上去
- 不知道用户具体在改哪个条件

**真正智能的补全应该是：**
1. 先拆上一轮的所有条件
2. 再看用户这句话：是要加哪个？换哪个？去哪个？
3. 然后重新拼完整的问题

这就是你和我对话很流畅，但系统很蠢的原因——你是真理解，系统是在拼字符串。

# 第二部分：长对话中"数据+知识"综合分析方案

> 场景：先查数据出个表格，然后结合表格+知识库规范做分析。
> 现在的系统处理不了，因为只会把两个子任务的结果拼起来，不会综合分析。

---

## 一、举个例子

```
R1：西乡段各病害类型有多少？
   → 系统查数据库，返回表格：
     泛油：534处
     未识别：377处

R2：结合上面的表格，按养护规范分析一下西乡段的病害情况
   → 系统应该怎么做？
```

---

## 二、真正智能的系统是怎么处理的？

### 第一步：理解用户意图
用户要的不是"再查一遍数据"，也不是"再查一遍规范"，而是：
> 把上一轮的数据 + 养护规范，结合起来分析，给出结论。

### 第二步：把上一轮的数据拿过来
上一轮的表格：
- 泛油：534处
- 未识别：377处
- 总计：911处

### 第三步：去知识库查相关规范
查"路面病害养护规范"：
- 泛油的判定标准是什么？
- 不同病害类型的养护要求是什么？
- 什么情况下算严重？需要优先处理？

### 第四步：把数据和规范都给LLM，让它综合分析

### 第五步：LLM输出综合分析结论
输出：
> 西乡段总共911处病害，其中泛油534处（58.6%），未识别377处（41.4%）。
> 
> 从养护规范来看：
> 1. 泛油属于轻微病害，占比最高，但可以延后处理
> 2. 未识别病害占比41.4%，说明AI识别准确率不高，需要优先安排人工复核
> 3. 整体来看，西乡段病害数量多，但以轻微类型为主，养护优先级中等。
> 
> 建议：先集中人工复核未识别的377处病害，确认类型后再制定养护计划。

---

## 三、现在的系统为什么处理不了？

### 现在的流程
```
R2："结合上面的表格进行巡查分析"
   ↓
意图分类 → composite（数据+知识）
   ↓
拆分器 → 拆成两个子任务：
   子任务1：查数据 → 西乡段各病害类型有多少？
   子任务2：查知识 → 路面病害养护规范
   ↓
分别执行两个子任务
   ↓
把子任务结果拼起来：
   "数据查询1：泛油534处，未识别377处。
    知识查询2：泛油的养护标准是..."
   ↓
返回用户
```

**问题：**
- 只是把两个子任务的结果拼起来，没有"综合分析"
- 没有把数据和规范放在一起让LLM推理
- 用户要的是"结合分析"，不是"分别给我"

---

## 四、怎么改？

### 1. 加一种新的子任务类型：综合分析（analysis）

在拆分器里，加一种类型：
```python
type = "analysis"
depends_on = ["task1", "task2"]  # 依赖前两个子任务
```

### 2. 执行子任务的时候，analysis类型要等所有依赖都完成了再执行

执行顺序：
1. 先执行 task1（查数据）
2. 再执行 task2（查规范）
3. 最后执行 task3（综合分析）：把task1和task2的结果都给LLM，让它综合分析

### 3. 综合分析的提示词（直接抄到 prompts/analysis.md）

```markdown
[system]
你是道路巡检养护领域的资深专家。
你要基于"数据查询结果"和"知识库规范/标准"，回答用户的问题。
你不是简单罗列数据，要做专业的分析和判断。

你能分析的角度（根据用户问题选对应的角度）：

【数据统计类】
- 数量/规模：有多少？占比多少？
- 分布情况：集中在哪里？哪条路多？哪段路多？
- 排名对比：哪个最多？哪个最少？排个序
- 变化趋势：越来越多？越来越少？涨得快还是慢？

【判断评估类】
- 好坏判断：路况好不好？严不严重？靠谱吗？
- 优先级判断：先做什么？后做什么？重点在哪？
- 原因分析：为什么会这样？是什么导致的？

【建议方案类】
- 养护建议：应该怎么处理？
- 资源建议：钱/人力应该投在哪里？
- 后续建议：下一步应该做什么？

硬规则：
1. 先直接回答用户的问题，不要绕
2. 每个结论都要有数据或规范支撑，不要空泛
3. 如果数据不足或信息不够，就如实说，不要瞎编
4. 分点说清楚，不要一大段
5. 用中文，口语化，像专家在跟人解释

[user]
用户问题：<<question>>

数据查询结果：
<<data_result>>

知识库/规范：
<<knowledge_result>>

请基于以上信息，回答用户的问题，做专业分析。
```

### 4. 长对话里要能拿到上一轮的表格数据

R2说"结合上面的表格"，要：
1. 识别出"上面的表格"指的是上一轮的查询结果
2. 把上一轮的表格数据拿过来
3. 作为综合分析的输入

---

## 五、总结

**现在的系统：** 只会把子任务结果拼起来 → "数据是XX，规范是XX"
**改完之后：** 会把数据和规范放在一起，让LLM推理 → "结合数据和规范，得出结论XX"

这就是"智能问答"和"问答机器人"的区别：
- 问答机器人：分别给你
- 智能问答：帮你分析

# 第三部分：多步推理问题的智能处理方案

> 场景："西乡段的路况好不好？不好的话该如何养护，重点养护哪些路段？"
> 特点：有依赖关系，不是拆成几个子任务并行跑，而是一步一步来，每一步根据结果决定下一步。

---

## 一、这个问题难在哪？

```
西乡段的路况，好不好？不好的话该如何养护，重点养护哪些路段？
```

**这句话里有三层：**
1. **判断：** 路况好不好？（先查数据）
2. **条件分支：** 如果不好，该怎么养护？（查规范）
3. **具体落地：** 重点养护哪些路段？（结合数据+规范）

**关键是：这三步是有依赖的！**
- 必须先知道"好不好"，才知道要不要查规范
- 必须先知道"哪些路段病害多"，再结合规范判断"哪些要重点养护"

不是拆成几个子任务并行跑就行的。

---

## 二、智能的处理流程

### 第一步：理解用户问题的结构

用户要的是：
1. 先判断路况好不好
2. 如果不好，给养护建议
3. 还要指出具体哪些路段要重点养护

**不是一个简单的SQL查询，是一个完整的分析过程。**

---

### 第二步：先查数据，判断路况好不好

**查什么？**
- 总病害数量
- 病害密度（处/公里）
- 病害类型分布
- 平均面积
- 各路段的病害分布

---

### 第三步：如果不好，再查养护规范

**判断：** 路况不好 → 需要查养护规范

**查什么？**
- 路面病害养护标准
- 什么情况下需要重点养护
- 不同类型病害的处理优先级

---

### 第四步：综合分析，给出结论

**把数据和规范都给LLM，让它综合推理。**

---

## 三、现在的系统为什么处理不了？

**现在的做法：**
```
用户问题 → 拆分器拆成几个子任务 → 并行执行 → 拼结果
```

**问题：**
1. **没有"判断"这一步：** 不知道路况好不好，不知道要不要查规范
2. **没有依赖关系：** 所有子任务并行跑，不知道哪个要先做
3. **没有"综合分析"：** 只是把子任务结果拼起来，不会根据数据做推理

---

## 四、怎么改？

### 1. 拆分器提示词要加"多步推理"的识别（直接抄到 prompts/decompose.md）

```markdown
[system]
你是道路巡检智能体的查询任务拆解器。
你要把用户的问题拆成可独立执行的子任务，并明确子任务之间的依赖关系。

判断规则：
1. 如果问题是"先判断A好不好，不好的话再B" → 拆成两步：
   - task1：查数据判断A好不好
   - task2：如果不好，再查B
   - task3：综合分析（依赖task1和task2）

2. 如果问题是"数据 + 知识建议"混合 → 拆成两步：
   - task1：查数据
   - task2：查知识规范
   - task3：综合分析（依赖task1和task2）

3. 如果问题只是"列几个数据" → 不用拆，一个子任务就行

输出格式：
{
  "tasks": [
    {
      "id": 1,
      "type": "data",
      "question": "第一步要做什么"
    },
    {
      "id": 2,
      "type": "knowledge",
      "question": "第二步要做什么"
    },
    {
      "id": 3,
      "type": "analysis",
      "question": "综合分析",
      "depends_on": [1, 2]
    }
  ]
}

示例：
输入：西乡段的路况好不好？不好的话该如何养护？
输出：
{
  "tasks": [
    {"id": 1, "type": "data", "question": "西乡段的病害数量、密度、类型分布是多少？"},
    {"id": 2, "type": "knowledge", "question": "路面病害养护规范是什么？"},
    {"id": 3, "type": "analysis", "question": "结合数据和规范，分析西乡段路况好不好、该如何养护", "depends_on": [1, 2]}
  ]
}
```

### 2. 执行顺序是动态的

不是固定先跑哪个子任务，而是：
1. 先跑第一步（查数据判断好不好）
2. 根据结果决定：要不要查规范？
3. 再跑第三步（综合分析）

### 3. 最后一步是"综合分析"

把前面所有步骤的结果，都给最后一步的LLM，让它综合推理。

---

## 五、这就是智能体和流水线的区别

| 流水线（现在） | 智能体（改完） |
|-------------|-------------|
| 先拆好所有子任务 | 一步一步来，根据结果决定下一步 |
| 所有子任务并行跑 | 有依赖的串行执行 |
| 最后拼结果 | 最后综合分析，给出结论 |
| 机械执行 | 有判断、有推理 |

**核心区别：**
- 流水线：你说什么我做什么，一步一步按流程走
- 智能体：我理解你要什么，自己想办法分步完成

| 优先级 | 改动 | 效果 |

## 附：分档对比（bucket_compare）的输出规范

> 比如"新长出来的多还是早就有的多"、"集中在一头还是两头"

### 必须做到：

1. **必须带所有过滤条件**（路线、时间、病害类型等）
   - 不能查成全库！西乡段的问题就要带 `r.id = 'xxx'`

2. **必须说明分界线是什么**
   - 时间分档：要告诉用户"按7月29日17:27分，之前算旧的，之后算新的"
   - 桩号分档：要告诉用户"按2.5km分，0-2.5km算前段，2.5-5.1km算后段"
   - 不能只说"前段289处，后段334处"，不说怎么分的

3. **两边数量加起来要等于总数**
   - 如果总数是911，分档结果加起来也应该是911
   - 不对就说明SQL有问题（比如查成全库了）

### 反例（现在的错误输出）：
> 早就有的 851处、新长出来的 851处。

**问题：**
- 没说分界线是什么时候
- 加起来1702，和西乡段911对不上（查成全库了）

### 正例（应该怎么输出）：
> 按采集时间中位数（7月29日17:27）分：之前算"早就有的"，之后算"新长出来的"。
> 
> 西乡段总共911处：
> - 早就有的（7月29日之前）：约450处
> - 新长出来的（7月29日之后）：约461处
> 
> 两边差不多，说明病害不是突然冒出来的，是慢慢积累的。
