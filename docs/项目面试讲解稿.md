# 巡检智能体项目面试讲解稿

## 一、三十秒版本

这是一个让业务人员用大白话查道路养护数据的系统。以前查一条路有多少病害、哪种类型涨得最快，得会写 SQL 或者提需求等技术排期。现在直接问一句话，系统给数，而且每个数都能点开看它实际执行了哪条 SQL、用了什么条件、数据截止到什么时候。

难点不在写 SQL，在选表和选列。十几张表里有大量同名列，一个字段选错，SQL 不报错，数字是错的。

## 二、为什么做这个项目

道路巡检的业务链条是这样的。巡检人员开车沿路采集，设备拍照片，系统记录病害位置、类型、尺寸。养护部门要根据这些记录决定先修哪条路、先治哪种病害、哪个路段要重点盯。

问题出在决策环节。数据都在库里，十几张表，巡检任务、路线、路段、病害、病害字典、设备、工单、资产台账。业务人员不会写 SQL，提需求给技术又要等。等数据出来，养护窗口可能已经过了。

所以这个项目要做的事很具体：把"哪条路病害最多""这个月比上个月多了还是少了""西乡段泛油多少处"这类问题，变成一句话就能问、几秒钟就能答、答完还能复核的东西。

## 三、整体逻辑，四步

整个系统只做四件事，顺序不能乱。

### 第一步，听懂问题

系统不抽关键词，而是把这句话拆成一张结构化的意图表。要判四件事。

问的是哪个对象。病害、路线、路段、巡检任务、设备还是资产。

问的是哪种形态。多少处、分布、趋势、明细、排名还是对比。

带哪些条件。路线、时间、病害类型、上下行、桩号区间、数值阈值。

有没有藏着第二问。"哪条路病害最多，多少处"实际上是两个问题，第一个是排名，第二个是计数，必须拆开。

这一步的产出不是 SQL，是一张意图表。这是整个设计的核心。因为 SQL 只是最后一步的表达方式，意图错了，SQL 写得再漂亮也是错的。

### 第二步，选路径

三条路径，按确定性从高到低排。

第一条是模板。这句话的结构如果跟库里某条验证过的模板完全对得上，直接套模板，不调模型，毫秒级出结果。模板本身跑过、验过，结果一定对。

第二条是语义层。模板接不住的复杂查询，分组统计、占比、密度、多指标、多路线，交给语义层。语义层的作用是给模型一份业务字典，写清楚每个业务概念对应哪张表哪个字段、怎么算、有什么口径约束。模型只在字典范围内选，不许自己发明字段。

第三条是通用生成。前两条都不行，才让模型自由写 SQL，写完必须过校验。

这个顺序的理由很直接。能用规则的不用模型，能用模板的不用生成，模型只在确定性覆盖不到的地方兜底。因为模板的错误可控，模型的错误不可控。

### 第三步，查

查之前有一道契约检查。问极值却没排序、问指标却给了明细视图、传进来的值是中文名但字段要编号，这些在生成 SQL 之前就拦下来，不让它跑出一条注定错的 SQL。

查之后还要验一遍。看结果形状对不对，看关键数字有没有出现在回答里，看行数是不是被截断。

### 第四步，回答

不是把结果原样倒出来，而是按问题形态决定怎么讲。

计数题给一句话加口径。分布题给排名加结论。趋势题给方向加提醒，首尾月份不完整就明说不能直接比大小。明细题给清单加指路，明细在结果工作台里看。

口径卡片附在最后，写清楚查了哪张表、用了什么条件、数据截止到什么时候。

## 四、高频问题怎么变成模板

这是这个项目最有价值的部分。逻辑分四层。

### 第一层，什么算高频

不靠人工统计，系统自己发现。

每次问答成功后，系统把这句话和它实际执行的 SQL 存成一对。存得多了，就按 SQL 的结构做聚类。结构一样、只有取值不同的那些，就是同一个问法。

举个例子。"G65 有多少处病害""S50 有多少处病害""西乡段有多少处病害"，这三条 SQL 结构完全一样，只有路线条件在变。它们就是同一个模板的三个样本。

### 第二层，怎么变成模板

系统把 SQL 解析成语法树，只做一件事：把每次都在变的值挖掉，换成占位符。

路线名挖成路线槽。时间挖成时间槽。病害类型挖成类型槽。数值阈值挖成阈值槽。表、关联、聚合、分组、排序这些结构，一个都不动。

这里有个关键判断，怎么知道哪个位置该挖、哪个位置该固定。

系统的做法是跨样本比对。同一个位置，如果不同样本取过不同的值，就挖成槽。如果所有样本都是同一个值，就固定住。

比如"泛油数量"这条模板，病害类型那一栏永远是泛油，那就写死，不再问用户。这一条判断决定了模板是通用问法还是某一次的特例。挖错了，模板就会答错。

### 第三层，怎么保证模板是对的

三条硬规矩。

第一条，挖出来的模板必须能回填原始值。回填之后跑一遍，结果跟原 SQL 一致，才允许入库。不一致就丢弃，并且记下丢弃原因。

第二条，只见过一次的模板标记成候选，不直接进推荐。要等第二次、第三次出现同样的结构，才转正。

第三条，模板有生命周期。被用户选中次数多的往上走，长期没人用或者审核发现参数错位的往下走，出严重问题的直接停用。审核只看两类严重问题，参数错位和只答一部分，因为误报的代价太大。

### 第四层，命中之后怎么办

不自动执行，把候选摆成卡片让用户确认。

卡片上写清楚这条口径查什么、按什么条件、参数当前值是什么、能不能改。用户点了才执行。

这个设计的理由很实在。模板是机器挖的，可能挖得不对，但用户一眼能看出"这不是我要的"。让用户点一下，比让系统赌一把安全得多。

## 五、用户问过的问题怎么沉淀

沉淀有三个入口。

第一个，问答成功后自动入库。问题、SQL、执行结果、走的哪条路径、耗时，全部记下来。这是原始矿。

第二个，后台定期挖矿。不是每次问答都挖，那样太慢。后台任务批量扫描新增的问答对，挖成模板，已经挖过的跳过，只处理新的。

第三个，用户点"答对了"或者"答错了"。点对了，这条问答对可信度提高，优先进入挖掘。点错了，进纠错流程，系统分析是口径错了还是理解错了。

沉淀不是无脑存，有三道筛子。

第一条，SQL 必须结构可解析，解析不出来的不挖。

第二条，SQL 必须结果可复现，回填跑一遍结果一致才要。

第三条，问题必须是单一问法。一句话问了两件事的，沉淀出来的模板只能覆盖一半，标记成部分覆盖，不进推荐。

## 六、相似问题怎么推荐

两种推荐，用途不同。

第一种是结构相似。用户问"西乡段泛油多少处"，系统发现库里有一条"某路段某类型病害数量"的模板，结构对得上，就把这条模板连同参数一起摆出来，参数默认填成本轮问的路线和类型。

用户看到的不是一条陌生 SQL，而是"你要查的这类问题，我们有现成口径，参数已经填好了"。

这种推荐按结构匹配，不看字面相似。因为中文问法太多样，"多少处""几处""数量是多少"是一个意思，按字面匹配会漏掉。

第二种是问法相似。用户换了个说法问同一个东西，系统能从历史问法里找到那句原话，告诉他"上次问过类似的，当时是这么查的"。

推荐有硬边界。

模板声明的槽位必须能覆盖这一问的全部条件。多出一个模板表达不了的条件，比如桩号区间、设备号、有没有图片，就直接放弃匹配。

用户要分组、模板没声明分组，不匹配。用户要面积、模板只出计数，不匹配。

这条规矩是整个推荐系统可信度的来源。推错了比不推更伤，因为用户会照着错的答案去做养护安排。

## 七、多表多字段到底难在哪

这一段是重点，六条，每条都能举实例。

### 第一难，同名列

十几张表里，`start_num` 和 `end_num` 在路线表有，在路段表也有。`create_time` 在病害表有，在巡检表也有。`up_or_down` 在病害表有，在路段表也有。

模型看到"起点"两个字，五张表都能接。选错了，SQL 不报错，数字是错的。

一张表的时候不存在这个问题，因为列名唯一。十几张表放在一起，列名本身就成了歧义源。

### 第二难，同名但含义不同

`damage_type` 这个名字看起来像"病害类型"，实际是"损坏程度"，取值是 0、5、10。真正的病害类型是 `problem_base_id` 这个外键。

这个坑很典型，字面看对，实际全错。全库 `damage_type` 等于 10 的有 10643 条，里面泛油只有 46 条，绝大部分是条状修补和裂缝。

这种坑靠模型防不住，因为模型只能看列名和注释，注释写错了它也跟着错。只能靠人工把口径钉死，写进语义层。

### 第三难，一个业务概念对应多张表

"路线"在路线表里有，在路段表里通过 `route_id` 关联，在病害表里通过 `routes_id` 关联，在巡检表里通过中间表关联。

同一个"西乡段"，在路线表是一条记录，在路段表是另一条记录，两条记录的编码还不一样。用户说"西乡段"，按路线查和按路段查，结果可能完全不同。

项目里就踩过这个坑。宝安大道西乡段在路线表有一条，在路段表也有一条，两套数据。

### 第四难，字典表有重复和脏数据

病害类型字典里，"泛油"有五行重复记录，id 不同，编码相同。按名称匹配会命中多条，必须用 id 集合。

还有"未知路线"这种占位记录，六个 id，名称全一样。它不是真路线，但查询的时候会被算进去。

### 第五难，时间字段不止一个

病害表有 `collection_time` 采集时间，也有 `create_time` 入库时间。巡检表只有 `create_time`，没有采集时间。

用户说"11 月 2 日"，按哪个字段过滤，结果可能差很多。项目里就遇到过按不存在的字段过滤，直接报错。

### 第六难，多对多导致重复计数

一条病害可能同时关联路线和路段。按路线汇总再按路段汇总，加在一起会翻倍。

项目里实测过，G65 是 1433，未知路线也是 1433，加起来 2866，实际只有 1433。

这六条讲完，评委就明白难度不在会不会写 SQL，在知不知道为什么这么写。

一句话总结。单表查询可以做到接近百分百，因为列名唯一、口径唯一。十几张表放在一起，难点从"写 SQL"变成了"选对表和选对列"。

## 八、怎么应对这六难

一条一条对着来。

同名列靠语义层消歧。语义层里每个业务概念只对应一个字段，而且必须带表限定。模型在语义层里选，选不到裸列名。

同名不同义靠人工钉口径。`damage_type` 是损坏程度不是病害类型，这条写进语义层说明，模型不许用。病害类型统一走 `problem_base_id`。

一个概念多张表靠实体解析。用户说"西乡段"，系统先去路线台账和路段台账里查，查到唯一一条才用，查到多条就返回候选让用户选，查不到就明说没有。不猜。

字典脏数据靠编码集合。类型名匹配不用字符串，用 id 集合。占位记录单独识别，不让它混进正常统计。

时间字段靠统一口径。默认归到采集时间，只有明确问入库时间才换。问巡检任务时间就用巡检表的创建时间。

重复计数靠唯一键。汇总之前先按病害 id 去重，再聚合。

## 九、怎么证明它是对的

SQL 执行成功不代表答案对。这是这个项目最反直觉、也最值钱的一点。

所以项目花了很大力气建题集、建回归。

早期建了九套基础题，覆盖数量、分布、趋势、排名、尺寸筛选、桩号密度、时间范围、上下行、病害类型。后来按能力单元改成考卷制，一个单元一套，分新题和旧题，新题考泛化，旧题考退化。每道题都有标准答案，标准答案是对着实库一条条查出来的。

每次改代码，全量跑一遍，看有没有退步。

这套东西的价值在于，它把"感觉对了"变成了"测过是对的"。

大部分 NL2SQL 项目死在没法验证上。因为没人能说清楚什么叫对，最后只能靠演示几个成功案例。

## 十、可能被追问的八个问题

### 问一，准确率多少

诚实回答。高频的结构化问题，比如数量、分布、排名、趋势，覆盖面已经比较完整。冷门问法和复合问法还在补。不给一个笼统的百分比，因为百分比掩盖了分布，有些问题稳，有些问题不稳。

### 问二，为什么不直接让大模型写 SQL

试过，不够稳。大模型看物理表结构写 SQL，遇到同名列会瞎猜，遇到语义陷阱会照字面理解。项目里就出现过把"损坏程度"当"病害类型"用的情况，SQL 没错，答案全错。

现在的做法是让模型在业务字典里选，不让它在物理表里猜。

### 问三，模板会不会把人框死

不会，因为模板是候选不是强制。用户看到卡片，觉得不对可以选"让 AI 回答"。模板解决的是高频重复问题，长尾交给通用路径。

### 问四，模板答错了怎么办

三道防线。入库前回填验证，结果不一致直接丢弃。入库后有人工确认卡，用户能看出来不对。出问题后有生命周期管理，严重问题直接停用。

### 问五，换个大模型会不会更好

短期不会。这个项目的瓶颈不在模型生成能力，在语义层和验证链条。模型再强，也解决不了"这张表的这一列到底是什么意思"。

### 问六，怎么保证新改的功能没把老的改坏

回归题集。每次改代码全量跑，看老题有没有退步。改代码只让新题过、老题退化的，不算修好。而且考卷跟代码版本绑定，改了代码旧考卷立刻作废，必须用新题重新考，防止对着考卷改代码。

### 问七，最难的在哪

不是写代码，是定义什么叫做对。业务口径要一条条跟业务人员确认，确认完还要写进语义层，写进去还要测。这部分工作量最大，也最没有成就感，但它决定了系统可不可信。

### 问八，这个项目你最大的收获

一句话。做数据类 AI 产品，真正的门槛不在模型，在把业务口径变成机器能执行、能验证的规则。

## 十一、讲的时候注意

不要一上来讲架构图。先讲一个具体场景，业务人员想问"西乡段泛油多少处"，以前要等技术，现在几秒钟，而且能点开看 SQL。

讲难点的时候一定要举实例。`damage_type` 那个坑，讲一遍评委就懂了，比讲十句"多表字段歧义"都管用。

讲验证的时候要讲数字。九套题、多少道、覆盖哪几个方向，这些具体的数字比"我们做了充分测试"有说服力。

不要回避边界。答不了的问题明确说答不了，这比吹百分百准确更让人信。
