# 冷门字段覆盖与交互智能化整改方案

---

## 一、问题1：模板快速通道吃掉冷门条件

### 现象
```
用户问：西乡段收藏的病害有多少处？
    ↓
答：共 911 处。（全部病害，不是收藏的）
```

### 根因
模板快速通道太蠢了——只要匹配到"有多少处"这个大模式，就直接拼SQL，根本不检查用户的问题里有没有它不认识的条件。

它只认识这5个条件：路线、桩号、病害类型、时间、上下行。
其他条件（收藏、关注、工单状态、病害来源）它根本不认识，直接吃掉。

### 改法

**模板入口加一道"冷门条件闸"：**

1. 定义"模板认识的条件词"白名单：
   - 路线、路段、桩号、K0+xxx
   - 病害类型（泛油/裂缝/坑槽...）
   - 时间（月份/日期/时间段）
   - 上下行
   - 面积大小

2. 定义"模板不认识的冷门条件词"黑名单：
   - 收藏、收藏的
   - 关注、标记的、重点
   - 工单、转工单、已处理、待处理
   - 来源、手动新增、车辆巡检、人工巡检
   - 路格、luge
   - 经纬度、附近、周边
   - 历史损坏程度

3. 规则：**只要用户的问题里包含任意一个冷门条件词，就绝对不能走模板快速通道，必须走Wren路径。**

### 为什么要这么严？
因为模板是写死的，它不可能认识所有条件。与其让它猜错（把冷门条件吃掉），不如干脆不放它进。

## 二、问题2：追问"你用哪个字段"太蠢了

### 现象
```
用户问：哪些病害是收藏了但还没转工单的？
    ↓
答：这条问题我还差一点信息，补充一下我马上查。
    原因：缺路线
    和这个问题最相关的字段：
    ai_problem.routes_id（varchar(32)）：路线id
    ai_problem.pile_number（varchar(16)）：桩号
    ...（甩了一堆字段名）
    你回复「用哪个字段、怎么筛」就行
```

### 根因
现在的逻辑是：当LLM不知道用什么字段时，就把字段列表甩给用户，让用户选。

**这完全搞反了！** 用户是来问问题的，不是来当SQL工程师的。用户根本不知道 `routes_id` 是什么，也不知道 `pile_distance` 是什么。

### 改法

**把"甩字段列表给用户"改成"LLM自己猜字段"：**

1. **取消字段追问交互**：再也不要把 `ai_problem.routes_id` 这种字段名甩给用户看
2. **LLM自己猜字段**：当LLM不知道用什么字段时，它应该：
   - 先去看MDL里的字段描述（每个字段都有中文注释）
   - 自己猜哪个字段最匹配用户的问题
   - 比如用户说"路线"，它就知道是 `routes_id`，不用问用户
3. **实在猜不出来，用自然语言追问**：
   - 错误示例："你回复「用哪个字段、怎么筛」就行"
   - 正确示例："你是想查哪条路的病害？告诉我路名就行，比如西乡段/恒明珠"

### 原则
**用户说人话，AI翻译成字段。** 反过来让用户说字段名，就是产品设计失败。

## 三、其他智能化建议

### 建议1：Wren提示词里明确说"所有字段都能用"

现在的Wren提示词里，只强调了几个常用字段：数量、类型、密度、时间。

要加一句：
> "注意：MDL里包含了所有业务字段（收藏、关注、工单状态、病害来源、路格、经纬度等），你可以根据用户的问题自由选择字段，不要只盯着数量/类型/时间这几个常用字段。"

### 建议2：字段要"说人话"，不说字段名

所有给用户看的地方，都不能出现 `routes_id`、`pile_distance` 这种字段名。
- 错误："和这个问题最相关的字段：ai_problem.routes_id"
- 正确："你是想查哪条路？"

### 建议3：冷门条件也要能分组统计

现在分组统计只支持：按类型、按时间、按路线、按上下行。
要扩展：
- 按工单状态分组（待转/已转/忽略 各有多少）
- 按病害来源分组（手动/车辆/人工 各有多少）
- 按是否收藏分组（收藏的有多少，没收藏的有多少）

### 建议4：结构超前于数据（最重要）

**现状：** 现在17张表里，只有4-5张有数据（病害/路线/路段/病害字典），其他12张都是空的（资产/定距/桥隧/工程/养护/工单...）。

**要求：** 智能体不能因为现在这些表是空的，就把它们从"可查询范围"里去掉。
**必须保证：** 等以后这些表有数据了，**不用改代码、不用改MDL，直接就能查**。

具体怎么做：
1. **MDL里必须保留所有17张表的结构**，不管现在有没有数据
   - 现在空的表（ai_asset_main、ai_distance_capture、bridges、tunnels、slope...），它们的表名、字段名、注释都要在MDL里
   - 不能因为现在没数据，就把这些表从MDL里删掉
2. **Wren提示词里要告诉LLM：**
   > "MDL里包含了所有业务表，不管现在有没有数据。用户问什么表，你就去MDL里找对应的表和字段，不要因为现在没数据就说'查不了'。"
3. **空表查询要友好：** 如果查出来是0条，就说"目前这张表还没有数据"，而不是说"这个字段不存在"或"不知道怎么查"。

### 为什么这很重要？
现在是测试阶段，大部分表都是空的。
等以后真上线了，资产表、工单表、工程表慢慢就有数据了。
如果现在把这些表从MDL里删掉，那以后每加一张表的数据，都要重新改MDL、改提示词、改代码——这就是"穷举"的老路。

**正确的做法：** 结构先搭好（MDL里有所有表），数据慢慢填。等数据来了，直接就能查，不用改任何代码。

## 四、问题3：跨库语义消歧太蠢了

### 现象
```
上一轮一直在聊西乡段的病害。

用户问：那你根据经度和纬度的数据，判断病害主要分布在西乡段的哪一侧？
    ↓
系统错误：去查了 PostgreSQL 的 gps_points 表
    SQL：SELECT COUNT(*) AS count FROM gps_points WHERE TRUE LIMIT 1
    ↓
答：0处。
```

### 根因
现在的跨库识别逻辑太简单了——看到"经纬度"就想到GPS表，完全不看上下文。

**这完全错了！** 用户说的"经纬度"，是指**病害的经纬度**（ai_problem.lng / ai_problem.lat），不是GPS轨迹的经纬度。

### 改法

**跨库识别要结合上下文做语义消歧：**

1. **不能只看关键词，要看上下文：**
   - 上一轮在聊病害 → 用户说"经纬度"，就是指病害的经纬度（ai_problem.lng/lat）
   - 上一轮在聊巡检轨迹 → 用户说"经纬度"，才是指GPS轨迹（gps_points.lat/lon）

2. **优先级规则：**
   - 如果当前对话的主题是"病害"，那"经纬度/位置/坐标"这些词，优先对应病害表的 lng/lat 字段
   - 只有当用户明确说"GPS轨迹/巡检路线/车辆位置"时，才去查 gps_points 表

3. **Wren提示词里加这条规则：**
   > "注意：'经纬度/位置/坐标'这些词，要看上下文。如果在聊病害，就是指病害的位置（ai_problem.lng/lat）；如果在聊巡检轨迹，才是指GPS轨迹表。不要一看到经纬度就去查GPS表。"

### 为什么这很重要？
同一个词在不同语境下指的是不同的表。
现在的系统只会"看到关键词就匹配表"，不会"结合上下文理解用户到底在说什么"。
这就是为什么我们一直觉得它不智能——它是在做关键词匹配，不是在做语义理解。

## 六、核心思想：所有语义判断都不要写死关键词

### 现状问题
现在整个系统里到处都是关键词写死的逻辑：
- 图片识别 → 写死 `_IMAGE_WORDS` 列表
- 跨库识别 → 写死"经纬度=GPS库、图片=SeaweedFS"
- 意图分类 → 写死"多少条=count、分布=distribution"
- 分组识别 → 写死"分别/各=group by"

**这都是穷举！** 用户换个说法就识别不出来了。

### 改法原则

**所有需要语义理解的地方，都不要写死关键词，要交给LLM来判断。**

关键词只能做**粗筛**（比如"这句话里连个'图'字都没有，肯定不是看图"），不能做**最终判断**。最终判断要交给LLM语义理解。

---

### 1. 跨库识别：不要写死"看到XX词就去XX库"

**现在的蠢逻辑：**
```
看到"经纬度" → 去PostgreSQL GPS表
看到"图片" → 去SeaweedFS
看到"病害" → 去MySQL
```

**问题：**
- 用户问"根据经纬度判断病害分布在哪一侧" → 它跑去查GPS表了，其实应该查病害表的经纬度字段
- 用户问"看看巡检车的轨迹在哪" → 它又不知道该查哪了

**正确做法：**
跨库识别要结合**上下文+问题语义**，让LLM判断：
> 这个问题到底在问什么？需要用哪张表/哪个库？

**给LLM的提示词：**
> "判断这个问题应该查哪个库：
> 1. 如果问的是病害/资产/工单/养护等业务数据 → MySQL主业务库
> 2. 如果问的是车辆轨迹/GPS定位/巡检路线 → PostgreSQL GPS轨迹库
> 3. 如果问的是现场照片/病害图片 → 还是MySQL（图片路径存在MySQL里）
> 
> 注意：不要只看关键词。比如用户问'根据经纬度判断病害分布'，虽然提到了经纬度，但这是在问病害的分布，还是查MySQL的病害表，不是GPS表。"

---

### 2. 意图分类：不要写死关键词

**现在的蠢逻辑：**
```
看到"多少" → count意图
看到"分别" → 分组意图
看到"图片" → image意图
```

**正确做法：**
意图分类交给LLM，让它理解用户到底想干什么。

**给LLM的提示词：**
> "判断用户的意图：
> 1. data：用户想查具体的数据（数量、列表、明细）
> 2. analysis：用户想做分析、对比、统计、趋势
> 3. knowledge：用户想了解规范、标准、方法
> 4. image：用户想看看现场长什么样、图片是什么样
> 5. composite：用户既要查数据又要分析/建议
> 
> 注意：不要只看关键词。比如用户说'西乡段泛油情况怎么样'，虽然没有'多少'，但也是想查数据。用户说'K0+100那的病害长什么样'，虽然没有'图片'两个字，但也是想看图。"

---

### 3. 分组识别：不要写死"分别/各"

**现在的蠢逻辑：**
```
看到"分别" → group by
看到"各" → group by
```

**问题：** 用户换个说法（"拆开看/按XX分/两边对比"）就识别不出来了。

**正确做法：**
分组识别交给LLM，让它理解用户是不是想要按某个维度拆开统计。

---

### 为什么要这么改？

**关键词穷举的数学本质：**
- 主体筛选有10种可能
- 度量有5种
- 分组有8种
- 关系有4种
- 组合空间 = 10×5×8×4 = 1600种

你写关键词列表，就算覆盖了100种，也只覆盖了6%。用户随便换个说法就漏了。

**LLM语义理解的优势：**
- 不管用户怎么说，LLM都能理解他到底想干什么
- 不用维护关键词列表
- 新问法自动支持

## 七、问题5：字段映射表写死在代码里

### 现象
代码里写了一大堆字段映射表：
```python
# nl2sql.py 里
_SELECT_FIELD_EXPRS = {
    "problem_type_name": "b.problem_type",
    "confidence": "CAST(JSON_EXTRACT(...))",
    ...
}

_TEMPLATE_SAFE_FIELDS = frozenset({
    "route_name", "area", "collection_time", ...
})

_CONDITION_VALUE_HINTS = {
    "collect": "0=未收藏，1=收藏",
    "problem_status": "0=待转工单，10=已转工单，15=忽略病害",
    ...
}
```

### 根因
**历史遗留问题：** 一开始没有Wren语义层，所有字段都得靠代码手写映射。
后来加了Wren，但是这些老的映射表没删，还在那里。

**现在的状态：**
- Wren MDL里已经有所有表的所有字段了
- 但是代码里又写了一份"字段映射表"
- 两份数据，一份在MDL里，一份在Python代码里
- 新字段出来，改了MDL忘了改代码，就出bug

### 为什么说它蠢？
1. **每加一个字段就要改三处代码**：字段映射表、模板安全字段列表、值映射表
2. **两份数据容易不一致**：MDL里改了，代码里忘了改
3. **新字段出来容易漏**：新字段忘了加到模板安全列表里，就走不了模板，或者走错模板

### 改法

**核心思想：** 既然已经有Wren语义层了，所有字段的映射都应该交给MDL来管，而不是在Python代码里再写一遍。

| 现在（写死在代码里） | 应该交给谁 |
|---------------------|-----------|
| `_SELECT_FIELD_EXPRS`（字段名→SQL表达式） | **Wren MDL**（已经有所有字段了，不用在代码里再写一遍） |
| `_TEMPLATE_SAFE_FIELDS`（模板安全字段白名单） | **不需要写死**——模板处理不了的，自然就走Wren |
| `_CONDITION_VALUE_HINTS`（代码值→中文映射） | **Wren MDL的字段描述**里应该包含这些说明 |

**正确的分工：**
- **Wren MDL**：管所有字段的定义、类型、注释、映射
- **Python代码**：只管流程控制（什么时候走模板、什么时候走Wren），不管字段映射

## 总结：所有问题一览

| 问题 | 核心 |
|------|------|
| 问题1 | 模板吃掉冷门条件 → 模板入口加闸 |
| 问题2 | 甩字段列表给用户 → LLM自己猜字段，用户说人话 |
| 问题3 | 跨库语义消歧太蠢 → 结合上下文判断"经纬度"指的是哪张表 |
| 问题4 | 图片展示太受限 → 图片数量和需求挂钩 + 关键词不写死 |
| 问题5 | 字段映射表写死在代码里 → 交给Wren MDL管，代码只管流程 |

### 现象1：只会返回固定的那三张

```
用户问：给我看看西乡段泛油的病害图片
    ↓
答：找到 3 张相关图片。（每次都是这三张，不会变）
```

### 根因
`_image_result` 函数里写死了上限：
- 最多取前50行数据
- 最多取9个候选图片路径
- 最多检查6个图片是否存在
- 最后展示的就是这6个里能打开的

**问题：** 不管用户问多少张，系统最多只展示6张，而且每次都是前几张，不会随机或按条件筛选。

### 改法
1. **图片数量要和用户的需求挂钩：**
   - 用户说"给我看看" → 展示3~6张
   - 用户说"把所有XX的图片都列出来" → 展示20~30张
   - 用户说"把明细都调出来" → 明细表格里带图片列

2. **要按条件筛选，不能永远是前几张：**
   - 问"面积最大的" → 按面积从大到小排，取前几张
   - 问"最近的" → 按时间从新到旧排，取前几张
   - 不能永远是随机的前几张

---

### 现象2："样图"识别不出来

```
用户问：把所有的病害样图都取出来给我看
    ↓
系统没识别成图片意图，走了数据查询，返回500条表格
```

### 根因
现在用 `_IMAGE_WORDS` 关键词列表来判断"是不是要看图"：
```python
_IMAGE_WORDS = ("照片", "图片", "现场图", "病害图", "影像")
```

**这还是穷举！** 用户换个说法（样图/样张/实景照/拍个照看看/现场什么样）就识别不出来了。

### 改法

**不要靠关键词列表，靠LLM语义判断：**

1. **关键词只做粗筛，不做最终判断：**
   - 先看有没有"图/照/影"这些字，没有的话肯定不是看图
   - 有这些字的，再交给LLM判断："这句话是在看图，还是在把图片当过滤条件？"

2. **意图分类器里加一句说明：**
   > "判断用户是不是要看图，不要只看关键词。只要用户的问题里包含'看/看一下/给我看看/展示一下/长什么样/现场是什么样'这类表达，并且和病害/设施/现场相关，就算是看图意图。"

3. **不要再维护 `_IMAGE_WORDS` 列表了**——用户的说法是无穷的，列表永远列不完。

| 测试用例 | 预期结果 |

| 西乡段收藏的病害有多少处？ | 返回收藏的数量，不是全部911处 |
