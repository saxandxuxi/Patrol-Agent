# 语义兜底机制与误判整改方案

> 本方案汇总四个实测问题，共同特点是：不是 SQL 写不出来，而是语义理解和兜底机制把本来能答的问题判成了"不能答/答非所问"。
> 四个问题：
> 1. "宝安大道的经纬度范围"被判成"本系统不支持"
> 2. 问题优化器会"宣布死亡"，代码还把拒绝声明当问题重查
> 3. "总处数、总面积、平均面积分别是多少"被误判成分组追问
> 4. 按桩号分组的分布结果，回复被压扁成一个总数

---

## 一、问题优化器无权"宣布死亡"（机制缺陷，优先级最高）

### 现象
用户问"宝安大道的经纬度范围"，系统最终回复：
> （按「本系统不支持查询经纬度字段，无法回答该问题。」重查）……缺少具体查询条件

优化器没有改写问题，而是输出了一句"系统不支持"的拒绝声明；执行链路把这句声明当成优化后的问题又查了一遍，自然什么都查不到。

### 根因
1. prompts/optimize_question.md 没有禁止输出拒绝性文本，反而有一条"只能补成本系统真的能查的口径，查不了的不要编"——模型遇到能力清单里没有的东西，就理解成"那我宣布查不了"。
2. nl2sql.refine_question() 对优化结果只做了两个校验：长度≥4、_lost_entities 有没有丢实体。"本系统不支持查询经纬度字段"这句话里"经纬度"还在，长度也够，于是通过了。
3. "到底什么算查不了"被提前到了改写阶段由优化器决定，但优化器看到的能力清单并不完整（见第二节），它没有资格做这个决定。

### 改法

提示词（optimize_question.md）加硬规则：
- 你的唯一职责是改写问题，不是判断系统能不能答。
- 严禁输出"不支持/无法回答/不能查询/查不了/没有该字段/没有权限/请联系管理员/系统无法"这类拒绝性文本。
- 即使你判断这个口径可能查不到，也必须原样返回用户的问题（或只做口径补全），由 SQL 生成和校验环节去判定，不许替系统宣布死亡。
- 输出必须是一个可以拿去查询的问题，不能是一句结论。

代码（refine_question）加一道拒绝声明拦截：
- 优化结果命中拒绝性模式（不支持|无法回答|无法查询|不能查|查不了|没有.*字段|不具备|无权）时，直接丢弃，返回空串，让调用方用原问题继续走其他兜底（换引擎/走 Wren/如实告知查不到）。
- 同时拦"输出里没有疑问/查询语义"的情况：优化后的文本必须包含查询诉求（多少/哪些/是什么/列出/分布/范围/排名…），是一句陈述句结论的一律作废。
- 真正"算不出来的口径"由 _CAPABILITY_HINT 的 unsupported 清单在 SQL 生成阶段决定，并且要如实告诉用户"系统里没有 XX 数据"，而不是让优化器编一句"不支持字段"。

## 二、补齐经纬度范围查询能力（能力缺口）

### 现象
"宝安大道的经纬度范围"被认为不支持，但数据是有的。

### 数据事实
- ai_problem 表有 lng（经度）、lat（纬度），类型是 varchar 字符串，比较/取极值必须 CAST 成数值。
- MDL 的 disease 模型已经暴露 d.lng / d.lat（sql_mdl.md 已有说明）。
- "一条路线的经纬度范围"= 这条路线上所有病害经纬度的四个极值：
  MIN(经度)、MAX(经度)、MIN(纬度)、MAX(纬度)。
- 用户说"宝安大道"，库里路线全称是"宝安大道西乡段"，路线名匹配要支持前缀/包含匹配；如果"宝安大道"能匹配到多条路线，列出各条的范围或让用户选，不要直接判缺路线。

### 改法
1. _CAPABILITY_HINT 能力清单补上：
   - 维度加"经纬度（病害自身的 lng/lat）"
   - 指标加"经纬度范围/边界（最东、最西、最南、最北，用 MIN/MAX）"
2. query_semantic.md：
   - output_fields / metrics 增加经纬度极值这一类（geo_bounds 或 min_lng/max_lng/min_lat/max_lat）。
   - "范围/边界/覆盖到哪/最东最西最南最北/经纬度从多少到多少"都归到这个形状，不要当成"列出每条记录的经纬度"。
3. sql_mdl.md / sql_physical.md 补写法示例：
   - MDL：SELECT MIN(CAST(d.lng AS DECIMAL(12,8))) ... （如果 MDL 已把 lng/lat 抽成数值列就直接 MIN/MAX，按实际 MDL 定义来）
   - 物理：MIN(CAST(p.lng AS DECIMAL(12,8))) AS 最西经度, MAX(...) AS 最东经度, MIN(CAST(p.lat...)) AS 最南纬度, MAX(...) AS 最北纬度，带路线 id 过滤和 del_flag=0。
4. 结果呈现：四个极值 + 说明这是"该路线病害采集点覆盖的经纬度范围"，不要说成是路线行政边界（台账里没有路线边界坐标）。
5. 注意和 GPS 轨迹区分：聊病害/路线的经纬度走 MySQL 的 lng/lat；只有明确说"轨迹/打点/行驶轨迹"才走 PostgreSQL（datasource.md 已有此规则，保持一致）。

## 三、"分别是多少"跟的是指标，不是分组维度

### 现象
问"宝安大道西乡段的泛油病害，统计总处数、总面积和平均面积分别是多少？"
系统追问"您说的『分别/各』看不出是按什么分（按类型？按路线？按上下行？按月份？）"。

### 根因
看到"分别/各"就机械地认为要 GROUP BY。但这里的"分别"是指"总处数、总面积、平均面积这三个指标各是多少"，是同一组对象上的多个聚合列，根本不需要分组。

区别：
- "各病害类型有多少 / 按类型分别多少" → "各/分别"后面是维度（类型、路线、月份、上下行）→ 真分组。
- "总处数、总面积、平均面积分别是多少" → "分别"后面是指标（多个聚合值）→ 不分组，一条 SQL 用多个聚合列（COUNT、SUM、AVG）一次算全。

### 改法
- 不要用"看到分别/各就追问分组口径"的机械规则。是否需要分组交给语义层 LLM 判断：看"分别/各"指向的是一个可分组的维度，还是一组要并列给出的指标。
- ambiguous_grouping_reason（低置信分组追问）只在"确实出现了分组信号、但分组字段无法确定"时触发；"分别"后面明确列举了多个指标的，直接判为单组多指标，不追问。
- 这类问题一条 SQL 就要把点名的指标全算出来（COUNT(*)、SUM(area)、ROUND(AVG(area),4)），不能只回一个。

## 四、分布/排名结果不能被总结成一个总数

### 现象
问"7月29日和30日这两天，病害主要集中在哪些路段或桩号？"
SQL 是按桩号分组、ORDER BY COUNT(*) DESC，表格里有完整的桩号排名，但回复只说"宝安大道西乡段：共30"。

### 根因
结果总结环节把"分组+排序"的结果当成了一个总数来念，没有理解用户问的是"集中在哪/主要是哪些/排名如何"——这类问题要的是排在前面的分组项，不是合计值。

### 改法（用语义理解，不要写死"分组就列 Top N"的规则）
- 结果总结交给 LLM 结合"用户问题 + 列结构 + 数据"来决定怎么念，不做固定形状的机械总结：
  - 用户问"集中在哪/主要是哪些/排名/最多的是哪里" → 把排名靠前的分组项和数值列出来（桩号+处数），说明集中度（前几名合计占比），最后才补总数。
  - 用户问"一共多少" → 才只给总数。
  - 用户问"列出明细" → 不做极值结论，引导看表格。
- 判断依据是用户的提问意图，不是"SQL 里有没有 GROUP BY"。同样一个分组结果，问"分布"要列排名，问"总数"要给合计，不能一刀切。
- 结果总结提示词（result_summary.md）里补这组对照示例，并要求：回答必须回应用户问题里的疑问词（哪些/哪里/排名/集中→给对象和排名；多少→给数值）。

## 五、共性原则

这四个问题本质是同一件事：**系统在"理解不了"的时候，选择了最糟糕的反应——要么宣布不支持、要么机械追问、要么把结果念扁。**

统一原则：
1. 任何环节都不许替用户/替系统宣布"查不了"，判定权收敛到 SQL 生成之后的校验环节，且要如实说明缺什么数据。
2. "分别/各/分布/集中"这类词的含义由 LLM 结合上下文判断，不用关键词机械触发分组、追问或总结。
3. 能力清单（_CAPABILITY_HINT）、语义枚举（query_semantic.md）、MDL 三者要保持一致并补全经纬度这类已有数据的字段；以后发现"数据有但系统说不支持"的，先补这三处。
4. 兜底链路每一级的输出都要校验"它还是不是一个合法的输入"：优化器输出必须是可查询的问题，不能是结论或拒绝声明。

## 六、验收用例

1. 宝安大道的经纬度范围
   - 期望：返回最东/最西/最南/最北四个经纬度极值，说明是病害采集点覆盖范围；不得出现"不支持"。

2. 西乡段采集点位的经纬度边界是多少
   - 期望：同上，走 MySQL 的 lng/lat，不去查 PostgreSQL 轨迹表。

3. 宝安大道西乡段的泛油病害，总处数、总面积和平均面积分别是多少？其中面积最大的一处是多少？
   - 期望：不追问分组口径；一条结果给出 COUNT、SUM、AVG、MAX 四个值。

4. 7月29日和30日病害主要集中在哪些桩号？
   - 期望：回复列出病害数最多的前几个桩号及处数、集中度，最后补总数，不能只有"共30"。

5. 西乡段各病害类型分别有多少？
   - 期望：这是真分组，按类型 GROUP BY，每个类型一行（回归用例，不能因为改了第三条而不分组）。

6. 人为构造一个优化器想拒绝的场景（问一个库里确实没有的东西，比如"车道级病害归属"）：
   - 期望：优化器输出原问题，由最终环节如实告知"系统中没有 XX 数据"，不得出现"本系统不支持查询 XX 字段"这种话，也不得拿拒绝声明去重查。
