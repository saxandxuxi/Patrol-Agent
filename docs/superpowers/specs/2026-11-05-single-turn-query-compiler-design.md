# 单轮巡检数据查询编译器与有界纠错设计

> 日期：2026-11-05
> 状态：设计待评审
> 范围：单轮巡检业务数据查询；先覆盖 MySQL，保留 PostgreSQL 扩展边界
> 决策：采用“受控查询编译器 + 有界纠错 Agent”

## 1. 背景

当前系统不是缺少大模型，而是缺少一条可靠的查询工程链路。同一句用户问题会依次经过意图识别、问题优化、语义规划、关系规划、SQL 生成和结果验收；每个阶段都有自己的提示词、规则和数据结构，阶段之间依靠自然语言字符串传递信息。

这造成了几类反复出现的问题：

- 同一条件在某个阶段被改写或丢失，后续 SQL 却仍被视为合法。
- 模型推断出的病害类型、字段或过滤条件可能直接进入 SQL。
- 规划器把汇总、分组和明细混成一个视图，执行 SQL 后再靠总结补救。
- 验收器主要看到问题、SQL、字段名和前 10 行，无法证明完整结果正确。
- 明细超过 500 行时，没有区分“查询命中数”和“页面展示数”。
- 后置计算可能把非空错误文案当成成功结果。
- 控制器只能重试少数预定义工具，不能根据失败证据修正具体计划节点。
- 回归脚本会把“明确失败”算作通过，`PASS` 只能证明程序结束。

Codex 能处理复杂任务，主要因为它具备稳定任务契约、可观察工具结果、独立成功判定和按失败证据修改方案的能力。该设计把这些能力引入巡检数据查询，但不引入自由行动的通用 Agent。

## 2. 目标与非目标

### 2.1 目标

1. 让智能体成为巡检业务数据专家，对数据库能够回答的问题给出高正确率 SQL 和答案。
2. 对字段、枚举、时间、路线、桩号和业务口径进行可追溯的解析。
3. 在 SQL 执行前检查计划和字段来源，在 SQL 执行后检查真实结果。
4. 单轮问题可以内部拆成多条查询，例如先取精确汇总，再取明细页，但始终只服务一个用户问题。
5. 失败时区分可修复、信息不足、数据不存在和系统错误，不能静默当作成功。
6. 明细超过展示上限时，准确说明命中总数、当前展示范围和数据是否截断。
7. 每个修复动作只能修改失败节点，不能删除或扩大用户原始范围。
8. 用真实答案和失败注入集衡量一次答对率、错答放行率、误停率和修复成功率。
9. 把巨型文件按稳定边界拆小，降低局部修改对其他数据流的影响。

### 2.2 非目标

- 本阶段不处理长对话补全和跨轮指代。
- 本阶段不重做知识库、图片查询和元数据画像主链。
- 不提供写库、建表、删除或修改权限。
- 不把全部工具一次性暴露给模型。
- 不为每个工具配置一个独立 LLM。
- 不允许模型自由改写用户的问题、实体、时间和查询范围。
- 不在本阶段承诺自动分析所有未知业务概念；无法证明时必须明确说明。

## 3. 核心原则

1. LLM 负责理解、提出 QuerySpec 和解释失败；代码负责校验、编译、执行和判定事实。
2. 用户意图在进入执行后不可变。任何修复都必须保持 `immutable_scope_hash` 不变。
3. 自然语言不是阶段间接口。阶段间只传结构化对象。
4. 语义预测不是执行事实。SQL 实际列、行数、截断、空值和覆盖范围必须来自 Observation。
5. 显示值和存储值显式分离。code 用于执行，中文标签用于展示。
6. 中间对象必须携带来源。无法追溯来源的字段或值不能进入 SQL。
7. 表达错误只修表达，数据错误才修 QuerySpec 或 SQL。
8. 明细验收检查查询范围、结构和元数据，不要求验收模型读取全部明细。
9. 验收采用 `accepted / repairable / unsupported / ambiguous` 状态，不使用会吞错误的成功兜底。
10. 每个模块必须能回答：输入是什么、谁生产、谁消费、消费方依赖的最小不变量是什么。

## 4. 单轮查询定义

“单轮”指用户只提供一个当前问题，不消费上一轮对话中的条件、实体或结果。

一个用户回合允许生成多个内部查询节点：

- 汇总查询与明细查询分离。
- 精确计数与分页明细分离。
- 数据查询与纯后置计算分离。
- 必要时先解析实体，再执行正式查询。

这些内部查询共享同一个不可变 `IntentContract`，不对应用户的多次追问。

## 5. 总体数据流

```text
用户单轮问题
  -> QuestionAnalysis
  -> IntentContract
  -> QuerySpec 候选
  -> FieldReachSet + PhysicalSchemaView + OutputProjection
  -> ValueResolver / ProvenanceResolver
  -> QuerySpec 校验
  -> QueryPlan（一个或多个内部查询节点）
  -> SQL Compiler（模板、Wren 或受控 LLM）
  -> SQL Linter / Runtime Executor
  -> ExecutionObservation
  -> Deterministic Verification
  -> Semantic Verification
  -> AnswerAssembly / Presentation Verification
  -> 最终 AnswerPackage
```

任何阶段失败都只能产出结构化状态，不得生成“看起来像答案”的空成功结果。

## 6. 核心数据契约

### 6.1 IntentContract

输入：用户原话、数据库范围、当前可用业务能力。

生产者：意图分析器和实体解析器共同生成；代码确认后冻结。

消费者：QuerySpec 生成器、QuerySpec 校验器、最终范围校验器。

最小不变量：

- `original_question` 保存用户原话。
- `intent_family` 只能是已知业务族，例如 count、distribution、top、trend、detail、calculate。
- 路线、时间、病害类型、阈值等用户范围必须完整保留。
- 每个范围项都有来源和标准化结果。
- `immutable_scope_hash` 在生成后不能变化。
- 无法识别的业务词进入 `unknown_terms`，不得静默删除。

### 6.2 FieldReachSet

输入：问题、字段注释、字段目录和业务词表。

生产者：字段触达器。

消费者：QuerySpec 生成器和字段建议器。

最小不变量：

- 只表示“命中过或可能相关的字段”，不是执行白名单。
- 每项带表名、列名、命中词、得分和来源。
- 不能作为“数据库真实存在该列”的证明。

### 6.3 PhysicalSchemaView

输入：数据库元数据目录。

生产者：Schema Catalog。

消费者：QuerySpec 校验器和 SQL 编译器。

最小不变量：

- 只包含数据库中真实存在的表、列、数据类型和允许关联。
- 每次查询记录目录版本或快照标识。
- 不在目录中的字段不能被 SQL 生成器使用。

### 6.4 OutputProjection

输入：用户明确要求的展示字段、必要定位字段和业务默认展示字段。

生产者：QuerySpec 生成器，经用户范围校验器确认。

消费者：SQL 编译器、答案组装器和前端结果表格。

最小不变量：

- 每个输出字段都有 `field_ref`、`display_label` 和来源。
- 只能展示用户要求或回答所必需的字段。
- 存储 code 可以在表格中保留为内部字段，但最终文案必须使用 display label。
- 不得把 FieldReachSet 或 PhysicalSchemaView 直接当作 OutputProjection。

### 6.5 ValueBinding

输入：用户原话中的值、实体解析器结果和字段字典。

生产者：ValueResolver。

消费者：QuerySpec 校验器和 SQL 编译器。

最小不变量：

```json
{
  "field": "up_or_down",
  "op": "=",
  "storage_value": "2",
  "display_value": "下行",
  "source": "user_explicit",
  "resolver": "enum:up_or_down",
  "raw_text": "下行"
}
```

- `storage_value` 与 `display_value` 不得互相替代。
- 字符串相等不能代替语义相等；短标签必须通过字典或明确规则解析。
- `source` 只能来自用户原话、字段字典、已验证前序结果或已批准业务规则。
- 模型推断值必须经过字典解析；解析失败则禁止进入 SQL。

### 6.6 QuerySpec

输入：IntentContract、字段和值解析结果。

生产者：受约束的 QuerySpec 生成器。

消费者：QuerySpec 校验器、QueryPlan 生成器和控制器。

最小结构：

```json
{
  "id": "q1",
  "kind": "mysql",
  "subject": "disease",
  "view": "distribution",
  "metrics": [],
  "dimensions": [],
  "filters": [],
  "order_by": [],
  "limit": null,
  "output_projection": [],
  "required_assertions": [],
  "provenance": [],
  "immutable_scope_hash": "..."
}
```

最小不变量：

- 只表达用户语义，不包含 SQL 字符串。
- 所有过滤值和展示字段都能追溯到来源。
- 指标、维度、排序和输出字段都能映射到 PhysicalSchemaView。
- `view` 与指标、维度一致。
- 用户要求的汇总和明细必须是独立节点，不能混在同一个 SELECT 视图里。
- QuerySpec 不合法时不得进入 SQL 生成。

### 6.7 QueryPlan

输入：一个或多个已验证 QuerySpec。

生产者：QueryPlanner。

消费者：执行器和控制器。

最小不变量：

- 每个节点只有一个结果视图。
- 依赖节点声明输入和输出键。
- 汇总与明细节点的范围一致。
- 明细节点声明最大行数、截断策略和分页标识。
- 后置计算节点只消费已接受的前序结果。

### 6.8 ExecutionObservation

输入：SQL 执行结果或工具执行结果。

生产者：Executor。

消费者：验收器、控制器、答案组装器。

最小字段：

```json
{
  "node_id": "q1",
  "ok": true,
  "engine": "wren",
  "sql": "...",
  "columns": [],
  "row_count": 0,
  "preview_rows": [],
  "rows_fetched": 0,
  "truncated": false,
  "total_count": null,
  "null_summary": {},
  "distinct_summary": {},
  "coverage": {},
  "runtime_error": null,
  "query_fingerprint": "..."
}
```

最小不变量：

- SQL、行数和截断状态来自执行事实。
- 预览样本不能冒充完整结果。
- 运行错误保留数据库原文。
- 同一查询指纹不能原样重复执行。

### 6.9 VerificationReport

输入：QuerySpec、QueryPlan、ExecutionObservation。

生产者：三层验收器。

消费者：控制器和答案组装器。

状态只能取：

- `accepted`：有足够证据证明结果满足查询契约。
- `repairable`：错误可定位到具体节点或表达。
- `unsupported`：数据、字段或业务能力不存在。
- `ambiguous`：信息不足且继续猜测会影响正确性。

最小不变量：

- 每个结论都包含失败层、失败码、对应节点和证据。
- `repairable` 必须给出允许的修复动作。
- 表达错误不得触发数据库重查。
- 语义模型不能覆盖确定性失败。

### 6.10 AnswerPackage

输入：已接受的结果、必需断言和展示投影。

生产者：答案组装器。

消费者：聊天接口和前端结果工作台。

最小不变量：

- 最终回答中的数字、单位、标签都来自 Observation。
- 要求的所有指标、分组标签、比较结论都出现在最终回答中。
- 明细被截断时，必须说明命中总数或“尚不确定总数”以及当前展示行数。
- 无法回答时说明失败阶段、已确认事实、缺失能力和可行补充条件。

## 7. 查询计划与执行边界

### 7.1 视图拆分

以下诉求不能合并在一个 `query_data` 节点：

- 全库汇总与按维度分组。
- 聚合值与逐条明细。
- 多个互不关联的指标口径。
- 精确计数与分页展示。
- 数据查询与后置比较计算。

### 7.2 多指标与分组

只有在同一粒度、同一分组和同一过滤范围内，多个指标才允许在同一节点返回。例如按路线返回病害数、总面积和路线长度属于同一分组视图。

### 7.3 SQL 生成边界

SQL 编译器只接收已验证 QuerySpec。允许三种生成路径：

1. 确定性模板编译。
2. Wren/MDL 编译。
3. 受控 LLM 生成后再次通过字段和范围校验。

三条路径都必须输出相同结构的 `CompiledQuery`，并由同一 SQL Linter 和执行器处理。

### 7.4 明细超过展示上限

默认展示上限仍是 500 行，但必须区分：

- `rows_fetched`：本次取回并展示的行数。
- `total_count`：同范围下的精确命中数。
- `truncated`：命中数是否大于展示数。

如果用户同时要求数量和明细：

1. 先生成精确汇总节点。
2. 再生成明细节点。
3. 最终回答说明“共 N 条，当前展示前 M 条”。

验收器不读取全部明细。对于 list 视图，只验证：

- SQL 范围与 QuerySpec 一致。
- 输出列覆盖用户要求。
- 样本行符合必选过滤条件。
- 精确总数与截断状态来自独立执行事实。
- 最终回复没有把前 500 条说成全量。

## 8. 三层验收

### 8.1 数据事实验收

只做确定性检查：

- SQL 是否成功编译和执行。
- 必需表和列是否存在。
- 所有 QuerySpec 过滤条件是否编译进 SQL。
- 是否出现用户未授权的过滤条件。
- 分组题是否有分组标签。
- 聚合题是否有聚合值。
- 明细题是否返回所需字段。
- 结果是否为空，空结果是否与覆盖范围一致。
- 行数、截断状态和精确计数是否正确。
- 关联是否造成明显行数放大或重复。

### 8.2 结果语义验收

只处理确定性规则无法判断的语义问题：

- SQL 是否真正回答了用户的问题类型。
- 分组、对象、指标和结论是否一致。
- 明细样本是否属于正确业务对象。

语义验收输入至少包含：

- 用户原问题。
- IntentContract。
- QuerySpec。
- CompiledQuery。
- ExecutionObservation 的元数据和样本。
- 必需断言检查结果。

语义模型不能检查它看不到的事实，也不能因为表达不佳判定 SQL 错误。

### 8.3 表达验收

只在数据事实通过后执行：

- 是否列出所有必需指标和分组。
- 单位是否正确。
- 存储 code 是否被错误展示。
- 是否明确说明空结果、截断、部分完成或数据缺失。
- 分析题是否给出基于已有数据的结论。

表达失败只允许调用 `repair_presentation`。不得重新执行 SQL。

## 9. 有界纠错

### 9.1 失败证据

所有可修复失败统一为 FailureEvidence：

```json
{
  "accepted": false,
  "stage": "contract",
  "failure_code": "missing_filter",
  "node_id": "q1",
  "reason": "用户要求的长度大于 2 米条件没有进入 SQL",
  "expected": "effective_disease_length > 2",
  "actual": "SQL 中未发现该条件",
  "evidence": {},
  "allowed_actions": ["patch_queryspec", "retry_compile"],
  "attempt": 1,
  "max_repair_rounds": 2
}
```

### 9.2 控制器动作

控制器输出 RepairPatch，而不是完整重写 QuerySpec：

- `patch_filter_value`
- `patch_metric`
- `patch_dimension`
- `patch_view_shape`
- `add_supporting_query`
- `retry_compile`
- `repair_presentation`
- `ask_user`
- `unsupported`

### 9.3 修复护栏

- 每个修复动作只能修改失败指针对应的节点。
- 修复前后必须校验 `immutable_scope_hash`。
- 相同的 QuerySpec、SQL 或工具参数不能原样重试。
- 数据事实错误最多修复 2 轮。
- 表达修复不计入数据库重查预算。
- 依赖修复节点的下游节点只有在修复通过后执行。
- 第二轮仍产生相同失败证据时停止重复，并返回明确原因。

## 10. 错误兜底的硬规则

禁止用非空文案把失败伪装成成功。

后置计算没有结果时必须返回结构化失败，例如 `PostCalcFailure`，并在执行边界转换为 FailureEvidence。`accepted` 不能由“回复是否非空”推导。

允许使用异常的场景：

- 编程错误、数据库连接错误、不可恢复的基础设施错误。

不依赖异常表达的业务失败：

- 缺少依赖值。
- 没有数据。
- 计算结果为空。
- 用户问题超出当前数据能力。
- 枚举无法解析。

这些失败必须返回带失败码的结构化结果，由执行器统一处理。

## 11. 模块拆分

新增单轮查询内核，旧入口只做适配：

```text
backend/app/query/
  service.py          # 单轮查询门面
  contracts.py        # IntentContract / QuerySpec / FailureEvidence
  analysis.py         # 问题分析与意图契约
  fields.py           # FieldReachSet / PhysicalSchemaView / OutputProjection
  values.py           # ValueBinding / Provenance
  planner.py          # QuerySpec 到 QueryPlan
  compiler.py         # QueryPlan 到 CompiledQuery
  executor.py         # 执行与 Observation
  verifier.py         # 三层验收
  repair.py           # RepairPatch / 有界 controller
  answer.py           # AnswerPackage 与表达修复
```

边界要求：

- `agent.py` 最终只保留入口路由和旧流程适配，不继续承载单轮 SQL 细节。
- `nl2sql.py` 逐步迁出 QuerySpec、字段解析、SQL 生成和回答摘要。
- `templatizer.py` 拆分模板识别、参数绑定、模板验证和审核。
- `react_agent.py` 拆分黑板、执行器、controller、修复策略和结果组装。
- 拆分跟随功能迁移进行，不做无关的大范围格式化或一次性重写。

## 12. 回归与评测

### 12.1 固定真实答案集

每道题必须记录：

- 问题。
- 期望业务状态。
- 必要字段和条件。
- 精确答案或可验证不变量。
- 是否允许空结果。
- 是否允许部分结果。
- 最大展示行数。
- 禁止进入 SQL 的条件或枚举。

“可回答题明确失败”必须判失败，不能算通过。

### 12.2 必测类别

- 简单计数。
- 单指标分组。
- 多指标同分组。
- 路线长度和单位换算。
- 枚举 code 与中文标签。
- 时间范围和月份分组。
- 汇总加明细。
- 明细超过 500 行。
- 空数据库与条件空结果。
- 无法识别字段和超出数据能力。
- SQL 编译错误注入。
- 相同失败重复发生的终止行为。
- 表达错误只修表达、不重查数据库。

### 12.3 质量指标

- 一次答对率。
- 最终正确率。
- 错答放行率。
- 可回答题误停率。
- 自动修复成功率。
- 平均查询次数。
- 重复 SQL 执行次数。
- 范围漂移次数。
- 超能力问题正确拒绝率。

临时诊断脚本和日志不进入仓库；固定回归题、真实答案和契约测试属于核心工程资产，必须版本化。

## 13. 首阶段覆盖题目

第一阶段以单轮数据题为准，至少覆盖当前已发现的问题：

1. `西乡段泛油有多少处？`
2. `按路线分组，统计每条路线的病害总数、病害总面积、平均单处病害面积，并关联获取该路线的长度`
3. `按路线和病害类型分组，统计各路线下每种病害类型的数量，找出每条路线数量最多的主要病害类型`
4. `11月2日巡检了哪些线路？`
5. `近三月有多少巡检记录？`
6. `裂缝集中在哪几个月？哪些路？这些路的病害密度怎么样？`
7. `数据库里各个月份的巡查次数分别是多少？总共多少次？`
8. `2026 年 11 月，巡检设备分别完成了多少次巡检？`
9. `泛油分别落在哪些路线、各有多少处？`
10. `哪个道路的泛油问题更严重？`
11. `哪个道路的病害最严重？`
12. `长沙－芷江高速公路病害数量，最近是在增加还是在减少？`
13. `统计第三季度，不同病害在不同道路上的新增情况`
14. `病害长度大于 2 米的有多少处？这些病害的总长度是多少米？把具体的数据调出来`
15. `AI识别的病害类型，靠谱吗？有多少是认不出来的？`

题目答案可以随数据库变化，但查询范围、必需条件、结构不变量和单位口径必须固定。

## 14. 迁移顺序

### 阶段 1：契约和只读影子路径

- 建立 IntentContract、QuerySpec、三类字段视图、Observation 和 VerificationReport。
- 对固定题目生成影子 QuerySpec，并记录旧链路和新链路差异。
- 不改变线上默认回答。

### 阶段 2：简单单查询切换

- 计数、分组、明细、阈值过滤先切换到新内核。
- 旧路径保留为显式降级开关。
- 验收一次答对率、误停率和范围漂移。

### 阶段 3：汇总加明细与后置计算

- 支持一个用户回合内的多节点 QueryPlan。
- 修复明细截断语义和 post_calc 成功状态。
- 表达修复与 SQL 修复彻底分离。

### 阶段 4：默认启用并清理旧分支

- 单轮数据查询默认进入新内核。
- 仅在新内核不能处理的能力类型上保留旧路径。
- 按依赖迁移完成后删除重复规则和宽松兜底。

## 15. 验收标准

首阶段完成必须同时满足：

1. QuerySpec 不合法时不会生成或执行 SQL。
2. 所有过滤值和展示字段都有来源。
3. code 与中文标签在输入、执行和输出三个方向都有契约测试。
4. 分组、聚合、趋势和明细视图不会被错误混用。
5. 汇总加明细可在一个单轮问题中正确执行。
6. 明细超过 500 行时准确报告总数、展示行数和截断状态。
7. 表达错误只修复回答，不重新查库。
8. post_calc 空结果不会被标记为成功。
9. 可回答题出现明确失败时，回归评测判失败。
10. 超出数据能力的问题返回具体原因，不返回猜测答案。
11. 同一失败原样重复执行会被拒绝。
12. 第一阶段固定题目全部通过真实答案或不变量验证。

## 16. 风险与控制

- 领域建模过度：只覆盖巡检业务已确认对象和查询模式，不做通用 BI 平台。
- 迁移风险：新内核先影子运行，再按查询类型逐类切换。
- LLM 波动：关键事实由确定性代码校验，模型不直接决定成功。
- 延迟增加：简单题保持在确定性编译路径；只有失败时才进入有界修复。
- 测试维护成本：真实答案只记录稳定事实和不变量，不硬编码容易变化的展示摘要。
- 大文件拆分风险：按功能迁移拆模块，禁止无关重构和全库格式化。
