# TopN 契约、用户裁决与晋级考试设计

> 日期：2026-11-07
> 状态：已由用户确认
> 适用范围：单轮巡检查询、可疑结果用户裁决、用户否决后的有界修复、智能体晋级考试

## 1. 背景

用户问“把面积排名前五名，和长度排名前五名的病害调出来”时，规划结果包含两个
`view=top` 节点：

- `metrics=[]`
- `dimensions=[]`
- `output_projection` 包含病害编号、类型、面积、长度、桩号、路线和时间
- `order_by` 分别是 `area desc` 和 `effective_disease_length desc`
- `limit=5`

编译器把 `top` 当成“分组后取前几名”，只从 `metrics` 和 `dimensions` 生成 SELECT。
由于两者都为空，实际 SQL 变成 `SELECT FROM disease ... LIMIT 5`，排序字段也没有进入
ORDER BY。这个错误说明规划器和编译器共享了一个含义不明确的 `top` 视图。

同时，现有“答对了/答错了”按钮只记录反馈，不能在用户判定答案错误后自动把真实计划、
SQL、结果样本和疑点反馈给规划器。语义验收器只能提出疑点，不能替代用户判断答案是否
真正回答了问题。

现有评测还会用固定题反复调参。通过旧题不能证明泛化能力。需要把“新题一次通过率”
作为晋级门槛，并确保同一套题只在一次考试中有证明力。

## 2. 目标

1. 用明确契约区分“前 N 条明细记录”和“分组后的前 N 名”，在执行前拒绝含义不明的
   TopN 计划。
2. 当验收器怀疑答非所问，或修复后仍出现相同疑点时，向用户提供裁决卡。
3. 用户拥有最终正确性判断权。LLM 和代码只能提出疑点，不能代替用户说“这是对的”。
4. 用户判定错误后，只修复可疑节点，保留原问题、范围、时间、对象和业务编号。
5. 建立基于全新题目的一次通过率晋级考试，禁止用同一套题反复修到 100% 冒充能力提升。

## 3. 非目标

- 本阶段不重做长对话上下文补全。
- 本阶段不把正确性判断权交给独立 LLM 裁判。
- 本阶段不允许用户直接编辑任意 SQL。
- 本阶段不为每个查询节点创建独立 LLM。
- 本阶段不使用关键词、正则或题目 ID 判断业务语义。

## 4. TopN 视图契约

### 4.1 规范视图

原始自然语言可以先由规划器输出 `top`，但进入 QueryPlan 前必须由代码归一化为以下之一：

- `top_records`：按真实字段排序，返回最多 N 条明细记录。
- `top_groups`：按维度分组，按聚合指标排序，返回最多 N 个分组。

不会允许一个不区分模式的 `top` 进入编译器。

### 4.2 top_records 最小契约

- `metrics` 必须为空。
- `output_projection` 必须非空。
- `order_by` 必须是非空数组。
- 每个 `order_by.field` 必须是当前主体可输出的真实字段。
- `limit` 必须是正整数。
- SQL 必须包含明确的 SELECT 列表、ORDER BY 和 LIMIT。
- SQL 不得仅因排序字段而引入 GROUP BY。

### 4.3 top_groups 最小契约

- `metrics` 必须非空。
- `dimensions` 必须非空。
- `order_by.field` 必须是当前 `metrics` 或 `dimensions` 中声明的字段。
- `limit` 必须是正整数。
- SQL 必须包含 GROUP BY、ORDER BY 和 LIMIT。

### 4.4 执行前失败

契约不满足时，不执行 SQL，返回结构化失败：

```json
{
  "status": "unsupported",
  "failure_code": "invalid_top_contract",
  "node_id": "q1",
  "reason": "top_records 必须声明输出字段和排序字段",
  "allowed_repairs": ["patch_view_shape", "patch_output_projection", "patch_order_by"]
}
```

同一不可执行计划不得原样重复生成 SQL。

## 5. 用户裁决闭环

### 5.1 谁可以提出疑点

以下来源可以创建 `ReviewSuspicion`：

- 确定性契约验收。
- 独立语义验收器。
- 有界修复后的复验。
- 同一失败证据重复出现。

任何来源都不能直接决定“用户认为答案正确”。

### 5.2 ReviewSuspicion

```json
{
  "suspected": true,
  "reason": "问题要求前五条明细，但结果只有一个聚合值",
  "failure_layer": "contract",
  "node_ids": ["q1"],
  "evidence": {
    "question": "把面积排名前五名的病害调出来",
    "view": "top_records",
    "sql_summary": "SELECT SUM(...) ...",
    "result_summary": "1 行，有效病害总长度 151579.56"
  }
}
```

### 5.3 用户裁决卡

回答 payload 增加可选字段：

```json
{
  "review_gate": {
    "review_token": "...",
    "title": "我不确定这次结果是否回答了你",
    "reason": "问题要求前五条明细，但结果看起来是聚合值",
    "nodes": []
  }
}
```

卡片展示：

- 用户原问题。
- 每个可疑节点的子问题。
- QuerySpec 视图摘要。
- SQL 摘要。
- 结果列、行数和样本。
- 疑点原因。

按钮只有两个：

- `回答正确，继续`
- `回答错误，重新规划`

### 5.4 用户判定正确

- 标记该 `review_token` 已接受。
- 保留当前结果。
- 记录一条 `good` 反馈。
- 不重新执行 SQL。

### 5.5 用户判定错误

- 后端只信任 `review_token` 绑定的缓存结果，不信任前端重新提交的计划或 SQL。
- 读取原问题、QueryPlan、QuerySpec、SQL、结果样本和疑点，生成结构化 `ReviewEvidence`。
- 进入有界修复，只允许修改 `node_ids` 指定的节点。
- 第 1 轮修复后再次验收。
- 若仍有疑点，最多进行第 2 轮修复。
- 第 2 轮后仍不能证明可用时停止，返回明确失败原因和已完成事实。
- `review_token` 只可消费一次；重复提交返回 `review_token_consumed`。

### 5.6 范围不变量

修复前后的以下对象必须保持一致：

- 用户原问题。
- 主体。
- 路线、路段、设备、任务和业务编号。
- 时间范围。
- 病害类型和实体成员。
- 阈值和比较方向。
- 用户要求的输出目的。

任何需要改变上述内容的修复都必须停止并请求用户确认，不能自动扩大或缩小范围。

## 6. 数据流

```text
用户问题
  → QuerySpec
  → TopN/视图契约校验
  → SQL 编译和执行
  → 确定性验收 + 语义验收
  → 无疑点：正常回答
  → 有疑点：回答 + 用户裁决卡
      → 用户判定正确：结束
      → 用户判定错误：ReviewEvidence
          → 只修复可疑节点
          → 重新验收
          → 最多两轮
          → 成功或明确失败
```

## 7. 模块边界

- `backend/app/query/shape_contracts.py`
  - 输入：QuerySpec、CapabilityRegistry。
  - 输出：通过或结构化契约问题。
  - 职责：top_records/top_groups 及其他视图执行前契约。
- `backend/app/query/review.py`
  - 输入：AnswerPackage、VerificationReport、结果缓存。
  - 输出：ReviewSuspicion、ReviewEvidence、ReviewDecision。
  - 职责：用户裁决和一次消费票据。
- `backend/app/query/repair.py`
  - 输入：ReviewEvidence。
  - 输出：受限 RepairPatch。
  - 职责：只修可疑节点，校验范围哈希。
- `backend/app/query/spec_mdl.py`
  - 只编译已经通过契约的 QuerySpec，不再自行猜测 `top` 模式。
- `backend/app/routers/chat.py`
  - 提供裁决提交接口，不承载修复逻辑。
- `frontend/src/components/ChatPanel.vue`
  - 只负责展示裁决卡和提交用户决定。
- `backend/evals/promotion/`
  - 出题、随机抽旧题、运行考试、语义判定、晋级报告。

## 8. 晋级考试原则

### 8.1 每轮题量

- 全新题：15 道。
- 历史题随机抽样：5 道。
- 总计：20 道。

### 8.2 新题来源

新题只能从 `docs/archive/巡查业务问题.md` 的业务能力重新组合生成，并满足：

- 不与当前考试集重复。
- 不复用上一轮新题。
- 不包含题目 ID 到 SQL 或字段的映射。
- 必须覆盖资产、病害、时间、巡检任务、设备、管养、TopN、趋势、明细和不支持能力。
- 至少包含一道需要明确拒绝或说明能力不足的题。

### 8.3 旧题来源

旧题池由以下冻结资产组成：

- `backend/evals/single_turn/cases.yaml`
- `backend/evals/single_turn/holdout_20.yaml`
- 后续正式保存的晋级考试题。

每轮使用记录在报告中的随机种子抽取 5 道。

### 8.4 通过标准

一轮考试同时满足以下条件才算通过：

- 新题首次运行至少 `12/15`。
- 旧题随机抽样至少 `4/5`。
- 总通过数至少 `16/20`。

### 8.5 题目作废规则

- 考试结果首次低于门槛后，可以诊断性重跑和修复。
- 同一套题修复后即使达到 `15/15`，也不代表晋级。
- 只要业务代码发生修改，下一次考试必须生成新的 15 道题。
- 考试报告记录代码指纹；代码指纹变化后复用旧考题，运行器必须判失败。

### 8.6 判定方式

- 使用独立语义裁判检查问题、QuerySpec、SQL、结果和最终回答是否一致。
- 不得使用 `required_contains`、关键词包含、正则或题目 ID 作为主要通过条件。
- 确定性契约测试可以用于定位失败层，但不能替代语义判定。
- 裁判无法证明正确时必须判 `unverifiable`，不能放行。

### 8.7 考试报告

每个考试集和运行结果必须记录：

- 考试集 ID。
- 生成时间。
- 业务文档版本或哈希。
- 随机种子。
- 15 道新题和 5 道旧题的题号。
- 代码指纹：Git HEAD + 工作区差异哈希。
- 每题状态、失败层和证据摘要。
- 新题通过数、旧题通过数、总通过数。
- 是否达到晋级线。

## 9. 验收标准

1. `top_records` 不会再生成空 SELECT，也不会丢失 ORDER BY。
2. 聚合指标混入 `top_records` 时在执行前失败。
3. `top_groups` 缺少指标或分组时在执行前失败。
4. 有疑点的回答会返回用户裁决卡。
5. 用户判定正确后不重新执行 SQL。
6. 用户判定错误后只修复可疑节点，最多两轮。
7. 修复不能改变原始范围和范围哈希。
8. 失效或重复使用的 review token 被明确拒绝。
9. 晋级考试固定 15 新题 + 5 随机旧题。
10. 新题首次低于 80% 时不能晋级。
11. 修改代码后复用旧考试集会被考试运行器拒绝。
12. 所有晋级判定使用独立语义裁判，不依赖关键词或题目 ID。

## 10. 风险与缓解

- 用户裁决过多：只在存在结构化疑点时展示，不打断所有正常回答。
- 修复扩大范围：用范围哈希和节点白名单约束。
- 题目泄漏：每轮生成新题并记录已曝光题。
- 裁判偏松：无法证明正确时判失败，并保留逐题证据供人工复核。
- 文件继续膨胀：业务逻辑放入 query 子模块，路由和 UI 只做适配。
