# 选模板直出仍偏慢 + 尾部"要不要再帮你看看"修复方案（给 codex）

## 一、现象

在确认卡里点了模板口径（例如"宝安大道西乡段的泛油病害中，面积超过 10 平方米的有多少处"），结果内容是对的（回"0 处，面积实际范围 0.17~7.52，>10 超范围"），但：

1. 比固定看板刷新、快捷查询慢很多（看板/快捷查询是亚秒级，这里要多等几秒到十几秒）。
2. 回复末尾被追加"要不要我再帮你看看：1.… 2.… 3.…"，用户不想要，要求直接给结果。

## 二、根因（已逐行定位，行号为 2026-09-22 快照，以函数名为准）

点模板是**第二次请求**（带 choose_token + capability_id），这条"纯执行"链路大部分已经做对了：

- `handle_message` 里 `execute_choice=True`，已跳过上下文补全、意图分类（agent.py:3055-3083，intent 直接给 "data"）。
- plan 用确认时暂存的 `chosen_plan`，不重新 `build_query_plan`（agent.py:1179 `plan = plan or ...`、3265 传入）。
- 模板 SQL 是物理 SQL，直接 `sql_engine.execute_sql` 执行，**不走 Wren**（agent.py:1484）。
- 所以不是"引擎选了仅 Wren"，也不是连库慢（连库已有缓存）。

问题出在一个**漏标的短路标记**：

1. `_build_query_result` 在执行 SQL 前先做范围校准 `calibrate.check(plan)`（agent.py:1283-1288）。阈值超出实际范围（coverage=="none"）时，在 agent.py:1290-1314 **提前 return 一条确定性校准回复**（engine="calibrated"），这个 dict **没有 `direct: True`**。而正常模板执行路径在 agent.py:1552-1554 显式设了 `result["direct"]=True`。
2. 外层入口 agent.py:2405 是 `if payload.get("direct"): return payload`。校准分支没标 direct，这一条件不成立，于是继续跑后置三步：
   - `_verify_and_refine`：calibrated 在跳过白名单里（agent.py:2574-2586），**不花 LLM**。
   - `_reflect_check_step`：短回复、source 非 analysis 时跳过（这次也没花 LLM）。
   - `_followup_step`（agent.py:2496-2508）：只看 `followup_suggestions` 开关（默认开，chat_settings.py:42-43 取 `config.followup_suggestions_enabled=True`），且只排除了 source=clarification/error；**calibrated、template、preset、chosen_* 这些确定性来源都不在排除名单 → 必然再调一次 LLM**（`_followup_suggestions_sync`，agent.py:2511-2524，用 role_model("knowledge")），既生成了"要不要再帮你看看"，又带来一次数秒到十几秒的模型往返。

结论：**这次点模板后多出的延迟和尾部追问，是同一件事——确定性结果漏标 direct，导致尾部 followup 大模型调用没被短路。** 正常"模板查到非空结果"的路径因为 1552 标了 direct 是快的；唯独"范围校准提前返回"这类分支漏了。

## 三、修改项

### P0-1 确定性直出统一短路（在外层一处兜底，避免再漏分支）

把 agent.py:2405 的判定从"只看 direct 标记"扩展为"direct 为真 **或** 来源属于确定性直出引擎集合"，命中就直接 return，不再跑 verify/reflect/followup：

```python
_DETERMINISTIC_ENGINES = {
    "template", "template_match",
    "preset", "chosen_preset",
    "chosen_auto", "chosen_auto",
    "chosen_example", "chosen_example_direct", "saved_example", "saved",
    "chosen_code_template", "generic", "chosen_generic",
    "calibrated", "post_calc", "dialogue-state",
}
if payload.get("direct") or str(payload.get("engine") or "") in _DETERMINISTIC_ENGINES:
    return payload
```

（集合以代码里实际出现的 engine 字符串为准：chosen_* 前缀来自 agent.py:3217 `f"chosen_{kind}"`，kind 取 capabilities.execute 的 preset/auto/example/example_direct/code_template/generic；按实际补齐。）

同时在 agent.py:1290 校准提前返回的 dict 里补 `"direct": True`（双保险）；并排查 `_build_query_result` 内 forced_sql 路径上是否还有其他"提前 return 的确定性分支"漏标 direct，一并补上。

### P0-2 确定性结果永不生成 followup，并默认关闭后续建议

- `_followup_step`（agent.py:2496）的排除逻辑与 `_verify_and_refine` 的引擎白名单对齐：engine 命中上面的确定性集合时直接 return payload，不生成追问。
- 把后续建议默认关掉：`config.py:140` `followup_suggestions_enabled: bool = False`（chat_settings.py:42-43 的默认值随之变 False）。用户明确表示不要"要不要再帮你看看"；前端设置项保留，需要的人可手动开。
- 若以后想保留该功能，建议只对 `source=analysis` 的非确定性长分析回答生成，计数/明细/校准类一律不生成。

### P0-3 校准在"已确认口径"下仍保留，但必须走直出短路

`forced_sql`（用户已在卡里确认）时 calibrate 范围校准可以保留——超范围直接回"0 处 + 实际范围"是对的，用户也认可这段内容；但它属于确定性直出，必须命中 P0-1 的短路，尾部不得触发任何 LLM。

## 四、验收

1. "西乡段泛油面积 > 10"：点模板后直接回"0 处 + 实际面积范围 0.17~7.52"，**无"要不要再帮你看看"**；后端日志该次请求在出卡之后零 LLM 调用，总耗时降到与快捷查询/看板刷新同量级（只剩 DB 的 MIN/MAX 校准查询，亚秒~1 秒级）。
2. 点模板返回非空结果（如西乡段泛油计数 = 534）同样无尾部追问、无后置 verify/reflect/followup。
3. AI 直答（非模板）路径：默认无 followup；在设置里手动打开后，也只有分析型长回答才出现追问。
4. 固定看板刷新、快捷查询、复合逐步骤、Wren 直答不回归。

## 五、改动文件

- `backend/app/services/agent.py`：2405 短路条件改为 direct 或确定性引擎集合；1290 校准返回补 `"direct": True`；`_followup_step` 排除确定性引擎。
- `backend/app/config.py:140`：`followup_suggestions_enabled` 默认改 False。
- 前端若有"后续建议/猜你想问"开关，默认态同步为关。

## 六、第二类慢路径：内置代码模板"首次自动直出"（没点确认卡）

### 6.1 现象（第二个实测例子）

问"置信度最高的病害是哪个？类型是什么？桩号？"，命中内置极值模板，第一次提问就直接出了结果（没走确认卡），但仍然不立即返回、末尾仍有"要不要再帮你看看"。

### 6.2 根因（与第三章不同的另一条路径）

这条不是确认卡 chosen（`forced_sql` 为空），问题有四个：

1. **最贵的规划被重复执行两次。** 总闸 agent.py:3114-3127 为了判断"模板能不能一次答对"，先跑了一次 `nl2sql.build_query_plan`（含 parse_semantics，qwen3-coder-plus，是链路上最贵的一次模型调用）拿到 `probe_plan`，但只用它判断 `build_template_sql(probe_plan)` 是否非空、然后只把 `mixed_request=False`，**`probe_plan` 没有传给后续**。进入 `_build_query_result` 后 agent.py:1179 `plan = plan or nl2sql.build_query_plan(...)` 又跑了一遍完全相同的规划。
2. **内置模板结果没标 direct、engine 名字还不一致。** 内置模板在 agent.py:1256-1262（兜底 1420）生成 `template_sql`，这不是 `forced_sql`；执行成功后 `from_template=True`，但 1552 的 `if forced_sql:` 不成立，**不标 `direct`**；engine 被 1560 `setdefault` 成 `"template"`（preset 结构匹配命中时才叫 `"template_match"`）。
3. **校验白名单漏了 `"template"`。** `_verify_and_refine` 的确定性跳过名单（agent.py:2574-2586）只有 `"template_match"`，没有 `"template"`；而这条结果是一行多列（编号/类型/桩号），不满足 `_is_single_scalar_result`（要求单行单列），于是又跑一次 `verify_answer` 大模型。
4. **followup 照跑。** `_followup_step` 不排除 `"template"`，再调一次模型生成"要不要再看看"。

再叠加首次请求前面必跑的意图分类（和可能的上下文补全），内置模板其实只省掉了"写 SQL"那一次，却仍有：意图分类 + 补全（可能）+ **规划×2** + verify + followup，所以只比全 LLM 略快，远达不到快捷查询 `/preset-query` 的亚秒级。

### 6.3 修改项

**P0-4 规划只跑一次。** 总闸算出的 `probe_plan` 一路传进 `_build_query_result`（作为 `plan=` 入参），让 agent.py:1179 直接复用，删掉第二次 `build_query_plan`；本次请求内对同一问题的 plan 做缓存兜底。

**P0-5 内置模板直出统一按确定性结果处理。**

- 1256-1262 / 1420 生成的模板 SQL 执行成功后，和 `forced_sql` 一样设 `result["direct"]=True`。
- 统一 engine 命名并对齐三处白名单：内置代码模板统一 `"template"`，把 `"template"` 同时加进第三章 P0-1 的外层确定性短路集合、`_verify_and_refine` 跳过名单（2574-2586）、`_followup_step` 排除集合；`"template_match"` 作为别名保留。`template` / `template_match` 两个名字不一致是这次漏校验/漏追问拦截的根因，建议在一处用常量集合统一定义，agent 各环节引用同一份。

**P0-6 内置模板首次直出是否校验，做成开关、默认不校验。** 内置模板是系统自动选用、用户没点过确认，理论上存在"模板能生成 SQL 但答非所问"的可能（极值/分布类）。新增设置 `verify_template_direct`，默认 **False**（信模板、直接出，最快）；保守的环境可开，开了也只允许一次、用便宜模型（flash）做校验，且**绝不生成 followup**。确认卡 chosen_* 路径永远不校验、不追问。

**P1（结构性，真正对标快捷查询的零 LLM 快路）。** 在意图分类、上下文补全**之前**加一条确定性快路：用不依赖 parse_semantics 的轻量槽位抽取（规则 + 字段目录 field_catalog / 字段触达，复用《字段目录配置与字段触达前置方案》）判断问题能否被内置/preset/auto 模板**完整绑定**（路线/类型/时间/阈值/极值/TopN 等槽位齐全且合法）；能完整绑定就直接 execute SQL 返回，全程不跑分类、补全、规划、verify、followup；绑定不了再进现有完整链路。这需要把模板匹配从"依赖 LLM plan"解耦成"轻量 plan"，是让高频确定性问题达到 `/preset-query` 亚秒级的根本做法，单列为 P1，不阻塞 P0。

### 6.4 验收（在第四章基础上追加）

1. "置信度最高的病害是哪个？类型是什么？桩号？"首次提问命中内置模板：后端日志里 `build_query_plan`/parse_semantics 对同一问题只出现 **1 次**；无"要不要再看看"；默认无 verify。
2. P0 完成后该请求耗时显著下降（去掉规划×1 + verify + followup）；P1 完成后命中确定性快路时为亚秒级、零模型调用，与看板刷新/快捷查询持平。
3. 内置模板返回多列结果默认不再触发校验；把 `verify_template_direct` 打开时才校验，且任何情况下确定性结果都不出现 followup。
4. `"template"` 与 `"template_match"` 两种 engine 标签在短路、校验跳过、追问排除三处行为一致。

### 6.5 改动文件（在第五章基础上追加）

- `backend/app/services/agent.py`：总闸把 `probe_plan` 传入 `_build_query_result`（消除重复规划）；内置模板成功路径标 `direct`；用一份常量集合统一确定性 engine（含 `template`/`template_match`）并在 2405 短路、2574 校验白名单、2496 追问排除三处共用。
- `backend/app/config.py` / `chat_settings.py`：新增 `verify_template_direct`（默认 False）；`followup_suggestions_enabled` 默认 False。
- P1：`nl2sql.py` / 模板匹配层新增"轻量 plan + 完整绑定判定"接口，`agent.handle_message` 在分类/补全前接确定性快路。

## 七、点了模板却显示"Wren 语义层"：确认动作静默失效（P0，必须加硬保证）

### 7.1 现象

确认卡已经把模板口径摆出来，用户点了"用这个口径查询"，结果工作台"执行引擎"仍显示 **Wren 语义层**，说明用户选的 SQL 根本没执行，被偷偷换成了 Wren 重查。这也是"说了三回命中即直出仍没改好"的真正原因——前几版改的是"绑定成功之后"的提速与去追问，而这次的问题发生在更前面：**绑定这一步失败了，却静默回退了**。

### 7.2 绑定成功的路径本来是对的（先排除怀疑）

`agent.py:3213` capabilities.execute 得到 chosen_sql → 3258 以 `forced_sql=chosen_sql` 进 `_build_query_result` → 1203 `template_sql=forced_sql` → 1274 `sql=template_sql` → 1319 `if not sql` 为假，**跳过 Wren** → 1484 物理执行 → 1564 `engine=forced_engine=chosen_*`。所以只要 chosen_sql 非空，就不会走 Wren。

### 7.3 真正的口子：三种"确认失效"全部静默回退，没有任何兜底

chosen_sql 在 agent.py:3195 初值为 None、chosen_engine 为 ""。以下三种情况任一发生，都不会报错、不会重新出卡，而是带着空的 forced_sql 走普通链路，模板没接住就落到 Wren（1319）：

1. **token 取不到暂存（cached is None）**：agent.py:3190 `cached = capabilities.take(choose_token)`，而 take 是进程内字典的**一次性 pop**（capabilities.py:31、596-603），TTL 过期或 token 已被消费过一次就返回 None；3191/3200 两个分支都不进，**没有 else**。常见诱因：前端重复/并发提交把 token 先消费掉、卡片停留超过 TTL、（若以后多 worker/重启）进程内 stash 不共享。
2. **候选 id 对不上（picked is None）**：agent.py:3206-3210 用 `capability_id` 在 candidates 里按 `item["id"]` 精确匹配；自动模板候选存在 `id` 与 `template_id` 两个值（execute 里 auto 用的是 `template_id or id`，capabilities.py:696），前端若回传了另一个，picked 就是 None，`if picked:` 整块跳过，**没有 else**。
3. execute 返回空 SQL 已有 raise ChooseCapability（agent.py:3237），这一种是安全的，不用改。

### 7.4 必须落地的硬保证（断言式，不是建议）

**P0-A 确认请求只允许两种结局，禁止静默换引擎。** 凡是请求带 `choose_token` 且 `capability_id` 不在 {ai,wren}：

- 绑定成功 → engine 必须是 `chosen_*`、direct=true、走用户选的 SQL；
- 绑定失败（cached None / picked None / execute 空）→ 必须重新生成确认卡（重新 collect 候选）或明确提示"你选的口径已失效，请重新选一次"，**严禁继续走 Wren/内置 LLM**。

在 agent.py:3190（cached None）和 3210（picked None）补 else：记日志并重新出卡/回到确认态，不允许带着空 chosen_sql 往下走到 3258。

**P0-B 加一条断言级校验。** 进入 `_build_query_result` 时若 `capability_id` 是确定性候选但 `forced_sql` 为空，直接视为绑定失败处理（同 P0-A），不允许该请求最终 engine=wren/llm。

**P0-C 可观测，一眼定位绑没绑上。** 每个确认请求落一条事件日志，取值：`capability_chosen`（成功，带 kind/id/note）/ `capability_token_missing`（take 为空）/ `capability_pick_missing`（id 对不上，带传入 id 与候选 id 列表）/ `capability_bind_failed`（execute 返回空），并记录**最终 engine**。复测时凭日志即可判断是"绑定失败回退"还是"绑定成功但后置没短路"。

**P0-D 复核候选 id 一致性。** 自动模板候选卡片回传的 id 必须与 capabilities 收集时 candidate["id"]、execute 内 auto 分支使用的 `template_id/id` 完全一致；统一成一个字段，杜绝 picked None。

**P0-E 暂存健壮性。** 本地 run.py 是单 worker（已核实 run.py:74-79，无 workers、reload=False），内存 stash 暂可用；但要在部署文档写明"确认卡依赖进程内内存，必须单 worker"。若以后上多 worker/多实例，把 `_STASH` 落到共享存储（Redis/DB/文件缓存，复用现有连库缓存那套），否则确认会概率性失效。

### 7.5 前端引擎标签要能区分"我选的模板"（否则用户无法验收）

ResultPanel.vue:301-306 的 ENGINE_LABELS 只认 template/wren/llm/builtin，`chosen_*`、`template_match`、`calibrated`、`preset/auto/generic`、`saved_*` 全都不认识，会直接显示英文原值。补全映射，让用户一眼确认走的是不是自己选的口径：

- `chosen_preset` / `preset` → "预置模板（已确认）"
- `chosen_auto` / `auto` → "自动模板（已确认）"
- `chosen_code_template` / `template` / `template_match` → "确定性模板（已确认）"
- `chosen_generic` / `generic` → "通用算子（已确认）"
- `chosen_example` / `chosen_example_direct` / `saved` / `saved_example` → "已存示例（已确认）"
- `calibrated` → "范围校准（未执行查询）"；`post_calc` → "后置计算"；`dialogue-state` → "对话状态"
- 同时在结果台展示一个"本次零大模型直出"标记（direct=true 时亮），点了模板却没亮即视为异常。

### 7.6 复合题确认同样要短路

agent.py:3243-3256 复合题逐步骤/整题确认后，结尾是无条件 `_verify_and_refine` + `_followup_step`（3255-3256）。改为：数据子步骤若来自 chosen_*（确定性直出），按第三章 P0-1 的确定性集合跳过 verify/followup；只有真正走 Wren/LLM 的步骤才保留校验。复合确认同样不允许出现"要不要再帮你看看"。

### 7.7 端到端红线（用户点"用这个口径查询"后的唯一允许时序）

绑定 SQL → 物理执行（不调 Wren、不调写 SQL 模型）→ 组装结果（engine=chosen_*、direct=true）→ 外层短路立即返回。这中间**不得**出现：意图分类、上下文补全、重新 build_query_plan、选表、Wren 编译、verify、reflect、followup。任何一步做不到，就回到确认卡让用户重点一次，而不是静默换路。

### 7.8 验收（针对本章）

1. 正常点预置/自动/内置模板：结果台显示"XX模板（已确认）"、零大模型直出标记亮、无追问，SQL 与所选模板一致。
2. 人为制造失效（重启后端清空 stash 后再点旧卡 / 传一个不存在的 capability_id）：系统必须回"口径已失效，请重新选一次"并重新出卡，**绝不允许**返回一个 engine=wren 的结果。
3. 日志四类事件齐全，成功时最终 engine=chosen_*。
4. 复合题逐步骤确认后无 followup，确定性步骤不校验。
5. 前端不再出现 chosen_xxx 这类英文原值。

## 八、弹卡本身也慢：为"决定摆不摆卡"跑了三遍大模型（P0/P1）

### 8.1 现象

第一次提问、系统摆出"用这个口径查询"确认卡之前，也要等十几秒。弹卡理论上只需要规则匹配，应当是毫秒~1 秒级。

### 8.2 弹卡前的真实调用链（自包含问题 + 命中确定性模板 + 首次提问，行号为 2026-09-22 快照）

| 顺序 | 步骤 | 位置 | 是否调模型 |
|---|---|---|---|
| 1 | 复用示例"同句"精确匹配 | nl2sql.find_reusable_example（不传 plan，走 5681-5704 本地分支） | 否，纯本地 |
| 2 | 上下文补全 contextualize | memory.py:895 无条件先调 `_llm_complete_followup`（dialogue_understanding 模型） | **会话有历史且未过期时，每一轮都先调 1 次，不管这句本身完不完整**；memory.py:927 那条"完整句直接返回"的规则，只在无历史/上下文过期/LLM 不可用的兜底分支才走到（见 P0-D） |
| 3 | **意图分类 classify_intent** | agent.py:3123-3127 → intent.py:121，model=role_model("semantic") | **是，每次必跑 1 次** |
| 4 | **总闸 build_query_plan**（只为判 mixed_request） | agent.py:3158-3171，3165 调 build_query_plan（含 parse_semantics，qwen3-coder-plus，链路上最贵） | **是，第 1 次** |
| 5 | **执行函数里再次 build_query_plan** | _build_query_result 开头 `plan = plan or build_query_plan(...)`（agent.py 约 1179）；总闸的 probe_plan 没传下来 | **是，第 2 次，与第 4 步完全重复** |
| 6 | collect_capabilities 收集候选 | capabilities.py:481-529，preset/auto 规则匹配、code_template 走纯函数 build_template_sql；命中 preset/auto 时不 rerank | 否 |
| 7 | raise ChooseCapability 弹卡 | — | 否 |

结论：弹一张卡串行跑了 **1 次意图分类 + 2 次最贵语义规划 = 3 次大模型**（短追问/纠正再加 1 次补全）。第 4、5 步是同一次规划跑两遍，纯浪费；而第 3、4、5 步对"摆模板卡"这件事都不是必需的——preset/auto/code_template 的结构匹配只依赖结构化槽位。

### 8.3 改造

**P0-A 规划全程只跑一次（先砍掉重复）。** 总闸算出的 `probe_plan` 必须传进 `_build_query_result`（plan 入参），让约 1179 行直接复用；本次请求内对同一 effective_message 的 plan 做缓存。删掉第 5 步那次重复 parse_semantics。

**P0-B 确定性探测前移到意图分类之前，命中模板就跳过分类。** 调整 handle_message 顺序：先做跨库规则判定和 `asks_knowledge`/混合题判定（保留 3162 那条，数据+规范混合不许模板接），再做确定性模板探测；只要 preset/auto/code_template/generic 结构匹配命中：
- ask 模式：直接摆确认卡，intent 由 plan.shape 映射（count/distribution/list→data/analysis），**跳过 classify_intent 这次大模型**；
- auto 模式：可完整绑定就直接执行直出。
- 只有确定性模板一个都没命中，才调 classify_intent + 完整 build_query_plan 走 Wren/LLM。
模板命中本身就是"这是查库题"的强信号，跳过分类不会误判知识题（知识/混合题已在前置规则排除）。

**P0-C 示例向量召回后置。** 步骤 1 的"同句精确匹配"是本地操作，保留在前面；需要向量/同义召回的完整版 find_reusable_examples（带 plan）只在确定性模板未命中后再做，避免弹卡路径多一次远程往返。

**P0-D 补全 LLM 加"自包含闸门"，长对话该调才调（修正一处现状浪费）。** 现状 contextualize 在 memory.py:895 只要会话有历史就**无条件**先调一次 dialogue_understanding，哪怕用户这轮明明新开了一句带全条件的完整题（如聊了几轮后突然问"西乡段7月泛油有多少处"），这次调用判完"new_topic/原样返回"等于没补，但钱和时间照花。改造：在 895 这次 LLM 之前，先用已有的零成本规则信号做一道闸门（这些信号代码里都有，不新增关键词体系）：

- 判为"强自包含、可跳过 LLM"需**同时**满足：句子自带实体条件（`_known_route_in_message` / parse_pile_range / parse_time_range / parse_device_id 任一命中，即 self_conditioned）**且**不含指代词（POINTING_WORDS：那/它/这/呢/这段/那条…）**且**不像追问（looks_like_followup）**且**不含强制 LLM 信号（_FORCE_LLM_HINTS：其中/也一起/多了多少/相差/加起来/错了/我说的是/应该是…）**且**不是短裸句（short_bare）。
- 满足 → 直接按独立题返回原文，不调 895 的 LLM（等价于让模型判 new_topic）。
- 任一不满足（短追问、指代、比较、纠正、承接、条件不全）→ **保留 895 的 dialogue_understanding LLM**，由模型做继承/替换/对比/指代消解，长对话能力一点不丢。
- 闸门原则是**宁可保守**：只有正向证据充分才跳过，任何不确定都走 LLM。正确性（别把追问误判成独立题）优先于省这一次调用。

快路的完整时序因此是：零成本自包含闸门 →（不自包含才花 1 次补全 LLM，把句子补成自包含）→ 对补全后的句子做零 LLM 轻量模板探测 → 命中即弹卡/直出；未命中才进 classify_intent + build_query_plan + Wren。首轮无历史天然不调补全；长对话里的完整独立题经闸门也不调；长对话追问保留 1 次补全，但补全后若能命中模板，仍可省掉后面的分类和两次规划。

**P1 轻量 plan 抽取器，让弹卡/直出做到零生成模型。** 新增一个不调用 coder-plus 的"轻量槽位抽取"：用规则 + 字段目录 field_catalog（复用《字段目录配置与字段触达前置方案》）抽出路线/病害类型/时间/桩号/阈值/极值/TopN/上下行等槽位与 shape。确定性模板（preset/auto/code_template/generic）的结构匹配与参数绑定只依赖这个轻量 plan。handle_message 在补全之后、意图分类之前插一条确定性快路：

1. 跨库规则判定、asks_knowledge/混合题判定；
2. 轻量槽位抽取 → plan_lite；
3. 确定性模板 / 已存示例匹配：ask→直接弹卡（零生成模型，亚秒级）；auto→完整绑定即直出；
4. 抽不出 / 匹配不上 / 槽位置信不足 → 回落到现有完整链路（classify_intent + 一次 build_query_plan + Wren），保证不漏题。

轻量 plan 与完整 plan 同一套槽位字段，后续 chosen 执行、口径卡片直接复用，不需要再抽一遍。

### 8.4 改造前后对照（命中确定性模板的首次提问）

| | 现状 | P0 后 | P1 后 |
|---|---|---|---|
| 意图分类 LLM | 1 次 | 命中模板跳过（0） | 0 |
| parse_semantics（最贵） | 2 次（重复） | 1 次 | 0（轻量抽取替代） |
| 补全 LLM（首轮/无历史） | 0 | 0 | 0 |
| 补全 LLM（长对话·完整独立题） | 1（判完等于没补，白调） | 0（自包含闸门跳过） | 0 |
| 补全 LLM（长对话·追问/指代/纠正） | 1 | 1（保留，该花） | 1（保留） |
| 弹卡耗时来源 | 3 次串行模型 | 1 次规划 | 规则+字段目录，无生成模型 |
| 体感 | 十几秒 | 数秒 | 亚秒~1 秒，与快捷查询同量级 |

未命中模板的难题保持完整链路，能力不降级，只是不再为简单题付全套模型成本。

### 8.5 验收

1. 命中确定性模板的问题首次提问：弹卡前日志中 classify_intent 0 次、build_query_plan/parse_semantics 全程 1 次（P0）；P1 后弹卡路径 0 次生成模型，弹卡耗时亚秒~1 秒。
2. 总闸与执行函数不再各规划一次（同一问题 parse_semantics 日志只出现 1 次）。
3. 补全闸门：首轮无历史不调补全；长对话中带全条件的完整独立题（如中途问"西乡段7月泛油有多少处"）不调 dialogue_understanding；短追问/指代/比较/纠正（"那恒明珠段呢""其中西乡段多少""多了多少""错了，是恒明珠"）仍必须调补全 LLM 且补全结果正确，不得因闸门漏判成独立题。
4. 知识题、数据+规范混合题、跨库题在快路被正确排除，仍走拆解/知识库，不被模板截胡（回归 H2/H3/H10、F8/F10）。
5. 轻量抽取抽不出槽位时必须无缝回落完整链路，不得答空或答非所问。
6. 确认卡展示的口径/SQL 与改造前一致（只改时机与次数，不改模板匹配结果）。

### 8.6 改动文件

- `backend/app/services/agent.py`：总闸 probe_plan 传入 `_build_query_result`（消除重复规划）；确定性探测前移到 classify_intent 之前，命中即弹卡/直出并跳过分类；示例向量召回后置。
- `backend/app/services/nl2sql.py`：新增"轻量 plan + 完整绑定判定"接口（P1），与完整 plan 同槽位结构；build_query_plan 增加请求级缓存。
- `backend/app/services/capabilities.py`：collect_capabilities 支持用轻量 plan 做确定性匹配。
- 复用《字段目录配置与字段触达前置方案》的 field_catalog 作为轻量槽位抽取的事实来源。
- `backend/app/services/memory.py`：contextualize 在 895 无条件 LLM 之前加"自包含闸门"（复用 POINTING_WORDS / looks_like_followup / _FORCE_LLM_HINTS / self_conditioned / short_bare 现有信号），强自包含独立题跳过 dialogue_understanding，追问/指代/比较/纠正保留 LLM。
