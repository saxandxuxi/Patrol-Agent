# 项目原则：AI 晋级考试与用户裁决

> 本文件与 `项目原则-禁止正则与关键词硬匹配.md` 同级生效。每次修改 QuerySpec、规划器、
> SQL 编译器、结果验收、答案组装或评测代码前，都必须先阅读这两份原则。

## 一、用户拥有最终正确性判断权

1. LLM、语义裁判和代码验收器只能提出疑点，不能代替用户判断答案是否正确。
2. 只有存在结构化疑点时，才展示用户裁决卡；正常且无争议的回答不被反复打断。
3. 用户点击“回答正确，继续”后，系统保留结果，不重新执行 SQL。
4. 用户点击“回答错误，重新规划”后，系统读取后端缓存的真实 QueryPlan、QuerySpec、SQL
   和结果样本，不信任前端重新提交的计划或 SQL。
5. 修复最多两轮。相同计划或相同失败证据不得原样重复执行。
6. 修复只能修改被用户判定为可疑的节点，其他节点必须逐字段保持不变。
7. 修复不得改变用户原问题、主体、过滤条件、时间范围、路线、病害、设备、任务或业务编号。

## 二、TopN 契约

1. `top_records` 表示按真实字段排序返回前 N 条明细。
2. `top_groups` 表示按维度分组、按聚合指标排序返回前 N 个分组。
3. 不允许一个含义不明的 `top` 进入 SQL 编译器。
4. `top_records` 必须有输出字段、排序字段和正整数 `limit`，不得声明聚合指标或分组维度。
5. `top_groups` 必须有聚合指标、分组维度和正整数 `limit`。
6. 聚合值不能冒充 TopN 明细；TopN 明细不能静默变成 SUM/AVG 汇总。

## 三、晋级考试

### 3.1 每轮题量

- 全新题：15 道。
- 随机旧题：5 道。
- 总计：20 道。

### 3.2 新题要求

1. 只从 `docs/archive/巡查业务问题.md` 的业务能力重新组合生成。
2. 不得复用上一轮新题或已经曝光的题目。
3. 不写题目 ID 到 SQL、字段或答案的映射。
4. 覆盖病害、资产、时间、巡检任务、设备、管养、TopN、明细、趋势和能力不足。
5. 至少一道题要求系统明确说明缺少数据能力或需要补充业务口径。

### 3.3 旧题随机池

旧题只从以下冻结题库抽取：

- `backend/evals/single_turn/cases.yaml`
- `backend/evals/single_turn/holdout_20.yaml`
- 后续正式保存的晋级考试题

每轮必须记录随机种子和抽中的题目 ID。

### 3.4 晋级线

同一轮首次运行必须同时满足：

- 新题至少 `12/15`。
- 旧题至少 `4/5`。
- 总计至少 `18/20`。

任一条件不满足，本轮不得晋级。

### 3.5 作废与重考

1. 同一套题可以重跑用于诊断，但重跑不能作为晋级证据。
2. 只要业务代码发生修改，必须重新生成 15 道新题。
3. 代码指纹变化后复用旧考试集，考试运行器必须直接失败。
4. 不能把同一套题修到 100% 后宣称能力已经达到晋级线。
5. 只有一套从未见过的新题首次运行达到晋级线，才算通过。

### 3.6 判定方式

1. 使用独立语义裁判检查原问题、QuerySpec、SQL、结果和最终回答是否一致。
2. 禁止使用 `required_contains`、关键词包含、正则或题目 ID 作为主要通过条件。
3. 裁判无法证明正确时必须判失败，不能默认放行。
4. 确定性测试用于定位契约和编译问题，不替代语义裁判。
5. 语义裁判必须获得与 Planner 同源的统一能力注册表事实，包括字段标签、枚举和
   `available/unavailable` 状态；不得用通用领域常识覆盖注册表中的字段含义。

### 3.7 报告

必须保存并版本化：

- 考试集 ID 和生成时间。
- 业务文档哈希。
- 随机种子和 5 道旧题 ID。
- 15 道新题 ID 和题目。
- 代码指纹。
- 每题状态、失败层和证据摘要。
- 新题、旧题和总通过数。
- 是否达到晋级线及具体原因。

### 3.8 基础设施阻塞

模型限流、余额不足、供应商停机、网络传输失败不得计入业务能力失败，也不得传给语义裁判。

1. 同一 `provider + base_url + model` 的所有角色共享限速；优先遵守 `Retry-After`。
2. 余额不足或账户停用必须立即失败关闭，不得进行普通限流重试。
3. 业务结果必须携带结构化失败代码，例如 `llm_rate_limited`、`llm_quota_exhausted`、
   `llm_transport_error`。
4. 考试遇到基础设施阻塞时，该题记为 `infrastructure_blocked`，后续题记为 `not_run`，
   不再调用语义裁判，也不输出“通过/不通过”的业务考试成绩。
5. 恢复基础设施后必须重新生成全新 15 题和随机 5 道旧题，不得沿用被阻塞的考试集。

## 四、修改检查表

每次修改相关代码前必须回答：

1. 本次改动是否修复一个共同契约或数据流漏洞，而不是单题特判？
2. 是否新增关键词、正则或题目 ID 映射？如果有，改动不合格。
3. 是否保留用户范围并具备范围哈希保护？
4. 是否增加了边界契约测试和同义改写测试？
5. 是否重新生成全新 15 题并搭配随机 5 道旧题？
6. 是否记录代码指纹，并拒绝复用已作废考试集？

## 五、业务单元考试

复杂能力不得用一套综合题掩盖局部逻辑漏洞。恢复阶段按业务单元逐项考试：

1. 每个单元固定生成 15 道与该业务能力直接相关的新题。
2. 另从冻结旧题库随机抽 5 道，随机种子和题目 ID 必须记录。
3. 单元晋级线仍是新题至少 `12/15`、旧题至少 `4/5`。
4. 单元题必须覆盖不同措辞、不同数据范围以及至少一个无数据或能力不足场景。
5. 首次未通过时，只按共同失败层修复，不按单题增加特判。
6. 只要业务代码发生变化，当前单元考试集立即作废，必须重新生成 15 道新题。
7. 一个单元通过后，下一单元重新生成全新题；不得把上一单元已经曝光的题当作新题。
8. 所有单元通过后，再生成覆盖多个业务维度的综合题。

当前恢复顺序：

1. 资产角度的时间维度。
2. 资产病害数量与规模。
3. 病害类型。
4. 分段查询。
5. 病害角度位置与分布。
6. 病害尺寸。
7. 设备与巡检任务。
8. 长时间变化。
9. 综合题。

管养维度在数据能力补齐前暂不纳入考试。

## 六、回答输出：准确度和体验都要管

准确率达标不等于体验达标。回答既要对，也要让人一眼看懂、问法换了结论不漂移。

1. **同义问法必须稳定**：“这次巡检的 AI 识别结果可信度怎么样”和“巡检数据质量怎么样”
   可以换字段描述，但不能给出互相矛盾的结论；换说法不该改变口径、字段或极值方向。
2. **极值/排名必须有排序**：最大、最小、最多、最少、最高、最低、最严重、排名、前几名
   这类问法，计划里必须有 `order_by`。带 `limit` 却没有排序的明细查询返回的是任意几条
   记录，属于无效计划，执行前就要拦住。
3. **指标必须真的被聚合**：声明了 `metrics` 就只能落在 `count`、`sum`、`avg`、
   `distribution`、`trend`、`top_groups` 上；`list`、`detail`、`data` 不聚合，声明指标
   等于把用户要的总面积悄悄换成明细行。
4. **链式依赖要带上条件**：依赖上一节点取值的查询，结果必须能看出“这是哪条路、哪种病害、
   哪次巡查”的数据，明细放进输出字段，分组放进分组维度，回答里也要写明沿用了什么条件。
5. **空值不等于 0**：只有确实补齐的枚举分组才能说“已按 0 计入”；分组里没有有效数值时，
   如实说明是空，不能含混成 0。
6. **数据题指路、分析题给结论**：数据题回答事实并指路结果工作台；分组结果要先给一行
   确定性的“排序前列”摘要，不能只丢一句“请在结果工作台查看”。
7. **拒绝要说清原因**：拒绝查询时必须区分能力缺失、计划不合法、范围确实没有记录，
   并把原因和下一步都说清楚，不能只甩内部视图名或英文异常。

## 七、工具执行与证据收集：禁止无信息重复

1. 每次调用工具前必须先说明它要补足的“证据缺口”；没有证据目标的操作不得重复执行。
2. 相同工具、相同参数、相同环境状态已经返回结果时，禁止原样再次调用。
3. 只有参数发生变化、外部状态发生变化，或明确属于一次性可恢复的瞬时故障时，才允许有界重试。
4. 重试必须记录次数和退避策略；达到上限后应停止该调用并报告结构化阻塞原因。
5. 若已有结果没有提供新信息，下一步必须读取不同证据源，例如日志、进程状态、数据库事实、
   SQL、执行计划或另一类只读工具，不能反复提交同一个操作。
6. 对仍在运行的长时间任务，不得连续轮询同一个状态接口。对 `write_stdin` 一类交互式会话，
   输出没有新增内容时禁止反复读取；只有出现新输出、阶段变化或明确的外部状态变化时，才允许
   再次读取。应优先换用日志、阶段事件或子任务进度等证据源。
7. 测试和 Agent 实现应记录工具调用指纹（工具名 + 规范化参数 + 关键环境状态）；发现重复
   指纹且没有新证据时，直接进入换查询、停止并说明原因或请求用户裁决，不能继续消耗额度。
