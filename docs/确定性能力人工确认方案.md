# 确定性能力人工确认方案（模板/示例命中后人来选）

这份方案解决一个问题：确定性模板和已验证示例能省成本、结果稳定，但不能由代码静默自动命中——一旦把问题理解错（例如把"病害尺寸"猜成宽度/高度），会直接跑出一个看着对、其实口径错的结果，中途既不给过程也不征求确认。

目标流程是：问题先转成 plan，按现有匹配逻辑找出可能命中的模板和示例，但**不执行**，而是把候选连同"这次会怎么查"的口径展示给用户，由用户选定后再确定性执行；没有候选就照常走 Wren，不打扰用户。

本方案只负责"把数据查对、把命中口径交给人确认"。占位值、异常值等脏数据属于数据清洗业务，不在本方案范围。

## 一、现状（已具备的基础）

代码里现在有三类确定性命中，命中后在 reuse_mode=auto 下直接执行：

1. 示例闸：nl2sql.find_reusable_example(message, kind, plan)，向量召回加结构同型、槽位对齐、条件覆盖，返回单条 spec（含 sql、doc_name）。
2. preset 模板闸：preset_lib.match_template(plan)，按 shape、主体、槽位结构匹配 preset_queries.json，返回 {id, sql}。
3. 代码模板闸：nl2sql.build_template_sql(plan)，即 nl2sql.py 里二十多个 _build_xxx_template 构造器，仅在 is_simple_single_query 时兜底，返回拼好的 SQL。"病害尺寸排名前三"就是被这一类自动接走的。

同时已有一套可直接复用的"执行前确认"往返协议：

- 开关 confirm_before_query、请求字段 confirmed；agent.handle_message 在未确认时可用 build_query_plan 出 probe、needs_confirm 判断，返回 source="confirm"、await_confirm=true、scope_card（口径卡片）和 restate（人话复述）。
- 前端 ChatPanel 已有"确认查询"按钮（confirmQuery）、confirmedNext 和 payload.await_confirm 的处理。
- preset_lib 已有 options_for（路线/月份/类型等参数选项）和文件版本热加载。

缺的只是：把"命中了哪个模板/示例、口径是什么"做成候选放进确认卡，由人选，而不是代码直接执行。

## 二、交互流程

对话内提问（看板卡片、快捷查询是用户手动点的，等同已确认，不弹此卡）：

1. 正常走长对话补全、意图分类、语义解析，得到 plan（这几步保留，不追求零调用）。
2. 候选收集器用 plan 同时跑三类匹配，得到 0 到 N 个候选，只收集、不执行。
3. 没有候选：直接走 Wren，链路和现在一致，用户无感。
4. 有候选：返回一张"选择查询口径"确认卡（复用 await_confirm 往返），列出候选，默认选中推荐项；用户可以：
   - 直接点"用这口径查询"：执行当前选中候选；
   - 改选其他候选；
   - 修改候选预填的槽位值（路线、月份、病害类型、上下行、Top N 等）；
   - 展开看该候选的 SQL；
   - 点"都不是，让 AI 自己查"：放弃候选，走 Wren。
5. 用户选定后，前端把所选能力标识和可能改过的槽位随 confirmed 请求发回，后端跳过重新匹配和 SQL 生成，直接绑定执行，返回结果结构与 /api/chat 一致。

复合问题：规划器拆成多个子问题后，对其中需要查库的子问题分别收集候选，在同一张确认卡里按步骤列出（每一步一行：子问题描述、推荐口径、可改选、可让该步走 AI），用户一次确认整条链路；后置计算、综合分析、知识检索这类不查库的步骤不需要确认。确认后各步按选定能力执行，链式 produces 回填逻辑不变。

## 三、模式开关

复用现有 reuse_mode，明确三档含义，对话内默认改为 ask：

- ask（默认，人决定）：命中确定性能力就弹候选确认卡，不自动执行。
- auto：高置信唯一候选自动执行，仅在多候选分差接近或槽位需补充时才询问（保留给追求速度、愿意事后核对的场景）。看板卡片和快捷查询始终直接执行，不受此开关影响。
- off：不使用任何确定性能力，全部走 Wren。

引擎开关 engine_mode（hybrid/wren）与 reuse_mode 保持两个维度，不合并、不新增更多开关。

## 四、后端改造

### 1. 候选收集器（只收集不执行）

新增 collect_capabilities(message, plan, kind)，按固定顺序调用三类匹配，输出统一候选列表：

- preset：preset_lib 模板，需要 match_template 支持返回有序候选（现在只回最佳一个，扩展为按匹配度返回若干条，每条带命中维度和缺口）。
- example：find_reusable_example 扩展为返回 topK（现在回单条），每条带结构同型、槽位对齐、相似度信息。
- code_template：把 build_template_sql 包装成候选，标明来自哪个 _build_xxx 构造器（如 generic_metric、metric_top、density），并给出该构造器实际使用的指标列、分组、排序口径。

统一候选结构：

- kind：preset / example / code_template
- id：模板 id、示例 doc_name 或代码模板名
- title、question：标题和原始问法
- scope：人话口径（范围、对象、指标、分组、时间、排序/Top N、过滤条件）
- shape、subject：查询形态和主体
- slots：识别到的槽位当前值，以及每个槽是否可改、可选项来源（复用 preset_lib.options_for）
- condition_coverage：条件覆盖检查结果（是否存在候选表达不了的多余条件）
- score 与 reasons：打分和命中/扣分理由，用于排序和"为什么推荐"
- sql_preview：可展开的 SQL（示例、代码模板给归一化或将要执行的 SQL；管理端可见，普通视图默认折叠）

### 2. 排序与推荐

规则打分，不靠模型自由发挥：形状一致、槽位齐全、条件完整覆盖为硬门槛（任一不满足不进候选或标灰并注明缺口）；在此之上按 槽位覆盖最全 > 条件覆盖最严 > 语义最接近（示例）> 历史成功率 排序，取第一名标"推荐"。确需在多个近似候选间判断时，可调用一次小模型，只让它输出排序和一句话理由，不让它生成或改写 SQL。

特别处理模糊指标：当问题里的指标无法唯一映射到物理列（"尺寸"可能指面积、病害长度、宽度、高度），代码模板候选必须在口径里明确写出"按哪个列算"（例如"按宽度 area_width、高度 area_height 排序"），让用户在确认卡上一眼看到分歧；这类候选不得作为静默自动执行项，ask 模式下天然由人纠正。

### 3. 候选与 plan 的暂存

候选确认是两次请求，为避免第二次重新规划、重新匹配花钱，第一次返回确认卡时把 plan 和候选列表缓存（内存或 result_cache，发一个 choose_token）。第二次请求带 choose_token、所选候选 id、槽位覆盖值和 confirmed，后端直接取出 plan 与候选执行。缓存设短 TTL（如三十分钟）即可。

### 4. 选定后执行

- preset：用所选 id 绑定（含用户改过的）槽位值，走现有 preset 白名单绑定执行。
- example：把槽位值填入示例的归一化 SQL 占位，经过和 preset 同样的值校验后执行。
- code_template：用（可能改过槽位的）plan 重新调用对应构造器生成 SQL 并执行；确定性，结果与展示口径一致。
- 用户选"让 AI 查"：该步走 Wren 正常链路。

三类执行都保留只读、SELECT/WITH 校验、明细 LIMIT 上限等现有约束。执行结果仍可走现有结果校验器；用户主动确认的口径若校验发现明显答非所问，仍可提示，但不强行改判用户明确选择的口径。

### 5. 返回协议

在现有 source="confirm"、await_confirm=true 的 payload 上增加：

- choose_token
- capability_choices：候选数组（结构同上）
- recommended_id：推荐候选 id
- 复合问题时按步骤分组，每步带自己的候选与推荐

### 6. 代码模板自动命中收口

ask 默认开启后，agent._build_query_result 中"命中即直接执行"的三处（约 1218-1248 行）改为：先 collect_capabilities；ask 模式下有候选就回确认卡，不再直接拼 template_sql 执行；auto/off 行为保持现状。这样代码模板和 preset、示例一样，都纳入"人确认"这一关。

## 五、前端改造

- 把现在单一的"确认查询"区域升级为候选确认卡：候选以卡片或单选项列出，推荐项置顶并标注推荐理由；每张卡显示人话口径，槽位用下拉/日期等控件预填可改（选项复用现有参数选项接口）；"查看 SQL"折叠展示；底部三个动作：用这口径查询、让 AI 自己查、取消。
- 复合问题在卡里按步骤分行，每步可独立选口径或标记该步走 AI。
- 看板卡片、快捷查询页不出现此卡（手动点选即确认）。
- 用户改槽位后，卡上口径文案随之更新，保证"所见即所查"。

## 六、验收用例

- 问"宝安大道西乡段病害尺寸排名前三是什么类型"：确认卡出现，代码模板候选明确写着"按宽度 area_width、高度 area_height 排序取前三"，用户看到口径不对，可改选其他候选或点"让 AI 自己查"，系统不会再静默返回宽度一百、高度五十、类型为空的结果。
- 问"西乡段泛油有多少处"：出现 preset/示例候选，口径为"西乡段、泛油、计数、排除已删除"，槽位预填正确，一键确认即确定性返回，不重新生成 SQL。
- 把同一问题换成不同问法（"西乡段有几处泛油"）：示例候选能被召回并出现在卡里。
- 候选槽位识别有误时，用户在卡里把路线从西乡段改成恒明珠，确认后按恒明珠执行，结果随之改变。
- 没有任何候选的问题不弹卡，直接走 Wren，交互无多余打断。
- 复合问题一次确认中能为不同子步骤分别选口径或让某步走 AI，确认后链式执行、前序产出正常回填后序。
- reuse_mode 切到 auto 时高置信唯一候选不弹卡直接执行，切到 off 时全部走 Wren；看板和快捷查询在任何模式下点击即执行。

## 七、落地步骤

1. preset_lib.match_template 与 find_reusable_example 支持返回有序多候选及命中/缺口信息。
2. 实现 collect_capabilities 统一收集三类候选并规则打分、给推荐和人话口径；为代码模板候选补指标列/分组/排序口径说明。
3. 实现 plan 与候选的 choose_token 暂存，以及选定后按三类分别绑定执行的入口。
4. agent 命中处接入 ask 分支：有候选回 capability_choices 确认卡，无候选走 Wren；复合问题按子步骤收集。
5. 前端把确认区升级为候选卡（选择、槽位编辑、SQL 展开、让 AI 查、复合分步）。
6. reuse_mode 对话默认改 ask，回归看板、快捷查询、auto/off 三种路径。
