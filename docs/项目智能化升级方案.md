# 项目智能化升级方案

> 目标：把现在"规则驱动 + LLM 兜底"的系统，改成"LLM 主导 + 规则做校验"的智能体。
> 核心思路：能交给 LLM 的判断都交给 LLM，规则只做硬校验。

---

## 一、当前项目为什么不够智能？

### 1. 到处都是"规则先判断，LLM 兜底"

现在的架构是：**规则能搞定的就不用 LLM，搞不定才找 LLM。**

结果就是：
- 意图分类：规则先匹配，匹配不上才找 LLM → "健康状况更好"被规则判成 knowledge
- 拆分器：规则先判断要不要拆，判断要拆才找 LLM 拆 → 该拆的没拆，不该拆的拆了
- SQL 生成：模板先试，模板不行才 Wren，Wren 不行才内置 LLM → 模板蠢得要死，但还在第一优先级
- 长对话补全：规则先补，补不上才找 LLM → 很多指代规则认不出来

**问题本质：** 规则是"穷举关键词"，覆盖不了所有问法。LLM 才是真理解语义的。

### 2. 没有多轮自我纠错能力

现在的流程：
```
生成 SQL → 执行 → 校验一次 → 对就返回 / 不对就优化一次 → 重查 → 还不对就放弃
```

**问题：** 只重试一次，而且是"优化问题"，不是"让 LLM 自己想哪里错了"。
- 第一次错了，LLM 根本没看到错在哪
- 只是把问题改了改，重新生成一遍，可能还是错
- 没有"反思"这个环节

### 3. 没有错误记忆

现在系统是"金鱼记忆"：
- 上次犯了什么错，下次遇到类似问题还是会犯
- 不知道这个用户经常问什么类型的问题
- 不知道哪种问法容易翻车

### 4. 没有工具调用能力

现在 LLM 是"闭着眼睛写 SQL"：
- 不知道表里有多少条数据
- 不知道某个字段实际有哪些值
- 写出来 SQL 对不对，全靠猜

---

## 二、怎么变得更智能？

### 核心原则：把判断权从规则手里拿过来，交给 LLM

| 现在（规则驱动） | 以后（LLM 驱动） |
|----------------|----------------|
| 规则判断意图 → 错了才找 LLM | LLM 直接判断意图 |
| 规则判断要不要拆 → 要拆才找 LLM | LLM 直接判断要不要拆 + 怎么拆 |
| 模板先试 SQL → 不行才 Wren → 不行才 LLM | LLM 直接写 SQL（Wren 做编译器） |
| 规则判断补全上下文 → 补不上才找 LLM | LLM 直接补全上下文 |
| 校验一次就放弃 | 校验不对就自己反思 → 再试 → 最多3次 |

---

## 三、具体升级方案

### 升级1：意图分类完全交给 LLM

**现在：** 规则先匹配，匹配不上才找 LLM
**改成：** 直接找 LLM 判断意图

**好处：**
- 不会把"健康状况更好"误判成 knowledge
- 能理解隐含意图（"这个问题严重吗？" → analysis）
- 不用维护规则关键词表

**改法：**
```python
# 现在
if 规则匹配到 "怎么处置/规范/标准":
    return "knowledge"
if 规则匹配到 "图片/看看":
    return "image"
# 规则匹配不上才找 LLM
intent = llm_classify(message)

# 改成：直接找 LLM
intent = llm_classify(message)
```

---

### 升级2：拆分器完全交给 LLM

**现在：** 规则先判断要不要拆，要拆才找 LLM 拆
**改成：** 直接找 LLM 判断"要不要拆 + 怎么拆"

**好处：**
- 不会把"上行和下行各有多少"误判成要拆
- 能理解"多个维度一次答全" vs "多个独立问题要拆"
- 不用维护拆分规则

**改法：**
```python
# 现在
if 规则判断 "包含多个问号/多个时间点":
    tasks = llm_decompose(message)
else:
    tasks = [单问题]

# 改成：直接找 LLM
tasks = llm_decompose(message)
if len(tasks) == 1:
    走单查询路径
else:
    走复合问题路径
```

---

### 升级3：SQL 生成只走一条路

**现在：** 模板 → Wren → 内置 LLM，三级降级
**改成：** 只走 Wren 一条路

**好处：**
- 不用维护模板了
- 所有问题都走 LLM 语义理解，准确率高
- 新场景改 MDL 就行，不用写 Python 模板

**改法：**
```python
# 现在
if is_simple_single_query(plan):
    sql = build_template_sql(plan)
    if sql 成功:
        执行返回
if wren_available:
    sql = generate_mdl_sql(plan)
    if 编译成功:
        执行返回
sql = generate_physical_sql(plan)  # 内置LLM

# 改成：只走 Wren
sql = generate_mdl_sql(plan)
编译执行
```

---

### 升级4：加多轮自我纠错（反思机制）

**现在：** 校验一次，不对就优化一次问题，重查一次
**改成：** 校验不对 → 让 LLM 自己反思"我哪里错了" → 改 SQL → 再执行 → 再校验，最多3次

**流程：**
```
第1次：生成 SQL → 执行 → 校验
   ↓ 不对
第2次：把"SQL + 结果 + 问题"给 LLM，问它"你觉得哪里不对？应该怎么改？"
   ↓ LLM 改 SQL
   ↓ 执行 → 校验
   ↓ 不对
第3次：再让 LLM 反思 → 改 SQL → 执行 → 校验
   ↓ 还不对
   ↓ 如实告诉用户"这个问题我答不好"
```

**好处：**
- 不是"改问题"，是"改 SQL"，更直接
- LLM 能看到自己哪里错了，下次就不会犯
- 最多3次，不会死循环

---

### 升级5：加错误记忆

**现在：** 每次都是新的，不记得之前犯过什么错
**改成：** 把每次错误的"问题类型 + 错误原因 + 正确做法"存下来，下次遇到类似问题提前提醒

**存什么：**
- 问题：西乡段上行和下行各有多少处？
- 错误：没写 GROUP BY，只返回了总数
- 原因：LLM 忽略了"各/分别"的分组信号
- 正确做法：SQL 里必须有 GROUP BY

**怎么用：**
- 下次生成 SQL 之前，把类似问题的错误经验放在提示词里
- 比如："上次你把'各有多少'写成了 COUNT(*) 没分组，这次注意"

---

### 升级6：加工具调用（Function Calling）

**现在：** LLM 闭着眼睛写 SQL
**改成：** LLM 可以自己调用工具：
- `查schema()`：看某张表有哪些字段
- `查表数据()`：看某条记录长什么样
- `校验SQL()`：跑一下看对不对

**流程：**
```
LLM 写 SQL
   ↓
觉得不确定 → 调用工具查一下 schema
   ↓
觉得不确定 → 调用工具跑一下看看结果
   ↓
确认没问题 → 返回给用户
```

**好处：**
- LLM 不会瞎猜字段名了
- 写出来 SQL 自己先验证一遍
- 准确率大幅提升

---

### 升级7：加结果解读的反思

**现在：** 结果出来直接总结，不管对不对
**改成：** 总结完之后自己再检查一遍

**检查什么：**
- 用户问了3个维度，我答了几个？
- 数字和 SQL 结果对不对？
- 有没有把单位搞错？
- 有没有答非所问？

**不对就自己改，不用用户说。**

## 四、改造优先级

| 优先级 | 升级项 | 预期效果 | 工作量 |
|--------|--------|---------|--------|
| P0 | 全部走 Wren，废弃模板 | 准确率提升 | 小（你已经决定了） |
| P0 | 意图分类完全交给 LLM | 减少误判 | 小 |
| P0 | 拆分器完全交给 LLM | 减少漏拆/错拆 | 中 |
| P1 | 加多轮自我纠错（最多3次） | 准确率再提升 | 中 |
| P1 | 加错误记忆 | 不重复犯错 | 大 |
| P2 | 加工具调用 | 准确率大幅提升 | 大 |
| P2 | 加结果解读反思 | 减少答非所问 | 中 |

---

## 五、为什么这样改就智能了？

**现在的系统：** 像一个新员工，只会按 SOP 办事，遇到 SOP 上没有的情况就懵了。

**改完的系统：** 像一个老员工，遇到问题自己想办法，错了自己改，下次不犯同样的错。

核心区别：
- **规则是死的，LLM 是活的**
- **规则是穷举，LLM 是理解**
- **规则是一次对，LLM 是越用越对**

你之前说"补一个漏一个"，就是因为在用规则穷举。把判断权都交给 LLM，就不用穷举了，LLM 自己会理解。
