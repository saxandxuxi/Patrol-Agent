# 多步推理链式依赖整改方案：结果回填机制

---

## 一、问题描述

有一类问题不是"几个独立子问题拼在一起"，而是"先查出一个对象，再拿这个对象去下钻"。后面查询的条件，来自前面查询的结果。

典型例子：

> 7月份数量最多的那一天，主要是什么类型的病害？集中在哪条路？为什么那天突然冒出来这么多？是那天巡检特别仔细，还是真的出了大面积病害？

这道题的正确思考顺序是：

1. 先查7月份每天的病害数量，找到最多的那一天（比如7月30日，104处）
2. 再查7月30日各病害类型的分布
3. 再查7月30日各路线的分布
4. 再查7月份每天的巡检任务次数（看那天是不是巡检也更频繁）
5. 最后综合分析：是巡检仔细还是真的病害多

这里步骤2、3的查询条件"7月30日"，在用户的原始问题里是没有的，必须等步骤1查完才知道。

---

## 二、现在的链路为什么不行

现在的任务规划器（planning.md）确实能把问题拆成多个步骤，但是有一个根本缺陷：

**规划器在一开始就把所有子问题的查询文本写死了，执行的时候子问题之间不传递结果。**

具体表现：

1. 规划器可能把步骤2写成"那一天各病害类型的数量分布"
2. 执行步骤2的时候，系统根本不知道"那一天"具体是哪一天
3. data类型的子任务之间没有依赖关系，depends_on 只有 analysis 和 post_calc 才会自动加
4. 步骤虽然是顺序执行的，但步骤1查到的"7月30日"这个结果不会回填到步骤2的问题里

结果就是：
- 要么步骤2查成全库的数据（时间条件丢了）
- 要么LLM自己瞎猜一个日期
- 要么直接报错说缺时间条件

同类问题还有很多，都是"先找对象，再下钻"的链式依赖：

| 用户问题 | 第一步要先查出 | 后面依赖这个结果 |
|---------|--------------|----------------|
| 病害密度最高的那条路，主要是什么病害类型？ | 密度最高的路线名（西乡段） | 查西乡段的类型分布 |
| 哪次巡检发现的病害最多？把那次的明细调出来 | 巡检任务编号（XCBH...） | 查这个编号的明细 |
| 面积最大的病害在哪条路？它是什么类型？ | 最大面积病害的id/桩号 | 查这条记录的路线和类型 |
| 7月份病害最多的那天，比平时多多少？ | 峰值日期和峰值数量 | 算峰值和平均值的差 |
| 泛油最严重的路段，上下游有什么区别？ | 泛油最多的路段名 | 查这个路段的上下行分布 |

这些问题的共同点：第二个问题的查询条件，是第一个问题的答案。

## 三、整改方案：加"结果回填"机制

核心思路：不要让规划器在一开始就把所有查询条件写死，而是允许子问题里带"占位符"，等前面的步骤查完，把结果填进去再查后面的。

### 整体流程

```
步骤1：查7月份每天病害数量
   ↓ 执行，拿到结果
   ↓ 从结果里提取关键值：峰值日期 = 7月30日，峰值数量 = 104
   ↓ 把这个关键值回填给后面依赖它的步骤
步骤2：查【7月30日】各病害类型分布     ← 占位符被替换
步骤3：查【7月30日】各路线分布         ← 占位符被替换
步骤4：查7月份每天巡检次数（独立，不用回填）
   ↓
步骤5：综合分析，拿到前面所有结果下结论
```

---

## 四、具体改动

### 改动1：规划器提示词（planning.md）要标清依赖和产出

现在规划器只输出 action / purpose / query，要让它多输出两个字段：

- produces：这一步会产出什么关键值（比如"峰值日期"、"巡检任务编号"、"路线名"）
- needs：这一步依赖前面哪一步产出的什么值，在query里用占位符标出来

输出格式改成：

```json
{
  "is_simple": false,
  "final_goal": "找到7月病害最多的一天，分析那天的病害特征和突增原因",
  "steps": [
    {
      "step": 1,
      "action": "query_data",
      "purpose": "找到7月份病害数量最多的那一天",
      "query": "7月份每天的病害数量分别是多少，按数量从高到低排序",
      "produces": [
        {"key": "peak_date", "label": "病害最多的日期", "from_column": "日期"},
        {"key": "peak_count", "label": "那天的病害数量", "from_column": "数量"}
      ]
    },
    {
      "step": 2,
      "action": "query_data",
      "purpose": "看那天主要是什么类型的病害",
      "query": "{{peak_date}}这一天，各病害类型分别有多少处",
      "needs": [{"key": "peak_date", "from_step": 1}]
    },
    {
      "step": 3,
      "action": "query_data",
      "purpose": "看那天病害集中在哪条路",
      "query": "{{peak_date}}这一天，各路线分别有多少处病害",
      "needs": [{"key": "peak_date", "from_step": 1}]
    },
    {
      "step": 4,
      "action": "query_data",
      "purpose": "判断那天是不是巡检也更频繁",
      "query": "7月份每天的巡检任务次数分别是多少"
    },
    {
      "step": 5,
      "action": "analyze",
      "purpose": "综合判断是巡检仔细还是真的病害突增",
      "query": "对比那天的病害数量和巡检次数，结合其他天的情况，分析病害突增是巡检频繁导致的，还是真的出了大面积病害",
      "needs": [{"key": "*", "from_step": 0}]
    }
  ]
}
```

规划器提示词要补充的规则：

1. 如果后面步骤的查询条件来自前面步骤的答案，必须在query里用 {{key}} 占位符标出来，不要写"那一天/那次/那条路"这种指代词
2. 产出关键值的步骤要写 produces，说清楚这个值从结果的哪一列取（from_column）
3. 用到占位符的步骤要写 needs，说清楚这个值来自哪一步
4. 一步只查一个明确的东西，不要把"先找最大值再分组"塞进一个SQL里（LLM写这种嵌套SQL容易错，拆开更稳）
5. 如果一个SQL就能算出来（比如GROUP BY + ORDER BY LIMIT 1直接带出类型），就不用硬拆，规划器自己判断

### 改动2：执行器（agent.py _handle_composite）加回填逻辑

现在的执行循环是按顺序执行每个task，改成：

1. 维护一个变量字典 values = {}，存前面步骤产出的关键值
2. 每执行一个data子任务前：
   - 检查它的 needs
   - 把query里的 {{key}} 替换成 values 里对应的真实值
   - 如果依赖的值还没查到（前面的步骤失败了），这一步标记为"缺依赖，跳过"，不要硬查
3. 每执行完一个data子任务后：
   - 如果这一步有 produces，让LLM从结果里提取关键值
   - 提取规则：看 from_column 指明的列，取第一行（因为前面的SQL一般都ORDER BY + LIMIT 1了）
   - 存进 values 字典，比如 values["peak_date"] = "2026-07-30"
4. 把回填后的真实问题（而不是带占位符的问题）传给这一步的NL2SQL链路
5. analysis 和 post_calc 步骤照常拿到前面所有结果

关键值提取建议用一个很轻量的LLM调用（或者直接代码取列值，因为produces已经标了from_column，大多数情况不用LLM）：
- 能直接从结果第一行某列取到的，直接代码取（峰值日期、任务编号、路线名都是这样）
- 取不到或者需要总结的，再让LLM提取

### 改动3：回填要处理值的"形态"

从结果里取出来的值，要变成能直接写进SQL WHERE条件的形态：

- 日期：结果里可能是 "2026-07-30 00:00:00"，回填到问题里要变成"2026年7月30日"，让语义层自己去转时间范围
- 路线名：直接用规范名（比如"宝安大道西乡段"），语义层会解析成route id
- 巡检编号：原样保留，并且提醒规划器/语义层"这是编号不是时间，不要加时间范围"（这个坑之前踩过）
- 数值：带单位回填，比如"104处"、"7.52平方米"

### 改动4：上下文记忆也要能接住这种链式追问

单轮的多步拆解决了，长对话里同样的场景也要能接住：

- R1：7月份哪天病害最多？ → 系统回答7月30日，同时把"peak_date=7月30日"存进会话上下文
- R2：那天主要是什么类型？ → 补全成"7月30日主要是什么病害类型"
- R3：集中在哪条路？ → 补全成"7月30日病害集中在哪条路"

这个和已有的长对话补全（context_rewrite.md）是一套机制，只是补全的时候要能拿到上一轮提取出的关键值，而不是只拿到一句自然语言回复。建议每轮回答完都提取一次关键实体（日期、路线、类型、编号、桩号、数值）存进上下文，和现在的 last_entity 机制合并。

## 五、和现有机制的关系

1. 不替代任务规划器，是在规划器输出的基础上加"依赖声明 + 结果回填"
2. 不替代后置计算（post_calc）：纯算术的（多多少、差多少）还走post_calc；需要再查一次库的链式下钻才走这个回填机制
3. 不替代综合分析（analysis）：analysis还是最后一步，只是它能拿到的前序结果现在更完整了
4. 模板快速通道不受影响：简单单查询不拆，也就没有回填这回事
5. 回填后的子问题，照样走"模板优先、Wren主力"的分流逻辑，不用特殊处理

## 六、验收标准

用下面几组问题端到端测试，重点看后面的子问题有没有正确带上前面查出的条件：

1. 7月份数量最多的那一天，主要是什么类型的病害？集中在哪条路？
   - 步骤2、3的SQL里必须出现步骤1查出的那个具体日期，不能是"那一天"也不能是全库

2. 我们管的这几条路，病害密度最高的是哪条？它主要是什么病害类型？
   - 第一步先算出密度排名，第二步的SQL必须只查密度最高那条路，不能又把所有路查一遍

3. 7月份哪次巡检发现的病害最多？把那次巡检的明细调出来
   - 第二步明细SQL必须带上第一步查出的巡检编号（patrol_id/patrol_number要探测对），不能加时间范围把编号当日期

4. 全库面积最大的病害在哪条路？是什么类型？有图片吗？
   - 后面几步都要锁定第一步查出的那一条病害记录

5. 西乡段泛油最多的桩号是哪个？那个桩号附近500米还有哪些病害？
   - 第二步的桩号范围必须来自第一步的答案

6. 简单问题不能被过度拆分（回归）：
   - "西乡段泛油有多少处"必须还是一步直接查，不能为了走回填机制硬拆成多步
