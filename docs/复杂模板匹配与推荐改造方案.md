# 复杂模板匹配与推荐改造方案（给 codex）

本文只解决一件事：L1 自动模板化落地后，**简单换参数已经能命中，复杂模板换参数一律推荐不到**。下面是连库实测的根因、改造任务、可直接落盘的提示词补丁和伪代码。所有行号是 2026-09-21 快照，以函数名为准。

配套测试题见 `docs/同模板换参数测试问答集.md`，改造完用它回归。

---

## 〇、一句话结论

模板"挖得出来、换参数却匹配不上"，卡点不在挖掘，在运行期三处：

1. 运行期 plan **抽不到"上行/下行、有没有图片、收藏/状态"这类枚举布尔过滤条件**（语义提示词只把"上下行"教成了分组维度，没教成过滤条件；has_image 根本没有过滤通道）。
2. 模板匹配要求**所有必填槽一次性填满，缺一个槽就整条放弃**，没有"差一两个槽、在确认卡里补填"的弹性。
3. 模板的自画像（match 里的 shape/group_by/metrics/conditions）是拿**第一条问题原文反推**的，不是从 SQL 本身抽的，导致 SQL 里明明 `SELECT COUNT(*), SUM(area)`，自画像却只记了 count。

这三点修好，复杂模板（多过滤 + 分组 + TopN + 枚举）才能像简单模板一样换参数复用。

---

## 一、实测证据（2026-09-21，连库 + 探针）

简单换参数 8/8 命中；构造的复杂模板（路线+方向+月份+面积阈值+按类型分组+TopN，结构指纹 `b645aac7fcfbdda5`）挖掘成功、跨两条变体后方向槽也能从 fixed 升级成 sample 槽，但**换参数的 5 个问题全部 NO AUTO MATCH**。

| 现象 | 实测事实 | 定位 |
|---|---|---|
| 方向条件丢失 | 所有含"上行/下行"的问题，`slots.up_or_down=None`、semantic_conditions 里没有方向条件 | `prompts/query_semantic.md` 条件字段清单（约 113-122 行）没有 up_or_down；方向只出现在 group_by=direction（约 50、170 行） |
| 方向列还指错了表 | `_CONDITION_FIELDS["up_or_down"] = ('ai_asset_main.up_or_down', False)`，但病害表 ai_problem 自己就有 up_or_down，病害查询应是 `p.up_or_down` | nl2sql `_field_rows()` 自动登记同名列时取到了资产表 |
| 有无图片无通道 | `_CONDITION_FIELDS["has_image"] = None`；op 白名单 `_CONDITION_OPS` 没有空值判断；"没采集图片"抽不出来 | nl2sql `_pick_conditions`（约 750 行）白名单 + query_semantic 条件清单都没有 problem_url 空值 |
| 必填槽缺一即弃 | `templatizer.match()`（约 1156-1164 行）每个 param 都要 `_plan_param_value` 取到值，任一取不到整条 skip | match 全必填 |
| 自画像漏指标 | 复杂 SQL 同时 SELECT COUNT 和 SUM(area)，模板 match.metrics 只有 ['count'] | `_declared_plan()`（约 938 行）对第一条问题原文 build_query_plan 反推，措辞只触发 count |
| JSON 列挖不动 | WHERE 含 `CAST(JSON_UNQUOTE(JSON_EXTRACT(pic_position,'$.confidence'))…)` 时，规则挖槽判定挖不动，**整条**交给 `_llm_skeleton` | `mine_sql`（约 600 行）/`_mine_predicate`（约 394 行），一个谓词失败拖垮整条 |
| 时间只剩月 | "7月30日"到模板侧只剩 month=2026-07，日粒度被月吞掉 | `_plan_param_value`/coerce 的 time 只认 month/date 键，没接 plan 的 time_start/time_end |

| 候选无区分度 | 所有 auto 候选固定 score=4.8 | match 约 1189 行 |
| generic 不可执行 | capabilities 收集了 generic 候选，但 `execute()`（约 614 行）没有 generic 分支 | capabilities.py |
| candidate 不能转正 | 只有 enable/delete/rebuild，set_enabled 不改 status；前端无转正按钮 | generic_api.py、AdminPanel.vue |

## 二、根因清单（按数据流排序）

- R1 语义解析提示词的"条件字段"覆盖面不足：方向只教成分组、没教成过滤；没有"有无图片"；枚举/布尔"作为过滤"和"作为分组"的区别没讲清。
- R2 字段登记表 `_field_rows()` 对跨表同名列归属错误（up_or_down/lng/lat/luge_name/mission_flag/preview_url 被登记到 ai_asset_main/ai_distance_capture，病害主查询应优先 ai_problem.p）。
- R3 空值/布尔类过滤没有 op（is null / = '' / 有值），has_image 虚拟字段未登记。
- R4 模板 match 自画像来自第一条问题反推，而非 SQL AST，metrics/group_by/conditions 会随措辞漏判。
- R5 match 全必填、缺槽即弃，确认卡的 card_slots 补填能力没用上。
- R6 规则挖槽"一个谓词挖不动，整条交 LLM"，且不识别 CAST(JSON_EXTRACT()) 包裹的裸列。
- R7 时间槽只到月，丢日粒度。
- R8 comparison/multi_route 整题不进模板，复合题子步骤的模板复用没接上。
- R9 候选评分固定，无法在多条候选里排序推荐。
- R10 generic 候选不可执行；candidate 无人工转正；前端看不到参数化 SQL/match/拒绝原因。

## 三、改造任务

### P0-1　让运行期 plan 抽到方向、有无图片、收藏、状态等过滤条件（治 R1/R2/R3）

这是复杂模板命中的**头号前提**——plan 是 preset/auto/Wren 所有路径的共同输入，plan 缺条件，后面每层都会错。

1. 替换 `prompts/query_semantic.md` 的 conditions 字段说明段，补 up_or_down、problem_url(has_image)，并明确"作为过滤条件"和"作为分组维度"的区别。**可直接落盘的全文见附录 A**。
2. 修 nl2sql `_field_rows()` 的跨表同名列归属：当 subject=disease（主表 ai_problem p）时，up_or_down/lng/lat/luge_name/mission_flag/collect 等 ai_problem 自带列必须登记成 `p.<列>`，不能取 ai_asset_main/ai_distance_capture 的同名列。建议字段登记按"主体表优先"，同名列以当前查询主表别名为准，而不是全局取第一张命中的表。
3. 给 `_CONDITION_OPS` 增加空值类操作：`is_null` / `not_null` / `empty` / `not_empty`；在 `_pick_conditions` 和模板 coerce/bind 里支持。新增虚拟字段 **has_image**：
   - has_image=否（没采集图片/没照片）→ `(p.problem_url IS NULL OR p.problem_url = '')`
   - has_image=是（有照片/有现场图）→ `p.problem_url IS NOT NULL AND p.problem_url <> ''`
   - 口径钉死用 problem_url（原始采集图）；preview_url 是画框缓存图，不要混用（如后续要区分再单列）。
4. 规则兜底：`parsers.parse_slots` 增加方向过滤抽取（"上行/下行/单向/双向"→ up_or_down code），LLM 超时也不丢。code：up_or_down 0=全部 1=上行 2=下行。
5. 验收（问答集 I 组）：I1"西乡段上行方向有多少处"conditions 必须含 up_or_down=1；I7"没采集图片的有多少"必须含 has_image=否；I2"上行下行分别多少"仍走 group_by=direction，二者不许混。

### P0-2　模板自画像改为从 SQL AST 抽取（治 R4）

废弃用第一条问题 build_query_plan 反推 match 的做法（`_declared_plan`），改成在 `mine_sql` 里已经 parse 出的 SQL AST 上直接归纳 match。复用现有的 `parse_one`、`_structure_signature`、`_classify_plain`、`_AGG_FUNCS`。抽取约定和伪代码见**附录 B**。要点：

- shape：无 GROUP BY 且 SELECT 是 COUNT→count；SUM/AVG 单值→sum/avg；有 GROUP BY→distribution；SELECT 明细列→list；有 ORDER BY 聚合 + LIMIT 1..50→top。
- metrics：遍历 SELECT 的聚合表达式，**有几个算几个**（COUNT→count、SUM(area)→total_area、AVG(area)→avg_area、AVG(confidence)→confidence_avg、COUNT(DISTINCT)→distinct），不许只留一个。F5 必须得到 metrics=[count, total_area]。
- group_by：GROUP BY 列经列角色映射（damage_type/route/up_or_down→direction/collection_time→month/day/pile_distance 分段）。
- conditions：WHERE 顶层 AND 每个谓词的列 → 对应声明键（route/damage_type/time_range/area/confidence/up_or_down/collect/problem_status/has_image…）；值在槽里变化的进 params，单样本固定的进 fixed。
- subjects：由 FROM/JOIN 表集合推（ai_problem→disease，ai_maintain_patrol→patrol，basic_facilities_routes→route）。
- top_n：ORDER BY + LIMIT n（1..50）记成 top_n 槽；纯 LIMIT 500 当结构保留不挖。
- 自画像与回环验证结果一起落库；旧的 5 条模板在下次 mine_all 时用新自画像重算 match。

### P0-3　缺槽弹性匹配 + 确认卡补填，最终由用户拍板（治 R5）

把 match 从"全必填硬匹配"改成"软匹配 + 槽位完备度 + 人工补填"。判定伪代码见**附录 C**。规则：

- **硬冲突（直接淘汰）**：结构指纹/shape/subject 不符；fixed 值与 plan 冲突；plan 给了模板表达不了的条件（语义超范围）；多对象/对比（见 P2-7）。
- **软缺槽（保留为候选）**：结构相符、必填的路线/时间能确定，只是方向、阈值、TopN、有无图这类枚举/数值槽没抽到 → 不淘汰，标记 `missing_slots`，照常进候选。
- 硬必填只保留会导致"查错对象/错口径"的槽：路线（route）、时间范围（问题明确给了时间时）。其余槽缺失都允许进确认卡补填。
- 确认卡对每个 missing_slot 用 params.options 给下拉（方向：全部/上行/下行；有无图：有/无；状态/来源：code 中文名；TopN：默认空或 5；数值阈值：输入框）。用户补齐后才 bind 执行；用户也可以选"不用模板，让 AI 重写"。
- 任何 auto 模板都**只推荐、不自动执行**，确认卡展示"推荐模板：标题 + 已识别槽 + 待补填槽"，多条候选按 P1-6 排序列出 top3 让用户选。

### P1-4　挖槽谓词级降级 + 识别 JSON/函数包裹列（治 R6）

- `mine_sql/_mine_predicate`：单个谓词挖不动时，只把**该谓词**标记为 `llm_predicate` 或转 fixed，其余裸列谓词正常挖槽；不要因为一个 CAST/JSON 谓词就把整条 SQL 丢给 `_llm_skeleton`。
- 识别函数包裹的裸列：对 `CAST(JSON_UNQUOTE(JSON_EXTRACT(p.pic_position,'$.confidence')) AS DECIMAL…)` 这类，用 `_CONDITION_FIELDS` 里已登记的 confidence 物理表达式做**归一匹配**（规范化空白/大小写后比对表达式，或维护"JSON path→逻辑字段"映射 pic_position.$.confidence→confidence），归到 confidence 槽，op/value 正常挖。
- 仍挖不动的整类（OR/XOR、LIKE、子查询）维持拒绝，但要在挖掘审计里写明拒绝原因（见第四节）。

### P1-5　时间槽保留日粒度（治 R7）

- coerce/`_plan_param_value` 的 time 优先读 plan 的 `slots.time_start/time_end`（build_query_plan 约 1784-1813 已解析精确边界），没有再退 month。
- 槽位类型区分 month 与 date：模板 params 里 time 槽带 `granularity: month|date`；"7月30日"绑定成 `2026-07-30 00:00:00 ~ 2026-07-31 00:00:00`，不能展开成整月。问答集 E2、L 组据此回归。

### P1-6　候选按契合度排序（治 R9）

替换固定 4.8，候选 score 建议（权重可调，落配置）：

- 结构指纹完全一致 0.4；shape/subject 相符 0.2
- 槽位完备度 = 已从 plan 取到值的必填槽 / 必填槽总数，占 0.25
- fixed 无冲突 0.05；variants/samples 数 0.05；历史 usage 与最近成功 0.05
- 缺槽候选完备度不满分但仍可排序，确认卡里标注"还差 N 个条件待补"。

### P2-7　对比/多路线/复合题走子问题级模板（治 R8）

- 整题 plan.comparison/multi_route 仍不做整题模板（SQL 结构是多对象 UNION/CASE，模板化收益低、易错）。
- 但 capabilities.`collect_steps` 已经把复合题拆成多个 data/aggregate 子任务：**每个子任务各自 build_query_plan 后照常跑 templatizer.match**，能命中的子步骤走模板、命中不了的子步骤走 Wren，最后由后置计算拼对比/差值/占比。
- 验收 H 组：H1 拆成西乡、恒明珠两个 count 子问题，各命中族 A 模板；H2 两个月各命中再做差；H4 两个 count 再相除。

### P2-8　generic 候选要么能执行、要么别产生（治 R10 之一）

capabilities.`execute()` 没有 generic 分支，却会收集 generic 候选。二选一（建议前者简单）：execute 增加 generic 分支 → 转 Wren 重新生成；或收集阶段 generic 仅在 deterministic_only=false 时作为"送 Wren"的占位，不进模板候选列表。避免前端出现一个点了不能跑的能力。

### P2-9　candidate 人工转正（治 R10 之二）

- 后端新增 `POST /templates/auto/{id}/promote`：把 status 从 candidate 置 mature（记录 promoted_by/时间）；set_enabled 只负责启停，不兼转正。
- 枚举类槽（up_or_down/collect/problem_status/has_image）维持"跨样本取过≥2 值才自动 sample 成熟"，但管理员可在维护页对单条 candidate 手动转正，转正时该槽按 domain 证据（取值域自带 code 字典）视为可换值，界面标注来源。
- 前端 AdminPanel 自动模板区给 candidate 加"转正"按钮。

### P2-10　实体槽列与 form 一致性（治第一节附带问题）

- bind 前校验实体槽：form=value 必须填 id、SQL 列是 id 列（routes_id）；form=label 必须填名称、SQL 列是名称列（short_name/full_name），二者不能交叉。
- 巡检次数模板 short_name 与中文全名不一致的，统一改成 `r.id = '{route_id}'`（form=value），与其他模板一致；回环 `_same_rows` 对 0 行/行数不符必须判失败，不允许 mature。

## 四、前端"问答集→模板"可视化改造

现状 AdminPanel.vue 已有"自动沉淀模板(L1)"表格（标题/槽位 chip/状态/命中次数/启停/删除/重新挖掘），但看不到 SQL、match 自画像、变体、样本，也无法转正、看不到"为什么某条成功问答没变成模板"。

建议在现有表格行下加**展开抽屉**，分四块：

1. 模板概览：标题、status（mature 可推荐 / candidate 待观察）、trusted、enabled、usage、fingerprint、created_at。
2. 参数化 SQL：代码块展示 sql，把 `{槽名}` 高亮成 chip，悬停显示 label/列/类型/confirmed_by（domain 取值域 / sample 跨样本）。
3. 匹配自画像 match：shapes / subjects / group_by / metrics / conditions / fixed 以标签展示（让使用者一眼看懂"什么样的问题会命中它"）。
4. 变体与样本：variants 问法列表、samples（原始问题 + 当时槽值）、missing_slots 说明。
5. 操作：mature 可启停/删除；candidate 额外有"转正"；每条有"试跑"（用 samples 的槽值直接执行，看板刷新式，0 LLM）。

新增**"挖掘审计"区**（后端落 mine 拒绝记录，接口 `GET /templates/auto/rejects`）：列出最近成功问答中没转成模板的 question + 原因分类（含 OR/LIKE/子查询/非只读/无业务过滤/谓词挖不动/回环不一致），让"为什么没沉淀"可见、可人工补救。

对话页**确认卡改造**（复杂模板）：

- 标题"为你找到可复用的查询模板"，列 1-3 个候选（按 P1-6 排序），每个展示模板标题、参数化 SQL 摘要。
- 选中后分区显示"已识别条件"（绿）和"待补条件"（黄，下拉/输入框），用户补完点"用模板查询"才执行；底部始终保留"不用模板，让 AI 重新生成"。
- 复合题展示分步卡：每个子步骤标"走模板 / AI 生成"，让用户看清楚哪几步省了生成。

## 五、后端接口与数据变更清单

- `generic_api.py` registry 返回补齐：sql（参数化）、match、variants、samples、confirmed_by、status、missing_slots、granularity。
- 新增 `POST /templates/auto/{id}/promote`；`GET /templates/auto/rejects`（挖掘审计）。
- templatizer match 返回结构从"只返回命中模板"扩成"候选 + 已填槽 + missing_slots + score"，供确认卡渲染；执行仍由用户确认后触发 bind。
- mine_all 落库 mine_rejects（question/kind/reason/时间），重挖时滚动保留最近 N 条。
- 字段登记/has_image/空值 op/时间粒度的改动，同步到物理路径与 MDL 路径两套渲染。

## 六、验收标准（用同模板换参数测试问答集回归）

1. 第一部分简单族 A-E 必须 100% 命中正确模板、槽值正确，不允许退化。
2. F 组：F0 沉淀出含 路线/方向/月份/面积阈值/分组/TopN 的模板后，F1-F5 换参数能推荐到同一条；缺方向/阈值时进确认卡补填而不是放弃；F5 自画像 metrics 同时有 count、total_area。
3. G 组：confidence JSON 阈值能挖成槽并换值复用；G1 的"没采集图片"形成 has_image=否条件。
4. I 组：I1 上行过滤、I3 收藏、I5 工单状态、I7 无图 都能正确进 conditions；I2 方向分组不被误当过滤。
5. H 组：复合题拆出的单对象子步骤命中模板，对比/差值由后置计算完成。
6. 长对话 J/K/L/M：被替换的槽不叠加、上一轮无用的答案数字不进过滤、patrol 编号不被当成时间、换路线不丢其他条件。
7. 所有 auto 模板执行都经过用户确认卡；candidate 能在维护页转正；挖掘审计能看到未沉淀原因。
8. 空结果诚实返回空算正确，不许为了凑数改口径。

## A.1 替换段（替换原 110-154 行）

```
- **conditions：用户给的"过滤条件"（先筛掉一部分数据再统计/列明细），抽成结构，不要靠关键词表。**
  只有用户**明确给了筛选**时才填；"有多少处"这种不带筛选的不要编条件。每项格式：
  {"field": "<字段>", "op": "<比较符>", "value": <数值或字符串>}

  【最容易错的一点：同一个维度，"当筛选"和"当分组"是两回事，别混】
  - 用户**只要其中一部分**（"上行的有多少""只看下行""收藏了的""没照片的""已转工单的"）
    → 这是过滤条件，填进 conditions。
  - 用户要**把几部分都列出来对比**（"上行和下行分别多少""有图没图各多少""各状态占比"）
    → 这是分组，填 group_by（direction / image_presence / problem_status…），conditions 里不要再加该条件。
  - 同一句话里先筛选再分组也允许（"上行方向里，各病害类型多少"→ conditions 有 up_or_down=1，group_by=damage_type）。

  field 取值（物理列逻辑名，写 SQL 时由后端映射到真实列）：
  · 路线/对象：route_name（路线名）、problem_type_name（病害类型中文名）、
    problem_number（病害编号）、patrol_number（巡查编号 XCBH 开头）、patrol_id（巡查任务id）、
    task_number（巡检任务号 XJJL 开头）、device_code（设备号）、vehicle_id（车辆id）、
    inspection_user_id（巡检用户id）
  · 数值/时间：area（面积）/ confidence（AI置信度，取自 pic_position JSON 的 $.confidence）/
    disease_length（长度）/ area_width（宽度）/ area_height（高度）/ pile_distance（桩号米数）/
    collection_time（采集时间）
  · 方向：**up_or_down（上下行，code：0=全部 1=上行 2=下行）**
    "上行方向/下行方向/只看上行/单向" 是过滤；"上行下行各多少/两个方向分别" 是 group_by=direction。
  · 有无图片：**has_image（是否采集了现场图片，布尔）**
    has_image=否：没采集图片/没照片/无现场图/图片缺失；
    has_image=是：有照片/有现场图/带图的。
    （后端据此生成 problem_url 是否为空；你只填 has_image，不要自己写 problem_url。）
  · 业务状态字段（库里一直有，用户问什么就填什么，漏了就等于把筛选吞掉）：
    collect（收藏）/ track_problem（关注病害）/ problem_status（工单状态）/
    problem_source（病害来源）/ mission_flag（是否绑定巡查任务）/
    luge_name（路格）/ history_damage_interval（历史损坏程度）/ map_position（病害位置）/
    lng（经度）/ lat（纬度）
  · 清单之外还有更多业务列（memo、problem_name、problem_describe、create_by…），
    用户问的字段只要在表里就按英文列名原样填 field，不许因为没列出来就丢。

  【中文↔code，库里存 code，别把中文写进 WHERE】
  up_or_down：0=全部 1=上行 2=下行；
  collect：0=未收藏 1=收藏；track_problem：0=否 1=是；
  problem_status：0=待转工单 10=已转工单 15=忽略病害；
  problem_source：0=手动新增 5=车辆巡检 10=人工巡检 15=新增历史工单 20=路长转养护 25=路政转养护；
  mission_flag：0=未绑定 1=已绑定；
  has_image：1=有图片 0=无图片。

  op 取值：= / != / > / >= / < / <= / between（value 给 [下限,上限]）/
  in（value 给数组）/ is_null（无值）/ not_null（有值）/ empty（空字符串或 NULL）/ not_empty。
  has_image 用 "=" 配 1/0；判断某字段"有没有填"用 is_null/not_null/empty/not_empty。
  value：数值写数字；时间写 'YYYY-MM-DD HH:MM:SS'；名称写字符串；code 字段写 code 字符串。

  【编号看前缀判家族，别按中文名猜】
  XJJL 开头=巡检任务号 task_number；XCBH 开头=巡查编号 patrol_number；
  BPLHZD/KZXB/ZXLF/LJLJ 等其余前缀=病害编号 problem_number。
  编号里的数字是标识，不是时间，不许据此加时间范围。

  【同一比较，换说法也要抽成同一结构】
  "正好/不多不少/恰好 7.52" → area = 7.52；
  "起码/不少于/开外 2 米" → disease_length >= 2；
  "别超过/顶多/不高于 0.8" → confidence <= 0.8；
  "0.5 到 0.8 之间" → confidence between [0.5,0.8]；
  "7月30号采集的" → collection_time between ['2026-07-30 00:00:00','2026-07-31 00:00:00']。
  时间端点方向："7月15日起/开始/以后" → collection_time >= '2026-07-15 00:00:00'；
  "截至/到7月15日为止" → collection_time <= '2026-07-15 23:59:59'。

  一个字段多个条件就给多项（"面积大于5且置信度低于0.7"→ area>5、confidence<0.7 两项）；
  一句话同时有筛选+分组+取前N，三类信息都要给全，不许只给一种。
```

# 附录 B　SQL AST → match 自画像抽取约定（伪代码）

在 mine_sql 已得到 sqlglot 解析树后，用下列规则归纳 match，替代 `_declared_plan` 对问题原文的反推：

```python
def portrait_from_ast(tree, template):
    agg = select_aggregates(tree)          # [(func, 列)]，如 [('COUNT','*'), ('SUM','area')]
    groups = group_by_columns(tree)        # 裸列集合
    wheres = top_level_and_predicates(tree)  # 只收顶层 AND 的谓词
    joins = joined_tables(tree)

    # shape
    if not groups and not agg:        shape = 'list'
    elif groups:                      shape = 'distribution'
    elif len(agg) == 1:
        shape = {'COUNT':'count','SUM':'sum','AVG':'avg'}.get(agg[0].func, 'count')
    if has_order_by_agg_with_small_limit(tree):  # ORDER BY 聚合 + LIMIT 1..50
        shape = 'top'

    # metrics：SELECT 里的聚合一个不漏
    metrics = [AGG_TO_METRIC[(f, col)] for (f, col) in agg]
    # COUNT(*)->count, SUM(area)->total_area, AVG(area)->avg_area,
    # AVG(confidence)->confidence_avg, COUNT(DISTINCT id)->distinct_pile/...

    # group_by：列角色映射
    group_by = [COLUMN_ROLE[c] for c in groups]
    # damage_type->damage_type, routes_id->route, up_or_down->direction,
    # DATE(collection_time)->month/day, FLOOR(pile_distance/1000)->pile_bucket ...

    # conditions / fixed / params：逐谓词归类
    conditions, fixed = [], {}
    for pred in wheres:
        key = COLUMN_TO_DECLARE.get(normalize(pred.left))   # routes_id->route,
              # b.problem_type->damage_type, collection_time->time_range,
              # p.area->area, <json confidence 表达式>->confidence,
              # p.up_or_down->up_or_down, p.collect->collect,
              # (problem_url IS NULL OR ='')->has_image ...
        if key is None: continue
        slot = template.param_for(pred)        # 已挖成可变槽
        if slot: conditions.append(key)
        else: fixed[key] = pred.value          # 单样本固定值
    if top_n := limit_slot(tree): template.params['top_n'] = top_n

    subjects = sorted({TABLE_SUBJECT[t] for t in [main_table(tree), *joins]})
    template.match = dict(shapes=[shape], subjects=subjects, group_by=group_by,
                          metrics=metrics, conditions=conditions, fixed=fixed)
```

注意：normalize 要把 `CAST(JSON_UNQUOTE(JSON_EXTRACT(p.pic_position,'$.confidence'))…)`
归一到 confidence（与 `_CONDITION_FIELDS['confidence']` 表达式做规范化比对）；
problem_url 的 `IS NULL OR =''` 组合归一到单个 has_image 谓词。

# 附录 C　弹性匹配判定（硬冲突 vs 软缺槽）伪代码

```python
def soft_match(plan, tpl):
    # 1) 硬冲突：直接淘汰
    if plan.comparison or plan.multi_route: return None          # 交给子步骤拆分
    if plan.shape not in tpl.match.shapes: return None
    if plan.subject not in tpl.match.subjects: return None
    if structure_fingerprint(plan) != tpl.fingerprint \
       and not shape_compatible(plan, tpl): return None
    for k, v in tpl.match.fixed.items():                          # 固定值不能撞
        if plan_value(plan, k) not in (None, v): return None
    if plan_has_condition_outside(tpl.expressible_conditions): return None

    filled, missing = {}, []
    # 2) 逐槽取值
    for name, p in tpl.params.items():
        val = plan_param_value(plan, name)
        if val is not None:
            filled[name] = coerce(p, val)
        elif p.get('required') and name in HARD_REQUIRED:        # 仅 route / 明确给过的时间
            return None                                          # 查错对象，不候选
        else:
            missing.append(name)                                  # 软缺槽，留待补填

    # 3) 完备度打分（与 P1-6 权重合并）
    completeness = len(filled) / max(1, len(tpl.params))
    return Candidate(tpl=tpl, filled=filled, missing_slots=missing,
                     score=base_score(plan, tpl) + 0.25*completeness,
                     needs_user_fill=bool(missing))

HARD_REQUIRED = {'route_id'}   # 只有会查错对象的槽硬必填；时间仅在用户明确给过时才必填
```

确认卡拿到 Candidate 后：filled 展示为"已识别条件"，missing_slots 用 params.options
渲染下拉/输入（方向、有无图、状态、来源、TopN、数值阈值），用户补齐 → bind(tpl, 合并参数)
→ 执行；用户选"让 AI 重写"则走 Wren。候选一律不自动执行。
