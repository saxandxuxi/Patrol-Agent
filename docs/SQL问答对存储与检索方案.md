# SQL 问答对存储与检索方案

## 一、不同阶段检索什么字段

不是所有阶段都把整个问答对拿出来。每个阶段分工不同，按需检索对应的字段。

### 阶段1：任务拆分（判断要不要拆、怎么拆）

**需要什么：** 类似的复合问题是怎么拆的，拆成几个子问题，每个子问题是什么。

**检索哪些字段：**
- `question`（用户问题原文）
- `subtasks`（拆出来的子问题列表）
- `query_type`（整体类型：single/multi/post_calc）

**不用拿什么：** SQL 语句、slots、tables 这些，拆分阶段不需要看 SQL。

---

### 阶段2：Query Plan 构建（解析槽位）

**需要什么：** 类似的问题里，路线/病害类型/时间/桩号是怎么解析的。

**检索哪些字段：**
- `question`（用户问题原文）
- `slots`（解析出来的槽位：路线、病害类型、时间、桩号）

**不用拿什么：** SQL 语句、tables、metrics 这些，槽位解析阶段不需要。

---

### 阶段3：SQL 生成（最核心的阶段）

**需要什么：** 类似的问题生成了什么样的 SQL，用了哪些表、哪些字段、什么 JOIN 方式。

**检索哪些字段：**
- `question`（用户问题原文）
- `sql`（最终 SQL 语句）
- `tables`（用到了哪些表）
- `query_type`（查询类型：单计数/分组/聚合/明细）
- `metrics`（查了哪些指标）
- `dimensions`（按什么维度分组）
- `slots`（槽位映射参考）

**不用拿什么：** 子问题拆分信息，SQL 生成阶段不需要。

---

### 阶段4：结果解读（把结果翻译成自然语言）

**需要什么：** 类似的查询结果，是怎么解读成自然语言的。

**检索哪些字段：**
- `question`（用户问题原文）
- `result_interpretation`（结果解读示例：查出来 COUNT+SUM 应该怎么说）

**不用拿什么：** SQL 语句、tables、metrics 这些，解读阶段不需要看 SQL。

---

## 各阶段检索字段速查表

| 阶段 | 拿哪些字段 | 不拿哪些字段 |
|------|-----------|-------------|
| 任务拆分 | question、subtasks、query_type | sql、slots、tables |
| Query Plan | question、slots | sql、subtasks、tables |
| SQL 生成 | question、sql、tables、query_type、metrics、dimensions | subtasks |
| 结果解读 | question、result_interpretation | sql、slots、tables |

**核心原则：每个阶段只拿它需要的字段，不要全塞给它。** 不然上下文太长，还容易干扰。

## 二、复合问题/多子问题怎么存

### 问题：一条复合问题，拆成多个子问题，怎么存？

**三种存法，各有优缺点：**

---

### 方案1：存成一条问答对，subtasks 字段存子问题列表

**结构：**
```json
{
  "question": "西乡段和恒明珠的泛油各有多少？哪个多？多多少？",
  "query_type": "post_calc",
  "subtasks": [
    {
      "id": 1,
      "type": "data",
      "question": "西乡段的泛油数量是多少？",
      "sql": "SELECT COUNT(*) FROM ... WHERE r.id = 'xxx' AND dd.problem_type = '泛油'",
      "slots": { "route": "西乡段", "damage_type": "泛油" }
    },
    {
      "id": 2,
      "type": "data",
      "question": "恒明珠的泛油数量是多少？",
      "sql": "SELECT COUNT(*) FROM ... WHERE r.id = 'yyy' AND dd.problem_type = '泛油'",
      "slots": { "route": "恒明珠", "damage_type": "泛油" }
    },
    {
      "id": 3,
      "type": "post_calc",
      "question": "哪个更多？多多少？",
      "depends_on": [1, 2],
      "calc_logic": "比较子问题1和2的结果，计算差值"
    }
  ]
}
```

**优点：**
- 完整保留了"一个复合问题怎么拆"的完整过程
- 任务拆分阶段检索到这个例子，就能学会这种问题该怎么拆

**缺点：**
- SQL 生成阶段检索到这个例子，里面有多个 SQL，不知道该参考哪个

---

### 方案2：拆成多条问答对，每个子问题存一条

**结构：**
```json
// 子问题1
{
  "question": "西乡段的泛油数量是多少？",
  "sql": "SELECT COUNT(*) FROM ...",
  "parent_question": "西乡段和恒明珠的泛油各有多少？哪个多？多多少？",
  "subtask_id": 1
}

// 子问题2
{
  "question": "恒明珠的泛油数量是多少？",
  "sql": "SELECT COUNT(*) FROM ...",
  "parent_question": "西乡段和恒明珠的泛油各有多少？哪个多？多多少？",
  "subtask_id": 2
}

// post_calc 不存 SQL，存计算逻辑
{
  "question": "哪个更多？多多少？",
  "post_calc_logic": "比较两个结果，计算差值",
  "parent_question": "西乡段和恒明珠的泛油各有多少？哪个多？多多少？",
  "depends_on": [1, 2]
}
```

**优点：**
- SQL 生成阶段检索的时候，每个子问题都是独立的，好匹配
- 每个子问题的 SQL 都是独立的，好参考

**缺点：**
- 任务拆分阶段检索的时候，看不到"完整的复合问题长什么样"
- 不知道这些子问题是怎么从一个完整问题拆出来的

---

### 方案3：双层存储（推荐）

**一条复合问题存两层：**
1. **外层：复合问题总览** —— 存原始问题 + 拆分结构 + 每个子问题的摘要
2. **内层：每个子问题单独存** —— 每个子问题的完整 SQL 和字段

**外层（复合问题总览）：**
```json
{
  "question": "西乡段和恒明珠的泛油各有多少？哪个多？多多少？",
  "query_type": "post_calc",
  "subtask_count": 3,
  "subtasks_summary": [
    { "id": 1, "type": "data", "question": "西乡段泛油数量" },
    { "id": 2, "type": "data", "question": "恒明珠泛油数量" },
    { "id": 3, "type": "post_calc", "question": "哪个多？多多少？" }
  ]
}
```

**内层（每个子问题独立存）：**
```json
{
  "question": "西乡段的泛油数量是多少？",
  "sql": "SELECT COUNT(*) FROM ...",
  "tables": ["disease", "route", "damage_dict"],
  "query_type": "single_count",
  "parent_question": "西乡段和恒明珠的泛油各有多少？哪个多？多多少？"
}
```

**为什么推荐这个？**
- **任务拆分阶段**：检索外层的复合问题总览，学会"这种问题应该拆成几个子问题、每个子问题是什么"
- **SQL 生成阶段**：检索内层的单个子问题，学会"每个子问题的 SQL 怎么写"
- 两层各司其职，互不干扰

## 三、长对话/多轮对话怎么存

### 核心思路：存之前先补全上下文，然后就和普通单轮一样存

长对话的问题，其实不需要特殊的存储结构。只要在存入 RAGFlow 之前，先把上下文补全——把指代词替换成完整实体，变成一个完整的单轮问题。然后就和普通单轮问答对完全一样存、一样检索。

**例子：**
```
第1轮：西乡段泛油有多少处？  → 完整问题，直接存

第2轮：那恒明珠呢？          → 补全成："恒明珠的泛油有多少处？" → 再存

第3轮：它俩哪个多？多多少？   → 补全成："西乡段和恒明珠的泛油哪个多？多多少？" → 再存
```

**这样做的好处：**
1. **存储简单**：不需要加任何特殊字段，和普通单轮问答对结构完全一样
2. **检索简单**：不需要特殊的检索逻辑，和普通单轮问答对完全一样
3. **不需要额外代码**：只是在存之前，先做一步上下文补全

---

### 补全规则

存长对话问答对之前，必须先做这一步：
1. 把用户原话里的指代词（"它"、"那"、"它俩"、"该路段"）替换成完整实体
2. 把上一轮提到的过滤条件（路线、病害类型、时间、桩号）继承过来
3. 最终得到一个**不依赖上下文也能独立理解**的完整问题

**⚠️ 重要：不要重复补全**
- 系统里已经有 `memory.contextualize()` 函数做上下文补全
- 存入 RAGFlow 之前，已经用这个函数补全过了
- 检索出来的示例，也都是补全后的完整问题
- **所以 SQL 生成阶段的提示词里，不要再让模型做上下文补全了**
- 补全只做一次：存入 RAGFlow 之前做，检索出来直接用

**补全示例：**
| 用户原话 | 补全后的完整问题 |
|---------|----------------|
| 那恒明珠呢？ | 恒明珠的泛油数量是多少处？ |
| 那它的平均面积呢？ | 西乡段泛油的平均面积是多少？ |
| 它俩哪个多？多多少？ | 西乡段和恒明珠的泛油哪个多？多多少？ |
| 那 K0+800 到 K0+900 呢？ | 西乡段泛油在 K0+800 到 K0+900 有多少处？ |

---

### 检索的时候怎么用

长对话的检索，和普通单轮完全一样：

**用户现在问了一句追问："那它的平均面积呢？"**

1. **第一步：上下文补全**（在系统内部完成）
   - 结合上一轮对话，把"那它的平均面积呢？"补全成"西乡段泛油的平均面积是多少？"
   
2. **第二步：检索问答对**
   - 拿补全后的完整问题去搜 RAGFlow
   - 和普通单轮问题的检索流程完全一样
   - 找到类似的单轮问题示例

3. **第三步：生成 SQL**
   - 照着检索到的示例生成 SQL

**整个过程不需要任何特殊处理**——长对话在存入的时候就已经补全了，检索的时候拿补全后的问题去搜，就和普通单轮没区别。

---

## 四、检索流程总结

### 任务拆分阶段
1. 拿用户的复合问题
2. 检索外层的复合问题总览（按问题相似度）
3. 看类似的复合问题拆成了几个子问题、每个子问题是什么
4. 照着拆

### Query Plan 阶段
1. 拿单个子问题
2. 检索 slots 字段（按问题相似度）
3. 看类似的问题槽位是怎么解析的

### SQL 生成阶段
1. 拿单个子问题
2. 先按 `query_type` 粗筛（比如单计数就筛 single_count 类型的）
3. 再按 `tables` / `metrics` / `dimensions` 细筛
4. 最后按问题相似度排序，拿最相似的 2-3 条 SQL 当示例

### 结果解读阶段
1. 拿用户问题 + 查询结果
2. 检索 result_interpretation 字段
3. 看类似的问题结果是怎么解读成自然语言的

---

## 一句话总结

**1. 每个阶段按需检索，不要全塞：拆分阶段拿拆分结构，SQL 阶段拿 SQL，解读阶段拿解读示例。**

**2. 复合问题双层存：外层存拆分结构，内层存每个子问题的 SQL。** 拆分阶段看外层，SQL 阶段看内层。

**3. 长对话不用特殊存：存之前先补全上下文，把指代词替换成完整实体，变成完整单轮问题，然后就和普通单轮一样存、一样检索。**
