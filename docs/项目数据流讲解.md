# 项目数据流讲解：从一句问题到查询单、SQL 和回答

这份文档只讲一件事：你在输入框里敲进去一句人话，系统内部到底经过了几道手，每一道手交给下一道手的是一张什么形状的纸。

不讲设计理念，不讲为什么这么架构。只讲零件和零件之间的传递物。

先说一个前提。这个项目现在开着单轮编译器开关 `single_turn_compiler_enabled`。只要问题被判断成数据、分析或复合题，主流程就走新版查询链路，代码在 `backend/app/query/` 目录里。

旧版查询链路的代码还留在 `backend/app/services/nl2sql.py`，但它已经不是新版失败后的自动兜底。`build_query_plan()`、`select_tables()`、`generate_mdl_sql()`、`generate_sql()` 这些旧入口现在会直接抛出 `LegacyQueryChainDisabled`，提示“旧查询链路已停用”。旧提示词文件也已经从 `prompts/` 删除。所以看代码时仍会看到旧函数，但不要把它们误认为当前还在运行的第二套流程。第十四节会把这件事单独讲清楚。

### 先认识五个词

| 名词 | 小白解释 | 本项目里具体是什么 |
| --- | --- | --- |
| `QuerySpec` | 一张“我要查什么”的结构化点菜单 | 模型交出的查询单，写主体、视图、字段、指标、过滤条件、分组和排序 |
| MDL-SQL | 用项目内部表名写成的“中间 SQL” | 例如 `FROM disease JOIN route ON disease.routes_id = route.id`，这里的 `disease`、`route` 是逻辑模型，不一定等于数据库表名 |
| 物理 SQL | 数据库真正能执行的 SQL | 里面有 `ai_problem`、`basic_facilities_routes`、`WITH`、子查询和数据库方言 |
| MDL 语义层 | 一套“内部菜单和真实后厨”的对照说明 | Wren 项目里的模型、字段、`ref_sql`、计算列和关系定义 |
| ReAct | 多步任务的“执行员加异常调度员” | 按冻结计划依次调用工具；正常时不额外问模型，出现异常时才让控制器选择纠偏动作 |

用点菜打比方：

```text
用户说的话
  ↓ 模型理解业务意图
QuerySpec：我要按路线统计病害数量
  ↓ 纯代码翻译成内部菜单编号
MDL-SQL：从 disease 模型查，按 route 模型分组
  ↓ Wren 对照 MDL 换成真实表和真实字段
物理 SQL：从 ai_problem 查，关联 basic_facilities_routes
  ↓ MySQL 执行
结果
```

下面讲的都是这条新版主链路。旧链路只作为历史实现说明，不再承担自动兜底。

## 零、先认人：这条链路上有几个干活的

一条问题从进来到出答案，一共要过十二站。真正由模型做主的只有五个关口：判断问的是不是数据、确认问的是哪类对象、把话拆成查询单、复查查询单、挑结果的刺。其中判断对象那一关经常用不上，因为大多数问题的主体一眼就能看出。剩下七站全是代码。

这个比例很重要。你之所以觉得这个项目能稳住，不是因为模型聪明，是因为大部分环节根本没让模型碰。

### 实测：三条真问题各自叫了哪几个模型

我在本机把三条真问题跑了一遍，在提示词加载函数外面挂了一个记录器，每加载一次就记一笔。下面这张表是实际发生的调用，不是从代码推出来的。

| 问题 | 实际调用的提示词 | 耗时 | 结果 |
| --- | --- | --- | --- |
| 2026年11月2日，宝安大道西乡段有多少处泛油 | `intent`、`query_spec`、`query_spec_audit`、`verify_answer` | 10.5 秒 | 0 处，附采集时间覆盖说明 |
| 11月2日巡检了哪些线路，发现了多少病害 | `intent`、`subject_router`、`query_spec`、`query_spec_audit`、`verify_answer` | 10.7 秒 | 按路线分组，1 行 1433 处 |
| 为什么上个月的病害比前一个月多这么多 | `intent`、`subject_router`、`query_spec` 连叫三次、`query_spec_audit` | 36.5 秒 | 先弹口径确认，等用户点 |

三条问题里，旧链路的 `query_semantic`、`sql_mdl`、`sql_physical`、`table_selector` 一次都没被调用。现在这些入口已经被代码禁用，对应提示词文件也已删除，所以它们连“兜底”都不再承担。第十三节会按当前 `prompts/` 目录重新说明提示词分布。

| 站 | 干活的 | 提示词文件 | 用哪个模型 | 它拿到什么 | 它交出什么 |
| --- | --- | --- | --- | --- | --- |
| 一 | 代码 | 无 | 无 | 用户敲的那句话 | 一个字符串 |
| 二 | 模型 | `intent.md` | 语义模型 | 问题原文、规则初判结果、表检索证据 | 一个意图标签 |
| 三 | 代码 | 无 | 无 | 问题原文 | 一份字段候选清单 |
| 四 | 模型，只在候选多于一个时才上 | `subject_router.md` | 语义模型 | 问题原文、几个候选主体的摘要 | 主体编号和理由 |
| 五 | 模型，主力 | `query_spec.md` | 语义模型 | 问题原文、库的真实字段表、字段候选、能力清单 | 一张查询单，多个节点 |
| 六 | 模型，复查 | `query_spec_audit.md` | 校验模型 | 问题原文、第五站交出的查询单 | 挑毛病的结果和补丁 |
| 七 | 代码 | 无 | 无 | 查询单 | 通过或者报错 |
| 八 | 代码 | 无 | 无 | 查询单 | 有没有现成模板可用 |
| 九 | 代码加 Wren 编译器；确定编译器未覆盖时可受控补写一次 | 正常无，兜底为 `mdl_sql_generator.md` | SQL 模型，仅兜底 | 查询单、冻结合同、失败证据 | 一份能审计、能执行的 SQL |
| 十 | 数据库 | 无 | 无 | 真 SQL | 几行结果 |
| 十一 | 代码加模型 | `verify_answer.md` | 校验模型 | 结果、SQL、准备说出口的回答 | 结果能不能用 |
| 十二 | 代码 | 无 | 无 | 全部东西 | 一段人话 |

常见的五个模型关口里，第三站经常用不上，第六站和第十一站是复查性质，真正干活的主力只有第五站一个。到第九站时，确定性编译器是首选；只有它明确报“未覆盖”，才会额外启动一次受控 MDL-SQL 补写模型。

先把这五个常见关口的名字和分工记住，后面每一节都会回来对号。

这五个是单步数据题最常见的模型关口，`mdl_sql_generator.md` 是第九站的条件式兜底。多步复合题还会进入 ReAct 执行分支；ReAct 顺利推进时不会额外调用控制器模型，只有某一步观察异常时才会调用 `react_controller.md`。具体机制见第 8.13 节。

| 提示词文件 | 它负责什么 | 什么时候被叫 |
| --- | --- | --- |
| `intent.md` | 判断这句话是问数据、问分析、问知识、要图片，还是复合题 | 每一句都先过它 |
| `subject_router.md` | 几个候选主体拿不准时，决定选哪个 | 候选多于一个才叫 |
| `query_spec.md` | 把一句人话拆成结构化查询单 | 判成数据类或分析类时调用 |
| `query_spec_audit.md` | 拿另一个模型复查查询单 | 每一份查询单都复查 |
| `mdl_sql_generator.md` | 在冻结合同合法、但确定性编译器明确未覆盖时补写 MDL-SQL | 只有该兜底条件成立时调用 |
| `verify_answer.md` | 拿另一个模型挑结果的刺 | 反思开关打开时，出答案后调 |

`prompts/` 目录当前有 28 个 md 文件，其中 `README.md` 是说明文档，不算提示词，实际是 27 个提示词文件。它们不等于都在这条主链上干活。第十三节会按“主链、修复、ReAct、其他入口、离线沉淀、评测”重新分组。

## 一、第一站：句子的原始形态

用户敲的这句话，进到代码里就是一个字符串变量，没有任何结构。

```
2026年11月2日，宝安大道西乡段有多少处泛油？
```

这句话里其实藏了四样东西：一个日期、一个路线、一个病害类型、一个要数的东西。但此刻它们在代码眼里只是一串字，连"哪个字是日期"都还不知道。

后面所有工作，本质上就是把这一串字里的东西一样样拆出来，拆成机器能拿去查库的形状。

---

## 二、第二站：先判断这是不是问数据

### 为什么需要这一步

用户可能问四种完全不同的话：

第一种是问数据，比如刚才那句。
第二种是问分析，比如"为什么上个月病害涨了这么多"。
第三种是问知识，比如"病害等级怎么划分的"，这个要去翻资料库，不查库。
第四种是要图片，比如"把这条路上拍的照片调出来"。

这四种走的是四条完全不同的流程。要是判断错了，后面全白费。

### 谁在做

`intent.md`。调用点是 `intent.classify_intent()`。

用得比较巧，不是直接问模型。代码先自己按关键词猜一个结果，叫它初判。然后把初判结果、问题原文，再加上从表说明里检索出来的三条证据，一起交给模型。

提示词里给模型看的东西长这样：

```
问题：病害工单的处理状态
规则初判：data
候选表证据：
- 表 work_order，相关度 5，命中证据是工单状态、处理进度
- ...
```

为什么要给证据？因为用户说的话经常是自己的叫法，不是库里的叫法。"拍的片子"在库里叫"病害照片"，"标了多少个点"在库里叫"采集点位数量"。光看字面，模型很容易把数据问题判成知识问题。代码里留了一条实测记录，说"病害工单的处理状态"这句曾经被判成知识问答，回了一句"资料中没有相关内容"，用户拿到手就是一句废话。

给了表证据以后，模型知道"哦，这个词在工单表里有对应，那是在问数据"。

### 它交出什么

一个标签，五选一：`data`、`analysis`、`knowledge`、`image`、`composite`。另外还有 `metadata`，用来问库本身的结构，比如"这台库里有哪些表"。

输出很短，就一个 JSON。模型要是挂了或者返回不认识的词，代码用回初判那个结果。所以这一步永远不会卡住整个流程，最多是判得糙一点。

### 这道题的结果

被判成 `data`。因为这句话里"多少处"是典型的计数问法。

判成 `data`、`analysis` 或 `composite` 以后，代码在 `agent.py` 的 `_maybe_single_turn_compiler()` 里把它交给 `start_single_turn()`，走新版单轮查询链路。其他意图返回空，之后进入知识问答、图片、元数据等各自的专用分支；这里并不是落回旧版 SQL 链路。

## 三、第三站：代码先去库里摸一遍

### 为什么需要这一步

模型看不见你的库。它不知道有哪几张表，也不知道字段叫什么名。要让它拆查询单，得先给它一份"这个库里可能相关的东西"的清单。

这一步叫字段触达，代码在 `backend/app/services/field_grounding.py`，没有任何模型参与。

### 它怎么摸

把问题里的词，拿去跟库里每张表的说明、每个字段的注释做相似度比对，算出一个分数，排个序。

这道题摸出来的结果，前三名是这样：

| 表 | 分数 |
| --- | --- |
| `basic_facilities_sections` | 7.65 |
| `basic_facilities_routes` | 5.45 |
| `basic_facilities_sections_pile_detail` | 3.6 |

字段层面也有一条命中，是 `basic_facilities_sections.surface_type`，中文叫路面类型，分数打到了满分 1.0。

### 这一步会犯错，而且经常犯

上面那条满分命中就是错的。为什么错？因为"西乡段"这三个字撞上了路段的表说明，代码以为用户在问路面类型，其实用户是在拿"西乡段"当路线名用。

这种误命中很常见。所以这一步的产物只是一份"参考清单"，不是判决书。真正决定用哪张表、哪个字段，是第五站模型的事。

如果代码在这一步就直接定字段，这种误命中就会一路带到 SQL 里，查出来必然是空的。这也是为什么后面还要有一道复查。

### 它交出什么

一份候选集合，里面有表候选、字段候选，每条带分数和命中理由。代码里管这个结构叫 `FieldReachSet`。

这份东西有两个用途：一是给第五站模型当参考，二是第五站模型写错字段时，第七站代码拿它来核对"这个字段到底存不存在"。

## 四、第四站：确认问的是哪类对象

### 为什么需要这一步

同样一句"多少处"，问的对象可能是病害，也可能是巡检任务、工单、路线台账、路段台账。

对象搞错，字段就全错。问病害数量要用病害表，问路线数量要用路线表，两张表的"数量"完全不是一个意思。

### 什么时候才叫模型

这一步大多数时候不叫模型。

代码先看问题里有没有直接说出来。比如说"病害"，代码就知道主体是病害，直接定了，置信度 0.9，模型一次都不调。

只有候选多于一个，说不清的时候，才叫 `subject_router.md` 来投票。

调用点是 `backend/app/query/capability_registry/subject_resolver.py` 里的主体解析函数，用语义模型。

### 模型看到什么

每个候选主体的一份摘要：这个主体的底表是哪张，允许用哪些视图，前十二个字段的中文名是什么。

```json
{
  "disease": {
    "base_table": "ai_problem",
    "allowed_views": ["count", "list", "trend"],
    "field_examples": ["病害编号", "病害类型", "面积", "桩号"]
  },
  "route": {
    "base_table": "basic_facilities_routes",
    "allowed_views": ["count", "list"],
    "field_examples": ["路线名称", "路线编号", "起点桩号"]
  }
}
```

模型看完挑一个，同时给出置信度和理由。

### 它交出什么

主体编号、置信度、理由、备选。要是模型挑不出来，置信度给 0.5，主体留空，后面第五站模型自己再判。

### 这道题的结果

问题里有"泛油"，泛油是病害类型，所以主体是 `disease`。这一步没调模型。

### 路线、病害、设备、路段到底在哪一步识别

这里容易把三件不同的事混成一件：

1. 句子里有没有提到某类实体，比如有没有路线名、病害名、设备号、路段名。
2. 最终答案问的是哪一类主体，比如 `disease`、`patrol`、`route`、`section`。
3. 用户说的"宝安大道西乡段"到底是哪一条台账记录，数据库 ID 是多少。

新版链路的真实顺序不是"先把路线等值全部解析完，再给 QuerySpec 模型看"，而是：

```text
完整问题
  ↓
第三站：field_grounding.ground()
  找出可能相关的表和字段，同时产生主体候选
  ↓
第四站：resolve_subject()
  用字段候选、已登记实体精确命中、字段中文名等证据判断主体
  多个主体拿不准时，才调用 subject_router.md
  ↓
进入 QuerySpec 规划前：detect_evidence()
  按配置检查关键词和正则，生成 trusted=false 的候选便签
  ↓
第五站：query_spec.md
  LLM 看完整原问题、主体能力、字段触达和候选便签
  自己判断路线名、病害类型、设备、路段、时间粒度等在原句中扮演什么角色
  LLM 只输出 raw_value，例如“宝安大道西乡段”“泛油”“只看下行”
  ↓
代码调用 values.resolve_value()
  路线名查路线台账，病害名查病害字典，枚举中文查 code_map
  桩号转米数，时间转起止边界
  ↓
用解析后的 ValueBinding 组装正式 QuerySpec
  ↓
QuerySpec 结构检查、审计、模板匹配、SQL 编译
```

所以"实体识别在 QuerySpec 之前"要说得再准确一点：

- **实体是否出现、最终答案是什么主体，以及这些词大概涉及哪些表字段，在 QuerySpec 规划前完成识别。**
- **实体的权威数据库 ID、编码或规范值，是在模型交出 `raw_value` 后，由代码在组装 QuerySpec 的过程中完成解析。**
- 这个解析仍发生在**正式 QuerySpec 成立之前**。如果路线台账里查不到，代码会直接报"路线不在数据库台账中"，不会先造出一份带着错误路线 ID 的查询单再执行。

为什么路线值不全部提前塞给模型？因为有些话里虽然出现了路线字样，但它未必是过滤条件。例如：

| 用户原话 | 路线名在这里的角色 | 正确结果 |
| --- | --- | --- |
| 宝安大道西乡段有多少处泛油 | 过滤值 | `route_name = 宝安大道西乡段` |
| 按路线统计病害数量 | 分组维度 | `GROUP BY route_name` |
| 哪条路病害最多 | 分组维度加排序 | 按路线分组、按病害数排序 |
| 展示路线和病害类型 | 展示字段 | 放进 `output_projection` |

同一个"路线"词，在四句话里的结构角色不一样。可以先由前置阶段知道"这里提到了路线实体"，但具体是过滤、分组还是展示，要让拿到完整句子的规划模型来判断。这是当前链路最重要的边界。

已登记实体还有一条独立证据链。`resolve_subject()` 会从能力注册表的实体目录里读取名称和别名，在完整问题里做精确命中。例如病害字典里的"泛油"命中后，会给 `disease` 增加主体候选。它的作用是判断"用户明确提到了哪类业务对象"，不是替模型决定整句话的查询结构。

历史上旧版 `plan` 链路确实是先由 `parse_semantics()` 判断意图和 `route_values`，再去路线台账解析名称和编码。那段代码现在已停用。当前新版把主体判断放在独立的 `subject_resolver`，并继续坚持“模型从完整原句里指认原文，代码去台账和字典核实事实”这条原则。新旧入口的关系见第十四节。

## 五、第五站：主力模型把一句话拆成查询单

这是整条链路上最重要的一关。前面四关都是在给它准备材料，后面所有关口都是在执行它交出来的东西。你说"小部分没看懂"，大概率就是这一关到 SQL 那一段之间没接上。

### 以前写在代码里的硬匹配，现在怎么交给大模型

项目早期确实在代码里堆过不少直接匹配：看到某个词就当某种意思，看到路线名样式就直接切字符串，看到"下行"就直接加枚举过滤。这种写法的问题是，同一个词在不同句子里角色不同，代码一旦命中就很容易把语义定死。

现在的做法是把"容易误判、但仍值得提醒模型"的匹配放进配置文件。当前主要分成两层：

| 层 | 文件 | 负责什么 | 能不能直接决定查询 |
| --- | --- | --- | --- |
| 候选证据层 | `resources/capabilities/assist_rules.yaml` | 关键词、正则、指标提示、字段别名 | 不能。全部标成 `trusted=false` |
| 权威事实层 | `entities.yaml`、`aliases.yaml`、`identifiers.yaml`、`predicates.yaml` | 实体来源、别名、编号规则、业务值定义 | 能提供事实和解析依据，但仍要经过对应解析器 |

`assist_rules.yaml` 文件开头写得很直接：

> 本文件只生成 `trusted=false` 的候选证据。代码不得直接据此决定语义或 SQL。

里面常见的配置有四类：

- `keyword_rules`：命中"趋势、对比、列出、最多"这类关键词。
- `regex_rules`：命中"本季度""2026年11月2日""按周""第三车道"这类固定样式。
- `metric_rules`：提示可能涉及的指标。
- `field_aliases`：把 `week_start_date` 等相近字段名归一到统一字段。

这比在 Python 里散落一堆 `if "下行" in question` 好维护，但它仍然不是判决书。配置文件只负责说：

```text
这句话里发现了“下行”两个字，
它可能和方向字段有关，
这是一张给规划模型的便签。
```

它不负责说：

```text
用户一定是在过滤 up_or_down='2'。
```

### 便签是怎样进入大模型的

调用链很短，可以逐行对上：

1. `analysis.py` 里的 `_analyze_once()` 先调用 `detect_evidence(original, kind)`。
2. `semantic_aids/engine.py` 读取 `assist_rules.yaml`，每命中一条就生成一个 `AssistEvidence`。
3. 每条证据至少带这些东西：规则编号、原文片段 `raw_span`、候选类型、候选字段、候选值、提示原因、`requires_field`、`discouraged_fields`。
4. `chat_json()` 调用 `query_spec.md` 时，把整句原问题、当前主体能力、物理字段和这批证据一起传进去。
5. `query_spec.md` 的第 29 条硬规则明确告诉模型：这些内容是 `trusted=false` 的候选，只能辅助，必须结合用户原话、字段目录和能力视图自行判断。

模型最后看到的不是被规则切碎的几句话，而仍然是完整的：

```text
2026年11月2日，宝安大道西乡段有多少处泛油？
```

候选证据只是附在旁边的小纸条。模型要自己判断"宝安大道西乡段"是路线过滤值，"泛油"是病害类型过滤值，"多少处"是计数，"2026年11月2日"是自然日范围。

"上下行"这个例子最能说明区别：

| 用户原话 | 规则可能命中的证据 | 模型应作出的判断 |
| --- | --- | --- |
| 展示病害的上行、下行 | 可能命中方向词 | "上行、下行"是展示字段，不是只筛下行 |
| 只看下行的病害 | 命中方向词和"只看"范围 | 下行是真实过滤条件 `up_or_down='2'` |

规则两次都可能说"这里出现了方向词"，但完整句意决定它是展示字段还是过滤条件。这就是为什么关键词命中不能直接生成 SQL。

模型交出草稿后，还有一道 `_assist_field_issue()` 检查：

- 用户明确点名了某个候选字段，模型有没有漏掉。
- 模型有没有用了证据里标成 `discouraged_fields` 的错误字段。
- 如果字段缺失或冲突，就把具体原因放进 `planning_feedback` 交回规划器，让它按原因重排，而不是盲目重试同一个问题。

所以完整分工是：

```text
代码从配置里“贴便签”
  ↓
完整原问题和便签一起交给 LLM
  ↓
LLM 负责判断语义角色、过滤、分组、展示和时间粒度
  ↓
代码用字段目录、实体台账、字典和枚举 code_map 确认事实
  ↓
结构检查只负责拒绝真正非法的查询
```

这里要特别注意，"关键词/正则匹配"和"权威实体解析"不是同一种东西：

- 正则命中"本季度"，最多只能说"这里可能有一个季度时间窗口"。
- 路线名、病害类型、设备号能不能用，必须去路线台账、病害字典或实体目录里核实。
- 枚举中文能不能变成 `0`、`1`、`2` 这样的存储值，必须看字段目录里的 `code_map`。
- 普通关键词没有权力推翻完整句意，也没有权力生成业务 ID。

多租户 JOIN 这类风险也只做提示或标注，不在这里直接把一条可能正确的查询判死。真正需要硬拒绝的，仍然是"表或列根本不存在""字段契约不成立""枚举值不在字典里"这类客观结构错误。

### 5.1 它手里有什么

调用在 `backend/app/query/analysis.py` 的 `analyze_single_turn()` → `_analyze_once()`，用语义模型，最多让它吐 4096 个 token。

当前提示词头和调用代码都按八个占位符传递，`backend/tests/query/test_prompt_contracts.py` 会检查两边是否一致。核对时以 `analysis.py` 里的 `analyze_single_turn()` / `_analyze_once()` 调用为准，不要只看文档。

| 占位符 | 塞进去的是什么 | 长度上限 |
| --- | --- | --- |
| `<<question>>` | 问题原文 | 不限 |
| `<<kind>>` | 库的类型，这道题是 mysql | 不限 |
| `<<current_date>>` | 今天的日期，用来算"上个月"这种相对时间 | 不限 |
| `<<capabilities>>` | 这个主体允许用的字段和视图清单 | 32000 字符 |
| `<<schema>>` | 主体底表的字段，只有底表，不是全库 | 5000 字符 |
| `<<planning_feedback>>` | 上一次规划失败的原因，重排时才有 | 不限 |
| `<<assist_evidence>>` | 配置化关键词/正则命中的候选证据，比如时间粒度、方向词、Top N | 6000 字符 |
| `<<reach>>` | 第三站摸出来的字段命中，每条带表名、字段名、命中词、分数 | 不限 |

这里要特别说 `<<schema>>` 和 `<<capabilities>>` 的分工。

`<<schema>>` 是硬邦邦的物理事实：这张表有哪些列，列叫什么名，是什么类型。它只给主体底表，因为把全库几千个字段贴进去，模型反而抓不住重点。

`<<capabilities>>` 是系统认过的能力清单：哪些视图能用，哪些字段是登记过的指标。这是软的约束，告诉模型"这个主体支持这么问，不支持那么问"。

两个加起来，模型既知道有什么，也知道什么能用。

这个约束听起来理所当然，实际上是最关键的一刀。没有这一刀，模型会自己编字段名，编出来的字段在库里不存在，SQL 一执行就报错。

### 5.2 它按什么顺序想

提示词里写死了五步，要求模型一步一步想完再输出。

第一步，先看有没有业务编号。`XJJL` 开头的是巡检查询任务号，`XCBH` 开头的是巡查编号，`BPLHZD` 和 `KZXB` 开头的是病害编号。这一步的作用是别把任务号当成工单号。

第二步，判断答案属于哪类对象。这一步是给第四站兜底，因为第四站有时判不出来。

第三步，看有没有比较结构。如果用户说"11 月 2 日和 11 月 3 日对比"，那要拆成两个数据节点，每个节点查一天，最后再加一个计算节点做减法。提示词里明确写了，每个日期必须覆盖完整自然日，11 月 3 日要写成大于等于 11 月 3 日且小于 11 月 4 日。

第四步，检查路线名。这一条很有意思，提示词直接告诉模型：路线名你不用操心转 ID，代码会转，你不要为了拿路线 ID 额外生成一个路线查询。

为什么要写这一条？因为模型很爱自作聪明。它会想"要按路线过滤，那我得先查一下这条路的 ID"，于是生成一个多余的节点，白跑一次 SQL。

第五步，输出前自检。每个节点的 `question` 字段要写清楚对象、路线、日期范围、指标和分组。这个字段看着像注释，其实是给下游执行器当说明书用的。

### 5.3 它交出什么

一道题交出来的东西长这样。这是实跑打印出来的原文，不是简化示意。

```json
{
  "id": "q1",
  "kind": "mysql",
  "subject": "disease",
  "view": "count",
  "metrics": ["count"],
  "dimensions": [],
  "filters": [
    {
      "field": "collection_time",
      "op": ">=",
      "storage_value": "2026-11-02 00:00:00",
      "display_value": "2026-11-02 00:00:00",
      "source": "model_inference",
      "resolver": "time_range",
      "raw_text": "2026-11-02"
    },
    {
      "field": "collection_time",
      "op": "<",
      "storage_value": "2026-11-03 00:00:00",
      "display_value": "2026-11-03 00:00:00",
      "source": "model_inference",
      "resolver": "time_range",
      "raw_text": "2026-11-03"
    },
    {
      "field": "route_name",
      "op": "=",
      "storage_value": "1b0b4a9f700477b1d96119caac87c168",
      "display_value": "宝安大道西乡段",
      "source": "user_explicit",
      "resolver": "route_dictionary",
      "raw_text": "宝安大道西乡段"
    },
    {
      "field": "problem_type_name",
      "op": "=",
      "storage_value": "泛油",
      "display_value": "泛油",
      "source": "user_explicit",
      "resolver": "damage_type_dictionary",
      "raw_text": "泛油"
    }
  ],
  "output_projection": [],
  "order_by": [],
  "limit": null,
  "required_assertions": ["preserve_user_scope"],
  "question": "统计2026年11月2日（>=2026-11-02 且 <2026-11-03），路线名称为'宝安大道西乡段'，病害类型为'泛油'的病害记录总数",
  "input_bindings": [],
  "calculation": null
}
```

一个字段一个字段拆开看。

`id` 是节点编号。`q1` 是第一个数据节点。编号后面在依赖传值时会用到，下游节点用 `depends_on` 指向上游的编号，不许用"上一题的结果"这种代词。

`subject` 是对象，这道题是病害。

`view` 是视图，十三个里挑一个。这道题是 `count`，意思是只数个数。十三个视图分别是 `count`、`sum`、`avg`、`distribution`、`list`、`detail`、`top`、`top_records`、`top_groups`、`trend`、`bucket_compare`、`photo`、`data`。

`metrics` 是算什么，只有一个 `count`。

`dimensions` 是按什么分组，这里是空的，因为用户没让分组。

`filters` 是过滤条件，这道题有四条。这是最能体现"拆解"的地方，一条过滤器讲了四层信息：

| 字段 | 什么意思 | 这道题的值 |
| --- | --- | --- |
| `field` | 库里哪个字段 | `collection_time`、`route_name`、`problem_type_name` |
| `op` | 怎么比 | 大于等于、小于、等于 |
| `storage_value` | 数据库里真实存的值 | 时间点、路线 ID、泛油 |
| `display_value` | 给人看的值 | 西乡段、泛油 |
| `source` | 这个值是哪来的 | 用户说的，还是模型推的 |
| `resolver` | 谁负责把原文翻成存储值 | 时间范围、路线字典、病害字典 |
| `raw_text` | 用户原话 | 西乡段 |

这张表值得多看一眼，因为它解释了这个系统最核心的一招：**模型不直接给 SQL，也不直接给库里的值，它只给"用户说了什么"，翻译工作是代码做的。**

模型交出来的是 `raw_text` 是"宝安大道西乡段"。代码拿到这四个字，去路线台账里查，查到了 ID `1b0b4a9f700477b1d96119caac87c168`，把 `storage_value` 填上，把 `display_value` 填成规范名。

模型有没有可能自己瞎编一个 ID？有可能。但代码不认模型给的 ID，代码只认自己查出来的。这就是为什么模型编错了也不会一路错到底。

病害类型这一条更能说明问题。`storage_value` 填的是"泛油"两个字，不是病害的 ID。为什么？因为病害类型的解析链路不支持直接翻 ID，而是拿名称去库里比对。所以同一个环节，路线翻成了 ID，病害类型保留了名字。这是两套不同的解析器，`route_dictionary` 和 `damage_type_dictionary`。

`output_projection` 是要输出哪些字段，这道题的计数节点是空的，因为只数个数，不要明细。

`order_by` 和 `limit` 是排序和取几行，这道题都没有。

`required_assertions` 是一条必须满足的承诺，`preserve_user_scope` 的意思是"不许偷偷改用户说的范围"。这一条后面会被第七站拿来核对。

`question` 是给执行器看的可执行子问题。注意它跟用户原话不一样，它把"多少处"翻译成了"病害记录总数"，把日期写成了明确的时间点。

这个字段里那对括号是程序自己拼进去的，不是文档的写作习惯。上面两个 JSON 是实跑原样复制的，一个字符都没改。

### 5.4 为什么一句问话变成两个节点

你只问了一句话，但系统交出了两个节点。

第二个节点是这样：

```json
{
  "id": "q2",
  "view": "list",
  "output_projection": [
    "problem_number",
    "problem_type_name",
    "area",
    "effective_disease_length",
    "pile_number",
    "route_name",
    "collection_time"
  ],
  "limit": 500,
  "question": "列出2026年11月2日（>=2026-11-02 且 <2026-11-03），路线名称为'宝安大道西乡段'，病害类型为'泛油'的病害明细，用于定位"
}
```

第二个节点跟第一个节点的过滤条件一模一样，只有视图不同：一个数个数，一个列明细。而且第二个节点自己声明了 `limit` 是 500，还指定了要输出七个字段。

为什么自动多出一个明细节点？因为提示词硬规则第四条写着：汇总加明细必须拆分。用户嘴上只说"多少处"，但看到数字以后一定会问"是哪些"。所以系统提前把明细也准备好，前端可以直接展开看。

这条规则有代价，每次都多跑一条 SQL。但用户体验上省了一次追问，值。

### 5.5 这个模型最容易错在哪

第一，自己发明视图名。模型有时会输出 `analysis` 这种词，它觉得这是"分析一下"的意思，但系统的十三种视图里没有这个名字。这时候第七站会报"不支持的查询视图"。你说过这个问题，后来的修法是把常见别名归一成标准名，同时把"计划里名字写错了"和"库里真没有这个数据"分开报，不能混成一句话。

第二，想用模糊匹配。模型很爱写 `like` 加百分号通配。提示词里明确禁止了，只允许 `=`、`!=`、`>`、`>=`、`<`、`<=`、`in`、`between`、`is_null`、`not_null` 这十种。为什么禁？因为模糊匹配会把"泛油"匹配到"泛油修补"里，数量直接翻倍，而且不报错。

第三，想自己把"裂缝"展开成十几种。提示词里写明了，写"裂缝"这个族名就行，代码会去病害字典里展开。

第四，把上一题的结果写成字符串。比如"按那条路查"，模型可能就把"长沙－芷江高速公路"直接塞进过滤值。这是上游结果传值最容易出的错：把给人看的名字当成库里的标识。提示词后来加了硬规则第十条：下游要用上游的值，必须在 `inputs` 里声明从哪个节点、哪个字段、怎么比，不许写成过滤值字符串。

## 六、第六站：换另一个模型复查查询单

### 为什么需要这一步

写查询单的模型和用查询单的代码不是同一个脑子。模型可能漏条件、可能把"各条路线"写成不分组、可能把"面积最大"写成没排序的明细。

让同一个模型自己复查，效果不好，它会觉得自己写得对。所以换一个模型。

### 谁在做

`query_spec_audit.md`，调在 `backend/app/query/audit.py` 的 `audit_query_plan()`，用校验模型，最多 4096 个 token。

这里有个设计细节值得说。`query_spec_audit` 用的是 `role_model("verify")`，`query_spec` 用的是 `role_model("semantic")`。两个不同的配置项，可以指向两个不同的模型。

代码注释里写了原因：裁判模型可以单独配。如果用同一个小 flash 模型既写又判，它会自说自话，把明显答非所问的判通过。分开配，才有一点点独立性。

### 它看到什么

问题原文、整份查询单的 JSON、今天的日期。

就这三样。它不看库，不看 SQL，只看"这张查询单能不能回答这个问题"。

### 它交出什么

一份挑刺结果。如果没问题，返回空；有问题，给出问题类型和怎么改。

改的方式是打补丁，不是重写。代码里 `_apply_audit_patches` 只允许改七个字段：`limit`、`view`、`metrics`、`dimensions`、`order_by`、`output_projection`、`required_assertions`。

为什么只让改这七个？因为这七个是"怎么展现"，改了不影响查什么。过滤条件和对象不让它动，动了就可能把用户的范围改掉。

## 七、第七站：代码核对查询单合不合法

到这一关，查询单已经在纸上写好了，但还没验证过它是不是能执行。这一步纯代码，在 `backend/app/query/planner.py`，整个文件只有 48 行。

它做四件事：

第一，字段名在不在库里。模型写 `route_name`，代码去物理视图里查，真有这个字段才放行。
第二，视图名在不在十三种里。
第三，运算符在不在那十种里。
第四，这个对象配这个视图合不合理。比如 `photo` 视图只能在明确要图片时用。

任何一项不过，直接抛错，错误信息是把所有问题用分号串起来的一句话，比如"字段 xxx 不存在；视图 xxx 不支持"。

这里的原则是宁可报错，不猜。猜错的成本比报错高得多，报错用户重问一次就过去了，猜错用户会拿着错数字去做决定。

## 八、第八站：模板系统，从“挖出来”到“推荐给谁”

查询单合法以后，系统会先问一句：**这个问题是不是已经有可复用的查询口径？**

这里最容易误解。模板匹配不是拿用户这句话去和模板标题做字符串相似度，也不是看见“病害”两个字就套病害模板。当前主链拿到的是上一站已经结构化的 `QuerySpec`，再用它和每张模板的“接单条件”逐项对。

可以把它想成一家已经配好菜的中央厨房：

```text
QuerySpec = 顾客点菜单
模板合同 = 这道菜能接哪些要求
候选卡 = 后厨把能做的几种做法端给顾客选
确认票 = 顾客选好后盖的一次性章
执行器 = 按盖过章的做法真正下锅
```

### 8.1 先把四种“可复用资产”分开

代码里经常把它们都叫“模板”，但它们的来源和执行方式不同：

| 资产 | 文件或来源 | 本质 | 新版单轮主链是否默认参与 |
| --- | --- | --- | --- |
| 内置代码模板 | `resources/capabilities/templates.yaml` 中 `source: builtin` 的记录 | 系统预置的查询形态声明 | 参与 |
| 预置查询 | `backend/app/data/preset_queries.json` | 人工维护的 SQL 模板和可绑参数 | 参与 |
| 自动沉淀模板 | `backend/app/data/auto_templates.json` | 从成功 SQL 中挖出来的参数化 SQL 骨架 | 参与，且只接受 `enabled=true`、`status=mature` 的记录 |
| 验证示例模板 | `VerifiedExampleTemplateProvider` 注入的 examples | 历史验证问答对转成的模板合同 | 代码支持，但 `start_single_turn()` 默认传的是空列表 |

`templates.yaml` 里还有 `source: generic` 的通用算子声明，它们不归新版单轮主链的 `BuiltinTemplateProvider` 使用。旧候选收集器、快捷查询和通用算子接口走的是另一套逻辑，不要混在一起。

截至本次核对时，文件里的数量是：`templates.yaml` 有 37 条记录，其中 28 条是 `source: builtin`；`preset_queries.json` 有 75 条预置查询；当前开发库的 `auto_templates.json` 有 15 条自动模板，全部是 `mature + enabled`。这些数字会随数据变化，读文档时应该把它当“本次快照”，不要当业务常量。

### 8.2 模板来源怎样变成统一合同

`backend/app/query/template_sources.py` 会把不同格式的模板源统一转换成 `TemplateContract`。合同里只保留匹配和执行真正需要的字段：

```text
id / version / source / status
subject        查询主体
view           查询形态
metrics        能算哪些指标
dimensions     能按哪些维度分组
filters        能接收哪些过滤条件
fixed_conditions  模板自己固定了哪些条件
output_projection 能返回哪些点名要看的字段
required_filters  用户必须明确给了哪些条件才允许接单
```

不同来源的转换规则：

- 内置模板和预置查询读 `match.shapes`、`match.subjects`、`match.metrics`、`match.group_by`、`match.slots`、`match.fixed`。
- 自动模板必须带完整的 `match.shapes/subjects/metrics/group_by/conditions/fixed/output_fields` 和 `params`。少了任何一块，就记录 `template_contract_rejected`，不进入候选。
- 自动模板只有 `enabled=true` 且 `status=mature` 时才转成 `active` 合同；`candidate`、`broken`、`cold` 都不会在在线主链被推荐。
- 验证示例会从示例 `spec` 提取主体、形态、指标、条件、输出字段；没有完整 `spec` 的示例同样会被拒。

这一步相当于先把各家模板的“菜单格式”统一。后面匹配时，系统不再关心它原来来自 YAML、JSON 还是示例库，只看统一合同。

### 8.3 新版主链怎样匹配：先过硬门槛，再谈推荐

`backend/app/query/service.py` 的 `start_single_turn()` 只对 `query_data` 节点调用：

```python
resolve_templates(node.spec, schema, providers)
```

默认提供者顺序是：

```text
BuiltinTemplateProvider
  → PresetTemplateProvider
  → AutoTemplateProvider
  → VerifiedExampleTemplateProvider
```

每张模板都要经过 `backend/app/query/templates.py` 里的 `_eligibility_issues()`。它是“全有或全无”的硬匹配，主要检查：

| 门槛 | 检查内容 | 不过时会发生什么 |
| --- | --- | --- |
| 状态 | `status == active` | 候选、冷门、坏掉的模板都不进 |
| 库类型 | `contract.kind == spec.kind` | MySQL 模板不会接别的库 |
| 主体 | `contract.subject == spec.subject` | `disease` 模板不会接 `route` 主体 |
| 形态 | `contract.view == spec.view` | `count`、`distribution`、`list` 等不能串用 |
| 指标 | QuerySpec 要的每个指标，模板都支持 | 少一个就是 `missing_metric` |
| 分组维度 | QuerySpec 要的每个分组，模板都支持 | 少一个就是 `missing_dimension` |
| 输出字段 | QuerySpec 点名要显示的字段，模板都能给 | 少一个就是 `missing_output` |
| 物理列 | 模板声明的物理列在当前字段目录中存在 | 字段被删会报 `missing_physical_column` |
| 过滤条件 | 用户每个过滤条件都必须由模板参数或固定条件表达 | 否则是 `missing_filter` |
| 必填过滤 | 模板声明必须由用户明确提供的条件必须存在 | 否则是 `missing_required_filter` |
| 固定条件 | 模板固定了某个值，用户就必须明确提出同一个值 | 没有或冲突都不命中 |

最后一条很重要。假设模板写死 `up_or_down='1'`（上行），用户只问“病害多少处”，没有说上下行。系统不能偷偷把模板补成“只看上行”。只有用户明确说“上行”，并且值也对得上，这条固定条件才允许通过。

过滤条件不是直接比字符串。代码会先用 `filter_semantic_name()` 把两边统一成同一种语义名，例如：

```text
route_name / routes_id          → route_id
damage_type / problem_type_name → 同一类病害条件
collection_time / create_time   → 同一类时间条件
limit / top_n                   → 同一类排名条件
```

所以“字段名不同但说的是同一件事”可以命中；语义根本不同就必须分开。

#### 预置查询还会多做一次真实绑定

预置查询不是结构对了就完事。`resolve_templates()` 还会调用 `preset_lib.bind()` 用本轮 QuerySpec 的值真正填一次 SQL，并检查：

- 路线、设备号等值必须能从本轮的动态选项里找到。
- `__ALL__` 这类“全部”值只有参数声明 `allow_all` 时才接受。
- 时间范围能不能正确落成起止日期。
- SQL 里是否真的用到了用户绑定的时间列。例如用户明确用 `create_time` 过滤，模板 SQL 却只写 `update_time`，会被 `missing_bound_column` 拒绝。

这防止一种很隐蔽的错：卡片上写着“11 月 2 日”，SQL 却按另一个字段或另一个日期查，结果看起来正常，口径已经变了。

#### 新版主链当前没有“相似度分数排序”

这里必须和旧推荐器区分：

- `resolve_templates()` 只做准入判断，准入通过就原样加入 `CandidateSet`。
- 它不计算相似度，不做槽位完备度加分，不按使用次数排序，也没有对大模型做重排。
- 候选顺序就是“提供者顺序 + 文件内顺序 + QuerySpec 节点顺序”。
- 前端当前拿到的候选 `score` 是 `0`，`recommended_id` 取候选列表第一条。
- 多个来源之间也没有统一去重；同一口径若同时来自预置查询和自动模板，可能同时出现两张卡。

这不是说推荐完全不挑，而是说当前主链的“推荐”本质上是**合同匹配后的候选列表**，不是搜索排序。真正决定用哪条的，仍是用户在确认卡上点。

被拒绝的模板会进入 `CandidateSet.rejections`，记录类似 `missing_metric:length`、`fixed_condition_conflict:up_or_down` 的原因，方便代码和日志排查。当前用户侧的确认卡只展示通过项，不会把全部拒绝原因逐条展开。

一个匹配例子：

```text
本轮 QuerySpec：
  主体 = disease
  形态 = distribution
  指标 = count
  分组 = route
  过滤 = route_name

模板合同：
  主体 = disease
  形态 = distribution
  指标包含 count
  分组包含 route
  参数能表达 route_id

结论：通过所有硬门槛，生成候选。
```

如果用户实际要的是 `count + total_area`，而模板只会算 `count`，即使它和问题意思很像，也不会推荐。宁可去 Wren 重新查，也不能拿一张只答一半的卡冒充答案。

### 8.4 候选怎样变成推荐卡

`backend/app/services/agent.py` 的 `_single_turn_compiler_payload()` 会把 `TemplateCandidate` 转成前端能渲染的卡：

```text
kind              来源，例如 preset / auto / builtin
id                本轮候选 ID，例如 preset:device_month_records:q1:v1
node_id           它属于 QuerySpec 的哪个查询节点
title             模板标题
scope             主体、视图、指标、维度、条件摘要
slots             已绑定参数，用户可以改
reasons           本模板覆盖了哪些约束
warn              是否有警告
```

一张卡不是“让 AI 自由猜”，而是明确告诉用户：**系统准备按这张查询单、这组参数、这个模板口径执行。**

当前新版主链有两个很明确的规则：

1. 只要任一查询节点找到候选，整个计划就先停在确认阶段，不自动执行。
2. 每个候选项的 `requires_confirmation` 都是 `true`，即使只有唯一一条候选也不会自动放行。

如果一个问题被拆成多个 `query_data` 节点，每个找到候选的节点都必须选一条。用户在卡片上点了某个节点的候选后，`_maybe_single_turn_compiler()` 会为其他节点自动补上各自候选列表的第一条，然后一起执行。这个行为也要记住：结构化多节点问题里，用户实际确认的是一组联合口径。

用户还可以选择“让 AI 自己查”。此时传入的 `capability_id` 是 `ai` 或 `wren`，代码会丢弃当前确认票，把问题重新交给 `start_single_turn(..., providers=())`，明确关掉模板来源，再走 Wren 编译链。

需要特别说明当前代码边界：

- `single_turn_compiler_enabled` 关闭后，数据、分析、复合题会直接返回“旧查询链路已停用”，不会偷偷回退。
- `reuse_mode=ask/off` 和 `auto_template_enabled` 主要是旧候选收集器/兼容路径的开关。新版数据题在 `_maybe_single_turn_compiler()` 就已经被接管，实际的“本次不要模板”入口是候选卡上的 AI/Wren 回执。

### 8.5 用户点确认后，票和参数怎样传递

确认不是按钮动画。它有一套一次性的票据流程，代码在 `backend/app/query/confirmations.py`。

第一次生成候选时：

```text
QueryPlan
  + CandidateSet
  + schema_snapshot
  ↓ issue_confirmation()
ConfirmationTicket
  token
  plan_scope_hash
  candidate_ids
  template_versions
  expires_at
```

服务进程还会把 `_PendingTurn` 暂存在内存里，保存：

- 冻结后的 QueryPlan。
- 候选集。
- 物理字段视图。
- 字段触达结果。
- 原始问题、库类型和模板提供者，供确认后的重排/修复继续使用。

用户点确认时，`consume_confirmation()` 会检查：

- token 是否存在且没有过期。默认有效期由 `capability_token_ttl_minutes` 控制，现在是 30 分钟。
- 每个有候选的节点是否都选了合法候选 ID。
- 回传的槽位值能否通过字段、枚举和值目录的校验。
- 同一个 token 是否已经被消费过。

任何一项不通过，都会明确报“确认票失效、候选不存在或参数被拒绝”，不会擅自拿第一条候选顶上。

确认成功后，`compile_query()` 还会再核一次：

```text
decision.token 必须存在
decision.choices[node_id] 必须等于当前 candidate_id
```

然后才允许执行模板。

当前版本有一个需要知道的实现细节：票里记录了 `template_versions`，候选 ID 里也带 `vN`，但 `consume_confirmation()` 当前没有重新读取注册表并比较“模板版本是否还是 N”。计划、候选合同和槽位会随 `_PendingTurn` 冻结；真正执行时，预置查询和自动模板又会按 ID 从当前注册表取 SQL。因此，如果管理员恰好在“弹卡后、确认前”改写了同一条模板，当前代码没有严格的版本冲突报错机制。这是后续可以继续补强的乐观锁点。

另外，确认票和待执行计划保存在当前 Python 进程内存中。后端重启后，旧卡会失效；如果以后部署多进程，还要把票据改成共享存储，否则请求落到另一个进程时找不到票。

### 8.6 确认后到底执行哪条 SQL

`compile_query()` 分两条路：

```text
用户选了候选模板
  → 模板执行器

没有候选，或用户选了 AI/Wren
  → QuerySpec 转 MDL-SQL，再由 Wren 转物理 SQL
```

三种模板适配器的实际行为不同：

| 适配器 | 当前执行方式 |
| --- | --- |
| `preset` | 重新取预置查询定义，按本轮值绑定参数，得到物理 SQL |
| `builtin` | 不使用文件里的 `builder` 字段，而是把本轮 QuerySpec 交给 `compile_queryspec_to_physical()` 重新编译 |
| `auto` | 按模板 ID 取当前自动模板，把 QuerySpec 条件映射到模板参数后 `bind()` |

所以“弹了内置模板卡”不等于执行一段固定的内置 SQL。当前主链里，它主要是告诉用户“这个查询形态已有成熟口径”，确认后仍走受控 `QuerySpec → MDL-SQL → Wren` 编译器。

自动模板执行时会做参数别名处理，例如路线条件既可能来自 `routes_id`，也可能来自 `route_name`；病害类型会按模板参数的声明找对应条件。绑定失败就返回明确的编译错误，不会改用别的模板静默顶上。

模板执行成功后，结果会和普通 Wren 结果一样进入后面的 `verify_result()`、时间覆盖检查、零结果解释和回答组装。

### 8.7 没命中模板时，怎样转回确定 SQL

如果所有 `query_data` 节点都没有候选，`start_single_turn()` 会直接执行计划：

```text
QuerySpec
  ↓ compile_spec_mdl()
MDL-SQL
  ↓ SQL 审计
  ↓ Wren dry-plan / 编译
物理 SQL
  ↓ MySQL
结果
```

这条路径就是第九站以后要讲的受控 SQL 链。它不会因为“模板看起来差不多”而硬套；也不会因为模板失败，就回去让模型自由写 SQL。

### 8.8 另一套“自动模板候选匹配”仍然保留在兼容路径

旧候选收集器和维护工具仍使用 `backend/app/services/templatizer.py` 的 `card_for_template()` / `match()`。这套算法比新版合同门更“宽松”，会允许缺少量槽位的弱候选，并把“还差什么参数”摆在卡上让用户补。

它主要用于旧候选收集路径、部分图片或兼容入口，以及快捷查询、模板维护和人工检查。不要再把它当作新版单轮数据题的唯一匹配器。

它对自动模板的主要判断是：

1. 模板必须 `enabled=true`、`status=mature`。
2. 当前问题不是多对象对比，除非模板自己声明了多值实体槽。
3. 问题明确给出的全部过滤条件，模板必须能表达。
4. `top_n`、查询形态、主体、分组和指标必须对得上。
5. 问题点名要显示的字段，模板 SQL 必须真的包含，否则不硬推。
6. 模板写死的业务条件和用户明确说的值必须一致；用户没说这个条件，也不能替用户加上。
7. 路线槽缺失、或用户明确给了条件却填不进模板，是硬淘汰。
8. 其他可缺的实体、时间、数值槽可以留在卡上让用户补，或按“本轮不限”整段去掉。
9. 一个模板的所有槽都没有从本轮问题取到值时，整条候选淘汰。否则“结构差不多但内容完全没对上”的模板会挤到最前面。
10. 可选条件被丢掉时，卡片会提示“命中范围比模板问法更宽”，并扣分，但不会假装是完全匹配。

这套旧推荐器用规则分数排序，主要来自 `backend/app/config.py`：

```text
基础分
+ 槽位完备度 × auto_template_score_completeness
- 缺槽数 × auto_template_score_missing_penalty
- 被丢掉的可选槽数 × 一半扣分
+ 使用次数的小幅加分
+ 同义召回 bonus（如果这条路带进来）
```

当前默认值是基础分 `4.0`、完备度加成 `0.6`、缺槽扣分 `0.15`。`capabilities.collect_capabilities()` 再把候选分层为“预置/自动模板 → 相似示例 → 通用算子/代码模板”，同类最多两条，默认最多摆六条。排序模型当前已经停用，`_llm_rerank()` 只在保留的缓存入口里按规则顺序返回。

### 8.9 历史示例怎样被召回并复现

历史示例和自动模板不是一回事。示例库保存的是“问题 + 验证过的 SQL + 查询结构 spec”；自动模板保存的是从若干示例 SQL 中挖出的参数化骨架。

旧候选路径上的示例召回复用大致是：

```text
用户问题
  ↓
先找完全相同的问法
  ↓
没有则做向量召回 + 本地问题骨架相似度
  ↓
检查查询形态、主体、对象数量和过滤条件覆盖
  ↓
按本轮 QuerySpec 回填路线、时间、病害类型等槽位
  ↓
检查 SQL 能解析、能编译、没有丢失用户条件
  ↓
摆成确认候选
```

几个关键硬门槛：

- 示例 SQL 能表达本轮的所有过滤条件。示例固定查 7 月，就不能拿来答用户刚问的 8 月。
- 示例没被用户提到的额外条件不能偷偷保留，否则会出现“卡片长得对，实际多过滤了一层”的静默错答。
- 单对象示例不能拿去接多路线对比，多对象示例也不能把同一个值塞进两个不同对象槽。
- 用户明确点了“交安事件”等编码条件，示例 SQL 却没有对应列，整条示例不摆。
- 回填后的 SQL 必须还能解析并通过执行前校验；Wren MDL-SQL 先编译成物理 SQL，编译不了就不让用户点到最后一刻才失败。
- 一条历史问法如果已经沉淀成自动模板，优先摆参数可改的模板卡，不再同时摆一张原始示例卡。
- 所有示例复用仍然只产生候选，不自动执行。

`direct_match.gate()` 当前只走两种高置信路径：本地完全相同问法，或者相似度达到阈值且结构同型。代码里虽然仍保留 `example_direct_match.md` 和 `_score()` 这一套“模型严格同问打分”，但 `gate()` 当前在本地快速路径未命中时直接返回空候选，没有再调用它。因此文档不能继续写成“每次相似示例都会多花一次打分模型”。

### 8.10 模板从哪里来：自动挖掘的完整流水线

自动模板不是在线问问题时现写的，而是从成功问答对里的 SQL 离线挖出来。来源既包括用户点“答对了”后固化的问答，也包括示例库/RAGFlow 同步进来的带 SQL 示例；能不能成熟由后面的结构和回环验证决定。入口函数是 `backend/app/services/templatizer.py` 的 `mine_sql()` 和 `mine_all()`。

一次完整挖掘可以分成下面几层：

```text
成功问答对
  ↓
解析 SQL / 必要时先把 Wren MDL-SQL 编译成物理 SQL
  ↓
AST 预检：只做 MySQL、只接受可稳定参数化的结构
  ↓
挖 WHERE 条件、LIMIT、分档粒度、时间粒度
  ↓
挖不动的条件要么声明成 fixed，要么拒绝沉淀
  ↓
用规则 + 限量 LLM 补漏，代码负责替换和复查
  ↓
按结构指纹聚类
  ↓
跨样本判断“参数槽”还是“固定值”
  ↓
静态字段/编码检查
  ↓
用原值回填：结构一致 + 实跑结果一致
  ↓
写入 auto_templates.json
  ↓
生命周期巡检 + LLM 审核建议
```

关键细节如下：

- 只有 `kind=mysql` 的成功 SQL 会进入模板化。Wren MDL-SQL 会先编译成物理 SQL，否则模板执行不能直接复用。
- `WHERE` 里有 `OR`、SQL 不可解析、非只读查询、槽位过多、没有业务过滤条件、所有用户点名数字都没挖成槽，都会拒绝沉淀。
- 只改值，不改结构。表、JOIN、聚合、`GROUP BY`、投影和条件之间的逻辑由原 SQL 决定。
- 路线、病害类型、时间、数值阈值、`top_n`、桩号分档、按年/月/周/日/小时的分组格式等，会按列语义挖成类型化参数。
- 有些条件挖不动但会原样留在 SQL 里，例如“未识别”这类固定业务值，会写进 `match.fixed`。以后复用必须由用户明确给出同一条件，不能悄悄扩大范围。
- 用户问题里的数字如果还留在 SQL 字面量中，系统宁可拒绝沉淀。典型错误是 `ORDER BY ABS(pile_distance - 1802)` 换一个桩号后仍然按 1802 排序，表面能跑，结果静默出错。
- 确定性 AST 挖不明白时，才会限量调用 `templatize_classify.md` / `templatize_sql.md`。模型只提出“这里可能是什么槽”，最终替换、白名单校验和回填仍由代码完成。
- 多条成功 SQL 按参数化 SQL 的指纹聚类。跨样本出现过不同值的实体、时间、数值天然可参数化；上下行、收藏、工单状态、有无图这类枚举，只有真的见过至少两个不同值才确认成参数，否则保守地写成固定条件。
- 如果模板没有任何可替换槽、只有一条固化 SQL，或者计数口径有风险，会先进入 `candidate`，不直接推荐。只有人工转正或满足成熟条件，才变成 `mature`。
- 源表当前没有数据时，回环只能验证“结构对”，验不出口径，也会保留为 `candidate` 并写明原因。
- `_verify()` 会把模板参数用原始样本值填回去，先比结构和原 SQL 是否一致，再实跑并比对结果行。任一项不一致都不入库。
- 入库时还会做表、列、CTE、派生表和编码值检查。字段契约不成立或枚举值根本不在字典里的模板，不能因为“以前跑过一次”就继续推荐。

写入后的记录大致长这样：

```json
{
  "id": "auto_xxx",
  "question": "原始验证问法",
  "sql": "WHERE route_id = '{route_id}' ...",
  "params": {"route_id": {"type": "entity", "declare": "route"}},
  "match": {
    "shapes": ["count"],
    "subjects": ["disease"],
    "group_by": [],
    "metrics": ["count"],
    "conditions": ["route"],
    "fixed": {}
  },
  "status": "mature",
  "enabled": true,
  "samples": [{"question": "...", "values": {"route_id": "..."}}],
  "usage": 0
}
```

挖掘触发点有四种：

- 启动后的示例库对账线程会调用 `templatizer.mine_all()`。
- 用户点“答对了 / 固化”后，`approve_result()` 先把问答对存进示例库，再启动后台增量挖掘。
- 看板执行示例同步后，后台再挖新同步进来的问答对。
- 管理接口可以手动全量重建、增量刷新、重挖单条模板或重新校准参数。

自动挖掘开关 `auto_template_mine_enabled` 默认是关的，避免污染模板库。手动维护接口传入 `manual=True` 可以绕过这个开关，但仍要经过同样的结构、静态字段和回环验证。

### 8.11 模板状态、审核和反馈怎样改变推荐

自动模板不只有“有没有”两个状态。当前主要有：

| 状态 | 含义 | 是否进入新版在线候选 |
| --- | --- | --- |
| `mature` | 已成熟、可复用 | 是，且还要 `enabled=true` |
| `candidate` | 证据不足、口径有风险或人工待确认 | 否 |
| `broken` | 当前字段目录里找不到表或列 | 否 |
| `cold` | 被摆出多次却一次没被复用，且模板年龄达到阈值 | 否，但保留 |

生命周期巡检 `sweep_templates()` 做两件事：

- 字段目录可读时，静态检查失败的表/列问题会把模板标成 `broken`。
- 最近窗口内被推荐过至少 `template_cold_after_offers` 次、使用次数仍为 0，并且模板创建超过 `template_cold_min_age_days` 天，才标成 `cold`。刚挖出来的模板不会因为跑批曝光多就被判冷门。

`review_template()` 会把问题、参数化 SQL 和已声明条件交给 `template_review.md`，结论写进 `review`。但当前默认不按 LLM 审核自动降级：`template_review_auto_demote=false`。只有两类情况才可能考虑降级，当前真正开放的自动降级类型只有 `parameter_misaligned`，而且还要求 SQL 里确实存在两个同类占位槽。其他硬编码条件、单位、只答部分等审核意见默认只作标注，交人工判断。

人工操作包括：

- 转正：`candidate → mature`。
- 降级：`mature → candidate`。
- 重挖：按当前挖掘器重新识别槽位，只有参数严格变多且回填 SQL 等价才替换。
- 忽略审核意见：保留结论备查，但不再提示或降级。
- 删除模板及可选来源问答对。

用户答错反馈也设计了闭环：`/feedback/report` 会从结果缓存里尝试找出候选 ID；同一模板连续三次 `bad`，调用 `demote()` 退回 `candidate`。但当前新版单轮结果结构里没有稳定写回 `candidate` 对象和自动模板原生 ID，`_feedback_context()` 更依赖旧候选路径保存的字段；同时新版执行器也没有调用 `bump_usage()`。所以“新版主链的自动曝光计数、使用次数和连续答错降级”目前还没有完整接线，维护和生命周期数据主要仍来自兼容候选路径。这是数据流里真实存在的未闭环处，不能写成已经全自动生效。

### 8.13 多步题还要经过 ReAct：它管的是“执行中出错怎么办”

这里的 ReAct 是英文 Reason + Act 的缩写，意思是“先看当前情况，再选一个动作，然后根据动作结果继续”。它不是前端开发里的 React 框架，也不是另一个专门写 SQL 的模型。

单步数据题通常走前面讲的查询单链路，不经过 ReAct。多步复合题会先由规划器拆成若干任务，再交给 `backend/app/services/react_agent.py` 执行。代码在 [agent.py](D:/Code/巡检智能体/backend/app/services/agent.py:2883) 里调用 `should_use_react()`，主要条件是：

- 至少有两个步骤。
- 每个步骤的类型都在 `data`、`aggregate`、`knowledge`、`analysis`、`post_calc` 之内。
- 图片步骤暂时不走 ReAct 主循环。

ReAct 拿到的是**已经做好的计划**，不是只拿到一句用户问题。计划里每一步通常有这些东西：

```text
id           第几步
type         查数据、查知识、后置计算、综合分析
question     这一步要完成的子问题
needs        这一步要从前面的步骤拿哪些值
produces     这一步做完后要给后面留下哪些值
depends_on   它依赖哪几步
contract     这一步的执行契约和静态检查结果
```

例如用户问：

```text
哪一周泛油最多？把那一周在宝安大道西乡段的泛油明细列出来。
```

规划器可能拆成：

```text
第 1 步：按周统计宝安大道西乡段泛油数量，找出最多的那一周。
第 2 步：用第 1 步找到的周，查询该周的泛油明细。
```

ReAct 不会重新理解整句话，也不会把"泛油"偷偷改成"所有病害"。它先执行第 1 步，把结果里的 `peak_week` 放进黑板，再把 `peak_week` 填进第 2 步的 `{{peak_week}}` 占位符。所以第 2 步拿到的仍然是完整、冻结后的子问题。

#### ReAct 的黑板是什么

可以把 `ReactBlackboard` 想成一块大家共用的白板，定义在 [react_agent.py](D:/Code/巡检智能体/backend/app/services/react_agent.py:17)。上面记着：

- 用户的完整问题和最终目标。
- 已经执行了哪几步。
- 每一步的观察结果。
- 前面步骤产出的链式值，例如峰值周、路线 ID、任务编号。
- 已经确认过的事实缓存。

每一步成功后，工具返回的结果会被写进黑板。下一步不靠猜，靠黑板上的真实结果继续。

#### 正常执行时，ReAct 控制器模型根本不启动

代码的主循环在 [react_agent.py](D:/Code/巡检智能体/backend/app/services/react_agent.py:842)：

```text
按计划取当前步骤
  ↓
填入前面产出的依赖值
  ↓
根据步骤类型选择工具
  ↓
执行工具，得到观察结果
  ↓
判断这一步是否成功
  ├─ 成功：写黑板，进入下一步
  ├─ 静态契约已非法：直接停止，不重试
  ├─ 结构化失败且不可重试/无候选工具：直接停止
  └─ 结构化失败且可修：才调用 react_controller.md 决策
```

步骤类型和工具的对应关系在 `_tool_for_step()`：

| 步骤类型 | 调用工具 |
| --- | --- |
| `data` / `aggregate` | `query_data` |
| `knowledge` | `query_knowledge` |
| `post_calc` | `post_calc` |
| `analysis` | `analyze` |

所以计划顺利时，`react_controller.md` 这个模型一次都不会被调用。前端看到的"该步骤无前置依赖，按冻结问法直接执行"这类思考，也是代码根据计划生成的状态说明，不是模型每次都在后台长篇推理。

#### 只有“可修”的异常，才让控制器在规定动作里选一个

这里要分清三件事，否则很容易误以为每次失败都会自动问一遍大模型：

1. **规则直接判死**：规划阶段发现静态执行契约不成立，比如字段组合非法、枚举来源不对，代码直接 `abort`。这一步不会调用 `react_controller.md`，也不会拿同一问法重跑。
2. **工具返回结构化失败，但明确不可重试，或者没有候选修复工具**：`_run_structured_repair()` 也直接 `abort`，并把 `failure.reason` 原样保留下来。
3. **工具返回结构化失败，且 `retryable=true`、确实存在允许的候选工具**：这时才调用 `_deviation_decision()`，把具体失败证据交给 `react_controller.md`。

几个典型分支可以这样记：

| 发生什么 | 谁处理 | 实际结果 |
| --- | --- | --- |
| 查询单违反静态字段契约 | 代码直接停 | 返回具体契约错误，不调用控制器，不重跑 |
| SQL 指向不存在的字段，且没有候选修复工具 | 代码直接停 | 返回“字段不存在”等具体原因 |
| “第 31 周”缺少起止日期，但存在时间换算工具 | 控制器选 `call_tool` | 先调用工具补出真实日期，再继续当前步骤 |
| SQL 执行报错，且允许重试 `query_data` | 控制器选 `retry_tool` | 把本轮 `failure` 作为 `repair_feedback` 交给下一次查询 |
| 修正后黑板上的依赖值完全没变 | 代码直接停 | 明确告诉用户继续重跑只会重复失败 |

所以控制器不是在旁边“看热闹”的。只有存在可改变的依赖值或可调用的修复工具时，它才有机会发挥作用。它能看到：

- 最终目标。
- 当前冻结的子问题。
- 工具返回的错误和结构化失败证据。
- SQL、字段、枚举或结果形状的具体失败原因。
- 当前允许调用哪些工具。
- 前面已经试过哪些调用和每次尝试的结果。
- 已经取到的真实覆盖范围和链式值。

控制器不能改写步骤，不能增删路线、时间、病害类型，也不能直接写 SQL。它只能在有限动作里选：

| 动作 | 代码实际会做什么 |
| --- | --- |
| `call_tool` | 调一个辅助工具补证据，例如先把周名换算成真实日期 |
| `retry_tool` | 带着本次失败原因重跑当前工具 |
| `retry_atomic` | 用原子工具修正依赖值，再把修正后的值用于当前步骤 |
| `skip_step` | 只有后续步骤不依赖它时才能跳过 |
| `ask_user` | 对象或范围确实无法确定，向用户说明 |
| `abort` | 保留已完成结果，停止并说明卡点 |

如果控制器选择 `retry_tool` 重跑 `query_data`，代码会把上一轮的 `failure` 放进 `repair_feedback`，连同冻结后的完整子问题一起交给查询工具。这样第二次执行能读到“上次为什么失败”，而不是盲目重复同一问法。

所谓"原子工具"，就是一次只做一件确定的小事，例如：

- 把 `2026 年第 31 周` 换算成起止日期。
- 把桩号转换成米数。
- 把病害中文名解析成规范类型。
- 把前面产出的值填进占位符。

这些换算由代码工具完成，控制器只负责选择用哪一个，不负责心算。

#### 为什么不会无限重试

代码加了几道很关键的止损：

- 规划前的执行契约已经被静态判成非法时，不重试，直接说明是哪条契约不成立。
- 前置步骤失败时，依赖它的后续步骤不会拿空数据继续编答案。
- 同一个工具和同一组参数不能原样重复调用。
- 修正后黑板上的依赖值没有发生任何变化时，不再重跑同一个冻结查询。
- 连续两次失败结果完全相同时，停止并保留两次的失败证据。
- 如果第二次结果虽然有语义警告，但已经带回了可用数据，会带风险提示继续，而不是把可用结果丢掉。

这解决的是一个很常见的问题：工具已经明确告诉你“字段不存在”“JOIN 不符合关系契约”或“这个修正没有改变任何输入”，此时再让模型重复同一个查询，只会多花两轮模型调用，结果仍然一样。无论是直接停止还是控制器决定停止，最终结果结构里都会保留失败原因，用户能看到卡在哪一步，不是静默失败。

#### ReAct 不负责什么

ReAct 是执行调度员，不是新的取数大脑：

- 不负责把用户整句话重新拆一遍。
- 不负责修改已经冻结的路线、时间和指标。
- 不负责写 SQL。
- 不负责把没有查到的数据补成"看起来合理"的数字。
- 不负责在每一步成功时都调用一次大模型。

它真正负责的是：按计划把每一步做对，遇到异常时选择最小的纠偏动作，并把真实观察结果传给下一步。

## 九、第九站：SQL 由受控 MDL-SQL 层生成

模型交出的仍然是 `QuerySpec` 查询单。系统先把查询单变成只读的 `MdlQueryContract`，
再优先由确定性编译器生成 MDL-SQL。只有合同已经合法、但确定性编译器明确没有覆盖时，
才允许同一个合同交给受控 LLM 补写一次 MDL-SQL。两条路径都不能修改用户范围，也都必须
经过同一套 SQL 审计和 Wren `dry-plan`。最后仍由 Wren 展开成数据库可执行的物理 SQL。

旧代码里曾经有过“让模型直接写 SQL”的两条路，但现在都已经停用：

| 路径 | 谁生成 MDL-SQL | 谁生成最终物理 SQL | 当前状态 |
| --- | --- | --- | --- |
| 新版受控链路 | 优先确定性编译器；未覆盖时由同一合同受控补写 MDL-SQL | Wren | 当前主路径 |
| 旧版 Wren 链路 | 以前由模型按 `sql_mdl.md` 写 | Wren | 入口抛 `LegacyQueryChainDisabled`，提示词已删除 |
| 旧版物理 SQL 链路 | 以前由模型按 `sql_physical.md` 直接写物理 SQL | 没有 Wren 这一层 | 入口抛 `LegacyQueryChainDisabled`，提示词已删除 |

下面只讲当前真正运行的新版受控链路。

### 9.1 代码把查询单翻成中间 SQL

先看谁在什么时候拼。`backend/app/query/compiler.py` 的 `compile_query()` 负责判断这次走哪条道：

如果用户在确认卡上选了现成模板，就走模板执行器，直接拿那条模板 SQL 执行。没选模板，就走 Wren 执行器。

`backend/app/query/spec_mdl.py` 的 `compile_spec_mdl()` 现在只是兼容入口，内部转交给
`backend/app/query/mdl_sql/compiler/pipeline.py`。真正的工作分成合同构建、并行事实视图、
确定性编译、受控补写、统一审计和 Wren 展开几层。

#### 查询单长什么样

假设用户问"按路线名称统计每类病害有多少处"，模型交出的查询单可以简化成：

```json
{
  "subject": "disease",
  "view": "distribution",
  "metrics": ["count"],
  "dimensions": ["problem_type_name", "route_name"],
  "filters": []
}
```

查询单没有写：

- `SELECT` 后面放什么 SQL 表达式。
- `FROM` 哪张物理表。
- `JOIN` 哪张表。
- `GROUP BY` 哪个字段。
- 最后应该给哪个别名。

它只表达业务要求：查病害，按病害类型和路线分组，每组数数量。

#### 代码怎么把查询单拼成 MDL-SQL

当前链路按下面的顺序处理：

1. 校验 QuerySpec 的主体、字段、枚举、指标、范围和视图形状。
2. 把 QuerySpec 投影成 `MdlQueryContract`，冻结合同哈希。
3. 同时构建三份互补上下文：`business_capability`、`mdl_subset` 和
   `assist_evidence`；关系子图直接来自 Wren MDL。
4. 确定性编译器按合同生成 `SELECT`、`FROM`、`JOIN`、`WHERE`、`GROUP BY`、
   `ORDER BY`、`LIMIT`。
5. 确定性编译器没有覆盖时，受控 LLM 只能使用同一合同和三份上下文补写一次 MDL-SQL。
6. 两条路径都必须经过同一套 SQL AST 审计和 Wren `dry-plan`，任何一步失败都不能
   被当成成功。

其中 `business_capability` 和 `mdl_subset` 是并行互补的两套事实，不是“谁优先”
或“谁失败才使用谁”：

- `mdl_subset` 来自 Wren MDL，负责模型名、真实列名、计算列、cube 指标和 23 条关系拓扑。
- `business_capability` 来自 `resources/capabilities/`，负责巡检业务字段标签、
  枚举、指标口径、实体层级、业务断言和受控谓词。
- `assist_evidence` 来自配置化口语规则，负责提供 `trusted=false` 的候选线索，
  帮助模型理解“第三车道”这类说法，但绝不能直接决定 SQL。

代码启动时会读取当前数据库对应的全部 MDL 模型。MySQL 的 18 个模型及相关关系会自动
进入能力注册表；`subjects.yaml` 只负责业务主体、MAIN TABLE 和 MDL 模型名的映射，
不再保存第二份 JOIN 链路。两套来源出现同名指标时，不静默覆盖：能证明公式和单位一致
就合并可用视图与关联依赖；公式或单位冲突就返回结构化证据并停止。

代码仍会显式加入有效数据条件，例如病害主体的 `disease.del_flag = 0`。这条默认规则
来自能力注册表和 MDL 事实，不是 Wren 临时加的，也不是模型自己想的。

例如最后可能得到：

```sql
SELECT
  disease.problem_type_name AS 病害类型,
  disease.route_name AS 路线名称,
  COUNT(*) AS 数量
FROM disease
WHERE disease.del_flag = 0
GROUP BY
  disease.problem_type_name,
  disease.route_name
ORDER BY 数量 DESC
```

或者当字段需要路线台账时：

```sql
SELECT
  route.level AS 道路等级,
  COUNT(*) AS 数量
FROM disease
JOIN route ON disease.routes_id = route.id
WHERE disease.del_flag = 0
GROUP BY route.level
```

这里注意三件事：

- `disease`、`route` 是 Wren 的模型名，不一定等于数据库物理表名。
- JOIN 不是模型临时写的，而是代码确定性生成的。
- MDL-SQL 里的 `del_flag = 0` 来自 `compile_spec_mdl()`，不是 Wren 猜出来的。

#### 为什么不再按主体写 if/elif

主体差异只通过配置事实和 MDL 事实表达：

- QuerySpec 的 `subject` 决定最终主体和根业务对象。
- `subjects.yaml` 把主体映射到 `mdl_model`，不再承担 JOIN。
- `MdlQueryContract` 把字段、指标、过滤、输出和排序绑定到合同。
- 确定性编译器只消费合同，不再针对 `disease`、`patrol`、`section` 等主体分别写拼接分支。
- 关系路径从 MDL 的 `relationships` 中计算，唯一路径才自动使用，多路径返回结构化歧义。

因此新增一个 MDL 模型时，不需要再加一段 Python 主体分支；未登记过的模型也会作为
MDL-only 主体继承到能力注册表。业务上暂时没有口径的模型仍会明确提示能力边界，
不会因为“能连表”就假装业务规则已经完整。

#### 不用 LLM，代码到底怎么知道该不该 JOIN

可以把它想成“业务字段说明书 + MDL 关系地图”。以
`disease JOIN route ON disease.routes_id = route.id` 为例：

1. 模型给的查询单里选了 `route_name` 或 `route_level` 这类字段。
2. 字段目录 `resources/capabilities/fields.yaml` 给这些字段标了
   `requires_join: [route]` 或具体关系 ID。
3. 合同构建器把业务绑定需要的模型或关系记录到合同。
4. 关系子图只从 Wren MDL 的 `relationships` 中取边；如果同一目标存在多条语义不同的
   路径，系统直接返回 `relationship_path_ambiguous`，不交给模型猜。
5. 确定性编译器按唯一关系边的 `field_pairs` 和 `cardinality` 生成 JOIN 或 `EXISTS`。

如果主体是巡检任务，代码不会直接拿 `patrol` 去拼一个不存在的路线字段，而是生成明确的两跳关系：

```sql
FROM patrol
LEFT JOIN patrol_route ON patrol_route.patrol_id = patrol.id
LEFT JOIN route ON patrol_route.routes_id = route.id
```

这些关联不再写在 `subjects.yaml`，也不再由各主体的 Python 分支手写 `ON` 片段。
模型、字段对、连接方向和基数都来自 Wren MDL；业务字段只引用关系名或目标模型。
所以这里不是“Wren 看到两个 id 就自动猜 JOIN”，而是业务能力声明依赖、MDL 提供唯一
关系事实、合同和审计共同限制可用 JOIN。

这段 SQL 叫中间 SQL，或者 MDL-SQL。它可以被人读懂，也可以交给 Wren 编译，但还不是数据库最后执行的那一段物理 SQL。

### 9.2 Wren 把中间 SQL 翻成真 SQL

Wren 是这一层的“翻译器加装配工”。它读的是 Wren 项目里的 MDL 定义，知道：

- `disease` 这个逻辑模型由物理表 `ai_problem` 构造出来。
- `route` 这个逻辑模型由物理表 `basic_facilities_routes` 构造出来。
- `disease.route_name` 不是物理表里的普通列，而是在 `ref_sql` 里通过 `routes_id` 查路线简称得到的。
- `disease.problem_type_name` 是通过病害字典关联出来的中文类型。
- `route.route_length_km` 是根据路线起止桩号或下属路段长度计算出来的。
- `disease.routes_id = route.id` 是已登记的业务关系，不是随便找两个同类型字段就能连接。

编译入口在 `backend/app/services/wren_engine.py`，核心函数是 `compile_mdl_sql_verbose()`。它大致做这些事：

1. 检查输入是不是本项目的 MDL-SQL，而不是已经写好的物理 SQL。
2. 检查 SQL 引用的是不是本项目认识的模型。
3. 用 `relationships.yml` 校验每个 JOIN 的字段对是否合法。
4. 把逻辑 SQL 交给 Wren 的 `dry_plan()`。
5. Wren 把模型名、计算列、`ref_sql` 和逻辑 JOIN 展开成当前数据库方言的真实 SQL。
6. 如果失败，把具体编译错误带回来，而不是只回一个空结果。

要特别纠正一个容易误解的说法：**Wren 不是看到两张表就自己猜 JOIN**。业务能力配置
声明字段或指标依赖哪个关系，MDL 提供合法的模型、字段对、连接方向和基数，合同与 SQL
审计决定这次查询能不能使用该关系。Wren 的职责是把已经写好的逻辑模型 SQL 展开、编译成
物理 SQL，并在编译过程中继续检查模型和字段。

### 9.3 中间 SQL 和真 SQL 到底差在哪

| 对比项 | 中间 SQL（MDL-SQL） | 真 SQL（物理 SQL） |
| --- | --- | --- |
| 面向谁 | 面向 Wren 和项目的逻辑模型 | 面向 MySQL 等真实数据库 |
| 表叫什么 | `disease`、`route` 这类模型名 | `ai_problem`、`basic_facilities_routes` 这类物理表名 |
| 字段叫什么 | `route_name`、`route_length_km` 这类业务字段 | 实际列、子查询、`CASE`、JSON 提取后的表达式 |
| JOIN 来自哪 | 合同引用业务依赖，关系边来自 Wren MDL，代码按唯一子图生成逻辑 JOIN | Wren 按 MDL 和关系定义展开成物理 JOIN |
| 能不能直接给数据库执行 | 通常不能，数据库不认识逻辑模型 | 可以 |
| 谁来生成 | 优先确定性编译器；明确未覆盖时才由同一合同受控补写 | Wren 根据 MDL 展开 |
| 适合谁看 | 开发者查看查询结构、字段和关系 | DBA 或数据库执行器 |

用生活里的例子说：

```text
QuerySpec：我要“按路线统计病害数量”
  ↓ 代码翻译
MDL-SQL：按项目内部菜单写成“disease 模型，按 route 模型分组”
  ↓ Wren 翻译
物理 SQL：写成数据库真正认识的 ai_problem、basic_facilities_routes、子查询和 JOIN
```

这三层不是重复写三遍，而是每层负责不同的事：

- `QuerySpec` 负责业务意图。
- MDL-SQL 负责项目内部统一的数据模型表达。
- 物理 SQL 负责数据库方言和真实表结构。

### 9.4 MDL 语义层以前是给模型看的，现在还有什么用

历史上，旧链路会把 MDL 的模型、字段、关系和示例交给大模型，让模型直接写中间 SQL。那时 MDL 的一个重要作用确实是“给 LLM 看”。现在旧提示词和旧 SQL 生成入口都已停用。

新版受控链路里，主 SQL 不再由 LLM 写，但 MDL 不但没有失业，反而成了底层基础设施。它现在至少有五个作用：

1. **字段触达**：字段目录会把 MDL 里声明、但物理表没有的计算列并进来。这样第三站能看见 `route_length_km`、`section_length_km`、`route_name` 这类语义字段，不会误判成“库里没有这一列”。
2. **逻辑模型到物理表映射**：代码写 `disease`，Wren 必须依靠 MDL 知道它对应 `ai_problem`。
3. **计算字段展开**：`route_name`、`problem_type_name`、`route_length_km` 这些业务字段，需要 MDL 里的 `ref_sql` 或计算表达式展开。
4. **JOIN 关系校验**：`relationships.yml` 决定 `disease.routes_id = route.id` 这类关系是否合法，防止随便猜外键。
5. **物理 SQL 编译**：Wren 最后把中间 SQL 变成真 SQL，靠的就是 MDL。

这里要补一句容易被误解的话：当前主链**不是**把整份 MDL 原样塞给 `query_spec.md` 让模型照着写 SQL。模型拿到的是经过整理的字段目录、能力清单、物理字段和候选证据；MDL 主要是在代码侧被字段目录读取，在编译侧被 Wren 使用。也就是说，MDL 现在从“模型直接照着写的 SQL 说明书”，变成了“系统内部多处共同依赖的事实底座”。

所以现在的主次关系是：

```text
历史旧链路（已停用）：
MDL → 给 LLM 当资料 → LLM 写 MDL-SQL → Wren 编译成物理 SQL

新版主链路：
MDL → 给字段目录、字段触达、JOIN 契约和 Wren 编译器使用
QuerySpec → 代码写 MDL-SQL → Wren 编译成物理 SQL
```

MDL 现在仍然非常有用，而且不能删。区别只是：它从“主要喂给模型看的说明书”，变成了“字段目录、代码、关系校验器和 Wren 共同使用的语义底座”。

还要把两类配置分开看：

- `resources/capabilities/*.yaml` 是项目的“业务能力清单”，告诉规划器哪些字段、指标、视图可用，哪些字段需要 JOIN。
- `wren_projects/road_mysql/*` 是“逻辑模型到物理数据库的说明书”，告诉 Wren `disease` 对应哪张表、`ref_sql` 怎么算、关系字段是什么。

两者配合，才完成从业务查询单到物理 SQL 的翻译。少了 MDL，字段目录看不见计算列，Wren 也不知道 `disease` 背后是 `ai_problem`，更无法展开 `route_name`。

### 9.4.1 Wren 复用边界

Wren 在这一层复用四类结构能力：

1. MDL 模型、真实列和计算列；
2. 关系拓扑及其唯一关系子图；
3. `dry-plan` 的结构校验和物理方言展开；
4. MDL-SQL 到真实数据库 SQL 的编译。

复用不等于让 Wren 拥有业务裁决权。QuerySpec 仍然决定用户范围、主体、指标、维度和
过滤；冻结合同固定本次允许使用的字段和关系；统一 SQL 审计检查只读、软删除和范围；
`dry-plan` 只证明逻辑 SQL 能展开，不证明它回答了用户问题。Wren 不能绕过这些前置
权威，也不能把失败的合同偷偷改写成另一条查询。

只有确定性编译器明确返回 `compiler_not_covered` 时，受控 LLM MDL-SQL 才能使用同一
份 MDL 子集和业务能力上下文补写一次；补写结果仍走同一合同、审计和 `dry-plan`。

### 9.5 真实的 SQL 长什么样

这道题最后执行的 SQL 是这样的，截取主干：

```sql
WITH disease AS (
  SELECT ... FROM (
    SELECT ai_problem.*,
      CAST(JSON_EXTRACT(pic_position, '$.confidence') AS DECIMAL(10, 6)) AS confidence,
      (SELECT r.short_name FROM basic_facilities_routes AS r
        WHERE r.id = ai_problem.routes_id LIMIT 1) AS route_name,
      (SELECT b.problem_type FROM ai_problem_base AS b
        WHERE b.id = ai_problem.problem_base_id
          AND NOT b.problem_type IS NULL LIMIT 1) AS problem_type_name,
      (CASE ai_problem.categories_type
        WHEN '0' THEN '路面病害'
        WHEN '5' THEN '路基病害'
        WHEN '10' THEN '沿路设施'
        WHEN '15' THEN '交安事件'
        ELSE ai_problem.categories_type END) AS category_name
    FROM ai_problem
  ) AS __source
),
route AS ( ... )
SELECT COUNT(*) AS 病害数量
FROM disease JOIN route ON disease.routes_id = route.id
WHERE disease.del_flag = 0
  AND route.id = '1b0b4a9f700477b1d96119caac87c168'
  AND disease.problem_type_name = '泛油'
  AND disease.collection_time >= '2026-11-02 00:00:00'
  AND disease.collection_time < '2026-11-03 00:00:00'
```

逐段看，每一段都能对上前面某一步。

`WITH disease AS` 这一段，是 Wren 根据 MDL 里 `disease` 模型的 `ref_sql` 展开出来的。`route_name` 这个字段在物理表里根本不存在，`ref_sql` 会拿 `routes_id` 去路线表查简称；`problem_type_name` 也不存在，`ref_sql` 会拿 `problem_base_id` 去病害字典表查中文类型。模型只写了“我要 `route_name` / `problem_type_name`”，并没有写这些子查询。

`CASE ai_problem.categories_type` 这一段，是把数字代码翻成中文。库里存的是 0、5、10、15，直接给用户看就是四个数字。

`WHERE` 这一段，五条条件一一对应第五站那四条过滤加一条默认规则。`del_flag = 0` 是 `compile_spec_mdl()` 生成 MDL-SQL 时显式加上的，模型没写，Wren 也没有替模型发明这条业务规则。`route.id = '1b0b4a9f...'` 是第五站 `route_name` 那条过滤翻译出来的，用户说的是西乡段，代码查路线台账后变成了 ID。`problem_type_name = '泛油'` 是病害类型那条过滤。

看到这里应该能明白一件事：从"西乡段"到 `'1b0b4a9f700477b1d96119caac87c168'`，中间隔着路线台账的一次查询。这个查询不是模型做的，是代码做的。

## 十、第十站：拿这张表去执行

执行在 `backend/app/query/executor.py`。

代码只做三件事：算一个 SQL 的指纹，拿去执行，把结果包成一个观察对象。

指纹是给结果做身份证的。同一个 SQL 再跑一次，指纹一样，就可以确认"这次的结果和上次是同一口径出来的"，而不是偷偷换了条件。

观察对象里有几样东西：行数、列名、前几行预览、完整结果、有没有被截断。

这道题返回了 0 行。

## 十一、第十一站：两道检查

返回 0 行，这时候有两种可能：一种是真的没有，一种是条件写错了或者数据没覆盖到。这两种对用户的意义完全不同，不能混成一句"0 处"。

### 11.1 代码检查

`backend/app/query/verifier.py`，纯代码，两个检查器：语义检查器和展现检查器。

语义检查器看的是"这个结果有没有背叛用户的范围"。比如用户要的是按路线分组，结果返回了一行不分组的数，那就是背叛。

展现检查器看的是"这个结果能不能正常呈现"。比如要明细却只有一列，那就是有问题。

这道题还多做了一件事，叫时间覆盖检查。代码去查了这条路线的病害记录实际分布在什么时间，查出来是 2026-07-15 02:10 到 2026-10-26 16:31。

用户问的是 11 月 2 日。11 月 2 日在覆盖范围之外。

所以答案是这么写的：

> 该查询范围内没有匹配记录，并且它超出这份台账的真实数据覆盖：宝安大道西乡段现有病害记录的采集时间在 2026-07-15 02:10 至 2026-10-26 16:31。因此这一问无法给出数值。

这句话跟"0 处泛油"差得很远。前者告诉你"这个时间点数据里根本没有，别拿这个数去做判断"，后者会让你以为那天真的没问题。

这是这一轮修复里最值钱的一条。返回 0 比报错更坏，因为 0 看起来像个正经答案。

### 11.2 模型裁判

代码查完以后，如果反思开关开着，还会叫一次模型。

`verify_answer.md`，调用点是 `nl2sql.verify_answer()`，由单轮结果组装和反思检查触发，用校验模型。

它看四样东西：问题原文、SQL、返回的列和行、系统准备说出口的那段回答。

它要判断的是"这段回答有没有答到点上"。比如用户问"哪条路最多"，回答里给了一个数但没说路名，那就是答非所问。

判得不对，会生成一个复核入口挂到回答上，用户在界面上点"答错了"，就走修复流程。

这个模型跟第六站那个复查模型是两个不同的关口：第六站查的是"计划写得对不对"，第十一站查的是"结果答得对不对"。一个在查库之前，一个在查库之后。

## 十二、第十二站：把结果组织成人话

回答组装主要由 `backend/app/query/service.py` 里的 `_answer_text()`、`_data_answer_text()` 和 `assemble_answer()` 完成，纯代码。

它拿查询单、观察对象、检查结果，拼出一段话。拼的规则按视图分：计数视图说"多少"，列表视图说"共多少条，前几条是什么"，趋势视图说"从哪涨到哪"。

有两个细节。

一个是加入沿用的条件。如果这一步用了上一步的结果当过滤条件，回答里必须写明"本次结果沿用了上一节点筛选出的条件：路线 长沙－芷江高速公路"。不写的话，用户只看到一堆桩号，不知道是哪条路的桩号。

另一个是分组枚举的完整性。当前代码会调用枚举补全和 `missing_explicit_top_group_labels()`：用户明确点名了“上下行、病害类型”等封闭维度时，如果结果里缺少某个合法分组，系统可以补出可确定的零值分组；TopN 后又不能把合成行硬塞进排名，所以缺失的请求分组会作为观察信息单独说明，避免用户把“没排进来”误读成“整个库里没有这一类”。

## 十三、当前提示词怎么分工

`prompts/` 目录当前有 28 个 md 文件，其中 `README.md` 是说明文档，不算提示词，实际是 27 个提示词文件。旧链路的 `query_semantic.md`、`table_selector.md`、`sql_mdl.md`、`sql_physical.md`、`optimize_question.md` 已删除。

### 第一组：单轮查询主链

| 文件 | 干什么 |
| --- | --- |
| `intent.md` | 判断问题属于数据、分析、知识、图片、复合题还是元数据 |
| `subject_router.md` | 有几个候选主体时，决定当前问题以谁为主 |
| `query_spec.md` | 看完整原问题、字段目录、能力清单和候选便签，交出一张查询单 |
| `query_spec_audit.md` | 拿另一个模型复查查询单，找漏字段、错条件、错视图 |
| `mdl_sql_generator.md` | 确定性编译器明确没覆盖、但冻结合同已合法时，受控补写一次 MDL-SQL |
| `verify_answer.md` | 拿到结果后检查回答有没有答非所问 |

这六个是单轮数据题常见的模型关口。`subject_router.md` 不是每次都调用，只有主体确实拿不准时才上；`mdl_sql_generator.md` 也不是首选，只有确定编译器明确报“未覆盖”时才走一次。

### 第二组：修复与多步编排

| 文件 | 干什么 |
| --- | --- |
| `query_spec_repair.md` | 查询单被代码指出具体毛病后，只对那几个路径打补丁，不重写整份单子 |
| `planning.md` | 把“先查 A，再查 B，最后比较”拆成多步计划 |
| `repair_plan.md` | 计划静态检查不通过时，带着具体问题让规划器重排 |
| `react_controller.md` | ReAct 某一步出现“可修异常”时，选择补证据、重试、追问或停止 |

`query_spec_repair.md` 走最小补丁路线，提示词里规定每个 JSON 路径最多一个补丁。这一轮实测里，桥梁那道题就是因为修复器连续提交相同补丁被代码判停，报出 `duplicate repair patch`。

ReAct 正常执行时，第二组只会先用到 `planning.md`；后两个不是每步都调用。静态契约直接判非法，或者失败不可重试时，代码会直接停，不浪费一次控制器调用。

### 第三组：其他入口

| 文件 | 干什么 |
| --- | --- |
| `knowledge.md` | 资料库问答，不查业务库 |
| `metadata.md` | 问库结构，比如“有哪些表” |
| `datasource.md` | 判断该去哪个数据源 |
| `dialogue_understanding.md` | 多轮对话补全，把“那那条路呢”补成完整问题 |
| `example_direct_match.md` | 判断当前问题能不能直接复用历史示例 |
| `bucket_basis.md` | 判断分段依据，比如按公里还是按时间 |
| `fix_sql.md` | SQL 执行报错后，基于真实错误修复 |
| `repair_presentation.md` | 结果展示坏了，修展示层 |
| `table_analysis.md` | 对单表做解释和分析 |
| `analysis.md` | 分析类问题的结论生成 |
| `result_summary.md` | 把结果表压成一段中文摘要 |
| `followup_suggestion.md` | 生成回答后的追问建议 |

这些文件是“其他门”，不是 QuerySpec 主链的备胎。`analysis.md`、`result_summary.md`、`followup_suggestion.md` 只影响话怎么说，不负责决定查哪些字段。

### 第四组：离线沉淀模板

| 文件 | 干什么 |
| --- | --- |
| `templatize_sql.md` | 从成功 SQL 中识别可替换的值，生成模板骨架 |
| `templatize_classify.md` | 判断一条 SQL 值不值得沉淀成模板 |
| `template_review.md` | 对沉淀出的模板再做一次检查 |

这条线在后台运行，不占在线查询的主等待时间。

### 第五组：评测

| 文件 | 干什么 |
| --- | --- |
| `promotion_exam_generate.md` | 给模板或链路生成考卷 |
| `query_holdout_judge.md` | 判卷、对比改动前后效果 |

一句话记忆：**单轮主链 6 个，修复与多步 4 个，其他入口 12 个，离线模板 3 个，评测 2 个，合计 27 个提示词；再加上 README，目录里一共 28 个 md。**

## 十四、为什么代码里还能看到旧链路

看到 `nl2sql.py` 里还有 `shape`、`subject`、`slots`、`route_match`、`semantic_conditions` 这些结构，容易以为项目同时开着两套查询引擎。实际不是。

### 旧实现还留着代码，但入口已停用

旧版计划结构主要来自 `backend/app/services/nl2sql.py`：

- `build_query_plan()` 过去负责生成旧版 `plan`。
- `select_tables()` 过去负责让模型选表。
- `generate_mdl_sql()` 过去负责让模型写 MDL-SQL。
- `generate_sql()` 过去负责让模型直接写物理 SQL。

现在这些函数已经不是“失败后自动兜底”，而是入口处直接调用 `raise_disabled()`。对应的旧提示词也已从 `prompts/` 删除。保留这些代码主要是为了历史逻辑、对照和后续安全清理，不代表在线主流程还会走到那里。

### 当前跑的是哪条

`agent.py` 的 `_handle_message_entry()` 先调用 `_maybe_single_turn_compiler()`。开关打开后，数据、分析、复合题会进入 `start_single_turn()`，后面的主流程是：

```text
完整问题
  ↓
意图、主体、字段触达
  ↓
query_spec.md 生成 QuerySpec
  ↓
query_spec_audit.md 复查
  ↓
resolve_templates() 检查模板
  ├─ 有候选：弹确认卡，用户选择后按候选执行
  └─ 无候选 / 用户选 AI：继续确定编译
  ↓
compile_spec_mdl() 生成 MDL-SQL
  ↓
Wren 编译成物理 SQL
  ↓
执行、校验、组织回答
```

如果合同合法、但确定性编译器明确没覆盖，才会在同一个冻结合同下让 `mdl_sql_generator.md` 补写一次 MDL-SQL；补写结果仍要过同一套 SQL 审计和 Wren 校验。如果合同本身无法编译，系统会返回明确的受控失败原因，不会再偷偷切到旧链路。如果意图不是数据类，才会进入知识、图片、元数据、复合题等其他专用分支。

### 最常见的一句总结

**模型负责理解业务意图和生成查询单；代码负责把查询单翻译成确定的 MDL-SQL；Wren 负责按 MDL 把 MDL-SQL 编译成物理 SQL；数据库只执行最后的物理 SQL。**

## 十五、稳定性到底从哪来

这是你真正想搞清楚的东西。一条链路能稳住，不是因为模型好，是因为四道锁。

### 第一道锁：模型不许发明名字

模型能用的字段名，是从物理视图里贴给它的。它只能用清单里的。它想用清单外的，第七站直接报错。这一条把"编字段"这个最常见的错堵死了。

### 第二道锁：模型不许碰语法

新版受控链路里，MDL-SQL 是代码拼的。模型不知道括号怎么配、JOIN 怎么写、子查询怎么套。它只需要说清楚“用哪个字段、怎么比、比什么值”。代码再根据 `requires_join` 生成逻辑 JOIN，Wren 负责把逻辑 SQL 编译成物理 SQL。

### 第三道锁：模型不许决定翻译

"西乡段"翻成哪个 ID，"上行"翻成 1 还是 2，这些不由模型决定。模型只给原文，代码去台账和字典里查。查不到就报错，不硬编。

这一条特别关键。模型编一个 ID，SQL 不报错，返回 0 行，没人发现。代码查不到就报错，用户立刻知道这条问不了。

### 第四道锁：0 行要解释

返回 0 行的时候，不会直接说"0 处"。会说清楚为什么是 0：条件本身没匹配，还是这个时间段根本没数据。

没有这一条，前面三道锁都白搭，因为最后一步会把所有错误包装成一个看起来正常的 0。

### 四道锁之外还剩什么风险

还剩三类，必须承认。

第一类，字段选对了但语义选错了。比如"长度"这个指标，库里有两个字段都能算长度，选错一个数字就对不上。这类错误四道锁都拦不住，只能靠考试和人工复核发现。

第二类，条件都在但漏条件。用户说了三个条件，模型只写了两个，第七站查不出来，因为漏掉的条件本来就不在查询单里。

第三类，数据本身的问题。比如路线台账里有六条同名的"未知路线"，按路线汇总会把数字翻倍。这不是模型的问题，是数据治理的问题。

面试时把这三类主动说出来，比说"我们能保证准确"可信得多。

## 十六、这套东西的边界

最后说清楚做不到什么，免得面试被追问时尴尬。

单表查询可以做到很准。一张表、字段清楚、条件明确，基本不会错。

多表关联才是真难。难在三个地方。

第一，同名字段到处都是。路线表有 `name`，路段表有 `name`，病害表也有路线名字段。模型看到一个"name"，不知道是哪张表的。

第二，同一个业务概念有好几种算法。路线长度可以按自身桩号差算，也可以按下属路段汇总算，两个结果差很多。库里没有唯一口径，代码只能定一个默认，用户不认就吵。

第三，数据本身脏。同一批巡检记录挂在一个叫"未知路线"的占位 ID 上，这个 ID 有六条同名记录。按路线汇总和按路段汇总是两个不同的数。

这三件事决定了"十张表以上的自然语言查询"没有百分百准确这回事。能做到的是：错了要能被发现，发现了要能说清楚错在哪，不能悄悄错。

这也是为什么这个项目花在检查、报错、确认卡上的代码，比花在生成上的代码多。
