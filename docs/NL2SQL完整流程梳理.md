# NL2SQL 完整流程梳理（2026-09-20 智能化升级版）

> 本文档基于当前代码逐行阅读整理，覆盖从问题输入到输出回答的所有分支情况。
> 核心变化：从"执行流水线"升级为"会思考的智能体"——加了任务规划、反思自检、后续建议三个新环节。

---

## 一、总流程图

```
用户问题输入
   ↓
┌─────────────────────────────────────────────────┐
│ 1. 问题改写归一化（query_rewrite.normalize）    │
│   - 去掉多余空格、统一标点、简化口语化表达       │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 2. 新话题判断（is_fresh_topic）                 │
│   ├─ 是新话题 → 清掉历史上下文                  │
│   └─ 不是 → 继续下一步                          │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 3. 长对话对话理解（contextualize）               │
│   ├─ 继承上下文 = false → 直接用原问题          │
│   ├─ 是追问/纠正/质疑 → 补全成完整问题          │
│   └─ 新话题 → 直接用原问题                      │
│                                                 │
│   升级：从"条件补全"升级到"对话理解"：           │
│   - 识别对话主题                                │
│   - 判断和历史的关系（继承/追问/纠正/换话题）    │
│   - 丢过上一轮窄口径（用户重新划范围时）         │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 4. 意图分类（classify_intent）                   │
│   ├─ knowledge → 走知识问答路径                  │
│   ├─ image → 走图片查询路径                     │
│   ├─ composite → 走复合问题路径                 │
│   ├─ data / analysis → 走数据查询路径           │
│   └─ 其他 → 默认 data                           │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 5. 跨库判断（cross_db.db_scope）                 │
│   ├─ 跨多个库 → 必须走复合问题路径              │
│   └─ 单库 → 继续下一步                          │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 6. 模板快速通道总闸                              │
│   ├─ 模板能生成SQL → 不走拆分，直接查           │
│   └─ 模板不能 → 走任务规划                       │
│                                                 │
│   为什么有这一步：简单问题不用走LLM规划，省成本 │
│   比如"有多少处"这种简单查询，直接用模板2秒出结果 │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 7. 任务规划（orchestrator.decompose）            │
│   ├─ 【LLM 优先】planning 提示词                │
│   │   - 先想清楚：要回答这个问题需要做哪几步？    │
│   │   - 每一步是查数据？查知识？还是综合分析？    │
│   │   - 最后必须有一步是综合分析（升级点）        │
│   │                                             │
│   └─ 【规则兜底】LLM 不可用时                   │
│       - 按连接词/问号切句子                      │
│       - 每个片段补全上下文                        │
│                                                 │
│   升级：从"拆分句子"升级到"任务规划"            │
│   以前：按"分别/问号"机械切开                    │
│   现在：先想清楚要做哪几步，每步为了什么         │
└─────────────────────────────────────────────────┘
   ↓
┌───────────┬───────────┐
│           │           │
单查询路径   复合问题路径
```

## 二、单查询路径：_build_query_result

```
单查询路径（_build_query_result）
   ↓
┌─────────────────────────────────────────────────┐
│ 1. 确定数据库类型（cross_db.resolve_db_kind）   │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 2. 桩号解析检查（clarify.has_unparsed_spatial）  │
│   ├─ 有空间词但没解析出桩号 → 追问用户          │
│   └─ 能解析 → 继续下一步                        │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 3. 构建查询计划（build_query_plan）              │
│                                                 │
│   ├─ 实体抽取（规则）：                          │
│   │   ├─ 路线识别（_route_matches）             │
│   │   ├─ 桩号解析（parse_pile_range）          │
│   │   ├─ 病害类型匹配（_resolve_damage_type）    │
│   │   ├─ 时间范围解析                            │
│   │   └─ 设备号解析                              │
│   │                                             │
│   └─ 维度识别（LLM parse_semantics）：           │
│       ├─ shape（count/distribution/list/top/bucket_compare） │
│       ├─ group_by（direction/month/damage_type） │
│       ├─ metrics（count/total_area/avg_area）   │
│       ├─ order_by（排序方式）                    │
│       ├─ derived（密度/间距/占比）              │
│       └─ output_fields（要SELECT哪些字段）       │
│                                                 │
│   失败/超时 → 退回规则结果                       │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 4. 检索上下文（retrieve_query_context）          │
│   ├─ RAGFlow 检索 SQL 示例                      │
│   └─ schema 信息                                 │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 5. 分组歧义检查（ambiguous_grouping_reason）     │
│   ├─ 有"分别/各"但识别不出分组维度 → 追问用户   │
│   └─ 能识别 → 继续下一步                        │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 6. 范围校准（calibrate.check）                   │
│   ├─ 桩号/时间超出实际数据范围 → 直接返回提醒    │
│   └─ 在范围内 → 继续下一步                      │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 7. SQL 生成：三级降级策略                        │
│                                                 │
│   ├─ 【第一级】模板快速通道                      │
│   │   ├─ 条件：简单单条件查询（is_simple_single_query） │
│   │   ├─ build_template_sql(plan)              │
│   │   └─ 成功 → 执行，engine="template"         │
│   │                                             │
│   ├─ 【第二级】Wren 语义层                      │
│   │   ├─ 条件：wren_engine.available(kind)      │
│   │   ├─ generate_mdl_sql → LLM 写 MDL-SQL     │
│   │   │   └─ 输入：问题 + MDL上下文 + 必须条件   │
│   │   │       + RAGFlow examples                │
│   │   ├─ compile_mdl_sql → Wren 编译成物理 SQL   │
│   │   ├─ validate_semantics(check_shape=False)  │
│   │   └─ 成功 → 执行，engine="wren"             │
│   │                                             │
│   └─ 【第三级】内置 LLM（Wren 失败后）           │
│       ├─ generate_with_context → LLM 写物理 SQL  │
│       ├─ validate_semantics(check_shape=True)    │
│       ├─ 执行 SQL                                │
│       ├─ _is_collapsed_comparison → 检查对比塌缩 │
│       └─ 重试 retry_limit 次                     │
│                                                 │
│   升级：模板从"第三级兜底"变成"第一级快速通道"   │
│   为什么：简单问题2秒出结果，不用花LLM的钱       │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 8. 全失败处理                                    │
│   ├─ 两个引擎都说"信息不足" → 追问用户          │
│   ├─ SQL 执行报错 → 如实说"SQL 跑不通"          │
│   ├─ 条件校验没过 → 说"条件校验没过"            │
│   └─ 对比类问题没跑通 → 说"对比对象没对齐"      │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 9. 结果校验（verify_answer）                     │
│   ├─ 对 → 结果解读 → 返回用户                   │
│   └─ 错 → 问题优化 → 重新生成（最多3次）        │
│                                                 │
│   校验规则（8条）：                              │
│   1. 聚合 vs 明细                                │
│   2. 分组识别                                    │
│   3. 字段匹配                                    │
│   4. 主体匹配                                    │
│   5. 单位匹配                                    │
│   6. 维度完整性（有没有漏维度）                  │
│   7. 指标口径一致性（范围对不对）                │
│   8. 推理/结论是否到位（reasoning_insufficient） │
│                                                 │
│   升级：判断类问题即使只回一个数也不跳过校验     │
│   以前：单值结果直接跳过校验                     │
│   现在：评价/判断类问题必须过校验               │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 10. 结果后处理                                   │
│   ├─ 图表分析（analysis_service.analyze）       │
│   ├─ 结果摘要（_summarize_result）              │
│   ├─ 一行多列兜底（_ensure_all_values_reported） │
│   ├─ 后置计算（_difference_conclusion）          │
│   ├─ 三元组 spec（plan_to_spec）                │
│   ├─ 理解置信度打分（interpretation_scores）     │
│   └─ engine 标签（template / wren / llm）        │
│                                                 │
│   升级：明细/清单/看图问题不做极值结论           │
│   以前：明细后面硬加"最多/最少"的结论           │
│   现在：要明细就老老实实返回清单，不瞎总结      │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 11. 反思自检（_reflect_check_step）【新增】      │
│   ├─ 对 → 继续下一步                            │
│   └─ 发现问题 → 改进回答                         │
│                                                 │
│   检查什么：                                    │
│   1. 逻辑自洽：数字前后一致吗？                 │
│   2. 数据支撑：结论有数据支撑吗？               │
│   3. 完整性：该说的都说了吗？                   │
│   4. 合理性：结论合理吗？                       │
│                                                 │
│   和 verify_answer 分工：                       │
│   - verify_answer 管"答没答到点"               │
│   - reflect_check 管"回答本身合不合理"         │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 12. 后续建议（_followup_step）【新增】           │
│   └─ 回答完了之后，主动给2~3个后续建议          │
│                                                 │
│   为什么加这个：从"查询机器"变成"顾问"          │
│   以前：用户问什么就答什么                       │
│   现在：回答完了主动引导用户下一步              │
└─────────────────────────────────────────────────┘
   ↓
返回用户
```

## 三、复合问题路径：_handle_composite

```
复合问题路径（_handle_composite）
   ↓
┌─────────────────────────────────────────────────┐
│ 1. 任务规划（orchestrator.decompose）            │
│                                                 │
│   ├─ 【LLM 优先】planning 提示词                │
│   │   ├─ 先想清楚：要回答这个问题需要做哪几步？    │
│   │   ├─ 每一步是查数据？查知识？还是综合分析？    │
│   │   └─ 最后必须有一步是综合分析               │
│   │                                             │
│   └─ 【规则兜底】LLM 不可用时                   │
│       ├─ 正则按连接词/问号切句子                │
│       ├─ 每个片段补全上下文                    │
│       └─ 判断子任务类型                         │
│                                                 │
│   子任务类型：                                  │
│   - data：普通数据查询                          │
│   - knowledge：知识问答                        │
│   - analysis：综合分析（专家思维四步法）        │
│   - post_calc：后置计算（差值/比较/求和）        │
│                                                 │
│   升级：从"拆分句子"升级到"任务规划"            │
│   以前：只会按句子切                            │
│   现在：会规划"查数据→查规范→综合分析"的完整链路 │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 2. 按依赖顺序执行子任务                          │
│   ├─ type=post_calc → _post_calc_payload       │
│   │   └─ 基于前序结果做计算（差值/比较/求和）    │
│   │                                             │
│   ├─ type=knowledge → _answer_knowledge         │
│   │                                             │
│   ├─ type=analysis → _analysis_payload          │
│   │   └─ 专家思维四步法：                        │
│   │       1. 看基本盘（数量/规模）              │
│   │       2. 看结构（类型/分布）                │
│   │       3. 看严重程度（密度/风险）            │
│   │       4. 下结论与建议                       │
│   │                                             │
│   ├─ 图片类 → _image_result                     │
│   │                                             │
│   └─ 其他 → _build_query_result                 │
│       └─ 子问题走 wren_first=True                │
│                                                 │
│   单个子任务失败不影响其他子任务                │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 3. 汇总所有子任务结果                            │
│   └─ 按顺序拼接回答                              │
└─────────────────────────────────────────────────┘
   ↓
┌─────────────────────────────────────────────────┐
│ 4. 反思自检 + 后续建议（和单查询路径一样）        │
└─────────────────────────────────────────────────┘
   ↓
返回用户
```

## 四、关键机制详解

### 4.1 对话理解器（升级点：从条件补全到对话理解）

**核心变化：** 以前只做"条件继承"，现在要理解整个对话的**主题、意图、关系**。

**对话关系类型：**

| 关系 | 特征 | 做法 |
|------|------|------|
| inherit | 继承上一轮条件 | 继承所有条件，只换个问法 |
| followup | 追问上一轮细节 | 继承所有条件，加新的追问角度 |
| correction | 纠正之前的说法 | 替换掉对应的条件，其他继承 |
| compare | 对比前两轮结果 | 把前两轮的答案数字带进来 |
| new_topic | 换新话题 | 不继承之前的任何条件 |

**窄口径丢弃规则：**
- 当用户自己重新划范围时（比如"给西乡段整体评价"）
- 上一轮的窄口径（比如"K0+800~K0+900"）要丢掉
- 不能硬继承，否则就变成了"给这100米做整体评价"

---

### 4.2 任务规划器（升级点：从拆分到规划）

**以前：** 拆分器只会按"分别/问号"机械切句子

**现在：** 任务规划器会先想清楚"要回答这个问题需要做哪几步"

**规划器输出的例子：**

用户问："西乡段路况好不好？不好的话该如何养护？"

规划器会输出：
```json
{
  "steps": [
    {"action": "query_data", "purpose": "查基本病害数据"},
    {"action": "query_data", "purpose": "查严重程度"},
    {"action": "query_knowledge", "purpose": "查养护规范"},
    {"action": "analyze", "purpose": "判断路况等级"},
    {"action": "analyze", "purpose": "给出养护建议"}
  ]
}
```

**为什么要这个：** 以前"给个整体评价"这类问题，拆成一堆数据查询，最后只把数字拼给用户，不会做综合判断。现在最后必须有一步是"综合分析"。

---

### 4.3 反思自检器（新增）

**和 verify_answer 的分工：**

| 模块 | 管什么 | 例子 |
|------|--------|------|
| verify_answer | 答没答到点 | 用户问了3个维度，回复只说了1个 |
| reflect_check | 回答本身合不合理 | 数字前后矛盾、结论没数据支撑 |

**反思器检查什么：**
1. 逻辑自洽：总数911，各类型加起来是不是911？
2. 数据支撑：说"路况差"，有没有数量/密度的数据？
3. 完整性：该说的都说了吗？
4. 合理性：结论合理吗？

---

### 4.4 后续建议（新增）

**为什么加这个：** 从"查询机器"变成"顾问"

**例子：**
> 用户：西乡段泛油有多少处？
>
> 系统：西乡段泛油共534处。
>
> **要不要我再帮你看看：**
> 1. 泛油在各桩号段的分布？
> 2. 和恒明珠的泛油数量对比？

---

### 4.5 SQL生成的三级降级

| 级别 | 路径 | 什么时候用 | 成本 |
|------|------|-----------|------|
| 第一级 | 模板快速通道 | 简单单条件查询 | 最低（不用LLM） |
| 第二级 | Wren语义层 | 模板匹配不上 | 中（LLM写MDL-SQL） |
| 第三级 | 内置LLM | Wren失败 | 高（LLM写物理SQL） |

**为什么模板从兜底变成快速通道：**
- 简单问题用模板2秒出结果，不用花LLM的钱
- 复杂问题还是走Wren/LLM，保证准确率

---

### 4.6 代码层面的几个修复

| 修复 | 解决了什么问题 |
|------|---------------|
| 语义字段→物理写法映射表 | 不会再写不存在的列名（problem_type_name） |
| 明细不走聚合模板 | 要明细不会再被答成总数 |
| 判断类问题不跳过校验 | 要整体评价不会再只给个数字 |
| 空结果保护 | 不会再直接崩溃（list index out of range） |
| 路线用ID不用名称 | 用简称不会再查出来0条 |
| 明细不加结论 | 明细后面不会再硬加"最多最少" |
