# 业务覆盖与抽象概念定义方案

> 解决两个问题：
> 1. 怎么做到不管怎么问，都能回答出来（业务全覆盖）
> 2. 抽象概念（老问题/新问题）不能黑盒，必须有明确定义

---

## 一、怎么做到不管怎么问都能回答出来？

### 核心思路

**把业务问题提纲拆成"标准查询模式"，让LLM不管用户怎么问，都能匹配到对应模式，然后用模板去答。**

### 第一步：拆解业务问题为标准查询模式

基于 `巡查业务问题.md`，整理出8个核心查询模式：

| 模式编号 | 模式名称 | 说明 | 举例 |
|---------|---------|------|------|
| M1 | 单维度计数 | 某条件下有多少条 | "西乡段泛油有多少处？" |
| M2 | 按维度分组统计 | GROUP BY 某个维度 | "各病害类型分别有多少？" |
| M3 | Top N 查询 | 排序后取前N | "数量最多的前3种病害？" |
| M4 | 范围筛选 + 列表 | 满足条件的明细列表 | "面积大于5㎡的病害有哪些？" |
| M5 | 时间趋势分析 | 按时间排序看变化 | "各月病害数量趋势" |
| M6 | 跨对象对比 | 多个对象横向对比 | "西乡段和恒明珠哪个密度高？" |
| M7 | 转弯计算 | 需要两步算 | 密度=数量÷长度；占比=部分÷总数 |
| M8 | 归因分析 | 为什么会这样 | "为什么数量最多的类型面积不是最大？" |

### 第二步：每个模式都写清楚"输入/输出/SQL写法"

比如 M2 按维度分组统计：
- **输入：** 分组维度（类型/上下行/月份/路段）、过滤条件（路线/时间）
- **输出：** 每组的数量、面积、占比
- **SQL写法：**
  ```sql
  SELECT 维度字段, COUNT(*) AS 数量, ROUND(SUM(area), 2) AS 总面积
  FROM disease d ...
  WHERE 过滤条件
  GROUP BY 维度字段
  ```

### 第三步：LLM 负责"听懂人话"，匹配到模式

用户不管怎么问，LLM 做两件事：
1. **识别属于哪个模式**：M1~M8
2. **提取参数**：过滤条件是什么？分组维度是什么？

然后用对应模式的SQL写法去生成查询。

### 第四步：抽象词映射表

把业务里常用的"人话"，映射到对应的模式和参数：

| 人话 | 对应模式 | 参数 |
|------|---------|------|
| 哪个最严重/养护压力大 | M6 对比 + 综合判断 | 数量+密度+面积 |
| 分散/集中 | M2 分组 + M7 密度 | 按路线分组，算密度 |
| 老问题/新问题 | M2 分组 | 按时间分两段 |
| 趋势如何/越来越多 | M5 时间趋势 | 按月份分组 |
| 靠谱吗/要复核吗 | M2 分组 | 按置信度分层 |
| 高发路段 | M2 分组 | 按桩号段分组 |

## 二、抽象概念不能黑盒，必须有明确定义

### 问题

"恒明珠段的病害是老问题多还是新问题多？"
系统答了：新问题414处，老问题335处
但**没告诉你怎么分的**，完全黑盒。

### 整改原则

**任何抽象概念，回答时必须说明"判断依据是什么"。**

### 具体怎么做

#### 1. 动态计算分界线（不靠写死的MDL）

**所有"大小/高低/多少/新旧"这种相对概念，都不能写死，必须靠数据本身的分布动态算。**

**统一思路：按中位数自动分。**
1. 先查这个指标的所有值，算出中位数
2. 中位数之前的算"低/小/旧"，之后的算"高/大/新"
3. 回答的时候把这个分界线说出来

---

### 需要动态算的所有维度

| 抽象概念 | 动态算法 | 举例回答 |
|---------|---------|---------|
| **老问题/新问题** | 按采集时间中位数分 | "按采集时间中位数（7月15日）分，之前的算老问题（335处），之后的算新问题（414处）" |
| **大病害/小病害** | 按面积中位数分 | "按面积中位数（2.5㎡）分，之前的算小病害（450处），之后的算大病害（461处）" |
| **高置信度/低置信度** | 按置信度中位数分 | "按置信度中位数（0.85）分，≥0.85的算高置信度（450处），<0.85的算低置信度（461处）" |
| **密集/稀疏** | 按病害密度中位数分 | "按病害密度中位数（100处/km）分，西乡段（178.6处/km）算密集，恒明珠（39.4处/km）算稀疏" |
| **严重/不严重** | 综合数量+面积+密度 | "综合来看，西乡段更严重：数量多（911处）、密度高（178.6处/km）、单处面积大（61.7㎡）" |
| **高发路段/低发路段** | 按桩号段的数量中位数分 | "按每公里病害数量中位数（150处）分，K0-K1算高发（200处），K1-K5算低发" |
| **多/少** | 按数量中位数分 | "按病害数量中位数（500处）分，西乡段（911处）算多，恒明珠（749处）也算多" |

---

### 为什么用中位数？

- **客观：** 基于数据本身的分布，不是人瞎定的
- **自动：** 时间怎么变、数据怎么变，都自动算，不用手动改
- **公平：** 不管数据多少，都是前一半后一半，不会极端

**好处：**
- 不用手动改，时间怎么变都自动算
- 客观，基于数据本身的分布
- 用户一看就知道怎么分的，不是黑盒

#### 2. 回答里必须说明依据
不管用户问什么，只要涉及抽象概念，回答必须包含：
> 按 **XX标准** 分，老问题335处，新问题414处。

**举例：**
> 按采集时间分（7月15日之前算老问题，之后算新问题），
> 老问题335处，新问题414处，新问题比老问题多79处。

#### 3. 如果没有标准，就问用户
如果业务上没有明确定义，系统应该反问：
> 你说的"老问题"和"新问题"，按多久分？比如按7月中旬之前/之后分？

**绝对不能自己瞎猜一个标准就答了。**

## 三、整改优先级

| 优先级 | 整改项 | 预期效果 | 工作量 |
|--------|--------|---------|--------|
| P0 | 抽象概念回答必须带依据 | 不再黑盒 | 小（改结果解读提示词） |
| P0 | 常用抽象概念写到MDL里 | 标准统一 | 中（改MDL） |
| P1 | 整理8个标准查询模式 | 覆盖大部分问法 | 中（改提示词） |
| P1 | 扩充抽象词映射表 | 更多人话能听懂 | 小 |
| P2 | 没有标准就问用户 | 不瞎猜 | 中（改提示词） |

## 四、为什么这样改就能"不管怎么问都能答"？

**现在的问题：** 系统在穷举"问法"，一种问法写一个模板，永远补不完。

**改完的思路：**
1. 不看用户怎么问，看用户**想做什么**（属于哪个模式）
2. 不管怎么问，只要想做的事一样，就用同一个模式答
3. LLM 负责把"人话"翻译成"模式 + 参数"

**举例：**
- "西乡段泛油有多少处？" → M1 单维度计数
- "西乡段泛油数量是多少？" → M1 单维度计数
- "西乡段有多少条泛油？" → M1 单维度计数
- "西乡段泛油总共有几处？" → M1 单维度计数

不管怎么问，都是同一个模式，同一个SQL。这就是泛化能力。
