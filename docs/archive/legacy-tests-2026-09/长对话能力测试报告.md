# 长对话/多轮对话能力测试报告

## 测试概况

- 测试脚本：`backend/test_multi_turn.py`
- 测试场景：8 个典型的多轮对话场景
- 测试结果：**2/8 个场景全部通过，6 个场景失败**

---

## 通过的场景（2 个）

### ✅ 场景1：简单追问-换主体
```
问：西乡段有多少处泛油？
答：共 534 处 ✅

问：那恒明珠呢？
答：（已沿用上一条问题的条件：泛油、有多少处）共 402 处 ✅
```
**效果：** 非常好！"那恒明珠呢？" 自动继承了上一轮的"泛油"，只换了路线主体。

### ✅ 场景4：中途换主题
```
问：西乡段泛油有多少处？
答：共 534 处 ✅

问：那恒明珠的裂缝呢？
答：0 处。巡检数据里一条裂缝都没采到... ✅
```
**效果：** 很好！用户明确说了"裂缝"，正确切换了病害类型，没有错误继承"泛油"。

---

## 失败的场景（6 个）

### ❌ 场景2：追问指标-继承主体
```
问：西乡段泛油有多少处？
答：共 534 处 ✅

问：那它的平均面积是多少？
答：这条问题我还差一点信息，补充一下我马上查。
    （原因：缺少具体的病害类型或路线信息）❌
```
**问题：** "那它的平均面积呢？" 应该自动继承上一轮的"西乡段+泛油"，但系统说缺信息。
**原因：** 规则匹配没识别出来这是追问——"它"这个指代词不知道指什么。

---

### ❌ 场景3：比较追问-结合前两轮
```
问：西乡段泛油有多少处？
答：共 534 处 ✅

问：恒明珠的泛油呢？
答：COUNT(*)=402 ✅

问：它俩哪个多？多多少？
答：我还不能确定你指的是哪个字段... ❌
```
**问题：** "它俩哪个多？" 应该自动结合前两轮的结果（534 和 402），post_calc 算出"西乡更多，多132处"。
**原因：**
1. 系统不知道"它俩"指哪两个对象
2. 也没有 post_calc 能力，不知道要把前两轮的结果拿过来算

---

### ❌ 场景5：多轮连续追问指标
```
问：西乡段泛油有多少处？
答：共 534 处 ✅

问：总面积多少？
答：缺路线、缺病害类型... ❌

问：平均面积呢？
答：缺病害类型、路线... ❌

问：最大的有多大？
答：缺具体对象... ❌
```
**问题：** 连续追问不同指标，每一句都应该继承上一轮的"西乡段+泛油"，但后面三句全部说缺信息。
**原因：** 规则匹配太死板——只有非常短的、像"那XX呢？"这种句式才会继承，"总面积多少？"、"平均面积呢？" 这种就识别不出来是追问。

---

### ❌ 场景6：带纠正的追问
```
问：西乡段有多少处病害？
答：共 911 处 ✅

问：我说的是泛油。
答：COUNT(*)=936 ❌
```
**问题：** "我说的是泛油" 应该继承上一轮的"西乡段"，只把病害类型改成泛油，结果应该是 534。
实际结果是 936（全库泛油总数），说明**没继承上一轮的路线过滤**，只继承了病害类型。
**原因：** 纠正类追问的上下文拼接逻辑有 bug，只继承了新说的病害类型，没继承上一轮的路线。

---

### ❌ 场景7：范围叠加类追问
```
问：西乡段泛油有多少处？
答：共 534 处 ✅

问：那 K0+800 到 K0+900 这一段呢？
答：病害数量=156 ❌
```
**问题：** 应该继承上一轮的"西乡段+泛油"，叠加桩号范围，结果应该是 81 处。
实际结果是 156（这一段所有病害的数量），说明**没继承上一轮的病害类型"泛油"**，只继承了路线。
**原因：** 范围叠加类追问的上下文拼接不完整，漏了病害类型这个条件。

---

### ❌ 场景8：复合问题+比较追问
```
问：西乡段和恒明珠的泛油各有多少处？
答：恒明珠 402 处，西乡段 534 处，合计 936 处 ✅

问：哪条路更多？多多少？
答：由于只有这一条数据，无法进行路线之间的对比... ❌
```
**问题：** 应该结合上一轮的结果（534 和 402），post_calc 算出"西乡更多，多132处"。
实际系统不知道"哪条路"指哪两条，又去查了一遍，结果只查到一条路。
**原因：**
1. 不知道"哪条路"指上一轮提到的两条路
2. 没有 post_calc 能力，不会用前一轮的结果做计算

---

## 核心问题总结

### 问题1：规则匹配太死板，识别不了追问
**现状：** 现在的上下文继承是靠规则匹配的（looks_like_refinement、looks_like_correction），只能识别非常固定的几种句式：
- "那XX呢？"（短问句）
- "我说的是XX"（纠正句）
- "XX呢？"

稍微换个说法就识别不出来了：
- "那它的平均面积呢？" → 识别不出来
- "总面积多少？" → 识别不出来
- "它俩哪个多？" → 识别不出来
- "那 K0+800 到 K0+900 这一段呢？" → 识别不完整

**本质：** 规则匹配是在做"字符串模板匹配"，不是在做"语义理解"。用户的问法是无限的，规则永远覆盖不完。

---

### 问题2：指代词替换能力弱
**现状：** "它/这个/那/它俩" 这类指代词，系统不知道指什么。

**应该做到：**
- "那它的平均面积呢？" → 补全成 "西乡段泛油的平均面积是多少？"
- "它俩哪个多？" → 补全成 "西乡段泛油和恒明珠泛油哪个多？多多少？"
- "那这一段呢？" → 补全成 "西乡段泛油在 K0+800 到 K0+900 这一段有多少？"

**现在的问题：** 补全逻辑是硬编码的，只能补路线，不能补病害类型、指标、比较对象。

---

### 问题3：没有 post_calc 能力
**现状：** "它俩哪个多？多多少？" 这种问题，系统不知道要结合前两轮的结果来算，又去重新查数据库了。

**应该做到：**
1. 上两轮分别查了西乡 534、恒明珠 402
2. 用户问"哪个多？多多少？" → 识别这是 post_calc
3. 直接用前两个结果算：534 > 402，差值 132
4. 不用再查数据库

**现在的问题：** 系统没有"基于历史结果做计算"的能力，每一句都是独立查数据库，完全不记得之前查过什么。

---

## 改进方向

### P0：把"追问理解"交给 LLM，不要靠规则匹配

**现状：** 规则匹配识别追问，死板、覆盖不全。

**建议：**
1. 把最近 3-5 轮的对话历史 + 当前用户问题，一起丢给 LLM
2. 让 LLM 做两件事：
   - 把指代词替换成完整实体名（"它"→"西乡段泛油"，"它俩"→"西乡段泛油和恒明珠泛油"）
   - 判断这是不是 post_calc 类问题（如果是，直接返回 post_calc 类型，不用查数据库）
3. 补全后的完整问题，再走后面的查询路径

**好处：**
- 不管用户怎么问，LLM 都能理解语义，补全上下文
- 不用再写一堆规则去匹配各种追问句式
- 从"字符串匹配"升级到"语义理解"，覆盖所有问法

---

### P1：把"post_calc 历史结果计算"加进去

**现状：** 所有问题都去查数据库，不知道用之前的结果。

**建议：**
1. 每一轮查询完，把结果存到会话历史里：`{"西乡段泛油数量": 534, "恒明珠泛油数量": 402}`
2. 用户问"哪个多？多多少？"的时候，LLM 先判断：这是不是可以用历史结果算？
3. 如果可以，直接 post_calc，不用查数据库
4. 如果不行，再走查询路径

---

### P2：上下文继承要更完整——不要漏条件

**现状：** 有时候继承了一部分条件，漏了另一部分：
- 场景6：只继承了病害类型，漏了路线
- 场景7：只继承了路线，漏了病害类型

**建议：** 交给 LLM 做上下文补全的时候，要求它**继承所有上一轮提到的过滤条件**：路线、桩号、病害类型、时间、设备号，一个都不能少。

---

## 总结

**现在的长对话能力：**
- ✅ 简单的"那XX呢？"（换主体）→ 能用
- ✅ 明确换主题的（说了新的病害类型）→ 能用
- ❌ 追问指标的（"那平均面积呢？"）→ 用不了
- ❌ 连续追问多个指标 → 用不了
- ❌ 比较类追问（"它俩哪个多？"）→ 用不了
- ❌ 纠正类追问（"我说的是泛油"）→ 条件继承不全
- ❌ 范围叠加类追问 → 条件继承不全

**根本原因：** 现在的上下文继承是靠规则匹配的，不是靠 LLM 语义理解的。规则只能覆盖非常有限的几种追问句式，用户问法稍微变一下就识别不出来了。

**你之前说的"交给 LLM 拆分"，在长对话场景下更应该这么做**——不仅单轮问题要交给 LLM 拆，多轮对话的上下文补全也应该交给 LLM。规则匹配在长对话这个场景下，数学上就是收敛不了的。
