## 一、问题复盘：用户为什么"问不出来"

### 1.1 现场还原

> 用户问：**宝安大道西乡段 K1+000至K3+000路段中数量最多的病害是哪种，以及数量总数是多少**

真实数据（2026-09-16 探针）：

| 数据源 | 西乡段实际范围 | 说明 |
|---|---|---|
| `basic_facilities_routes` 台账 | start_num=**K0+000**、end_num=**K5+100**、distance=**5.60km**、6 车道 | 路线台账全长 5.6 公里 |
| `basic_facilities_sections` 路段 | start_meter_total=**0**、end_meter_total=**5100** | 与台账一致 |
| `basic_facilities_sections_pile_detail` 桩号明细 | **52 个桩点**，0~5100m | 桩号标到 K5+100 |
| `ai_problem` 实际病害 | **min=11（K0+011）、max=887（K0+887），911 处全部在此** | **实际巡检只覆盖不到 0.9 公里！** |

- 用户问的 **K1+000~K3+000 区间在病害数据里一条都没有**（实测 `BETWEEN 1000 AND 3000` = 0 条）。
- 所以"问不出结果"不是 bug 的随机发生，而是**必然**：台账说路有 5.6 公里，但巡检数据只采了 0.9 公里。

### 1.2 三类"条件有问题"的场景（本文件要解决的）

| 类型 | 场景 | 例子 |
|---|---|---|
| **A. 超数据范围** | 用户给的桩号区间超出**实际巡检数据**范围 | 西乡段 K1+000~K3+000（数据只到 K0+887） |
| **B. 台账≠数据** | 台账有桩号、有路段，但**没有巡检数据** | 西乡段 K5+000 附近有没有病害？→ 台账有、数据无 |
| **C. 隐含起点** | 用户没给桩号，要用**台账起点桩号**算长度 | 西乡段前 500 米和后 500 米哪段泛油多？ |

## 二、解决方案设计（给 Codex 的实现指引）

### 2.0 先说本质：这是"条件存在性校验"问题，不止桩号

桩号只是第一个暴露的字段。**用户问题里的任何条件都可能"在数据里不存在/部分存在"**：

| 条件类型 | 字段例子 | "不存在"的形态 |
|---|---|---|
| 枚举/字典 | 病害类型、资产类型、路面类型 | 字典里没有这个类型；或字典有但数据里没采到 |
| 实体 | 路线名、路段名、桩号点 | 台账里没有这条路 |
| 数值/范围 | 桩号、面积、置信度、日期 | 用户区间超出数据 min/max |
| 组合 | 路线+类型+区间+时间+置信度 | 每个条件单独存在，但组合后为空 |

**统一解法 = 三层判定 + 条件消融**（见 2.5）。下面 2.1~2.4 以桩号为例讲机制，2.5 讲通用化。

### 2.1 范围校准层（Range Calibration）—— 核心新能力

**目标**：用户条件超范围时，**不硬查、不硬答 0**，而是：① 提醒"该区间没有数据"；② 给出实际数据范围；③ 给实际范围内的统计结果。

**触发**：`parse_pile_range` 命中桩号区间，且 subject=disease/route 系。

**步骤**：
1. 解析出路线 + 用户桩号区间 `[U1, U2]`；
2. 查路线**实际数据范围**：`SELECT MIN(pile_distance), MAX(pile_distance) FROM ai_problem WHERE routes_id=...`（数据本身的 min/max，不依赖台账）；
3. 对比用户区间与数据范围 → 三态判定：
   - **full**：用户区间 ⊆ 数据范围 → 正常查询；
   - **partial**：部分重叠 → 正常查询 + 回答里附一句"Kx 之外暂无数据"；
   - **none**：完全不重叠 → **不执行无意义查询**，直接返回：
     - 提醒："该路段台账全长 K0+000~K5+100，但当前巡检病害数据实际只覆盖 K0+011~K0+887，您查询的 K1+000~K3+000 暂无病害记录"；
     - 附带实际范围内的统计（如"实际覆盖范围内的病害：泛油 534 处、未识别 377 处，合计 911 处"）；
4. 同类问题返回 `answer_format="calibrated"`，前端可高亮提示。

**语义 JSON 扩展**：
```json
{
  "shape": "count",
  "subject": "disease",
  "filters": [{"field":"route","value":"宝安大道西乡段"},
              {"field":"pile_range","from":1000,"to":3000}],
  "calibration": {
    "data_range":  {"min": 11, "max": 887},
    "ledger_range":{"start":"K0+000","end":"K5+100"},
    "coverage": "none",
    "note": "台账全长 K5+100，巡检数据实际只覆盖到 K0+887"
  }
}
```
翻译器看到 `coverage="none"` → 走校准回答分支；`partial` → 正常 SQL + 附注。

### 2.2 台账-数据双源校验（Ledger vs Data）

**目标**：把"路线台账（routes/sections）"和"实际数据（ai_problem）"两套事实分开，回答里主动暴露不一致。

- 建立**路线信息缓存**：routes.start_num/end_num/distance/lane_count + sections.start_meter_total/end_meter_total/tech_grade/surface_type + 数据实际 min/max；
- 凡涉及"路段/桩号/长度"的问题，把这份信息注入 SQL 生成上下文；
- 用户问"这条路全长多少/最远到哪/某某桩号有没有病害"时，**同时报台账值和实际数据值**，不一致时明说。

### 2.3 起点桩号推导（前 N 米 / 后 N 米）

**目标**：用户说"前 500 米/后 500 米"时，**不需要用户报桩号**，用路线起点桩号计算区间。

- 口径：`前N米 = [start_meter_total, start_meter_total+N)`，`后N米 = [start_meter_total+N, start_meter_total+2N)`；
- start_num 缺失时退化为按**数据 min_pile** 起算，回答注明口径；
- **已实测验证**：西乡段泛油 前500=**288**、后500=**246** → "前 500 米泛油多（288 vs 246，多 42 处）"。

### 2.4 需要新增的语义类别（挂进语义中间层方案）

| 新增 | 说明 |
|---|---|
| `shape=range_top` | 区间内"数量最多的类型/最严重位置"，翻译成区间 GROUP BY + ORDER BY |
| `filters[].pile_range.auto` | 由起点桩号推导的区间（标记 auto，回答注明口径） |
| `subject=route` | 路线台账信息查询（start_num/end_num/distance/lane_count/tech_grade） |
| `subject=section` | 路段信息查询（sections 表，字段丰富：tech_grade/surface_type/section_property 等） |
| `subject=patrol` | 巡检任务（ai_maintain_patrol：task_number/patrol_type/patrol_mileage/valid_task） |
| `subject=asset_dict` | 资产类型字典（ai_asset_base：asset_type/asset_code/categories_type） |
| `answer_format=calibrated` | 范围校准回答（提醒+实际范围+实际统计） |

### 2.5 通用条件存在性校验（Condition Validation）—— 三态判定 + 条件消融

> 本节回答你问的"**怎么判断问题条件存不存在**"。机制分三层，成本从低到高，能覆盖绝大多数场景。

#### L1 枚举/实体层（元数据缓存，不查库）

把"用户可能拿来当条件值"的东西做成缓存表，LLM 归一化用户条件后先做**值匹配**：

| 缓存 | 来源 | 示例 |
|---|---|---|
| 路线名表 | `basic_facilities_routes.short_name/full_name`（3623 条，实际含"宝安"只有 2 条） | "宝安大道龙华段"→ 查无此路 |
| 病害类型表 | `ai_problem_base.problem_type`（42 类） | "泛油"✓、"横向裂缝"✓（字典有）、"鼓包"✗（字典无） |
| 资产类型表 | `ai_asset_base.asset_type`（88 类） | "护栏"✓ |
| 桩号格式 | 正则 `K\d+\+\d+` / 整数米 | "K1+000"→ 1000m |

匹配用模糊匹配（含"西乡"即可命中"宝安大道西乡段"）；匹配失败 → 明确告知"未找到名为 X 的路线/类型"，**不再进 SQL**。

#### L2 数值/范围层（统计缓存，定时刷新）

对每个数值/时间字段维护 **MIN/MAX/COUNT**（表级或按路线级），用户条件区间先跟缓存比对：

| 字段 | 实测范围（2026-09-16） | 用户问越界的例子 |
|---|---|---|
| `ai_problem.pile_distance`（全库） | 11 ~ 20000m | 西乡段 K1~K3（西乡段数据只到 887） |
| `ai_problem.collection_time`（全库） | **2026-06-18 ~ 2026-07-30** | "2024 年病害"→ 0；西乡段"6月"→ 0（西乡段数据 07-15 起） |
| `confidence`（JSON 解析） | **0.407527 ~ 0.945732** | "置信度 0.95 以上"→ 0 |
| `area`（泛油） | **0.16 ~ 7.52㎡** | "泛油面积 10㎡ 以上"→ 0 |
| `basic_facilities_routes.distance` | 0 ~ 5.60km | "全长 10km 的路"→ 需比对 |

越界判定 → 走 calibrated 分支（提醒 + 给实际范围 + 给范围内统计），**不执行必为空的 SQL**。

#### L3 组合层（查询时动态，条件消融 Condition Ablation）

**关键难点**：每个条件单独存在，组合后可能为空（如 西乡段✓ + 泛油✓ + K1~K3✓（值合法但区间越界）→ 组合为空）。无法用缓存全判，必须在查询结果上做**消融诊断**：

```
主查询（条件 A∩B∩C）→ 结果为空
→ 依次去掉 A、去掉 B、去掉 C 各查一次 COUNT（轻量、走索引）
→ 定位"哪个条件把结果砍没了"：
   去掉 A 有 N1 条、去掉 B 有 N2 条、去掉 C 有 N3 条
   → 报告：A∩B∩C 为空；实际 A∩B 有 N3 条（即去掉 C 后），B∩C 有 N1 条……
→ 输出"条件诊断报告"：
   "您查询的 西乡段+K1~K3+泛油 无数据。
    原因：西乡段病害实际只覆盖 K0+011~K0+887（K1~K3 无记录）。
    实际范围内：泛油 534 处，共 911 处。已按实际范围为您统计。"
```

**成本控制**：空结果才触发消融（正常查询无额外开销）；消融最多 n+1 次轻量 COUNT（n=条件数），且可用同一路线的统计缓存替代一部分。

#### 三态判定的通用定义（回答形态）

| 判定 | 定义 | 回答形态 |
|---|---|---|
| **完全存在** | 所有条件值合法且组合有数据 | 正常回答 |
| **部分存在** | 条件值合法，组合数据不足（如区间越界/类型数据为 0） | 正常回答 + 附注"X 超出实际范围/暂无记录，实际是…" |
| **完全不存在** | 条件值本身非法（路线不存在/类型不在字典/表为空） | 直接提醒"没有这条路/这种类型/该业务暂无数据"，不执行 SQL |

#### 判断难点（为什么"好难好难"）—— 诚实清单

1. **值匹配难**：口语化/简称/错别字（"宝安大道西乡段"vs"西乡段"vs"宝安西乡"）；
2. **格式归一难**：K1+000 / 1000 / 1km / K001+000 多种写法；
3. **字典有 vs 数据有是两回事**：横向裂缝在字典里有 42 类之一，但巡检数据一条都没有（0 条）——必须分开判断；
4. **组合爆炸**：n 个条件，空因可能是任意子集（消融只能查一阶，两两组合要 C(n,2) 次）；
5. **语义条件**："病害严重"→ 面积>5 或置信度>0.8，不是字面条件；
6. **脏数据**：全库 area 有 5000/19/11 等异常值，统计缓存必须先清洗（如限定泛油）；
7. **"无数据"≠"条件错"**：恒明珠 GPS 空库是"该业务暂未采集"，路线不存在是"条件错"，回答要区分。

#### 落地建议（分阶段）

- **阶段 1**：L1 路线/类型缓存 + L2 统计缓存 + 空结果触发消融诊断（先做这个，覆盖 80% 场景）；
- **阶段 2**：诊断报告可交互（"您问的 X 无数据，是否改看 Y？"）；
- **阶段 3**：同义词/别名表，沉淀用户纠正历史（用户说"就是西乡段"→ 把"宝安西乡"加入别名）。

### 3.3 表结构坑（Codex 的 schema 字典必须修正，否则题必崩）

1. **桩号明细表**：桩号字段是 `pile_map_position_name`（桩号名）+ `meter`（米），**不是** pile_number/pile_distance；
2. **巡检表**：无 routes_id/sections_id（要关联路线需走 `ai_problem.patrol_id` 或 `scope_record_id` 链路）；`patrol_mileage` 数据异常（单次均值 3200+km，疑似单位错误），**不要用里程出题**；
3. **sections 表**：里程字段是 `start_meter_total`/`end_meter_total`（int 米）+ `start_num`/`end_num`（字符串桩号）；
4. **ai_problem.damage_type 注释写"损坏程度"，实际存的是病害类型代码**（JOIN ai_problem_base.problem_code 得类型名）——注释与用法不符；
5. **ai_asset_base.categories_type 注释写"0条状 1点状"，实际值是 10/20/30/40/60/70/80**（7 组）——注释与实际不符；
6. **ai_problem.pile_distance（解析桩号米数）≠ pile_meter（距离路段起点米数）**：桩号范围条件必须用 pile_distance；
