# 全表全字段可达性测试报告

测试时间：2026-09-20。目的：回答"592 个 MySQL 字段、20 个 PG 字段是不是都找得到"。方式：19 张表（MySQL 17 张 + PostgreSQL 2 张）每张出两道题——T 题"把 XX 台账/记录明细全部调出来"（SELECT *，一次覆盖该表全部字段），F 题用业务中文名点名要多个冷门字段（测字段能否被按语义选中），共 38 题，走完整 agent 链路，再从生成的 SQL 里自动判断表名和字段命中率。脚本 backend/test_all_fields.py，原始结果 docs/全字段可达性测试结果.json，全字段清单 docs/全字段清单.json。

## 一、总体结果

表可达 29/38（76%）。其中：

- 字段题 F：17/19 选对表（89%），字段总命中 115/145（79%）。
- 表清单题 T（只说表名、不给字段）：12/19（63%），是主要短板。
- 有数据的表：10/14 表可达。
- 空表：19/24 能定位到正确的表并如实回答"暂无数据"（79%）。

一个关键对比：同一张表，字段题（带具体字段业务名）几乎都能选对，表清单题（只说"XX 台账/明细全部调出来"）反而经常失败。例如隧道 T 题失败、F 题 10/10 字段全中；路线 T 题失败、F 题 12/12 全中；路段 T 题失败、F 题 10/10 全中。这说明表和字段在 MDL 里都有、也能被选中，缺的是"表级业务叫法 → 物理表"的选择能力，而不是字段没接入。

空表的好消息：桥梁、隧道字段题、工程项目、养护项目、病害工单、养护工单、GPS 轨迹点、倾斜监测字段题等，都能定位到正确的表、生成含目标字段的 SQL、如实返回空。也就是说"表结构在 MDL 里，以后数据写入即可查"这条路基本成立。

## 二、找不到 / 走错的表（9 个表次）

- basic_facilities_routes：T 题"把路线台账明细全部调出来"，系统把"调出"两个字误当成路线名，报"没有找到路线'调出路'"。
- basic_facilities_sections：T 题走到知识库，回"资料中没有路段台账完整定义"。
- basic_facilities_sections_pile_detail：T 题 Wren 报 No field named pile_point.pile_number（该表没有 pile_number，桩号名字段是 pile_map_position_name），还被强加了 pile_distance 必填条件。
- ai_distance_capture：T/F 题都走错到 disease（病害表）或 patrol 表，没有定位到定距采集表。
- basic_facilities_tunnels：T 题 SQL 校验没过；但 F 题 10/10 全中。
- basic_facilities_slope：T 题把"边坡"理解成"边坡落石"这种病害去查 disease，F 题直接走知识库说"不包含边坡台账"，整张表 0/9。
- ai_problem_base：F 题问"病害类型的别名/描述/公式/单位/阈值"，走到知识库回"资料中没有"，SQL 为空（T 题列字典能成功，84 行）。
- inclination_points（PG）：T 题把"把每一条记录的完整字段"误当成路线名；F 题 6/6 全中。

## 四、根因与修复（给 codex）

### 1. 表级业务叫法选不准（最高优先级）

只给表名、不给字段时，选表器选不准物理表，还会把表名误解成病害类型或路线名、或路由到知识库。

修复：

- 在两步走选表器（table_selector）里给每张表补"用户会怎么称呼这张表"的别名和一句话边界，至少包括：
  - 路线台账/路线基础信息 = basic_facilities_routes（模型 route）
  - 路段台账/路段基础信息 = basic_facilities_sections（模型 section）
  - 里程桩号坐标点/桩点明细 = basic_facilities_sections_pile_detail（模型 pile_point，桩号名是 pile_map_position_name，没有 pile_number）
  - 定距采集/定距采集图片 = ai_distance_capture（不是病害、不是巡查任务）
  - 桥梁台账 = basic_facilities_bridges；隧道台账 = basic_facilities_tunnels；边坡台账 = basic_facilities_slope（这些是构造物台账，不是病害，"边坡"不等于"边坡落石"病害）
  - 在建工程项目 = project_manage_project_main；养护项目 = maintenance_project；日常养护作业 = maintenance_road_work_record
  - 病害工单 = ai_work_order；养护工单 = maintenance_work_order
  - GPS 轨迹/车辆打点 = PostgreSQL gps_points；倾斜监测 = PostgreSQL inclination_points
- 把"把 XX 台账/记录/明细全部调出来、列出全部 XX"识别为全表清单意图：直接 SELECT * FROM 该表 LIMIT 500，不强制要求路线/时间/桩号等 WHERE 条件，不从中抽取路线名，不路由到知识库。
- "调出/列出/全部"这种动词和量词不要进实体抽取（本次"调出路""把每一条记录的完整字段"被当成路线名）。

### 2. 字典元数据问题被误路由到知识库

"某病害/资产类型的别名、描述、计算公式、计量单位、置信度阈值、是否主要关注"是查字典表（ai_problem_base / ai_asset_base），属于数据查询；只有问养护规范、评定标准、处置办法时才走知识库。数据源判断提示词要补这条区分。

### 3. 点名字段全覆盖校验

用户在问题里明确点名的字段，SQL 的 SELECT 列表里必须全部出现，缺了就判错重写，不允许只回一两个字段（本次 workrec、distance、pile、assetmain、工单 assign_time 都漏字段）。这和之前的"维度完整性"是同一条规则的字段版本：把"用户点名的字段/维度清单"与"SQL SELECT 列 + 结果表头"做比对，少一个就补。

### 4. 禁止臆造字段、隔离跨库模型

- Wren 编译报 No field named X 时，要把该表真实存在的列回喂给模型重写，而不是放过或换表：pile_point 没有 pile_number（用 pile_map_position_name），patrol 没有 collection_time（用 create_time/end_date/over_time）。
- 修复跨库串模型：本次 MySQL 题 fallback 时出现 table 'wren.public.disease' not found，是 PG 的 wren 项目上下文里引用了 MySQL 的 disease 模型。两个 wren 项目（road_mysql / road_pg）的模型命名空间要隔离，PG 库只能引用 gps_points / inclination_points，不能引用 disease/route 等 MySQL 模型。

### 5. 空表字段题也要把字段选全

空表返回 0 行是对的，但 SELECT 仍应包含用户点名的全部字段（用于确认字段存在、数据写入后立即可见）。本次空表 T 题大多正确，F 题部分只选了少量字段，按第 3 条统一处理即可。
