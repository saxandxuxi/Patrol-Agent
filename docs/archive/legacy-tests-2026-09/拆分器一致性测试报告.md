# 拆分器一致性测试报告（同一答案·不同问法）

## 测试概况

- 测试脚本：`backend/test_decompose_consistency.py`
- 测试方法：同一语义的问题，换不同的问法，看拆分结果是否一致
- 测试结果：**6 个测试组，3 个一致，3 个不一致**

---

## 一致的测试组（3 个）

### ✅ 1. 单指标数量查询（不该拆）
所有问法都正确不拆，结果一致：
```
西乡段泛油有多少处？           → 不拆
西乡段有多少处泛油？           → 不拆
请问西乡段一共有多少处泛油？   → 不拆
西乡段的泛油病害数量是多少？   → 不拆
帮我查一下西乡段泛油有多少条？ → 不拆
西乡段总共多少处泛油病害？     → 不拆
西乡段泛油一共多少？           → 不拆
西乡段有几处泛油？             → 不拆
```

### ✅ 2. 分组统计查询（不该拆）
所有问法都正确不拆，结果一致：
```
西乡段各病害类型分别有多少处？   → 不拆
西乡段有哪些病害类型？各有多少？ → 不拆
西乡段按病害类型分组，各类型数量是多少？ → 不拆
西乡段的病害类型分布是怎样的？   → 不拆
西乡段都有哪些病害？分别多少处？ → 不拆
```

### ✅ 3. 数据+规范混合（该拆）
所有问法都正确拆成 data + knowledge，结果一致：
```
西乡段泛油有多少处？泛油应该怎么处理？           → 拆成2个
西乡段泛油数量是多少？养护规范要求怎么处置？     → 拆成2个
查一下西乡段泛油数量，还有泛油的养护方法         → 拆成2个
```

## 不一致的测试组（3 个）

### ❌ 1. 转弯计算-病害密度（该拆）→ **全部都没拆！**

所有问法都没拆，**完全失败**：
```
西乡段平均每公里有多少处病害？   → 不拆 ❌
西乡段病害密度是多少？           → 不拆 ❌
西乡段每公里平均发现几处病害？   → 不拆 ❌
西乡段平均每公里多少处病害？     → 不拆 ❌
西乡段的病害密度怎么样？         → 不拆 ❌
```

**为什么全部没拆？**
看 `should_decompose` 函数的逻辑：
```python
_POST_CALC_HINTS = ("多多少", "差多少", "哪个更多", "哪条更长", "长多少", ...)

def should_decompose(message):
    # 只有命中这些关键词才返回 True
    if has_data and any(word in message for word in _POST_CALC_HINTS):
        return True
```

哦！**"密度"、"平均每公里"这些词根本不在 _POST_CALC_HINTS 里！** 所以 `should_decompose` 返回 False，根本不会走 LLM 拆分，直接当成单个任务了。

**这就是为什么你之前感觉"转弯问题一个都不会"**——不是 LLM 拆不对，是 `should_decompose` 这一关直接把所有转弯计算类问题都拦住了，根本不给 LLM 拆的机会！

---

### ❌ 2. 多对象对比（该拆）→ **问法不一样，拆分结果不一样**

| 问法 | 拆分结果 |
|------|----------|
| 西乡段和恒明珠的泛油各有多少处？ | 不拆 ❌ |
| 西乡段和恒明珠的泛油数量分别是多少？ | 不拆 ❌ |
| 请问西乡段有多少泛油？恒明珠呢？ | 不拆 ❌ |
| 西乡段和恒明珠，哪个泛油多？多多少？ | 拆成2个 ✅ |
| 西乡段泛油比恒明珠多多少？ | 拆成3个 ✅ |

**为什么不一致？**
- 带"哪个多"、"多多少"的问法 → 命中 _POST_CALC_HINTS → 拆 ✅
- 只问"各有多少"的问法 → 没命中关键词 → 不拆 ❌

**同样是两个对象对比，问法不一样，拆分结果就不一样。** 这就是规则匹配的问题——它只能识别它认识的关键词，识别不出来的就当没看见。

---

### ❌ 3. TOP N 查询（不该拆）→ **换个问法就被误拆**

| 问法 | 拆分结果 |
|------|----------|
| 西乡段数量最多的前3种病害是什么？ | 不拆 ✅ |
| 西乡段最多的3种病害分别是什么？ | 不拆 ✅ |
| 西乡段哪几种病害最多？各有多少？ | 拆成2个 ❌ |
| 列出西乡段数量排名前3的病害类型 | 不拆 ✅ |

**为什么被误拆？**
看 `should_decompose` 的另一个判断：
```python
superlative = any(word in message for word in ("最多", "最大", "最高", ...))
same_object_metrics = any(word in message for word in ("各自", "分别", "各多少", ...))
return has_data and superlative and not same_object_metrics and (问号数 >= 2)
```

"西乡段哪几种病害最多？各有多少？" 这句话：
- 有"最多" → superlative=True
- 有两个问号
- 没有"各自/分别" → same_object_metrics=False
- 所以 should_decompose 返回 True → 拆了

但实际上这是同一个问题（TOP N + 各有多少），一次 GROUP BY 就能出结果，不该拆！

---

## 核心问题总结

**所有不一致的问题，根源都是同一个：`should_decompose` 这个前置判断函数太死板了。**

现在的流程是：
```
用户问题 → should_decompose（规则匹配）→ 不拆就直接走单任务
                                      → 拆就走 LLM 拆分
```

`should_decompose` 是靠关键词匹配的，它有两个致命问题：

### 问题1：覆盖不全
转弯计算类（密度、间距、占比）的关键词根本没加进去，导致这类问题**全部被拦住，根本走不到 LLM 拆分**。

你之前说"转弯的题目 LLM 一个都不会"——不是 LLM 不会，是 `should_decompose` 根本不让它上！

### 问题2：误判
同样语义的问题，问法稍微变一下，就被误判成"要拆"或者"不要拆"：
- "各有多少处？" → 不拆
- "哪个多？多多少？" → 拆
- "哪几种最多？各有多少？" → 误拆

**规则匹配的本质问题：它是在做字符串匹配，不是在做语义理解。** 用户的问法是无限的，你写多少条规则都覆盖不完，而且还会误判。

---

## 改进建议

### P0：把 `should_decompose` 这个前置判断去掉，直接让 LLM 拆

**现状：** 先过规则判断要不要拆，再决定走不走 LLM。
**建议：** 不管什么问题，都先让 LLM 判断要不要拆、怎么拆。

**理由：**
1. LLM 能理解语义，不管用户怎么问，都能判断"这个问题需不需要拆"
2. 不会出现"转弯计算类全被拦住"的问题
3. 不会出现"问法不一样、拆分结果不一样"的问题
4. 规则匹配永远覆盖不完所有问法，交给 LLM 才是正路

**改造成本：** 很小，就是把 `decompose` 函数开头的 `if not should_decompose(message): return [单个任务]` 这行去掉，直接走 `_llm_tasks`。

---

### P1：如果觉得所有问题都走 LLM 太贵，可以改成"LLM 判断要不要拆"

**现状：** 规则判断要不要拆。
**建议：** 让 LLM 做两步判断：
1. 第一步：这个问题需不需要拆？（是/否）
2. 如果需要，再拆成子问题。

这样比规则匹配准多了，而且只多一次 LLM 调用。

---

### P2：转弯计算类的关键词还是要加进去（即使去掉了 should_decompose，也要加到提示词里）

即使 `should_decompose` 去掉了，转弯计算类的问法还是要告诉 LLM：
- 密度类："每公里多少处"、"病害密度"
- 间距类："平均多少米一处"
- 占比类："占百分之多少"

这些都要加到 `prompts/decompose.md` 的提示词里，告诉 LLM 这些都要拆成"查原始数据1 + 查原始数据2 + post_calc"。

---

## 总结

**你之前感觉"同一个问题换个问法就不行"，这个感觉是对的。** 根源就是 `should_decompose` 这个前置规则判断太死板——它靠关键词匹配，不是靠语义理解，所以：

1. **转弯计算类全被拦住**（没加关键词）→ 根本走不到 LLM 拆分
2. **多对象对比看关键词**（有"多多少"就拆，没有就不拆）→ 问法不一样结果不一样
3. **TOP N 类容易误拆**（有"最多"+两个问号就拆）→ 其实是同一个问题

**最该改的：把 `should_decompose` 这个前置判断去掉，直接让 LLM 拆。** 规则匹配在"判断要不要拆"这个场景下，数学上就是收敛不了的。
