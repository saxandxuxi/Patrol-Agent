# 全字段逐题可达性测试报告（612 个字段）

测试时间：2026-09-20。在 38 题表级测试基础上，这次对 MySQL 17 张表的全部 592 个字段加 PostgreSQL 2 张表的 20 个字段，逐字段各出一道题，共 612 题。题目由建表时的字段注释（中文名）自动拼成，不暴露物理列名，例如字段 collect、注释"收藏：0否，1是"，题目是"查询病害记录，给我每条记录的收藏：0否，1是"。每题走完整 agent 链路，再从最终 SQL 严格判断：表有没有选对、该字段有没有出现在 SELECT 里。脚本 backend/test_all_592_fields.py，逐题结果 docs/全字段逐题结果.jsonl，可断点续跑。

## 一、总体结果

- 通过（表对、字段也选中）：512 / 612，83.7%

- field_miss（表对了但该字段没 SELECT）：22，3.6%
- 程序异常 error：0

## 二、最高杠杆根因：19 个 Wren 模型的表描述全部为空

检查 wren_projects/road_mysql/target/mdl.json 和 road_pg/target/mdl.json，17 + 2 个模型的 description 全部是空字符串。字段有中文注释（所以带字段名的题命中率高），但表没有任何业务说明，选表只能靠表名猜。这次所有整表性失败几乎都源于此：

- 养护工单 maintenance_work_order 26/26 全挂：问"养护工单"，系统选成了 ai_work_order（病害工单），SQL 实际查的是 ai_work_order。两张表结构几乎一样、描述都为空，无法区分。
- 倾斜监测 inclination_points 时好时坏（4/11）：同样的表，x/y/now_gps 能查到，device_id/collect_time 被判"倾斜监测点不在本系统查询范围""缺少倾斜监测点相关表"，没有生成 SQL。
- 病害字典 ai_problem_base 9/25：问别名、计算公式、置信度阈值这类字典属性，直接走知识库回"资料中没有相关内容"，SQL 为空。
- 定距采集 ai_distance_capture 的桩号、图片、巡查编号字段走到病害表或被要求"先给路线条件"。

修复：给每个模型补 description，写清三件事——这张表业务上是什么、用户会怎么称呼它、和容易混淆的表怎么区分。建议文案如下，可直接写进 wren_projects/road_mysql/overrides.yml 和 road_pg/overrides.yml 的模型描述，再跑 sync_wren_mdl.py：

- disease（ai_problem）：道路巡检实际发现的每一条病害/损坏记录。用户说"病害、损坏、坑槽裂缝泛油、采集到的问题"指本表。一条病害属于某条路线、某个路段，带桩号、上下行、病害类型、面积、置信度、采集时间、图片。
- damage_dict（ai_problem_base）：病害类型字典/分类标准，存每种病害类型的名称、别名、所属大类、计算公式、计量单位、置信度阈值、样图。问"病害类型有哪些、某类型的别名/公式/单位/阈值/样图"查本表，属于数据查询，不是知识库规范。
- route（basic_facilities_routes）：路线台账，每条路线一行，存路线全称简称、起止桩号、起终点经纬度、行政级别、车道数、限速、通车日期、管养单位。用户说"路线台账、某条路的基础信息"。
- section（basic_facilities_sections）：路段台账，路线下细分的路段，存技术等级、路面类型、路面/路基宽度、车道特征、涵洞数、建成/改建时间。用户说"路段台账、分段基础信息"。
- pile_point（basic_facilities_sections_pile_detail）：里程桩号坐标点，存每个桩号的名称、坐标、经纬度、米数、排序。桩号名称字段是 pile_map_position_name，本表没有 pile_number。
- patrol（ai_maintain_patrol）：巡查/巡检任务，每次巡检一行，存任务编号、巡查编号、巡查类型/状态/方式、是否有效、巡查人、巡检里程、起止时间。
- ai_distance_capture：车辆定距采集记录（按固定里程拍照），存定距采集编号、原始图片、缓存图片、图片画框位置、桩号、经纬度、采集时间。它不是病害、不是巡查任务。
- ai_asset_base：资产类型字典，存资产类型名称、别名、大类、单位、颜色、样图、置信度阈值。问"资产类型有哪些、某资产的单位/样图"查本表。
- ai_asset_main：实际采集到的资产明细记录（资产实例），引用 ai_asset_base 的类型。
- basic_facilities_bridges：桥梁构造物台账（名称、中心桩号、跨径分类、技术等级、跨越地物、养护单位、图片）。是构造物台账，不是病害。
- basic_facilities_tunnels：隧道构造物台账（长度、净宽净高、分类、通风照明消防、各类技术评定等级、管养单位、图片）。
- basic_facilities_slope：边坡构造物台账（名称、高度长度、性质、边坡类型、防护工程、是否绿化、修建年度、施工/养护单位）。"边坡"指本表，不等于"边坡落石"这类病害。
- project_manage_project_main：在建公路工程项目台账（投资、规模、里程、开竣工日期、招标中标、参建单位）。
- maintenance_project：养护工程项目台账（养护里程、负责人、起止日期）。
- maintenance_road_work_record：日常养护作业记录（清扫、绿化等作业类型、作业时间、作业情况、作业图片）。
- ai_work_order：病害维修工单，由病害（disease）转来的小修/大中修工单。用户说"病害工单、维修工单、某条病害的工单"指本表。
- maintenance_work_order：养护工单，面向养护工程/日常养护的工单，与 ai_work_order 结构相同但业务来源不同。用户说"养护工单"指本表，不要选成 ai_work_order。
- gps_point（PG gps_points）：车辆 GPS 轨迹打点数据，存设备号、经纬度、速度、卫星数、方向、接收时间。属于 PostgreSQL gpsdb 库。
- inclination_point（PG inclination_points）：倾斜监测设备上报的数据点，存设备号、垂直/水平距离、x/y 坐标、当前与上一 GPS 位置、采集时间。属于 PostgreSQL gpsdb 库。用户说"倾斜监测、倾角、位移监测"指本表，本系统支持查询。

## 三、其他需要修的问题（按优先级）

### P0 整表/整类不通

1. 养护工单 maintenance_work_order 0/26：靠上面的表描述区分 ai_work_order 与 maintenance_work_order；选表器在两张结构相同的工单表之间要按"病害维修 vs 养护"业务词区分。
2. 病害/资产字典的元数据问题误走知识库：问"某类型的别名、描述、计算公式、计量单位、置信度阈值、是否主要关注、样图、颜色、启用状态"是查字典表（damage_dict / ai_asset_base），必须生成 SQL；只有问养护规范、评定标准、处置办法才走知识库。涉及字段 problem_alias、formula、length_unit、confidence、main_focus、problem_sample_image、enable_type、disease_categories_type、problem_code、asset_sample_image、asset_color、init_icon_image、init_image。
3. PG 倾斜监测表 4/11：把 inclination_point 完整纳入选表和数据源路由，不得回"不在查询范围/缺少倾斜监测表"；同时核对 PG Wren 模型名是 inclination_point（单数），判分和选表别按物理表名 inclination_points 找不到就放弃。

### P1 字段级系统性问题

4. 图片字段被主动放弃 SELECT：routes.picture、bridges.picture、tunnels.picture、slope.picture、maintenance_road_work_record.work_picture、两张字典的 init_image，表选对了但模型回复"该表不包含图片字段"就不查了。字段既然在 schema 里就必须 SELECT 并返回 URL，不允许模型凭先验断定"这表没有图片"。定距采集的 distance_capture_url/preview_url/pic_position 同理。
5. 近似字段被替换：问路段"车道特征 lane_type"（单车道/双车道/四车道…枚举），模型自作主张换成 lane_count（车道数）。点名字段必须按 schema 精确选择，不能拿语义相近的字段顶替。
6. 清单题被强制要求过滤条件：问"定距采集记录的图片地址逐条列出"，被要求"先给路线/时间/桩号范围"。"把 XX 逐条列出/全部调出来"是全表清单意图，SELECT 字段 FROM 表 LIMIT 500 合法，不强制 WHERE。
7. 非病害表的桩号/路线字段串到病害表：ai_distance_capture、ai_asset_main 的 routes_id、pile_distance、pile_meter、patrol_number 被引到 disease 或 patrol。选表确定后，字段必须取自该表自身。
8. Wren 编译臆造字段（实测报错 No field named X）：disease.lng_lat（实际 lng、lat 分开）、basic_facilities_slope.report_dept_name（实际 report_dept）、slope.memo（实际 remark）、slope.pile_number（不存在）、ai_asset_base.org_name（不存在）、project_manage_project_main.start_num（不存在）、ai_work_order.problem_status（工单表是 order_status，problem_status 在病害表）。编译报 No field 时要把该表真实列清单回喂模型重写，而不是放过或换表。
9. 跨库模型串用：MySQL 题的 fallback 里反复出现 table 'wren.public.disease' / 'wren.public.route' / 'wren.public.patrol' / 'wren.public.pile_point' not found——PG（public）Wren 项目里引用了 MySQL 模型。两个项目命名空间隔离，PG 只能引用 gps_point / inclination_point。

### P2 零散字段

- 路线/路段的 distance、abslute_distance、old_route_distance：模型倾向用计算列 route_length_km，点名要原始里程字段时应原样返回。
- tunnels.rfid_tag_num（标签号）、civil_construction_evaluate_unit（土建评定单位）、supervisor_unit_name（监理单位）、slope.maintenance_dept、patrol.equipment_id、ai_problem.problem_base_id 未选中，属字段登记表/选字段覆盖不全。
- pile_detail.lng 物理列注释被写成"精度"（应为经度），注释笔误会误导模型，建议改注释。
- 约 19 个系统字段（id、del_flag、tenant_id、create_by/update_by、create_time/update_time）table_miss，用户基本不会单独问，优先级最低；但"把整表明细全部调出来"SELECT * 时应能带回。

## 四、修复后验收

重跑 backend/test_all_592_fields.py（删除 docs/全字段逐题结果.jsonl 即全量重跑，保留则只补跑），应达到：

- maintenance_work_order 26/26、ai_problem_base ≥ 23/25、inclination_points ≥ 10/11。
- 图片类字段（picture/url/image/init_image）全部选中并返回链接。
- 不出现"资料中没有/不在查询范围/缺少 XX 表"这类对真实存在表和字典属性的回绝。
- 不出现 No field named 臆造列报错和 wren.public.<MySQL模型> not found 跨库报错。
- 整体通过率从 83.7% 提升到 95% 以上（剩余主要是用户不会问的系统字段）。

## 五、结论

逐字段实测表明：常用业务表和绝大多数字段（512/612）已经能被自然语言查到，空表也能正确定位并答空，"以后数据写入即可查"的方向成立。当前短板不是字段没接进 MDL，而是表级语义缺失——19 个模型描述全空，导致易混淆表（两张工单）、字典元数据、PG 倾斜监测表和一批图片字段选不准。优先把模型描述补齐、把字典属性留在 SQL 路径、让模型严格按 schema 选字段，就能以很小改动覆盖绝大部分失败用例。
