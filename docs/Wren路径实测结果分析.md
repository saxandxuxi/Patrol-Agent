# Wren 路径实测结果分析

## 测试概况

- 测试脚本：`backend/test_wren_path.py`
- 测试题数：90 道（单轮题，跳过多轮题）
- 测试模式：`engine_mode = wren`（强制走 Wren 路径）

## 总体统计

| 结果 | 数量 | 占比 | 说明 |
|------|------|------|------|
| ✅ Wren 成功 | 19 道 | 21% | 走了 Wren 编译路径并返回结果 |
| ⚠️ 走了模板 | 39 道 | 43% | 明明设了 wren 模式，但还是匹配到模板，直接走模板了 |
| engine=unknown/calibrated | ~20 道 | 22% | 知识问答、图片查询、上下文校准等非 SQL 路径 |
| ❌ 降级到内置 LLM | 1 道 | 1% | Wren 搞不定，降级到内置 LLM 直接写 SQL |
| ❌ 出错 | 0 道 | 0% | Wren 编译器基本不会报错，都能编译通过 |

---

## 关键发现一：模板路径太强势，Wren 根本没机会上场

**这是你一直觉得"Wren 没起作用"的根本原因。**

明明设置了 `engine_mode=wren`，但 39 道题（43%）还是直接走了模板。流程是：

```
用户问题 → 先匹配模板 → 匹配到就直接执行模板 SQL → 根本不进 Wren
```

模板路径是**前置拦截**的，不管你 engine_mode 设成什么，只要模板能匹配上，就直接走模板了。Wren 只有在模板匹配不上的时候才会被触发。

**走了模板的典型题目：**
- 简单数量统计（"有多少处泛油"）
- 简单条件查询（"K0+800到K0+900有多少"）
- 其他表的查询（资产、桥梁、隧道、工单、巡查任务等）
- 泛油/龟裂等常见病害类型的数量查询

---

## 关键发现二：Wren 能搞定什么，搞不定什么

### ✅ Wren 能搞定的（19 道成功）

| 类型 | 例子 | 效果 |
|------|------|------|
| 明细列表查询 | "列出 K0+100到K0+500 的泛油病害明细" | ✅ 正确 |
| 简单条件数量 | "面积超过10㎡的泛油有多少处" | ✅ 正确 |
| 日期过滤查询 | "7月29日当天发现了多少处泛油" | ✅ 正确 |
| 桩号区间查询 | "K1以西有多少处泛油" | ✅ 正确 |
| 设备过滤查询 | "某设备采集的病害6月7月各多少条" | ✅ 正确 |
| 多条件复合查询 | "置信度≥0.7且面积>5㎡的泛油，分路线呢？" | ✅ 正确 |
| 按星期/时间分布 | "病害大多集中在星期几" | ✅ 正确 |
| 按天统计 TOP | "7月泛油哪天最多？哪天第二多？" | ✅ 正确 |

### ❌ Wren 搞不定/答案不对的

| 类型 | 例子 | 问题 |
|------|------|------|
| **转弯计算类** | "两天泛油合计占7月总数的多少比例" | ❌ 答案不对，Wren 不会算占比 |
| **转弯计算类** | "6月和7月平均每天各多少条" | ❌ 答案不对，Wren 不会算日均 |
| **转弯计算类** | "全库泛油平均面积是多少？超过平均的有多少条？" | ❌ 答案不对，需要先算平均再当过滤条件 |
| **复合统计** | "每条路的总数、泛油数、未识别数各是多少" | ❌ 答案不对，多列聚合容易错 |
| **数据完整率** | "图片、经纬度、置信度、预览图各有多少" | ❌ 答案不对，多字段非空统计容易错 |
| **跨字段关联** | "设备采集的数据：各多少条？都是什么类型？有图片吗？" | ❌ 答案不对，多维度混合查询容易错 |
| **对比类问题** | "哪条路的泛油平均面积更大？" | ❌ 降级到 LLM |
| **范围统计** | "西乡段泛油覆盖了多长范围" | ❌ 答案不对，桩号 min/max 统计容易错 |

## 关键发现三：Wren 编译器很稳，但 LLM 写的 MDL-SQL 逻辑容易错

**好消息：** Wren 编译器几乎不会失败（0 道题出错），只要 LLM 写的 MDL-SQL 语法对，就能编译成物理 SQL 并执行。

**坏消息：** LLM 写的 MDL-SQL 经常逻辑不对：
1. 字段用错（比如该用中文病害类型名，用了代码）
2. JOIN 条件写错
3. 聚合函数用错
4. 转弯计算类问题，LLM 不知道怎么写 SQL（比如占比、日均）

---

## 关键发现四：其他表全部走模板，因为 MDL 里没有模型

走了模板的 39 道题里，有 20+ 道是查其他表的：
- 资产类型统计
- 桥梁/隧道/边坡数量
- 工单数量和状态
- 巡查任务统计
- 工程项目统计

这些表在 MDL 里**根本没有对应的模型**，所以 Wren 根本不知道这些表存在，只能走模板。

当前 MDL 里只有 `disease` 一个主模型，其他 10+ 张表的模型虽然定义了，但没有对应的 cube，LLM 也不知道怎么用。

## 需要完善的地方（按优先级排序）

### P0：先解决"Wren 没机会上场"的问题

**现状：** 模板前置拦截，匹配到就直接走模板，Wren 根本没机会跑。

**建议：**
1. 不要把模板路径放在最前面当拦截器
2. 改成：**先判断问题类型，如果是复杂/不常见的问题，走 Wren；简单常见问题才走模板**
3. 或者：**模板和 Wren 并行跑，哪个答案置信度高用哪个**
4. 至少：**模板匹配不上的时候，Wren 要能兜住**（现在已经是这样了，但模板覆盖太广）

### P1：完善 MDL，把其他表的模型加上 cube 和指标

**现状：** 只有 disease 一个 cube，其他表的查询全部走模板。

**建议：**
1. 给 route、patrol、asset、work_order 等表都加上 cube
2. 每个 cube 定义常用的 measures（数量、面积、时间等）和 dimensions（路线、类型、时间等）
3. 这样 Wren 才能处理其他表的查询，不用全部靠模板

### P2：转弯计算类问题交给拆分器，不要让 Wren 直接算

**现状：** 问"占比多少""日均多少""密度多少"，Wren 直接写 SQL 经常算错。

**建议：**
1. 拆分器先把转弯计算类问题拆成：查原始数据1 + 查原始数据2 + post_calc
2. 每个原始数据查询走 Wren（简单统计 Wren 很擅长）
3. post_calc 由代码或 LLM 计算，不用 Wren 算
4. 这样 Wren 只负责它擅长的：简单的 SELECT + WHERE + GROUP BY

### P3：Wren 路径的提示词要优化，加 RAGFlow 示例

**现状：** Wren 路径的 `generate_mdl_sql` 函数**根本没传 RAGFlow 示例**，LLM 写 MDL-SQL 时看不到任何示例。

**建议：**
1. 给 `generate_mdl_sql` 加上 examples 参数（从 RAGFlow 检索）
2. 在提示词里加几个正确的 MDL-SQL 示例
3. 明确告诉 LLM：只能用 MDL 里定义的模型名和字段名

### P4：加 Wren 路径的回归测试

**现状：** 没有专门测 Wren 路径的脚本，不知道每次改提示词/MDL 后 Wren 准确率是升是降。

**建议：**
1. 用 `backend/test_wren_path.py` 作为基础
2. 每次改 MDL 或提示词后，跑一遍回归测试
3. 跟踪 Wren 成功率和正确率的变化趋势

---

## 总结

Wren 现在的状态：
- ✅ 编译器很稳，几乎不会报错
- ✅ 简单查询（明细、简单条件、日期/桩号过滤）准确率很高
- ❌ 被模板路径"架空"了，大部分问题走不到 Wren
- ❌ 转弯计算类、复合统计类问题容易错
- ❌ 其他表没有 MDL 模型，全靠模板

**下一步最该做的：**
1. 先把模板前置拦截的逻辑改一下，让 Wren 有机会上场
2. 把转弯计算类问题交给拆分器，Wren 只做简单查询
3. 完善 MDL，把常用表的 cube 和指标加上
