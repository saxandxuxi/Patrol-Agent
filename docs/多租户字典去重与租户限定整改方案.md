# 多租户字典表去重与租户限定整改方案（给 codex）

## 一、现象（实测，库 new_four_road_base_ai）

1. 问"系统里一共定义了多少种病害类型" → 答 **42**；追问"这 42 种有哪些" → 却列出 **84 条明细**。
2. 连库核对 `ai_problem_base`（del_flag=0）：
   - 物理行数 **84**，`COUNT(DISTINCT problem_type)`=**42**，`COUNT(DISTINCT problem_code)`=**42**；
   - 每个中文名恰好 2 行、且 problem_code 完全相同（如"泛油"两行 code 都是 `10`），唯一差别是 `tenant_id`：
     - tenant_id=`1`（系统内置字典）42 行；
     - tenant_id=`8b304a5d7addb0dad4e0fbf9aa842f73`（业务租户，复制的一套）42 行；
   - 即 **42 种类型 × 两个租户各一份 = 84 行**。
3. 业务表 `ai_problem`（del_flag=0）1702 行，tenant_id 全部是业务租户 `8b304a5d…`；damage_type 实际存短码（`10`、`5`、`NULL`）。
4. **更严重的连带问题——JOIN 字典会一对多翻倍**：
   `SELECT COUNT(*) FROM ai_problem p JOIN ai_problem_base b ON p.damage_type=b.problem_code WHERE p.del_flag=0`
   返回 **1872**，而不是病害总数 1702。原因是每个 code 在字典里有两个租户两行，能 join 上的病害（936 行，damage_type 非 NULL）被翻成 1872，未识别类型（damage_type='NULL'，766 行）join 不上。
   这会让所有"病害 JOIN 类型字典但不限定租户/不去重"的计数、SUM(area)、AVG(area)、分组统计整体失真。
5. information_schema 中带 `tenant_id` 列的表有几十张（ai_problem、ai_problem_base、ai_asset_main、ai_maintain_patrol、basic_* 等），多租户复制是系统性现象，不只病害类型字典一张。

## 二、根因

- 基础字典随租户初始化被复制一份（系统租户 1 + 业务租户），同 code 同名；
- "多少种"用了 `COUNT(DISTINCT …)` 恰好抵消了重复，得到正确的 42；
- "列明细"是裸 `SELECT … FROM ai_problem_base`（或 JOIN 不带租户条件），把两套字典都取了出来 → 84；
- 模板/语义层生成的 JOIN 没有把租户条件当固定结构，存在一对多翻倍风险（现在内置模板用 `SELECT DISTINCT problem_code, problem_type` 子查询，因两列在两租户完全相同被 DISTINCT 压成一行，侥幸没翻倍；但这是隐式依赖，换个字典/租户数据不一致就会错）。

## 三、整改规则（通用，不写死某张表）

### 3.1 字典/基础表与业务表 JOIN：必须同租户关联，杜绝一对多
- 业务表 JOIN 字典/基础表时，固定带上同租户条件，例如：
  `JOIN ai_problem_base b ON p.damage_type=b.problem_code AND b.tenant_id = p.tenant_id AND b.del_flag=0`
  （能引用业务表别名时用 `b.tenant_id = p.tenant_id`；纯字典查询没有业务表别名时，用当前请求的租户 id。）
- 适用于所有"代码值→中文名"字典 JOIN：病害类型、病害大类、资产类型、设备、巡检状态等，不限于 ai_problem_base。
- 租户 id 从现有租户上下文取（请求/会话/配置里的当前租户），不要在代码里硬编码 `8b304a5d…`；单租户部署也要走同一套取值，保证以后加租户不改逻辑。

### 3.2 字典枚举"有哪些"：去重或限定单租户
- "列出所有病害类型/资产类型/状态枚举"这类查询，默认对 code（或 code+name）做 `DISTINCT`，或限定当前租户，保证每种只出现一行；
- "有多少种"与"列出种类"必须用同一套去重/租户口径，禁止一个 COUNT(DISTINCT)、一个裸 SELECT。

### 3.3 把租户条件提升为固定结构（和 del_flag 同级）
- 语义层 MDL、确定性模板、templatizer 自动挖槽：对带 tenant_id 的表，租户过滤属于**固定业务条件**，不是可变槽位，默认补齐、不允许挖成参数、也不允许漏掉；
- templatizer 挖槽时，`tenant_id = …` 应与 `del_flag=0` 一样识别为 fixed 结构保留；从问答对挖出的字典 JOIN SQL，若缺同租户条件，要么自动补、要么不允许 mature（避免把会翻倍的 SQL 固化成模板）。

### 3.4 自动模板/选项的字典去重
- templatizer 生成实体槽 options（病害类型等）时，按 code/label 去重并限定当前租户，不再把两个租户的重复项、以及 adsad213223 这类测试脏值内联进去（与《自动模板挖掘代码评审与整改方案.md》P1-2 合并实施）。

### 3.5 结果校验加一道"JOIN 翻倍"护栏
- 校验器/结果自检增加规则：当 SQL 对业务主表做 COUNT/SUM/AVG 且 JOIN 了字典/基础表时，用"不 JOIN 字典的主表计数"对一次总数；若 JOIN 后计数 > 主表实际行数，判定为一对多翻倍，判错并触发问题优化/重写，而不是把放大后的数字返回。
- 例：病害类问题 JOIN 类型字典后的 COUNT(*) 不应超过同条件 `ai_problem` 的行数。

### 3.6 空表/未来表同样适用
- 规则按"表是否有 tenant_id 列 + 是否字典/基础表"自动生效，不依赖现在有没有数据；以后其他租户/其他字典表有数据时，同样自动限定租户、自动去重，不需要逐表加关键词。

## 四、落地位置
- 语义层 MDL / Wren 模型关系：字典表与业务表的 join 关系补 tenant 等值条件（或在模型里把字典表按当前租户建成单一视图）。
- `nl2sql.py` 确定性模板、`build_template_sql`、条件拼装：JOIN 字典统一补同租户 + del_flag。
- `templatizer.py`：tenant_id 识别为 fixed；缺同租户 JOIN 的字典 SQL 不 mature；options 按租户+code 去重去脏。
- 结果校验（verify）：新增 3.5 的翻倍护栏。
- 字段目录/MDL：标注哪些是"每租户复制一份的字典表"，供选表与 JOIN 生成使用。

## 五、验收（连库断言）
1. "系统一共多少种病害类型"= 42；"这 42 种有哪些"返回 **42 行**（不是 84），每种类型一行。
2. 病害 JOIN 字典后的统计与不 JOIN 一致：
   - `ai_problem` del_flag=0 总数仍为 1702，不因 JOIN 类型字典变成 1872；
   - 西乡段泛油仍为 534（不翻倍为 1068）；
   - 总面积、平均面积与 JOIN 前同口径结果一致。
3. 任意带类型/大类名称的明细或分组 SQL，EXPLAIN/文本里都含 `b.tenant_id = p.tenant_id`（或当前租户过滤）且 `b.del_flag=0`。
4. 自动模板 options 中病害类型无重复、无测试脏值、只含当前租户。
5. 人为构造一条"漏租户条件 JOIN 字典"的查询，校验器能报翻倍并拦截，不返回放大结果。
6. 切换/新增租户后，查询只返回当前租户数据，不串租户、不重复。
