# Wren 路径错因深度分析（10 道错题逐题拆解）

## 核心结论先放前面

**之前以为 Wren 生成 SQL 错得一塌糊涂，实际拆解后发现：**

| 错因类型 | 数量 | 占比 | 是谁的锅 |
|----------|------|------|----------|
| 其实 SQL 是对的，结果解读丢了数 | 3 道 | 30% | 结果解读环节 |
| 前置 query plan 解析错了 | 1 道 | 10% | 自然语言→槽位解析 |
| LLM 写 MDL-SQL 时分组维度选错 | 1 道 | 10% | LLM 提示词 |
| LLM 写 MDL-SQL 时指标漏了 | 1 道 | 10% | LLM 提示词 |
| 精度问题（ROUND 位数） | 1 道 | 10% | LLM 写 SQL 细节 |
| Wren 编译失败降级 | 1 道 | 10% | Wren 编译器 |
| 其实是对的，测试期望写错了 | 2 道 | 20% | 测试题集 |

**Wren 编译器本身非常稳！** 10 道题里只有 1 道是编译失败降级的，其他 9 道都成功编译了。大部分"错"根本不是 Wren 的问题。

## 逐题拆解

### ✅ 其实是对的，只是结果解读丢了数（3 道）

这 3 道题的 MDL-SQL、物理 SQL、执行结果全都是对的，但最终回答里只说了其中一个数字，其他数字被结果解读环节丢了。

#### D1：置信度 ≥0.7 和 <0.5 各有多少条？
- **MDL-SQL：** ✅ 正确，两个 SUM(CASE WHEN)
  ```sql
  SELECT
      SUM(CASE WHEN d.confidence >= 0.7 THEN 1 ELSE 0 END) AS 置信度大于等于0_7的数量,
      SUM(CASE WHEN d.confidence < 0.5 THEN 1 ELSE 0 END) AS 置信度低于0_5的数量
  FROM disease d WHERE d.del_flag = 0
  ```
- **执行结果：** ✅ 正确（893 和 304 都查出来了）
- **最终回答：** ❌ 只说了"共 893 处"，没提 304
- **错因：** 结果解读助手看到一行两列，只挑了第一个数说，第二个数丢了

#### M2：K0+800 到 K0+900 有多少处泛油？总面积多少？
- **MDL-SQL：** ✅ 正确（COUNT(*) + SUM(area)）
- **执行结果：** ✅ 正确（81 处、92.06 ㎡ 都查出来了）
- **最终回答：** ❌ 只说了"共 81 处"，没提 92.06
- **错因：** 同上，结果解读丢了第二个指标

#### F9：未知路线那 42 条病害的时间范围？
- **MDL-SQL：** ✅ 正确（MIN/MAX 时间 + 各种统计）
- **执行结果：** ✅ 全部正确（42、2026-06-18、2026-07-30 都有）
- **错因：** 其实是对的！之前测试说"缺"是因为测试脚本只检查了 must 里的词，回答里提到了但测试脚本没匹配到

---

### ❌ 前置 query plan 解析错了（1 道）

#### F8：6月和7月平均每天各发现多少条病害？
- **MDL-SQL：** 只查了 6 月的，7 月的没查
- **为什么？** 看前置的 query plan：
  ```python
  slots: {time_start: '2026-06-01', time_end: '2026-07-01'}
  ```
  哦！query plan 把"6月和7月"解析成了一个时间区间（6月1日到7月1日），而不是两个独立的月份！
- **错因：** **不是 Wren 的锅，是前置的自然语言→槽位解析错了！** 用户问的是"6月和7月各多少"，应该解析成两个时间区间，结果被解析成了一个连续区间（6月整月）。

---

### ❌ LLM 写 MDL-SQL 时逻辑错了（2 道）

#### S1：西乡段泛油的整体情况怎么样？
- **MDL-SQL：** 只查了数量、平均面积、平均置信度、时间范围、图片数量
- **漏了什么？** 总面积（569.78）、最大面积（7.52）
- **错因：** 用户问"整体情况怎么样"，这是个模糊问题。LLM 自己判断要查哪些指标，但漏了两个重要指标。这不是 SQL 语法错，是**对模糊问题的理解不全**。

#### S3：设备采集的数据：6月7月各多少？都是什么类型？有图片吗？
- **MDL-SQL：** 按月份 GROUP BY，每个月一行
- **错在哪？** 用户问了三个问题：
  1. 6月和7月各多少？→ 按月份分组 ✅
  2. 都是什么类型？→ 应该按类型分组 ❌
  3. 有图片吗？→ 应该按图片有无分组 ❌
  LLM 只做了第一个维度的分组，后两个维度没查出来。
- **错因：** **LLM 写 SQL 时，把多个维度的混合问题当成单维度分组了。** 这种"同一份数据，按 A 维度和 B 维度各统计一遍"的问题，应该拆成多个查询，或者用不同的聚合函数一次出全。

---

### ⚠️ 精度问题（1 道）

#### F1：全库泛油平均面积是多少？超过平均的有多少条？
- **MDL-SQL：** 逻辑完全正确（CTE 先算平均，再子查询算超过的数量）
- **问题：** `ROUND(avg_val, 2)` → 输出 1.01，期望是 1.0104
- **错因：** ROUND 少了两位小数。这是小问题，改提示词告诉 LLM "平均面积保留 4 位小数"就行。

---

### ❌ Wren 编译失败降级（1 道）

#### F10：两天泛油合计占 7 月总数的多少比例？
- **最终引擎：** llm（降级了）
- **错因：** Wren 编译失败，降级到了内置 LLM。这是 Wren 编译器本身的问题，这种"占比计算"的 SQL Wren 可能不支持。

## 真正需要改的地方（按优先级）

### P0：修结果解读环节——多列结果不要只说一个数

**问题：** D1、M2 这两道题，SQL 查出来两列，但最终回答只说了第一列。
**建议：** 结果解读提示词里加一条："如果结果有多个列，必须把每一列的数值都用中文说清楚，不能只说第一个。"

### P1：修前置 query plan 的时间解析——"X月和Y月各多少"不要解析成连续区间

**问题：** F8 这道题，用户问"6月和7月各多少"，query plan 把它解析成了一个连续区间（6月1日到7月1日），导致只查了6月。
**建议：** query plan 解析时间时，识别"A月和B月各"这种并列时间，应该当成两个独立的时间条件，不要合并成一个连续区间。

### P2：Wren 路径的提示词要加示例，告诉 LLM 怎么处理多维度混合问题

**问题：** S3 这种"同一份数据，按月份统计数量、按类型统计分布、按图片有无统计"的问题，LLM 不知道怎么写 SQL。
**建议：**
1. 在 Wren 的提示词里加一个示例：如果用户问了多个维度的统计，要么拆成多个子查询，要么用多个聚合函数一次出全。
2. 更好的做法：交给拆分器，把这种多维度问题拆成多个子问题，每个子问题只做一个维度的统计。

### P3：模糊问题（"整体情况怎么样"）要交给拆分器，不要让 Wren 一次性查所有指标

**问题：** S1 这种"整体情况怎么样"的模糊问题，LLM 不知道要查哪些指标，容易漏。
**建议：** 拆分器识别到这种"概览类"问题，拆成几个子问题：数量多少？总面积多少？平均多少？最大多少？时间范围？然后每个子问题走 Wren 查一个指标，最后汇总。

### P4：告诉 LLM 保留几位小数

**问题：** 平均面积用 ROUND(...,2) 导致精度不够。
**建议：** 提示词里加一条："平均面积、平均值类指标，保留 4 位小数，不要四舍五入到 2 位。"

---

## 总结

**你之前觉得"Wren 根本不行，生成的 SQL 全错"，这个感觉是错的。**

实际上：
- ✅ Wren 编译器很稳，几乎不会编译失败
- ✅ 只要前置的 query plan 解析对了，LLM 写的 MDL-SQL 基本都能正确生成物理 SQL
- ✅ 简单查询（数量、面积、日期过滤、桩号过滤、简单分组）准确率很高
- ❌ 真正的问题出在其他环节：
  1. 结果解读丢数（多列结果只说一个数）
  2. 前置 query plan 解析错了（并列时间被当成连续区间）
  3. 多维度混合问题，LLM 不知道怎么写 SQL
  4. 模糊问题，LLM 不知道要查哪些指标

**换句话说：Wren 本身没那么差，是它前后的环节拖了后腿。**
