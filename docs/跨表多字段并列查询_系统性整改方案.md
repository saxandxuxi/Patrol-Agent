# 跨表多字段并列查询 · 系统性整改方案

> 针对的问题类型：用户在一句话里同时要**多张表的多个字段**，如"养护任务编号和病害描述""每个路段多少米，以及每条路线的起始桩号""收藏的病害里工单状态和病害来源分别是什么"。
> 现状：拆开来问都能答，合在一起问就报错/反问。本方案从数据结构上解决，不是逐个修补。

---

## 一、问题定义（这一类问题的通用模式）

**模式**：一句话里包含 ≥2 个字段诉求，且这些字段**分散在 ≥2 张表**中，字段之间可能有关联也可能只是并列。

| 例子 | 字段1（表） | 字段2（表） | 关系 |
|---|---|---|---|
| 养护任务编号和病害描述 | task_number（ai_maintain_patrol） | problem_describe（ai_problem） | 可关联（patrol_id） |
| 每个路段多少米，每条路线起始桩号 | distance（sections） | start_num（routes） | 无关联，并列 |
| 收藏的病害里工单状态和来源 | problem_status（ai_problem） | problem_source（ai_problem） | 同表（不算跨表） |
| 桥梁的技术等级和隧道的通风方式 | tech_grade（bridges） | ventilate_mode（tunnels） | 无关联，并列 |
| 西乡段病害的类型名称和计算公式 | damage_type（ai_problem） | formula（ai_problem_base） | 字典表关联 |

**关键特征**：用户不是在问"一个主体的多个属性"，而是在问"多个东西各自的属性"，或者"一个东西的属性散在多张表"。

---

## 二、根因（三层叠加，任何一层漏了都不行）

### 层 1：plan 数据结构只支持单主体
`nl2sql.build_query_plan` 输出的 plan 里 `subject` 是**单个字符串**（如 "disease"/"route"），不是列表。
→ 一个 plan 只能对应一张主表，天然表达不了"查 A 表的 X 字段 + B 表的 Y 字段"。

### 层 2：字段触达只定一个 top_table
`field_grounding.ground()` 最终只输出一个 `table`（落点表），并且**落点表定了之后，列证据只留这张表的**（代码 279-280 行 `scored = [item for item in scored if item["table"] == top_table]`）。
→ 即使字段触达发现了 B 表的列，只要 top_table 是 A，B 表的列就被扔掉。

### 层 3：复合拆分器可能漏拆
`orchestrator.decompose`（LLM 拆分）和 `cross_db.decompose_cross_db` 主要针对：
- 跨库（MySQL vs PostgreSQL）
- 数据+知识混合
- 明显的多步推理

**但"同库跨表多字段并列"不在拆分器的重点识别范围内**，LLM 经常当成单任务处理 → 走单表路径 → 查不到 → 反问用户。

---

## 三、系统性解决方案（三层一起改）

### 层 1：plan 扩展——支持多表字段声明

**文件**：`nl2sql.py` `build_query_plan` 的输出结构 + 对应提示词

**改法**：plan 增加 `fields` 数组，每个元素声明一个字段诉求及其归属表：
```json
{
  "subject": "multi",
  "fields": [
    {"name": "task_number", "label": "养护任务编号", "table_hint": "ai_maintain_patrol"},
    {"name": "problem_describe", "label": "病害描述", "table_hint": "ai_problem"}
  ],
  "conditions": [...],
  "relation": "parallel"  // parallel（并列）/ joined（关联）/ lookup（字典表）
}
```
- `subject: "multi"` 表示这是跨表多字段问题；
- `fields[].table_hint` 是 LLM 根据字段名/业务语义猜的归属表（可被字段触达修正）；
- `relation` 表示字段之间的关系类型（见层 2）。

**提示词补充**：在 planning 提示词里加 few-shot 例子，明确"当问题要的字段明显在不同表时，输出 multi subject + fields 数组"。

### 层 2：字段触达扩展——多表字段检测 + 分类处理

**文件**：`field_grounding.py` + `agent.py` 执行链路

**改法**：字段触达不再只输出一个 top_table，而是输出 `table_fields` 映射（表 → 该表命中的列）：
```python
ground() 返回增加：
"table_fields": {
    "ai_maintain_patrol": [{"column": "task_number", "label": "任务编号", "score": 4.0}],
    "ai_problem": [{"column": "problem_describe", "label": "病害描述", "score": 3.0}]
}
```

然后在执行链路里，根据 `relation` 分三类处理：

#### 类型 A：并列（parallel）——字段之间无关联
**判断**：fields 分属多张表，且表之间没有外键关联，问题里没有"的/对应/关联"等连接词。
**处理**：拆成多个独立子查询，每个子查询查一张表，最后合并回答。
**例子**："每个路段多少米，每条路线起始桩号" → ①查 sections.distance ②查 routes.start_num → 合并。

#### 类型 B：关联（joined）——字段之间可通过外键/JOIN 关联
**判断**：fields 分属多张表，且表之间有外键（或 relationships.yml 定义了关系），问题里有"的/对应/那次"等连接词。
**处理**：自动生成 JOIN SQL，一次查询拿回所有字段。
**例子**："那次养护任务发现的病害描述" → JOIN ai_maintain_patrol + ai_problem ON patrol_id。
**兜底**：如果 JOIN 条件不明确（外键缺失），退化为类型 A（拆成两个子查询，用第一个的结果做第二个的过滤条件）。

#### 类型 C：字典表（lookup）——其中一个字段在字典/基础表
**判断**：其中一张表是 `*_base` 字典表（如 ai_problem_base），且另一张表有外键指向它。
**处理**：用子查询或 LEFT JOIN 字典表，把编码翻译成中文/描述。
**例子**："病害的类型名称和计算公式" → ai_problem JOIN ai_problem_base ON damage_type=problem_code。

**不再反问用户**：只要 fields 里每个字段都能在某张表找到对应列，就自动处理；只有当某个字段完全找不到对应列时，才反问。

### 层 3：拆分器增强——识别跨表多字段并列

**文件**：`orchestrator.py` 拆分提示词 + `cross_db.py`

**改法**：
1. 在 `orchestrator.decompose` 的提示词里加一类拆分模式："跨表多字段并列"——当问题要的字段分属不同业务实体（任务/病害/路线/桥/隧），拆成多个子任务；
2. 加 few-shot 例子（3-5 个，覆盖并列/关联/字典表三种）；
3. `cross_db.decompose_cross_db` 里，单库内如果 `orchestrator.decompose` 返回 1 条但 plan.subject=="multi"，**强制按 fields 拆成多条子任务**（不依赖 LLM 第二次判断）。

## 四、判断逻辑流程图（伪代码）

```
用户问题
  │
  ▼
build_query_plan → plan
  │
  ├─ plan.subject != "multi" → 走原有单表链路（不变）
  │
  └─ plan.subject == "multi" → 跨表多字段链路
       │
       ▼
  field_grounding 输出 table_fields（多表→多列）
       │
       ▼
  每个 field 都能找到对应列？
       ├─ 否 → 反问缺哪个字段（只问真正缺的）
       │
       └─ 是 ▼
  判断 relation 类型：
       ├─ parallel（并列无关联）→ 拆成 N 个子查询，各查各的表，合并回答
       ├─ joined（有关联/外键）  → 自动 JOIN，一次查询
       └─ lookup（字典表）       → 子查询/LEFT JOIN 字典表
       │
       ▼
  执行 → 结果合并 → 自然语言总结（标明每个字段来自哪张表）
```

## 五、验收（多个例子，覆盖三种类型）

### 类型 A（并列）
1. "每个路段多少米，以及每条路线的起始桩号" → 拆成 sections.distance + routes.start_num，不反问，不查桩点表。
2. "桥梁的技术等级和隧道的通风方式" → 拆成 bridges.tech_grade + tunnels.ventilate_mode。

### 类型 B（关联）
3. "养护任务编号和病害描述" → 识别为可关联（patrol_id），JOIN ai_maintain_patrol + ai_problem，返回任务编号+对应病害描述。
4. "西乡段7月那次巡检的病害编号和采集时间" → JOIN patrol + problem。

### 类型 C（字典表）
5. "病害的类型名称和计算公式" → ai_problem JOIN ai_problem_base。
6. "资产的类型名称和资产描述" → ai_asset_main JOIN ai_asset_base。

### 回归
7. 单表多字段（"收藏的病害里工单状态和来源"）→ 走原有单表链路，不退化。
8. 之前通过的所有题不退化。

---

## 六、不做的（明确边界）
- 不做自动推断 JOIN 条件（外键缺失时不瞎猜，退化为并列拆分）；
- 不做跨库 JOIN（MySQL 和 PostgreSQL 之间不 JOIN，只分别查再合并）；
- 不改单表链路（plan.subject != "multi" 时完全不变）；
- 不做自然语言到 JOIN 条件的 LLM 生成（用外键/relationships.yml 的确定性关系，不调 LLM 猜）。

---

## 七、实施顺序建议
1. **第一步**：plan 扩展 `subject: "multi"` + `fields` 数组 + 提示词 few-shot（层 1）；
2. **第二步**：字段触达输出 `table_fields`，执行链路加三类处理（层 2）——这是核心；
3. **第三步**：拆分器提示词增强 + cross_db 强制拆分（层 3）——兜底，防止 LLM 漏拆；
4. 每步做完跑验收例子，确认不回归再进下一步。
