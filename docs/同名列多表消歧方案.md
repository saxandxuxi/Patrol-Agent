# 同名列多表消歧（给 codex）

## 一、问题
库里大量列名/列注释跨表重复，ground（字段触达）在"用户没点名表"时，同名列同分只能靠表级词重合或表名字典序拍板，容易选错表；而且同名列在不同表语义完全不同。

## 二、实测：同名列分布
- `lat`（纬度）：4 张表 = ai_asset_main、ai_distance_capture、ai_problem、basic_facilities_sections_pile_detail
- `lng`（经度）：4 张（同上）
- `lane_count`（车道数）：3 张 = basic_facilities_routes、basic_facilities_sections、basic_facilities_tunnels
- `pile_number`（桩号）：3 张 = ai_asset_main、ai_distance_capture、ai_problem
- `pile_distance`：3 张；`start_num/end_num`：5 张

## 三、语义不同的同名列（最容易错）
- `ai_problem.lat/lng` = **病害发生点**的经纬度（"病害都分布在哪一侧""病害集中在路的哪边"该用它）
- `basic_facilities_sections_pile_detail.lat/lng` = **路线桩点**的经纬度（"西乡段的纬度范围/走向"该用它）
- `lane_count`：routes（整条路）/ sections（路段）/ tunnels（隧道）三个粒度不同

## 四、现在的逻辑与缺陷
field_grounding.ground：
1. 表级按"表名/表注释词重合"选 top_table；
2. top_table 定后（约 219-220 行）只留该表列，其他表同名列滤掉。

缺陷：
- 用户没点名表时（"纬度范围"），多张表的 lat 列同分（列名命中都 +3），表级"纬度"不是表名词帮不上，最后按表名字典序排（ai_asset_main < ai_distance_capture < ai_problem < sections_pile_detail），**字典序拍板，不是按语义**；
- 这次"纬度范围"碰巧选对 sections_pile_detail 是蒙的；换"病害分布在哪侧"就该用 ai_problem.lat，现在没有机制区分。

## 五、整改
1. **同名列多表时，按已识别的 subject 消歧**：
   - subject=disease（病害/巡检/工单）→ 同名列优先 ai_problem（病害点 lat/lng、病害桩号）；
   - subject=route/section（路线/路段台账）→ 优先 routes/sections 及 sections_pile_detail（路线走向 lat/lng、车道数）；
   - 隧道/桥梁/资产类 → 对应表。
2. **真分不清时别默默选一个**：同名列在多个候选表都高分、且 subject 不足以判定时，把歧义写进 plan["grounded"]（如 "lat 候选：ai_problem=病害点 / sections_pile_detail=桩点"），让规划 LLM 看到歧义再判，而不是字典序定死。
3. **表级打分别只看表名词重合**：同名列相同时，把"该列对当前 subject 的归属"加权，避免 ai_asset_main 这类字典序靠前的空表被选中。
4. 已有数据的表优先：同一列在多张表都有数据时，按"这张表对当前 subject 是不是主表"选，不按表名排序。

## 七、另一个隐患：偏 MySQL、PG（GPS）与冷门表覆盖
实测现状：
- MySQL 字段目录已收录 **17 张表**，含 basic_facilities_slope（边坡台账）、basic_facilities_tunnels（隧道台账）、basic_facilities_bridges（桥梁）、maintenance_project / project_manage_project_main（养护/工程项目）——表层面没漏。
- PostgreSQL 只有 **2 张表**：gps_points（GPS 轨迹点）、inclination_points（倾斜监测点），且当前都是空表（agent.py 注释明说）。

隐患 1：PG 被"偏 MySQL"规则压着。cross_db.py 的 `pg_evidence_weak`（约 164 行）：MySQL 表得分≥8 且是 PG 2 倍时，直接砍掉 PG、拉回 MySQL。后果就是之前踩过的"问 GPS 轨迹，却查了 MySQL 病害表的 lat/lng"——因为 MySQL 病害表也有经纬度、得分高，GPS 类问题被拽到 MySQL。PG 表以后有数据了，这条规则仍会把它当空表砍掉。

隐患 2：边坡/隧道/工程表虽在目录，但通用算子/模板/示例现在几乎只服务"病害+路线"这一组；以后问"隧道的通风方式""边坡的坡度分布"，会落到病害主表或答不出来。

整改：
1. PG 不再"默认砍"：gps_points/inclination_points 一旦有数据（行数>0），pg_evidence_weak 对 GPS/轨迹/定位类问题不再砍 PG；只有真没落点才回 MySQL。
2. POSTGRESQL_TERMS 保持 gps/轨迹/定位/倾角/坐标/经纬度；但"坐标/经纬度"这种 MySQL 病害表也有的词，要按上下文判：问"轨迹/行车路线/巡检路径"→PG；问"病害分布/病害在哪一侧"→MySQL 病害点。
3. 边坡/隧道/工程表：字段目录已收录，补通用算子的"某台账表明细/某列分布"入口，别只服务病害+路线；新表进 catalog 后自动可达，不靠手写。

## 六、验收
1. "西乡段的纬度范围" → 落 sections_pile_detail.lat（路线走向），不落到 ai_problem；
2. "病害都分布在路的哪一侧" → 落 ai_problem.lat/lng；
3. "西乡段和恒明珠各几车道" → lane_count 落 routes（整条路），不误落 sections；
4. 同名列多表时不再按表名字典序拍板；分不清的歧义要进 plan 让 LLM 判，不静默选错。

## 七、事实核对（codex 实测，2026-09-23）

结论先放这儿：**§二 的数据全对，§三 的语义差异成立，§四 的"缺陷"描述一半对一半不对**；
而且真正的问题不是方案写的那个。

### 7.1 §二 同名列分布：逐项核对全对

```
lat/lng          4 张 = ai_asset_main / ai_distance_capture / ai_problem / sections_pile_detail
lane_count       3 张 = basic_facilities_routes / basic_facilities_sections / basic_facilities_tunnels
pile_number      3 张 = ai_asset_main / ai_distance_capture / ai_problem
pile_distance    3 张（同上）
start_num/end_num 5 张 = ai_distance_capture / ai_problem / routes / sections / slope
```

（另：全库 17 张表、592 列、去重列名 321 个，其中 **93 个列名跨 ≥2 张表**。）

### 7.2 §三 "同名列语义不同"：成立，标签实测如下

```
ai_asset_main.lat                  label=资产纬度      comment=资产纬度
ai_distance_capture.lat            label=定距采集纬度   comment=定距采集纬度
ai_problem.lat                     label=病害纬度      comment=病害纬度
basic_facilities_sections_pile_detail.lat  label=纬度  comment=纬度
```

### 7.3 §四 "字典序拍板 / 蒙对"：一半不对

方案说"多张表的 lat 列同分（列名命中都 +3），最后按表名字典序排，这次选对是蒙的"——**实测不是这样**：

```
西乡段的纬度范围 → 落点 = basic_facilities_sections_pile_detail（4.0 分）
   该表 lat 的 label 恰好是 2 个字的"纬度" → field_grounding._phrase_hit 给 +3（列名硬命中）
   其余三张表的 label 是"病害纬度/资产纬度/定距采集纬度"（4~6 字），匹配不上用户的裸词"纬度" → 只拿 1.0（列注释重合）
```

所以它**不是同分、也不是字典序**，而是"某张表的列注释恰好是短名"拿到的硬命中。这个机制能选对，
但**确实不靠语义**（靠注释长短），方案说"机制脆"这点成立，说"蒙对"不准确。

真正"同分 → 字典序拍板"的是 `lane_count`：

```
西乡段和恒明珠的车道数分别是多少 → 落点 = basic_facilities_routes
   三张表（routes/sections/tunnels）的标签都是"车道数"，全部 +3 同分
   scored.sort 的次键是表名 → basic_facilities_routes < ..._sections < ..._tunnels
   → routes 胜出靠的是字母序（这次恰好是对的粒度）
```

而"病害都分布在路的哪一侧"实测**落到 ai_problem 了**（表级"病害"词重合），所以方案说
"现在没有机制区分"不成立——§六 验收 1、2 目前都是过的，验收 3 只在"表级词也命中"时才过。

### 7.4 方案没写到、实测发现的真问题：单字枚举值假命中

`field_grounding._code_value_hits` 判"用户说了某个枚举中文值"用的是 `value in text`，
而库里有 **21 列的枚举取值是单字**（`是`/`否`/`无`：is_built、main_focus、is_close、built、
is_rail_road、is_lighting…）。中文句子几乎都含"是"，于是：

```
西乡段和恒明珠分别是几车道   ← "分别**是**" 里的"是"命中了 6 个无关列（各 +1.5）
                              → 列级候选被这批垃圾占满、且没有一个列达到 3.0 的门槛 → 落点表 = 空
宝安大道西乡段的基本情况是什么样的？  ← 同样命中 basic_facilities_bridges.is_rail_road
哪些路段的土路肩是已硬化的          ← 命中 basic_facilities_sections.built
10 条常见问题里 4 条的返回列里混进了这类假命中
```

这比方案里说的"字典序拍板"更值得先修：`lat` 那类已经被列名硬命中解决了，
真正会把落点带偏的是这个。**（本轮只核对、没改，等确认。）**

### 7.5 对 §五 整改的建议

1. 先修 7.4 的单字枚举假命中（一行守卫：枚举值短于 2 字不参与命中），它影响面最大；
2. 再做 `lane_count` 这类"标签同名 → 真同分"的 subject 消歧（方案 §五.1 的方向可行）；
3. `lat/lng` 这类不需要额外机制——已验证会按列注释长短选表，改成 subject 加权反而可能把
   "西乡段的纬度范围"从桩点表带回病害表。

## 八、本轮实施记录（codex，2026-09-23）

### 8.1 §7.4 单字枚举假命中：已修

`field_grounding._code_value_hits` 现在要求枚举取值 **≥2 个字**才算命中（"全面通风"这类多字值照常命中，
"是/否/无"不再参与）。实测 12 条常见问题 **0 条被污染**（改之前 4/10 被污染）：

```
宝安大道西乡段的基本情况是什么样的？   → 不再命中 basic_facilities_bridges.is_rail_road
西乡段和恒明珠分别是几车道             → 不再被 6 个无关布尔列占满候选
隧道里哪些是全面通风                   → ventilate_mode 仍命中（多字枚举没被误伤）✓
```

### 8.2 §五.1/.3 同分消歧：不再按表名字典序

`ground` 的列级排序次键从"表名（字母序）"改成"**表级检索排名**"（`wren_engine.search_models`
给出的语义表序）：

```
西乡段和恒明珠的车道数分别是多少 → 落 basic_facilities_routes.lane_count
  （routes/sections/tunnels 的"车道数"同分；以前靠 basic_facilities_routes 字母序靠前赢，
    现在靠表级语义排名赢 —— 结果一样，但不再是运气）
```

### 8.3 §五.2 歧义不再静默：记进结果 + 日志（但**不喂给规划 LLM**）

`ground()` 的返回多了 `ambiguous` 字段：同名列跨多张表、分并列、且表级也没证据时记下
`{"column": ..., "candidates": [{"table","label"}...]}`，并写一条
`column_ambiguous_across_tables` 日志。

**为什么没喂给规划 LLM**：§六 那种"把 ground 前置到规划之前"上一轮已实测有害（把"基本情况"
带到桥梁表），所以 ground 仍在规划之后；歧义目前只用于观测。真要让它影响答案，应该喂给**写 SQL
那一步**（那里已经有 plan），这属于另一件改动。

### 8.3b 表级落点也改成按语义表序（"基本情况"不再落到桥梁表）

§8.2 只改到**列级**排序；表级落点（`top_table`）当时还是"谁先遍历到谁赢"，于是
"宝安大道西乡段的基本情况是什么样的？"因为桥梁表注释 `基本设施_桥梁表` 和路线表注释
`基本设施_路线表` 都含"基本"而打平，按目录顺序落到了**桥梁表**。现在表级同分同样比
**表级检索排名**：

```
宝安大道西乡段的基本情况是什么样的？ → basic_facilities_routes ✓（修前 basic_facilities_bridges）
各条路线分别有多少座桥梁？          → basic_facilities_bridges ✓（没被带偏）
```

### 8.4 §七 隐患 1/2（PG 被 MySQL 压着）：已改

`cross_db` 现在把 PG 证据分两级：

```python
_PG_CONTEXT_ONLY_TERMS = ("坐标", "经纬度")        # 两边都有的词：必须带上下文
_PG_TRAJECTORY_TERMS  = ("轨迹", "路径", "行车", "行驶", "巡航", "漂移")
```

- **强词（gps/轨迹/定位/倾角/两张表名）→ 表级分再高也不砍 PG**。实测
  "西乡段的轨迹坐标点有多少个"原来会被 MySQL 病害表的"坐标"列顶到 8 分以上、PG 被砍掉，
  结果拿病害点当轨迹点答；现在走 PG。（这一条**没有**按 §七.1 那样"等 PG 有数据才生效"——
  实测 PG 空表时这个坑就已经在发生了，与表里有没有数据无关。）
- **弱词（坐标/经纬度）→ 只在带轨迹上下文、且 PG 表里确实有数据时才算 PG**；
  否则按 MySQL 处理。实测：

```
设备 8c5f 的 GPS 点位有多少条？  → postgresql ✓
西乡段的轨迹坐标点有多少个？      → postgresql ✓（修前 mysql ✗）
倾斜监测点里的接收时间          → postgresql ✓
西乡段的经纬度范围              → mysql ✓（修前 postgresql ✗ —— 拿空表 GPS 当路线经纬度）
宝安大道西乡段的桩点经纬度      → mysql ✓
西乡段的病害都分布在路的哪一侧   → mysql ✓
```

配套加了可调项 `PG_PROBE_TTL_SECONDS`（PG "有没有数据"的探测缓存，默认 300 秒）。

### 8.5 §七 隐患 3（冷门表只有一个"明细"入口）：已补"某列分布"

`capabilities` 新增一条入口：`shape=distribution` 但语义层没给 `group_by` 时，
拿**字段触达在这张表上挑出的那一列**当分组维度，产出 `generic_dist:<表>:<列>`
（最高分列不唯一就弃权，不许拿别的列顶替）。实测：

```
各隧道的照明情况       → generic_dist:basic_facilities_tunnels:is_lighting ✓
桥梁的技术评定等级分布  → generic_dist:basic_facilities_bridges:tech_level ✓
边坡的坡度分布         → 无候选（**正确**：边坡表里没有坡度列，只有高度/长度/类型/防护工程）
养护项目的投资额分布    → 无候选（**正确**：养护项目表里没有投资额列）
```

后两条是"查不到就该弃权"的正例——以前和现在都不给候选，区别是现在**能确认**是"库里真没这列"，
而不是"通用算子没覆盖这张表"。
