## 一、先用一句话理解

巡检智能体现在做的不是“让大模型直接猜一条 SQL”，而是：

> 把用户问题变成结构化查询单，先检查查询单是否合法，再把它编译成 SQL，
> 执行后检查真实结果，最后根据真实数据生成回答。

可以把它想成去医院检查：

1. 用户描述症状。
2. 导诊员判断要查什么。
3. 医生开检查单，不能随便写医院里不存在的项目。
4. 检验科按单执行。
5. 审核员检查报告是否完整、单位是否正确。
6. 最后由医生解释报告。

大模型负责“理解和解释”，代码负责“校验、执行和判定事实”。

## 二、当前有两条执行路线

### 2.1 当前单轮数据主路线

设置项 `single_turn_compiler_enabled` 打开后，检测到 `data`、`analysis`
或 `composite` 类问题时，优先进入单轮查询编译器。

```text
用户问题
  -> 判断问题大类
  -> 读取真实数据库字段目录
  -> LLM 生成 IntentContract + QuerySpec
  -> 代码解析路线、时间、枚举、编号
  -> 代码校验 QuerySpec
  -> LLM 独立审查查询计划
  -> 代码校验审计补丁
  -> 查找合适模板并要求用户确认
  -> 编译 SQL
  -> 执行 SQL
  -> 生成 ExecutionObservation
  -> 确定性验收
  -> 后置计算（如果需要）
  -> 生成 AnswerPackage
```

这是目前巡检数据问题的主路线。

相关入口：

- [`backend/app/services/agent.py`](../backend/app/services/agent.py)
- [`backend/app/query/service.py`](../backend/app/query/service.py)

### 2.2 旧 ReAct 路线

项目里还保留一套 ReAct 执行器和结构化修复器，主要特征是：

```text
执行一个步骤
  -> 得到 Observation
  -> 发现 failure
  -> 根据 failure_code 从 YAML 找候选工具
  -> Controller LLM 选择动作
  -> 代码检查工具名、参数、重复调用
  -> 有限次数重试
  -> 成功继续；失败阻断依赖步骤
```

相关文件：

- [`backend/app/services/react_agent.py`](../backend/app/services/react_agent.py)
- [`backend/app/services/react_repair.py`](../backend/app/services/react_repair.py)
- [`resources/repair_policy.yaml`](../resources/repair_policy.yaml)

需要特别注意：

> 当前单轮数据主路线并不等于“自由 ReAct”。
>
> 它借鉴了“观察结果后再判断”的思想，但执行范围被 QuerySpec 和代码契约限制得更死。

原因是数据库查询不能像改代码一样随意试。查询范围、路线、时间、枚举和单位
一旦被模型擅自改写，就可能出现“SQL 能跑，但答案已经错了”的情况。

## 三、一条问题从进入到回答，具体经过什么

### 第 1 步：识别这是哪一类问题

系统先判断用户是在问：

- 数据查询：data
- 分析判断：analysis
- 复合问题：composite
- 知识问答
- 图片问题

如果当前开启单轮编译器，数据、分析和复合问题优先进入单轮查询服务。

这一步只决定“走哪条路”，还不生成 SQL。

### 第 2 步：读取数据库真实字段目录

系统会读取当前数据库真实存在的表和列，形成“物理字段目录”。

这一步非常重要，因为它和另外两种字段信息不同：

| 名称 | 白话解释 | 能不能证明数据库里真有这个字段 |
|---|---|---|
| 字段触达集合 | 根据问题猜“可能相关”的字段 | 不能 |
| 完整物理字段目录 | 数据库真实存在的表和列 | 能 |
| 输出投影 | 最终要展示给用户的字段 | 不能代替物理目录 |

因此模型可以“想到一个字段”，但不能因为想到了就直接拿来写 SQL。

相关代码：

- [`backend/app/query/fields.py`](../backend/app/query/fields.py)
- [`backend/app/services/schema_catalog.py`](../backend/app/services/schema_catalog.py)

### 第 3 步：让 LLM 生成结构化查询单 QuerySpec

LLM 不直接返回 SQL，而是返回一份结构化查询单。

可以把 QuerySpec 理解成一张标准点菜单：

```json
{
  "subject": "disease",
  "view": "distribution",
  "metrics": ["count"],
  "dimensions": ["route_name", "problem_type_name"],
  "filters": [
    {
      "field": "problem_type_name",
      "op": "=",
      "raw_value": "裂缝"
    }
  ],
  "output_projection": ["route_name", "problem_type_name", "count"]
}
```

用白话解释：

- `subject=disease`：问的是病害。
- `view=distribution`：结果要分组展示。
- `metrics=count`：算数量。
- `dimensions=route_name, problem_type_name`：按路线、病害类型分组。
- `filters=裂缝`：只统计裂缝类病害。
- `output_projection`：最终给用户展示哪些列。

QuerySpec 的核心字段定义在
[`backend/app/query/contracts.py`](../backend/app/query/contracts.py)。

### 第 4 步：把自然语言值变成数据库能执行的值

用户说“长沙－芷江高速公路”，数据库里可能存的是路线 ID；
用户说“下行”，数据库里可能存的是代码 `2`；
用户说“裂缝”，数据库中可能是“横向裂缝、纵向裂缝、网状裂缝”。

所以系统要做值解析：

| 用户表达 | 解析后存储值 | 展示值 |
|---|---|---|
| 长沙－芷江高速公路 | 真实路线 ID | 长沙－芷江高速公路 |
| 下行 | `2` | 下行 |
| 裂缝 | 横向裂缝、纵向裂缝、网状裂缝 | 裂缝 |
| XJJL202611040003 | `patrol.task_number` 过滤条件 | XJJL202611040003 |

这里有四条硬规则：

1. 存储值用于 SQL，展示值用于回答用户。
2. 模型推断值不能直接进 SQL，必须经过字典、业务规则或受控解析。
3. 路线名不能直接冒充路线 ID。
4. 编号要按前缀判断所属字段，例如 XJJL 是巡检任务号。

相关代码：

- [`backend/app/query/values.py`](../backend/app/query/values.py)
- [`resources/query_identifiers.yaml`](../resources/query_identifiers.yaml)

例如：

- `XJJL...` -> 巡检任务号 `task_number`
- `XCBH...` -> 巡查编号 `patrol_number`
- `BPLHZD...`、`KZXB...` -> 病害编号 `problem_number`

### 第 5 步：代码补充和归一化查询契约

LLM 第一次规划不一定完美，所以代码还会做确定性修正。

例如：

- `group`、`aggregate`、`summary` 统一成 `distribution`。
- 指标对象 `{"field":"task_id","agg":"count"}` 统一成 `count`。
- 设备字段 `device/device_id` 统一成 `equipment_id`。
- 桩号分段别名统一成 `pile_segment_500m`。
- “按路线统计数量、面积、平均面积并关联路线长度”会固定到同一个分组视图。
- 密度、趋势、严重程度和 AI 可靠性问题会补 `post_calc` 节点。

这不是针对某一道题的字符串特判，而是在规范查询结构。

### 第 5.1 步：问题优化不能自由发明字段

问题优化器会先拿到三类不同信息：

- 用户原话命中的字段。
- 当前主表真实存在的物理列。
- 最终允许展示的业务字段。

预规划补全必须输出：

```json
{
  "required_dimensions": ["路线", "病害数量", "总面积", "病害密度"],
  "required_fields": ["route_name", "area"],
  "required_metrics": ["count", "total_area", "density"],
  "include_detail": false
}
```

代码只信任 `required_fields` 和 `required_metrics`：

- `required_fields` 必须逐字等于真实列名。
- `required_metrics` 必须来自受控指标集合。
- 模型自由写的 `question` 只作为说明，不会原样成为规划输入。
- 最终规划问题由“用户原话 + 已验证字段 + 已批准指标”组装。

例如用户问“养护资金应该投哪条路”，优化器不能编造 PCI、预算金额或风险评分。
如果数据库里没有这些字段，只能写成：

```text
按路线名称（route_name）比较病害数量、总面积和病害密度，
并明确说明这些指标只能代表病害压力，不能等同于真实资金成本。
```

另一个规则是：用户明确限定时间、路线、病害类型或任务，并问“检出多少/查出多少”时，
优化要求应同时包含：

1. 精确总数。
2. 完全相同的过滤范围内，最多 500 条可核对明细。
3. 命中总数、展示数量和是否截断。

### 第 6 步：把问题拆成计划节点

一个用户问题可以变成多个内部节点。

例如：

> 裂缝集中在哪几个月？哪些路？这些路的病害密度怎么样？

可以拆成：

```text
q1_month_dist：按月份统计裂缝数量
q2_route_dist：按路线统计裂缝数量和路线长度
q3_density_calc：基于 q2 计算密度
```

节点之间的依赖关系会明确写出来：

```text
q3_density_calc.depends_on = [q2_route_dist]
```

如果 `q2` 失败，系统不会偷偷拿空数据继续算 `q3`，而是阻断 `q3`
并说明原因。

### 第 7 步：执行前检查最小契约

在真正生成 SQL 前，系统检查：

- 使用的字段是否真的存在。
- 来源是否可追溯。
- 指标和分组是否冲突。
- 是否把“路线长度”这种指标误当成分组字段。
- 查询顺序、限制和输出字段是否合理。
- 依赖节点是否有可执行输入绑定。

如果不合格，就不允许生成 SQL。

### 第 8 步：独立审计查询计划

系统会让另一个“审计角色”检查计划是否完整回答用户问题。

但审计模型不能随意改计划。它只能提出有限的结构补丁，例如：

- 增加分组维度。
- 修正指标。
- 修正视图类型。
- 调整排序或限制。

代码还会执行第二道检查：

1. 补丁应用后重新校验 QuerySpec。
2. 再尝试受控编译。
3. 如果原计划能编译、审计补丁反而不能编译，就拒绝补丁。
4. 如果审计只是重复抱怨但没有提出有效变化，不阻断合法计划。

这样可避免“审计器把本来正确的 SQL 改坏”。

### 第 9 步：模板匹配和确认卡

系统会从以下来源寻找模板：

- 内置代码模板
- 预置查询模板
- 自动沉淀模板
- 已验证示例

模板不能只看“看起来相似”。必须同时满足：

- 主体一致。
- 视图一致。
- 指标完整覆盖。
- 分组完整覆盖。
- 过滤条件完整覆盖。
- 没有偷偷加入用户没要求的条件。
- 引用字段真实存在。

只要命中模板，就展示确认卡，不自动执行。

确认卡会告诉用户：

- 模板来自哪里。
- 查询范围是什么。
- 参数值是什么。
- 固定条件是什么。
- 输出指标和分组是什么。

用户确认后，系统会重新检查：

- 查询单有没有变化。
- 模板版本有没有变化。
- 字段目录有没有变化。
- 用户修改的参数是否合法。

### 第 10 步：编译 SQL

目前有几种编译方式：

1. 用户确认过的模板 SQL。
2. QuerySpec 受控编译器。
3. Wren 把受控 MDL-SQL 编译为物理 SQL。
4. 在受控编译器不能覆盖时，再走原有的 Wren/LLM SQL 路径。

重要原则：

> SQL 不是 QuerySpec 之外的第二套事实来源。
>
> SQL 必须服从已经验证过的 QuerySpec。

### 第 11 步：执行并记录 Observation

SQL 执行后，系统不会只拿一段文字。

它会记录：

- 是否成功。
- 使用的引擎。
- 实际 SQL。
- 返回字段。
- 返回行数。
- 前几行样本。
- 是否截断。
- 精确总数（如果单独执行了计数 SQL）。
- 运行错误原文。
- SQL 指纹。

这个对象叫 `ExecutionObservation`，白话就是“这次工具到底发生了什么”的观察记录。

### 第 12 步：确定性验收

当前单轮主路径会先做确定性验收，例如：

- SQL 是否成功执行。
- 空结果是否属于明确有过滤范围的合法空结果。
- 明细是否缺少展示字段。
- 分组标签是否全是 NULL。
- 应该有数值指标时是否没有数值。
- 命中总数大于实际取回行数时，是否正确标记截断。

这些检查不依赖 LLM 主观判断。

注意：验收器里虽然保留了“语义验收”和“表达验收”的接口，但当前
单轮执行主路径主要启用的是确定性事实验收；独立 LLM 语义检查目前主要发生在
执行前的计划审计阶段。

相关代码：

- [`backend/app/query/verifier.py`](../backend/app/query/verifier.py)

### 第 13 步：后置计算

数据库擅长查询，但不一定适合直接给出所有业务结论。

以下情况会使用 `post_calc`：

- 两天结果对比。
- 数量和面积计算密度。
- 趋势是增加还是减少。
- 每条路线的主要病害类型。
- 低置信度占比。
- 多组数据比较。

后置计算只能消费已经验收通过的完整前序结果，不能重新自由查库。

如果后置计算没有可用结果，会返回明确的 `post_calc_empty` 失败，不会把
“数据不足，算不出来”这种非空文字当成成功。

### 第 14 步：生成最终回答

最终回答只拼接终端节点。

例如：

```text
查询 1：按月统计裂缝
查询 2：按路线统计裂缝和路线长度
计算 3：计算密度
```

用户最终主要看到“计算 3”的结论，但查询 1 和查询 2 仍保留在结果工作台里。

每个结果段现在都有：

- `title`：例如“q2. 按路线统计裂缝”
- `question`：完整子问题
- `tool`：使用的是什么类型的工具
- `sql`
- `columns`
- `preview_rows`
- `status`

这样控制台可以知道每一段结果对应哪个子问题。

### 第 14.1 步：数据题和分析题使用不同回答方式

聊天区不再承担“复制整张表格”的职责。

- `data` 数据题：
  - 单值统计（多少处、总面积）可以正常给数字。
  - 分组、Top、趋势和明细结果只说明“共多少行，请到结果工作台查看”。
  - 明细题说明命中总数和是否截断，但不把前 10 行或前 80 行贴进聊天。

- `analysis` 分析题：
  - 查询结果仍然完整保存在工作台。
  - 系统自动追加一个终止 `post_calc` 分析节点。
  - 分析节点不会读取整张表，而是先把结果压缩成：
    - 总行数；
    - 分组字段；
    - 每个数值指标的最小值、最大值及对应对象。
  - 模型只基于这份紧凑证据回答，必须先给结论，再说明判断维度和关键数字。
  - 如果结论使用代理指标，例如用病害数量、面积、长度推断“健康状况”，必须明确说明
    这不是 PCI、RQI、预算成本或正式综合评分。

这种拆分解决了两个不同问题：

1. 数据题避免聊天区与工作台重复展示大表。
2. 分析题避免把几十、几百行原文塞进模型上下文，只输入真正有判断价值的证据。

## 四、系统出错时现在怎么处理

### 情况 1：第一次 QuerySpec 解析失败

系统会把失败原因反馈给规划模型，最多再试一次。

### 情况 2：审计器提出错误修改

代码会重新校验补丁：

- 非法字段不进入 SQL。
- 非法分组不进入 SQL。
- 会把可编译原计划改坏的补丁被拒绝。
- 空补丁不会无限循环。

### 情况 3：SQL 运行报错

数据库错误原文进入 `ExecutionObservation.runtime_error`，
验收状态变为失败，不会把错误文本包装成查询答案。

### 情况 4：SQL 能运行，但结果结构不对

例如：

- 分组题没有分组标签。
- 数量题没有数值。
- 明细题没有展示字段。

确定性验收会返回 `repairable`，并给出失败码。

### 情况 5：空结果

系统区分两种情况：

- 有明确过滤范围、条件合理的空结果：可以回答“没有匹配记录”。
- 本应有数据的空结果：判为异常，不猜测成业务为零。

### 情况 6：上游节点失败

依赖它的下游步骤直接阻断，不生成假综合分析。

最终会告诉用户：

- 哪一步失败。
- 依赖哪一步。
- 为什么不能继续。

### 情况 7：问题超出数据能力

系统不会猜。

当前已有明确能力限制：

- 车道分布数据尚未更新。
- 管养单位只有 ID，没有可验证的名称和台账关联。

系统会返回 `unsupported` 和具体原因。

能力限制配置在
[`resources/query_capabilities.yaml`](../resources/query_capabilities.yaml)。

### 情况 8：问题口径本身不清楚

例如“最近两次巡检”没有说明：

- 是最近两个全局任务？
- 还是每条路线各取最近两次？
- 时间范围是什么？

系统会返回 `ambiguous`，要求补充口径，而不是自己猜。

## 五、旧 ReAct 修复器是怎么做的

旧 ReAct 修复器采用有限动作，不让 LLM 无限自由发挥。

可用失败策略写在：

[`resources/repair_policy.yaml`](../resources/repair_policy.yaml)

例如：

| 失败类型 | 可以尝试什么 | 最大轮数 |
|---|---|---:|
| SQL 运行错误 | 重试 query_data | 2 |
| SQL 语义不匹配 | 重试 query_data | 2 |
| 结果结构不匹配 | query_data 或 check_coverage | 2 |
| 意外空结果 | check_coverage、query_data、询问用户 | 1 |
| 后置计算为空 | post_calc 或询问用户 | 2 |
| 计划契约错误 | 只能询问用户 | 0 |

Controller 接收：

- 当前步骤。
- 冻结后的子问题。
- Observation。
- FailureEvidence。
- 允许使用的工具。
- 之前失败的尝试。
- 之前调用过的工具和参数。
- 覆盖率与链式依赖值。

代码还会检查：

- 工具名是否在允许列表。
- 必填参数是否齐全。
- 是否重复调用完全相同的工具和参数。
- 是否超过最大修复轮数。
- 新结果是否和旧失败完全相同。

如果连续两次结果一样且仍失败，系统会停止，并说明可能是生成器或验收器本身有问题。

## 六、当前纠错能力哪些已经完成，哪些还没完成

| 能力 | 当前状态 |
|---|---|
| QuerySpec 执行前校验 | 已完成 |
| 字段来源追溯 | 已完成 |
| 存储值与展示值分离 | 已完成 |
| 路线、病害类型、枚举解析 | 已完成 |
| 审计补丁归一与编译门禁 | 已完成 |
| SQL 执行事实 Observation | 已完成 |
| 确定性结果验收 | 已完成 |
| 后置计算失败 fail-closed | 已完成 |
| 下游依赖阻断 | 已完成 |
| 旧 ReAct 有界工具修复 | 已完成 |
| 当前单轮编译器的“执行后自动修复” | 尚未完全接通 |

最后一条要重点理解：

> 当前单轮主路径在执行后能发现 `repairable`，但不会自动把这些失败全部交给
> 旧 ReAct controller 再修一轮。它目前更多是结构化返回失败，而不是完整自动闭环。

因此，当前更准确的描述是：

- 规划阶段：有自动反馈和有限修复。
- 执行阶段：有事实验收和明确失败。
- 执行后修复：旧 ReAct 有机制，但尚未和单轮编译器完全统一。

下一步最有价值的改造，是把：

```text
VerificationReport(status=repairable, allowed_actions=...)
```

接到：

```text
FailureEvidence
  -> repair_policy 筛选候选工具
  -> Controller 选择 RepairPatch
  -> 代码校验工具与参数
  -> 只修失败节点
  -> 重新执行
  -> 对比修复前后 Observation
```

但必须继续保留以下护栏：

- 不修改用户问题。
- 不扩大查询范围。
- 不删除用户过滤条件。
- 不猜业务口径。
- 不无限重试。
- 修复失败时回退。
- 依赖节点失败时阻断下游。

## 七、没有给每个工具单独配一个 LLM

当前设计不建议“每个工具一个 LLM”。

更省事也更可靠的方式是：

```text
所有工具统一返回结构化 Observation
  -> 一个 Controller 根据失败码选择工具
  -> 代码检查工具名和参数
```

不同角色可以使用不同模型，例如：

- `semantic_model`：理解问题和生成 QuerySpec。
- `verify_model`：审计查询计划。
- `sql_model`：生成或修复 SQL。
- `controller_model`：选择下一步工具动作。

这不是“每个工具一个模型”，而是“不同职责可以选不同模型”。

## 十、开发修改时必须先回答的四句话

以后改数据流时，先写清楚：

1. 这个对象的输入是什么？
2. 谁生产它？
3. 谁消费它？
4. 消费方依赖的最小不变量是什么？

例如 `QuerySpec`：

1. 输入：用户问题、字段目录、值和来源。
2. 生产者：问题分析和值解析。
3. 消费者：校验器、模板解析器、SQL 编译器和执行器。
4. 最小不变量：字段真实存在、过滤值有来源、指标和分组不冲突、
   用户范围不可静默改变。

如果这四个问题答不清，就不要先改代码。

## 十二、最后的结论

巡检智能体目前已经有一条比较清楚的受控数据链路：

```text
先理解
-> 再结构化
-> 再解析真实值
-> 再校验
-> 再编译
-> 再执行
-> 再看真实结果
-> 再回答
```

它不是“模型直接写 SQL 后靠运气”，也不是“每个工具单独配一个 LLM”。

它现在能较好地处理明确的巡检数据库问题，也能对超能力、歧义和依赖失败
给出具体原因。

距离完整闭环还差最后一段工程连接：

> 把执行后的 `repairable` 失败证据，安全地接入有界 ReAct controller，
> 只修失败节点，并比较修复前后结果。

这一步完成后，系统才会更接近“发现错误后自己尝试纠正，纠不正就明确停下”的目标。
